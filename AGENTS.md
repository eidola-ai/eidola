# AGENTS.md

Guidance for AI coding agents working in this repository.

## Server Architecture

The server is an OpenAI-compatible proxy that translates requests to upstream AI providers. It includes a billing system with anonymous credentials for privacy-preserving usage tracking.

**Current upstream:** Tinfoil (inference.tinfoil.sh) — OpenAI-compatible, all models run in confidential enclaves (AMD SEV-SNP / Intel TDX / NVIDIA CC)

**Database:** PostgreSQL 17+ (see `crates/eidola-server/schema/schema.sql`)

**Deployment:** Tinfoil Containers — all services run inside confidential enclaves (AMD SEV-SNP). The Tinfoil shim handles TLS termination with attestation-bearing certificates; the server runs plain HTTP behind it.

**Build & Verify Artifacts:** `artifacts.yml` contains four jobs — `oci` (ubuntu-24.04), `apple` (self-hosted Mac: Nix-based macOS universal-binary builds for both the cli and the GUI .app bundle), `linux-gui` (ubuntu-24.04: the Nix-built Linux GUI — a glibc dynamic binary; see `flake.nix`'s `eidola-gui-linux` for why it can't be a static-musl StageX artifact like the server/cli), and `artifact-manifest` (ubuntu-24.04). The cheap cargo gates (cargo fmt/clippy/test, OpenAPI freshness) live in a separate `rust-checks.yml` workflow that runs on PRs to both `next` and `main` (and on push to `next`/`main`/tags — the `next`/`main` pushes save the cargo cache that `next` PRs restore from); `artifacts.yml` is intentionally scoped to `main` only so the expensive chain never runs on `next` PRs. The `oci` job mirrors the local `just update-manifest` flow end-to-end in five inline phases — (1) bake server + postgres, (2) stamp the freshly-built server digest into the workspace `tinfoil-config.yml`, (3) recompute the enclave from the stamped config and overwrite `releases/trust/server-enclave.json`, (4) bake cli (its build context COPYs the just-overwritten `server-enclave.json`), (5) emit the stamped config, recomputed enclave, and combined OCI partial as job outputs — and verifies the built OCI subset against the committed `artifact-manifest.json`. `apple` and `linux-gui` both `needs: oci`, install the stamped config + recomputed enclave from `oci`'s outputs, then build their Nix desktop artifacts against that same trust root. `artifact-manifest` gates on `oci`, `apple`, and `linux-gui`; it materializes all three `oci` outputs into the workspace, runs `verify-full` (which recomputes the enclave from the stamped config and compares the composed manifest to the committed `artifact-manifest.json`), and on PRs posts a REQUEST_CHANGES review whose body contains all three files (`tinfoil-config.yml`, `releases/trust/server-enclave.json`, `artifact-manifest.json`) verbatim. Because the Build & Verify Artifacts workflow executes the entire generation chain (server build → stamp → measure → cli build → compose) inside one job rather than verifying disjoint partials, those three suggestions are guaranteed internally consistent: committing them as-is reproduces a fixed point of the chain. `oci` runs first; `apple` follows `oci` so it sees the same trust root the linux cli was built against. The `oci` job's StageX builds share a per-image registry layer cache (`ghcr.io/<owner>/eidola-buildcache:{server,cli,postgres}`, wired in `docker-bake.hcl` via the `CACHE_REGISTRY` bake variable that both the dev and `ci-*` variant of each image inherit): the promotion PR builds the dev targets and the post-merge push to `main` builds the `ci-*` targets, sharing one ref per image so the push reuses the PR's freshly-built layers instead of recompiling (a registry cache is used rather than `type=gha` because the Actions cache ACL isolates a PR's cache from the `main` branch run, and to keep the large build cache out of the 10 GB Actions budget). `CACHE_REGISTRY` is empty for `v*` release tags (so attested artifacts compile clean) and for any PR into `main` that isn't this repo's `next` → `main` promotion PR — so only trusted producers (pushes and the promotion PR) ever read or write the shared cache, and a stray or fork PR to `main` builds fully cold. `cache-to` also carries `ignore-error` so a credential-less run degrades to a cold build instead of failing. Cache poisoning is bounded regardless: every cached build's digest is verified against the committed manifest, and releases ignore the cache entirely. A separate `cla.yml` workflow verifies that every PR author/committer email is covered by the current `CLA-INDIVIDUAL.md` or `CLA-CORPORATE.md` hash recorded in `CLA-SIGNERS.txt`. A separate `tinfoil-build.yml` workflow runs on `v*` tags and has two responsibilities: (1) generate `tinfoil-deployment.json` from `artifact-manifest.json`, attest it to Sigstore via `actions/attest`, and create the GitHub release — this is the artifact Tinfoil's verifier chain consumes; (2) sign `artifact-manifest.json` with `cosign sign-blob` (Fulcio keyless via the workflow's OIDC identity) and upload the manifest + its Sigstore bundle as release assets for the client's self-update verifier. The filename `tinfoil-build.yml` is mandated by Tinfoil's closed-source deployment system — do not rename. The release is intentionally not marked `latest` here; the release engineer's tooling does that once their human attestation is signed and uploaded.

**Branch flow (`next` → `main`):** `next` is the integration trunk; `main` is the verified, promotion-only branch. Feature/dependency PRs target `next` (Dependabot is pointed at `next`). The cheap workflows (`rust-checks`, `cla`, `dependency-review`, `codeql`, `zizmor`, `pinact`) run on `next` PRs. `rust-checks` always *triggers* but path-scopes its work: a first `scope` step diffs the PR and runs the cargo gates (fmt/clippy/test/openapi) only when a file that can affect them changed (any `*.rs`/`Cargo.*`/`rust-toolchain.toml`/`.cargo/*` plus everything under `crates/` and `releases/` — schema SQL, build-script trust/measurement JSON, fixtures, `openapi.json`), the markdown lint only when markdown or `.rumdl.toml` changed, and neither for PRs that touch only docs/scripts/compose/Containerfiles/other-CI. Editing `rust-checks.yml` itself forces a full run (it defines both gates and their scoping, so a workflow-only change must re-exercise both). The job itself always runs and reports (only the expensive *steps* are gated, so the required check never hangs pending), unrecognized files force a full run, and a full run is unconditional on every push and on **any** PR into `main` — so the `next` → `main` promotion always gets the real gate. The expensive `Build & Verify Artifacts` (`artifacts.yml`) chain does **not** run on `next` PRs — it is scoped to `main` (push + the `next` → `main` promotion PR) and is the required gate for `main`. The merge gate for `main` is the `Guard` job in `artifacts.yml`: on a PR into `main` it passes only for this repo's `next` → `main` promotion PR (and for `push`/`v*` events), and fails fast for any other head — short-circuiting the expensive OCI + macOS chain (the downstream jobs `needs: guard`, so they skip) rather than building it. Crucially it is **never green for an invalid head** — it's red on the `opened`/`synchronize` run, or never runs (leaving the required check pending) if the base is flipped in via an `edited` event, which `artifacts.yml` doesn't listen to — so there is no success status an attacker could reuse by flipping the base back to `main` (the reuse concern from PR #151). `enforce-branching-strategy.yml`'s `retarget` job is now a convenience only: it moves any non-promotion PR's base onto `next` and returns success (failing only if it cannot retarget); it no longer manufactures a blocking red, because the gate lives in `artifacts.yml`. Promotion: open a `next` → `main` PR (this is the collaborative surface where the full `Build & Verify Artifacts` chain runs and integration/nondeterminism debugging happens); when it's approved and green, a maintainer comments `/promote` and `promote.yml` fast-forwards `main` to the validated `next` head SHA. The push is non-force, so GitHub rejects anything that isn't a fast-forward — `main` stays a strict ancestor of `next` (`main ⊆ next`), SHA-identical to a real `next` commit, and lands exactly what the Build & Verify Artifacts chain validated. `branch-guard.yml` continuously asserts `main ⊆ next` (on push to either branch + every 6h) as a backstop against out-of-band divergence. **GitHub config (not in-repo):** on `main`, require the `Build & Verify Artifacts` checks — the `Guard` job in particular **must** be required, since it's the only one that stays red (or pending) for an invalid head; the other jobs report *skipped* there, which GitHub treats as satisfied, and the `Retarget onto next` job is **not** required — restrict direct pushes to the promotion GitHub App as the sole ruleset bypass actor (its App ID + private key live only on the `main`-restricted `promote` Environment, so only `promote.yml` running from `main` can mint a token — see `docs/contributing/promotion-security.md`), and block force-pushes; on `next`, block force-pushes and deletions; `Build & Verify Artifacts` is required for `main` but **not** for `next`. The single human rule: never commit to `main` directly — everything funnels through `next`.

**Image tagging:** `main` (rolling, updated on each promotion to `main`), `v*` (immutable release tags), `sha-<short>` (per-commit). No `:latest`. Images published to `ghcr.io/<owner>/eidola-server`, `ghcr.io/<owner>/eidola-cli`, and `ghcr.io/<owner>/eidola-postgres`. A separate `ghcr.io/<owner>/eidola-buildcache` package (tags `server`/`cli`/`postgres`, each a single mutable ref overwritten in place) holds the BuildKit layer cache — not a release artifact.

**Key design decisions:**

- Axum-based HTTP server with typed routing, extractors, and `utoipa-axum` OpenAPI integration
- Plain HTTP internally; TLS terminated by Tinfoil Container shim with attestation-bearing certificates (attestation hash + HPKE key encoded in SANs, issued by public CA)
- Tinfoil attestation verification via `tinfoil-verifier` crate — verifies SEV-SNP hardware attestation per-connection, caching verified fingerprints for fast reconnections; handles load-balanced deployments
- Deterministic enclave measurement via `measure-enclave` crate — pre-computes SEV-SNP and TDX measurements from source, written to `releases/trust/server-enclave.json` (the cli build input) and recorded in `artifact-manifest.json` (the signed deployment record)
- Statically linked musl binaries for Linux deployment
- StageX-based OCI images (reproducible, `FROM scratch`, runs as non-root)
- Request-based (no sessions/caching in the proxy layer)
- Account auth (Basic + Argon2id) via `BasicAuth` extractor, chat completions auth via `TokenAuth` extractor
- **Tool calling is wire-level pass-through** (`types.rs`): the request accepts `tools` / `tool_choice`, an assistant `tool_calls` with nullable `content`, and `role: "tool"` + `tool_call_id`; the response and SSE chunk relay `message.tool_calls` / `delta.tool_calls` and `finish_reason: "tool_calls"`. The server **never executes a tool** — the loop lives in app-core. Each of those new fields is a raw `serde_json::Value`, deliberately: the proxy re-serializes everything it parses (`.json(request)` upstream, `to_string(&chunk)` downstream), so a narrower struct would silently drop provider extension fields and the streaming-only `index` framing key the client's accumulator needs — the same defect the `reasoning_content` / `reasoning` fields were added to fix. `content` is `Option` but has **no** `skip_serializing_if`, so a client's deliberate `"content": null` survives to the upstream chat template. The strict `deny_unknown_fields` on the request stays: the server remains the authority on what it accepts, and the opacity is scoped to the *inside* of the tool payloads. No "supports tools" capability bit — an upstream 4xx pass-through stays the honest v1 error
- Stripe integration via thin `reqwest` wrapper (no `async-stripe` dependency)

**API endpoints:** Defined in `crates/eidola-server/openapi.json` (generated from utoipa annotations — see Conventions).

**Environment variables:**

- `TINFOIL_API_KEY` (required) - Tinfoil inference API key
- `DATABASE_URL` (required) - PostgreSQL connection string
- `DATABASE_PASSWORD` (optional) - PostgreSQL password; in production with an external database, inject this as a Tinfoil secret instead of embedding it in `DATABASE_URL`
- `DATABASE_SSL_CERT` (optional) - PEM-encoded root CA certificate for PostgreSQL TLS verification; public material, so this can be passed as a normal env var
- `CREDENTIAL_MASTER_KEY` (required) - Hex-encoded 32-byte AES-256 key for encrypting issuer private keys at rest in Postgres; in production, injected as a Tinfoil secret; in local dev, use the all-zeros key from `.env.example`
- `BIND_ADDR` (default: `127.0.0.1:8443`) - Address to bind (HTTP); Containerfile overrides to `0.0.0.0:8080`
- `STRIPE_API_KEY` (optional) - Stripe secret key; account billing endpoints return 503 without it
- `STRIPE_WEBHOOK_SECRET` (optional) - Stripe webhook signing secret; webhook endpoint returns 503 without it
- `TINFOIL_BASE_URL` (optional) - Override the default Tinfoil API base URL (`https://inference.tinfoil.sh/v1`)
- `TINFOIL_REPO` (optional) - Source repository the upstream enclave is attested against via the Tinfoil ATC `POST /attestation` endpoint (default: `tinfoilsh/confidential-model-router`); must match the GitHub repo whose signed measurements correspond to the running enclave. Also the repo whose latest release the runtime measurement resolver (`src/upstream_trust`) verifies
- `TINFOIL_MEASUREMENT_REFRESH_SECS` (optional) - How often the `src/upstream_trust` resolver re-checks Tinfoil's latest release for a new enclave measurement (default: `600`, 10 minutes). Bounds the race window between Tinfoil cutting a release and deploying the new enclave; 10m stays well within GitHub's unauthenticated rate limit (~3 calls/refresh)
- `TINFOIL_PRICING_OVERRIDES` (optional) - JSON object overriding per-model pricing; e.g. `{"kimi-k2-6":{"input":2.0,"output":6.0}}`. Token-based models accept `input`/`output` ($/M tokens); per-request models accept `request` ($/request). See `backend.rs` `MODEL_CATALOG` for defaults
- `PRICING_MARKUP` (optional) - Pricing markup factor applied to all model prices (default: `1.5`). The server refuses to start if it is below 1.5 — the pricing contract's safe cost factor (`eidola-common`'s `SAFE_COST_FACTOR_NUM/DEN = 3/2`): the contract charges prompt bytes at 1/1.5 of their worst-case token count, so a lower markup would sell tokens below cost (see `validate_pricing_markup` in `backend.rs`)
- `TERMS_FEED_BASE_URL` (optional) - Base URL of the published website (production: `https://www.eidola.ai`) the terms-feed poller (`src/terms_feed.rs`) polls for the current legal-document versions. Each document's exact source bytes are published by the site builder at `/terms/source.md` and `/privacy/source.md` (alongside the rendered pages, whose head carries `eidola:version` / `eidola:source-sha256` meta tags and a visible version line); the server computes the SHA-256 itself, parses the front-matter `version`, and records observed versions in the shared `required_document` table — **append-only**, one row per (document, version) with its `first_required_at`; the gate enforces the highest recorded version per document, so monotonicity is structural (a stale CDN edge or website outage can only pause advancement, never regress it) and the table is a permanent audit trail of which version was enforced when. A same-version observation with different bytes is detected as a versioning-contract violation and refused (warn from the poller; fatal for an explicit env seed). Because the table is shared, one instance observing a new version converges every instance's gate immediately. This decouples terms updates from the (measured, per-release-immutable) server config — legal documents outlive any client/server release. CI enforces the ordering contract: any PR changing a legal document's bytes must increment its front-matter version by exactly 1 (`scripts/check-legal-doc-versions.sh`, wired into `rust-checks.yml`)
- `TERMS_REFRESH_SECS` (optional) - Terms-feed poll interval (default `600`)
- `TERMS_OF_SERVICE_SHA256` / `PRIVACY_POLICY_SHA256` (+ optional `_VERSION`, default 1, and `_URL`) (optional) - Static dev/test pins seeded once at startup through the same monotonic upsert (e.g. `shasum -a 256 www/pages/terms.md`). Neither feed nor pins set = gate disabled. **Gate semantics:** checkout and credential issuance require the account's max accepted version per document to be `>=` the required version (HTTP 428 `terms_acceptance_required`; clients fetch `GET /v1/terms`, record acceptance via `POST /v1/account/terms`, stored append-only in `account_acceptance` with the version stamped — so accepting a newer version satisfies an instance whose view briefly lags). `AppCore::account_create` records acceptance automatically after the UI captures consent (GUI onboarding checkbox; CLI `account create --accept-terms`); `AppError::TermsAcceptanceRequired` routes re-acceptance (`eidola account accept-terms` / `AppCore::accept_current_terms`)
- `OTEL_EXPORTER_OTLP_ENDPOINT` (optional) - OTLP endpoint; enables OpenTelemetry export of traces, metrics, and logs when set (e.g. `https://otlp-gateway-prod-us-central-0.grafana.net/otlp`)
- `OTEL_EXPORTER_OTLP_HEADERS` (optional) - OTLP auth headers (e.g. `Authorization=Basic <base64(instanceID:apiKey)>`)
- `OTEL_SERVICE_NAME` (optional) - Override service name in telemetry (default: `eidola-server`)

**Observability:**

The server uses OpenTelemetry to ship traces, metrics, and logs directly to Grafana Cloud (or any OTLP endpoint) via HTTP/protobuf. Enabled when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; otherwise only stdout logging. Telemetry respects the privacy boundary between the "linked" account layer and the "unlinked" anonymous service layer: chat completion spans/metrics contain only model name, token counts, status, and latency — never account IDs, credential data, or message content. Account layer spans may include account_id. The middleware (`middleware.rs`) classifies routes and creates per-request spans; metric instruments are defined in `telemetry.rs`.

**Tinfoil Containers / TEE integration:**

The server runs as plain HTTP inside a Tinfoil Container. The Tinfoil shim handles TLS termination externally, generating attestation-bearing certificates (attestation hash and HPKE key encoded in SANs, issued by a public CA via ACME). The shim serves `/.well-known/tinfoil-attestation` for client-side verification.

The credential master key (`CREDENTIAL_MASTER_KEY`, AES-256, hex-encoded) encrypts issuer private keys at rest in Postgres. In production, it is injected as a Tinfoil secret (environment variable, encrypted, only accessible inside the enclave). In local dev, use the all-zeros dev key from `.env.example`. The key must remain stable across upgrades so encrypted issuer keys in the database remain accessible.

When using an external PostgreSQL instance until Tinfoil supports persistent disks, keep connection metadata in `DATABASE_URL`, inject `DATABASE_PASSWORD` as a Tinfoil secret, and pass the PEM-encoded server root CA in `DATABASE_SSL_CERT` if the server certificate does not chain to a default WebPKI root. The root CA certificate is public material; only the password and private keys need to be kept secret.

The container has access to `/dev/sev-guest` (via the undocumented `devices` field in `tinfoil-config.yml`) for requesting SEV-SNP attestation reports. The pre-generated attestation document and TLS key material are also available at `/tinfoil/` inside the container.

**Enclave measurement (`crates/measure-enclave/`):**

The `measure-enclave` binary pre-computes the hardware attestation measurements that a legitimate Tinfoil Container will produce. The measurement is a deterministic function of:

1. OVMF firmware (pinned from `tinfoilsh/edk2`)
2. CVM kernel + initrd (versioned from `tinfoilsh/cvmimage`, hash-verified)
3. Kernel command line (embeds dm-verity roothash + SHA-256 of `tinfoil-config.yml`)
4. vCPU count and type

The binary uses `sev` (with `crypto_nossl` feature ��� pure Rust, no OpenSSL) for SEV-SNP launch digest computation and `tdx-measure` for TDX RTMR1/RTMR2 runtime measurements. Both work natively on macOS. Output JSON matches the Tinfoil deployment manifest predicate (`snp-tdx-multiplatform/v1`): `{snp_measurement, tdx_measurement: {rtmr1, rtmr2}, cmdline}`.

`tinfoil-config.yml` is the Tinfoil Container configuration. It references container images by digest (from `artifact-manifest.json`), declares `_HASH` env vars for measured secrets (Argon2id hashes generated via `cargo run -p hash-secret`), and specifies CVM resources (cpus, memory). The SHA-256 of this file is embedded in the kernel command line and bound into the enclave measurement, so any change to the config produces a different measurement.

The measurement flow: `source → deterministic OCI build → server digest → tinfoil-config.yml (with digest) → cmdline (with config hash) → measurement → releases/trust/server-enclave.json → cli build embeds it as its trust root → cli OCI/macOS narHash → artifact-manifest.json`. The `server-enclave.json` step exists to break the otherwise-circular self-reference that would happen if the cli build COPYed the manifest containing its own digest; isolating the enclave fields lets the cli build see a stable input even as the manifest is regenerated. All values are committed and verified by CI. CVM artifacts are cached locally at `~/.cache/eidola/cvm/`. Pass `--verify-attestations` to `artifact-manifest.sh` (used by CI) to additionally verify CVM manifest provenance via Sigstore (`gh attestation verify --deny-self-hosted-runners`); this fails hard if verification fails.

**Tinfoil attestation verification (`crates/tinfoil-verifier/`):**

The `tinfoil-verifier` crate exposes `attesting_client()`, which returns a `reqwest::Client` that re-verifies enclave attestation on every new TCP+TLS handshake. There is no startup bootstrap and no verified-fingerprint cache: `attesting_client()` performs no network I/O, the *first* real request through the returned client is also the first attestation, and every subsequent new TLS handshake re-attests independently. Policy changes (TCB floor, allowed measurements) take effect on the next handshake without a process restart. Callers that want fail-fast-at-startup semantics issue a single throwaway request through the client immediately after construction and treat its outcome as the readiness check (the eidola server does this by hitting `{base}/models`).

**Per-handshake flow.** The client's connector layer (`AttestingConnectorLayer`) wraps reqwest's inner connector. On every new TCP+TLS handshake, after the TLS layer completes, the connector generates a fresh random 32-byte nonce and issues an inline HTTP/1.1 `GET /.well-known/tinfoil-attestation?nonce=<hex>` over the **same** connection (using `httparse` for response parsing and `hyper-util::TokioIo` to bridge `hyper::rt::Read/Write` to `tokio::io::AsyncRead/Write`). The enclave responds with a *freshly collected* hardware report whose `REPORT_DATA` is `SHA-256(tls_key_fp ‖ hpke_key ‖ nonce ‖ gpu_hash ‖ nvswitch_hash)` (the inference router is CPU-only, so the GPU/NVSwitch hashes are empty), plus the PEM TLS leaf cert and an ECDSA signature over the document. The fresh document does **not** carry the VCEK, so the connector consults Tinfoil's ATC service (`POST /attestation` with `{enclaveUrl, repo}`) over a side channel to backfill it (the shim mock self-carries the VCEK, so tests need no ATC). It then verifies, in `bundle.rs` + `attesting_client.rs`: the echoed nonce equals the one sent (freshness); `report_data.tls_key_fp == sha256(SPKI(peer_cert))` and the document's embedded cert matches the peer cert; the document's ECDSA signature against that cert (P-384 in production, P-256 for the mock, both SHA-256-prehash — signature reconstructed by blanking the `signature` value in the raw served bytes so unknown fields survive); the AMD VCEK chain (ARK → ASK → VCEK, RSA-PSS SHA-384); SEV-SNP / TDX report signature; TCB policy (bl≥0x07, snp≥0x0e, ucode≥0x48); measurement against the caller-supplied allowed set (the client's pinned server-enclave measurement on the client→server path; the runtime-resolved set from `src/upstream_trust` on the server→upstream path); and finally that the hardware report's `REPORT_DATA` equals the recomputed `SHA-256(tls_key_fp ‖ hpke_key ‖ nonce ‖ …)` — which authenticates every claimed `report_data` field against the AMD/Intel signature. Only if all of that passes is the connection yielded to hyper for the real request. ALPN is pinned to `http/1.1` so the inline attestation request and the subsequent application request share one HTTP lifecycle. Subsequent HTTP requests on a pooled keepalive connection do not re-trigger the connector and inherit the binding to the TLS key (and the nonce-bound report) that was attested when the connection was first established. The same-connection guarantee makes this safe behind load balancers: whatever backend the LB routes you to is the backend you attest.

The enclave's own fresh `/.well-known/tinfoil-attestation?nonce=<hex>` document is the source of truth. ATC is the single fallback target for the chain itself (today: the VCEK), and the legacy static `?v=3` / v2 attestation documents are no longer used. The verifier *does* fetch AMD KDS CRLs in production mode for revocation checks, but this is gated on `trusted_ark_der.is_none()` — test deployments that supply a custom mock ARK skip CRL fetching entirely (AMD KDS has no revocation entries for mock chips and the CRL signature would fail to verify against the mock ARK anyway). `trusted_ark_der` / `trusted_ask_der` only feed the SEV-SNP attestation chain verifier; they are **not** added to any TLS root store.

TLS trust roots are supplied by the caller via `AttestingClientConfig::tls_roots` and used for **all** outbound HTTPS the verifier performs (attested inference endpoint, ATC fallback, AMD KDS CRL fetches). The verifier crate intentionally does not depend on `webpki-roots` or `rustls-native-certs` so each consumer can pick the source that fits its environment without dragging the wrong dep into the others: the server runs `FROM scratch` inside an enclave with no system trust store and supplies `webpki-roots`; the CLI and macOS app supply `rustls-native-certs` so developers can install local dev CAs (e.g. the tinfoil shim mock's `tls-ca.pem`) in their OS keychain. The verifier crate's pure-Rust deps (`sev`, `x509-cert`, `der`, `tower`, `hyper`, `hyper-util`, `httparse`) — no OpenSSL.

The per-handshake nonce guarantees *freshness* — the enclave folds our random nonce into a freshly collected `REPORT_DATA`, so a stale or captured document can't be replayed against a different nonce, and we know a live, genuine CC machine currently holds the cert key. It does **not** by itself defeat exfiltration of the TLS key: the report binds the long-term TLS *key* (cert SPKI), not the live TLS *session*, so an attacker holding the stolen key could actively MITM (deriving the session keys despite TLS 1.3 forward secrecy) and relay a fresh nonce-bound report from the enclave's public endpoint, passing every client check. Closing that requires channel binding (a TLS-session/exporter value in `report_data`); today it still rests on the key staying sealed in the enclave. Separately, the fresh document is not yet *fully* self-contained — it omits the VCEK — so the ATC fallback remains in place; once Tinfoil folds the VCEK into the document, that path will go cold and can be removed entirely.

**Upstream measurement resolution (`crates/eidola-server/src/upstream_trust/`):**

`inference.tinfoil.sh` is a *router* enclave that reverse-proxies to separate per-model GPU enclaves; the router trusts those downstream enclaves via "latest Sigstore-signed release of the repo" (see `tinfoilsh/tinfoil-go` / `tinfoil-rs`). Statically pinning the router measurement and gating changes on a human PR therefore bought little rigor over Tinfoil's own model, while causing a fail-closed outage every time Tinfoil shipped a router release (their sign→deploy lag is ~zero; ours was hours). So the server resolves the allowed router measurement **at runtime** to match Tinfoil's actual trust level, while still running our *superior* per-handshake, nonce-fresh `tinfoil-verifier` attestation on every request. **This subsystem is temporary — it is deleted when we self-host inference, at which point `main.rs` hands `attesting_client` a statically pinned measurement set instead.** It never touches `tinfoil-verifier` (whose connector bakes the allowed set in at construction): to change the set we rebuild the `reqwest::Client` and hot-swap it via `arc_swap::ArcSwap` (the backend reads the current client lock-free on each request; `main.rs` supplies an `AttestingClientFactory` closure that owns all the `attesting_client` wiring so this module stays telemetry-free). `sigstore.rs` verifies the GitHub artifact attestation (a Sigstore **`dsse`/in-toto** bundle, distinct from the `hashedrekord` blob bundle the client updater's `eidola-app-core::updater::ci_sigstore` verifies) end-to-end: Fulcio chain + identity (GitHub Actions OIDC issuer + repo **and exact tag** — tighter than Tinfoil's own clients, which accept any `@refs/tags/*`), DSSE PAE signature, Rekor SET + RFC 6962 inclusion proof, and `sha256(tinfoil-deployment.json) == subject digest`; the measurement is read from the signed `snp-tdx-multiplatform/v1` predicate. Its crypto primitives were ported from app-core's `ci_sigstore` (same pinned `releases/trust/sigstore-trusted-root.json`, the sole `releases/` input the server `build.rs` embeds), so the SCT + Rekor-checkpoint gaps in `docs/gaps.md` apply identically. **There is no static fallback:** bootstrap resolves + verifies the latest release synchronously as the readiness gate, and if that fails (GitHub unreachable, bad signature, …) the server refuses to start. Bootstrap's *initial* allowed set is already a rolling window of 2 — the latest release plus the immediately-previous **published** (non-draft, non-prerelease) release — so a cold start that lands mid rolling-deploy still attests the still-draining previous router enclave answering the readiness probe instead of aborting; that previous entry is best-effort (a missing/unverifiable previous release logs a warning and boots with latest-only, unlike the fatal latest). The periodic refresh (`TINFOIL_MEASUREMENT_REFRESH_SECS`, default 10m — the window that bounds the release→deploy race) keeps a rolling window of the last two measurements (so in-flight rolling deploys still attest) and never clears or widens trust on error: a new measurement is adopted only after its replacement client builds successfully; a resolve/build failure keeps the current client (requests fail closed until the next successful tick). The old static-pin path — `releases/trust/tinfoil-enclaves.json` + the `update-measurements.yml` review-PR workflow — was **removed** in favor of this. End-to-end regression: `crates/eidola-server/tests/upstream_trust_verify.rs` verifies a real captured `v0.0.115` release bundle against the embedded trust root and asserts the tag/repo/digest/tamper rejections.

**Compose files:**

- `compose.yaml` — local development. Two supported workflows share one file:
  - **Full container stack** (`just dev`, → `scripts/dev.sh --container`) — postgres + server + shim + stripe-cli all in containers, detached. Server image is rebuilt each invocation.
  - **Host mode** (`just services`, → `scripts/dev.sh --host`) — postgres + shim + stripe-cli in containers, with `SHIM_UPSTREAM_URL=http://host.docker.internal:8080` so the shim forwards to a cargo-built server running on the host.   - Both modes share `scripts/dev.sh`. Both build only the images they need, idempotently apply `schema.sql` to postgres, capture the Stripe webhook secret if `STRIPE_API_KEY` is set (otherwise skip stripe-cli), and start everything detached. `just down` tears down both modes.

## App Core Architecture

The GUI app and CLI share a common Rust core (`crates/eidola-app-core/`) consumed as a normal library — no FFI layer. All business logic — config management, local database, HTTP client construction, account operations, wallet/credential management, and chat inference — lives in the core crate. Consumers construct an `AppCore` and call its methods directly. **`AppCore::new` is fallible** (`Result<AppCore, AppError>`): it takes the process-lifetime exclusive advisory lock on the local database before building anything else, so a second opener is refused with `AppError::DatabaseInUse` (see Local Database & Migrations). **State & async doctrine:** how state is owned, shared, mutated, and synchronized (domain stores, the invalidation bus, task ownership, atomicity rules) is governed by `crates/eidola-gui/STATE.md`. All state-touching code follows it; do not invent parallel patterns.

**Core crate modules:**

- `backends.rs` — **the backend registry: where an ask can be routed.** A `backend` DB table holds the configured inference destinations, four kinds today: `eidola` (the confidential service — singleton; a backend row describes how to reach and trust that backend, so the eidola row now owns the whole connection + trust bundle — `base_url`, `trusted_measurements` (JSON overrides), and `hardware_root_ca` / `hardware_intermediate_ca` (PEM ARK/ASK overrides) — each NULL by default = the embedded trust-root pin; `update_backend` accepts exactly this bundle for the eidola row and nothing else), `local` (Eidola-managed on-device models — singleton), `openai` (any user-configured OpenAI-compatible server: base_url + optional api_key), and `llamacpp` (a user-owned llama.cpp install: Eidola scans its `models_dir` and starts/stops engines but never downloads/deletes the files — the "one-click self-hosted stack" integration). The anticipated self-hosted-device routing (an Eidola on your Mac serving your phone) is one future kind + one transport arm; the registry, references, and forensics already fit it. Singletons are enforced by a partial unique index on `kind` and seeded idempotently at every DB open (`ensure_default_backends`); they can be **disabled** but not removed — disabling `eidola` is exactly the "no account, on-device only" configuration. External backends soft-remove (`removed_at`) so the forensic `request.backend_id` reference stays resolvable forever; re-adding the same id revives the row. **Model references** follow one rule uniformly: `<model>@<backend-id>` (split at the last `@`; ids validated to `[a-z0-9-]{1,32}`, so Ollama `name:tag` and HF `org/model` ids survive), with a single sugar — `eidola`, being the default backend, may be written bare, and `qualified_model_id` keeps the bare form canonical so the common case reads clean everywhere. Every other backend's models are spelled qualified, the local singleton included (`<slug>@local`); `parse_model_ref` / `qualified_model_id` are the unit-tested pair. Because "OpenAI-compatible" does **not** guarantee `GET /v1/models` (Azure's deployment model, scoped gateway keys, partial proxy listings), each backend carries nullable `model_overrides` (a pinned JSON list that replaces the fetch); `backend_models(id)` resolves per kind — eidola → the attested catalog, openai → overrides-or-listing (a failed listing suggests pinning), local/llamacpp → the loaded engines. **`llamacpp` backends carry two extra columns** (both llamacpp-only, refused on openai and the singletons in `add_backend`/`update_backend`): `engine_path` (an explicit `llama-server` path — `None` = discover it) and `auto_start` (default `1`; when `0` a request may **not** start an engine on demand — it must be pre-loaded explicitly). `update_backend` does **per-kind field validation** (not a blanket singleton refusal): the `eidola` row accepts only its connection + trust bundle (base_url / trusted_measurements / hardware CAs, each clearable back to NULL = pin) and refuses external fields; `local` refuses everything (built in, enable/disable only); `openai` / `llamacpp` accept their own fields but never the trust bundle. The eidola-trust setters (`AppCore::set_base_url` / `clear_base_url_override` / `set_hardware_root_ca` / `set_hardware_intermediate_ca` / `trust_measurement` / `untrust_measurement`) are thin async wrappers over `update_backend` on the eidola row — they validate then write and emit `Change::Backends` (not `Change::Config`). CRUD (`add_backend` / `set_backend_enabled` / `update_backend` / `remove_backend`) emits `Change::Backends`. Tests: `tests/backends.rs` (registry lifecycle + revive incl. the engine-path/auto-start columns, the eidola connection+trust bundle round-trip + per-kind update validation, and — via the chat harness — openai turns sending `Bearer` with no credential/Wallet and recording `backend_id`, llamacpp turns keyed per backend, the auto-start-off request refusal, disabled/unknown refusals).
- `changes.rs` — `Change` enum (eleven domain variants: `Config`, `Account`, `Wallet`, `SpaceIndex`, `Space(SpaceId)`, `Record`, `UpdateState`, `LocalModels`, `Backends`, `Participants`, `Templates`). `Participants` = a space's per-space participant membership/config changed; `Templates` = the space-template registry changed — deliberately split (not one `Change::Participants`) because they map to two GUI surfaces (the per-space Participants view vs. the Space Templates settings pane), keeping the STATE.md 1:1 variant↔store rule and avoiding cross-invalidation. `ChangeSource` trait (the narrow seam for the v2 Turso-CDC extension point), and `BroadcastSource` (the v1 in-process `tokio::sync::broadcast` implementation). `AppCore::subscribe_changes()` hands out independent receivers; lagged receivers get `RecvError::Lagged` and should refresh everything. Bus capacity is 256. Every durable commit in `lib.rs` emits after the write succeeds. `chat`/`chat_stream` **defer the new-space row insert until after `ensure_spendable_credential` succeeds**, so a typed onboarding failure (`NoAccount` / `InsufficientBalance`) on a blank window leaves zero durable trace (no orphaned empty space) and emits nothing. Once the space is persisted, partial-failure paths emit on every explicit error exit, mirroring the success path: `Change::Wallet` immediately after `insert_pre_credential_refund` (credential enters `spending` state) regardless of outcome; the network-error arms, the `Ok`-arm response read/parse/`flush_attestations` failures, the body-refund `process_refund` failure, and `chat_stream`'s mid-SSE read failure all emit `Change::Space(id)` plus `Change::SpaceIndex` when `is_new_space || auto_titled` (emitting the committed user turn so other windows see it; `Change::Wallet` too if a successor credential was recovered); the non-2xx error return additionally emits `Change::Record` (the request row is committed there). Plain `?` on the intervening local-DB action/content inserts stays unemitted (internal-consistency failures). Every error returned after the space is persisted is wrapped as `AppError::ChatFailed { space_id }` (Display defers to source) so a blank GUI `Space` can adopt its id on failure; pre-space errors stay unwrapped, and `AppError::root()` unwraps it for variant-routing callers (CLI hints, GUI onboarding). Pure errors with no durable side effects never emit. The full exit-point → emissions table lives in `tests/bus.rs`'s doc module.
- `lib.rs` — `AppCore` struct, all high-level operations (account create/show/allocate, post, chat, wallet, spaces: list/archive/rename), DTO record types (`ConfigState`, `ChatResult`, `PostResult`, `PriceInfo`, `SpaceInfo`, etc.), internal helpers (ACT token serialization, attestation flushing, HTTP response handling). `list_spaces(include_archived)` returns title + first-message snippet + last-activity + message-count signals for the GUI's Library; `chat`/`chat_stream`/`post` auto-title an untitled space on its first exchange from the first line of the user's prompt (local heuristic — markdown markers stripped, ~64-char word-boundary truncation; no model call). **`post(space_id, prompt)` is the save side of the save-vs-request split (wave 5):** it persists a `user_input` action (a fresh gen-0 item) with **no credential, no account, no HTTP** — creating the space if new, auto-titling, linking a `reply` antecedent edge to the prior tail — and emits `Change::Space(id)` plus `Change::SpaceIndex` (new space or auto-title). It is the pure-save path that `chat`/`chat_stream` (post + request a response) will be recomposed on top of; until then the two coexist. Tested directly in `tests/bus.rs` (no HTTP), not the chat harness. **`edit_post(action_id, new_prompt)` is the human side of collaborative editing:** it appends a new `user_input` **generation** of the action's item (append-only — supersedes the item's current tip, replicates its `reply` edge, prior generation preserved), so `item_current` resolves to the edit; emits `Change::Space(id)` + `Change::SpaceIndex`. `list_spaces`/`first_user_text` count and snippet **current generations of post-bearing types only** (a tip filter on `supersedes_action_id` plus the `POST_ACTION_TYPES_SQL` filter), so editing replaces in the default view without inflating `message_count` — and neither a tool trace, a decision, nor a branch summary can move a space's message count or its last-activity in the Library. **`run_turn(space_id, model, target_action_id, mode, budget)` is the request side** (extracted from `chat`): it provisions a credential, assembles the turn's **upstream thread** as context (`get_upstream_context`: the target's reply ancestry, each hop resolved to the antecedent item's current tip, so an edited upstream post contributes its latest text — `Reply` walks from the post being answered *inclusive* (the whole conversation on a linear thread; exactly the target's branch on a branched space — sibling branches never leak), `Revise` (regenerate) walks from the generation being replaced *exclusive* (the model never sees its own prior output or anything downstream)) — calls the model, and persists the inference + request rows + refund. Regressions: `regenerate_sends_only_upstream_context_at_current_versions` and `branch_reply_sends_only_its_branch_context` in `tests/chat_path.rs` (the harness mock records chat request bodies via `chat_bodies()`). `chat` is now `post` + `run_turn(Reply)` (post-first: a funding failure leaves the saved post and carries its id; onboarding gates at *request* time, not the keystroke), and **`regenerate(action_id, model)`** = `run_turn(tip, Revise)` — a new agent generation of an inference's item. `budget` caps the charge of **each round** (see the tool loop below). `run_turn` emits `Wallet` at spend start, `Space`+`Record` on non-2xx, `Space`+`Wallet`+`Record` on success — never `SpaceIndex` (`post` owns new/auto-title). `chat_stream` is likewise `post` + `run_turn_stream(Reply)` (the streaming twin; same attach-by-mode, budget, and emission contract, differing only in SSE transport and refund-via-recovery-endpoint). **The twins share one implementation**: `prepare_turn` builds a `TurnPrep` (attested client, attach plan, upstream context, charge estimate + budget gate — the prompt side of the estimate is the shared `eidola-common::chargeable_prompt_tokens` contract (content-byte term at the safe cost factor + per-message + per-request constants), not bytes-as-tokens; the server recomputes the identical function of the identical `messages` array as its pre-flight minimum and clamps its charged prompt tokens to it, so the hold covers the charge by construction — spend proof + pending refund, ACT header — the `Wallet` "spending" emission happens here) and `TurnPrep::persist_turn` writes the durable rows (inference action + reply edge, context assembly, content blocks, request row); the transports are thin — one reads a JSON body (inline-refund fast path), the other pumps SSE (recovery-endpoint refund). Emissions stay at the transport exit points, so the `tests/bus.rs` exit-point table is unchanged. **A turn is a bounded agentic loop (task 20).** Each iteration is one HTTP request: the model either answers — the loop ends, persisting the `inference` — or returns `tool_calls`, in which case the round is persisted, executed, appended to the in-flight messages array, and the next round runs. `MAX_TURN_ROUNDS = 8` caps the **model requests** per turn (a small fixed constant, not a setting — it bounds one ask's worst-case spend); reaching it with the model still asking for tools ends the turn with `AppError::ToolLoop` rather than passing a tool request off as an answer, and the capped round's tools are deliberately *not* executed since their results could never be sent. A turn whose registry is empty can only ever take one iteration, so the single-inference path is untouched — see `tools.rs` for why an empty registry also sends byte-identical requests. **Wire format:** `tools` carries the OpenAI function schema; `tool_calls` are read off the blocking body's `message` and assembled *incrementally* from SSE `delta.tool_calls` (per-`index` accumulators concatenating id/name/arguments — nothing is guaranteed to arrive whole). The follow-up request replays the model's call objects **verbatim** (ids and provider fields intact) in an `assistant` message with `content: null` — for a streamed call that means the accumulator also carries every *non-canonical* key through reassembly (shallow, **last-non-null-wins**: unknown fields have no fragmentation contract, so concatenating them would corrupt structured values, and later deltas refine earlier state; the streaming-only `index` framing key is deliberately not replayed), so a backend whose extension metadata is load-bearing cannot work when blocking and break when streaming, followed by one `tool` message per result — **raw, with no `#<handle> · <label>` header**, because a tool result is neither a post nor authored by a participant. **Per-round holds, not hold reuse:** the ACT protocol consumes a credential per request (the spend proof is bound to that credential and that charge, and the server answers with the refund that mints its successor), so each round re-estimates over the *grown* messages array, re-checks `budget`, and acquires its own hold under `spend_gate` (`Inner::acquire_spend` / `begin_next_round`; `Change::Wallet` therefore fires per round, and `ChatResult::credits_charged` is the sum). The estimate reads exactly what the server reads — literally the same function, `eidola_common::prompt_charge` (the server converts its parsed request with `to_value` and calls it too), which since task 25 counts **tool bytes too**: every message's `content` string, every `tool_calls` entry's **compact JSON serialization** (the whole entry — id, `type` and provider extensions included, because the whole entry is what gets forwarded and the proxy cannot know which fields a given chat template renders into the prompt; Mistral's renders the call id, Qwen's and Llama's don't), and every advertised tool schema's compact JSON serialization (once per request, since the chat template re-injects it every round). The one thing still charged per *message* rather than per byte is message-level scalar framing (`name`, a tool result's `tool_call_id`), which the per-message allowance exists to cover — an allowance that is per message and so could never stretch over the *N* call objects one assistant message may carry. All of it lands in the byte term at the same safe cost factor — tool bytes are prompt bytes, and `actual_tokens ≤ bytes` holds for JSON as it does for prose. Counting only `content` would have let a tool loop's largest inputs ride upstream uncharged (a margin leak, never a safety one — the hold and the charge cap are the same function). `TurnPrep.tool_schemas` is serialized once at preparation so every round's estimate and every round's wire request read one array, exactly as they both read `messages`; hold ≥ charge stays structural. Regression: `a_tool_rounds_hold_covers_the_tool_bytes_it_sends` in `tests/chat_path.rs`, which recomputes the contract over each recorded body. **Persistence:** a round writes a `tool_call` action (the agent's own; `tool_use` blocks carrying `tool_name` + `tool_call_id` + the raw argument string, plus any `thinking`/`text` the model produced alongside, and that round's own tokens/credits) and a `tool_result` action (`tool_result` blocks keyed by call id; no model, no credits — tools run locally; status `error` if any tool failed). Both chain off **the post the turn answers**, never off the inference: a cap or budget exit ends the turn without an inference, so hanging the trace there would leave it parentless — and because `get_space_tree` keeps only post-bearing types the whole chain collapses out of the render for free while staying fully resolvable in the Record (raw request rows per round + the new actions). `db::last_action_in_space` was narrowed to the last **post** for the same reason: a turn that ended on a trace must not become the next post's reply parent. `persist_turn` records the round actions in the context assembly alongside `context_rows`, since they *were* fed upstream. **Traces are first-person (task 33)** — a turn's tool rounds are replayed to the **responding participant** on later turns and to nobody else. `render_messages` still renders only `user_input`/`inference` as posts; `prepare_turn` splices each spine inference's own rounds in *before* it, in the wire shape the model produced them in (`assistant` with `content: null` + `tool_calls`, then one `tool` message per result — both built by the same `assistant_tool_call_message`/`tool_result_message` helpers the live loop uses, so the live bytes and the replayed bytes cannot drift). **Attribution is the context assembly**, not the reply DAG: a trace chain hangs off the *post* the turn answered (a capped or declined turn writes no inference), so nothing structural links it to the answer it produced — but the writing turn recorded exactly its own rounds as fed context (`db::assembly_trace_blocks`), which makes the rule *you see the traces of the turns whose posts you can see*, branch-correct and regeneration-correct by construction (a `Revise` turn's excluded generation takes its working with it; a sibling branch's rounds and an abandoned chain never appear). A turn also records the traces it **replayed** in its own assembly (the record stays literally "the actions fed into this inference"), and the reader dedupes first-on-spine-wins, so each trace renders once, at its producing turn. **The assembly is the ordered composition of the prompt**, not a re-derivation of it: `prepare_turn` builds `TurnPrep.context_action_ids` in the *same* loop that builds `messages`, so a replayed trace occupies the position it occupied on the wire (between the post it answered and the answer it produced) and only the current turn's own rounds land at the end — where the loop appended them live (`the_context_assembly_records_the_order_the_messages_were_sent_in`). **No sliding-window elision:** traces stay inline until an explicit future consolidation event, so a participant's trunk is append-only — every request's `messages` array is a literal prefix of every later one's (`a_participants_trunk_is_append_only_across_turns`). One fidelity limit: only `(id, name, arguments)` are persisted, so a replayed call is reconstructed canonically and a provider's extension fields on a call do not outlive their turn. Trace bytes ride the messages array, so `eidola_common::prompt_charge` charges a replayed `tool_calls` entry exactly as it charges a live one — the same walk over the same bytes on both sides (`a_later_turns_hold_covers_the_traces_it_replays`). **Model mistakes are results, not failures:** an unknown tool name, unparseable `arguments`, or a tool's own error become the tool *result* text the model reads next round; only a *structurally* unusable value fails the turn, recording the raw exchange with no action attached: a call with no id / no function name (nothing that can be executed or written as a `tool_use` block), or a `tool_calls` that is present and non-null but **not an array** (blocking body or SSE delta alike — reading that as "no tools requested" would persist an often-empty completion as a successful answer, exactly the silent truncation the loop promises never to do). An absent or explicitly `null` `tool_calls` *is* "no tools" and stays an ordinary completion — plenty of OpenAI-compatible servers always emit the key. Streaming: tool rounds are **invisible pauses** in v1 — no new `ChatStreamEvent` variants; content deltas are still forwarded verbatim in every round, so a model that narrates before calling a tool has that narration streamed and then persisted on the round's `tool_call` action (where the render collapses it), the one visible seam of the simplification. **Reasoning ("thinking") is durable.** Both transports recover the model's own reasoning from the same two provider extensions — streaming `delta.reasoning_content` / `delta.reasoning`, blocking `message.reasoning_content` / `.reasoning` — and `persist_turn` writes it as a `thinking` content block at ordinal 0, ahead of the answer's `text` block (the schema already allowed the type; **no schema change, no migration**). It rides the success arm's existing emissions, so no new exit point. It is **never replayed upstream and never part of the readable transcript**: both context queries (`db::get_upstream_context`, `db::get_space_actions_for_context`) join content blocks `ON … AND cb.block_type = 'text'`, so a persisted thinking block is a render-side disclosure only. This is what makes the GUI's "Thinking…" disclosure survive a reload instead of dying with the process. Regressions in `tests/chat_path.rs`: `streamed_reasoning_persists_as_a_thinking_block`, `blocking_reasoning_persists_as_a_thinking_block`, `persisted_thinking_is_not_sent_upstream`. **Thread map + navigation tools (task 21).** `get_upstream_context` scopes a turn to its own branch, so without help a model cannot know sibling branches exist at all. `prepare_turn` therefore builds a per-turn `ThreadSnapshot` — from exactly the GUI's materials (`db::get_space_tree_data` → `build_post_tree`), so threading and post rendering each keep **one** path — and appends a **trailing thread map**: a `<thread-map>` block naming every fork point on the turn's spine and the branches hanging off it, anchored to task-19 handles (`at #h12`), each entry `#handle · author · posts · last activity — opening line` (the opening reuses `derive_space_title`, the auto-title heuristic; relative times are coarse buckets so the bytes don't churn per second), plus — for a branch the **responding participant** has posted in — a `· you participated, N posts` segment (task 33), the retrieval prompt that gets a model to descend at all; it is per-participant, which costs nothing because the map is the volatile tail (`db::post_authors` → `ThreadSnapshot::with_viewer`). **No silent stripping**: every branch gets a line — a dormant one just gets a terse one. **Placement is pinned *after* the post being answered**, with an explicit `Respond to #h.` pointer. That keeps exactly *one* message volatile, so a re-request of the same turn (retry, regenerate, a second agent answering the same post in a fan-out) reuses the whole prefix **including** the post it answers; placing the map before the final post would make positions N-1 and N both recompute for no gain. **Cache doctrine holds structurally**: branch metadata is never interleaved inline at fork points and the map's *data* never enters the system prompt — the only system-message change is the static `THREAD_MAP_NOTE` (plus `THREAD_MAP_TOOLS_NOTE` when the tools attach), which flips **once** per space, at the moment it first branches (the same moment the tool schemas would appear), and is byte-stable thereafter. A **linear space is byte-identical to pre-task-21**: no map, no note, no `tools` field. A `Revise` turn's map excludes the generation being replaced *and its whole subtree*, mirroring exactly what `get_upstream_context` withholds from the messages — otherwise regeneration would hand the model its own prior output through the side door. Header-**in-content**, deliberately not the OpenAI `name` field, whose support across open-model chat templates is inconsistent to absent. **Handles are derived, never persisted:** `post_handle(item_id)` (pub) is the first 7 characters of lowercase RFC 4648 base32 over `SHA-256(item_id)` — the **item** id, so a handle survives edits/regenerations, and *hashed* rather than a prefix because item ids are UUIDv7 and lead with a 48-bit timestamp (prefixes of near-in-time posts would collide pathologically). Handle → id resolution is the caller's lookup over its own space. **Strip-on-receipt:** models mimic visible scaffolding, so `strip_leading_header` removes a leading header-shaped line from model output before it is persisted or returned in `ChatResult` (both transports, at persist time — streamed deltas still reach the caller verbatim, so the emission contract is untouched), and `HEADER_PROTOCOL_NOTE` — appended to the turn's system message, likewise unpersisted — instructs against emitting one. Headers ride inside the messages array, so `chargeable_prompt_tokens` covers them on both sides by construction; `prepare_turn`'s system-prompt prepend, embed expansion, and charge-estimate ordering are unchanged. `db::SpaceActionRow` carries the `item_id` / `participant_id` / effective `participant_label` (`COALESCE(space_participant.override_label, participant.label)`) this needs — no schema change. **Labels are one-line by construction.** Because the label lands in a wire-protocol header whose one-line shape is a promise, a label with an embedded line break would inject a second paragraph attributed to that author (prompt injection through a rename). Both layers enforce it: `validate_label` (trim, refuse empty, refuse any control character or U+2028/U+2029) gates **every** label write seam — `add_space_participant`, `update_space_participant`, `set_space_participant_override`'s `override_label` (which keeps the `NULL` = inherit / `''` = override-to-empty distinction, so only the control-char half applies), and `validate_template_participants` (so `create_template` / `update_template`) — and `message_header` sanitizes offending characters to spaces anyway, so a future write path cannot silently break the invariant. Regressions: `participant_labels_reject_control_characters` (`tests/bus.rs`, per entry point + no emission) and `hostile_label_cannot_break_the_one_line_header` / `validate_label_rejects_control_characters` (`lib.rs`). `ChatResult` gained `response_action_id` (the persisted **inference** id) so a caller can re-plan a cascade on the fresh post, and `declined: Option<DeclineOutcome>` (`Some` when the turn ended at the agent-side decline checkpoint — see `decline.rs`). The two are mutually exclusive by construction: a decline wrote no post, so `response_action_id` is `None` and the `decision` action id rides in `DeclineOutcome { reason, action_id }` instead. That split is the point — a caller that re-planned on a `decision` would cascade off something nobody can reply to, and keeping the id out of the post-shaped field makes the mistake unrepresentable rather than merely documented. **`submit(text, space_id, reply_to)`** = `post` + **`plan_notifications(space_id, post_action_id)`**, returning `SubmitResult { post, plan: NotificationPlan }`. The post is committed and emitted *before* planning, so the may-decline router's call never delays the writer seeing their own words and can never fail a submit. **`AppCore::plan_notifications` is plan + router refinement, and it is the only planning entry point that drives turns** — refinement is deliberately not opt-in, because a cascade re-plans on every hop and one unrefined hop would notify agents the router already filtered out (see `router.rs`). The unrefined computation is a **pure read** (commits nothing, emits nothing, no HTTP) reachable only through the deliberately-named `AppCore::mechanical_notification_plan`, for tests and inspection: it computes the notify set over the space's participants (owned ∪ referenced, effective config) — `all` → always; `human` → only when the post's author is human; `explicit` → never (only an explicit ask reaches them) — excluding the post's author and model-less agents, each planned turn carrying `cascade_depth`. It also refuses to plan off a **non-post** action (`decision` / `tool_call` / `tool_result` → zero turns), the defense-in-depth half of the decline split above. Turn driving stays caller-driven: run one **`respond_stream_as(space_id, participant_id, target_action_id, sender)`** (the participant-aware analog of `respond_stream`, an explicit ask that bypasses the cascade guard) per `PlannedTurn`, then re-plan on each resulting post to continue the cascade. `chat`/`chat_stream` remain thin (`post` + drive one `TurnSelector::Model` turn), unchanged for the single-participant common case. **Space consistency is an app-layer guard** (`Inner::require_action_in_space`): the schema does not constrain an `action_antecedent` edge (or a turn's `target_action_id`) to one space, so a mismatched (space, action) pair could otherwise splice space A's thread into space B — send A's ancestry to B's agent, persist a cross-space reply edge. `plan_notifications` (post↔space), `prepare_turn` (target↔space, both modes — so `respond_stream_as`/`respond_stream` and the same-space `chat`/`regenerate`), and `post` (`reply_to`↔space, validated before any write) all reject a foreign/missing action with a typed `AppError::NotConfigured`; a participant from another space is already rejected by `resolve_explicit_participant` (non-member). **Cascade guard (data-derived, no schema state):** `db::agent_cascade_depth` counts consecutive agent-authored posts in a post's reply ancestry back to the last human post (branch-scoped, item-tip-resolved like `get_upstream_context`; authorship is stable across an item's generations so edits/regenerations don't shift it); at the space's `cascade_limit` (default 4) `plan_notifications` returns `NotificationPlan::Paused { depth, limit }` instead of turns. Explicit asks (`respond_stream` / `respond_stream_as`) never consult the guard, so they always run — that is the "explicit asks reset depth". **ACT provisioning queue:** `Inner::spend_gate` (a `tokio::sync::Mutex`) serializes the credential acquire → spend-proof → flip-to-`spending` step in `prepare_turn` across concurrent turns, so two turns fired at once (a fan-out) never both spend one credential — the first flips it to `spending` inside the lock; the second (entering next) finds another active credential, auto-allocates fresh from balance (the pool), or **waits bounded for an in-flight refund** (a sibling turn's recovery writes a successor) with a typed `AppError::ProvisioningTimeout` on the deadline (routes through the recoverable-failure UI). The wait fires **only when a mid-spend credential whose own face value covers the charge exists** — a refund recovers a successor worth at most the original credential and never tops up account balance, so a smaller in-flight credential can never fund the turn; that case returns `InsufficientBalance` immediately rather than burning the wait. Because `find_spendable_credential` (active) and `list_spending_credentials` (spending) are separate reads, a sibling credential can **settle** in the gap between them — and settlement is a *single atomic insert* that flips the original out of `spending` and makes an active successor queryable **at the same instant** (`credential_lifecycle` derives `spending`→`spent` from successor existence), so mid-settle both reads are stale (successor not yet active, original no longer spending). Before any terminal verdict the loop re-reads `find_spendable_credential` once, which observes that successor. This makes the verdict **instant-consistent**: the whole function runs under `spend_gate`, and the only active→`spending` flip (`insert_pre_credential_refund`) is under that same gate, so no credential can enter `spending` while it runs — the covering-`spending` set only *shrinks* (via settlement) between the two reads. A terminal `InsufficientBalance`/`ProvisioningTimeout` therefore reflects a real instant with no covering credential in any state; it **cannot** be a false negative from an in-flight sibling refund (the property the original split-read bug violated). It does **not** guarantee observing funding that arrives *after* that instant from a write exogenous to the turn machinery (an explicit `account_allocate`, startup recovery) — an ordinary post-read TOCTOU no non-serialized check can exclude, which the recoverable error routes the caller to retry to resolve. turso is single-writer, so `db::connect` also sets `PRAGMA busy_timeout` — concurrent per-turn row writes block-and-retry instead of erroring. Engine lifecycle: `load_local_model` (accepting `<slug>@<backend>`, or a bare slug as the managed-store shorthand) spawns `llama-server -m <gguf> --port <free> --alias <selection-id> -c 8192 --jinja --no-webui -ngl 999` — the alias equals the selectable id, so a chat body's `model` matches verbatim — polls `/health` until ready (5-min budget, stderr tail captured into failure messages), and a supervisor task owns the child — unload signals it, an unexpected exit records the failure and emits, `kill_on_drop` reaps children if the process dies. **`AppCore::shutdown_engines` is the quit-path teardown** (the GUI's `on_app_quit` hook): synchronous, infallible, and reading the **engine registry** — it drains the map and signals every supervisor, touching no filesystem and no database. It exists separately from a loop over `local_models_state` precisely because that snapshot is *reconstructed by scanning* the model directories and consults the engine map only to decorate a `.gguf` it already found, so an engine whose backing file was renamed or deleted mid-session is missing from it while its subprocess is alive — and on macOS, where `[NSApp terminate:]` ends in `exit()` and `kill_on_drop` never fires, that means orphaning it to launchd. Draining is not enough on its own: a load already past its `await`s (backend lookup, port pick, `fs::metadata`) but not yet at `reserve_engine` would resume *after* the drain saw an empty registry and spawn into a process about to `exit()`, so the drain also sets a one-way **shutdown latch** — inside the same `engines` lock the reservation takes, and checked inside the reservation's own critical section, so there is no instant where the registry is empty and loads are still permitted (the authority is checked at the write point, never captured — the same cure as the derive-scope-in-insert idiom). A quit is also the one time **nothing** on this path emits: the process is exiting, so nobody can render it, and the GUI's app-lifetime bus bridge is a foreground task gpui keeps driving through its bounded shutdown block *after* `App::shutdown` sets `quitting` — a dispatch would reach `LocalModelsStore::refresh` → `cx.spawn` → gpui's "Can't spawn on main thread after on_app_quit" panic, turning a clean quit into a crash on exactly the machines that have an engine loaded. Silencing the drain alone was not enough, because the drain only *signals*: `supervise_engine` emits from its own shutdown arms right after killing the child, into the same window. So **every** emission in the supervisor goes through one gate that is silent while the latch is set — gated on the latch rather than on the shutdown *arm*, since during a quit no path should emit, including a child that happens to exit on its own then; an ordinary unload is not a quit and still emits. The same latch fixed a second swallow: the warming loop's `/health` probe was awaited *outside* its `select!`, so the shutdown oneshot was not polled for the probe's duration — and warming is exactly when `/health` hangs rather than refuses (the socket is accepted while a multi-gigabyte model loads, and that client sets no request timeout), so a quit landing there was never observed and the child outlived the process. The probe now races the signal. - `tools.rs` — **the tool registry: the seam a turn's bounded tool-calling loop runs.** v1 tools are **harness-internal only** — a `Tool` implementation living in-process (no external/MCP surface; that whole area is the deferred roles/tools/capabilities item). A `ToolRegistry` (name → implementation, last registration of a name wins) is held on `Inner`, **empty by default**, and mutated through `AppCore::register_tool`. Two properties are load-bearing: **empty is invisible** — `TurnPrep::request_body` omits the `tools` field entirely when the turn's registry snapshot is empty, so a registry-less install sends byte-identical requests (upstream prefix caches and every pinned-bytes test are undisturbed, and a `tools` field is what an "OpenAI-compatible" backend is least likely to accept) — and **names are the key**: a name the registry doesn't know is *not* a turn failure, it is reported back to the model as a tool *result*, exactly like unparseable arguments or the tool's own `ToolError`, because all three are model mistakes the model can correct on the next round. `prepare_turn` snapshots the registry once per turn, so registering mid-turn never changes a tool set already advertised. Ships with `EchoTool` (returns its `text` argument) so the loop is exercisable end to end with no other dependency; nothing registers it in production. Task 22's `decline` tool landed in its own `decline.rs` (an ordinary `Tool` plus one checkpoint seam in the round loops) and changes nothing else about the turn machinery. **Navigation tools (task 21):** `list_branches`, `read_thread(handle, limit?, offset?)` and `read_post(handle)` — `pub(crate)` `Tool` impls over the turn's `Arc<ThreadSnapshot>`. They are read-only over a **snapshot** (stale-ok, the same contract a file-reading agent harness gives its model), so they need no database handle, no lifetime and no synchronization. Handle → id resolution is harness-side: the snapshot derives `post_handle` over the space's items and matches; a handle it doesn't know is answered honestly **in the result** ("…the map is a snapshot; call `list_branches` for the current structure"), never as a turn error. `read_thread` renders posts through `with_header` — the exact task-19 wire format, one rendering path rather than two — and states its window bounds and how to page rather than truncating silently. `read_post` is the one exception to the snapshot-only rule: its optional `quote: N` argument follows a reference edge to the post it quoted, which may live in another space, so it also carries a `Weak<Inner>` and the responding participant and re-checks membership **per call** (task 37 — see the `lib.rs` bullet for the addressing choice and the non-leaking denial). **The three names are reserved** (five in all, with task 35's `remember` — see `memory.rs` — and task 36's `list_my_spaces` — see `discovery.rs`): `AppCore::register_tool` returns `Err` for `tools::RESERVED_TOOL_NAMES`. Without that a consumer's `read_thread` would register fine, work on every linear turn, and then be silently replaced by the built-in the moment a space branched (the turn layers its tools onto the snapshot and `ToolRegistry::register` is last-write-wins) — the advertised schema and the executed implementation diverging on exactly the turns the feature exists for. These are protocol surface, not ordinary built-ins: the map's system note promises the model these three names, and each reads the turn's own snapshot, which a process-scoped registration structurally cannot supply. `ToolRegistry::register` keeps its raw last-write-wins semantics (it is what the turn layers with); the reservation lives at the one seam that reaches the process registry. **Attachment is per turn, in `prepare_turn`, layered on top of the process-registry snapshot** (these tools are scoped to one space and one turn's snapshot, so process scope would be meaningless), and it is gated on the space actually **having branches** — so a linear space's requests stay byte-identical and the task-20 empty-registry pins keep passing — **and** on the backend being able to carry a `tools` field. That second condition is one static exclusion plus one *learned* fact, and the distinction is load-bearing. Statically: `eidola` is excluded because its `ChatCompletionRequest` is `#[serde(deny_unknown_fields)]` with no `tools` member (removal trigger: **task 25**), so a branched eidola space gets the full structural map — which rides the messages array and is unaffected — but not the descend-further affordance. For everything else, **backend kind establishes nothing** and the capability is discovered rather than assumed: llama.cpp answers HTTP 500 `tools param requires --jinja flag` without `--jinja`, and *with* `--jinja` still 500s with a template-render crash when the model's tool block uses Jinja filters it lacks (Qwen3 Coder does exactly this), and a generic OpenAI-compatible endpoint may refuse the field outright. Because attachment is **automatic on branch**, assuming capability would make "branching your conversation" break every subsequent turn on that model, with no opt-out. So the round loop **degrades on rejection**: if round 1 fails with an `AppError::Server` status and the turn attached the tools itself, it withdraws them, acquires a fresh hold (`begin_next_round`), and retries the round once — and the blocking transport returns *before* persisting the error inference in that case, because an error generation there would consume the turn's item identity (a fresh `Reply` item's only root, or the `Revise` successor slot) and the retry could not write its answer at all; the rejected request row is still committed, since it carries the `tools` field the endpoint refused. A backend whose toolless retry **succeeds** is remembered in an in-process set (`Inner::tool_incapable_backends`) and never offered tools again, so the probe costs one request per backend per process rather than one per branched turn. Recording only on retry success is deliberate: a round that fails both with and without tools was failing for another reason and must not silently cost the backend its tool support. The memo is an *observation*, not configuration — no column, no setting, nothing to migrate, and a backend that gains tool support is re-probed after a restart — which keeps the real per-backend capability flag genuinely deferred. Only the tools *a turn attaches* are ever withdrawn or gated; a consumer's own registrations are an explicit opt-in and fail honestly, exactly as task 20 decided. Regressions: `a_backend_that_rejects_tools_degrades_to_a_toolless_retry`, `a_backend_observed_to_reject_tools_is_not_offered_them_again`, `a_rejection_unrelated_to_tools_does_not_downgrade_the_backend`, `registering_a_reserved_navigation_tool_name_is_refused`.
- `router.rs` — **the may-decline router: one cheap model call that filters the mechanical notify set.** `plan_notifications` stays a **pure read** (the CI-deterministic mechanical candidate set: notify policies + the data-derived cascade guard); this module adds the step *between* planning and turn-driving. `AppCore::plan_notifications` plans **and then refines**: the refinement step sends the triggering post's upstream thread slice (last 6 posts, clipped) plus one **candidate card** per planned participant (label, one-line persona digest from its effective system prompt, notify policy) to a small model and keeps only the subset it names. Candidates are addressed by **1-based index**, not participant id — the ids are UUIDv7s and a small model echoing one back verbatim is a needless failure mode; the reply is strict `{"notify": [n, …]}`, read by the pure, unit-tested `parse_router_selection` (tolerant of fences/prose around the object, strict about the object; an **empty** list is a valid decision meaning nobody responds). **Failure doctrine: degrade, never block.** An unset router model (**the default — the feature is off**), an unreachable router, or unparseable output all return the mechanical plan **unchanged** with an honest stderr warning: the failure mode is *extra* notifications, never lost ones, and a post is never blocked on router availability. Router **non-selections are not persisted** — not notifying is exactly what an `explicit`-policy participant already experiences, which writes nothing. **Explicit asks bypass entirely** (`respond_stream` / `respond_stream_as` consult no guards and no router) and **a `Paused` plan short-circuits before any call** (the cascade guard speaks first; it is unchanged and still applies to whatever the router lets through). **Settings:** the router model is a **space setting and a template setting** (`space.router_model` / `space_template.router_model`, copied at instantiation exactly like `cascade_limit`), a qualified `<model>@<backend>` reference written through `AppCore::set_space_router_model` (emits `Change::Space`) / `set_template_router_model` (emits `Change::Templates`) — deliberately their own setters rather than extra parameters on `create_template`/`update_template`, whose signatures are unchanged. Both validate the backend up front so a typo fails loudly at write time rather than degrading silently on every post. **The call is not a turn:** no actions, no context assembly, no request rows, no attestation records. It runs through the shared chore runner (`utility.rs`), so an engine-backed reference takes the zero-spend path (genuinely free — no charge, no credential, no account) while a remote `eidola` reference **bills a normal inference on every triggering post** (it spends and settles its refund like a turn's round would, `Change::Wallet` included); any settings surface must say that plainly. **No caller can forget it:** there is no public API that returns an unrefined plan for driving — `AppCore::plan_notifications` refines, `submit` goes through the same `Inner::plan_and_refine`, and the unrefined set is reachable only through `AppCore::mechanical_notification_plan`. That matters because a cascade re-plans on every hop (the GUI's turn runner does exactly this after each response); an opt-in refinement would have been applied to the first hop and silently skipped on the rest. **GUI: deferred.** `cascade_limit`'s only surface today is the Templates settings pane (there is no per-space settings pane at all), so this PR is app-core + schema; the settings UI — including the remote-cost warning — is a follow-up. Tests: `tests/participants_orchestration.rs` (selection drops the unchosen candidate leaving the survivor's `cascade_depth` untouched, empty selection → zero turns, degrade on 500 / on prose / on a body-read failure that also settles the remote router's credential hold rather than stranding it in `spending`, unset → not one HTTP call, `Paused` never reaches it, explicit-ask bypass) over a `RouterBehavior` arm on the mock upstream that answers requests whose wire model is the registered local router; the prompt builder and reply parser are unit-tested in-module. **Judgment-tier evals are explicitly out of CI** (real-model output is not deterministic across machines): whether the router decides *well* is an offline eval over a golden set of (post, cards, slice) → expected notify set, living beside the other offline harnesses, never in `tests/`
- `decline.rs` — **the agent-side decline checkpoint.** An orthogonal *quality* valve, not a gating mechanism: by the time it can fire the prefill is paid for, so it saves the reader, not the money (the cheap filter is `router.rs`, which decides before a turn is driven). `DeclineTool` is an ordinary `tools::Tool` (`decline`, one optional `reason`); what makes it a checkpoint is one seam in both round loops, placed after the round's `tool_call` action is persisted and **before** the round cap (a decline is terminal, so it never needs another round). - `utility.rs` — **the harness chore runner: one cheap model call that is deliberately not a turn.** Extracted from `router.rs` (which duplicated `prepare_turn`'s backend-routing head) when the branch summarizer became its second consumer. Two phases, and the split is the point: `Inner::resolve_utility_target` answers *where would this go* from the backend registry alone — no engine start, no network, so a broken model reference degrades before anything is started — and `Inner::utility_completion` then opens the route (leasing or starting an engine, building the attesting or plain client, placing a hold for a remote call), makes one non-streaming completion, and settles the refund. - `summaries.rs` — **LLM-written branch summaries: the progressive enhancement over the structural thread map** (task 21's checkpoint 3). One optional line under a map entry, précising what the branch is about; everything here can fail or be off and the map is exactly what it was. **Cache keyed on the branch tip** — the newest of the branch's *resolved current generations* — so a summary regenerates when the branch grows and never otherwise; reading it off the resolved generations is what makes an edit **anywhere** in the branch move it too (an edit is a new action, so it is the branch's newest generation the moment it lands — a non-tip edit is not invisible to the cache); a stored summary is rendered even once the branch has grown past it (a snapshot, like the navigation tools' results, beside a structural line that carries the fresh counts). **Storage is a versioned item**: an `action_type = 'checkpoint'` action with `intent = 'branch_summary'`, authored by the new global `db::SYSTEM_PARTICIPANT_ID` (Eidola on its own behalf — attributing it to a human or an agent would be a lie in the Record), the text as its one `text` block, and two `reference` antecedent edges carrying the keys in real relations rather than packed into a string: ordinal 1 → the branch root (its *item* is the branch's stable identity, so an edited root doesn't orphan the summary), ordinal 2 → the tip it read. - `memory.rs` — **agent memory (task 35): the second of the three participant layers** — charter (human-owned config), **memory** (agent-owned, self-revised, human-inspectable), experience (the transcript + task 33's first-person traces). Keeping charter and memory separate is deliberate: the human's instructions stay authoritative, and "operator config" and "notes you wrote yourself" are each more credible to a model than one undifferentiated blob of standing instructions. **A block is an item**, exactly the task-27 branch-summary precedent: each revision is a generation (`action_type = 'memory'`, superseding the item's tip), so the existing machinery supplies append-only history, a diffable trail, and — because every generation records its author — a **structural** distinction between a self-revision and a human correction. `memory` is not a post type, so `get_space_tree`, both context queries and the notification planner's post allowlist collapse it out for free. **Provenance** is what a string-blob store cannot do: a revision may carry `reference` antecedent edges (ordinals `1..=N`; ordinal 0 stays empty — a block has no `reply` edge, it is not part of the thread) naming the posts it learned from, with the model's annotation, so an inspector can ask *why* the agent believes each thing. **Ownership vs scope (promotion-critical):** the new `memory_block` table carries the block's identity — one **owner** (the agent, pinned by the same `(id, scope)` composite echo `action` uses), a scope *label* (`core` = loads wherever the owner goes, `space` = loads in its residence only), and a **residence** `space_id` (the space the block is about, where its actions live). Scope is addressing, never co-ownership, which is what makes task 36's in-place promotion a no-op for memory — a promoted agent's blocks keep their owner, names, scope labels and residence, and only the pinned owner echo cascades. Residence for a space-owned agent is always the space it is standing in; **task 36 added the one exception** — a `core` block a **global** agent writes is about no space, so it resides in that agent's notebook, which is what the notebook is for. Residence is decided once, at creation, and never moves. Names are unique per **owner** (not per owner+space) so `remember` addressing a name is unambiguously the same block wherever the agent stands. **The loading rule:** per turn the *responding* participant's core blocks plus the blocks about the current space — and nobody else's, ever — render at the **head**, inside the system message, after the charter and the static notes (that placement keeps the charter+notes prefix byte-stable, so a revision invalidates as little of the prefix cache as the rule allows; a memory edit invalidating that participant's cache is correct and accepted — CLAUDE.md semantics). Slow memory at the head, volatile thread map at the tail; the bytes ride the `messages` array so `chargeable_prompt_tokens` covers them on both sides by construction. **The tool seam is turn-scoped**, the task-21 navigation-tool precedent rather than task 20/22's consumer registration: `remember(block, text, scope?, sources?, annotation?)` is bound to *this* turn's responding participant, residence space and `ThreadSnapshot` (handle → provenance), none of which the process registry's `Tool` trait can carry — a shared `Arc<dyn Tool>` is called concurrently by every turn in the process and could only guess whose memory it was writing. So the name is **reserved** (`tools::RESERVED_TOOL_NAMES`, now four) and the tool is constructed in `prepare_turn`. **Off by default** like every other agentic capability here: the whole feature — the loading read *and* the tool — is gated on `AppCore::set_memory_enabled` (process-scoped consumer opt-in, exactly like `register_tool`; a UI with a stored preference reads its own setting and calls this), which is what preserves the `tools.rs` invariant that a non-opted-in install sends byte-identical requests. The `eidola` backend still cannot carry a `tools` field (`deny_unknown_fields`), so a remote turn *reads* its memory but cannot revise it until task 25 — the same limit the navigation tools have. **Hygiene** is revision-shaped, not append-shaped (COW makes revising the cheap default), plus two guard rails — `MAX_MEMORY_BLOCKS` (8) per owner and `MAX_MEMORY_BLOCK_BYTES` (2000) per block — whose refusals are *tool results* (a model mistake it can correct), honest about the limit and what is already held, and decided **before any write** so a refusal leaves zero durable trace. A committed block emits `Change::Space(residence)` — the one place a successful tool round emits, safe mid-loop because `memory` is not a post type (its `tests/bus.rs` row). Inspection: `AppCore::memory_blocks(participant_id)` (pure read; each block with its full revision trail — contents, author and provenance per generation), the data a later GUI inspector renders. Tests: `tests/agent_memory.rs` (the head-of-context bytes pinned in `chat_bodies()`, off-by-default byte-identity, revision-supersedes-not-accumulates with both authors, provenance edges + an unknown handle reported rather than dropped, both budgets refusing with zero trace, another participant in the same space loading none of it, the emission, the reserved name), the loading rule's SQL in `db.rs` (`participant_memory_loads_core_everywhere_and_space_blocks_only_at_home` — the promotion-critical half, which only the query can prove while v1 residence is always the owner space), and in-module unit tests for the rendered block, the one-line name invariant, the budgets and the receipt. Memory *quality* (generalization, hygiene, retrieval, adherence) is offline-eval material, never CI
- `discovery.rs` — **cross-space discovery (task 36): `list_my_spaces`, the space-level analogue of `list_branches`.** A turn's context is branch-scoped and always will be, so a promoted agent — one identity in several conversations — cannot otherwise know the others exist. The tool mirrors the human's Library, **bounded by membership**: it reads `db::participant_spaces` (owned rows ∪ live reference rows) and nothing else, and takes no arguments, so there is no space id or filter a model could supply to reach a space it is not in, and a space it was removed from leaves its view the moment the human removes it — the boundary is the query, not a check a caller could forget. It reports *what and where*, never contents, and says so in the result rather than leaving a model to infer it from a missing affordance (cross-space reading and search-within-membership are their own decisions). Turn-scoped and **reserved** like `remember` (bound to the responding participant, which is the whole boundary), attached in `prepare_turn`. **Its gate is structural, deliberately not the memory opt-in:** it attaches only when the responding participant is a `global` agent, and a global agent exists only because a human promoted one — so an install that has promoted nothing sends byte-identical requests for the same reason a linear space does. Riding the memory opt-in was rejected in both directions: it would leave a promoted agent unable to see where it is until memory was enabled, and would switch on cross-space visibility nobody asked for the moment it was. The `GLOBAL_AGENT_NOTE` joins the system message on the same terms, so it flips once (at promotion) and is byte-stable after. Renderer unit-tested in-module; the round trip in `tests/global_agents.rs`
- `error.rs` — `AppError` enum, request error classification (attestation vs network vs server), typed onboarding variants (`NoAccount`, `InsufficientBalance { available, required }`, `ProvisioningTimeout { message }` — the ACT provisioning queue's bounded-wait timeout), `ToolLoop { message }` (a turn's bounded tool loop could not finish honestly — the round cap was reached with the model still asking for tools, or its `tool_calls` were structurally unusable; everything that did happen is committed first and the error is wrapped with the space id like any other post-persist failure), `DatabaseInUse { pid, message }` (another Eidola process holds the local database's advisory lock — distinct from `Database` so the CLI prints an actionable hint and a GUI can route to a startup dialog; `pid` is best-effort, `None` when the lockfile's stamp was unreadable, and the `message` already names it), `NotAParticipant { participant_id, action_id }` (the cross-space reference ACL, task 37: creating a reference into a space you are not a member of, or following one there. **Non-leaking by construction** — it names only the action the caller itself supplied, never the referenced space's id, title, participants or content, because it is rendered into UI a non-member sees and its tool-result twin `tools::FOLLOW_DENIED` into a model's context), and `ChatFailed { space_id, source }` — the id-carrying wrapper `chat`/`chat_stream` attach to any error returned after a space is persisted (Display defers to `source`; `root()` unwraps it for variant-routing callers, `chat_space_id()` extracts the id for blank-space adoption; `into_chat_failed(space_id)` wraps idempotently — a no-op if already `ChatFailed` — and is applied at the `run_turn`/`run_turn_stream` call site to `prepare_turn`'s result so the **early setup failures** (client build / `/v1/models` fetch / attestation flush, which run before the turn's inline `wrap` closure) also carry the id; without it those escaped unwrapped and a blank GUI space couldn't adopt its id — Retry suppressed, a follow-up stranding a second space)

**Automatic credential provisioning:** turns resolve their spend credential via `Inner::ensure_spendable_credential`, called **under the wallet-level `spend_gate`** (the ACT provisioning queue): an active wallet credential covering the estimated charge is used directly; otherwise app-core auto-allocates `min(available, max(DEFAULT_ALLOCATION_CREDITS, charge))` from the account balance and proceeds transparently. `DEFAULT_ALLOCATION_CREDITS = 1_000_000` (credits are micro-USD-denominated, so ≈ $1.00 of balance ≈ 30 worst-case per-turn holds; the constant's doc comment carries the full sizing rationale). Because it runs under the gate as a bounded retry loop, a concurrent turn that finds the balance already committed **waits for an in-flight refund** rather than double-booking — but only when a mid-spend credential whose face value actually covers the charge exists (a smaller one's refund could never cover it, so that is an immediate `InsufficientBalance`). Failures are *typed* so UIs route on variants, not strings: `AppError::NoAccount` (no usable credential and no account configured), `AppError::InsufficientBalance { available, required }` (account exists but cannot cover the charge), and `AppError::ProvisioningTimeout` (a sibling turn holds the only coverage mid-spend and its refund never landed within the bounded wait — retry once it settles). The explicit `account_allocate` path is unchanged; both the GUI and CLI get the silent-provisioning behavior for free.

**Chat-path test harness:** The full `chat` / `chat_stream` HTTP paths are exercised by `crates/eidola-app-core/tests/chat_path.rs` on top of the in-process mock-upstream harness in `crates/eidola-app-core/tests/chat_harness/`. Per-test `ChatBehavior` selects blocking/streaming/streaming-with-a-mimicked-header/non-2xx/mid-SSE-abort/connection-drop plus the tool-calling arms (`ToolRoundsBlocking(n)` / `ToolRoundsStreaming(n)` — answer with a tool call for the first `n` requests, then normally; the SSE arm splits one call across four deltas so the client's per-index accumulator is genuinely exercised rather than handed a pre-assembled chunk — plus `ToolRoundsStreamingWithExtras(n)` for provider-field preservation — and `ToolCallMalformed` / `ToolCallBadArguments` / `ToolCallsNotAnArray` / `ToolCallsNotAnArrayStreaming` / `ToolCallsNull`, plus `ToolScript` — the next request asks for every call in the shared, interior-mutable `MockConfig::tool_script`, which exists because task 21's navigation-tool arguments are post handles that only exist once the fixture space has been built — and `RejectTools`, which 500s any request carrying a `tools` field with llama.cpp's own `tools param requires --jinja flag`, the verified upstream shape behind the tool-rejection degrade), plus `DeclineBlocking` / `DeclineStreaming` for the agent-side decline checkpoint), `RouterBehavior` scripts the may-decline router independently — it answers only requests whose wire model is the registered local router model, so one mock serves both the router and the turns in a single test — `SummaryBehavior` does the same for the branch summarizer, which shares the router's *model* and so is recognized by its system prompt instead (dispatched first; `tests/branch_summaries.rs` drives passes through the `test_refresh_branch_summaries` seam, since the production trigger is debounced) — and `RefundMode` selects refund-recovery success vs failure. **CLI usage (`crates/eidola-cli/`):** Depends on `eidola-app-core` as a regular Rust crate. Calls `AppCore::new(config_dir, data_dir)` and invokes methods directly. `main` parses argv **first** (so `--help` / `--version` / argument errors work even when another Eidola holds the local database) and then builds the core, routing a construction failure through the same `report(&err)` renderer as a command failure. That renderer prints actionable hints for the typed errors (`NoAccount` → `eidola account create`; `InsufficientBalance` → `eidola account prices` / `checkout`; `DatabaseInUse` → quit the other Eidola). `eidola chat` without `--model` resolves the default template's agent model (the async `AppCore::default_model()`, kept as the model-picker default for CLI/GUI display; the model-picker chat path uses `TurnSelector::Model`, so a plain pick reuses the space's matching agent); `--model` accepts qualified `<model>@<backend>` references (see `backends.rs` above). `eidola backend {list,add openai,add llamacpp,enable,disable,remove,models}` manages the backend registry (`disable eidola` is the no-account on-device mode); `add llamacpp` takes `--engine-path` and `--no-auto-start`, and `list` shows the engine + auto-start state for llamacpp rows. `eidola model {list,download,delete,load,unload,pin,unpin}` manages local llama.cpp models (see `local_models.rs` above); a chat against any engine-served model loads the engine on demand inside the request path (the CLI just narrates the wait), and `eidola model load` serves until Ctrl-C. `eidola update check` runs the update-notification check and prints the same five states the GUI's Updates window renders (exit code 2 for the unverifiable security state, 3 for claims-changed); the previous full-pipeline command moved to `eidola update verify`. `eidola service {install,start,stop}` (`service.rs`) is the Linux long-lived-app sugar (task 17 wave 2): `install` writes `$XDG_CONFIG_HOME/systemd/user/eidola.service` — a `const` template with the resolved `eidola-gui` path substituted, launching it `--windowless` — then `systemctl --user daemon-reload` + `enable`; `start`/`stop` are the matching calls. The resolved path is made **absolute, checked for existence, and checked for the executable bit** (`absolute_existing_exec` — lexical `std::path::absolute`, deliberately *not* `canonicalize`: the two things a `--exec` most often names are symlinks on purpose, a Nix profile entry and `target/release/eidola-gui`, and pinning the unit to today's link target would make a rebuild silently keep launching the old binary; a mode-644 file is refused because systemd rejects it too, `Command … is not executable: Permission denied`) and **quoted for the executable word** (`systemd_quote_exec`: `"…"` with `\`-escaped `"`/`\`, and `%` → `%%`). `ExecStart=` splits on whitespace, so a bare `/home/me/Eidola Builds/eidola-gui` would run `/home/me/Eidola` with the rest as an argument, and a space in a desktop path is entirely ordinary. **`%` is escaped but `$` is deliberately not**, and the asymmetry is real: a specifier is expanded everywhere in the unit, quotes included (verified — `"/opt/100%dir/eidola-gui"` is rejected by `systemd-analyze verify` with `%d` substituted mid-path), while environment expansion does *not* apply to the program word — "Note that the first argument (i.e. the program to execute) may not be a variable" (systemd.service(5)) — so escaping `$` to `$$` is not merely unnecessary but **corrupting**, and systemd takes the doubled form literally (verified: the literal path passes `systemd-analyze verify`, the escaped one is rejected as nonexistent). The function is named `_exec` because the rule flips for a later *argument*, where `$$` is the documented literal-dollar escape; the unit's only other word is the fixed literal `--windowless`. **These three verbs are handled in `main` before the core is built**, because the running service holds the local database's exclusive lock and `service stop` has to work exactly then. **The install preflight probes `systemctl --user daemon-reload`, not `--version`**: the version query is answered by the binary itself and succeeds in a container, under WSL, or anywhere no per-user manager runs — so it proved only that a file existed while the very next call failed to connect to the bus, *after* the unit had been written (a half-install). `daemon-reload` is the cheapest operation that must actually reach the user manager, is idempotent, and is the call install has to make anyway — so refusal happens before any write, the zero-trace pattern. The unit is a Rust `const` rather than a `data/` asset on purpose: the Nix build's crane source filter keeps Rust plus a short extension allowlist (`.sql`, `.ttf`), so a `.service` file would silently vanish from the packaged source. Unit-tested against a temp XDG dir (`the_rendered_unit_starts_the_gui_windowless`, `a_path_with_whitespace_stays_one_argument`, `quoting_escapes_what_systemd_would_otherwise_read`, `a_dollar_bearing_path_reaches_the_unit_intact`, `a_relative_exec_is_resolved_against_the_cwd_not_written_verbatim`, `a_resolved_exec_is_absolute_in_the_unit`, `a_symlinked_exec_keeps_the_link_not_its_target`, `a_missing_exec_is_refused_rather_than_written`, `a_non_executable_file_is_refused_rather_than_written`, `install_writes_into_the_xdg_user_unit_directory`, `writing_the_unit_twice_replaces_it`, `an_explicit_exec_wins_over_discovery`).

**GUI usage (`crates/eidola-gui/`):** Native Rust gpui app. Depends on `eidola-app-core` as a regular crate; `core.rs` wraps `AppCore` in an `Entity<Core>` that bridges tokio (the core's runtime) to gpui's smol-based executor via `oneshot` channels, and holds cached snapshots that views read reactively. **The process outlives its windows** (task 17 wave 2): `src/lifecycle.rs` owns the quit policy (`QuitMode` — never on macOS or in `--windowless`, with the last window on a windowed Linux launch), macOS reactivation (Dock/Spotlight → focus a window, else open the Library), the `on_app_quit` engine teardown that makes ⌘Q a real full shutdown on macOS (`[NSApp terminate:]` ends in `exit()`, so no destructor downstream of `main` ever runs) — via **`AppCore::shutdown_engines`**, which drains the live engine registry rather than looping a `local_models_state` snapshot, because that snapshot is rebuilt by *scanning* the model directories and cannot see an engine whose backing `.gguf` moved, and the `--windowless` launch mode the Linux systemd user unit starts. **See `crates/eidola-gui/AGENTS.md` for the full architecture** — window model, app lifecycle, Circadian theme + Newsreader bundling, transparent titlebar / gradient overlay, macOS menu/keybinding setup and ordering invariants, the per-view `CloseWindow` / `Settings` singleton patterns, the `.app` bundling requirement, the two-tier test model (behavior tests as the regression gate; visual snapshots as a local debug aid), and the accessibility + QA-probe doctrine — one `.probe(name, role, label)` annotation feeds both the AccessKit tree and the interactive UI driver (`just driver`), which lets agents open fixture scenes in real offscreen-rendered windows and click/type/screenshot over a JSON-lines protocol.

**Crate layout:** Pure Rust crates in `crates/` implement capability logic — `eidola-app-core`, `eidola-server`, `eidola-common` (shared contract logic that must be bit-identical across crate boundaries: the pricing contract the client and server both compute — `chargeable_prompt_tokens`'s arithmetic, `PromptCharge`'s accounting semantics, and `prompt_charge`, the **single walk** over a request's `messages`/`tools` that both sides call, so *what counts* cannot drift; the crate is no longer zero-dep, and the rule that replaced that is written into its docs — a dependency is admissible only if it is already in every consumer's graph and is required for contract fidelity, today just `serde_json` — and the `embed` marker-recognition rule app-core's upstream quote expansion shares with the markdown editor's embed plugin), `tinfoil-verifier`, `gpui-markdown-editor` — plus operational utilities such as `generate-openapi`, `tinfoil-shim-mock`, `hash-secret`, and `measure-enclave`. `crates/devtools/` is an anchor crate (package name `eidola-devtools`) whose sole purpose is to pull upstream Rust-based dev tools (currently `rumdl` and `just`) into the workspace dep graph for lockfile pinning; `.envrc` builds them and direnv puts them on `PATH`.

## Local Database & Migrations

Both the CLI and GUI use an embedded [Turso](https://crates.io/crates/turso) (pure-Rust libSQL) database at `~/Library/Application Support/eidola/eidola.db` for local app data (wallet credentials, conversation history, attestation records, etc.). The database layer lives in `crates/eidola-app-core/src/db.rs`.

**One writer, loudly (`db::DbLock`):** turso is single-writer, and two processes opening one `eidola.db` (the open GUI app plus an `eidola …` CLI invocation is the everyday case) used to contend for the file with no honest signal — writes just failed or misbehaved. `AppCore::build` therefore takes an **exclusive advisory lock** (`flock`, via the `fs4` crate — one pure-Rust crate on top of the already-present `rustix`) on a sidecar `<data_dir>/eidola.db.lock` **before** building anything else, and `Inner` holds it for the process lifetime. A second opener is refused at construction with `AppError::DatabaseInUse` naming the holder's pid, which is why **`AppCore::new` / `with_test_http_client` return `Result`**. **Keep it `flock`, not a pidfile-existence check:** the lock lives on the *open file description*, so the kernel releases it however the process exits — a crash cannot wedge it, and a leftover lockfile on disk means nothing (regression-tested). The file's contents are only the holder's pid, stamped after the lock is taken, purely so the refusal can name a process; an unreadable/garbage stamp still refuses, it just reports `pid: None`. The lock is keyed on the **data** dir, so disjoint data dirs never contend — which is what keeps the many tests that build an `AppCore` over their own tempdir parallel-safe. Two `AppCore`s in one process are refused exactly like two processes (separate `open()`s are separate file descriptions); no production flow constructs two, and tests that model a *restart* drop the first core first. Surfacing: the CLI parses argv **before** building the core (so `--help` works while the app holds the database) and prints an actionable hint; the GUI has no startup-failure surface yet and aborts with the honest message (see `stores/mod.rs`) — a real dialog is a follow-up. Tests: `crates/eidola-app-core/tests/db_lock.rs`.

**Schema management (fresh-start, no migrations):**

- `crates/eidola-app-core/schema/schema.sql` is the canonical schema — always reflects the current desired state, and **is the whole baseline**. The Participants v1 reset collapsed the pre-release migration history; there are **no** incremental migrations (no real users)
- Fresh installs (`user_version == 0`) apply `schema.sql` directly via `execute_batch` and set `PRAGMA user_version` to `LATEST_VERSION`
- A database already at `LATEST_VERSION` just re-runs its idempotent seeds. **Any other non-zero `user_version` is refused** — `initialize` returns an honest "your local Eidola database is from an incompatible build … delete your dev database (~/Library/Application Support/eidola/eidola.db)" error rather than limping against a schema it doesn't match. This is sanctioned by the fresh-start decision: delete the dev DB by hand

**Changing the schema (fresh-start rules):**

1. Edit `schema.sql` to the new desired state (this IS the change — no `MIGRATION_N` constant, no `migrate()` block)
2. Bump `LATEST_VERSION` in `db.rs` so existing dev databases are detected as incompatible and refused (they must be deleted, not migrated)
3. Run `cargo test -p eidola-app-core` — `migrations_match_schema` still runs (comparing a direct `schema.sql` apply against the `initialize` path; trivially green with zero migrations), and the seed/idempotency + projection + stale-version tests cover the new tables

**FK enforcement:** turso defaults `foreign_keys` **OFF** — every `REFERENCES`/composite FK is unenforced documentation until you turn it on, per connection. `db::connect()` sets `PRAGMA foreign_keys = ON` on every connection (and `Inner::db_conn`/`open()` route through it); the scope-owned participant model depends on the composite FKs + CHECKs actually firing. `turso_enforcement_smoke` in `db.rs` pins the observed behavior (single/composite FK, MATCH-SIMPLE NULL-skip, CHECK, and `ON UPDATE CASCADE` on a composite FK — task 36's in-place promotion depends on that last one, so it was proven before anything was built on it). When adding tables, respect insertion/seed order (the referenced row must exist first) — enabling enforcement surfaces latent order bugs rather than silently accepting dangling rows.

**Limitations:** The `turso` crate does not support `ALTER TABLE ALTER COLUMN`. Since there are no migrations this rarely bites, but a `NOT NULL` column still needs a `DEFAULT <value>` (see `notify_policy`/`cascade_limit`).

## Build Commands

**Prerequisites:** `rustup`, `direnv`, `docker`

The `justfile` is the primary development interface. Run `just` to see all available recipes. `just` itself is not a separate install: it is one of the Rust-based dev tools pinned by the `crates/devtools/` anchor crate, built by `.envrc`, and put on `PATH` by direnv — so `rustup` + `direnv` is enough to get it (see Conventions for how the anchor works).

**Key recipes:**

- `just build {server,cli,gui,www}` — local-toolchain builds for fast iteration. The `gui` target on macOS additionally runs `scripts/package-gui-app.sh` to assemble `crates/eidola-gui/build/Eidola.app` (the .app wrapper is required for AppKit to treat the binary as a real app rather than a command-line tool — see `crates/eidola-gui/AGENTS.md` for why). The `www` target builds the website to `target/www`.
- `just run {server,cli,gui,www}` — build and run. For `gui`, opens the assembled `.app` via `open`. For `www`, serves the site locally with drafts + rebuild-on-change. Accepts trailing args (e.g. `just run cli chat "hello"`).
- `just test` — runs `cargo test`.
- `just check` — clippy, rustfmt, and `rumdl check` over committed markdown (see `.rumdl.toml`). Run `just lint-md-fix` to apply auto-fixable formatting.
- `just dev` / `just services` / `just down` — container-based development workflows (see Compose files above).

**Dev profile:** the root `Cargo.toml` optimizes *dependencies* at `opt-level = 2` in dev builds (`[profile.dev.package."*"]`) while our own crates stay unoptimized. Dependencies are recompiled almost never and executed constantly, so this buys 8-17x faster frames in the GUI (measured with `crates/eidola-gui/tests/record_perf.rs`) and halves the debug binary, for ~90 s of one-time cold-build cost and no measured effect on incremental rebuilds. What it costs is debugging *inside* a dependency — stepping is unreliable and dependency locals often read "optimized out"; backtraces are unaffected. The full measurements and the companion settings that were rejected are in the comment block above the profile.

## Conventions

- Pure Rust dependencies preferred (for cross-compilation)
- Keep Rust workspace packages under `crates/`; do not add a separate top-level `tools/` tree
- `just` is the task runner — wrap scripts and common commands as recipes
- Server and CLI OCI images are built with StageX (reproducible, `FROM scratch`, runs as non-root)
- Nix is used for CI quality gates and the reproducible desktop-app release builds — the macOS universal binaries (CLI + GUI `.app` bundle) and the Linux GUI (`.#eidola-gui-linux`, a glibc dynamic binary) — not daily Rust development
- **Bundled inference engine sidecar (`local` backend):** `packages.llama-server` (flake.nix `llamaServer`) is a statically-linked llama.cpp `llama-server` — `pkgs.llama-cpp` with its `src` bumped to llama.cpp release **b9960** (the pinned nixpkgs ships 6981, which predates the `gemma4` GGUF architecture the curated catalog uses; the known short commit is injected directly instead of the recipe's `leaveDotGit` dance) and appended `-DLLAMA_CURL=OFF -DBUILD_SHARED_LIBS=OFF -DLLAMA_SERVER_SSL=OFF` cmake flags (the base package hardcodes the first two ON and exposes no `curlSupport` arg; later `-D` wins; the server otherwise auto-detects OpenSSL for httplib TLS, which we don't need over loopback and which would pin nix-store dylibs), with the unused curl buildInput dropped and a `postInstall` that trims the closure to the single `bin/llama-server`. This statically links llama.cpp's own libs into the one shipped binary, leaving only system frameworks (Metal/Accelerate/libc++/libSystem on Darwin — the Metal library is *embedded* via `LLAMA_METAL_EMBED_LIBRARY` and compiled at runtime, so no Xcode). It is bundled into every desktop artifact: the macOS `.app` at `Contents/Resources/bin/llama-server`, next to `bin/eidola` in the CLI universal output, and in the Linux GUI closure (exposed via `EIDOLA_LLAMA_SERVER`, `--set-default` by the wrapper). app-core resolves the engine exe-relative and never scans `$PATH`, so no system llama.cpp install is required. **The macOS sidecar is deliberately arm64-only** (not lipo'd with an x86_64 slice) — Apple's Intel Metal stack is weak/EOL, so an Intel-slice CPU engine isn't worth its weight; Intel Macs get no bundled engine and the GUI's Local tab shows the honest missing-engine state, with `llama_server_path` as the escape hatch. `autoSignDarwinBinariesHook`'s postFixup walks every Mach-O in `$out`, so the copied sidecar is (re-)signed with the same deterministic ad-hoc signature as the main binary; no LC_UUID zeroing is needed for it (it comes from a separate fixed-hash derivation). **Linux ships CPU-only** for now — a Vulkan build (`vulkanSupport = true`) is coherent to compile (shaderc builds SPIR-V at build time) but usable GPU inference also needs Vulkan ICD driver files at runtime, and the wrapper hands app-core the bare unwrapped `EIDOLA_LLAMA_SERVER` path; wiring the ICDs is the follow-up. Dev path: `just engine` (`nix build .#llama-server -o crates/eidola-gui/build/llama-server`) materializes the sidecar, and `scripts/package-gui-app.sh` copies it (or an `EIDOLA_LLAMA_SERVER` override) into the dev `Eidola.app` best-effort; a checkout without it just shows the missing-engine state. `just build gui` does **not** depend on Nix.

- Server API is documented via utoipa `#[utoipa::path]` annotations on handler functions and `ToSchema` derives on request/response types. `OpenApiRouter` (in `lib.rs::build_router()`) collects paths and recursively discovers schemas automatically — only SSE streaming types that aren't referenced from path annotations are listed manually in `api_doc.rs`. When adding or changing server endpoints, add the annotation on the handler and register it in `build_router()` via `routes!()`, then run `just update-openapi` to regenerate the committed `openapi.json`
- Rust-based dev tools are version-pinned in the workspace `Cargo.lock` through the `crates/devtools/` anchor crate (package name `eidola-devtools`, lib-only, no code — just `=X.Y.Z` deps so each upstream tool is in our dep graph). `.envrc` first sources a gitignored `.envrc.local` if present (machine-local env — e.g. pkg-config/sysroot wiring for building the GUI's C deps on a box without system-wide dev headers), then runs `cargo build --quiet -p rumdl -p just` and direnv puts `target/debug/` on `PATH`, so a `rustup` + `direnv` checkout has the pinned `just`, `rumdl`, etc. with no separate install. `cargo build -p <tool>` resolves unambiguously to the upstream crate because the anchor's package name differs from every tool it anchors; only crates with a `lib` target can be anchored (a bin-only crate cannot be a `[dependencies]` entry — `just` and `rumdl` both qualify). Adding a tool is one `=X.Y.Z` dep in `crates/devtools/Cargo.toml` plus a `-p <tool>` in `.envrc`; bumping one is a single edit there. Markdown specifically is linted via [rumdl](https://rumdl.dev/): `just check` runs `rumdl check .` (rumdl is already on `PATH` via direnv). CI deliberately does not install direnv (no apt in the build chain); it emulates `.envrc` by building only rumdl and prepending `target/debug` to `PATH`, so the `rumdl check .` invocation matches the local one without compiling the rest of the pinned toolset. Configure rules in `.rumdl.toml`
- `artifact-manifest.json` (`schema_version: 1` — integer; see `docs/trust-root.md` for why our schema versions are integers, not semver) records expected OCI digests, the Nix `narHash`es of the desktop artifacts (macOS universal CLI binary, macOS GUI `.app` bundle, and the Linux GUI binary), and enclave measurements (SEV-SNP + TDX + cmdline) with type/platform metadata; the enclave block shape matches the Tinfoil `snp-tdx-multiplatform/v1` predicate so `tinfoil-build.yml` can project it directly into `tinfoil-deployment.json`. the Build & Verify Artifacts workflow verifies the full file by merging digests captured from the real OCI, macOS, and Linux GUI build jobs and recomputing enclave measurements from `tinfoil-config.yml`. Note: the desktop `narHash`es now cover the bundled `llama-server` sidecar too, so they change whenever the pinned llama.cpp or the sidecar wiring changes; regenerating them (`just update-manifest`) is deferred to release time — do not run it as part of a feature change
- `releases/trust/server-enclave.json` (`schema_version: 1`) holds the same enclave block in isolation — `snp_measurement`, `tdx_measurement: {rtmr1, rtmr2}`, `cmdline`. It is the only build-time input that ties the cli to the server, intentionally separated from `artifact-manifest.json` so the cli build context doesn't drag its own digest into its own inputs. `verify-full` cross-checks both files against the freshly-recomputed enclave so neither can drift unobserved
- Use `just update-manifest` to regenerate both, on macOS or Linux, with the pinned amd64 BuildKit builder plus the host's native Nix desktop builds. The script runs a phased build (server + postgres → stamp tinfoil-config.yml → recompute enclave → write `server-enclave.json` → cli OCI + the host platform's native Nix desktop artifacts + the Linux GUI → write `artifact-manifest.json`), so a single invocation reaches a fixed point. The **Linux GUI narHash is always regenerated**, on either host: natively on Linux, and on Darwin by reproducing CI's native `x86_64-linux` build inside a pinned `linux/amd64` Nix container (`nixos/nix`, driven by plain `docker run` — a deliberately *different* mechanism from the StageX buildx builder; `build_linux_gui_via_docker` in `scripts/artifact-manifest.sh`). This works because a pinned, sandboxed, reproducible Nix derivation yields an identical narHash whether built natively on CI or emulated under `linux/amd64` on an arm64 Mac — the same emulation determinism the StageX OCI digests already rely on. The container mirrors CI's Nix flags (`sandbox = true`, `sandbox-fallback = false`) with one emulation concession — `filter-syscalls = false`, since qemu can't load Nix's seccomp BPF filter (which only blocks setuid-type syscalls a Rust/gpui build never makes, so it can't affect output) — and keeps `/nix` warm across runs via a digest-keyed docker volume, so only the first run is a cold, emulated build. The **darwin** narHashes remain the sole host-exclusive entries: they can't be cross-built from Linux, so on a Linux host they're carried over from the committed manifest. CI's `apple` + `linux-gui` jobs remain the cross-platform authority that verifies the full set
