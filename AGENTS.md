## Architecture at a glance

**Gateway** (`crates/eidola-server-gateway`): Axum-based OpenAI-compatible proxy to Eidola's own inference engines, its only inference upstream; PostgreSQL 17+; anonymous-credential billing (`eidola-billing` owns purchase valuation, refunds, disputes and closure, shared with the private `eidola-billing` CLI; Stripe via a thin `reqwest` wrapper); deployed as a StageX `FROM scratch` image inside Tinfoil Containers (AMD SEV-SNP), plain HTTP behind the attestation-bearing TLS shim. Tool calling is wire-level pass-through — the gateway never executes a tool. Responses leave the gateway shaped: a chat stream as fixed-size frames on a fixed tick, every other response (refusals and 404s included, by a layer around every route) padded to a size bucket (`src/padding.rs`), so a network observer cannot read token sizes or timing; the inference node shapes its answer to the gateway the same way, through the framer and reader both sides share (`eidola_common::stream_shape`). The client and server both compute the pricing contract from `eidola-common` (`prompt_charge`), so the client's hold covers the server's charge by construction.

**App core** (`crates/eidola-app-core`): the GUI and CLI share this crate as a normal library — no FFI. All business logic lives here: config, the embedded Turso (libSQL) database, attested HTTP clients, accounts/wallet, chat inference (a bounded agentic tool loop), participants/templates, agent memory, local llama.cpp models. `AppCore::new` is fallible (exclusive advisory `flock` on the local DB — one writer, loudly; second opener gets `AppError::DatabaseInUse`). A `Change` bus broadcasts domain invalidations after every durable commit, each carrying whether a caller is waiting on the write (`ChangeOrigin`) so a busy consumer can tell its own writes from a background one's. A sub-space turn driver gives windowless delegated rooms their turns, and a credential provisioner keeps a small buffer of anonymous credits issued ahead of need, at random times unrelated to any request (issuance itself is idempotent, so a lost response is asked for again rather than lost). Because the local database has one writer, the process holding the lock answers for the profile over a Unix control socket in the data dir (`ipc` — NDJSON frames, typed `AppCore` verbs, no raw-database verb; the listener lives in the GUI, which is the process that holds the lock; the CLI dials it and falls back to opening the profile itself when nothing answers). The **local inference proxy** (`proxy` — an OpenAI-compatible HTTP surface other tools on this machine reach Eidola-served models through) splits the same way: app-core owns the wire contract and a space-free turn that pays and records but writes nothing at the semantic layer, and the GUI binds the TCP listener. The Eidola model catalog is compiled in too (`model_catalog`): a turn names the weights hash it resolved to on every request, and the client says when a followed tag moved, when a pin's tag has newer weights, and when weights retire. A turn sends a prefix-cache key only for a model whose catalog row declares an engine prefix cache: one secret per lineage (one participant answering in one space), rotated within the declared retention, withheld from the Record (`prefix_cache`). **Any change to the chat path must extend the chat harness** (`tests/chat_path.rs` + the `tests/bus.rs` exit-point table).

**Local database:** fresh-start, no migrations — `crates/eidola-app-core/schema/schema.sql` is the whole baseline. Schema changes edit `schema.sql` and bump `LATEST_VERSION` in `db.rs`; other versions are refused ("delete your dev database"), never migrated. turso defaults `foreign_keys` OFF; `db::connect()` enables it per connection.

**Trust chain:** deterministic OCI build → gateway digest → `tinfoil-config.yml` (pinning a platform IGVM release inline) → SEV-SNP launch identity (`measure-enclave`: the release image's launch digest, HOST_DATA = the config's SHA-256, guest policy) → `releases/trust/server-enclave.json` → embedded in the cli/GUI as their trust root → `artifact-manifest.json` (the signed deployment record). Clients re-verify enclave attestation on every TLS handshake (`tinfoil-verifier`). One level down, the gateway pins Eidola's own engine deployments the same way: `deploy/engine/<name>/<variant>/tinfoil-config.yml` → TDX launch identity, with the machine policy and PPID allowlist derived from the platform provider's Sigstore-signed platform endorsements (vendored under `releases/trust/platform-endorsements/`, verified offline) → `releases/trust/engine-enclaves.json` → compiled into the gateway, checked against the committed configs on every gateway build and bound to the model catalog at compile time (`crates/eidola-server-gateway/AGENTS.md` → Eidola-hosted engines). **A model is its weights hash**: the catalog is one hand-written file per hash under `models/` (tags are movable names for a hash; a client names `tag`, `tag@sha256:<hex>` or `sha256:<hex>`, resolved to the hash at the gateway's edge), architectures live in code (`eidola_common::architecture`), and the build binds catalog rows to engine pins one to one by hash (`crates/eidola-server-gateway/AGENTS.md` → Model catalog; `docs/model-identity.md`). Every served row is a pinned engine model. The catalog holds one, MiMo-V2.6-Flash (`models/mimo/mimo-v2.6-flash.toml`), pinned to one committed engine deployment (`deploy/engine/mimo-v2.6-flash/b300x1/`) that is not deployed: a gateway built from this tree lists it and refuses its requests with 503 and a full refund until placement names a running deployment.

**Inference engine** (`crates/eidola-engine*`): Eidola's own Rust serving engine for the one model family it serves (MiMo-V2.6), on confidential GPUs. `eidola-engine` is the serving core (executor seam, scheduler, paged KV, salted prefix cache with bounded retention, zero-on-free and idle entries encrypted under a key derived from the client's, demoted as that ciphertext to a page-locked host tier in the VM's memory under device pressure, speculative-decoding control); `eidola-engine-model` holds the config, weight loader, and the dense f32 reference forward that is the numerics oracle; `eidola-engine-cpu` is the reference executor that must reproduce that oracle bit for bit through the real scheduler, and the contract every GPU executor is held to; `eidola-engine-chat` is the tokenizer, chat template (byte-exact to the upstream Python rendering), and reasoning/tool-call parsers; `eidola-engine-kernels` compiles the open GPU kernels ahead of time (pinned CUDA toolkit, no runtime JIT) into a byte-reproducible, hash-manifested set; `eidola-engine-cuda` is the CUDA executor that runs them through the CUDA driver API (no CUDA runtime, no runtime compilation, no host C++). `eidola-server-engine` is the process on each inference node: it serves one model through these crates in process, behind a strict gateway-only API (bearer token verified against a measured Argon2id hash; every request names the expected **weights hash**, a SHA-256 over every file read from the weights directory, and is refused before admission on a mismatch; a pinned node opens no GPU that NVML does not report in production confidential-computing mode). Engine deployments boot the GPU image of Tinfoil's firmware-less IGVM releases (`X+gpu`; that line is pre-release at Tinfoil) and run the node's release image, `oci/eidola-server-engine/Containerfile`, compiled by StageX like the gateway's but as a dynamic glibc binary, because the node `dlopen`s the platform's NVIDIA driver: StageX's rustc cross-compiles it against StageX's glibc, with a standard library built from its own `rust-src`, and the GPU kernels come in as an image pinned by digest (`oci/eidola-engine-kernels/Containerfile`, built by Nix because they need NVIDIA's toolkit, checked against their committed manifest) (`crates/eidola-server-engine/AGENTS.md` → The image). The gateway pins node deployments (`engine_trust`) and routes every chat request to them (`engine_router`: operator placement in Postgres as availability only, per-handshake attestation against the compiled-in pins, a weights-checking probe before traffic, cache-key affinity); one deployment is committed and pinned, none is running.

**Website** (`crates/eidola-www` + `www/`): in-workspace static-site generator; docs render directly from `docs/`; adding a doc requires a `www/docs-nav.toml` entry (the build fails otherwise).

**Billing runtime** (`crates/eidola-billing-cli`): the `eidola-billing` binary runs private support commands, `serve-webhooks`, or `work`. Receiver and workers are separate processes sharing one optional OCI image (`docker buildx bake billing`), independently deployable outside the attested confidentiality boundary. The gateway queues authenticated account repairs in PostgreSQL and exposes their status; it neither receives Stripe webhooks nor starts billing workers. Database locks coordinate replicas and direct CLI execution. Producer/executor protocol checks and the pending-work generation protect upgrades and requests arriving during processing. Production placement and credential provisioning are operator-owned; `compose.yaml` is development wiring only.

## Branch flow

`next` is the integration trunk; `main` is verified and promotion-only. **Never commit to `main` directly** — feature/dependency PRs target `next`; a maintainer promotes via `/promote` on the `next` → `main` PR, which fast-forwards `main` to the validated head. Cheap gates (`rust-checks`, lint, CLA, …) run on `next` PRs; the expensive `Build & Verify Artifacts` chain runs only for `main` (push + the promotion PR) and its `Guard` job is the merge gate. Full doctrine: `.github/AGENTS.md`.

## Build commands

**Prerequisites:** `rustup`, `direnv`, `docker`. The `justfile` is the primary development interface — run `just` to see all recipes. `just` itself is one of the Rust dev tools pinned via the `crates/devtools/` anchor crate, built by `.envrc`, and put on `PATH` by direnv.

- `just build {gateway,billing,cli,gui,notepad,www,engine-server}` — local-toolchain builds. `billing` builds the support CLI, receiver and worker binary. `gui` on macOS also assembles `crates/eidola-gui/build/Eidola.app` (required for AppKit to treat the binary as a real app); `notepad` likewise assembles `crates/eidola-notepad/build/Eidola Notepad.app`.
- `just run {gateway,cli,gui,notepad,www,engine-server}` — build and run; accepts trailing args (e.g. `just run cli chat "hello"`). `www` serves locally with drafts + rebuild-on-change; `engine-server` serves a synthetic dev model on the CPU executor.
- `just test` — `cargo test`. `just test-billing` runs billing transactions, worker recovery, receiver and gateway boundaries against an explicitly configured disposable `BILLING_TEST_DATABASE_URL`.
- `just check` — clippy, rustfmt, `rumdl check` over committed markdown (`.rumdl.toml`), `cargo-deny check licenses bans sources` against `deny.toml`, and `scripts/check-manifest-determinism.sh` (nothing key-dependent may enter `artifact-manifest.json`; bash + python3 stdlib, no jq, so a fresh checkout needs nothing extra); `just lint-md-fix` applies auto-fixes.
- `just dev` / `just services` / `just down` — container-based dev workflows (full stack vs. host-mode services; see `crates/eidola-server-gateway/AGENTS.md` → Compose files).
- `just client-local` / `just client-reset` — point this machine's client (the GUI and CLI share one profile) at the local dev stack, and revert. Dev-only convenience over the sanctioned override surface: `scripts/local-client.sh` shells out to `eidola configure`, which writes base URL + ARK/ASK + trusted measurement as per-column overrides on the `eidola` backend row; `client-reset` clears each back to NULL, which *is* the compiled-in trust-root pin. Attestation is never weakened — the client runs the same per-handshake verification against the mock shim's chain. Quit any running Eidola first (single-writer local DB). Trusting the shim's mock TLS root in the OS trust store needs `sudo` and stays a human step: the script prints the command, never runs it; macOS reset guidance removes every same-name dev root so rotated roots cannot remain trusted. **Only the trust bundle moves** — the account (config.toml) and the wallet (local DB) stay with the profile, and neither is per-column overridable, so `client-local` pre-flights the profile and warns specifically when either is present (`eidola account create` refuses while an account exists; a production credential can be picked for a local turn and parked until `eidola wallet credentials recover` after `client-reset`).
- `just update-openapi` — regenerate the committed `openapi.json` after changing gateway endpoints.
- `just update-brand` — regenerate every identity asset (macOS `.icns` + `Assets.car`, website favicon + touch icon, Linux themed icons including the symbolic mark) from the geometry in `brand/generate.py`. macOS-only; the outputs are committed, so nothing builds them. See `brand/AGENTS.md`.
- `just update-manifest` — regenerate `artifact-manifest.json` + `releases/trust/server-enclave.json`. **Release-time only; do not run as part of a feature change** (desktop `narHash` / `archiveSha256` move with any sidecar/toolchain/packer change).
- `just engine-platform-endorsements <platform-vX.Y.Z>` — vendor a release of the platform provider's signed platform endorsements (the engine pins' TDX machine policy), verified offline before it is written; the only network fetch of them. See `deploy/engine/README.md`.
- `just engine-image` — build the inference node's release image as CI does (Docker, linux/amd64; slow under emulation) and print its digest, the value an engine deployment pins. It builds the GPU kernel image too and fails unless that image's digest is the one the node's Containerfile pins; `just engine-kernels-image` builds only the kernel image and prints the digest to pin.
- `just engine-kernels [--verify|--update]` — build the inference engine's GPU kernels ahead of time on a GPU-less Linux builder (pinned Nix inside a pinned container; Docker required) and, with `--verify`, fail unless the result equals the committed `kernels.manifest.json` byte for byte. See `crates/eidola-engine-kernels/AGENTS.md`.
- `just engine` — materialize the bundled llama.cpp sidecar via Nix for the dev `.app` (optional; `just build gui` does not depend on Nix).
- `just apple-roundtrip [path/to/Eidola.app]` — re-run the Apple detached-signature round-trip checks on a built universal `.app` (macOS-only; with no path it builds `.#eidola-gui-macos-universal` first, which is slow). Measurement and verdict: `scripts/fixtures/apple-roundtrip/round-trip.md`.
- `just verify-apple <unsigned.tar.gz> <sigbundle.zip>` — reconstruct a signed macOS app in a temporary directory from the reproducible unsigned archive plus detached signatures, validate the placement record byte-for-byte, and print structurally parsed embedded claims. The unsigned input is the flake's gzip'd POSIX tar (`.#eidola-gui-macos-universal-archive`), the bytes `archiveSha256` covers; the detached material has no manifest-bound container, so either argument may be a tar or a zip and the container is read from the file's magic bytes, never its name. Those claims are not independent Apple authentication; the signed release attestation binds the input, detached material, output, and expected identity. Runs on macOS or Linux with POSIX `awk` and `od`, plus Info-ZIP `unzip` for a zip input and a `-z`-capable `tar` (GNU tar or bsdtar) for a tar one. The reconstruction is a *tree*, and the file a browser downloads is a zip: `just pack-shipping-zip <tree> <out.zip>` is the other half, packing that tree with the one recipe the flake's `.#eidola-gui-macos-universal-zip` also runs (`scripts/pack-shipping-zip.sh` — same portability contract, and modes normalized so the packer's umask cannot reach the hash). A tar input also needs directory modes deferred to the end of extraction, or a read-only directory refuses the members packed after it: bsdtar defers by default and GNU tar is passed `--delay-directory-restore`, which the script probes for rather than assuming an implementation. `just test-verify-apple` gates all of that, and runs its body under two userlands — the host's own tools and then GNU tar + mawk (via `nix shell` when the host is not already GNU) — so a Mac exercises the userland most verifiers actually run; see `crates/eidola-apple/AGENTS.md`.

**Dev profile:** dependencies build at `opt-level = 2` in dev (`[profile.dev.package."*"]`) while our crates stay unoptimized (except the engine's numerics crates, whose tests run real model forwards) — 8-17× faster GUI frames for ~90 s one-time cost. The cost is debugging *inside* a dependency (locals read "optimized out"); backtraces are unaffected. Measurements in the comment above the profile in the root `Cargo.toml`.

prefix-cache key's shape and its one encoding, the weights header, the node's stream cadence), the traffic shape of a streamed response, its framer and reader, and the body bucket (`stream_shape`), the engine-deployment config grammar the node boots with and the gateway's pin check and `measure-enclave` read through (`engine_deployment`), the model architectures and the numbers each fixes ## Conventions

- Pure Rust dependencies preferred (cross-compilation); OpenAI API format is the canonical interface.
- **One Rust version everywhere: the pinned StageX release's.** `rust-toolchain.toml` names the Rust that `pallet-rust` ships (recorded in `oci/pallet-rust`), so the native toolchain lints and tests on the compiler that builds the release images; `scripts/check-rust-toolchain.sh` (`just check`, `rust-checks`) enforces it and the node's image build checks the record against the image. The toolchain moves only with the StageX release (`.github/AGENTS.md` → StageX).
- Gateway endpoints are documented via utoipa `#[utoipa::path]` annotations + `ToSchema` derives, collected by `OpenApiRouter` in `lib.rs::build_router()` (SSE-only types listed manually in `api_doc.rs`). New/changed endpoints: annotate, register via `routes!()`, run `just update-openapi`.
- Nix is used for CI quality gates and reproducible desktop release builds (macOS universal cli + GUI `.app`, Linux GUI), not daily development. The bundled llama.cpp `llama-server` sidecar (`packages.llama-server` in `flake.nix`, pinned to release b9960 for `gemma4` support, trimmed to one binary) ships in every desktop **payload**; app-core resolves it by **one rule on every platform — a `llama-server` sibling of the running executable** — and never scans `$PATH`. That is why the macOS `.app` ships it at `Contents/MacOS/llama-server`, beside the main binary (where Apple expects a bundle's executables, and what keeps signing/notarization straightforward), and why the Linux Nix GUI **copies** it to `$out/bin/llama-server` next to the *copied* GUI binary (`$out/bin/.eidola-gui-wrapped`): the bundle layout lives in `flake.nix` + `scripts/package-gui-app.sh`, never in app-core. Every shipped executable is copied, never referenced by store path — Nix store paths are input-addressed, so a reference binds the build recipe but not the output bytes (`docs/verification.md` → Copied, not referenced). The macOS sidecar is deliberately arm64-only (Intel Macs get the honest missing-engine state); Linux ships CPU-only for now, and with BLAS off: nixpkgs' default BLAS backend is a shared library a static binary cannot carry, and it measured an order of magnitude slower at prompt processing anyway. The sidecar derivation remaps `$NIX_BUILD_TOP` out of C `__FILE__` (and zeros Darwin `LC_UUID`) so copied sidecar bytes are a function of source. Nixpkgs Mesa on the current Linux GUI is a *reference* (`VK_ADD_DRIVER_FILES`), not a copy — those driver bytes are outside `archiveSha256`. Vocabulary (payload / archive / envelope / installable) and the hash table: `docs/verification.md`.
- **The sidecar's linkage is per-platform, and enforced in the derivation rather than asserted in prose.** On Linux it is fully static against musl (`pkgsStatic`) — no `PT_INTERP`, no `DT_NEEDED` — which `postFixup` checks with `readelf` so a nixpkgs bump cannot quietly reintroduce a dependency. On Darwin llama.cpp's own libraries are folded into the one binary and only the system frameworks (Metal/Accelerate/libc++/libSystem) remain, which is as static as an Apple platform gets: libSystem is never linked statically. `postFixup` checks that too, failing the build if any load command names a library outside `/usr/lib/` or `/System/Library/`.
- **Linux has two payloads, from the same build.** The Nix one (`packages.eidola-gui-linux-nix`) carries a whole userland out of the store and references nixpkgs Mesa. The host-generic one (`packages.eidola-gui-linux-fdo`) is the same release binary with the two pieces of post-link metadata that bind it to the store removed by `patchelf` — `RUNPATH`, and the interpreter, reset to the filesystem-hierarchy path — so the host's own Wayland, Vulkan loader, and Mesa or proprietary NVIDIA drivers load into the glibc they were built for. `packages.eidola-linux-deb` wraps that binary and the sidecar into a byte-reproducible `.deb` (both arches, built by CI's `linux-gui` and `linux-deb-arm64` jobs): both executables at `/usr/libexec/eidola/`, with a `/usr/bin/eidola-gui` symlink, which keeps the sibling-of-exe engine rule intact because `/proc/self/exe` reports the symlink's target. The oldest glibc a shipped executable may demand lives in `flake.nix` as `glibcSymbolFloor` and is checked against the built binary's symbol versions, so raising it fails the build and never a user's launch. Debian dependencies are declared there too, and every `DT_NEEDED` soname must have a package or the build fails.
- Artifact/trust files: `artifact-manifest.json` (emitted at `schema_version: 2`, accepted at `2`, `3` or `4` — integer, see `docs/trust-root.md` and `docs/verification.md`) records OCI `digest`s, Nix desktop `narHash` plus `archiveSha256` of the flake-built `.tar.gz`, the `sha256` of each published single file (the `.deb`s and the unsigned macOS zip, from schema 3), and enclave measurements; `releases/trust/server-enclave.json` isolates the enclave block as the cli's build input. **Every measured file a release publishes is attached to the tagged release and re-hashed against the manifest before the upload is allowed** (`scripts/release-assets.sh`, gated by `scripts/test-release-assets.sh` on every PR); asset names are derived from the manifest key that records them. **Every value in it is a function of source** — Apple envelope hashes and identities live in the human attestation, and `scripts/check-manifest-determinism.sh` (in `just check` and `rust-checks`) makes that structural, down to a job-graph assertion that signing can never feed the manifest. A manifest schema rotates accept-side one release before emit-side (`releases/README.md`), and `attestation.json` rotates the same way — accepted at `1` or `2`, emitted at `1`, with schema 2 carrying the macOS signing block (shipped-container and detached-material hashes, Team ID, signing identifier) that the manifest may never hold. Regeneration and verification doctrine: `.github/AGENTS.md` and `crates/measure-enclave/AGENTS.md`.
- CLA state lives in `CLA-INDIVIDUAL.md`, `CLA-CORPORATE.md`, `CLA-SIGNERS.txt`; changing either CLA text requires new signer entries (the hash changes).
- **Every square logo surface is generated from `brand/`** — one hexagon-grid mark, one generator, committed outputs (macOS `.icns` + `Assets.car` for light / dark / tinted, website favicon + touch icon, Linux themed icons including the symbolic mark). Never hand-edit a derived asset, and never build a brand asset out of an SF Symbol: Apple licenses those for use inside an app, not as icons, logos, or trademarks. The GUI's status-item glyph remains the real `circle.hexagongrid` symbol at runtime, which that licence does allow. Doctrine: `brand/AGENTS.md`.
- **User-facing GUI strings are localized, and every translation is a build input.** They live in Fluent files under `crates/eidola-gui/locales/`, embedded at compile time and reached through build-generated typed accessors; nothing loads a translation at runtime, because an unmeasured string file could rewrite security-critical UI text without breaking a signature. `eidola-app-core` stays locale-free (typed errors out; the presentation layer localizes), and the CLI and website are English. Doctrine: `crates/eidola-gui/AGENTS.md` → Localization.
- **Licensing is per-component**: `eidola-server-gateway`, `eidola-server-engine`, `eidola-billing`, `eidola-billing-cli` and the inference engine crates are AGPL-3.0-only; `eidola-app-core`/`eidola-cli`/`eidola-gui`/`eidola-notepad` are GPL-3.0-only; every other crate and the repo default is MIT OR Apache-2.0; `docs/` and `www/` content is CC-BY-4.0 (terms/privacy/CLA texts carved out). `LICENSE.md` is the human map and `REUSE.toml` the machine-readable declaration — a new crate needs a `license` field in its `Cargo.toml`, and a crate changing license buckets must update both files. Third-party dependency licenses are vetted by `cargo-deny` (`deny.toml`, whole-graph, gated in `rust-checks` and `just check`; advisories run on a daily schedule instead — see `.github/AGENTS.md`) and by `dependency-review.yml` (lockfile diffs, all ecosystems); the two allow-lists are kept aligned per the note in `deny.toml`. Workspace crates are exempt via `licenses.private.ignore` since nothing is published.
