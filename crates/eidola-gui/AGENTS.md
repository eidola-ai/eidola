# crates/eidola-gui — gpui-based Eidola

Guidance for AI coding agents working on the gpui macOS app. Cross-cutting workspace context (server, app-core, build-system, conventions) lives in the top-level `AGENTS.md`.

## What this app is

A native Rust client for Eidola, built on [gpui](https://github.com/zed-industries/zed/tree/main/crates/gpui) (the immediate-mode UI framework Zed is built on) and [gpui-component](https://github.com/longbridge/gpui-component) (a shadcn-style widget library on top of gpui). The primary GUI for the project; the CLI in `crates/eidola-cli/` shares the same `crates/eidola-app-core/` backend. macOS is the primary target; Linux is supported for build/test (compiles, behavior tests pass) with no release packaging yet — see [Linux build/dev target](#linux-builddev-target).

**State & async doctrine — read first.** All state ownership, async tasks, and cross-window synchronization follow `crates/eidola-gui/STATE.md` (domain stores, `Loadable`, task-as-field with replace-cancels, the invalidation bus, `WindowInput`). Where existing code in this crate contradicts the doctrine, the doctrine wins — the migration is in progress; do not extend the old patterns (`Core::spawn`/busy flag, detached tasks, view-owned domain data).

## Stores (`src/stores/`, `src/loadable.rs`, `src/bridge.rs`)

`AppCore` lives in `crates/eidola-app-core/`; gpui can't host it directly because gpui's executor is smol-based and `AppCore` has its own tokio multi-thread runtime. State ownership and the async bridge follow `crates/eidola-gui/STATE.md` (the binding doctrine) — read it before touching state-bearing code. The old `Core` god-object has been dissolved into per-domain stores.

- **Domain stores** (`src/stores/`): one gpui entity per domain — `ConfigStore`, `BackendsStore` (the backend registry: which inference destinations are configured — refreshed on `Change::Backends`; add/enable/remove ops with optimistic list edits and an `op_error`, and a failed op re-fetches the registry to reconcile its optimistic edit — a failed write emits no `Change::Backends`, so nothing else would), `ModelsStore` (**per-backend model catalogs**: one `BackendCatalog { backend, models: Loadable }` per enabled fetch-based backend — kinds `eidola` and `openai` — each with its own fetch slot keyed by backend id, so one dead server never blanks another's list; `refresh` re-reads the registry then fans out per-backend fetches, `refresh_backend(id)` re-fetches one; the Participants view's model field is the main consumer since the composer's request panel was retired; `models()`/`list()` remain the eidola-catalog compatibility view), `LocalModelsStore` (the engine domain: downloaded/downloading models, running llama.cpp engines, the resolved engine binary, plus every llamacpp backend's scanned directory via `external[_loaded]_models(id)` — refreshed on `Change::LocalModels`; its ops are thin initiating calls, the downloads/engines themselves are core-owned so closing a window interrupts nothing), `AccountStore`, `WalletStore`, `SpacesStore`, `UpdateStore`, `ParticipantsStore` (**per-space** participant membership, keyed `HashMap<SpaceId, Loadable>` like `ModelsStore`'s per-backend catalogs — refreshed on `Change::Participants` (which carries no id, so *every* cached space re-lists); `ensure(space_id)` lazily loads on view open; its CRUD ops — `add` / `update_everywhere` / `set_override` / `remove` — compose `write; re-list` in the space's slot so the store reconciles even bus-less), `TemplatesStore` (the space-template registry — refreshed on `Change::Templates`; `create` / `update` / `remove` / `create_from_space` compose `write; re-list`), plus the data-less `RecordStore` bus-relay (see [The Record](#the-record-window--the-trust-doors-engine-room)) — created once at startup, bundled in `Stores` (held by `AppGlobal`), and handed to every view's constructor. Each store owns its `Loadable` snapshots, its in-flight `Task` *fields* (one slot per operation, replace-cancels), its subscription to the invalidation bus, and *all* mutations of its domain. **No shared busy flag.** Views call store methods and observe the specific store entities they render; they never call `AppCore` directly.
- **`Loadable<T>`** (`src/loadable.rs`): the universal async cell — `NotLoaded` / `Loading` / `Loaded { value, stale }` / `Failed { error, prior }`. A re-fetch over existing data stays `Loaded { stale: true }` (never a blank `Loading` flash); `Loading` is for initial loads only and always implies a live task in the sibling slot.
- **Method shapes:** `refresh_*` is fire-and-notify (the store owns the task; callers observe). `request_*` is awaitable (returns a `oneshot::Receiver`; the *caller* awaits it inside its own slot, so the work dies with the caller — e.g. the onboarding checkout poll). Ownership = cancellation authority.
- **The bus bridge** (`stores::install_bus_bridge`, installed once at startup): a task on `AppCore::runtime()` forwards every `AppCore::subscribe_changes()` event through an mpsc channel into one gpui main-thread loop, which dispatches each `Change` to the owning store(s) (`Change::Config` → config + models, `Change::Wallet` → wallet, …). On `Lagged` it refreshes everything. This is the **only** place tokio receivers touch gpui, and its app-lifetime task is the **one sanctioned `.detach()`** (commented as such) — every other task is an entity-owned field. It returns a **`BusBridge`** handle whose `quiesce()` stops the dispatch loop; the quit hook calls it first (see [App lifecycle](#app-lifecycle--the-app-outlives-its-windows)), which is what makes "no `Change` dispatches after quit begins" true for every emitter rather than for the ones patched so far.
- **`src/bridge.rs`**: the runtime-agnostic `oneshot`/`mpsc` glue. `bridge(core, f)` runs `f` on the tokio runtime and awaits the result on gpui (used inside store `cx.spawn` tasks). The free functions `chat_stream` / `get_space_tree` (the threaded-post render DTO) now back the **`Space` entity**'s owned runner/load tasks (step 3); `list_attestations` / … back the Record reader's owned task slots (per-`Listing` page-fetch slots + one detail slot, replace-cancels). All take the `Arc<AppCore>` out of the `Stores` bundle and hand back a receiver the owning entity awaits inside its own `Task` slot.
- **Stub mode (tests):** `Stores::stub_with(StoresStub { … }, cx)` builds backend-less stores from a declarative fixture (replacing `Core::stub()` field-poking). Each store also has a `stub(...)` constructor. With no backend, `refresh_*`/`request_*` are no-ops, so views that drive async work transition their *local* state and stop at the backend guard — exactly the behavior tests assert. `Stores::for_test(Arc<AppCore>, cx)` injects a real tempdir-backed `AppCore` for store-machinery tests (`tests/stores.rs`).

All view roots are wrapped in `gpui_component::Root` before being handed to `cx.open_window`. **Root is required** — `gpui_component::Input` calls `Root::read(window, cx)` to track the focused input, and panics if the window's root view type isn't `Root`.

**No shared busy flag.** Each store operation has its own task slot, so concurrent refreshes never starve each other — the structural fix for the wave-2 launch-order bug where a shared `busy` gate dropped the first window's model-list fetch behind the startup wallet recovery (see the replay test in `tests/stores.rs`). Multi-part work either composes inside one store task (e.g. `WalletStore::refresh` fetches lifecycle + active credentials in one `bridge` call) or composes by *event* — write through `AppCore`, let the bus drive each store's own refresh; one store never orchestrates another's tasks. View-owned flows that must outlive a single observe (onboarding account-create / checkout / balance poll) use the awaitable `AccountStore::request_*` methods and own the await in the view's own task slot.

## The Space entity

`space.rs`'s `Space` is the per-conversation **domain entity** (`crates/eidola-gui/STATE.md` → "Space entities — shared, registried"). It owns everything about one conversation, so a window opening/closing never re-derives or destroys it:

- **State it owns:** `id: Option<String>` (`None` for a blank ⌘N space until its first exchange persists and assigns one), `transcript: Loadable<Vec<ChatMessageView>>`, the live `streams: Vec<StreamingTurn>` (one entry per in-flight response turn, in start order — each carries its `seq` render key, the responding `participant_id`, the `target_action_id` it's answering, and its own `StreamingResponse` buffers with reasoning + content + disclosure-`expanded`), `failed_turn: Option<FailedTurn>` (who a failed ask asked, about what — the Retry record), and `last_submitted_model` (set before the backend guard on regenerate so behavior tests see what a real regenerate would use). There is **no per-space model selection** — who answers, and with what model, is Participants configuration.
- **Tasks-as-fields (no `.detach()`):** `post_runner: Option<Task<()>>` is the **exclusive mutation slot** for the save-side operations — submit (post + notification plan), post-only, edit, regenerate; a mutation while one is in flight is a no-op (the current UX). `turn_runners: HashMap<u64, Task<()>>` is the **keyed slot map** (STATE.md's "independent per-key work") for streaming response turns: a submit's notification plan can fan out to several participants at once (Participants v1), and each turn owns its own runner + buffers, so concurrent turns stream side by side and one turn's failure never disturbs its siblings. `load_task: Option<Task<()>>` is the supersede slot for the reopened-space initial transcript load.
- **The optimistic user turn carries its reply antecedent** (`optimistic_user_turn`, shared by `submit` / `post_only`). Without it the row is unparented, and `space_view::model::build_tree` chains an unparented row onto the *previous row in the flat list* — the transcript tail, not the post being replied to. Posting into a **branch** then momentarily emptied that branch of all but its first sibling; gpui clamps the parent strip's scroll offset to the single remaining page, and the branch selection was gone by the time the reload restored the second child — the "post in a new branch jumps back to the first branch" bug. Carrying the parent keeps the new post in the exact slot the draft occupied, so the selected branch survives the save with no re-selection dance and no flash. Regression: `space_post_in_a_new_branch_stays_on_that_branch`. **The antecedent it carries is kept honest by `SpaceView::rebuild` → `rethread_drafts`** — see the `space_view` [`model.rs`/`rebuild`](#space-view--tree-navigation-conversation-surface-srcspace_view-wave-6) note: a draft names its parent by *action* id (the tree's node id), so an edit of that post — committed from another window on the same shared `Space`, or by this window's own Edit session, which *keeps* a non-empty fork draft — leaves it naming a generation the reloaded transcript no longer carries. Reply threading follows **item** identity, so the draft is forwarded to that item's current tip on the rebuild that drops it.
- **Submit = post + plan + fan-out.** `Space::submit` appends the optimistic user turn and drives `AppCore::submit` (post + `plan_notifications`); on `NotificationPlan::Turns` it runs one `start_turn` (→ `bridge::respond_stream_as`) per planned responder — concurrent keyed turns, timestamp-ordered siblings; on `Paused { depth, limit }` it emits `SpaceEvent::CascadePaused` (the resumable state the view renders as the quiet cascade notice). Each turn's completion **re-plans the cascade** on its fresh post (`plan_notifications` again — best-effort; a failed plan read is not a failed turn), driving follow-on turns until the guard pauses. `Space::ask(participant_id, target_action_id)` is the **explicit ask** (a separator's Ask, the cascade notice's continue, Retry) — it runs as an independent keyed turn (legal while others stream; duplicate asks and asks during the exclusive mutation are no-ops) and bypasses the cascade guard by construction (`respond_stream_as`).
- **The load-vs-mutation race is serialized inside the entity**, which retired the old `transcript_generation` counter: one entity owns both the transcript loads and every mutation, so they serialize on `&mut self` between awaits. Every mutation entry point (submit / post-only / edit / regenerate / ask) runs the shared prologue `supersede_load_for_mutation` at the moment it is accepted — dropping the in-flight `load_task` (replace-cancels; the same stale-fetch class as the Record listing race from PR #179) and stepping a data-less `Loading` cell back to `NotLoaded` so no spinner outlives its task — and `apply_loaded_transcript` is a no-op while anything owning the transcript's truth is in flight (`is_busy`: the exclusive mutation or any turn; defense in depth). A slow load that finishes after a local mutation cannot clobber it: the mutation's own post-commit reload is authoritative. **Cancelling that load is a debt the operation owes at every exit** (`crates/eidola-gui/STATE.md` → "Concurrency patterns"): the success arms reload inline, and every failure arm goes through a shared completion — `fail_mutation` for the exclusive slot, **`fail_turn`** for one streaming turn — which adopts a `ChatFailed` id, **restarts the transcript load**, and emits `Failed` with the unwrapped source. `fail_turn` removes only *that* turn's buffers + runner (siblings keep streaming; while they do, the restarted load is dropped as stale and their completions re-establish the truth) and records the `FailedTurn`. Without the restart, a cancelled bus-driven refresh (another writer's change) is silently lost, and durable rows a failed mutation itself committed (its `Change::Space` is dropped by the `on_space_changed` busy guard) never render until an unrelated invalidation — the codex finding on PR #206. Replay tests: `space_stale_initial_load_does_not_replace_submitted_prompt`, `space_edit_and_regenerate_supersede_in_flight_load` (behavior), `space_mutation_failure_restarts_superseded_load` (stores). **A failed turn never bricks the space:** the saved post stays (the tail composer reappears and per-post Edit stays live), and **`Space::retry()`** re-asks the *recorded* `failed_turn`'s participant about the same post via `Space::ask` (no re-post) — gated by **`can_retry()`** (a failure is recorded and the exclusive slot is free; sibling turns streaming do *not* block a retry). `retry` **returns the target action id** it ran against so `SpaceView::retry_failed` can `select_path_to` that post's branch *before* the next render — otherwise, in a branched space, the streaming node could attach under whatever branch the user navigated to after the failure (PR #218 review). **The recovery notice's lifetime is owned by the `failed_turn` record, not by the view-local `error` string that events clear:** `SpaceView::on_space_event` clears the notice on `StreamEnded` **only when the space has no `failed_turn`**, so a *sibling* turn of a fan-out succeeding after another failed never silently removes the still-recorded turn's Retry (the notice renders inside the error band). `Space::ask` clears the record only on an **exact `(participant_id, target_action_id)` match** — a real Retry — so an explicit ask of the same participant about a *different* post can't orphan the recorded failure. The notice persists until the turn is retried or **explicitly dismissed** (`SpaceView::dismiss_error` → **`Space::clear_failed_turn`**, which ends the recovery so `can_retry` reads `false`). Recovery-path tests: `space_failed_ask_{can_edit_original,can_re_request,can_add_followup}`, `space_failed_ask_notice_is_dismissible`, `space_failed_ask_retry_selects_the_failed_posts_branch`, `space_turn_failure_leaves_sibling_streams_untouched` (per-turn isolation + retry-beside-siblings), `space_sibling_success_keeps_failed_turn_notice` (a sibling's success does not hide the notice; dismiss ends the recovery), and `space_ask_other_post_keeps_unrelated_failed_turn` (asking the same participant about another post keeps the original Retry); the real fan-out is driven end-to-end in `space_post_fans_out_one_turn_per_planned_responder` (two concurrent turns, independent failure completions).
- **Incoming references are per-space domain state.** `incoming_refs: HashMap<action_id, Loadable<Vec<IncomingReference>>>` plus a keyed `incoming_ref_tasks` slot map (STATE.md's "independent per-key work") holds the reverse index behind the source-post highlights — every current-generation post quoting a given post. It lives here rather than in a window because it is durable, queryable, per-space data: two windows on one space must paint identical highlights, and `Change::Space` must refresh both (STATE.md — "views never own domain data"). `ensure_incoming_references(action_id)` is the lazy, idempotent per-post load the view calls for the posts it actually renders (highlights are decoration, so a not-yet-loaded index paints nothing rather than a spinner, and a failed one is not re-requested every frame). `invalidate_incoming_references` drops the whole cache; `SpacesStore::notify_space_changed` calls it on **every** live space, not just the changed one, because a quote written in space B changes what space A should highlight and the bus event carries only B's id.
- **Trace disclosures are per-space domain state.** `traces: Loadable<HashMap<anchor_action_id, Vec<PostTrace>>>` plus one supersede fetch slot holds `AppCore::space_traces` — every turn's tool rounds and decline decisions, the actions `get_space_tree` deliberately collapses out. It lives on the shared entity for the reason the reverse index does (two windows on one space must disclose the same activity), but is loaded **once per space** rather than per post: one query answers the whole space, and a turn's rounds are by construction written in the space that ran them — so `SpacesStore::notify_space_changed` calls `invalidate_traces` on **the changed space only** (contrast `invalidate_incoming_references`, which sweeps every live space because a quote in B changes what A highlights). `ensure_traces` is the lazy, idempotent fetch the view calls once per frame; a blank space is left `NotLoaded` so the index loads the moment its first exchange assigns an id. `traces_expanded` rides here too, like `reasoning_expanded` — a reload, or the other window, must not collapse a disclosure under the reader. It is keyed on **`PostTrace::id`** (the turn), not the anchor: a post can carry several turns' disclosures.
- **Reasoning is durable.** app-core persists a turn's captured thinking as a `thinking` content block beside the answer's `text` block (`TurnPrep::persist_turn`; see the workspace `AGENTS.md`), so a reopened space still carries it. `ChatMessageView::from_post` splits the two: `text` blocks are the reading column (and the only quotable spans — a `PostBlockSpan` is never minted for a thinking block), the `thinking` block becomes `reasoning`. The live per-turn buffer is still attached at finalize (by `response_action_id`) so the disclosure never blinks out in the frame between the stream ending and its reload landing, and `merge_from_db` treats the prior snapshot's reasoning as a **fallback only** — it fills a row the tree didn't carry and never overwrites what the tree supplied (overwriting would blank a reloaded space's disclosure with a stale `None`). `reasoning_expanded` is pure view state and is always carried forward, so a reload can't collapse an open disclosure under the reader.
- **`EventEmitter<SpaceEvent>`** — `MessagesChanged` / `StreamDelta` / `StreamEnded` / `Failed(AppError)` / `CascadePaused { depth, limit, target_action_id }`. Plain `cx.observe` covers re-render; the events let a view react *semantically* (tail-scroll on `StreamDelta`, degraded-onboarding routing on `Failed`, the cascade notice on `CascadePaused`). `StreamEnded` is also emitted when a plain post persists — either way the space now has a durable id, which is what the registry's blank-space adoption keys off.

**The registry lives in `SpacesStore`** (`HashMap<SpaceId, WeakEntity<Space>>`):

- `open(id)` is **get-or-create with join-existing**: a live registered entity is returned as-is, so two windows opening the same space share **one** `Space` (and its single transcript load). This is the structural fix for wave-2 bug 4 — a submit/stream in window A appears in window B live, because both render the same entity. Replay/behavior tests: `space_joins_shared_entity_for_same_id` (behavior) and `spaces_registry_joins_existing_and_blanks_are_distinct` (stores).
- `blank()` mints an id-less space for ⌘N (instant, no load). The registry **adopts** it once its first exchange assigns an id — whether that exchange **succeeds** (`StreamEnded`) **or fails after the space was persisted** (`Failed`). `SpacesStore` subscribes to both events, reads the now-present `id()`, and keys the entity under it (the shared `adopt_blank` path; a no-op when the id is still `None`, e.g. a pre-persist `Failed` like `NoAccount`) — so a later `open(that_id)` joins the same entity. The id reaches a *failed* blank because app-core wraps any post-persist error as `AppError::ChatFailed { space_id }`; `Space`'s failure arm reads `chat_space_id()` off the wrapper into `self.id` before emitting `Failed` (with the unwrapped source, via `root()`, so the view's error routing sees the real variant). This closes the former known gap where a blank window's first exchange failing never taught it the persisted id (the id only arrived via `ChatResult` on success). Regression test: `blank_space_adopts_id_on_wrapped_failure`.
- `Change::Space(id)` from the invalidation bus is routed (in `stores::dispatch_change`) to `SpacesStore::notify_space_changed(id)`, which tells the live registered `Space` to refresh its transcript (how an in-process CLI write to the same space appears). The space ignores the refresh while any of its own operations is in flight (each turn/mutation reloads on its own completion).

## Onboarding window

`onboarding/mod.rs`'s `OnboardingView` is the production onboarding surface: a standalone **singleton window** presenting **one continuous scrolling page** of stacked **slides**. The window opens **matching a new space window** (the same square "writing surface" — `lib.rs::writing_surface_side`, shared with `open_chat_window` — so onboarding feels like the page it leads into), but each **slide is sized by its content** (a `min_h` of one window, growing past it when the prose is longer than the window — see the Snap bullet), *not* fixed to the window. It **supersedes** the retired in-chat empty states (deleted with `chat.rs`). Opened two ways: automatically at launch when `ConfigState` has no account **and the eidola backend is enabled** (`run()` checks `!has_account || !has_account_secret` synchronously, then gates on a spawned `list_backends` read — a user who chose "continue without an account" disabled the backend, and their choice must silence the auto-open; a failed read errs toward showing the dismissible window), and via the Eidola menu → **Get Started** (`GetStarted` action, singleton like Settings).

**At launch onboarding opens *instead of* a blank space, not on top of one** — there is nothing to ask yet, so a space behind the door is premature and just one more window to close. That makes the launch window choice exclusive (`run()`: onboarding when account-less + eidola-enabled, otherwise `open_main_window`) and, in the account-less case, one spawned `list_backends` read behind launch — the first window appears after that read, not before it. The corollary is that **onboarding then owes the user a window on the way out**: `OnboardingView::leave` (the deliberate exits — `skip_account` / Done / Later) opens a blank space via `crate::open_blank_space_window` **only when onboarding is the last window** (`cx.windows().len() <= 1`; from the Eidola menu there's a window behind it already, and a surprise second blank space is not what "Later" means). **Order is load-bearing: open first, close second.** `Window::remove_window` only sets a `removed` flag — gpui tears the window down as the update unwinds (`app.rs`'s `trail`), fires the close observers, and *then* runs its own quit-on-empty check (the `QuitMode` — `LastWindowClosed` for a windowed Linux launch; see [App lifecycle](#app-lifecycle--the-app-outlives-its-windows)), so the replacement must already be in `cx.windows()` by then; a `cx.defer`'d open (the Library's row-click pattern) would land after the app had quit. A bare ⌘W / red-button dismissal deliberately stays a plain `remove_window` — closing the only window means closing it (macOS lingers dock-only and reopens via `on_reopen`; Linux quits, per the last-window-closes rule). Behavior tests: `onboarding_skip_account_disables_eidola_and_hands_off_to_a_space` and `onboarding_leaving_with_a_window_behind_opens_no_extra_space`. Borrows the space view's look wholesale — the Newsreader prose column (`space_view::prose_style`, a disabled `MarkdownEditor` per slide, **left-aligned** in a centered reading column, with the **CTAs center-aligned in normal flow *beneath* the prose** — never overlapping it, even when a long slide overflows a small window), the transparent-titlebar drag band (`titlebar::drag_band`), a right-edge **scroll indicator shown only while scrolling** (`gpui_component::scroll::Scrollbar` in `ScrollbarShow::Scrolling` mode — drop-in, bound to the page scroll handle; the same control the rest of the app shares via `crate::scrollbar::vertical`, see [Scroll indicators](#scroll-indicators-srcscrollbarrs)), and a **proximity snap** (CSS `scroll-snap-type: proximity`: settle onto a slide only when a gesture ends *near* a boundary — see the Snap bullet — reusing `space_view::nav`'s `ease_out_cubic` / `snap_duration` and the new `proximity_snap_target`).

- **Structure — stateful view + stateless slide components.** `onboarding/mod.rs` owns all state (the reveal machine, scroll/snap physics, async account ops) and a single `render_slide` **router** match that instantiates the matching slide component with props + boxed callbacks. Each slide in `onboarding/slides.rs` is a self-contained `#[derive(IntoElement)]` + `RenderOnce` component — gpui's analogue of a React functional component — carrying its own `MARKDOWN` const, extras (links, inputs, credentials, plans), and CTAs, so one slide reads top-to-bottom in one place. The slide's disabled prose editor is **element-owned state** (`window.use_keyed_state`, keyed per slide in `slide_frame`) — the `useState` analogue — initialized once and evicted by the framework the frame after the slide stops rendering (branch truncation), which is safe *only because* every revealed slide paints every frame (a plain `flex_col` stack — the scroll container holds the slides as its **direct children** so the page scroll handle tracks a per-slide child bound — with no virtualization); if the slides ever render conditionally or through `list()`, lift that state back onto the view (the retired chat view's `text_states` lesson: element-owned parsed state dies with an unmounted `list()` item). State the view must read or that must outlive a frame (the id/secret `InputState`s read by `begin_verify`, the `agreed` consent bit, async-op results and task slots) stays lifted on the view. Flow sequencing (which slide a CTA reveals next) deliberately stays in the router so the branch structure is visible in one match; the components are pure presentation over lifted state.
- **Reveal state machine.** `revealed: Vec<Slide>` starts as `[Slide::Pause]`; only revealed slides render. Each slide's ghost-button CTA calls `reveal(after, next)` which appends `next` after `after` — animate-scrolling to it — and, when the choice **changes** (a different `next` than what currently follows `after`), **truncates the stale downstream slides first**. So re-choosing a branch upstream (new-account vs. existing-account at "Get started") replaces the whole downstream tail. Idempotent when `next` already follows (just re-scrolls). `reveal` records a `pending_scroll` index that `render` consumes (where `window` is available) to start the glide, so the async account-op callbacks can reveal without holding a `Window`.
- **Back navigation.** Every slide **past the first** carries a quiet up-chevron "back" affordance (`slides::back_button`, probe `onboarding/back/{index}`) pinned near the top (just below the titlebar drag band) — a *visible* alternative to the scroll-back gesture, which many people don't think to try. Clicking it glides to the previous slide via `glide_to_index(idx - 1)`. Both directions of flow sequencing live in the parent, so the back wiring is in the `render` router (which wraps each non-first slide in a `relative` container + the overlay), not on the stateless slide components. The `pinned_y` resting offset is set synchronously by the glide, which is the behavior test's seam (`scroll_to_slide` + `pinned_y_for_test`).
- **Slides:** `Pause → Tool → Control → Responsibility → GetStarted`, then the branch: **new** (`CreateAccount → NewAccount → Purchase`) or **existing** (`ExistingAccount → Purchase`) — or neither: `GetStarted` carries a quiet third choice, **"Continue without an account — on-device models only."** (`OnboardingView::skip_account`, probe `onboarding/cta/skip-account`), which disables the `eidola` backend through `BackendsStore` and closes the window; reversible any time in Settings → Backends. Conditional content within a slide is state-driven: `CreateAccount` carries a **required agreement checkbox** (`agreed: bool`) that gates its "Create a new account." button (disabled until checked) and shows a create error inline; `NewAccount` shows the freshly-minted id/secret (mono, with Copy affordances); `ExistingAccount` shows the balance-check result and swaps its CTA set (verify → then purchase/done); `Purchase` renders `plans::plan_rows`.
- **Construction — content-sized slides, one scrolling page.** `slide_frame` lays each slide out as a `v_flex` with **`min_h(chrome::content_size().height)`** (one window, the content box — not the raw surface, so Linux CSD shadow padding is excluded) and **`justify_center`**: a short slide fills exactly one window and centers its reading column vertically; a long slide **grows past** the window (min-height, never fixed) and the page simply scrolls to it. The reading column (prose + `extras`) and the **CTA group sit in normal flow, the CTAs last** — so a slide's call-to-action is always *after* its prose and can never overlap it. This replaced the old fixed-`h(window)` slides whose vertically-centered prose overflowed onto the CTAs and, under mandatory snapping, left the overflow unreachable — the exact small-window breakage this rework fixed.
- **Snap = proximity, not mandatory** (CSS `scroll-snap-type: proximity`). While the finger is down (`Moved`, `!owning`) the page scrolls natively and we record the last step as the release velocity (`last_dy`). At finger-lift (`Ended`) `nav::proximity_snap_target(slide_tops, viewport_top=-offset.y, last_dy, proximity=content_h*SNAP_PROXIMITY_FRACTION)` decides over the **live slide-top offsets** (`slide_tops` reads the page scroll handle's per-slide `bounds_for_item`, so it copes with slides taller than the window): a rest **near** a boundary (or a flick beside one) returns `Some(index)`, a rest **deep in a slide's content** returns `None`. On `Some` we `glide_to_index` — set `owning`, pin the resting offset, drive our **own** ease-out glide (`drive_snap` frame loop) — and **suppress** the OS momentum that follows (in this gpui pin macOS delivers post-lift momentum as `TouchPhase::Moved` with **no end signal** — `gpui_macos` reads only `NSEvent.phase()`, so `phase = None` maps to `Moved` — so we `stop_propagation` + **`reassert_scroll`** onto our glide/pin on every trailing step, like `nav.rs::reassert_horizontal`). On `None` we **release** — clear `owning`/pin/glide and let native momentum carry the page to rest where the reader is, never yanking them off a long slide. A fresh `Started` releases ownership so the user scrolls freely again. **Reveal and back glides are programmatic** — `glide_to_index` computes the target slide's exact top (a just-revealed slide's top is its predecessor's measured bottom) and always lands on it; proximity governs only *user* gestures. `glide_to_index` falls back to a one-window-per-slide estimate before the first paint. `SNAP_PROXIMITY_FRACTION = 0.25` (a quarter window). `proximity_snap_target` is a pure fn unit-tested in `nav.rs`.
- **Account ops** go through `AccountStore`'s awaitable `request_*` methods, each owned in a view task slot (dies with the window): `begin_create` → `request_account_create` (on success stores id/secret from the now-`secret`-carrying `AccountCreateResult`, refreshes config + balances, reveals `NewAccount`); `begin_verify` → `request_verify_account` (a new store method: sets the entered credentials, fetches the balance, and **rolls the write back on failure** so a bad attempt strands nothing — success links the account); `begin_checkout` → `request_checkout` → `cx.open_url`. The server collapses "no such account" and "wrong secret" into one `401` (anti-enumeration), so `verify_error_copy` shows those as one honest message; other failures surface their real reason.
- Tests: `onboarding_*` in `tests/behavior.rs` (first-slide start, reveal advance + idempotence, branch re-choice truncation, back-arrow glide to the previous slide, verify field-guard, stub backend-gating, **and `onboarding_slides_size_to_content_and_grow_on_small_windows`** — the min-height-and-grow contract: on a deliberately small window the short opening slide measures exactly one window tall while the long narrative slides grow past it, proving content-sizing over the old fixed-window height); the proximity decision itself is unit-tested as the pure `proximity_snap_target` in `nav.rs`; a probe test in `tests/probe.rs` (`onboarding/cta/*`, `onboarding/input/*`, `onboarding/back/*`). Driver scene: `onboarding` (note: the headless test dispatcher does not pump the `on_next_frame` glide animation, so reveal/back scrolls don't visibly complete under `just driver` — behavior tests assert `pinned_y` synchronously instead; the layout at rest is what the driver verifies). **Deferred:** distinguishing not-found vs. wrong-secret (server-limited), a "manage subscription" affordance (no portal API), and a post-checkout balance poll (checkout opens the browser; balance reflects on the next refresh).

## Theme — Circadian (`src/theme.rs`)

The theme has **two user-facing axes**, persisted in app-core's config and surfaced in Settings → General → Appearance:

- **Day/night** (`AppearanceSetting`, config key `appearance`): `system` (default — track the OS light/dark appearance), `day` / `night` (pin one family), or `auto` (follow the sun — day is between timezone-approximated sunrise and sunset; fixed 06:00–18:00 without geography).
- **Time of day** (`TimeOfDayTint`, config key `time_of_day_tint`): `on` (default) tints the palette with the light's `LightCharacter` *right now* — cool around sunrise, neutral at solar noon/midnight, warm around sunset; `off` pins the character to the user's **`light_character`** config choice (`cool` / `neutral` default / `warm`; serde aliases keep the pre-rename `bluish`/`orange` values parsing), selected in a third Settings row that appears only while the axis is off. Together the axes make **six palettes** (Dawn, Sunrise, Day, Sunset, Dusk, Night) anchored to the real solar day.

**Type scale (`font_scale`)** is the theme's third persisted axis — the single lever behind View → Actual Size / Zoom In / Zoom Out (and the Settings → General **Text size** row `A− / A+ / Reset`). It rides `ThemeSettings.font_scale` (from `ConfigState.font_scale`, wired by `theme::wire_config` like the other axes) and multiplies the type ramp at exactly **two** anchors, because the app has exactly two font-size roots: (1) the theme's UI font size (`UI_FONT_SIZE` = 14, scaled in `circadian_day`/`circadian_night`) — gpui-component installs this as the window **`rem_size`** (`root.rs` `set_rem_size(cx.theme().font_size)`), so scaling it scales **every** `rems()`-relative chrome size, line height, and padding in one move; and (2) the prose reading size (`space_view::prose_style`, the one place the ramp is spelled in absolute pixels rather than `rems()`, so it multiplies `theme::font_scale(cx)` itself — its `rems()`-based leading and paragraph gap ride the scaled `rem_size` and stay proportional for free). The space view's height cache is keyed on `(body_width, scale)` — a zoom reshapes every post, so `Layout::ensure_width(width, scale)` clears the cache exactly like a column change, and `estimate_post_height` multiplies by `Layout::scale()` so unmeasured posts estimate at the current zoom. Scaling is clamped to `[0.8, 2.0]` (`FONT_SCALE_MIN/MAX`) and stepped through the discrete `FONT_SCALE_STEPS` ladder in app-core. Pixel-perfect fixed-px chrome (the titlebar reserve, the Settings nav-band width) does **not** scale — at high zoom a wide nav label may wrap; acceptable per the design's "chrome may be excluded" allowance.

**Geography from the timezone** (`src/solar.rs`): the IANA zone name (from `$TZ` or the `/etc/localtime` symlink) resolves to representative coordinates via the OS's own tzdb tables (`zone1970.tab` on Linux, `zone.tab` on macOS — same format), and the standard sunrise equation (pure fn, unit-tested against solstice day lengths + polar cases) yields today's `DayPhases` — no location permission, no network, no chrono. `canonical_hour` warps wall time so actual sunrise lands at canonical 06:00 and sunset at 18:00 (halves stretch linearly; `Clock` fallback is the identity), and the fixed slot table reads unchanged on the warped clock. The tinted slots hug the sun's events — ±2 canonical hours, since the real transitions are brief: dawn 04–06 + sunrise 06–08 cool, sunset 16–18 + dusk 18–20 warm, with long neutral middles (day 08–16, night 20–04) — so December's sunset character arrives ~16:30 and June's ~20:30. Degrades honestly: geography-free zones (`UTC`, `Etc/*`, POSIX `TZ` specs) and unreadable tzdb → `DayPhases::Clock` (the old fixed schedule); polar no-event days → `PolarDay`/`PolarNight` (clock-slot characters; `auto` forced day/night). The tzdb coordinate lookup is memoized per zone name in the theme global (`zone_cache`); the zone name is re-checked each tick (a readlink), so travel is picked up automatically.

The tinted variants are **derived, not hand-authored**: `tinted` blends every color of the neutral palette a few percent toward a per-family blue/ember anchor (`tint_spec`; the dark family blends harder), preserving alpha suffixes and relative contrast — so tuning a neutral color tunes all six palettes. One targeted exception: the **day** variants tint the near-white paper grounds (`DAY_PAPER_SOFT_TINT` — background, cards, title/tab bars, the `muted` separator band) at a reduced 0.6× amount, so the sheet stays continuous with neutral day while the cast reads in the chrome and mid-tones. The day palette's chip/chrome family (secondary/accent surfaces, sidebar grounds, segmented tab bar, list rows, group box) is **neutral grey in the base palette** — luminance-matched greys in the separator band's family, with warm brown foregrounds (day's mirror of night's cool-chip/warm-text tension); warm cream chrome under the cool cast read muddy, and neutral chrome takes every cast cleanly, so no per-character exception is needed. `resolve(settings, system_is_dark, now_min, phases)` is the pure core (unit-tested); `apply` is the one path that ever changes the global `Theme` (derives both `ThemeConfig`s, sets the mode, refreshes every window).

Wiring:

- `theme::install` (after `gpui_component::init`) loads fonts and applies the **neutral** palettes under the system appearance — tests, the visual harness, and the driver stop here, so their palettes are deterministic (never wall-clock- or sun-tinted).
- `theme::wire_config` (production `run()` only) seeds `ThemeSettings` from the `ConfigStore` snapshot, re-applies on every config change (the Settings chips write through `ConfigStore::set_appearance` / `set_time_of_day_tint` / `set_light_character` → `Change::Config` → bus → store refresh → this observer), and starts a once-a-minute clock task that re-applies when the resolved (mode, character) pair crosses a slot boundary. Both the observation and the clock task are app-lifetime (the sanctioned `.detach()`).
- Each opened window subscribes via `theme::observe_window_appearance(window)`, which routes through `apply` — so toggling macOS Light/Dark updates live in `system` mode and is correctly ignored under a pinned/auto appearance.
- Local civil time comes from `libc::localtime_r` (no chrono dependency; the schedule is about the user's local day, unlike the Record's UTC timestamps); `tm_gmtoff` supplies the UTC offset the solar equation maps events through.

The base palettes are **neutral** — the light has no cool/warm character at solar noon or solar midnight; character is applied only in the ±2h windows around sunrise/sunset by the tint (cool toward dawn, warm toward dusk), which is how the chrome tracks the character of real light through the embodied day. Two fixed backgrounds anchor them (the product's "good paper at noon, reading lamp at midnight" pair): **Day `#ffffff`** — a neutral near-white paper; the base's only warmth is a few accent *foregrounds* (warm-brown chip labels), never the ground or chrome (the ground takes a cast only under the tint) — and **Night `#15191e`** — a cool blue-grey dark whose elevated surfaces (cards, chips, borders, rows) all follow the anchor's blue-grey ramp (R < G < B throughout), while text stays warm-grey (`#d4d0c8`) and the brand stays warm orange (`#c39669`). The warm-on-cool night tension is deliberate; don't "fix" it by cooling the foregrounds. An earlier palette was seeded from the marketing site — the site is no longer the reference, these anchors are.

**Body font is Newsreader 16pt** (SIL OFL 1.1) — six static TTF instances (Regular, Italic, Medium, SemiBold, Bold, BoldItalic) from `productiontype/Newsreader`, bundled in `crates/eidola-gui/assets/fonts/Newsreader16pt-*.ttf`, embedded via `include_bytes!`, and registered with `cx.text_system().add_fonts`. License at `assets/fonts/OFL.txt`.

We ship statics rather than the variable upright + italic because **gpui's macOS text system does not apply variable-font weight axes**: `gpui_macos::text_system::add_fonts` registers each TTF as one face with the properties of its default instance, and `font_kit::matching::find_best_match` picks the closest face per weight request. With only the variable TTFs registered, every weight request — `**strong**` (BOLD), headings (SEMIBOLD/BOLD/MEDIUM), etc. — resolved to the Regular default and rendered un-bold. Six static faces make `find_best_match` pick correctly. The **Medium (500)** face backs the prose heading weight (`space_view::prose_style` pins every heading to Medium and lets the size ramp carry hierarchy — see [Prose typography](#prose-typography--book-metaphor)); without it a 500 request falls back to Regular. Family name in the theme is `"Newsreader 16pt"` (the typographic family — nid 16 — that all six faces report; the non-RIBBI Medium/SemiBold set nid 16 explicitly to override their nid 1 = `Newsreader 16pt Medium`/`… SemiBold`, the canonical workaround for the Windows OS/2 4-style-per-family limit).

## Prose typography — book metaphor

Conversation prose is the long-form reading surface, so it gets typography of its own rather than inheriting the 16px UI baseline (settings/wallet/account stay on the theme default). The knobs live in `space_view/mod.rs` — `PROSE_FONT_SIZE` (17px), `PROSE_LINE_HEIGHT` (1.65), `PROSE_PARAGRAPH_GAP` (1.5) — and feed `space_view::prose_style`, the `MarkdownStyle` shared by every post body *and* the composer, so a post renders pixel-identical to what the user typed:

- **Body 17px / 1.65× leading.** Newsreader at 17 sits in proportion with a real book page; 1.65 is the readability sweet spot for serifs at this size.
- **Reading measure capped at `BODY_MAX_WIDTH` (600px)**, centered between the two symmetric gutters (`layout::body_width`) — ~65–72 chars/line, the canonical long-form measure.
- **Heading ramp anchored to the body size** (h1 2.5× / h2 1.75× / h3 1.25× / h4–h6 1.125×), every level at a uniform **Medium (500)** weight (`heading_weight`): size carries the hierarchy and the flat weight keeps headings from shouting — mirrors the website's prose ramp (`www/static/site.css`), the shared source of truth for both surfaces. (The editor crate's *default* ramp is still the flatter h1 1.5× / weight-carries-hierarchy scheme; only the app's prose surface overrides it.)
- **Paragraph gap 1.5 rem** — clear paragraph breaks without the run-on tightness of a chat tool.
- **Inline code in Courier New.** Mono at the same nominal size as a low-x-height serif reads visually larger; Courier New's x-height (0.423 em) matches Newsreader's (0.426 em) almost exactly, where Menlo (0.547 em) read ~28% larger. Fenced code blocks keep Menlo.

**Identity travels with each post**: the byline gutter is part of the post row and scrolls with the body it labels — there is no separate persistent participant indicator, and neither the title band nor the composer carries model chrome (who answers, and with what model, is Participants configuration — `Space > Participants…`). The gutter stacks up to three lines: the author (small bold — "You", or an agent turn's **participant label**), the serving **backend's display name** (quiet second line, assistant rows only — "Gemma 4 E2B" over "Local" instead of the raw `gemma-4-E2B_q4_0-it@local` id; suppressed when it would just repeat the author line, e.g. a synthetic "Eidola" row), then the time. The split comes from `SpaceView::model_display` (in `space_view/mod.rs`), resolved into the `PostData` snapshot at `rebuild` — which the `local_models`/`backends` store observers also trigger, so a display name landing after the transcript re-labels the gutter — and the minimap's a11y labels inherit it for free; an in-flight turn's byline is its participant's label, resolved live via `SpaceView::participant_label`. The raw selection id remains what's persisted (participant labels, `action.model`).

## WindowInput — per-window modifier state

`src/window_input.rs` — `WindowInput` is a **per-window gpui entity** that holds the live keyboard modifier state for one window. It exists because `ModifiersChangedEvent` in gpui (at our pinned commit 969a67fc) dispatches along the **focused element's ancestor path only** — a listener on a sibling branch of the focused node never fires. Without `WindowInput`, a Settings pane's `on_modifiers_changed` listener was dead while a text input in a different pane had focus (wave-2 bug 2).

**Pattern — one listener per window, registered on the root view only:**

- Each `open_*_window` builder creates one `WindowInput::new(cx)` and passes it to the view constructor.
- The root view (`SpaceView::render` root div, `SettingsView::render` root h_flex) registers the window's **single** `on_modifiers_changed` listener and calls `wi.update(cx, |wi, cx| wi.update_modifiers(event, cx))`.
- Descendant views (`GeneralView`) observe the entity (`cx.observe(&window_input, …)`) and read `window_input.read(cx).alt_held()`. They never register their own `on_modifiers_changed`.

**Rule — enforced structurally, not by convention alone:** No view below the root may call `.on_modifiers_changed(…)` anywhere in its `Render` impl. The `WindowInput` entity is the only mechanism for sharing modifier state within a window. Adding a new ⌥-affordance in any descendant view means: observe `window_input`, never add a second listener.

**Staleness:** gpui at 969a67fc has no window-activation or "window became/resigned key" observer hook. If the user switches away while holding ⌥, `alt` may linger `true`. This is self-healing: the next `ModifiersChangedEvent` in this window writes the current state. The stale `true` is transient and harmless (the ⌥ reveal is a cosmetic affordance with no irreversible action).

**Test helper:** `WindowInput::set_alt_for_test` mutates `modifiers.alt` directly (no `ModifiersChangedEvent` construction) for snapshot tests that need to render the revealed state without synthesizing platform events. Behavior tests use `VisualTestContext::simulate_modifiers_change` to drive the real dispatch path through the root listener.

## Streaming chat

The **`Space` entity** drives response turns via `bridge::respond_stream_as` (which wraps `AppCore::respond_stream_as` from `crates/eidola-app-core/`) inside its keyed `turn_runners` slots — not detached view tasks. The core's streaming method posts `stream: true` to the responding participant's backend and forwards each SSE chunk's `delta.content` as `ChatStreamEvent::ContentDelta` and `delta.reasoning_content` / `delta.reasoning` (vLLM-style) as `ChatStreamEvent::ReasoningDelta`. The terminal `ChatResult` is delivered on a oneshot after the delta channel closes.

While streaming, each in-flight turn's `StreamingTurn` in `Space::streams` holds its live `reasoning` + `content` buffers and a disclosure-`expanded` flag, and each delta emits `SpaceEvent::StreamDelta`. `SpaceView` renders every turn (`post.rs::render_streaming_body(seq, …)`) as a streaming leaf attached at its **target** post — concurrent replies to one post land as timestamp-ordered sibling branches (each with its own per-`seq` body editor in `streaming_bodies` and its own "Thinking…" disclosure toggling `Space::toggle_streaming_reasoning(seq)`; the band's branch **dots include streaming leaves**, tinted `info`, so a fan-out's second stream is discoverable and navigable while it runs). The disclosure **survives finalize and reload**: reasoning is persisted as a `thinking` content block, so the same toggle renders on the finished post (`render_post_body` → `Space::toggle_message_reasoning`) whether the turn just ended or the space was reopened weeks later. On done, the turn's runner removes its stream entry, reloads the transcript from the DB (which now carries the thinking block), attaches the captured reasoning to the persisted response (by `response_action_id` — a belt-and-braces cover for the frame before the reload lands), emits `StreamEnded`, and re-plans the cascade. **A turn waiting on its engine says so**: while the responding participant's model is an engine-served one that is still *warming*, the streaming leaf leads with a quiet **"Loading model…"** line in the same slot the "Thinking…" toggle occupies — a readout (`Role::Label`, probe `space/streaming/{seq}/loading`), not a control. The correlation is pure GUI (`SpaceView::turn_engine_is_warming`) over two snapshots the view already re-renders on: the turn's `participant_id` → the participant's effective `model_ref` (`ParticipantsStore`) and that model's `LocalModelStatus::Loading` (`LocalModelsStore`, refreshed on `Change::LocalModels`, which app-core emits the moment a request-triggered load reserves its engine). A remote backend, an unknown participant, or a loaded engine shows nothing — the silence is then genuinely the model thinking, and saying otherwise would be a lie. Regression: `space_streaming_turn_reads_loading_model_while_its_engine_warms` (`tests/probe.rs`); driver scene `space_model_loading`. **The toggle has three states**, all in the shared quiet-verb look (`post::verb_button` — the same family as Edit / Regenerate / Save / Cancel, so the disclosure reads as a control rather than a caption): "Thinking…" while the turn is live, then "Show thinking" / "Hide thinking" once it has finished (`post::thinking_labels`, a pure fn; the accessible name always says what the click *does*, even while the visible label narrates the stream). Because the streaming state lives on the shared entity, a second window on the same space watches the same buffers fill (wave-2 bug 4).

The CLI uses streaming too: `crates/eidola-cli/src/main.rs` pumps `ContentDelta` to stdout and `ReasoningDelta` to stderr (dimmed and prefixed with `thinking: ` when stderr is a TTY) so a piped stdout still captures only the final answer.

Refund handling for streaming differs from blocking only in *where* the refund token comes from: SSE responses have no inline JSON body to carry it, so the streaming path always goes through the `/v1/credentials/refund` recovery endpoint after the stream ends. Same recovery endpoint as the existing network-error fallback in the blocking `chat()`.

## Space view — tree-navigation conversation surface (`src/space_view/`, wave 6)

`SpaceView` is the **window root** for a conversation. It replaced `ChatView`, whose every remaining feature has since migrated — onboarding to its own window, inline edit/regenerate as the post action-gutter verbs, and the finalized-reasoning disclosure onto the post body — and `chat.rs` is deleted. (The interim ⌥ model picker / request panel migrated here too, then was retired by Participants v1 — see `composer.rs`/`post.rs` below.) It renders a space as the `examples/eidola_space.rs` mockup does: a tree of **recursively-nested scrollers** — vertical scroll walks the selected root→leaf path; horizontal scroll flick-**snaps** between sibling branches, each page carrying its *whole subtree* so a branch slides sideways as a unit — with a right-edge topology **minimap** and a floating/docking **composer**. It is a window-local lens over the shared `Entity<Space>` (registry join-existing), constructed as `SpaceView::new(stores, space_id, window_input, window, cx)`.

Decomposed into focused submodules (impl blocks split across files on one `SpaceView`):

- `model.rs` — the UI tree. `Space` loads a flat `Vec<ChatMessageView>` (DFS pre-order, each row carrying `parent_action_id`); a per-frame-cheap `PostData` snapshot (rebuilt only on transcript change, `SharedString` refcounted clones) feeds `build_tree`, which relinks the flat list into `TreeNode`s. **Unparented rows chain onto the previous row** (an optimistic user turn, a synthetic test row) so the conversation forms one spine even when only some rows carry links — a real `get_space_tree` result has exactly one unparented row (the root). Pure + unit-tested (`node_ref` / `parent_of` / `path_ids` / `attach_overlay`). `NodeSrc` is `Msg(idx)` | `Streaming(seq)` | `Draft`; each in-flight turn is a synthetic leaf (`streaming_node_id(seq)`) attached at its **target** post — so a fan-out's concurrent replies to one post land as timestamp-ordered siblings; a target-less synthetic turn falls back to the selected leaf — and the composer draft attaches at its reply target, all via `attach_overlay`. **`PostData` carries `item_id` beside `action_id`**, because a window-local reference to a post can outlive the generation it names: `SpaceView::rebuild` → **`rethread_drafts`** forwards any draft whose parent action id vanished from the incoming snapshot to that item's current tip (resolving the vanished id through the *outgoing* snapshot). Without it a draft that outlived an edit of its parent — another window's edit on the shared `Space`, or this window's own Edit session keeping a non-empty fork draft — mis-threaded three ways at once: `effective_tree` re-attached it as its own root, and `composer::send_active_draft` (which only forwards a parent it can find among the current posts) dropped the antecedent entirely, so the post landed **durably at the space tail** instead of beside its sibling. Regression: `space_draft_rethreads_onto_an_edited_parents_current_tip`.
- `layout.rs` — **the performance core.** The mockup re-measured every post every frame (a `canvas` per post) and rendered the whole tree → O(all posts) of text shaping. Here a `Layout` height cache (interior-mutable, `Clone`) holds each post's measured height keyed by node id for the current width; only posts intersecting the viewport (± `VIRT_MARGIN`) render the real `MarkdownEditor` (carrying a measuring `canvas` that refreshes the cache) — off-screen posts render as **sized placeholders** of the cached/estimated height (`estimate_post_height`). So per-frame shaping is bounded to *visible* posts and the document total/scroll-range/minimap stay correct. **The cache is keyed on the reading-column width (`body_width`), not the raw window width** — a post's measured height depends only on the column, which is capped at `BODY_MAX_WIDTH` above a ~836px window, so resizing a wide window doesn't reflow anything and (correctly) doesn't invalidate the cache. Keying on the raw width instead cleared the cache on *every* resize, dropping every post back to a rough `estimate_post_height` and jittering the page — and the minimap, which sums the same heights — as the near-viewport posts re-measured estimate→real, *even where no text reflows* (the resize-jitter bug; the warm pass only ever measures posts within ~a viewport of the fold, so the far off-screen posts it can't reach stay estimated and flip visibly on each clear). A resize that leaves `body_width` unchanged is now a no-op for the cache; a genuine column change (narrow windows) still clears. Regression: `space_resize_above_column_cap_does_not_churn_height_cache` asserts a wide-window resize bumps `Layout::clears()` zero times, a narrow one non-zero. **The warm pass** closes a related gap: an off-screen post measuring lazily (estimate→real) the moment it scrolls into view *shifts the whole document below it* — which jumps the composer's dock/float threshold (and its drop shadow) and resizes minimap columns as you approach them. So whenever the selected path has an unmeasured post (`path_has_unmeasured` — a cold open, a width change, a freshly added post), `render` arms `warm_remaining` and forces **every** on-path post to render real for a couple of frames (prepaint fires for off-screen elements, so they measure without being shown), establishing the real document height up front. It's self-terminating (stops once the path is fully measured) and only inspects the on-path posts, never off-branch siblings (which never render on the path and would keep it armed forever). This file also holds the selection/height computations (`active_child_index`, `selected_levels`, `selected_subtree_height`, `placeholder_doc_top`) that read the scroll handles. **The document's top reserve is unconditional** (`doc_reserve` = `TITLE_BAR_RESERVE`), and what keeps it free is `standalone_slot_h` — the height a slot that stands *alone* claims, one window **below** the reserve (`runway_height`'s floor, the inactive draft's `node_height` floor, and the inline draft frame's `min_h`/editor fill). The pair replaced a conditional reserve (zero until the space had posts), which made a composer-only notebook lay its draft out a reserve *higher* than the post it was about to become: the whole document dropped by `TITLE_BAR_RESERVE` at the submit moment, moving the words the user had just typed (task 40). The `standalone_slot_h` half is what preserves the invariant the conditional bought — a lone composer plus the reserve is exactly one window, so an empty notebook still has nothing to scroll (`space_blank_composer_does_not_scroll`) — and it also brings a fully-docked composer to rest with its slot top *at* the reserve rather than sliding its text up under the titlebar, which is why `composer_bar_h`'s ramp is parameterized on that resting `dock_floor` (`doc_reserve + half_pad`) rather than on the reserve alone. Composer-to-post continuity is otherwise structural and was already right: a docked composer's editor starts `half_pad + composer_chrome() = POST_PAD_Y` below its slot top, exactly where a post's body starts under its own `py(POST_PAD_Y)`. Regressions: `space_composer_text_sits_where_its_post_will_land` (the blank notebook — first-ink parity measured off painted line geometry, not recomputed from the constants) and `space_reply_draft_text_sits_where_its_post_will_land` (the same rule one post in, which is why a *reply/fork* draft never had the asymmetry).
- `nav.rs` — snap physics (`SnapAnim`, `ease_out_cubic`, `snap_target_index` flick decision, `snap_duration`) + the gesture bookkeeping (`ScrollAxis`/`ScrollOwner` locks, `resolve_scroll_axis`, `start_snap`/`drive_snap` frame loop, `reassert_horizontal`, `remap_for_resize`, `select_path_to`). Same "take over at finger-lift" approach as the mockup (macOS exposes no momentum-end signal). **Horizontal branch scrolling locks its owning strip for the whole gesture** (`h_scroll_owner`, mirroring the vertical `ScrollOwner`): the first strip to handle a horizontal step is elected owner and held until the gesture ends. This matters because sibling branches differ in height — as the owner's pages slide, the cursor can drift over a *nested* strip on the incoming branch, and gpui dispatches the wheel to that innermost strip. Without the lock the nested strip would steal the gesture (halting the slide, or scrolling a sub-branch). Instead a non-owner strip undoes the built-in scroller's step on itself and **forwards the delta to the owner**, then the finger-lift snaps the owner (sized by its own branch count from the per-frame `scroller_counts` map, since the strip under the cursor at lift may not be the owner). Reset on `TouchPhase::Started`.
- `post.rs` — one post (byline gutter beside the reading column) + the separator band. The gutter column itself is the shared `byline_gutter` helper (label color/opacity as params), used by posts, inline drafts, and the floating composer so the gutter geometry can't drift between them — activating a draft must not shift its byline. Posts render through a **`disabled` `MarkdownEditor`** styled with the same `prose_style` as the composer, so a post is **pixel-identical** to what the user typed. `render_post_or_placeholder` is the virtualization decision. **Per-post affordances (the action gutter's tenants):** hovering a post reveals quiet verbs in its right gutter — **Edit** on your own posts, **Regenerate** on the assistant's (`Space::regenerate_post` with the post's **own recorded model** — regenerating re-asks the model that answered; the resolved default is the fallback for rows carrying none); hidden while streaming (the entity refuses mutations mid-stream, so dead verbs would lie), and only on rows with a real `action_id`. Hover state uses the Library's out-of-order-leave guard (`set_post_hover`). **Edit is in place**: `begin_edit` enables the post's *own* body editor (the same entity `sync_bodies` keeps synced — the sync deliberately skips the editing node, so a bus reload mid-edit can't clobber typing; regression: `space_edit_buffer_survives_transcript_sync`), stashes the original, retires any active draft, and routes the editor's ⌘↩ `PressEnter` to `commit_edit` → `Space::edit` (a new human generation; `item_current` resolves to it). Esc → `cancel_edit` restores the stashed original; while editing, the gutter shows the session's Save/Cancel verbs. **Finalized reasoning keeps its disclosure**: a post carrying re-attached reasoning renders the same "Thinking…" toggle as the streaming leaf (`render_post_body` → `Space::toggle_message_reasoning`) — previously the disclosure vanished the moment a stream finalized.
- `composer.rs` — the **draft model** (the mockup's, restored after Phase 1's single-composer simplification). A `Draft` (`SpaceView::drafts`) is a **window-local UI node** with its own editor, attached to the persisted tree as a leaf of the post it replies to (`None` parent = a blank-space root). Because `drafts` is view state (not the `Space`/DB), "drafts live in the UI, not the data" + "empty drafts never persist to the DB" both fall out for free. Two kinds, told apart by whether the parent is a current leaf ([`SpaceView::tail_parents`]):
  - **Tail draft** — the always-present, **docked** composer at the **end of every branch** (the leaf's reply affordance; a leaf's band therefore never offers *Reply*, though it still shows the "+" for Ask when the space has agents). `sync_tail_drafts` (run each frame in `render`, idempotent; skipped while streaming and until the transcript loads) ensures one per leaf and prunes empty, inactive, non-leaf drafts. An empty tail draft **persists** (docked) — Escape just deactivates it, it is never deleted. An **ask** at the tail applies the tail-draft rule (see the action-gutter bullet): empty → discarded (the response becomes the tail), non-empty → kept as its own branch.
  - **Fork draft** — the band menu's **Reply** (offered only on a post that already has a committed reply) starts a new branch via `create_draft`; the freshly-created draft selects its branch on the next render via `pending_select`, then `dock_active_draft` scrolls it home. An empty fork draft is **deleted** on retire (`retire_active_draft` deletes an empty draft *only* when it isn't a tail).
  - **Dots tint with activity** — `post::subtree_has_draft_content` tints a branch dot `info` once its draft is non-empty (the always-present empty tail drafts don't paint every branch), and an in-flight streaming turn's dot is `info` too — a fan-out's sibling streams stay discoverable and navigable while they run.
  - **Empty/active machinery is shared** — `create_draft_node` mints the editor (focus→activate, Enter→submit); a draft is always the end of its branch, so an inactive draft reserves `max(natural, standalone_slot_h)` height (`min_h` + the `node_height` floor) — the active composer's runway — so activating/deactivating never shifts the layout. One draft is *active* (focused, floating/docking); focusing another, or **Escape**, retires the current one (a kept one blurs to the view root so it reads as exited; clicking an inactive draft re-activates it directly). `⌘↩`/`⌘⇧↩` (`Send` = Post / `PostOnly` = Post quietly) **consume** the active draft into a persisted post — but **only once the space accepts the submit** (`send_active_draft` calls `Space::submit`/`post_only` first and consumes the draft only on a `true` return; a rejected submit — the space is busy: streaming *or* an in-flight save/plan whose `post_runner` is occupied but not yet streaming — leaves the draft intact and active, so a Post landing in that save window never loses the typed content: `space_post_during_save_window_preserves_draft`). An accepted post then runs `settle_on_new_post`: **rebuild** the render snapshot (the optimistic turn's `MessagesChanged` is delivered *after* this handler returns, so `self.posts` is otherwise still the pre-post snapshot and every measurement below would describe the document a post short of reality), **select** the branch the post joined (the same select-before-render rule the explicit asks follow, so the response renders where the reader is looking), **scroll** to the end of that branch, and **arm the tail pin** so the growth that follows — the persisted post coming back re-keyed and re-measuring, then the response's own leaf — keeps the reader at the end instead of stranding them above it (see [Tail-following](#space-view--tree-navigation-conversation-surface-srcspace_view-wave-6) and `space_post_parks_the_reader_at_the_tail_and_holds_it_there`); a typed failure — the post itself, or any one *turn* of the notification fan-out — surfaces the **recovery notice** (`SpaceView::render_error_band`) — an on-theme, dismissible danger card bottom-anchored to the failed exchange (never a terminal wall): the error text with a **Copy** affordance (gpui text isn't selectable here, so Copy is the "get this text out" idiom, cf. onboarding's credential rows), a **×** dismiss (`dismiss_error` — ends the recovery: clears the notice **and** the `failed_turn` record via `Space::clear_failed_turn`, so a later sibling success can't resurrect an orphaned notice and `can_retry` reads `false`; the space itself is already recovered), and a **Retry** action (`retry_failed` → `Space::retry`, shown only when `can_retry()` — i.e. a failed *turn* is recorded) that re-asks the same participant about the same post without re-posting, leaving any sibling turns still streaming untouched. The notice is owned by that `failed_turn` record (not the view-local `error` string): a sibling turn finishing (`StreamEnded`) never hides it while the failure stands. Probes `space/error/{dismiss,copy,retry}`. A brand-new blank (⌘N) space opens with its root tail draft already focused (cursor in an empty notebook). **Notes-editor click target:** because a docked composer (and every inactive draft) reserves at least a standalone slot, most of its body is blank runway below the text; clicking it should land the caret at the end. This is **owned by the editor**, not an overlay: the composer/draft passes `MarkdownEditor::min_height(..)` so the editor itself fills the runway, and the editor resolves a click below its last line to document end (see the editor crate's `min_height`/`offset_for_position`). A click on the text stays a normal caret placement — one listener (the editor's), no ancestor click handler juggling ranges. The **active composer** sizes the editor to `body_h − rail` (the footnote rail shares the bar); its bar height comes from `content` = the editor's `content_height()` (natural text height, decoupled from the `min_height` floor so there's no feedback loop) **plus the tail below that text** — `max(rail, breath)`: the rail's measured occupancy (the `flow_mark` pair — see `references.rs`), or a bare half-pad breath when there is no rail — all recorded by the `record_height` canvas in its paint phase. **The tail is a `max`, not a sum, because the bar's bottom breath is drawn exactly once**: a populated rail already carries it as its own bottom padding (inside the measured span), so adding `composer::bottom_breath()` on top would reserve it twice and inflate the bar — and the floating/dock runway with it — by a pad-height, visible as a gap between the last line of text and the footnote rule (the editor's floor, `body_h − rail`, grows to swallow the surplus). With no rail the marks coincide, the `max` degenerates to the breath, and the editor's runway draws it as live notes space rather than a dead strip — no branch on "is the rail empty" either way. Every term is read off real rendering, so the bar reserves exactly what the body draws, in both rail states (regression: `space_composer_counts_the_bottom_breath_once`). **The top chrome renders split at the scroll clip** (`composer_chrome()` = `half_pad` remains the *total* in every height/dock/runway computation — the split is a render concern only): a thin `COMPOSER_SEPARATOR_H` pane-separator band sits *outside* the scroll clip — the bar's only dead space when internally scrolled, where the fold shadow paints — and the remaining `composer_scroll_gap()` rides *inside* the scroll content as an in-flow spacer above the editor (a spacer child, **not** container padding: gpui adds padding to the scrollable extent, which would mint a gap-sized phantom scroll on a fit-height composer), with the byline and action gutters taking the gap as a compensating top margin. Unscrolled, nothing moves — the text and gutters sit exactly `composer_chrome()` below the bar top as before; scrolled, the spacer rides away with the content so the dead band is only the separator, and the fold shadow appears only once actual text (not the spacer) is cut. The split invariant (`separator + gap == composer_chrome()`) is pinned by `top_chrome_split_preserves_the_text_position`. The **inactive draft placeholder** fills the editor to `standalone_slot_h − 2·POST_PAD_Y` (matching the frame's `min_h(standalone_slot_h)` runway); its row keeps a thin `on_click` that only re-activates the draft + focuses (for clicks on the byline gutter that miss the editor) — clicking the editor itself activates via its `Focus` event, and the editor owns caret placement, so there's no cursor-resetting overlay. (This replaced an earlier ancestor-`on_click` approach that reset the caret to end even on text clicks, because the editor doesn't stop the *click gesture* on ancestors.) **Composer scroll — always-on tracking, gated ownership, pre-dock glide + dock ramp:** the composer body's `overflow_y_scroll` + `track_scroll` stay on **unconditionally**. What's gated (on `composer_scrollable = overlayed && chrome + content > bar_h`, cached in a `Cell` for the wheel handler) is only *ownership*: the composer **owns** the wheel (`ScrollOwner::Composer`, `stop_propagation`, page locked out) just when it's floating with real overflow; otherwise `ScrollOwner::Body` (no `stop_propagation`) — so a floating fit-height composer scrolls the *page* underneath (moving it toward its dock), and a scrolled composer nearing its dock lets the page scroll while the pre-dock glide walks its frozen offset to the top. Two things depend on tracking staying on: **(1) no phantom scroll** — a fit-height composer has `scroll_max == 0` (the editor exactly fills `body_h`, and the `record_height` measuring canvas is pinned to the origin so it adds nothing to `content_size`; an inset-less `absolute` child would otherwise sit at its static post-editor position and inflate the scroll range by a full `body_h`, letting a one-liner scroll ~half a window out). **(2) The dock transition.** The primary smoothing is the **pre-dock glide** (`SpaceView::glide_composer_toward_dock`, run once per `render` after the frame's page offset is final): while the dock threshold sits *under* the floating bar — the draft's would-be dock top (`slot_top + half_pad`, the value the dock decision compares against the float line) within the last `float_bar_h` (≤ half a window) of page travel before docking — each increment of page scroll consumed toward the threshold scales the internal offset by the ratio of dock runway remaining (the pure, unit-tested `dock_runway` / `approach_glide_offset` pair), so the content sits at **exactly** its top the moment the composer docks, instead of docking mid-scroll and unwinding afterwards. The multiplicative form is the robustness story: steps telescope, so the glide is path-independent over any stop/restart descent through the zone; a retreat leaves the offset alone (the glide never reverses — scrolling away from the dock doesn't re-scroll the composer) yet a resumed descent still lands exactly at zero; landing on or jumping past the threshold multiplies by zero (exact by construction, no accumulated drift); and outside the zone the runway saturates, so page scrolling never moves the internal content. Running at render time — not in the wheel handler — makes every page-scroll source participate (wheel anywhere in the window, minimap drag, tail-follow, programmatic docks like `go_home`), and placing it before the `composer_prev_off_y` baseline means the wheel handler's frozen-offset restore can never undo a step; `composer_dock_runway` carries the previous frame's runway and resets whenever no active on-path draft renders, so a branch switch can't seed a bogus first step. Behind it, the **dock ramp** stays as the docked geometry plus backstop: as the docked bar rises, `bar_h`→`body_h` (the scroll viewport) grows from the floating height toward the full content height (the pure, unit-tested `composer_bar_h` ramp), so `scroll_max = content − body_h` reaches 0 and gpui clamps out any residual offset the glide couldn't see (a mid-zone resize, a document reflow). Gating `overflow_y_scroll`/`track_scroll` off while docked (an earlier version) abandoned the offset the instant it docked and snapped the content to the top. Regression: `space_scrolled_floating_composer_glides_to_its_top_by_the_dock` (zone gating, monotone unwind, mid-zone reversal held, ~0 on the very first docked frame, held through the docked traversal). **The float height is per-window, draggable state** — `SpaceView::composer_fraction` (a ratio of the window height, default `COMPOSER_MAX_FRACTION` = 50%; deliberately never persisted to the space, config, or other windows, so every window opens at the default) applied per `composer::ComposerSizing`: **Max** (the bar grows with content up to the fraction — the resting behavior every activation starts from) or **Exact** (the bar is pinned to exactly the fraction while floating — it enters/leaves the floating state on that height rather than its content's, and holds it as content shrinks). While floating, the separator doubles as a **resize handle** — a centered dot, the vertical-resize cursor over a slightly generous hit band, probe `space/composer/resize` (absent when docked) — and dragging it writes the fraction directly: the grab switches to Exact immediately, snapshotting the bar's *current* ratio so nothing jumps (which is what lets the bar be sized in excess of its content), motion applies as a delta from the grab clamped to `[COMPOSER_FRACTION_MIN, COMPOSER_FRACTION_MAX]`, the drag tracks window-globally (the minimap-drag pattern, so it survives leaving the thin strip — and a mid-drag dock), and the pre-dock glide suspends its runway tracking for the drag's duration (the float line itself is moving; runway deltas would be the handle, not page travel). Deactivation — Escape, a post consuming the draft, an ask discarding it — or selecting a different draft reverts the sizing to Max (`reset_composer_sizing`); the **fraction survives** as the window's cap until re-dragged. Everything reads the bar through one helper (`layout::composer_float_bar_h`, pure core `composer::float_bar_height` — the render, the pre-dock glide, and the off-branch `floating_pad` all take it, so they can't disagree). Tests: `float_bar_height_caps_under_max_and_pins_under_exact` (unit), `space_composer_resize_drag_pins_exact_height_and_reverts_on_deactivate` + `space_composer_resize_reverts_to_max_when_the_draft_posts` (behavior), and the floating-present / docked-absent handle-probe assertions in `tests/probe.rs`. **`bar_h` is virtual geometry, not the painted quad** — this is what makes the ramp reach `full_h`. The window clipping that keeps the bar's rounded corners aligned belongs to the *quad* (`quad_h = (bar_h + content_shift).min(win − bar_top)`), at both ends; clamping `bar_h` itself (which PR #211's CSD-containment change did) pinned the scroll viewport to the visible height, so `scroll_max` never reached zero and a docked composer stayed scrolled off its own top by `doc_reserve + rail` and clipped at the bottom by the same — the regression `dock_ramp_reaches_the_full_content_height` now guards. **Caret-into-view on edit:** the editor has no internal scroll (it lays out to full height and the host scrolls it), so when an edit moves the caret below (or above) the fold, *something* scrolls to keep it visible — and which scroll handle owns that depends on how the composer sits this frame. The wiring: the active draft's `MarkdownEditorEvent::Change` **and `SelectionChanged`** arm `composer_caret_scroll_pending` (`create_draft_node`) — an edit *and* a pure keyboard-navigation move (arrows/Home/End/word moves, which emit only `SelectionChanged`) both scroll the caret into view; a zero-visual `caret_into_view` canvas — a later sibling of the editor in the composer body, so its paint sees this frame's post-edit `last_blocks` (same ordering `record_height` relies on) — reads the editor's `caret_content_y()` (content-local `(top, bottom)`) and the natural height, and if the caret is outside the viewport writes a clamped offset via the pure `caret_scroll_offset(caret_top, caret_bot, viewport_h, cur_off, scroll_max, margin)` helper (unit-tested), then clears the flag (one-shot per edit, so a manual scroll isn't yanked back). The canvas branches on the composer's **visible bar height** this frame (`body_h`, passed from the same render):
  - **Floating with overflow** (the frame floats *and* `natural − body_h > 0`): the composer scrolls its own **`composer_scroll`** (viewport = `body_h`). A fit-height floating bar (`natural − body_h ≈ 0`) is a no-op — the caret already shows, and the bar floats at the window bottom, not at its slot (under Exact sizing that includes content shorter than the pinned bar, whose runway shows the caret by construction).
  - **Docked** (the frame docks — the bar ramping toward the full window, incl. the blank ⌘N notebook that expands and grows below the window): the composer owns no usable internal scroll, so the caret's *window* visibility is a **`page_scroll`** concern. The caret's document position is `placeholder_doc_top + POST_PAD_Y + caret_content_y` (all `page_scroll`-independent — the slot's doc top comes from the tree heights, the caret span is content-relative), so following it with `page_scroll` converges in one shot (no oscillation as the dock ramp smooths `bar_h`). **The `POST_PAD_Y` term is load-bearing:** the editor's content body does *not* begin at the slot's document top — the docked composer's `top_y` sits `half_pad` below the slot top and the bar's top chrome (the separator + the in-content spacer, together `composer_chrome() = half_pad` — see the top-chrome split below) precedes the editor, so the editor content (where `caret_content_y` measures from y=0) starts `2·half_pad = POST_PAD_Y` below the slot top (exactly where a post's body sits under its `POST_PAD_Y` top pad). Omitting it aimed every docked caret target a pad-height too high — scrolling down never fully revealed the line, scrolling up over-revealed it. Guarded by `space_docked_composer_edit_scrolls_page_into_view`, which asserts the recorded slot-relative offset (`caret_doc_bottom − caret_content_bottom` = `page_slot_doc_top + POST_PAD_Y`, a frame-independent value on `docked_caret_slot_offset` — the final clamped `page_scroll` races under parallel test load). The page `scroll_max` is computed from the editor's **fresh** `natural` height (`page_slot_doc_top + max(window, chrome + natural + half_pad) − window`), *not* `scroll_min_y` — the latter derives from the frame-behind `composer_content_h` and would clamp the target back on the edit frame; the fresh form reproduces exactly the `scroll_min_y` the next frame settles to, so the page scroll lands immediately (the way the floating branch uses fresh `natural`). The offset is set via `page_scroll.set_offset` (the `dock_active_draft` pattern); the page wheel handler (`ScrollOwner::Body`) restores no frozen offset, so a following wheel won't fight it.

  The discriminator is the **render's own docked/floating decision, passed into the canvas** alongside `body_h` (frame-consistent by construction) — **not** the `composer_overlayed`/`composer_scrollable` cells: those derive from the frame-behind `composer_content_h` and read inconsistently under a repaint across the dock/float transition (both scenarios can momentarily read `overlayed == false`). (An earlier version re-derived the decision as `body_h > COMPOSER_MAX_FRACTION · window` — a proxy that only held while the float cap was a fixed constant, which the window-local fraction retired, and that silently classified the whole lower dock ramp as "floating".) The offset written during paint applies on the next frame, so the canvas schedules a repaint (mirrors `record_height`). Behavior tests: `space_composer_edit_arms_caret_scroll_into_view` (floating composer — tall doc, page scrolled to top — asserts `composer_scroll` moved) and `space_docked_composer_edit_scrolls_page_into_view` (blank ⌘N notebook — asserts `page_scroll` moved while `composer_scroll` stays 0); the geometry is unit-tested by `caret_scroll_offset`. **Deferred (page-scroll case that remains):** *inline post edits* (a post edited in place via `post.rs::begin_edit`, whose editor lives in `page_scroll` at the post's laid-out doc position, not in the composer) still don't follow the caret — the docked composer above is now handled, but the inline-post path needs its own arming (the edit-session subscription only routes `PressEnter` today) plus a fresh page-`scroll_max` reconstruction for a *mid-document* post (whose own cached height lags on grow, like the composer's runway but without a clean `natural`-derived total), so it's left as a follow-up rather than half-plumbed. A *nav-only* Home/End (no buffer change) emits no `Change` but **does** emit `SelectionChanged`, which the composer also arms on — so keyboard navigation off the visible region follows the caret too (composer only; inline-post edits remain the deferred case above).
  - **The floating composer is its own stacking layer** (`render_active_draft`'s return: `layered(composer, reach)` — a small local `Element` that paints its child inside one `Window::paint_layer`). gpui assigns each primitive a draw `order` from a `BoundsTree` (`order = 1 + max order of already-painted primitives whose *registered* bounds it overlaps`) and batches by `(order, primitive_kind)`. A drop shadow's registered bounds are the element rect grown by its *spread* only — **the blur reach is not included** (`Window::paint_drop_shadows`). So an inline shadow, in the ~20px window around the dock/float threshold where its blur visually spills over the final separator band but the composer rect hasn't reached it, lands in a disjoint BoundsTree chain from the band; the band (bumped by the high-order posts above it) sorts on top — the shadow renders *behind* the separator, then "jumps" in front once the rects overlap. `paint_layer` gives every composer primitive **one shared order** computed from the layer bounds, which `layered` dilates upward (`reach = blur − offset_y + margin`, from the `SHADOW_BLUR`/`SHADOW_OFFSET_Y` consts) to cover the blur — so that order overlaps the band and the whole composer, shadow included, sits above the page for the entire transition (internal order survives: within the shared order, batching still draws Shadow-kind under Quad-kind under text). **No `deferred` wrapper** (this replaced an earlier `deferred(…).with_priority(0)`, kept for symmetry on the minimap): paint order already does the work — the composer is a later root child than the scroll subtree, so it paints after every post/band and its layer order lands above them; the minimap is a later child still, so it paints after the composer and — overlapping it on the right edge — its BoundsTree order is bumped above the layer, keeping the scroll map on top of the bar. Staying in the normal paint pass (rather than the late deferred pass) also keeps both **below** window-level overlays like the gpui dev **inspector**, which the deferred versions painted over.

- `context_menu.rs` — **the right-click menu over any of the space's editors** (task 28): the pointer route to verbs that already exist on the keyboard and in the Edit menu. (Deriving enablement locally instead is what put an unconditional Paste on an empty clipboard: a visible row that did nothing, which is the one thing this menu promises never to show. `can_perform` is also why Cut/Paste are *structurally* absent from a read-only body rather than merely omitted.) Rendered as the root's **last** child so it sits above the minimap and the floating composer.

Key dispatch bubbles inner→outer, so the view root's handler runs *last*, after every inner one — which makes the root the only place that closes the menu, and makes every inner Escape handler's job to *yield* via `SpaceView::context_menu_absorbs_escape` (the composer, before deactivating a draft; a post row, before cancelling an inline Edit session). The split is not cosmetic: an inner handler that forgets to close is harmless, where one that forgets to yield acts on the *same* press that dismissed the menu — which, on the edit-session row, silently threw away an unsaved edit (a right-click mid-edit, then Escape to dismiss, restored the pre-edit buffer). - `references.rs` — **quoted references** (wave 2), the space view's half of the ordinal seam (`action_antecedent.ordinal` ↔ the body's `{{ embed N }}` ↔ the editor's embed map ↔ the footnote index — see the workspace `AGENTS.md`). Three surfaces over two editor plugins:
  - **Quote creation.** Each post body editor is subscribed for `SelectionChanged` (`sync_bodies` mints the subscription beside the editor), and a live selection resolves to a `PostSelection` — the concrete generation quoted, the content block, a **block-relative** byte range, the passage. The mapping is the pure `block_range_for` over `PostData.blocks` (the `PostBlockSpan` list `ChatMessageView::from_post` records while joining the blocks): a selection **crossing block boundaries names no single block and is not quotable**, because a reference edge points at one block and inventing one would make the stored range a lie. `Edit > Quote` (`SpaceView::quote`) attaches it to the active draft — next ordinal, a `PendingReference`, `set_embeds` so the marker renders as a real quote block, then `insert_embed_marker` at the caret; `Edit > Quote in Reply` (`quote_in_reply`) does the same into a draft replying to the **quoted post**, reusing that post's existing empty tail draft rather than stacking a second one beside it. Both actions are **registered only while a quotable selection exists** (a `.when(..)` around the two `on_action`s on the view root), so `is_action_available` is false otherwise and macOS greys the menu items — the `CloseWindow`/`OpenParticipants` registration-is-enablement mechanism plus a selection condition; `note_body_selection` re-renders on exactly the transitions that flip it (not on every drag step).
  - **Drafts carry pending references.** `Draft.references: Vec<PendingReference>` is window-local, ordinals `1..` in add order, **never renumbered on removal** (the survivors' markers already address them; a gap is correct). Removing one (`remove_draft_reference`) drops the row *and* its marker via the editor's `remove_embed_marker` — a stranded marker would render as literal `{{ embed N }}` text. The gap is reconciled exactly once, at the durability boundary: `composer::compact_draft_references` (pure, unit-tested) renumbers onto `1..=N` and rewrites the recognized markers to match, because `AppCore::post_with_references` assigns edge ordinals `1..=N` **in supplied order**. It is *computed*, never written back, so the **accept-before-consume** contract extends to quotes — a rejected post leaves the draft and its references exactly as they were.
  - **The footnote rail** (`render_post_footnotes` / `render_draft_footnotes`) renders **outside the markdown** — the editor never learns what a reference is, so removal UX never touches editor internals (the wave-1 design note). A hairline rule over single-line rows in the quiet register: index, the quoted post's byline, the passage. `FootnoteBody` is a genuine three-way state, not a nullable string — `Quote` (resolves), `Unresolvable` ("quoted an earlier version" — a stored range that no longer maps is **never** remapped or approximated), `Backlink` ("referenced" — no range was ever recorded). The **active composer reserves room for the rail out of its own bar** (subtracted from the editor's `min_height` runway, and folded into the bar's natural height by `record_height`) instead of letting it hang below the fold — and the height it reserves is **measured, not derived**: two zero-height in-flow probes (`references::flow_mark`) bracket the rail in the composer body and their difference is its exact occupancy, margin and rule included, so the reservation cannot drift from the styling (a row-count formula did, and the rail was cut off). With no rail the two marks coincide and the reservation is zero — no special case. The active composer's rail also carries the bar's bottom breath as its own padding — `composer::rail_breath` (a post's full `POST_PAD_Y`, not the half-pad `bottom_breath` that mirrors the chrome above the byline: under a ruled, text-bearing footer the half-pad read as crowding, where under a bare runway it reads as open notes space) — so the last footnote never sits flush against the window edge, which is why `record_height` takes the **max** of the measured rail and the bare breath rather than their sum (see `composer.rs`). **The rail is the bar's footer, so it is laid out against the bar's *visible* bottom** (`clipped_tail` in `render_active_draft`): `bar_h` is virtual, and the dock ramp carries the bar's bottom past the window edge — from exactly `win` at the float line to `doc_reserve + full_h` fully docked — while the painted quad is clipped back to the window. The rail, sitting at the end of the body's flow, went with the clipped part: on a docked composer it was cut off, reappearing only once the page reached the very end and the two bottoms coincided again. Subtracting exactly what the quad clipped from the editor's runway floor (`min_height = body_h − rail − clipped_tail`) lifts the rail back onto the visible edge, and degrades correctly — when the draft's text is taller than the runway the floor doesn't bind, so the rail keeps following the text below the fold (reachable by page scroll) instead of overlaying it. Regression: `space_docked_composer_keeps_its_footnote_rail_on_screen` (docked mid-ramp via the composer's own "See in context", asserting the rail's measured bottom lands *on* the window edge — neither clipped below nor floated above it). Clicking a row navigates to the quoted post. A draft's rows carry an **embed** affordance (`embed_draft_reference` → the editor's `insert_embed_marker`) that puts a quote back into the body — a reference and its marker are separable, so deleting the block leaves the footnote as the way back; it is offered only while that ordinal has no recognized block, since a second marker would render the quote twice — and a remove ×; a **post's** rows become removable chips inside the existing per-post Edit session (`toggle_reference_removal` → `EditingPost.removed_references` → `Space::edit` → `edit_post_with_removals`, which drops them from the *new* generation only). **A removed footnote takes its marker with it**: `commit_edit` runs the submitted string through `references::strip_removed_markers` (the editor's own `embed_blocks` recognition over a map of just the removed ordinals, so a fenced or surviving-reference marker is untouched), closing the paragraph gap it leaves. Left behind, that `{{ embed N }}` would render as literal wire syntax on reload *and* go upstream literally — there is no edge left for `expand_embed_strings` to expand it against. The strip is pure over the submitted value: the live buffer is never touched, so **Cancel still restores the stashed original and a submit the space rejects (busy) loses nothing**. **Ordinal 0 — the structural reply edge — never renders and is refused here as well as core-side:** the reply is the thread, not an annotation on it.

A plain click routes through `on_highlight_click` — one referencer navigates directly, several open a small picker (the band-menu pattern; its row labels run through `strip_embed_blocks` so the `{{ embed N }}` wire format can never surface as chrome text). - `traces.rs` — **trace visibility** (task 34): the quiet, subordinate disclosure that lets a reader audit what a turn actually did without leaving the space. Tool rounds, navigation-tool descents and decline decisions are persisted as `tool_call` / `tool_result` / `decision` actions the post tree collapses out; `AppCore::space_traces` is the **parallel read** that puts them back, each anchored to a post the tree already renders — which is what keeps `PostNode` and its virtualization untouched (a flag on the tree DTO would have widened a documented, load-bearing contract). **Two anchors, and the difference is the point:** a turn that *answered* anchors on its own inference (attribution is the turn's context assembly, task 33 — the trace chain itself hangs off the *post*, so the DAG can't tell you which answer it produced), and a turn that produced **no post at all** — a decline, a round-cap exit, a failed loop — anchors on the post it answered. That second case is the **gap**, and it is the whole audit value of a decline: a non-event is visible where the answer would have been. **One disclosure per *turn*, not per post** — several turns routinely share an anchor (a fan-out where two agents both bow out, a reader asking the same agent again after a decline, an answer a third participant then declines to follow), and one aggregated line would have to pick a single byline for all of them and total everybody's rounds into it. So the view renders one line per `PostTrace`, keyed on the DTO's per-turn `id`, and `Space::toggle_trace` / `trace_expanded` key on that id too, so opening one turn never opens its neighbour (found in review). Register: collapsed by default to one line per turn in the quiet `text_xs` register at the very bottom of the reading column, below the footnote rail (references belong to the post's own story; activity is operational detail subordinate to all of it) — "3 tool calls", or "Mara — declined to respond · 1 tool call" where the turn left no post to carry the byline, so the line has to name whose non-event it is. Expanded it becomes a ruled rail in the footnote rail's exact language (`references.rs` is the aesthetic precedent): one line per round — index, tool name, `arguments → result`, flattened and elided by the pure `summarize`. **Disclosure, not duplication:** a round's line is a `Link` that opens the Record on **that round's own raw request/response pair** (`request.action_id` is the `tool_call` action, so the id rides in the DTO), rather than re-rendering a payload in the reading column; a `decision` has no exchange of its own and is a plain `ListItem`. Probes are `space/post/{i}/trace/{t}` per turn — a `probe_value` whose **value is the summary line**, since that line is the content and it has settled (the index is refetched wholesale on `Change::Space`, never mutated under the reader) — and `space/post/{i}/trace/{t}/round/{n}` per round. An unexecuted round (the cap withholds a capped round's tools) reads "not run" rather than showing a blank result. Nothing floats, so the overlay-containment doctrine has nothing to contain. Cross-window: `crate::open_record_request` raises-or-opens the Record singleton and drives `RecordView::show_request` — reachable because `AppGlobal` now holds the Record's `WeakEntity<RecordView>` beside its `WindowHandle` (every window's root is a `gpui_component::Root`, so the view can't be recovered by downcasting the handle). It is a no-op without `AppGlobal`, which is why `SpaceView::open_in_record` records `last_record_request` *before* the guard — the `Space::last_submitted_model` seam applied to a cross-window verb. Tests: `space_trace_disclosure_is_collapsed_until_asked` (incl. that the anchor is *not* a disclosure key), `space_decline_renders_in_the_gap_under_the_post_it_answered`, `space_trace_row_deep_links_into_the_record`, `space_change_invalidates_the_trace_index` (behavior); `space_probes_record_the_trace_disclosure` (probe — the toggle's two labels and summary value, the round rows' `Link`-vs-`ListItem` split, and that a collapsed disclosure reveals no rows) and `space_probes_record_a_disclosure_per_turn` (two agents declining one post: two lines, two bylines, independent expansion); the summary/detail/elision helpers are unit-tested in-module; driver scene + visual case `space_traces` (whose last post stacks three declines — two agents, one asked twice).
- `minimap.rs` — the topology minimap, drawn from the selected path's cached heights + the live scroll offset (no per-frame canvas sweep), with the macOS-overlay-scrollbar show/linger/fade. A draft counts on **its own** branch (it's a tree node on the selected path); a **floating off-branch** draft pads other branches by its bar height (`layout::floating_pad`, folded into the minimap denominator + a trailing spacer) so the scroll indicator maps 1:1 on every branch. Because that denominator is the *same* `total_h = reserve + selected_h + pad` as the real scroll range, the column is a linear 1:1 image of the document (`scale = viewport_h / total_h`; document `doc` ↔ minimap-local `doc * scale`), which the **scrollbar-like interaction** relies on (pure mapping math in `doc_at_minimap_y` / `cell_fraction` / `scroll_for_press` / `handle_range` / `drag_grab` / `drag_scroll`, unit-tested). Each column's mousedown routes through `minimap_press`, which reads the press's minimap-local y: a press on a **different** branch switches to it (`select_path_to`) and positions by direct manipulation — the exact document point pressed (its vertical fraction *within* that item) lands under the cursor on the new page — then **completes** (no drag; switching branches changes the page height, so continuing would be meaningless); a press on the **selected** branch (or the dark on-screen **handle**) instead begins a **scrollbar-thumb drag** locked to that branch, moving only `page_scroll`. Grabbing the handle grabs at the press offset (no jump); pressing the selected-branch *track* jumps the handle center to the cursor, then drags. The drag snapshots `scale`/floor at start (`MinimapDrag`) and tracks the cursor window-globally via `Window::on_mouse_event::<MouseMoveEvent/MouseUpEvent>` (re-registered each frame from a hitbox-free `canvas` that also records the container bounds — mirroring `gpui_component::Scrollbar`), so the drag keeps following after the cursor leaves the 36px strip and never switches branches mid-drag. Interactive only while the overlay is up so a faded strip can't steal clicks. Annotated for accessibility — a `Group` "Conversation map" of per-node `Button`s labelled "*byline*: *snippet*" (or "Draft" / "Eidola, responding"), with `aria_selected` on the active path. Probes `space/minimap` + `space/minimap/cell/{level}/{i}` double as driver click targets.

**Read-only `MarkdownEditor` (the editor crate, breaking out the user's "Phase 2"):** a `disabled` editor renders as **published** markdown — `MarkdownEditorState::render_spec` calls `render::render_readonly` (a no-cursor render, `CursorRange::nowhere()`), so every WYSIWYG delimiter is hidden and a post reads as finished prose. Without this, a disabled editor's offset-0 cursor revealed leading delimiters (a post starting with `**bold**` showed the `**`). The editable path is unchanged (`render` → `render_with_cursor` with the real selection). A read-only post is still **selectable** (mouse drag, double-click word, triple-click line — see the editor crate's pointer-selection notes) and copyable; the selection handlers register regardless of `disabled`. **Re-seeding is keyed on the post, not the buffer**: `sync_bodies` re-seeds a body editor only when the *post's* content changed since the last seed (`body_seeds`), never because the editor's live buffer differs from the post — comparing against the buffer turned any buffer-vs-source divergence into a per-frame `set_value` reset loop that silently killed pointer selection on the affected post (the editor no longer rewrites read-only buffers at all — `update_readonly` in the editor crate — so this is defense in depth). Regression: `space_readonly_selection_sticks_on_noncanonical_post`; driver scene `space_structured` mirrors the user-reported space's structure (branched root, markdown-heavy spine reply) with placeholder text.

**Selection autoscroll for tall posts.** A post editor has no internal scroll — it lays out to its full height and the page owns the scroll — so a selection drag that runs past the viewport edge can't be followed by the editor alone. `SpaceView::autoscroll_selection` (run each frame in `render`, after `scroll_min_y` is set) closes that: while a readonly post reports `MarkdownEditorState::is_selecting()`, it scrolls `page_scroll` toward whichever viewport edge the pointer is pressed against (`selection_autoscroll_delta`, a pure ramp/clamp helper — unit-tested like the minimap's mapping math) and re-extends that editor's selection from the stationary pointer via `drag_extend_to`, then schedules the next frame (self-terminating when the drag ends or the page clamps at an end). Paired with the editor's window-global drag tracking, this is what makes a long AI response selectable in one gesture — previously the drag froze at the fold. Drafts (the editable composer, which floats in its own scroll) are excluded; they route caret-into-view separately.

**Tail-following while a turn streams.** `SpaceView::follow_streaming_tail` (run in `render`, immediately after `scroll_min_y` is set for the frame, so every `clamped_scroll_y` consumer sees the followed position) keeps a reader who is parked at the end of the branch pinned to the growing tail — the answer writes itself into view instead of running off the bottom — and leaves a reader who has scrolled away exactly where they are. **"At the end" is answered by observation, not by a sticky flag**: the page is following iff its current offset still sits at the *previous* frame's end-of-document (the value `scroll_min_y` held before this frame's document was measured — `render` takes it via `Cell::replace`, with `TAIL_FOLLOW_EPSILON` of slack for layout rounding). Every scroll source therefore participates for free — wheel, minimap drag, selection autoscroll, a programmatic dock — with no state to keep in sync and no mode to get wedged in: scrolling up leaves the band and following stops; scrolling back down re-enters it and following resumes. Gated deliberately on **the selected path carrying a live stream** (`layout::selected_path_is_streaming` — the same observation-of-the-rendered-tree style as `selected_levels`/`path_has_unmeasured`, no flag), *not* on the space-wide "is some turn streaming?": a document that grows for any *other* reason is the composer's runway or a post measuring for the first time, and neither should move the reader (composer growth keeps its own `composer::caret_into_view` path, which this must not race). Scoping it to the space re-opened exactly that race whenever a Participants-v1 fan-out streamed on a **sibling** branch — a routine state in which the reader's own branch is by definition not producing, so its growth is all non-stream growth. **The one deliberate widening is a just-submitted post** (`SpaceView::tail_pin`, folded into the `producing` argument by the caller): a submit *is* the reader's own branch producing, but the stream that proves it starts only once the post has persisted and the notification plan resolves, and across that gap the document still grows (the persisted post comes back re-keyed — a new node id, so it drops to an estimate and re-measures). The reader `composer::settle_on_new_post` parked at the end would be left above it, `at_tail` false by the time the first delta arrives — the answer then writes itself off the bottom, which is the bug the pin fixes. ## Window model

**Space windows are non-singleton; the space *entity* they share is not.** Every `NewSpace` opens a fresh `SpaceView` via `open_main_window` → `open_chat_window(cx, stores, None)`; with `space_id: None` `SpaceView::new` calls `SpacesStore::blank()` for an id-less `Space` (instant ⌘N; the registry adopts it once its first exchange assigns an id). The Library reopens via `open_space_window(cx, stores, space_id)` (`Some(id)`): `SpaceView::new` calls `SpacesStore::open(id)`, which **joins** the registry — so opening the same space twice yields two independent *windows* over **one shared `Space`** (transcript, streaming, submit, model selection are common; submits/streams in one window appear in the other). The composer draft stays per-window by design. There is still no window *dedup* (two windows is fine, acceptable v1) — the change from before is that they no longer each hold a private transcript copy. `open_chat_window` calls `cx.activate(true)` after `cx.open_window` so a window opened from another app's context (dock right-click while a different app is foreground) brings Eidola to the front rather than opening behind.

**The Participants window is non-singleton, per-space** (like space windows): `Space > Participants…` (`OpenParticipants`) is registered per-`SpaceView` (like `CloseWindow`), so the menu item targets the *focused* space and macOS greys it when no space window is open; the handler (`SpaceView::open_participants`) reads the space's id (a no-op on a not-yet-persisted blank ⌘N space) + its title from the Library index and `cx.defer`s `open_participants_window(cx, stores, space_id, title)`. Each space gets its own window; no dedup (acceptable v1).

**Settings, Library, Updates, Record, About, and Onboarding are singletons.** `AppGlobal.settings_window` / `AppGlobal.library_window` / `AppGlobal.updates_window` / `AppGlobal.record_window` / `AppGlobal.about_window` / `AppGlobal.onboarding_window` (`Option<WindowHandle<Root>>`) cache the handles, and `OpenSettings` / `OpenLibrary` / `CheckForUpdates` / `OpenRecord` / `About` / `GetStarted` raise the existing window via `window.activate_window()` if it's still open (shared helper `try_focus_existing_singleton`, parameterized over the `AppGlobal` slot). The onboarding window also opens automatically at launch when no account is configured (and the eidola backend is enabled). Both open paths are **synchronous** (via `App::open_window`) so the cache is populated before the handler returns. Liveness is checked by matching the cached `WindowId` against `cx.windows()` (the authoritative live list) — borrowing Zed's pattern, except Zed can use `AnyWindowHandle::downcast::<SettingsWindow>` directly because their settings root is uniquely typed; ours is `gpui_component::Root` (shared with chat windows), so we match by id instead. A stale id self-heals on the next invocation — no `on_release` bookkeeping needed. At launch onboarding opens **instead of** the blank space window, and hands one off when the user leaves it — see [Onboarding window](#onboarding-window). `OpenLibrary` additionally calls `SpacesStore::refresh` on every invocation (not just first open) so a long-lived Library window doesn't show a stale listing. `CheckForUpdates` follows the same singleton pattern via `AppGlobal.updates_window`, and re-runs `UpdateStore::check_now` when raising an existing window so the menu gesture always produces a live check.

## App lifecycle — the app outlives its windows

`src/lifecycle.rs` (task 17, wave 2). The process is becoming longer-lived than any window it shows: loaded local engines already belong to it, and continuous capture plus the OpenAI-compatible proxy will. Everything below is expressed at gpui's own seams — **the spike found no upstream gap at our pin**; the module docs carry the full survey (`QuitMode`, `Application::on_reopen`, `App::on_app_quit`, `App::on_window_closed`).

- **Quit policy is one pure function**, `lifecycle::quit_mode(opts)`, handed to `Application::with_quit_mode`. Three cases: **windowless** (either platform) never quits by itself — the window-less process *is* the app and a window is a visitor; **macOS windowed** never quits by itself — the platform idiom, and what `on_reopen` exists for; **Linux windowed** quits with the last window. Naming the mode replaced both the inherited `QuitMode::Default` `cfg!` and the hand-rolled `cx.on_window_closed` quit rule, because on Linux this is a *launch-mode* decision no upstream default can make. Unit-tested (`windowless_never_quits_on_its_own`, `windowed_quit_mode_follows_the_platform_idiom`).
- **Reactivation** (`lifecycle::reactivate`, wired to `Application::on_reopen`): a Dock click, a Spotlight relaunch of the running app, or a second `open -a Eidola` focuses a window — the active one if the platform still names one, else the front-most of `App::window_stack()` — and otherwise opens **the Library**, the app's table of contents being the honest door back into a process that has been running without a face. `cx.activate(true)` runs either way (a reopen can arrive while another app is foreground). **"Most recent" is `window_stack()`, not `windows().last()`**: `App::windows()` enumerates gpui's `SlotMap`, which reuses a closed window's slot, so after a close-and-reopen its last entry is whatever landed in the highest slot index rather than the window the user saw last; `window_stack()` is the platform's real front-to-back order (macOS implements it as `MacWindow::ordered_windows()`), and reactivation is a macOS-only event, so that is exactly the platform answering it. `windows().last()` remains the deterministic fallback where the platform returns `None` — including the test platform, which is why the behavior tests still walk a real path. The "open when empty" branch is a parameter so the decision is testable without `AppGlobal`: `reactivating_with_no_windows_opens_the_door`, `reactivating_with_a_window_focuses_it_instead`. **On Linux gpui stores the reopen callback and nothing ever fires it** — there is no platform mechanism — which is why "a second launch asks the running instance for a window" is the wave-4 socket's job there and not something this wave can fake.
- **Quit is a full shutdown — engines, everything** (decided; no two-tier quit). `lifecycle::install_engine_shutdown` registers an `on_app_quit` hook that calls **`AppCore::shutdown_engines`** — synchronous, infallible, and reading the **live engine registry**, never a model snapshot. That distinction is the fix for a real defect: `local_models_state` is *reconstructed by scanning* the model directories (a `read_dir`, a `stat` and a sidecar read per `.gguf`, plus a DB round trip) and consults the engine map only to decorate a file it already found — so an engine whose backing `.gguf` was renamed or deleted mid-session is **absent from it while its subprocess is still running**, its `Result` means an unreadable directory could skip the sweep entirely, and a large or slow directory could spend the whole budget on I/O before killing anything. Signalling is not reaping (the supervisor owns the child), so the hook then yields on gpui's *own* executor to let the tokio threads run them. **The hook's first act is to close the bus bridge** (`stores::BusBridge::quiesce`), before the drain and before the grace wait. That is the *class* cure for a defect that had already been patched twice at the emitter: app-core's quit-time engine drain was silenced, then its engine supervisors, and a model **download** reporting progress during the grace window would have been a third — any `Change` dispatched after `App::shutdown` sets `quitting` reaches a store's `refresh` → `cx.spawn` → "Can't spawn on main thread after on_app_quit", and gpui keeps driving that app-lifetime foreground task throughout the shutdown block. Fixing it at the single door every `Change` in the process comes through covers every emitter, present and future; **app-core keeps its own quiet-on-quit rules for a different consumer** (the CLI embeds `AppCore` with no gpui, and the bus is a documented contract there — `tests/bus.rs` enumerates every exit point's emissions), and neither layer relies on the other. Regression: `a_quiesced_bus_bridge_dispatches_nothing` (`tests/stores.rs`), which drives the live tokio→gpui plumbing rather than the `dispatch_change_for_test` seam, because closing the loop is the thing being asserted. Three further properties on the app-core side make the hook safe rather than merely correct, and all three are about the same window: the drain sets a **shutdown latch** under the same lock the reservation takes — checked *twice*, at `reserve_engine` (so a load mid-`await` when the quit landed cannot resume and reserve) and again immediately before `command.spawn()` (so a reservation accepted a moment earlier, whose supervisor task is first polled *after* the drain walked the registry, cannot start a child into a dying process); **nothing on the quit path emits** — neither the drain nor the supervisor's own shutdown arms, app-core's half of the story above; and a warming engine's `/health` probe **races** the shutdown signal rather than preceding it (awaited outside the supervisor's `select!`, a hanging probe — which is exactly what a warming engine's `/health` does — meant the signal was never polled and the child outlived the process). **The grace is unconditional, not gated on the drained count**: `unload_local_model` returns as soon as it has signalled, so an unload immediately followed by a quit finds an empty registry, and a count-gated yield would skip precisely when a child is still dying. On macOS this hook is the *only* thing that delivers a real shutdown: `cx.quit()` becomes `[NSApp terminate:]`, which ends in `exit()`, so the tokio runtime is never dropped and the `kill_on_drop` reaping that covers the Linux path (where the event loop returns and `main` unwinds) never happens — without the hook a quit leaves every loaded `llama-server` running, adopted by launchd. It is **best-effort by construction**: `gpui::SHUTDOWN_TIMEOUT` is 200ms and a quit that outruns it still exits. Regressions (app-core): `shutdown_reaches_an_engine_the_model_scan_cannot_see`, `a_load_after_the_shutdown_drain_is_refused_and_spawns_nothing`, `the_shutdown_latch_also_refuses_a_spawn_that_was_already_reserved`, `the_shutdown_drain_emits_nothing`, `the_supervisors_shutdown_arm_emits_nothing`, `a_hanging_health_probe_does_not_swallow_the_shutdown_signal`. A hard guarantee wants the OS to enforce it (`PR_SET_PDEATHSIG` on Linux; macOS has no equivalent and would need an explicit synchronous reap in app-core) — a follow-up.
- **`--windowless`** (`lifecycle::LaunchOptions`, parsed in `main.rs`): no window at launch, no foreground activation, and nothing that closes later can stop the process. Every other launch step still runs — stores, bus bridge, update polling — because that *is* the app. Argument parsing is deliberately lenient about flags it doesn't know (LaunchServices hands a launched `.app` `-psn_0_…`; Xcode adds `-NSDocumentRevisionsDebugMode`), and `--help` prints `lifecycle::USAGE`. On a Linux box with no display gpui's own `guess_compositor()` already resolves to its headless client, so the mode needs no platform plumbing of its own.
- **Signals** (`lifecycle::install_signal_quit`, unix, windowless only): `SIGTERM`/`SIGINT` are translated into an ordinary `cx.quit()` so a `systemctl --user stop` runs the quit observers (and with them the engine teardown) instead of killing the process out from under them. The signal is awaited on the core's tokio runtime — the one runtime in the process that can host `tokio::signal` — and handed to gpui through the same `oneshot` bridge every other core → gpui hop uses.
- **What is *not* here.** A second GUI launch on Linux still hits app-core's `AppError::DatabaseInUse` (the task-23 flock) with no friendly path; macOS gets one free from LaunchServices reactivation. Closing that on Linux is the wave-4 socket. The status item and the Regular ⇄ Accessory activation-policy flip are wave 3 and ship **together** — an Accessory app with no windows and no status item is invisible and unquittable, so the intermediate state is deliberately: outlives windows, Dock icon stays.
- **What only a human can verify.** `TestPlatform::quit` is a no-op and no test dispatcher delivers a Dock event, so the behavior tier proves the window-registry half (every window closes, a fresh one opens cleanly over the same live stores: `every_window_can_close_and_a_new_one_opens_cleanly`) and the pure decisions; that the *process* survives ⌘W-to-empty and comes back on a Dock click is hand-verified against the real `.app`.

## Updates window

`updates.rs` renders the verified update-notification flow (`eidola_app_core::updates` — see the workspace `AGENTS.md` for the verification model and failure-mode matrix). Small singleton (480×360 default), opened via Eidola menu → "Check for Updates…" (directly under "About Eidola", the standard macOS placement).

## Library — table of contents, not a sidebar

`library.rs` renders the space listing as a book's table of contents (520×620 default): one column, hairline `theme.border` rules *between* entries (border-top on `idx > 0`, no boxes/cards/avatars), each row a title — or, for untitled spaces, the first-message snippet in `theme.muted_foreground` — with a right-aligned relative date ("today" / "3d ago" / "2w ago"; see `relative_date`) in `text_sm` muted. A heading ("Library", italic, between hairline rules) echoes a book's interior typography so the window reads as another page of the same book. Empty state is a single centered muted line. The data comes from `SpacesStore` (the `Loadable<Vec<SpaceInfo>>` index, archived excluded), refreshed via `SpacesStore::refresh`.

**Virtualized.** The listing renders through gpui's `uniform_list` (see [Virtualized lists](#virtualized-lists)): rows are fixed-height (`ROW_H`, single line), the closure (`render_rows`) is a dumb indexer that clones only the visible slice from `SpacesStore`, and the list self-scrolls via a stored `UniformListScrollHandle`. The centering wrapper is `h_flex().flex_1().min_h_0().justify_center()` around a `relative` column capped at `max_w(rems(34))` that holds the list plus the right-edge overlay scroll indicator (`crate::scrollbar::vertical`, bound to the list's `UniformListScrollHandle` — the indicator rides the *list's* right edge, not the window's; see [Scroll indicators](#scroll-indicators-srcscrollbarrs)); the list carries `.h_full().w_full()` so it fills the height (so it actually scrolls) while staying capped at the prose measure and centered — a library too long for one screen now renders O(visible), not O(rows).

Interactions: clicking a row opens the space (`open_space` defers `open_space_window` via `cx.defer` so the new window opens after the current update cycle); hovering a row (`hovered: Option<usize>` tracked via `on_hover`) reveals **two ghost buttons in a fixed-width reveal slot** (so their appearance doesn't shift the date column) — a rename affordance (the bundled Lucide set has no pencil glyph, so `IconName::CaseSensitive` / "Aa" is the quiet text-edit cue) then the archive ×. The pencil starts the inline rename; the × archives via `SpacesStore::archive` — which removes the cached row *immediately* (so the UI responds without a backend round-trip, and so stub-store tests exercise the local path) and then runs the real archive + re-fetch. `archive` / `open_space` / `begin_rename` are public methods so behavior tests drive them directly instead of synthesizing mouse events; `set_hovered_for_test` exists for the hover snapshot. **Pencil/× propagation (the "click both renames and opens the row" race).** Each affordance is wrapped in a slot `div` that stops propagation on **both** mouse-down and mouse-up (not just the click), and the pencil **defers `begin_rename`** via `cx.defer_in`. `cx.stop_propagation()` inside a child `on_click` only stops the click's mouse-up *bubble* phase, but gpui arms a click on mouse-**down** (each hovered ancestor records its own `pending_mouse_down`) and captures it on the mouse-up *capture* phase — both before the child's bubble click runs (`gpui/div.rs` paint + `window.rs::dispatch_mouse_event`: capture outer→inner, then bubble inner→outer). So the row had already armed and captured its own pending click; `begin_rename` reshaping the row *between* the captured down and the firing up (reveal slot hidden, title → input) could land the up on the bare row and complete the ROW's open on top of the rename. Blocking the **down** stops the row from ever arming; deferring `begin_rename` keeps the gesture resolving against the pre-rename layout. (gpui's #24600 guard, the row dropping its `on_click` on reshape, and the pencil's `stop_propagation` cover every *synchronous* path, so the production failure is the intermittent multi-frame timing race; the regression test guards the invariant deterministically — stripping the pencil's propagation blocking makes the row's `open_space` fire under a real simulated click.) The archive × needs no defer — its row vanishes (different masking) — but takes the same both-phase block for symmetry. Each slot also carries a `debug_selector` so the regression test can locate the pencil's hitbox. **Hover-event ordering:** the `on_hover` listener routes through `set_row_hover(idx, hovering)`, which on hover-false clears `hovered` **only if `idx` is still the hovered row** — moving the cursor *up* the list, the row being left can fire `on_hover(false)` *after* the row being entered fired `on_hover(true)`, and an unconditional clear would wipe the new row's reveal buttons (the asymmetric "× flickers off when moving up the list" bug). Replay: `library_hover_survives_out_of_order_leave`.

**Inline rename.** The hover-revealed pencil calls `LibraryView::begin_rename(space_id, current_title, window, cx)` (replacing the former double-click trigger, which was unreachable — a single click opens the row immediately, so a double-click's second click landed in the freshly-opened window). `begin_rename` creates an `Entity<InputState>` seeded with the current title, focuses it immediately, and subscribes to `InputEvent`: `PressEnter` → `commit_rename` (writes through `SpacesStore::rename`, which optimistically updates the cached row and then calls `AppCore::rename_space` + re-fetches); `Blur` → `cancel_rename` (drops the draft without writing). Pressing Escape inside the `InputState` propagates through (the `Input` context doesn't capture Escape by default when `clean_on_escape` is false), which causes the input to lose focus and fires `Blur`, which cancels. The active rename space is tracked in `renaming: Option<(String, Entity<InputState>, Vec<Subscription>)>` on the view; `renaming_space_id()` returns the id for tests. The reveal slot is hidden while a row is being renamed so the buttons don't compete with the input. `SpacesStore::rename` uses the same optimistic-update + supersede-slot pattern as `archive`; the bus-driven `Change::SpaceIndex` reconciles all windows. Replays: `library_pencil_begins_rename` and `library_pencil_click_does_not_also_open_row` (the real-click propagation guard).

## Settings — calm two-pane, edit-in-place

`SettingsView` (620×520) is an `h_flex`: a narrow nav band (`NAV_WIDTH` 132px) on `theme.sidebar` with quiet text items (active = `sidebar_accent` pill), and the selected pane in the content column. **Up to five panes: General · Backends · Templates · Account · Wallet.** General, Backends, and Templates (the Space Templates registry — see [Participants & Templates](#participants--space-templates)) are always present; **Account and Wallet render only while the eidola backend is enabled** — the account *is* the eidola backend's configuration, and with it disabled ("on-device only") there is nothing to bill. - **Backends**: the backend registry — *where an ask can be routed* (see `src/backends_settings.rs` and the workspace `AGENTS.md`'s `backends.rs` / `local_models.rs` sections). ## The Record window — the trust door's engine room

`record.rs` (`RecordView`, singleton, ⇧⌘L / Eidola → "Record…", 860×640) exposes the raw local Turso trail. Three sections in a quiet text strip that doubles as the title bar (`STRIP_LEFT_PAD` 80px clears the traffic lights; right side carries a Refresh affordance and an italic "The Record" wordmark):

- **Attestations** — `attestation` rows (middle-truncated hash, pcr digest, connection count, doc size, UTC timestamp). Click → the full raw document: pretty-printed JSON when it parses, UTF-8 text, hex otherwise.
- **Requests** — `request` ⋈ `connection` rows (mono `METHOD /path`, status colored by outcome, transport/duration/attempt/credential/error subline). Click → full detail: kv rows (the attestation hash links through to its attestation detail) + raw request/response headers and bodies.
- **Spending** — the `spend_trail` view grouped by credential (consecutive same-nonce rows share a group header with held/charged amounts; rows are time-ordered so the grouping matches reality). Rows click through to the request detail.

Mechanics worth knowing:

- **Windowed fetch, owned tasks.** `Listing<T>` per section; each page asks app-core for `PAGE+1 = 51` rows (`LIMIT/OFFSET`) to learn `has_more` without a COUNT. Data flows through the `bridge` free functions (`bridge::list_attestations` / `list_requests` / `spend_trail` / `attestation_detail` / `request_detail`, taking the `Arc<AppCore>` from `Stores::app_core()`), and the view **owns every fetch in a task slot** (doctrine task-as-field, never `.detach()`): each `Listing` carries its page-fetch slot, and one shared `detail_task` slot covers both detail kinds. Replace-cancels is what makes `refresh()` safe — resetting a `Listing` drops its in-flight task, so a superseded fetch can never land late and append duplicate rows (the codex-found race on PR #179; replay test `record_refresh_supersedes_in_flight_fetch`), and the detail slot retires the old `detail_pending` staleness check (closing a detail cancels its fetch outright). Stub stores skip the fetch; tests install rows via `set_*_for_test`.
- **Bus-driven staleness (the doctrine's "Record pattern").** No global store owns the Record's rows, so `Change::Record` is routed (in `stores::dispatch_change`) to the data-less `RecordStore` relay, which just bumps an `epoch`. Each open `RecordView` observes it, compares the epoch against the one it last refreshed at, and sets its `stale` flag — rendering the strip's Refresh affordance as a quiet "New entries — refresh" (`theme.link`) instead of mutating rows under the user's scroll position. `refresh()` resets all three sections (the current one re-fetches immediately, the others on next visit), clears `stale`, and re-snapshots the epoch. A bus `Lagged` also bumps the relay (the dropped change may have been a Record write). Tests: `record_marks_stale_on_record_change_and_refresh_clears` (behavior), `bus_bridge_routes_record_change_to_record_store` (stores).
- **Virtualized listings + flat display model.** Each populated section renders through `uniform_list` (see [Virtualized lists](#virtualized-lists)), so frame work is O(visible), not O(loaded) — the wave-2 bug-3 fix (the window used to slow to a crawl as "Load more…" appended pages, because every row re-rendered every frame). To keep the `uniform_list` closure a dumb indexer, each `Listing<T>` precomputes a flat `Vec<DisplayRow>` (`Header(i)` / `Data(i)` / `LoadMore`) on every state change (`rebuild_flat_display` for attestations/requests; `rebuild_spending_display` for the grouped Spending view). **Spending group headers survive virtualization** because they are precomputed `Header` rows interleaved into the display model, not a render-time `prev_nonce` branch the windowed closure couldn't reconstruct. All rows — data rows, group headers, and the trailing load-more row — are normalized to one fixed height (`ROW_H`); the formerly taller spending group headers are slightly tighter now (even spacing carries the group rhythm instead of extra top padding — an intentional, documented change). **Load-more stays windowed:** the trailing `DisplayRow::LoadMore` is an explicit, quiet "Load more…" row that appends the next 51-row page; while a fetch is in flight it renders an honest "Loading more…" in-flight row (it maps to a real task, never an infinite spinner). The empty/loading/detail bodies stay in an ordinary `overflow_y_scroll` container (`scroll_wrap`, tracking `detail_scroll`); only a populated listing is the self-scrolling `uniform_list`. Both shapes carry the right-edge overlay scroll indicator (`crate::scrollbar::vertical`, bound to `detail_scroll` or the active section's `UniformListScrollHandle`; see [Scroll indicators](#scroll-indicators-srcscrollbarrs)).
- **Raw payloads are never redacted** (the user's own traffic on their own machine). Inline rendering is capped at 64 KiB with an honest note; the per-section **Copy** affordance always writes the *full* payload to the clipboard. Raw text renders selectable through `TextView::markdown` inside a code fence whose backtick run is computed to exceed any run in the content (`fenced`); the `TextViewStyle` mirrors `theme.mode.is_dark()` so the block ground tracks Circadian night.
- **Parse caching (no per-frame projection).** Opening a detail builds a `DetailCache` **once**: the raw-payload projection (pretty-printed JSON / UTF-8 / hex dump), the `fenced` + 64-KiB-capped inline string, and the full Copy string are all computed at open time and stored as `CachedPayload`s. The render path (`raw_section`) only reads the cache — it never re-projects per frame. This is the other half of bug-3: a large attestation document or response body used to re-run `serde_json::to_string_pretty` / `hex_dump` / `fenced` on every frame. **TextView itself does not re-parse per frame at our pin** (verified in `gpui-component@dadfca9`): `TextView::markdown(id, text)` resolves its `TextViewState` via `window.use_keyed_state` keyed on the element `id`, and `TextViewState::set_text` early-returns when the text is unchanged — so a *stable id + stable string* parses exactly once. The per-frame cost was always our own Rust-side projection, which the cache removes; passing the cached `fenced` string (identical bytes each frame) under the payload's stable `id` keeps TextView's parse a one-time cost. Perf is guarded by `record_frame_work_is_constant_in_loaded_rows` (behavior test: 1 page vs 10 pages — the visible-window render produces the same fixed row count and does not scale in time).
- **Detail-body frame cost — measured, and the selection scan is the thing to watch.** The detail body is *not* virtualized: the whole capped payload is one `TextView` per section inside `scroll_wrap`'s `overflow_y_scroll`. That is deliberate and it is cheap — drawing a 46 KB request/response pair costs ~8 ms per frame in a dev build (~0.5 ms in release) and grows linearly with payload size, because gpui shapes each source line once into a frame-scoped line-layout cache and skips glyphs outside the content mask. Keeping the payload whole is also what keeps a drag selection able to span it, which a forensic surface needs. **The cost that isn't linear is the selection geometry scan.** `gpui-component`'s `Inline::layout_selections` runs on every paint while a window text selection exists, and it walked *every character* of the element calling `TextLayout::position_for_index` twice — a call that rescans the layout from line 0 — so the per-frame cost was O(characters × lines). Measured on the dev profile: 4 KiB → 14 ms/frame, 16 KiB → 94 ms, 32 KiB → 310 ms, 64 KiB → **1117 ms**; the real 46 KB request that prompted this was 476 ms/frame (~2 fps). Select a passage in a large body and every subsequent scroll frame paid it. The cure is upstream and structural — skip lines whose vertical band misses the selection *or* the content mask (so the scan is bounded by the text on screen), and take per-character positions from one ordered pass over the shaped glyphs — which flattens selecting to idle cost (476 ms → 8 ms) with byte-identical selection results. Until that lands in our `gpui-component` pin, the wall is still there in the shipped app; it is bounded by `INLINE_CAP` but that bound is 64 KiB per payload, which is already deep into the quadratic. **Two traps to avoid when touching this:** (1) geometry must use `TextLayout::line_height()` (pixel-snapped at layout time), not `window.line_height()` — they differ by a device pixel, which is enough to move a hit; (2) `layout_selections` clips the reported selection to the content mask, so selecting inside a payload and pressing ⌘C yields only the part that was *on screen* — the per-section **Copy** affordance is the honest whole-payload path and is why it exists.
- **The measuring instrument (`tests/record_perf.rs`).** A third local-only tool beside the visual tier, same shape (`harness = false`, macOS only, `EIDOLA_RUN_RECORD_PERF=1`, never runs in CI): it opens a real offscreen window on a request detail and reports (a) `Window::draw` time in four states — idle / scrolled / clicked / **selecting** — across a payload-size ladder, and (b) **selection fingerprints**, the hashed text that a fixed set of drag geometries actually selects. (a) is how you see a frame-cost regression; (b) is the differential gate on any change to selection machinery — capture before and after and diff, because on a forensic surface "faster" must never mean "selects something else". Real payloads can be fed in via `EIDOLA_RECORD_PERF_REQ` / `EIDOLA_RECORD_PERF_RESP` (bytes extracted from a `request` row), and `EIDOLA_RECORD_PERF_SHOTS=<dir>` writes a PNG per case. Run it on the **dev** profile as well as `--release`: `just build gui` is unoptimized, so the dev numbers are the ones a developer actually feels.
- **Deep link in.** `RecordView::show_request(id)` selects the Requests section and opens that request's detail — the door a space's trace row (task 34) comes through, via `crate::open_record_request`, which raises-or-opens the singleton and reaches the view through the `AppGlobal::record_view` weak handle held beside the window handle. Backing out of the detail therefore lands on the listing the request belongs to.
- **Space cross-link.** The request detail view includes a "Space" kv row when `RequestDetail.space_id` is set (a LEFT JOIN through `action → space` added to `db::get_request`). The row renders as a quiet link (`theme.link` color, hover underline) whose click defers `open_space_window(cx, stores, space_id)` — the same path the Library uses, so opening a linked space from the Record is a single click. The label is `space_title` when present, the bare id otherwise. Behavior test: `record_request_detail_exposes_space_link`.
- **Mono is for data, the UI font is for chrome** — `mono()` (Menlo 12/13px) wraps every hash, nonce, path, and payload; labels, timestamps and empty states stay in Newsreader. Timestamps are UTC and say so (`fmt_utc`, Hinnant `civil_from_days` — no chrono dependency).

## Virtualized lists

Fixed-height lists render through gpui's `uniform_list` (`crates/eidola-gui/STATE.md` → "Lists"): the **Record** sections (attestations / requests / spending) and the **Library** index. The **space view**'s posts are variable-height and use their own height-cache virtualization instead (see [Space view → `layout.rs`](#space-view--tree-navigation-conversation-surface-srcspace_view-wave-6)). The `uniform_list` idiom (mirrors zed's project panel / pickers at our pin):

- **Item-range closure via `cx.processor`.** `uniform_list(id, count, cx.processor(|this, range, _window, cx| this.render_rows(range, cx)))` — the closure is a *dumb indexer*: it renders only `range` (the visible window), so per-frame work is O(visible), never O(loaded). Any structure the closure would otherwise have to reconstruct from a bare range (group headers, separators, a load-more affordance) is **precomputed into a flat display model** (`Vec<DisplayRow>` in the Record) so the closure stays a pure index→element map.
- **Fixed row height.** `uniform_list` measures one row and lays every row out at that height, so all rows in one list must be the same height. Rows are normalized to an explicit `.h(ROW_H)` (deterministic, not font-metric-coupled); variable content (multi-line sublines, depth) is truncated with the middle-ellipsis helpers and pushed into the detail view — the listing row is always fixed-height.
- **Stored scroll handle.** A `UniformListScrollHandle` lives on the view and is passed to `.track_scroll(&handle)` each frame (so scroll position survives re-renders and supports programmatic `scroll_to_item`).
- **Sizing.** `ListSizingBehavior::Auto` (the default) makes the list fill its flex parent and scroll internally — place it as a `flex_1` child (v_flex parent) or give it `.h_full()` inside a `flex_1().min_h_0()` parent (h_flex, e.g. the Library's centering wrapper). The list's own `overflow.y = Scroll` is set by `uniform_list`; do **not** wrap it in another `overflow_y_scroll` div (that nests two scroll surfaces and the inner list collapses).

## Scroll indicators (`src/scrollbar.rs`)

Every scrollable surface that isn't the space page carries a quiet **overlay scroll indicator** — the macOS overlay idiom the onboarding window established, factored into `crate::scrollbar`. It is a right-edge `gpui_component::scroll::Scrollbar` in `ScrollbarShow::Scrolling` mode: it appears while scrolling and fades out, reserves **no** permanent gutter, and shifts nothing (a surface that never overflows shows nothing). `Scrollbar::vertical` binds to either a plain `ScrollHandle` (an `overflow_y_scroll` div's `track_scroll`) or a `UniformListScrollHandle` (a `uniform_list`'s) — both implement `ScrollbarHandle`.

- **Two constructors, by whether the viewport meets a window corner.** `vertical(id, handle, window)` is the **window-edge** strip (a view's full-height scroll body): its ends can coincide with the window's rounded corners, so it applies corner clearance (below). `vertical_floating(id, handle)` is a **bounded** overlay — a dropdown/popover floating mid-window (the model picker) that never touches a window corner, so it takes **no** clearance (and needs no `Window`); applying window-corner clearance to a mid-window element would wrongly inset its thumb on Linux, since `corner_clearance` keys off the window's decorations, not the element's position.
- **Placement rule.** The overlay is dropped as a **sibling** of the scroll container inside a `relative` ancestor that spans the scroll viewport — never a *child* of the `overflow_y_scroll`/`uniform_list` element (a child scrolls away with the content). So each host wraps its scroll body in a `relative` column holding `body` + the overlay.
- **Corner duty (Linux CSD).** `vertical` insets both ends by `crate::chrome::corner_clearance` (the minimap precedent), so the thumb never paints over a rounded window-corner arc; zero on macOS / SSD / tiled edges, so hosts apply it unconditionally. `vertical_floating` skips it (see above).
- **Interactivity.** The gpui-component `Scrollbar` handles its own thumb drag/hover; it is **not** a `.probe(…)` target (a plain indicator, not one of our accessible affordances), so it adds nothing to the AccessKit tree or the driver's selector vocabulary.
- **Where it's wired.** Window-edge (`vertical`): the **Library** (`self.scroll`, on the centered list's right edge), the **Record** (each section's `UniformListScrollHandle` for the virtualized listing, plus a `detail_scroll` for the `scroll_wrap` detail/pending/empty bodies), every **Settings** pane (one shared `body_scroll` on the content column — General · Backends · Templates · Account · Wallet), the **Participants** roster (`body_scroll`), and the **Updates** body (`body_scroll`). Bounded (`vertical_floating`): the **model-picker dropdown** shared by the Participants editor/add form and the Templates pane (`participants_view::model_field`; the host holds a single `picker_scroll` reset to the top on each open, since at most one picker is open at a time — the dropdown's own `max_h(220)` scroller is independent of the roster/settings body underneath it). The **onboarding** page-scroll uses `vertical` inline (its own `page_scroll`). **Excluded:** the space view's page scroll — its **minimap is the scroll indicator** — and the composer's text scroll (the delicate composer/minimap machinery). Render-smoke coverage: `*_renders_with_scroll_indicator` in `tests/behavior.rs` (each view draws with the overlay bound; the Participants case also opens the add-form picker over a 12-model catalog so the dropdown overflows and its own indicator binds); the driver's `library` / `record` / `settings` / `participants` scenes exercise it interactively (the `record` scene seeds attestation rows and the `participants` scene a full model catalog so their listings/picker scroll).

## Edge-to-edge titlebar

`transparent_titlebar()` returns `TitlebarOptions { appears_transparent: true, title: None, traffic_light_position: Some(point(14, 11)) }`. macOS extends the content view under the traffic-light buttons and stops painting a separate titlebar background. Each view leaves room at the top so the lights (macOS) / the CSD window controls + primary-menu wordmark (Linux — see [Linux window chrome](#linux-window-chrome--csd-primary-menu-keyboard)) don't land on real UI. The reserves are now platform-uniform:

- **`space_view::TITLE_BAR_RESERVE`** (36px): vertical reserve, plus a `theme.background → transparent` linear-gradient overlay (the space view's title band, wired through `titlebar::make_draggable`) painted absolutely over the scroll area. Posts scrolling up under the band fade smoothly into the chrome instead of clipping at a hard edge. The band is pure chrome — identity rides in each post's gutter byline, and neither the band nor the composer carries model chrome (see Prose typography / the Space view section).
- **`settings::NAV_TOP_RESERVE`** (44px): the traffic lights (macOS) / CSD window controls (Linux) sit over the sidebar nav band, so the band's first item starts below them.
- **`record::STRIP_LEFT_PAD`** (80px on macOS / 86px on Linux): horizontal pad on the Record's section strip, which doubles as the title bar — the traffic lights (macOS) or the chrome "Eidola" menu wordmark (Linux) live to its left. 80px matches gpui-component's own `TITLE_BAR_LEFT_PADDING`. The strip's right padding adds `chrome::controls_reserve(window)` so the Refresh affordance and wordmark clear the Linux window controls.

**The header captures the mouse** — one instance of the overlay-containment rule below. A press on the transparent band used to land in the post scrolled beneath it, so the window-move gesture dragged out a text selection with it (task 32). The fix is `titlebar::make_draggable` declaring the strip `Overlay::Fade` plus painting the space view's band **after** the page it covers; moving it also restored the documented fade, which never rendered while the band painted under the posts. Regression: `space_title_band_press_does_not_select_the_post_beneath`.

**The drag band is 36px in every window** — `titlebar::DRAG_BAND_HEIGHT`, which every per-module `TITLE_BAR_RESERVE` and Settings' `NAV_TOP_RESERVE` now alias. Settings alone used to reserve 44, purely to fake the top padding the Backends pane lacked; once the band began *blocking* the mouse that extra 8px strip sat over the pane's tab strip and made the Eidola/Local/External tabs unclickable. The band is a hit target the user cannot see, so a uniform height is what makes "grab the top of any window" mean one thing — and panes carry their own heading padding rather than having the band fake it. Regression: `settings_backends_tabs_paint_clear_of_the_drag_band` (probe test, geometric: every tab's painted top is at or below the band).

## Overlay containment — surfaces that cover live content (`src/overlay.rs`)

**gpui does not occlude by painting.** A hit test reports **every** hitbox under the cursor and a listener fires whenever its own hitbox is hovered, so an element drawn on top of another does not take the mouse away from it. Containment is an explicit opt-in (`.occlude()` / `.block_mouse_except_scroll()`) and it suppresses only hitboxes registered **before** the blocking one — so a contained surface must *also* be painted after whatever it covers. Both halves were forgotten twice in the same shape (the drag band above; the floating composer, where a drag-select fell through to the post underneath, selecting it *and* driving the page's selection-autoscroll, so selecting your own draft scrolled the window). Two instances of one bug class is why the rule is a shared seam rather than a third local `.occlude()`.

Every surface that visually overlays live content declares an `Overlay` class via `overlay::Contain::contain_mouse`. The axis is **what should happen to the wheel** — clicks are unambiguous, they always belong to what you can see under the pointer:

| Class | Clicks | Wheel | Primitive |
| --- | --- | --- | --- |
| `Overlay::Fade` — translucent chrome you read live content *through* | captured | **falls through** to the page | `block_mouse_except_scroll`, no scroll handler |
| `Overlay::Scrolling` — an opaque surface that owns its own scrolling | captured | reaches the surface's **own** handler | `block_mouse_except_scroll` + a scroll handler |
| `Overlay::Popover` — an opaque surface with nothing to scroll | captured | captured | `occlude` |

`Fade` and `Scrolling` share a primitive; what separates them is that a `Scrolling` surface registers a scroll handler, so the wheel is consumed by the surface under the cursor (the macOS convention) instead of continuing to the page. The composer's handler deliberately *routes* rather than always consuming — a floating composer with nothing of its own to scroll hands the gesture to the page, which moves it toward its dock — and that policy living on the surface is exactly why `Scrolling` is not just `Popover`. `Popover` blocks the wheel because a menu whose page scrolled out from under it would be anchored to content that has moved.

**The inventory** (space window unless noted; "before" = what it did prior to this pass):

| Surface | Before | Class | Note |
| --- | --- | --- | --- |
| Title/drag band (every window) | blocked non-scroll | `Fade` | migrated onto the seam |
| Floating/docked composer | **nothing** — opaque, leaked clicks | `Scrolling` | the reported bug |
| Context menu | `occlude` | `Popover` | migrated; already correct on both clicks and wheel |
| Band menu (Reply-or-Ask) | `occlude` | `Popover` | migrated |
| Source-highlight picker | **nothing** (had `on_mouse_down_out` without the block) | `Popover` | fixed |
| Failure notice / cascade notice | **nothing** | `Popover` **on the card** | never on the transparent full-width wrapper, which spans the window and would swallow clicks nowhere near the notice |
| Minimap | **nothing** (clicks gated on `minimap_visible`) | `Fade`, **only while visible** | a faded-out 36px strip must contain nothing; the wheel always passes — this strip *is* the page's scroll indicator |
| Library / Participants / About drag bands | blocked, but painted **first** — a no-op | `Fade`, now painted **last** | this file previously claimed every other window already painted its band last; it did not |
| Linux chrome controls + primary menu | both-phase press swallow / `occlude` | unchanged | `chrome.rs` owns its own idiom |
| Overlay scroll indicators | gpui-component internal | not ours | `ScrollbarShow::Scrolling` swallows presses only while visible — upstream behavior, unchanged |

**When you add a floating surface:** pick a class, call `contain_mouse`, and paint it after what it covers. Tests: `space_composer_drag_is_contained_and_does_not_scroll_the_page` (the composer's press stays in the composer *and* the page's scroll offset is unmoved — its teeth are a fixture-derived point where composer text and post text genuinely overlap) and `space_title_band_press_does_not_select_the_post_beneath`.

**Window dragging is wired explicitly** (`src/titlebar.rs`). With the transparent titlebar macOS no longer hands us a draggable strip, gpui's `WindowControlArea::Drag` is a no-op there, *and the Wayland backend never implements the control-area hit-test either* — so one explicit gesture serves both platforms: arm on left mouse-down, call `Window::start_window_move()` on the first move while armed (so a plain click never starts a drag). Double-click forwards to `Window::titlebar_double_click()` on macOS (respects the user's zoom-vs-minimize preference) and `Window::zoom_window()` on Linux (maximize toggle); right-click calls `Window::show_window_menu(pos)` — the *compositor's* window menu (move/resize/workspace/always-on-top), the idiomatic Linux window-scoped menu, a no-op on macOS. The armed flag is **element-owned state** (`window.use_keyed_state` inside `make_draggable`, keyed on the strip's id, holding a `Cell<bool>` mutated without an entity update so arming never re-renders): it survives any re-render landing between the mouse-down and the first move because element state persists while the element keeps painting, and the drag strip is unconditional window chrome — no view field or constructor plumbing. A left mouse-down inside the CSD resize band is ignored (`chrome::in_resize_band`, always false off Linux) so the very edge belongs to the resize, not the move. `titlebar::drag_band(id, height, window, cx)` builds a full-width transparent overlay band absolutely positioned over the reserve (used by About / Library / Settings / Onboarding, painted **last** so it wins hit-testing over the columns beneath); `titlebar::make_draggable(stateful_el, key, window, cx)` attaches the same gesture to an existing strip (Updates' top spacer, Record's section strip — whose tabs keep their own clicks since a plain click never arms — and `space_view`'s gradient title band, which now routes through the helper instead of inlining the gesture).

## Linux window chrome — CSD, primary menu, keyboard

Everything lives in `src/chrome.rs` (see its module docs for the full rationale); this section is the map.

**Decoration model.** Wayland has no server titlebar unless the compositor implements `zxdg_toplevel_decoration_v1` — KWin does, Mutter never does. Every window *requests* `WindowDecorations::Client` (`lib.rs::base_window_options`, which also sets `window_background: Transparent` so the shadow padding is see-through, and the Wayland `app_id`); `chrome::ChromeRoot` — a wrapper view `lib.rs` interposes between `gpui_component::Root` and each window's real view (`ChromeRoot::wrap`, an identity on macOS so the macOS render tree is untouched) — then renders by what was actually granted:

- **`Decorations::Client`** (GNOME always; KDE by default): the zed-pattern CSD frame — shadow padding on untiled edges (`SHADOW_SIZE` 12px, folded into `set_client_inset`), a 1px `theme.border` frame, rounded corners on **all four** window corners (`CORNER_RADIUS` 12px, the Adwaita radius), resize-edge mouse handling (`start_window_resize` on the backdrop; the hit band spans the whole shadow margin **plus 4px inside the visible frame edge**, so the resize cursor is discoverable at the border — drag strips check `chrome::in_resize_band` on mouse-down and yield to the resize there), and the **window-controls cluster** at top-right — quiet ghost buttons in our voice, not fake-native: minimize / zoom render only if `window.window_controls()` reports the capability (sway shows close-only; GNOME shows all three), close always. Maximize/fullscreen fold into `Tiling::tiled()`, so shadow/rounding/resize collapse automatically when maximized. Resize *cursors* are declarative zones — transparent, listener-less absolute divs over the band, each with `.cursor(...)` — never `window.set_cursor_style` from a paint callback: an imperatively set cursor is a per-frame request against the last-painted hitboxes, so a full-window request outlives the pointer's stay in the band until the next repaint (the "stuck resize arrow" bug).
- **`Decorations::Server`** (KDE forced-SSD): no frame, no controls, no drag band duty — the native titlebar handles window management (this arm paints the window background, since `themed_root` strips Root's). The **primary menu still renders** (it's app chrome, not window management).

**Single CSD authority.** `gpui_component::Root` ships its *own* Linux CSD layer (`window_border()`: shadow padding, a 1px `theme.window_border` frame, resize hit zones, and an opaque `bg(theme.background)` across the whole window). Stacked under ours it painted our shadow padding as an opaque cliff and put resize cursors at the wrong edge. Every window is therefore built through `chrome::themed_root` (Root with `bordered(false)` + transparent background — Root must stay the outermost view because gpui-component's `Input` resolves it via the window root), and both Circadian palettes pin `window_border` transparent as belt-and-braces. `Root::bordered(false)` (upstream gpui-component [#2466](https://github.com/longbridge/gpui-component/pull/2466)) makes `Root::render` return its inner content directly instead of wrapping it in `window_border()`, so the competing layer — shadow padding, frame, resize zones, *and* the BoxShadow it painted at the surface edge — is gone entirely, not merely zeroed. (The earlier approach, `window_shadow_size(0)`, left `window_border` in the tree and it still painted a zero-blur full-surface black veil at α 0.3 — a hard outer edge on the shadow band; adopting the upstream opt-out removed that residue.)

**Content-box discipline.** `window.viewport_size()` is the whole surface *including* the CSD shadow padding. Any view math that anchors to the window bottom/right or sizes a page (the space view's floating composer, minimap, scroll ranges, dock positions) must use `chrome::content_size(window)` (viewport minus `chrome::content_insets`) or bottom-anchored overlays hang into the shadow band. On macOS/SSD/tests it equals the viewport.

**Containment + corner duty.** The chrome frame clips all descendants to its rect (`overflow_hidden`; gpui deferred draws re-apply the content mask captured at their tree position, so even deferred overlays — the chrome's own controls/menu, or any future one — stay contained; the space view's composer/minimap paint in the normal pass and are masked trivially). The clip is rectangular (gpui masks carry no radii), so the rounded corner *notches* remain each corner-touching surface's duty: window roots apply `chrome::round_client_corners`; partial-edge bands use the top/bottom/single-corner variants (the Settings nav band rounds `tl` + `bl`; the space view's gradient title band rounds top only; the **space composer bar** — the window's bottom-most opaque surface — rounds bottom with `bar_h` clamped to end exactly at the window bottom, and when the docked bar covers the window (a draft slot scrolled above the viewport makes `top_y` negative) its *visible quad* is split from the virtual geometry — quad pinned at the window top, inner content hung at the virtual offset — so its top corners round at the window's top arcs instead of a square mid-section filling the notches); full-height edge strips inset their ends by `chrome::corner_clearance` (the minimap, which also scales its map into the reduced run). All helpers are no-ops on macOS/SSD/tiled, so views apply them unconditionally.

**Primary menu.** The Linux replacement for the macOS app/Space/View menus (`cx.set_menus` builds no UI on Linux): a quiet italic **"Eidola" wordmark** at the window's top-left (GNOME's primary-menu idiom in our voice — a signature on the page, not a hamburger) opening a popover of the app-scoped commands — New Space, one "New Space from “{title}”" row per live template (the macOS "New Space from Template ▸" submenu flattened; read from `TemplatesStore` at render time, so the list is fresh on every open), Participants… (a no-op without a focused space window, matching the greyed macOS item), and the selection-scoped **Quote** / **Quote in Reply** pair (the macOS Edit menu's quote verbs — Linux has no Edit menu here, and Quote carries no chord, so the popover is its only pointer route; they group with the space-scoped items because that is what they act within); then the View-menu zoom trio (Actual Size, Zoom In, Zoom Out); then Library, Record, Settings, Check for Updates, About, then Quit — each with its Ctrl-chord rendered beside it (the zoom trio shows Ctrl+0 / Ctrl++ / Ctrl+-), so the popover doubles as the keyboard-reference card. It is one flat list (no File/app split), but the grouping mirrors the macOS structure: the **space-scoped group** leads (the macOS "Space" menu: New Space + templates + Participants…), the **zoom trio** is its own group (the "View" menu), and Library/Record group with the app-level items below. Items dispatch the same actions the macOS menus use (`window.dispatch_action` → the global handlers). Toggled by click or **F10** (the desktop-standard key; bound Linux-only, handled by an `on_action` on ChromeRoot's wrapper div — an ancestor of every focused element). Dismissal: click-out, re-toggle, or selecting an item; no in-popover keyboard navigation in v1 (every item shows its direct chord). Probes: `chrome/menu`, `chrome/menu/panel`, `chrome/menu/{slug}`; regression tests in `tests/probe.rs` cover action-toggle, the real **F10 keystroke** through the production keymap, and a **real simulated click** on the wordmark's painted bounds (the deferred-hitbox + press-swallow interplay).

**Chrome z-order.** The controls cluster and menu render `gpui::deferred` at priority 100/101 — the deferred pass paints after the whole normal-pass tree, so chrome sits above all view content (including the space view's layered composer and normal-pass minimap — see the space view section). Both swallow their mouse-down (both-phase, the Library-pencil pattern) so clicks never arm the drag band beneath. The minimap's top strip passes under the controls; acceptable (it's interactive only while its overlay is up).

**Keyboard.** Three layers (see `install_keybindings` + `gpui_markdown_editor::init`):

- **Chord commands** bind with gpui's **`secondary-` alias** (⌘ on macOS, Ctrl elsewhere): all globals (`secondary-n/l/shift-l/w/q/,`, `secondary-alt-i`) and the editor's clipboard/select-all/submit chords (Ctrl+↩ Posts, Ctrl+⇧↩ posts quietly on Linux).
- **Motion/deletion** differ structurally, so the editor keymap has per-platform tables: macOS keeps ⌥=word / ⌘=line-or-document; Linux gets Ctrl+arrows=word, Ctrl+Home/End=document, Ctrl+⌫/Del=word-delete (a blanket alias would have made Ctrl+← "line start"). Home/End are platform-neutral.
- **Not bound on Linux**: ⌘H/⌥⌘H (hide — an AppKit concept) and ⌘M (minimize — the compositor's job on Wayland).

User-visible chord copy goes through `actions::{primary_chord, primary_shift_chord, alt_name}` ("⌘N" on macOS, "Ctrl+N" on Linux) — never hardcode the mac glyphs in strings.

**Lifecycle & identity.** On Linux a *windowed* launch quits when its last window closes — now expressed as `QuitMode::LastWindowClosed` rather than an `on_window_closed` observer (see [App lifecycle](#app-lifecycle--the-app-outlives-its-windows)); there's no dock/menu-bar presence to make a windowless app reachable, so a lingering headless process would just be a leak. A user who *wants* the long-lived process asks for it with `--windowless`, which is what the systemd user unit (`eidola service install`) launches. Every window sets `app_id = "tech.m6i.Eidola"`, matching the basename of `releases/linux/tech.m6i.Eidola.desktop` (shipped in the Nix artifact under `share/applications/`) — that equality is what gives us a name in Alt-Tab/the shell and dock pinning. The desktop entry references a themed icon (`Icon=tech.m6i.Eidola`) that **does not exist yet** — an icon asset is an open design task; until it lands the shell shows a generic icon with the right name. For the dev loop, symlink the .desktop into `~/.local/share/applications/` (with `Exec` pointing at the dev binary) if you want shell integration for `cargo`-built runs.

**Validated headlessly** (2026-07-02/03, sway headless + grim under Nix — GNOME blocks unattended screenshots; the rig injects text but not wheel events, so scrolled states were reached with a temporary debug scroll hook that has since been removed): frame/rounded corners/shadow/border render, controls are capability-driven, the wordmark paints, text input and Ctrl+A work through a live Wayland virtual keyboard, and `xdg_toplevel.set_app_id("tech.m6i.Eidola")` is on the wire (`WAYLAND_DEBUG=1`). Shadow compositing was proven by pixel-scanning the band over two different desktop colors (the band tracks the backdrop per-pixel; with the dependency patch applied it fades smoothly to zero on all four edges, symmetric top/bottom). Pointer injection doesn't reach headless-sway surfaces, so click paths are guarded by the in-process probe-bounds tests instead.

## macOS UX — menus, keybindings, action dispatch

All wired in `src/lib.rs::install_menus`, `install_keybindings`, `install_action_handlers`. **Order of those calls matters** — see [Ordering invariant](#ordering-invariant) below.

### Menus (`cx.set_menus`)

- **Eidola**: About / Check for Updates… / Get Started / Settings… / Library… / Record… / Hide / Hide Others / Show All / Quit — Library and Record live here (not under a "File"/"Space" menu) because they open app-level windows over your whole trail, not the current space; they sit just under Get Started / Settings…, the other app-scoped entries
- **Space**: New Space / Close Window — the space-centric replacement for the conventional "File" menu (the space/conversation is our unit of work). "New Space" keeps the deeply-established File→New idiom even though it isn't strictly space-scoped; genuinely space-scoped items (space settings, export, …) will land here
- **Edit**: Undo / Redo / Cut / Copy / Paste / Select All / **Quote** / **Quote in Reply** — Cut/Copy/Paste/Select All declared via `MenuItem::os_action(_, _, OsAction::*)` so they bind to the standard macOS selectors `cut:` / `copy:` / `paste:` / `selectAll:` and route through the responder chain to whatever has focus. The **quote pair** is an Edit-menu verb because it acts on the *selection*, like Cut/Copy; both handlers are registered per-`SpaceView` **and only while a quotable post selection exists**, so macOS greys them the rest of the time (see [Space view → `references.rs`](#space-view--tree-navigation-conversation-surface-srcspace_view-wave-6))
- **View**: Actual Size / Zoom In / Zoom Out — the standard macOS type-size trio (the `ActualSize` / `ZoomIn` / `ZoomOut` actions). Deliberately kept minimal and scoped to just these items so it composes with a concurrent File/app-menu restructuring without collision — this file only ever *adds* a View menu. The handlers write the `font_scale` config override through the shared `ConfigStore` (`reset_zoom` / `zoom_in` / `zoom_out`, which read the current scale off the snapshot and step the app-core ladder), so the write emits `Change::Config` and `theme::wire_config`'s observer re-applies the scaled palettes on every window
- **Window**: Minimize / Zoom

`cx.set_dock_menu` adds "New Space" and "Library…" for the dock right-click menu.

**The "Window" menu name is special.** gpui_macos detects a menu literally named `"Window"` and calls `app.setWindowsMenu_(menu)` — which is how AppKit recognizes the app as a fully-wired macOS app and reliably dispatches menu key-equivalents in edge cases (no key window after ⌘Tab back, all windows closed). The Hide / Hide Others / Show All trio play the same "I'm a real app" signaling role.

### Keybindings (`cx.bind_keys`)

Global chords bind with the **`secondary-` alias** (⌘ on macOS / Ctrl on Linux — see [Linux window chrome → Keyboard](#linux-window-chrome--csd-primary-menu-keyboard)): `secondary-,` (Settings), `secondary-n` (NewSpace), `secondary-l` (OpenLibrary), `secondary-shift-l` (OpenRecord), `secondary-w` (CloseWindow), `secondary-q` (Quit), the View-menu zoom trio `secondary-0` (ActualSize) / `secondary-=` + `secondary-+` (ZoomIn — both the bare `=` and the shifted `+` that shares the physical key) / `secondary--` (ZoomOut). The former `SpaceView`-context ⌥⌘M (`ToggleModelPicker`) is **removed** with the request panel — the composer carries no model choice (Participants configuration owns it), so the chord has no coherent meaning and was retired rather than repurposed. The zoom chords are global (no context) so they fire even with the composer focused — the `MarkdownEditor` keymap binds none of `0`/`=`/`+`/`-` under the primary modifier. Regression: `zoom_keystrokes_resolve_to_actions` in `tests/probe.rs` drives all four keystrokes through the production keymap. macOS-only: ⌘H (Hide), ⌥⌘H (HideOthers), ⌘M (Minimize). Linux-only: F10 (TogglePrimaryMenu). The submit chords ⌘↩/Ctrl+↩ (**Post** — the space's participants decide who responds) / ⌘⇧↩/Ctrl+⇧↩ (**Post quietly** — notify no one; the ⌥-revealed verb) are **not** view bindings — they live in the `MarkdownEditor` context (`gpui_markdown_editor::init`) and reach `Send`/`PostOnly` via the editor's `PressEnter` event, routed by each draft's subscription (`space_view::composer::create_draft_node`) and by an edit session's subscription (`post.rs::begin_edit`); binding them on the view would shadow the editor (the composer is the inner focus). Esc (band-menu dismiss → draft deactivation, and edit cancel) routes through element key handlers rather than bindings, so it composes with the editor's focus without a parking dance.

### Ordering invariant

`install_keybindings(cx)` **must** run before `install_menus(cx)`. `cx.set_menus` snapshots the keymap when it builds NSMenuItems and attaches each item's `keyEquivalent` from `keymap.bindings_for_action(action)`. Setting menus before binding keys leaves the keymap empty at lookup time, no keystroke is attached, and macOS can't intercept the shortcut at the menu level — which then breaks ⌘N / ⌘Q etc. when no window has key focus (the only path that *requires* the menu-level intercept; with a window focused, gpui's per-window binding dispatch handles it independently). **Diagnostic signal**: items appear in the menu without their shortcut text on the right side.

### Action handlers (`cx.on_action`)

Most handlers are global (registered on `App`). Two notable patterns:

- **Window-targeting handlers** (`Minimize`, `Zoom`) capture `cx.active_window()` and call `cx.defer` to invoke `window.minimize_window()` / `zoom_window()` *after* the current update completes. Without `defer`, a direct `handle.update(cx, …)` on the same window we were dispatched inside fails (its slot is already taken), `.ok()` swallows the Err, and nothing happens.
- **`CloseWindow` is registered per-view**, not globally. Each view (the chat/space window included) does `.on_action(cx.listener(|_, _: &CloseWindow, window, _| window.remove_window()))` on its root, and `track_focus`es a handle that's `focus()`ed in the view's constructor (so the dispatch path reaches the listener even before the user clicks anything). The intentional consequence: `is_action_available` returns true only when a window with the listener is alive, so macOS auto-disables the "Close Window" menu item (and ⌘W) when no window is open.

### Lifecycle

- `cx.activate(true)` at launch: brings the app to the foreground from frame 0 so the menu bar is fully connected before the user interacts.
- `Application::on_reopen` (registered on the `Application` builder *before* `run()` — the method takes `&self` and returns `&Self`, while `run()` consumes by value, so it can't be chained inline; bind the application to a local first): focuses a window, or opens the Library when there is none. Without this, closing the last window leaves the app running but unreachable. See [App lifecycle](#app-lifecycle--the-app-outlives-its-windows).

## .app bundling — required, not cosmetic

A bare `cargo run -p eidola-gui` binary launches as a command-line tool from AppKit's perspective, not a real app. `setActivationPolicy(Regular)` papers over the common path (menu shows, items enable, mouse clicks dispatch), but **menu key-equivalents fail to dispatch when no window is key**, even with the keymap-ordering fix above. The diagnostic signal is the menu bar showing the binary name (`eidola-gui`) instead of the app name (`Eidola`).

The fix is a proper macOS bundle:

- `crates/eidola-gui/Support/Info.plist` — `CFBundleIdentifier = tech.m6i.eidola-gpui`, `CFBundleExecutable = Eidola`, `NSPrincipalClass = NSApplication`, `NSHighResolutionCapable = true`.
- `scripts/package-gui-app.sh` — copies `target/{debug,release}/eidola-gui` to `Contents/MacOS/Eidola` (renamed to match `CFBundleExecutable` — mismatch falls back to tool-mode), copies the Info.plist, ad-hoc codesigns. Output at `crates/eidola-gui/build/Eidola.app` (gitignored). This is the **dev path** — fast cargo iteration, ad-hoc signed for local launch only.
- `just build gui` runs `cargo build` then the package script on macOS. `just run gui` builds + `open`s the .app. Non-macOS falls back to `cargo run`.
- **Release path:** `nix build .#eidola-gui-macos-universal` (flake.nix) builds an aarch64 + x86_64 universal binary, zeros LC_UUID for reproducibility, and assembles the same `Eidola.app` layout into a Nix store output that's recorded as `eidola-gui-macos-universal` in `artifact-manifest.json` (Nix `narHash`, `darwin/universal` platform). Built locally via `just update-manifest` (alongside the CLI universal binary) and in CI by the `apple` job. Two reproducibility tricks make this work inside the Nix sandbox: (1) gpui's Metal shaders are compiled at app startup via `runtime_shaders` (passed through `gpui_platform/runtime_shaders` → `gpui_macos/runtime_shaders`) instead of via Apple's closed-source `metal` compiler at build time; (2) `flake.nix`'s `commonArgs.preBuild` stitches a missing `assets/assets/icons` sibling layout into the cargo-vendored gpui-component dep, working around an upstream packaging bug where the `icon_named!` proc-macro reads `../assets/assets/icons` relative to its `CARGO_MANIFEST_DIR` (a path that only resolves in the upstream workspace layout, not in `cargo vendor`'s flattened tree).

## Testing — two tiers

Both tiers run via `cargo test -p eidola-gui` (`crates/eidola-gui` has both `[lib]` and `[[bin]]` so the integration tests can import view modules). A third, non-gating tool — the interactive UI driver — sits alongside them for agent-led QA sessions; see [The UI driver](#the-ui-driver-examplesdriverrs--interactive-qa-sessions).

### Behavior tests (`tests/behavior.rs`) — the regression gate

Built on `gpui::TestAppContext` (mocked rendering, deterministic dispatcher) so they run on libtest's worker thread without AppKit. Pattern:

1. Build stub stores with `Stores::stub_with(StoresStub { … }, cx)` — a declarative fixture scene (config snapshot, balances, prices, spaces, …).
2. Open a window with the view under test (via `cx.open_window`).
3. Drive interactions through the view's `focus_handle()` — the same path keystrokes take in production.
4. Assert against the view's public state, or the store entities (`stores.account.read_with(cx, …)`), with `read_with`.

Stub stores have no backend, so `Stores::app_core()` returns `None`; views that hit that path early-return after the local state mutation, and store `refresh_*`/`request_*` are no-ops. The store *machinery* itself (supersede, the bus bridge's dispatch, the launch-order replay) is tested against a real tempdir-backed `AppCore` in `tests/stores.rs` (via `Stores::for_test`). HTTP-mocked tests (real `AppCore` against a `wiremock` server) are the natural next layer.

### Visual snapshots (`tests/visual.rs`) — local-only debug aid

**Not** a regression gate. Built on `gpui::VisualTestAppContext` (real Metal renderer, offscreen window at -10000,-10000, deterministic dispatcher). Configured as `[[test]] harness = false` so `fn main()` runs on the macOS main thread (libtest's worker-thread harness would SIGABRT inside AppKit).

Cases live in `tests/visual/cases.rs`; the harness in `tests/visual/harness.rs` wraps each user view in a `Root` and renders it **twice — once in Circadian Day, once in Circadian Night** — by calling `Theme::change` between renders. Each case writes/compares two files: `tests/snapshots/<name>-day.png` and `<name>-night.png`. Case build closures must be `Fn` (invoked once per mode); they construct fresh entities each call.

The PNGs are **gitignored** — pixels are platform- and machine-bound (Metal+CoreText vs wgpu+cosmic-text on Linux; font hinting differs across macOS minor versions), so committing them would mean false-positive regressions in CI and on every other developer's machine. Their value is local: agents/humans can `Read` a PNG to "feel" a view at a state, and a developer iterating on a UI change can re-render and eyeball-diff their previous run.

Behavior:

- Missing PNG → write it and report `written`.
- Mismatch against a previously-written local PNG → write `<name>-<mode>.new.png` for review and fail.
- `UPDATE_SNAPSHOTS=1` overwrites.

Recipes: `just render-snapshots` (verify/write), `just render-snapshots-update` (accept).

### Why both tiers?

Behavior tests catch logic regressions (clicking X must call `store.Y(z)`; an empty Send must be a no-op) and survive across platforms. Visual snapshots are the "did I accidentally change the layout?" check that's only meaningful to the dev making the change. Together they let agents make UI changes confidently: behavior tests gate the merge, visual snapshots let the agent verify the change *looks* right by reading the freshly-written PNG.

### The UI driver (`examples/driver.rs`) — interactive QA sessions

The third leg, sitting between the two tiers: a **long-running interactive session** ("Playwright for eidola-gui") that an agent drives over a JSON-lines stdin/stdout protocol. Run with `just driver` (→ `cargo run -p eidola-gui --example driver`; it's an *example* so cargo's dev-dependency unification gives it gpui's `test-support` feature outside `cargo test`). It boots a `VisualTestAppContext` — real Metal rendering into offscreen windows at (-10000,-10000), deterministic `TestDispatcher` underneath — installs the production keymap (`eidola_gui::install_keybindings`, made `pub` for exactly this), and then loops: one JSON request per stdin line, one JSON response per stdout line.

- **Commands**: `scenes` / `open` (a named fixture scene, optional width/height) / `windows` / `elements` (named click targets with painted bounds, from the probe registry — see [Accessibility & QA probes](#accessibility--qa-probes)) / `click` (by probe `target` or x/y, with alt/command/shift, and `button:"right"` for the context-menu gesture) / `drag` (`from_x/y`→`to_x/y` press-move-release with an optional `click_count` for double/triple-click selection and `hold` to pump frames so host autoscroll-while-selecting runs) / `type` / `keys` (gpui keystroke syntax, e.g. `"cmd-enter"`) / `modifiers` (hold/release — drives the real `ModifiersChangedEvent` path, so ⌥ reveals work) / `scroll` / `resize` / `screenshot` (PNG to a path the agent `Read`s) / `theme` (day|night, optional `character`: cool|neutral|warm — renders the tinted circadian variants production derives from the sun) / `settle` (advance the test clock + park) / `close` / `quit`. Full protocol docs in the example's module comment.
- **Scenes** are stub-store fixtures mirroring `tests/visual/cases.rs` — onboarding welcome/plans, empty + populated chat (with a model list so the ⌥ reveal and picker are live), library, settings, updates, record. No backend, no network: store-backed flows stop at the stub guard exactly as behavior tests do, while all window-local interaction (composer editing, submit's local append, picker open/navigate/select, hover reveals, pane navigation) is fully live.
- **Why this exists**: snapshots show one state; behavior tests assert one transition. The driver lets an agent *converse* with the UI — act, look at the actual pixels, act again — closing the QA loop that previously required a human. It needs no Accessibility/Screen Recording permissions, shows nothing on screen, and parallel sessions across worktrees don't interfere.
- **Element staleness**: every `elements` call (and every by-name `click`) clears the window's probe entries, forces a fresh frame, and re-reads — so an unmounted element (a dismissed picker, a row scrolled out of a virtualized list) can never linger as a ghost target. Regression-tested in `tests/probe.rs`.
- **Limits (v1)**: app-global action *handlers* (⌘N/⌘L/Settings…) aren't installed — they need the real `AppGlobal`/backend; window-scoped actions and keybindings all work. Scenes are stub-backed; a real-`AppCore`-against-mock-upstream scene is the natural extension once the wave-4 chat harness lands. macOS-only, like the visual tier.

## Accessibility & QA probes

gpui has AccessKit integration (zed #56065, in our pin): elements opt in per node — an element appears in the platform accessibility tree only if it carries an `ElementId` (`.id(…)`) **and** a role, with labels and state via the aria-style builders on `StatefulInteractiveElement` (`.role(…)`, `.aria_label(…)`, `.aria_selected(…)`, …). On macOS this produces real `NSAccessibility` nodes via `accesskit_macos`.

Our annotation point is **`crate::probe::Probe`** — `el.id("…").probe(name, role, label)` — which does two things at once: sets the AccessKit role + label (always), and records the element's painted bounds into a process-global registry (only when probes are enabled — the driver's `elements`/`click target:` vocabulary). The pairing is the doctrine: **the accessible name is the driver's selector**, so the AT surface and the automated-QA surface are the same annotation and cannot drift apart. The registry is recorded via the public `canvas` idiom (an absolute, paint-nothing, hitbox-free child), because gpui keeps its own bounds maps (`debug_bounds`, the AccessKit tree) crate-private on real-rendering windows; probes are inert in production (the canvas child isn't even constructed when disabled, and the trait bound on `StatefulInteractiveElement` makes ".id() before .probe()" a compile error to forget).

**`probe_value(name, role, label, value)`** is the same annotation plus `aria_value` — the **content** channel, as distinct from the label that names the element. It exists because wave C's whole subject is content, and because `aria_value` is otherwise unobservable: the emitted `TreeUpdate` is crate-private, so a value could only be compile-checked. `ProbeEntry` therefore carries `value: Option<SharedString>` (`None` for a plain `probe`), `tests/probe.rs`'s `assert_probe_value` asserts it, and the driver's `elements` reports it. Read the value rule below before wiring one.

Conventions:

- **Names** are slash-scoped lowercase paths: `space/composer`, `space/band/menu/ask/{idx}`, `library/row/{idx}/archive`, `settings/nav/general`. Dynamic rows interpolate their index — and the name is the driver's selector, so it **must be unique per painted element**: index every repeated affordance (`space/band/dot/{i}`, `record/attestation/{i}`, `onboarding/link/{slug}`), and when a shared component (`plans::plan_rows`) renders in more than one host, the host passes a `name_prefix` so its rows scope under `settings/account/plan/{i}` vs `onboarding/plan/{i}` rather than colliding.
- **Labels** are what a screen reader should say — user-meaningful, not internal names; dynamic where the content is (`"Model: gemma4-31b"`, a library row's title, `"POST /v1/chat/completions — 200"` for a Record request row).
- **Roles** come from `gpui::Role` (re-exported accesskit): Button, Link, Tab, ListBox/ListBoxOption, ListItem, TextInput, Alert, Group, `Article` (a post), `Label` (a static readout — `AXStaticText`), plus the landmark/container set below. **`Alert`** marks status text that must be *announced*, not just readable — the Updates window's Unverifiable "Security warning" band, and the General / Account / onboarding error banners (the last keyed per slide, `onboarding/error/{create,verify,checkout}`, so concurrently-revealed slides don't collide). Disclosures also carry state: the reasoning "Thinking…" toggles set `.aria_expanded(expanded)`; single-select rows/tabs set `.aria_selected(active)`.
- **`Role::Heading` is broken at this pin — do not add new ones.** `accesskit_macos` maps it to the bare string `"Heading"` rather than `NSAccessibilityHeadingRole` (`"AXHeading"`), and exposes no `AXHeadingLevel` at all, so `.aria_level(…)` never reaches VoiceOver either (`accesskit_macos-0.26.2/src/node.rs:125`; the neighbouring `Role::DocSubtitle` line hand-writes the *real* `"AXHeading"`, which is what makes this read as an upstream slip rather than a choice). An unknown AXRole string cannot match VoiceOver's heading rotor, so the annotation buys nothing. Two pre-existing uses remain (`about/title`, `library/title`) — harmless, not worth churning. Use a **named landmark** instead: that is what the Settings content column and the Record body do. *Removal trigger: accesskit emitting `NSAccessibilityHeadingRole` + `AXHeadingLevel`.*
- **gpui-component widgets** (`Button`, `Input`) don't implement the probe traits and have no a11y annotations at our pin (upstream is working on it — longbridge/gpui-component#2407): wrap them in a shrink-wrapped probed `div` (see the `*-wrap` ids in `general.rs`/`wallet.rs`/`account.rs`).
- **New interactive UI must ship with probes.** When you add a clickable affordance, annotate it in the same change — it's one call, and it's what makes the element visible to both AT and the driver. Coverage is asserted in `tests/probe.rs` (per-view tests over stub scenes — Record rows/tabs, the Account & Wallet & General panes, onboarding plans/links, the space composer/minimap); extend it when you add probes to a new view.

**Landmarks and containment.** Role-less containers collapse in the a11y tree — children attach to the nearest role-bearing ancestor — so without deliberate containers every affordance hangs directly off the window root. The named containers, all `.probe`d so they are asserted like anything else:

| Probe | Role | What it contains |
| --- | --- | --- |
| `space/conversation` | `Main` | the scrollable page body — the `space/post/{i}` articles themselves |
| `space/minimap` | `Navigation` | the topology strip — this window's table of contents |
| `settings/nav` | `TabList` | the five `settings/nav/*` tabs (`aria_orientation` vertical) |
| `settings/content` | `Main` | the selected pane, **named for it** (`"Backends settings"`), so switching panes renames the landmark |
| `settings/backends/tabs` | `TabList` | the Eidola · Local · External strip |
| `record/sections` | `TabList` | the section strip (which doubles as the title bar) |
| `record/body` | `List` / `Region` | the virtualized listing when one renders, a named region for the detail / empty / loading shapes |
| `library/list` | `List` | the space listing |

Two things this pass had to work around, both worth knowing before touching them again:

- **`uniform_list` cannot carry a role.** It implements `InteractiveElement` but not `StatefulInteractiveElement`, where gpui's aria builders live — so the `List` parent goes on the container that already spans the viewport (`library/list`, `record/body`), never on the list element. Do not wrap a `uniform_list` in a *new* div to get one; the existing wrapper is there because of the scroll-container invariant, and a second one would break it.
- **Set position is mandatory on a virtualized row — and it counts *data* rows.** `uniform_list` renders only the visible window, so AT sees six of six hundred spaces unless the row sets `.aria_position_in_set` / `.aria_size_of_set`. The index to use is the row's position among the section's **loaded data rows**, never its display index: the Record's display model interleaves spending group headers and a trailing load-more row, so a display-index position announces the first spending entry as "2 of N" and `display.len()` counts the button as a phantom item. `record::RecordView::row_set_metadata` is the one rule all three listings call (Library rows index their store list directly). `size` is the *loaded* count — with `has_more` the server-side total is unknown and gpui offers no way to say so. gpui does not handle `accesskit::Action::ScrollIntoView`, so this metadata plus an explicit paging affordance ("Load more") is the whole story for long lists today.

**Space-window reading order: the minimap is deliberately last.** The audit (`work/tasks/12a`) wanted it moved earlier, on the grounds that it was the *only* conversation content in the tree. It isn't movable without a pixel change and it no longer needs to be. gpui builds a11y nodes in **prepaint** order, which for a div's children is its child order — the same order that decides paint, and the minimap is the last sibling precisely so it paints above the floating composer they overlap on the right edge (`deferred` doesn't decouple them: it defers prepaint too). What resolves the finding instead is the `Main` landmark above it: the conversation region already precedes the composer, and `Navigation` maps to `AXLandmarkNavigation`, so the strip is reachable from the landmark rotor rather than only at the end of a linear walk — which is the correct shape for a table of contents anyway.

**Every window is named.** Each `open_*_window` calls `Window::set_window_title` (see the note on `transparent_titlebar` for why this paints nothing), which is what labels the a11y tree's root node — previously all seven window types presented an unnamed `AXWindow`. Static for the singletons; the space window's title is **live**, tracking the Library index via `SpaceView::sync_window_title` (guarded on change, so an unchanged title never re-enters AppKit), so an auto-title or a rename renames the window.

**Write the title from an observer, never from `render`.** `Window::draw_roots` builds the frame's AccessKit root — label and all — in `a11y.begin_frame()` **before** prepainting the root element, and `set_window_title` marks nothing dirty, so it schedules no follow-up frame. A title set during `render` therefore lands *after* that frame's root was built from the previous one: the platform title (Window menu, switcher) updates at once while the *accessible* root keeps the stale name until some unrelated redraw. So `SpaceView` observes `stores.spaces` with `cx.observe_in` (for the `&mut Window`) and writes the title there, ahead of the frame its own `notify` schedules, plus once at construction. **This ordering is not testable at this pin** — `App::flush_effects` draws every dirty window inside the same update under `test-support`, so both placements look identical from a test, and the AccessKit root label itself is crate-private.

**Labels are spoken, not written.** A label is read aloud, in full, every time the element is focused — which makes three things defects rather than nits: (1) **raw markup** — the minimap cells carry post text through `minimap::spoken_snippet`, which resolves embed markers away (`references::strip_embed_blocks`), drops block markers, and truncates on a word boundary. Its inline pass (`strip_inline_markup`) is **positional, not a blanket delete**: deleting every `*` and backtick corrupts exactly the posts this app carries most — `` `x * y` `` was spoken as "x y" and a literal `\*` lost its character — so a backslash escape yields the escaped character, a **code span is spoken verbatim** (its content is code, so nothing inside it is markup; joining the lines first makes a fenced block's two fences pair here too), and a `*`/`_` run is dropped only when it reads as a delimiter (not whitespace-flanked on both sides, not intraword for `_`, and appearing flanking at least twice so an unpaired `2*3` stays literal). Residual miss cases are documented at the helper rather than parsed away; (2) **repeated context-free verbs** — Edit / Remove / Rename / Archive name their subject (`"Archive Tides and the moon"`), via `participants_view::ghost_button_labeled` where the visible label must stay short; (3) **long hex** — a hash is announced character by character, so labels carry a short form (`record::spoken_hash`, `backends_settings::hex_summary`) and the full value rides in `.aria_value(…)`, which AT reads on request. Controls whose group label is a node-less `div` fold it into their own name (`"Day & night: Auto"`, `"Larger text, currently 100%"`).

**Content is in the tree — and only when it has settled (wave C).** The tree used to hold affordances and nothing else: in the space window a screen-reader user perceived no post text, no byline, no composer content, no error message. What fixed it is `probe_value`, applied under one rule.

*The rule* (the audit's §4, the single most dangerous trap in this area): **an `aria_value` may only be bound to text that has stopped changing.** Assistive technology re-reads a focused control's whole value on every change, so a value wired to a streaming reply or a live editor buffer re-speaks the entire text per token/keystroke — annotation that makes the app *less* usable than silence, while looking more accessible. So:

- **A settled post is an `Article`** (`space/post/{i}` — `AXGroup` + subrole `AXDocumentArticle`), named `post::article_label` (author · serving backend · time — the byline gutter's three stacked, node-less lines folded onto one) with the whole post as its value via `minimap::spoken_text` (the `spoken_snippet` pipeline with no truncation: markdown punctuation dropped, embed blocks resolved away, lines folded). **A streaming reply gets no node at all** — the row becomes one the moment the stream finalizes into a settled row. Live progress belongs in an announcement, which needs `aria_live` (U1), so until then streaming is honestly unannounceable and we say so rather than fake it.
- **The composer's value is frozen while it is focused** (`SpaceView::composer_aria_value`, snapshot `(draft id, text)`), refreshing at settled moments only. This is Zed's own text-field behaviour, for the same stated reason. **The moment that matters is `activate_draft` — an editing session beginning — which seeds the snapshot from the draft's buffer**; the render-time rule adds a frame where focus has left the composer, plus an is-this-a-different-draft backstop. Seeding at activation is not an optimization: Escape (and every other retirement) clears `active_draft` *before* any frame renders the composer unfocused, and re-opening focuses the **same** draft, so on a type → Escape → reopen round trip neither render-time condition can ever fire and the reopened composer would report its pre-typing text forever. Every reopen path — the band's Reply, a click on an inactive draft, the editor's own `Focus` event, the quote paths — funnels through `activate_draft`, which is why the seed lives there rather than at retirement (retirement would also miss the quote paths, which set the buffer and *then* activate). Regression: `space_composer_reopened_draft_reads_the_text_it_holds`.
- **The space's failure and cascade notices are `Alert`s** (`space/error`, `space/cascade`) whose **message is the value**, not the label — `node_updated` re-announces only when a node's *value* changes, so that is the shape that starts speaking the day `aria_live` lands, and it is perceivable today regardless.
- **Static values ride their own `Label` node**: `settings/account/balance`, `settings/account/pool/{i}` (source · amount · humanized expiry), `about/version`, `updates/version`; the plan rows keep their name/price label and carry the credits-and-expiry subline as the value.
- **Deliberately excluded by the same rule:** the Local backend pane's model rows, whose status line is a download counter ticking at ~2.5 Hz. They need the announcement channel, not a value. The Wallet pane's credential rows are simply not yet swept.

**The regression gate, and exactly how far it reaches.** `tests/probe.rs`'s `fresh_entries` + `assert_probe` / `assert_probe_value` assert the **role, label and value** recorded at each probe call site, not merely that a probe exists — that is what makes landmark roles, label quality and now content exposure regression-tested. It is the whole seam: `Window`'s emitted AccessKit `TreeUpdate` is crate-private at this pin, so **nothing** in the tests or the driver can observe tree *shape*, node parentage, reading order, focus reporting, or the aria attributes that don't pass through `.probe()`/`.probe_value()` (`aria_position_in_set`, `aria_size_of_set`, `aria_selected`, `aria_level`) — those are compile-checked and eyeballed, nothing more — where such an attribute is load-bearing enough to regress silently, expose the computation instead and assert *that* (`RecordView::row_set_metadata_for_test` walks the real display model through the real rule; `SpaceView::composer_aria_value_for_test` is how the composer freeze is gated, since the freeze is a property of *when* the value moves rather than of one frame's value). Window titles are likewise unobservable through gpui (`TestWindow` doesn't implement `get_title`, so `Window::window_title()` reads back empty); the space window's live title is asserted through the view's own `window_title_for_test`. *Removal trigger:* upstream added `Window::debug_a11y_tree_json` (zed#60397, six days past our pin) — **but it returns `None` under `TestAppContext` and always will** (a11y activates via a platform `a11y_init` callback that `TestWindow` no-ops), so it is a live-app debugging tool, not the headless seam. Closing this gap needs upstream to expose the retained `TreeUpdate` to test windows.

**Coverage today.** Every interactive affordance across the window set carries a probe, and (wave C) the content-bearing nodes carry their content: the Record listing rows (attestation/request/spend, indexed) + section tabs + refresh + load-more + the detail cross-links/back/copy; the space view's per-post edit/regenerate/reasoning verbs, branch dots, drafts, composer Post / Post-quietly / home, band Reply-or-Ask menus, cascade-notice chips, footnote-rail rows + their removal chips (post and draft), the source-highlight picker, and minimap cells; the Settings nav + General (base-url edit/save/cancel/change/revert + advanced Record link + appearance chips) + Backends (tab strip + per-backend toggle/remove/autostart + local model verbs + catalog/URL + add-form + the embedded Account create/reset/refresh/plans) + Wallet (refresh/recover); onboarding CTAs/inputs/checkbox/credential-copy/links/plans/back-arrow; About, Updates, and Library affordances. Valued nodes: `space/post/{i}`, `space/composer`, `space/error`, `space/cascade`, `settings/account/balance`, `settings/account/pool/{i}`, `{prefix}/plan/{i}`, `about/version`, `updates/version`, plus the pre-existing full-hash values behind the shortened Record / measurement labels.

**What is still missing** (the audit's waves B, D and E; this section covers waves A and C):

- **Prose has no *text* semantics.** Wave C put content in the tree as node values, which makes it readable in one utterance — but everything still renders through `MarkdownEditor`, which carries no annotations, so there is no caret tracking, no typed-character echo, no line-level review, no `AXStringForRange`, and no selection round-trip. Those are the editor's own text semantics (`a11y_synthetic_children` + `Role::TextRun` + `set_text_selection`) and they are wave D, in `gpui-markdown-editor` — which must make its constant `.id("markdown-editor")` per-instance first, or the duplicate-node-id assert fires the moment that element gains a role.
- **Nothing is focusable or keyboard-reachable.** Zero uses of `tab_index` / `tab_stop` / `focusable()` in the crate, so `TreeUpdate.focus` is `ROOT_NODE_ID` on every frame of every window and AT's cursor is permanently decoupled from app focus. The high-leverage fix is making `Probe::probe` also apply `.focusable()` / `.tab_index(…)` — one edit, ~147 affordances — but it needs a focus-ring design first (wave B). This also gates the hover-revealed Edit/Regenerate and Library rename/archive verbs, which need a reveal-on-focus-within path.
- **Nothing can ever be announced.** gpui has no `aria_live` builder and never calls `accesskit::Node::set_live`, and the macOS adapter announces *only* for a node with a live setting **and a value** — so every `Role::Alert` we have is perceivable but silent. Wave C closed our half of that (`space/error` / `space/cascade` carry their message as the value, which is what the adapter would announce); the remaining ~10 lines are genuinely upstream, sketched in the audit's §7. When it lands, `.aria_live(Live::Polite)` on those two nodes is the whole client change, and streaming progress finally has a home.

**AT-initiated activation works.** (Corrected — this section previously said it wasn't wired.) `Window::handle_a11y_action` has a built-in `Action::Click` fallback that synthesizes a mouse down/up at the node's centre from `a11y.node_bounds`, so VoiceOver activation of our probed divs works today without `on_a11y_action`; that hook is needed only for non-click actions.

Zed itself currently ships with AccessKit force-disabled after early teething (zed #57954) — that's about *Zed's* rollout, not the gpui API; our annotated elements are a much smaller, fixture-tested surface. If instability appears in the real app, `Application::new_inaccessible()` is the upstream kill-switch to reach for.

## gpui / gpui-component pinning

`gpui-component` (longbridge, rev `3229ac92c47a5942de41a91181bce88e1a0af32e`) pulls `gpui` and `gpui_platform` from `zed-industries/zed` without a rev. We mirror that exact spec in `Cargo.toml` so cargo unifies on a single `gpui` copy. `Cargo.lock` is the canonical pin for the resolved zed commit. gpui-component and gpui move in lockstep: a given gpui-component rev expects a matching gpui (e.g. the `flex_shrink_1`/`flex_grow_1` helpers it calls landed in gpui commit `8982fb17`), so bump both together. This rev is 13 commits past the former `dadfca97` pin (same zed dep, so no gpui bump was needed) and carries `Root::bordered(false)` (PR #2466) — the opt-out the Linux CSD layer uses to disable Root's built-in `window_border` (see [Linux window chrome → Single CSD authority](#linux-window-chrome--csd-primary-menu-keyboard)).

**The zed pin is at `f9c9947` (2026-07-07)** — `Cargo.lock` is authoritative; this line read `34cd17f` well past the move, so check the lock rather than the prose. The pin was previously held back at `969a67fc` because the commit after it (zed #57835) added a global action-timing profiler whose process-wide `ACTION_STATISTICS` spinlock panicked under libtest's parallel `gpui-markdown-editor` behavior tests. Upstream fixed the race (zed #58813) and then made the profiler opt-in behind the `gpui/profiler` feature (zed #58942, off by default — we don't enable it), so the hold is obsolete. The historical rule stands as practice: when advancing the pin, re-run the full editor behavior suite under default libtest parallelism before committing the lock. The pin also includes gpui's AccessKit integration (zed #56065, merged 2026-05-27) — see [Accessibility & QA probes](#accessibility--qa-probes).

## Non-Rust dependencies

Native deps differ per platform, and gpui pulls them all — no GTK/Qt/node/python either way. **macOS:** system frameworks that ship with the OS (Cocoa, AppKit, CoreFoundation, CoreGraphics, CoreText, CoreVideo, Metal, Foundation); build deps require Xcode Command Line Tools (`xcode-select --install`). **Linux (Wayland-only):** fontconfig, freetype, libxkbcommon, libwayland, libGL/EGL, and the Vulkan loader for wgpu — see [Linux build/dev target](#linux-builddev-target) for how to supply them (distro dev packages or `nix develop .#gui`).

## Linux build/dev target

macOS is the primary target; Linux is a supported build/run/release target (compiles, behavior tests pass, runs on a live Wayland session with full window chrome + keyboard idiom — see [Linux window chrome](#linux-window-chrome--csd-primary-menu-keyboard) — and has a Nix-built release artifact, see below). End-user packaging *format* (AppImage/tarball/deb) is still a ship-time decision on top of the release artifact.

**Linux targets Wayland only — a settled decision; do not reintroduce X11.** Rationale: a cleaner fully-open-source story (no ties to closed drivers) and narrower deployment breadth. Multi-monitor Wayland works fine on 2026 desktops (the old caveat was NVIDIA's proprietary driver, fixed by NVIDIA 555+ in 2024), and the genuinely X11-stuck demographic (old NVIDIA cards, old LTS distros, X11-only tiling-WM power users) is not the target audience — people who want confidential AI without self-hosting are almost all on default GNOME/KDE, which are Wayland-by-default.

- **Cargo features.** `gpui_platform` is built with `wayland` and `font-kit` (plus `runtime_shaders` for macOS). `wayland` is `cfg(target_os = ...)`-gated inside gpui, so enabling it universally is a no-op on macOS — no `[target.'cfg(...)']` split needed. Mirrored in `[dev-dependencies]` so tests/examples build on Linux too. The `x11` feature (and its libxcb/x11rb dependency cluster) is deliberately absent. One residual wart: upstream `gpui_linux` hardcodes `xkbcommon = { features = ["wayland", "x11"] }` (the crate feature isn't gated by gpui's backend features), so `libxkbcommon-x11` must be present at **link time** even for Wayland-only builds — but no symbol from it is referenced, `--as-needed` drops it, and the final binary's `DT_NEEDED` is X11-free (verified: only `libxkbcommon.so.0` + libc/libm/libgcc; fontconfig/freetype/wayland/vulkan are dlopened). An upstream PR to gate the dep feature is planned; until then keep `libxkbcommon-x11-dev` installed for builds.
- **The visual tier is macOS-only.** `tests/visual.rs` already compiles to a skip-stub `fn main()` on non-macOS (`VisualTestAppContext` instantiates `gpui_macos::MacPlatform` and `current_headless_renderer()` returns `None` off macOS). Behavior tests (`tests/behavior.rs`) are the cross-platform regression gate. A Linux headless renderer (`PlatformHeadlessRenderer` via wgpu offscreen render-to-texture + readback) is the natural follow-up that would let snapshots run in Docker.
- **Non-Linux hosts.** There is no dedicated dev container — a Linux build from a macOS host is a plain `just run gui` (or any `cargo build -p eidola-gui`) inside a Debian/Ubuntu container with the C build deps installed (the same set `nix develop .#gui` supplies) and `mold` as the linker (GNU `ld` OOM-kills linking gpui's debug binary under Docker Desktop's default memory ceiling). Point `CARGO_TARGET_DIR` at a Linux-only path (e.g. `./target-linux/`) if you bind-mount the workspace, so the container's artifacts don't clobber the host's `./target/`.
- **Native Linux dev.** On a Linux host, plain `cargo build -p eidola-gui` works once the C-level build deps (pkg-config, wayland, libxkbcommon, fontconfig, freetype, vulkan-loader headers) are present — either from the distro's dev packages or via `nix develop .#gui`, which supplies exactly that set at link time (the binary runs against the host's own runtime libraries; wayland/vulkan/fontconfig are dlopened by name).
- **Release pipeline is Nix, not StageX (settled decision).** The GUI's Linux release artifact is `nix build .#eidola-gui-linux` (flake.nix): a `x86_64-unknown-linux-gnu` release build against nixpkgs-provided wayland/libxkbcommon/fontconfig/freetype/vulkan-loader (RUNPATH-pinned into the closure), **wrapped with bundled Mesa Vulkan drivers** (`VK_ADD_DRIVER_FILES` set as an overridable default — distro ICD manifests reference drivers by bare soname, which a Nix binary's linker can never resolve, and dlopening host Mesa into a Nix glibc invites symbol-version mismatches; bundling makes the artifact's host surface kernel + compositor socket + `/dev/dri`). The wrapped output also ships `share/applications/tech.m6i.Eidola.desktop` (from `releases/linux/`; basename = the binary's Wayland `app_id`). Recorded in `artifact-manifest.json` as `eidola-gui-linux-amd64` (Nix `narHash`, `linux/amd64`), built in CI by the `linux-gui` job in `artifacts.yml` (a sibling of the macOS `apple` job, consuming the same stamped trust root from the `oci` job). StageX was ruled out for this artifact class, not abandoned casually: a desktop app must be a **glibc dynamic** binary (the Vulkan loader dlopens Mesa ICDs, which every distro builds against glibc; a musl binary can't dlopen glibc libraries), and stagex is musl-by-design and packages no graphics userland (no mesa, no libdrm). The server/cli keep their StageX pipeline unchanged. A containerized `just run gui` on a non-Linux host (see above) is the fast iteration loop only — it is not the release path.
- **Validated on real hardware** (2026-07-02, Ubuntu 26.04 + GNOME Wayland, amdgpu/Radeon): the binary builds natively, all behavior tests pass, and the app runs against a live Wayland session — Vulkan hardware ICD picked up (DRM fds open on amdgpu), no panics. One upstream bug was worked around in our code: gpui delivers appearance changes from inside its xdg-desktop-portal callback while holding the Wayland client `RefCell` mutably, so a theme flip that repaints synchronously panics ("RefCell already mutably borrowed" — deterministic at startup on GNOME, which pushes an initial color-scheme event); `theme::observe_window_appearance` therefore spawns the theme application onto the next executor tick instead of applying it inline (see the comment there; an upstream gpui fix — dropping the borrow before window callbacks — is the real cure). Still open: the release binary size/packaging story.
