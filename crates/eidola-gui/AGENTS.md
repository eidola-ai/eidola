# crates/eidola-gui — gpui-based Eidola

Guidance for AI coding agents working on the gpui macOS app. Cross-cutting workspace context (server, app-core, build-system, conventions) lives in the top-level `AGENTS.md`.

## What this app is

A native Rust client for Eidola, built on [gpui](https://github.com/zed-industries/zed/tree/main/crates/gpui) (the immediate-mode UI framework Zed is built on) and [gpui-component](https://github.com/longbridge/gpui-component) (a shadcn-style widget library on top of gpui). The sole macOS GUI for the project; the CLI in `crates/eidola-cli/` shares the same `crates/eidola-app-core/` backend. macOS-only today; Linux is the next target.

**State & async doctrine — read first.** All state ownership, async tasks, and cross-window synchronization follow `docs/architecture/state.md` (domain stores, `Loadable`, task-as-field with replace-cancels, the invalidation bus, `WindowInput`). Where existing code in this crate contradicts the doctrine, the doctrine wins — the migration is in progress; do not extend the old patterns (`Core::spawn`/busy flag, detached tasks, view-owned domain data).

## Stores (`src/stores/`, `src/loadable.rs`, `src/bridge.rs`)

`AppCore` lives in `crates/eidola-app-core/`; gpui can't host it directly because gpui's executor is smol-based and `AppCore` has its own tokio multi-thread runtime. State ownership and the async bridge follow `docs/architecture/state.md` (the binding doctrine) — read it before touching state-bearing code. The old `Core` god-object has been dissolved into per-domain stores.

- **Domain stores** (`src/stores/`): one gpui entity per domain — `ConfigStore`, `ModelsStore`, `AccountStore`, `WalletStore`, `SpacesStore`, `UpdateStore` — created once at startup, bundled in `Stores` (held by `AppGlobal`), and handed to every view's constructor. Each store owns its `Loadable` snapshots, its in-flight `Task` *fields* (one slot per operation, replace-cancels), its subscription to the invalidation bus, and *all* mutations of its domain. **No shared busy flag.** Views call store methods and observe the specific store entities they render; they never call `AppCore` directly.
- **`Loadable<T>`** (`src/loadable.rs`): the universal async cell — `NotLoaded` / `Loading` / `Loaded { value, stale }` / `Failed { error, prior }`. A re-fetch over existing data stays `Loaded { stale: true }` (never a blank `Loading` flash); `Loading` is for initial loads only and always implies a live task in the sibling slot.
- **Method shapes:** `refresh_*` is fire-and-notify (the store owns the task; callers observe). `request_*` is awaitable (returns a `oneshot::Receiver`; the *caller* awaits it inside its own slot, so the work dies with the caller — e.g. the onboarding checkout poll). Ownership = cancellation authority.
- **The bus bridge** (`stores::install_bus_bridge`, installed once at startup): a task on `AppCore::runtime()` forwards every `AppCore::subscribe_changes()` event through an mpsc channel into one gpui main-thread loop, which dispatches each `Change` to the owning store(s) (`Change::Config` → config + models, `Change::Wallet` → wallet, …). On `Lagged` it refreshes everything. This is the **only** place tokio receivers touch gpui, and its app-lifetime task is the **one sanctioned `.detach()`** (commented as such) — every other task is an entity-owned field.
- **`src/bridge.rs`**: the runtime-agnostic `oneshot`/`mpsc` glue. `bridge(core, f)` runs `f` on the tokio runtime and awaits the result on gpui (used inside store `cx.spawn` tasks). The free functions `chat_stream` / `get_space_tree` (the threaded-post render DTO) now back the **`Space` entity**'s owned runner/load tasks (step 3); `list_attestations` / … still back the Record reader's view-owned tasks (a window-scoped reader entity is a later step). All take the `Arc<AppCore>` out of the `Stores` bundle and hand back a receiver the owning entity awaits inside its own `Task` slot.
- **Stub mode (tests):** `Stores::stub_with(StoresStub { … }, cx)` builds backend-less stores from a declarative fixture (replacing `Core::stub()` field-poking). Each store also has a `stub(...)` constructor. With no backend, `refresh_*`/`request_*` are no-ops, so views that drive async work transition their *local* state and stop at the backend guard — exactly the behavior tests assert. `Stores::for_test(Arc<AppCore>, cx)` injects a real tempdir-backed `AppCore` for store-machinery tests (`tests/stores.rs`).

## View structure

Every view takes the `Stores` bundle (or a single store entity from it) at construction and observes the specific stores it renders; the "Stores" column lists those data sources.

All view roots are wrapped in `gpui_component::Root` before being handed to `cx.open_window`. **Root is required** — `gpui_component::Input` calls `Root::read(window, cx)` to track the focused input, and panics if the window's root view type isn't `Root`.

**No shared busy flag.** Each store operation has its own task slot, so concurrent refreshes never starve each other — the structural fix for the wave-2 launch-order bug where a shared `busy` gate dropped the first window's model-list fetch behind the startup wallet recovery (see the replay test in `tests/stores.rs`). Multi-part work either composes inside one store task (e.g. `WalletStore::refresh` fetches lifecycle + active credentials in one `bridge` call) or composes by *event* — write through `AppCore`, let the bus drive each store's own refresh; one store never orchestrates another's tasks. View-owned flows that must outlive a single observe (onboarding account-create / checkout / balance poll) use the awaitable `AccountStore::request_*` methods and own the await in the view's own task slot.

## The Space entity

`space.rs`'s `Space` is the per-conversation **domain entity** (`docs/architecture/state.md` → "Space entities — shared, registried"). It owns everything about one conversation, so a window opening/closing never re-derives or destroys it:

- **State it owns:** `id: Option<String>` (`None` for a blank ⌘N space until its first exchange persists and assigns one), `transcript: Loadable<Vec<ChatMessageView>>`, the live `streaming: Option<StreamingResponse>` buffers (reasoning + content + disclosure-`expanded`), `selected_model` (per-space, not per-window — see the request panel in the Space view section), and `last_submitted_model` (set before the backend guard so behavior tests see what a real send would use).
- **Tasks-as-fields (no `.detach()`):** `submit_runner: Option<Task<()>>` is the single runner slot — a submit while one is in flight is a no-op (the current UX), and the runner owns both the streaming pump *and* the post-stream transcript reload. `load_task: Option<Task<()>>` is the supersede slot for the reopened-space initial transcript load. The retired chat view's detached streaming/load tasks moved here; this is where that detachment debt was paid.
- **The load-vs-submit race is serialized inside the entity**, which retired the old `transcript_generation` counter: one entity owns both the initial load and every submit, so they serialize on `&mut self` between awaits. A submit drops the in-flight `load_task` and `apply_loaded_transcript` is a no-op while `streaming.is_some()` — a slow initial load that finishes after a local submit cannot clobber the just-appended user turn (the submit's own post-stream reload is authoritative). Replay test: `space_stale_initial_load_does_not_replace_submitted_prompt`.
- **Streaming reasoning stays ephemeral.** The DB persists only the assistant's final content; reasoning is captured into the streaming buffer and re-attached to the new last assistant entry at finalize. `merge_messages_from_db` preserves reasoning *by position* across a transcript reload (we only ever append, so positions are stable).
- **`EventEmitter<SpaceEvent>`** — `MessagesChanged` / `StreamDelta` / `StreamEnded` / `Failed(AppError)`. Plain `cx.observe` covers re-render; the events let a view react *semantically* (tail-scroll on `StreamDelta`, degraded-onboarding routing on `Failed`).

**The registry lives in `SpacesStore`** (`HashMap<SpaceId, WeakEntity<Space>>`):

- `open(id)` is **get-or-create with join-existing**: a live registered entity is returned as-is, so two windows opening the same space share **one** `Space` (and its single transcript load). This is the structural fix for wave-2 bug 4 — a submit/stream in window A appears in window B live, because both render the same entity. Replay/behavior tests: `space_joins_shared_entity_for_same_id` (behavior) and `spaces_registry_joins_existing_and_blanks_are_distinct` (stores).
- `blank()` mints an id-less space for ⌘N (instant, no load). The registry **adopts** it once its first exchange assigns an id — whether that exchange **succeeds** (`StreamEnded`) **or fails after the space was persisted** (`Failed`). `SpacesStore` subscribes to both events, reads the now-present `id()`, and keys the entity under it (the shared `adopt_blank` path; a no-op when the id is still `None`, e.g. a pre-persist `Failed` like `NoAccount`) — so a later `open(that_id)` joins the same entity. The id reaches a *failed* blank because app-core wraps any post-persist error as `AppError::ChatFailed { space_id }`; `Space`'s failure arm reads `chat_space_id()` off the wrapper into `self.id` before emitting `Failed` (with the unwrapped source, via `root()`, so the view's error routing sees the real variant). This closes the former known gap where a blank window's first exchange failing never taught it the persisted id (the id only arrived via `ChatResult` on success). Regression test: `blank_space_adopts_id_on_wrapped_failure`.
- `Change::Space(id)` from the invalidation bus is routed (in `stores::dispatch_change`) to `SpacesStore::notify_space_changed(id)`, which tells the live registered `Space` to refresh its transcript (how an in-process CLI write to the same space appears). The space ignores the refresh while its own submit is streaming.

## Onboarding window

`onboarding/mod.rs`'s `OnboardingView` is the production onboarding surface: a standalone **singleton window** of full-window **slides** stacked vertically, sized to **match a new space window** (the same square "writing surface" — `lib.rs::writing_surface_side`, shared with `open_chat_window` — so onboarding feels like the page it leads into). It **supersedes** the retired in-chat empty states (deleted with `chat.rs`). Opened two ways: automatically at launch when `ConfigState` has no account (`run()` checks `!has_account || !has_account_secret` after `open_main_window`), and via the Eidola menu → **Get Started** (`GetStarted` action, singleton like Settings). Borrows the space view's look wholesale — the Newsreader prose column (`space_view::prose_style`, a disabled `MarkdownEditor` per slide, **left-aligned** in a centered reading column, with the **CTAs center-aligned** on the window below it), the transparent-titlebar drag band (`titlebar::drag_band`), a right-edge **scroll indicator shown only while scrolling** (`gpui_component::scroll::Scrollbar` in `ScrollbarShow::Scrolling` mode — drop-in, bound to the page scroll handle), and a **computed-momentum snap** (take over at finger-lift, drive our own decaying glide, suppress the OS momentum — reusing `space_view::nav`'s `ease_out_cubic` / `snap_duration` / `snap_target_index`).

- **Structure — stateful view + stateless slide components.** `onboarding/mod.rs` owns all state (the reveal machine, scroll/snap physics, async account ops) and a single `render_slide` **router** match that instantiates the matching slide component with props + boxed callbacks. Each slide in `onboarding/slides.rs` is a self-contained `#[derive(IntoElement)]` + `RenderOnce` component — gpui's analogue of a React functional component — carrying its own `MARKDOWN` const, extras (links, inputs, credentials, plans), and CTAs, so one slide reads top-to-bottom in one place. The slide's disabled prose editor is **element-owned state** (`window.use_keyed_state`, keyed per slide in `slide_frame`) — the `useState` analogue — initialized once and evicted by the framework the frame after the slide stops rendering (branch truncation), which is safe *only because* every revealed slide paints every frame (a plain v_flex stack, no virtualization); if the slides ever render conditionally or through `list()`, lift that state back onto the view (the retired chat view's `text_states` lesson: element-owned parsed state dies with an unmounted `list()` item). State the view must read or that must outlive a frame (the id/secret `InputState`s read by `begin_verify`, the `agreed` consent bit, async-op results and task slots) stays lifted on the view. Flow sequencing (which slide a CTA reveals next) deliberately stays in the router so the branch structure is visible in one match; the components are pure presentation over lifted state.
- **Reveal state machine.** `revealed: Vec<Slide>` starts as `[Slide::Pause]`; only revealed slides render. Each slide's ghost-button CTA calls `reveal(after, next)` which appends `next` after `after` — animate-scrolling to it — and, when the choice **changes** (a different `next` than what currently follows `after`), **truncates the stale downstream slides first**. So re-choosing a branch upstream (new-account vs. existing-account at "Get started") replaces the whole downstream tail. Idempotent when `next` already follows (just re-scrolls). `reveal` records a `pending_scroll` index that `render` consumes (where `window` is available) to start the glide, so the async account-op callbacks can reveal without holding a `Window`.
- **Slides:** `Pause → Tool → Control → Responsibility → GetStarted`, then the branch: **new** (`CreateAccount → NewAccount → Purchase`) or **existing** (`ExistingAccount → Purchase`). Conditional content within a slide is state-driven: `CreateAccount` carries a **required agreement checkbox** (`agreed: bool`) that gates its "Create a new account." button (disabled until checked) and shows a create error inline; `NewAccount` shows the freshly-minted id/secret (mono, with Copy affordances); `ExistingAccount` shows the balance-check result and swaps its CTA set (verify → then purchase/done); `Purchase` renders `plans::plan_rows`.
- **Snap = computed momentum + OS-momentum suppression** (the space view's horizontal-branch approach, on the vertical axis). While the finger is down (`Moved`, `!owning`) the page scrolls natively and we record the last step as the release velocity (`last_dy`). At finger-lift (`Ended`) we pick the target slide (`snap_target_index(from_y, stride=window_h, last_dy, count)` — nearest, or ±1 on a flick), set `owning`, pin the resting offset, and drive our **own** ease-out glide (`glide_to_index` → the `drive_snap` frame loop). The reason we take over rather than ride native momentum: in this gpui pin macOS delivers post-lift momentum as `TouchPhase::Moved` events with **no end signal** (`gpui_macos` reads only `NSEvent.phase()`, so momentum's `phase = None` maps to `Moved`), and gpui applies each to the handle — so we `stop_propagation` and **`reassert_scroll`** (re-set the offset to our live glide point, or the pin once the glide completes) on every trailing momentum `Moved`, exactly like `nav.rs::reassert_horizontal`. The result is one continuous curve that lands exactly on a slide (no post-arrival drift, no two-phase settle). A fresh `Started` releases ownership (`owning = false`, clears the pin + glide) so the user scrolls freely again. Reveal-scrolls use the same `glide_to_index`, so a revealed slide is likewise pinned until the next gesture.
- **Account ops** go through `AccountStore`'s awaitable `request_*` methods, each owned in a view task slot (dies with the window): `begin_create` → `request_account_create` (on success stores id/secret from the now-`secret`-carrying `AccountCreateResult`, refreshes config + balances, reveals `NewAccount`); `begin_verify` → `request_verify_account` (a new store method: sets the entered credentials, fetches the balance, and **rolls the write back on failure** so a bad attempt strands nothing — success links the account); `begin_checkout` → `request_checkout` → `cx.open_url`. The server collapses "no such account" and "wrong secret" into one `401` (anti-enumeration), so `verify_error_copy` shows those as one honest message; other failures surface their real reason.
- Tests: `onboarding_*` in `tests/behavior.rs` (first-slide start, reveal advance + idempotence, branch re-choice truncation, verify field-guard, stub backend-gating) and a probe test in `tests/probe.rs` (`onboarding/cta/*`, `onboarding/input/*`). Driver scene: `onboarding`. **Deferred:** distinguishing not-found vs. wrong-secret (server-limited), a "manage subscription" affordance (no portal API), and a post-checkout balance poll (checkout opens the browser; balance reflects on the next refresh).

## Theme — Circadian (`src/theme.rs`)

Two `ThemeConfig`s, "Circadian Day" (Light) and "Circadian Night" (Dark), installed onto the global `gpui_component::Theme` after `gpui_component::init`. Switching is driven by OS appearance:

- `Theme::sync_system_appearance` reads the appearance via `cx.window_appearance()` (or `window.appearance()` if a window is passed) and applies the matching config.
- Each opened window subscribes to appearance changes via `theme::observe_window_appearance(window)` so toggling macOS Light/Dark updates live.

The palettes are anchored on two fixed backgrounds (the product's "good paper at noon, reading lamp at midnight" pair): **Day `#fefaf5`** — every other day surface is the same warm family translated up in lightness — and **Night `#15191e`** — a cool blue-grey dark whose elevated surfaces (cards, chips, borders, rows) all follow the anchor's blue-grey ramp (R < G < B throughout), while text stays warm-grey (`#d4d0c8`) and the brand stays warm orange (`#c39669`). The warm-on-cool night tension is deliberate; don't "fix" it by cooling the foregrounds. An earlier palette was seeded from the marketing site — the site is no longer the reference, these anchors are.

**Body font is Newsreader 16pt** (SIL OFL 1.1) — five static TTF instances (Regular, Italic, SemiBold, Bold, BoldItalic) from `productiontype/Newsreader`, bundled in `crates/eidola-gui/assets/fonts/Newsreader16pt-*.ttf`, embedded via `include_bytes!`, and registered with `cx.text_system().add_fonts`. License at `assets/fonts/OFL.txt`.

We ship statics rather than the variable upright + italic because **gpui's macOS text system does not apply variable-font weight axes**: `gpui_macos::text_system::add_fonts` registers each TTF as one face with the properties of its default instance, and `font_kit::matching::find_best_match` picks the closest face per weight request. With only the variable TTFs registered, every weight request — `**strong**` (BOLD), headings (SEMIBOLD/BOLD), etc. — resolved to the Regular default and rendered un-bold. Five static faces make `find_best_match` pick correctly. Family name in the theme is `"Newsreader 16pt"` (the typographic family — nid 16 — that all five faces report; SemiBold sets nid 16 explicitly to override its nid 1 = `Newsreader 16pt SemiBold`, the canonical workaround for the Windows OS/2 4-style-per-family limit).

## Prose typography — book metaphor

Conversation prose is the long-form reading surface, so it gets typography of its own rather than inheriting the 16px UI baseline (settings/wallet/account stay on the theme default). The knobs live in `space_view/mod.rs` — `PROSE_FONT_SIZE` (17px), `PROSE_LINE_HEIGHT` (1.65), `PROSE_PARAGRAPH_GAP` (1.5) — and feed `space_view::prose_style`, the `MarkdownStyle` shared by every post body *and* the composer, so a post renders pixel-identical to what the user typed:

- **Body 17px / 1.65× leading.** Newsreader at 17 sits in proportion with a real book page; 1.65 is the readability sweet spot for serifs at this size.
- **Reading measure capped at `BODY_MAX_WIDTH` (600px)**, centered between the two symmetric gutters (`layout::body_width`) — ~65–72 chars/line, the canonical long-form measure.
- **Gentle heading ramp anchored to the body size** (h1 1.5× / h2 1.25× / h3 1.125× / h4–h6 1×): the gpui default (h1 = 2×) reads like a marketing page; a book has a flatter type ramp where weight carries most of the hierarchy.
- **Paragraph gap 1.5 rem** — clear paragraph breaks without the run-on tightness of a chat tool.
- **Inline code in Courier New.** Mono at the same nominal size as a low-x-height serif reads visually larger; Courier New's x-height (0.423 em) matches Newsreader's (0.426 em) almost exactly, where Menlo (0.547 em) read ~28% larger. Fenced code blocks keep Menlo.

**Identity travels with each post**: the byline gutter (author + time) is part of the post row and scrolls with the body it labels — there is no separate persistent participant indicator, and the title band carries no model chrome (the model lives in the composer's action gutter).

## WindowInput — per-window modifier state

`src/window_input.rs` — `WindowInput` is a **per-window gpui entity** that holds the live keyboard modifier state for one window. It exists because `ModifiersChangedEvent` in gpui (at our pinned commit 969a67fc) dispatches along the **focused element's ancestor path only** — a listener on a sibling branch of the focused node never fires. Without `WindowInput`, a Settings pane's `on_modifiers_changed` listener was dead while a text input in a different pane had focus (wave-2 bug 2).

**Pattern — one listener per window, registered on the root view only:**

- Each `open_*_window` builder creates one `WindowInput::new(cx)` and passes it to the view constructor.
- The root view (`SpaceView::render` root div, `SettingsView::render` root h_flex) registers the window's **single** `on_modifiers_changed` listener and calls `wi.update(cx, |wi, cx| wi.update_modifiers(event, cx))`.
- Descendant views (`GeneralView`) observe the entity (`cx.observe(&window_input, …)`) and read `window_input.read(cx).alt_held()`. They never register their own `on_modifiers_changed`.

**Rule — enforced structurally, not by convention alone:** No view below the root may call `.on_modifiers_changed(…)` anywhere in its `Render` impl. The `WindowInput` entity is the only mechanism for sharing modifier state within a window. Adding a new ⌥-affordance in any descendant view means: observe `window_input`, never add a second listener.

**Staleness:** gpui at 969a67fc has no window-activation or "window became/resigned key" observer hook. If the user switches away while holding ⌥, `alt` may linger `true`. This is self-healing: the next `ModifiersChangedEvent` in this window writes the current state. The stale `true` is transient and harmless (the ⌥ reveal is a cosmetic affordance with no irreversible action).

**Test helper:** `WindowInput::set_alt_for_test` mutates `modifiers.alt` directly (no `ModifiersChangedEvent` construction) for snapshot tests that need to render the revealed state without synthesizing platform events. Behavior tests use `VisualTestContext::simulate_modifiers_change` to drive the real dispatch path through the root listener.

## Streaming chat

The **`Space` entity** drives chat via `bridge::chat_stream` (which wraps `AppCore::chat_stream` from `crates/eidola-app-core/`) inside its single `submit_runner` slot — not a detached view task. The core's streaming method posts `stream: true` to the OpenAI-compatible upstream and forwards each SSE chunk's `delta.content` as `ChatStreamEvent::ContentDelta` and `delta.reasoning_content` / `delta.reasoning` (vLLM-style) as `ChatStreamEvent::ReasoningDelta`. The terminal `ChatResult` is the function's return value, not an event — the channel just closes.

While streaming, `Space::streaming: Option<StreamingResponse>` holds the live `reasoning` + `content` buffers and a disclosure-`expanded` flag, and each delta emits `SpaceEvent::StreamDelta`. `SpaceView` renders it (`post.rs::render_streaming_body`) as a streaming leaf attached at the selected branch: a clickable "Thinking…" disclosure whose toggle calls back into `Space::toggle_streaming_reasoning`, the reasoning body when expanded, and the partial markdown content as it grows. The disclosure **survives finalize**: the re-attached reasoning renders the same toggle on the finished post (`render_post_body` → `Space::toggle_message_reasoning`). On done, the `Space` drops `streaming`, reloads the transcript from the DB, re-attaches the captured reasoning to the new last assistant entry, and emits `StreamEnded` — only the final content is persisted; reasoning is **ephemeral by design** (not written to the local DB), and `merge_messages_from_db` preserves it by position across reloads. Because the streaming state lives on the shared entity, a second window on the same space watches the same buffers fill (wave-2 bug 4).

The CLI uses streaming too: `crates/eidola-cli/src/main.rs` pumps `ContentDelta` to stdout and `ReasoningDelta` to stderr (dimmed and prefixed with `thinking: ` when stderr is a TTY) so a piped stdout still captures only the final answer.

Refund handling for streaming differs from blocking only in *where* the refund token comes from: SSE responses have no inline JSON body to carry it, so the streaming path always goes through the `/v1/credentials/refund` recovery endpoint after the stream ends. Same recovery endpoint as the existing network-error fallback in the blocking `chat()`.

## Space view — tree-navigation conversation surface (`src/space_view/`, wave 6)

`SpaceView` is the **window root** for a conversation. It replaced `ChatView`, whose every remaining feature has since migrated — onboarding to its own window, the ⌥ model picker as the request panel, inline edit/regenerate as the post action-gutter verbs, and the finalized-reasoning disclosure onto the post body — and `chat.rs` is deleted. It renders a space as the `examples/eidola_space.rs` mockup does: a tree of **recursively-nested scrollers** — vertical scroll walks the selected root→leaf path; horizontal scroll flick-**snaps** between sibling branches, each page carrying its *whole subtree* so a branch slides sideways as a unit — with a right-edge topology **minimap** and a floating/docking **composer**. It is a window-local lens over the shared `Entity<Space>` (registry join-existing), constructed as `SpaceView::new(stores, space_id, window_input, window, cx)`.

Decomposed into focused submodules (impl blocks split across files on one `SpaceView`):

- `model.rs` — the UI tree. `Space` loads a flat `Vec<ChatMessageView>` (DFS pre-order, each row carrying `parent_action_id`); a per-frame-cheap `PostData` snapshot (rebuilt only on transcript change, `SharedString` refcounted clones) feeds `build_tree`, which relinks the flat list into `TreeNode`s. **Unparented rows chain onto the previous row** (an optimistic user turn, a synthetic test row) so the conversation forms one spine even when only some rows carry links — a real `get_space_tree` result has exactly one unparented row (the root). Pure + unit-tested (`node_ref` / `parent_of` / `path_ids` / `attach_overlay`). `NodeSrc` is `Msg(idx)` | `Streaming` | `Draft`; the streaming reply and the composer draft are synthetic leaves attached at the selected leaf / reply target by `attach_overlay`.
- `layout.rs` — **the performance core.** The mockup re-measured every post every frame (a `canvas` per post) and rendered the whole tree → O(all posts) of text shaping. Here a `Layout` height cache (interior-mutable, `Clone`) holds each post's measured height keyed by node id for the current width; only posts intersecting the viewport (± `VIRT_MARGIN`) render the real `MarkdownEditor` (carrying a measuring `canvas` that refreshes the cache) — off-screen posts render as **sized placeholders** of the cached/estimated height (`estimate_post_height`). So per-frame shaping is bounded to *visible* posts and the document total/scroll-range/minimap stay correct. **The cache is keyed on the reading-column width (`body_width`), not the raw window width** — a post's measured height depends only on the column, which is capped at `BODY_MAX_WIDTH` above a ~836px window, so resizing a wide window doesn't reflow anything and (correctly) doesn't invalidate the cache. Keying on the raw width instead cleared the cache on *every* resize, dropping every post back to a rough `estimate_post_height` and jittering the page — and the minimap, which sums the same heights — as the near-viewport posts re-measured estimate→real, *even where no text reflows* (the resize-jitter bug; the warm pass only ever measures posts within ~a viewport of the fold, so the far off-screen posts it can't reach stay estimated and flip visibly on each clear). A resize that leaves `body_width` unchanged is now a no-op for the cache; a genuine column change (narrow windows) still clears. Regression: `space_resize_above_column_cap_does_not_churn_height_cache` asserts a wide-window resize bumps `Layout::clears()` zero times, a narrow one non-zero. **The warm pass** closes a related gap: an off-screen post measuring lazily (estimate→real) the moment it scrolls into view *shifts the whole document below it* — which jumps the composer's dock/float threshold (and its drop shadow) and resizes minimap columns as you approach them. So whenever the selected path has an unmeasured post (`path_has_unmeasured` — a cold open, a width change, a freshly added post), `render` arms `warm_remaining` and forces **every** on-path post to render real for a couple of frames (prepaint fires for off-screen elements, so they measure without being shown), establishing the real document height up front. It's self-terminating (stops once the path is fully measured) and only inspects the on-path posts, never off-branch siblings (which never render on the path and would keep it armed forever). This file also holds the selection/height computations (`active_child_index`, `selected_levels`, `selected_subtree_height`, `placeholder_doc_top`) that read the scroll handles.
- `nav.rs` — snap physics (`SnapAnim`, `ease_out_cubic`, `snap_target_index` flick decision, `snap_duration`) + the gesture bookkeeping (`ScrollAxis`/`ScrollOwner` locks, `resolve_scroll_axis`, `start_snap`/`drive_snap` frame loop, `reassert_horizontal`, `remap_for_resize`, `select_path_to`). Same "take over at finger-lift" approach as the mockup (macOS exposes no momentum-end signal). **Horizontal branch scrolling locks its owning strip for the whole gesture** (`h_scroll_owner`, mirroring the vertical `ScrollOwner`): the first strip to handle a horizontal step is elected owner and held until the gesture ends. This matters because sibling branches differ in height — as the owner's pages slide, the cursor can drift over a *nested* strip on the incoming branch, and gpui dispatches the wheel to that innermost strip. Without the lock the nested strip would steal the gesture (halting the slide, or scrolling a sub-branch). Instead a non-owner strip undoes the built-in scroller's step on itself and **forwards the delta to the owner**, then the finger-lift snaps the owner (sized by its own branch count from the per-frame `scroller_counts` map, since the strip under the cursor at lift may not be the owner). Reset on `TouchPhase::Started`.
- `post.rs` — one post (byline gutter beside the reading column) + the separator band. The gutter column itself is the shared `byline_gutter` helper (label color/opacity as params), used by posts, inline drafts, and the floating composer so the gutter geometry can't drift between them — activating a draft must not shift its byline. Posts render through a **`disabled` `MarkdownEditor`** styled with the same `prose_style` as the composer, so a post is **pixel-identical** to what the user typed. `render_post_or_placeholder` is the virtualization decision. **Per-post affordances (the action gutter's tenants):** hovering a post reveals quiet verbs in its right gutter — **Edit** on your own posts, **Regenerate** on the assistant's (`Space::regenerate_post` with the current model); hidden while streaming (the entity refuses mutations mid-stream, so dead verbs would lie), and only on rows with a real `action_id`. Hover state uses the Library's out-of-order-leave guard (`set_post_hover`). **Edit is in place**: `begin_edit` enables the post's *own* body editor (the same entity `sync_bodies` keeps synced — the sync deliberately skips the editing node, so a bus reload mid-edit can't clobber typing; regression: `space_edit_buffer_survives_transcript_sync`), stashes the original, retires any active draft, and routes the editor's ⌘↩ `PressEnter` to `commit_edit` → `Space::edit` (a new human generation; `item_current` resolves to it). Esc → `cancel_edit` restores the stashed original; while editing, the gutter shows the session's Save/Cancel verbs. **Finalized reasoning keeps its disclosure**: a post carrying re-attached reasoning renders the same "Thinking…" toggle as the streaming leaf (`render_post_body` → `Space::toggle_message_reasoning`) — previously the disclosure vanished the moment a stream finalized.
- `composer.rs` — the **draft model** (the mockup's, restored after Phase 1's single-composer simplification). A `Draft` (`SpaceView::drafts`) is a **window-local UI node** with its own editor, attached to the persisted tree as a leaf of the post it replies to (`None` parent = a blank-space root). Because `drafts` is view state (not the `Space`/DB), "drafts live in the UI, not the data" + "empty drafts never persist to the DB" both fall out for free. Two kinds, told apart by whether the parent is a current leaf ([`SpaceView::tail_parents`]):
  - **Tail draft** — the always-present, **docked** composer at the **end of every branch** (it replaces the leaf "+"; that's why a leaf's band shows **no** "+"). `sync_tail_drafts` (run each frame in `render`, idempotent; skipped while streaming and until the transcript loads) ensures one per leaf and prunes empty, inactive, non-leaf drafts. An empty tail draft **persists** (docked) — Escape just deactivates it, it is never deleted.
  - **Fork draft** — a band's "+" (shown only on a post that already has a committed reply) starts a new branch. An empty fork draft is **deleted** on retire (`retire_active_draft` deletes an empty draft *only* when it isn't a tail). The "+" forks via `create_draft`; the freshly-created draft selects its branch on the next render via `pending_select`, then `dock_active_draft` scrolls it home.
  - **Dots tint only with content** — `post::subtree_has_draft_content` (not the structural `subtree_has_draft`, which was removed) tints a branch dot `info` only once its draft is non-empty, so the always-present empty tail drafts don't paint every branch.
  - **Empty/active machinery is shared** — `create_draft_node` mints the editor (focus→activate, Enter→submit); a draft is always the end of its branch, so an inactive draft reserves `max(natural, window)` height (`min_h` + the `node_height` floor) — the active composer's runway — so activating/deactivating never shifts the layout. One draft is *active* (focused, floating/docking); focusing another, or **Escape**, retires the current one (a kept one blurs to the view root so it reads as exited; clicking an inactive draft re-activates it directly). `⌘↩`/`⌘⇧↩` (`Send`/`PostOnly`) **consume** the active draft into a persisted post; a typed submit failure surfaces a **minimal error band**. A brand-new blank (⌘N) space opens with its root tail draft already focused (cursor in an empty notebook). **Notes-editor click target:** because a docked composer (and every inactive draft) reserves at least a window height, most of its body is blank runway below the text; clicking it should land the caret at the end. This is **owned by the editor**, not an overlay: the composer/draft passes `MarkdownEditor::min_height(..)` so the editor itself fills the runway, and the editor resolves a click below its last line to document end (see the editor crate's `min_height`/`offset_for_position`). A click on the text stays a normal caret placement — one listener (the editor's), no ancestor click handler juggling ranges. The **active composer** sizes the editor to `body_h`; its bar height comes from `content` = the editor's `content_height()` (natural text height, decoupled from the `min_height` floor so there's no feedback loop) folded with the half-pad breath, measured by the `record_height` canvas in its paint phase. The **inactive draft placeholder** fills the editor to `window − 2·POST_PAD_Y` (matching the frame's `min_h(window)` runway); its row keeps a thin `on_click` that only re-activates the draft + focuses (for clicks on the byline gutter that miss the editor) — clicking the editor itself activates via its `Focus` event, and the editor owns caret placement, so there's no cursor-resetting overlay. (This replaced an earlier ancestor-`on_click` approach that reset the caret to end even on text clicks, because the editor doesn't stop the *click gesture* on ancestors.) **Composer scroll — always-on tracking, gated ownership, smooth dock ramp:** the composer body's `overflow_y_scroll` + `track_scroll` stay on **unconditionally**. What's gated (on `composer_scrollable = overlayed && chrome + content > bar_h`, cached in a `Cell` for the wheel handler) is only *ownership*: the composer **owns** the wheel (`ScrollOwner::Composer`, `stop_propagation`, page locked out) just when it's floating with real overflow; otherwise `ScrollOwner::Body` (no `stop_propagation`) — so a floating fit-height composer scrolls the *page* underneath (moving it toward its dock), and a docked composer lets the page scroll while its own frozen offset ramps. Two things depend on tracking staying on: **(1) no phantom scroll** — a fit-height composer has `scroll_max == 0` (the editor exactly fills `body_h`, and the `record_height` measuring canvas is pinned to the origin so it adds nothing to `content_size`; an inset-less `absolute` child would otherwise sit at its static post-editor position and inflate the scroll range by a full `body_h`, letting a one-liner scroll ~half a window out). **(2) Smooth dock ramp** (imported from `examples/eidola_space.rs`): as a *scrolled* floating composer docks, `bar_h`→`body_h` (the scroll viewport) grows from the floating height toward the full content height, so `scroll_max = content − body_h` shrinks toward 0 and gpui clamps the frozen internal offset toward the top — the content glides up and lands exactly at the top as it docks. Gating `overflow_y_scroll`/`track_scroll` off while docked (an earlier version) abandoned the offset the instant it docked and snapped the content to the top.
  - **The floating composer is its own stacking layer** (`render_active_draft`'s return: `layered(composer, reach)` — a small local `Element` that paints its child inside one `Window::paint_layer`). gpui assigns each primitive a draw `order` from a `BoundsTree` (`order = 1 + max order of already-painted primitives whose *registered* bounds it overlaps`) and batches by `(order, primitive_kind)`. A drop shadow's registered bounds are the element rect grown by its *spread* only — **the blur reach is not included** (`Window::paint_drop_shadows`). So an inline shadow, in the ~20px window around the dock/float threshold where its blur visually spills over the final separator band but the composer rect hasn't reached it, lands in a disjoint BoundsTree chain from the band; the band (bumped by the high-order posts above it) sorts on top — the shadow renders *behind* the separator, then "jumps" in front once the rects overlap. `paint_layer` gives every composer primitive **one shared order** computed from the layer bounds, which `layered` dilates upward (`reach = blur − offset_y + margin`, from the `SHADOW_BLUR`/`SHADOW_OFFSET_Y` consts) to cover the blur — so that order overlaps the band and the whole composer, shadow included, sits above the page for the entire transition (internal order survives: within the shared order, batching still draws Shadow-kind under Quad-kind under text). **No `deferred` wrapper** (this replaced an earlier `deferred(…).with_priority(0)`, kept for symmetry on the minimap): paint order already does the work — the composer is a later root child than the scroll subtree, so it paints after every post/band and its layer order lands above them; the minimap is a later child still, so it paints after the composer and — overlapping it on the right edge — its BoundsTree order is bumped above the layer, keeping the scroll map on top of the bar. Staying in the normal paint pass (rather than the late deferred pass) also keeps both **below** window-level overlays like the gpui dev **inspector**, which the deferred versions painted over.
- `request.rs` — the **request affordances**: how a draft becomes a request. The page geometry is **symmetric** — `[byline gutter | reading column | action gutter]`, both gutters `GUTTER_WIDTH` (`layout::body_width` subtracts both) — the left gutter says who wrote a post, the right one is where you act on it (posts fill it on hover with the Edit/Regenerate verbs — see `post.rs`; `post::action_gutter` is the shared geometry). The **active composer's** action gutter carries the discoverable submit: **Ask** (text_sm semibold, quiet hover — posts *and* requests a response, the pointer twin of ⌘↩) with the **model chip** below it (text_xs, mirroring the byline's time line — the *addressee*), and holding **⌥ reveals Post** (post without asking, ⌘⇧↩) plus the keyboard hints beside both verbs. The affordances render only once actionable — a non-empty draft, ⌥ held, or the panel open (the blank page stays sacred; the gutter is otherwise reserved empty space). Clicking the chip (or **⌥⌘M**, `ToggleModelPicker` bound in the `SpaceView` context; the handler no-ops without an active draft to anchor to) opens the **request panel**: the model list with honest per-model info (`request.rs::model_info_line` — context length + the credit rates actually charged), current + config-default markers, and a quiet "Set … as default" footer (only when it would change anything). Selection goes through `SpaceView::select_model` → the shared `Space::select_model` (per-space; a mid-stream switch applies to the *next* send). The panel anchors to the action gutter via `composer_anchor_top` (a `Cell` the composer records each frame): it opens **downward** when the composer sits high (a docked blank notebook) and **upward** when it floats near the bottom, height-capped to the available room. Dismissal: click-out (`on_mouse_down_out`), Esc (the composer's key handler closes the panel *before* deactivating the draft), retiring/sending the draft, or selecting. The root registers the window's single `on_modifiers_changed` listener (mirroring into `WindowInput` — see [WindowInput](#windowinput--per-window-modifier-state)). **The panel is the designed home of per-request config** (temperature, thinking/no-thinking): those wait on app-core plumbing them through `run_turn`/`chat_stream` — no fake controls until the wire exists; they join as rows below the model list. No keyboard row-navigation yet (the retired chat picker's focus-parking dance is deliberately not replicated until the panel earns arrows).
- `minimap.rs` — the topology minimap, drawn from the selected path's cached heights + the live scroll offset (no per-frame canvas sweep), with the macOS-overlay-scrollbar show/linger/fade. A draft counts on **its own** branch (it's a tree node on the selected path); a **floating off-branch** draft pads other branches by its bar height (`layout::floating_pad`, folded into the minimap denominator + a trailing spacer) so the scroll indicator maps 1:1 on every branch. The map is a navigable **table of contents**: draft columns use the `info` hue (same on/off/sibling opacity ramp as the scroll colors); every column is **click-to-navigate** (`navigate_to_node` → `select_path_to` that branch + scroll its top into view via `selected_path_doc_top`), interactive only while the overlay is up so a faded strip can't steal clicks; and it's annotated for accessibility — a `Group` "Conversation map" of per-node `Button`s labelled "*byline*: *snippet*" (or "Draft" / "Eidola, responding"), with `aria_selected` on the active path. Probes `space/minimap` + `space/minimap/cell/{level}/{i}` double as driver click targets.

**Read-only `MarkdownEditor` (the editor crate, breaking out the user's "Phase 2"):** a `disabled` editor renders as **published** markdown — `MarkdownEditorState::render_spec` calls `render::render_readonly` (a no-cursor render, `CursorRange::nowhere()`), so every WYSIWYG delimiter is hidden and a post reads as finished prose. Without this, a disabled editor's offset-0 cursor revealed leading delimiters (a post starting with `**bold**` showed the `**`). The editable path is unchanged (`render` → `render_with_cursor` with the real selection).

`ChatMessageView` gained two minimal UI fields for this surface: `parent_action_id` (relink the tree) and `created_at` (the gutter time byline), set in `from_post`. Tests: `space_view::{model,layout,nav}` unit tests (tree shape, cache invalidation, snap math); behavior tests (`space_*` in `tests/behavior.rs` — auto-tail-draft-at-each-leaf, submit→stream+consumes-draft, post-only, empty no-op, reply-branches, Escape-keeps-empty-tail / deletes-empty-fork-keeps-nonempty, shared-entity join, request-panel toggle-requires-composer / select-model-routes-next-submit / closes-on-deactivate, alt-modifiers-reach-WindowInput, cmd-enter-routes-through-PressEnter, stale-load-vs-submit race, edit commit/cancel + the sync-bodies guard, regenerate-uses-selected-model, post-hover out-of-order-leave, reasoning projection + toggle); probe tests (`space/composer`, `space/band/add`, `space/composer/ask`, `space/composer/model`, `space/request-panel[/row/*]`, plus the panel open/dismiss staleness dance); visual cases (`space_branches` = existing with docked tail drafts, `space_blank` = focused root composer, `space_composer_actions` = the revealed action gutter, `space_composer_alt` = ⌥ expansion, `space_request_panel` = the open panel); driver scenes (`space_blank`, `space_conversation`, `space_branches`). **Deferred:** per-request sampling config in the request panel (needs app-core support), hiding the inline "Draft" byline, and a floating/windowed editor for very long scrolls (Mike, design-acknowledged — start inline, revisit).

## Window model

**Space windows are non-singleton; the space *entity* they share is not.** Every `NewSpace` opens a fresh `SpaceView` via `open_main_window` → `open_chat_window(cx, stores, None)`; with `space_id: None` `SpaceView::new` calls `SpacesStore::blank()` for an id-less `Space` (instant ⌘N; the registry adopts it once its first exchange assigns an id). The Library reopens via `open_space_window(cx, stores, space_id)` (`Some(id)`): `SpaceView::new` calls `SpacesStore::open(id)`, which **joins** the registry — so opening the same space twice yields two independent *windows* over **one shared `Space`** (transcript, streaming, submit, model selection are common; submits/streams in one window appear in the other). The composer draft stays per-window by design. There is still no window *dedup* (two windows is fine, acceptable v1) — the change from before is that they no longer each hold a private transcript copy. `open_chat_window` calls `cx.activate(true)` after `cx.open_window` so a window opened from another app's context (dock right-click while a different app is foreground) brings Eidola to the front rather than opening behind.

**Settings, Library, Updates, Record, About, and Onboarding are singletons.** `AppGlobal.settings_window` / `AppGlobal.library_window` / `AppGlobal.updates_window` / `AppGlobal.record_window` / `AppGlobal.about_window` / `AppGlobal.onboarding_window` (`Option<WindowHandle<Root>>`) cache the handles, and `OpenSettings` / `OpenLibrary` / `CheckForUpdates` / `OpenRecord` / `About` / `GetStarted` raise the existing window via `window.activate_window()` if it's still open (shared helper `try_focus_existing_singleton`, parameterized over the `AppGlobal` slot). The onboarding window also opens automatically at launch when no account is configured. Both open paths are **synchronous** (via `App::open_window`) so the cache is populated before the handler returns. Liveness is checked by matching the cached `WindowId` against `cx.windows()` (the authoritative live list) — borrowing Zed's pattern, except Zed can use `AnyWindowHandle::downcast::<SettingsWindow>` directly because their settings root is uniquely typed; ours is `gpui_component::Root` (shared with chat windows), so we match by id instead. A stale id self-heals on the next invocation — no `on_release` bookkeeping needed. `OpenLibrary` additionally calls `SpacesStore::refresh` on every invocation (not just first open) so a long-lived Library window doesn't show a stale listing. `CheckForUpdates` follows the same singleton pattern via `AppGlobal.updates_window`, and re-runs `UpdateStore::check_now` when raising an existing window so the menu gesture always produces a live check.

## Updates window

`updates.rs` renders the verified update-notification flow (`eidola_app_core::updates` — see the workspace `AGENTS.md` for the verification model and failure-mode matrix). Small singleton (480×360 default), opened via Eidola menu → "Check for Updates…" (directly under "About Eidola", the standard macOS placement).

- **State is derived, not stored**: `UpdatesView::derive_display(update_store)` maps the `UpdateStore` snapshot + its `checking` flag to a `UpdatesDisplay` enum — `Checking` (only when a check is genuinely in flight *and* there's nothing else to show; a re-check over a standing result keeps the result up and just disables the footer button into "Checking…"), `NoneYet`, `UpToDate` (with last-checked relative time), `UpdateAvailable` (one primary action: "View Release…" → `cx.open_url`), `Unverifiable` (danger-tinted security band quoting the exact failure reason; deliberately **no** link to the artifact), `ClaimsChanged` (side-by-side expected/attested delta table; the only affordance is the explicit, non-primary "Treat as Update" → `UpdateStore::accept_changed_claims`), and `CheckFailed` (quiet muted copy — an offline blip is not a security signal).
- **Background polling**: `run()` calls `UpdateStore::start_polling` at launch (app-core runs one check immediately + every ~6h on its tokio runtime, persisting results). The view constructor calls `UpdateStore::load_last` so a poll result that landed while no window was open is reflected on next open — no banners in chat windows.
- **Store plumbing**: `UpdateStore` holds the cached `snapshot` + `checking` flag; `check_now` owns its own supersede task slot and its `checking` flag makes re-entry a no-op while a check is in flight (so the constructor-triggered check and the menu handler's re-check are naturally idempotent). There is no shared busy gate.
- Behavior tests cover the display derivation for every matrix row plus stub no-op actions; visual snapshots cover all six states (`updates_*`), day+night.

## Library — table of contents, not a sidebar

`library.rs` renders the space listing as a book's table of contents (520×620 default): one column, hairline `theme.border` rules *between* entries (border-top on `idx > 0`, no boxes/cards/avatars), each row a title — or, for untitled spaces, the first-message snippet in `theme.muted_foreground` — with a right-aligned relative date ("today" / "3d ago" / "2w ago"; see `relative_date`) in `text_sm` muted. A heading ("Library", italic, between hairline rules) echoes a book's interior typography so the window reads as another page of the same book. Empty state is a single centered muted line. The data comes from `SpacesStore` (the `Loadable<Vec<SpaceInfo>>` index, archived excluded), refreshed via `SpacesStore::refresh`.

**Virtualized.** The listing renders through gpui's `uniform_list` (see [Virtualized lists](#virtualized-lists)): rows are fixed-height (`ROW_H`, single line), the closure (`render_rows`) is a dumb indexer that clones only the visible slice from `SpacesStore`, and the list self-scrolls via a stored `UniformListScrollHandle`. The centering wrapper is `h_flex().flex_1().min_h_0().justify_center()` around the list, which carries `.h_full().w_full().max_w(rems(34))` so it fills the height (so it actually scrolls) while staying capped at the prose measure and centered — a library too long for one screen now renders O(visible), not O(rows).

Interactions: clicking a row opens the space (`open_space` defers `open_space_window` via `cx.defer` so the new window opens after the current update cycle); hovering a row (`hovered: Option<usize>` tracked via `on_hover`) reveals **two ghost buttons in a fixed-width reveal slot** (so their appearance doesn't shift the date column) — a rename affordance (the bundled Lucide set has no pencil glyph, so `IconName::CaseSensitive` / "Aa" is the quiet text-edit cue) then the archive ×. The pencil starts the inline rename; the × archives via `SpacesStore::archive` — which removes the cached row *immediately* (so the UI responds without a backend round-trip, and so stub-store tests exercise the local path) and then runs the real archive + re-fetch. `archive` / `open_space` / `begin_rename` are public methods so behavior tests drive them directly instead of synthesizing mouse events; `set_hovered_for_test` exists for the hover snapshot. **Pencil/× propagation (the "click both renames and opens the row" race).** Each affordance is wrapped in a slot `div` that stops propagation on **both** mouse-down and mouse-up (not just the click), and the pencil **defers `begin_rename`** via `cx.defer_in`. `cx.stop_propagation()` inside a child `on_click` only stops the click's mouse-up *bubble* phase, but gpui arms a click on mouse-**down** (each hovered ancestor records its own `pending_mouse_down`) and captures it on the mouse-up *capture* phase — both before the child's bubble click runs (`gpui/div.rs` paint + `window.rs::dispatch_mouse_event`: capture outer→inner, then bubble inner→outer). So the row had already armed and captured its own pending click; `begin_rename` reshaping the row *between* the captured down and the firing up (reveal slot hidden, title → input) could land the up on the bare row and complete the ROW's open on top of the rename. Blocking the **down** stops the row from ever arming; deferring `begin_rename` keeps the gesture resolving against the pre-rename layout. (gpui's #24600 guard, the row dropping its `on_click` on reshape, and the pencil's `stop_propagation` cover every *synchronous* path, so the production failure is the intermittent multi-frame timing race; the regression test guards the invariant deterministically — stripping the pencil's propagation blocking makes the row's `open_space` fire under a real simulated click.) The archive × needs no defer — its row vanishes (different masking) — but takes the same both-phase block for symmetry. Each slot also carries a `debug_selector` so the regression test can locate the pencil's hitbox. **Hover-event ordering:** the `on_hover` listener routes through `set_row_hover(idx, hovering)`, which on hover-false clears `hovered` **only if `idx` is still the hovered row** — moving the cursor *up* the list, the row being left can fire `on_hover(false)` *after* the row being entered fired `on_hover(true)`, and an unconditional clear would wipe the new row's reveal buttons (the asymmetric "× flickers off when moving up the list" bug). Replay: `library_hover_survives_out_of_order_leave`.

**Inline rename.** The hover-revealed pencil calls `LibraryView::begin_rename(space_id, current_title, window, cx)` (replacing the former double-click trigger, which was unreachable — a single click opens the row immediately, so a double-click's second click landed in the freshly-opened window). `begin_rename` creates an `Entity<InputState>` seeded with the current title, focuses it immediately, and subscribes to `InputEvent`: `PressEnter` → `commit_rename` (writes through `SpacesStore::rename`, which optimistically updates the cached row and then calls `AppCore::rename_space` + re-fetches); `Blur` → `cancel_rename` (drops the draft without writing). Pressing Escape inside the `InputState` propagates through (the `Input` context doesn't capture Escape by default when `clean_on_escape` is false), which causes the input to lose focus and fires `Blur`, which cancels. The active rename space is tracked in `renaming: Option<(String, Entity<InputState>, Vec<Subscription>)>` on the view; `renaming_space_id()` returns the id for tests. The reveal slot is hidden while a row is being renamed so the buttons don't compete with the input. `SpacesStore::rename` uses the same optimistic-update + supersede-slot pattern as `archive`; the bus-driven `Change::SpaceIndex` reconciles all windows. Replays: `library_pencil_begins_rename` and `library_pencil_click_does_not_also_open_row` (the real-click propagation guard).

## Settings — calm two-pane, ⌥-revealed advanced

`SettingsView` (620×520) is an `h_flex`: a narrow nav band (`NAV_WIDTH` 132px) on `theme.sidebar` with quiet text items (active = `sidebar_accent` pill), and the selected pane in the content column. Settings keeps **no raw-data dumps** — summaries link to the Record window.

- **Scroll-width invariant (again).** The content pane's scroll container is a `v_flex().flex_1().h_full().min_w_0()` wrapping `div().id("settings-body").w_full().flex_1().overflow_y_scroll()`. Without the `w_full` on the scroll div, taffy content-sizes the pane: long lines refuse to wrap and rows shrink to content width (same failure mode as the chat transcript invariant).
- **General**: the Base URL row shows the resolved value plus an honest source line — "Built-in pin" vs "Override — the built-in pin is …" with a one-click "Revert to pin" (`AppCore::clear_base_url_override`; `ConfigState` carries `base_url_pin` / `base_url_is_override`). Saving a value equal to the pin is treated as a revert. The **advanced rows** (attestation URL, domain separator, hardware CAs, trusted-measurements summary + Record link) render only while **⌥ is held**: `SettingsView`'s root `h_flex` registers the window's single `on_modifiers_changed` listener and mirrors events into `Entity<WindowInput>` (see [WindowInput — per-window modifier state](#windowinput--per-window-modifier-state)); `GeneralView` observes `WindowInput` and calls `set_advanced` when `alt_held` changes. `GeneralView` **never** registers its own `on_modifiers_changed` — doing so would be dead while a text input in a sibling pane (Account / Wallet) or in General's own Base URL field has focus, because `ModifiersChangedEvent` dispatches along the focused element's ancestor path only (wave-2 bug 2). A one-line italic hint discloses the affordance at rest. The measurements row never shows hex — it links to the Record via `window.dispatch_action(Box::new(OpenRecord), cx)`.
- **Account**: balance + pools (humanized future expiries, `humanize_expiry`), plans via the shared `plans::plan_rows` with the same checkout flow as onboarding (`AccountStore::request_checkout`, view-owned pending state), and Reset behind a **two-step inline confirm** (`request_reset` → armed warning + "Reset account" / "Keep account"; no modal). The manual allocate-credits input was removed — app-core auto-provisions credentials from balance, so it no longer justified its row. **Account create/reset failures are surfaced, not dropped** (honest-states rule): `AccountStore::create_account` / `reset_account` store the `Err` in `account_op_error` (cleared at the start of the next attempt and on success), and `AccountView` renders it in the `error_banner` style directly under the Account controls so the button never silently does nothing. Hidden by default, so the `settings_account` snapshots are unchanged at rest. Behavior test: `account_op_error_surfaces_and_clears`.
- **Wallet**: one history listing from `WalletStore` (via `WalletStore::refresh` → `AppCore::wallet_lifecycle`, the local `credential_lifecycle` view): active / in flight (warning color, recoverable) / spent / expired (muted). "Recover in-flight" appears only when something is actually in flight.

## The Record window — the trust door's engine room

`record.rs` (`RecordView`, singleton, ⇧⌘L / File → "Record…", 860×640) exposes the raw local Turso trail. Three sections in a quiet text strip that doubles as the title bar (`STRIP_LEFT_PAD` 80px clears the traffic lights; right side carries a Refresh affordance and an italic "The Record" wordmark):

- **Attestations** — `attestation` rows (middle-truncated hash, pcr digest, connection count, doc size, UTC timestamp). Click → the full raw document: pretty-printed JSON when it parses, UTF-8 text, hex otherwise.
- **Requests** — `request` ⋈ `connection` rows (mono `METHOD /path`, status colored by outcome, transport/duration/attempt/credential/error subline). Click → full detail: kv rows (the attestation hash links through to its attestation detail) + raw request/response headers and bodies.
- **Spending** — the `spend_trail` view grouped by credential (consecutive same-nonce rows share a group header with held/charged amounts; rows are time-ordered so the grouping matches reality). Rows click through to the request detail.

Mechanics worth knowing:

- **Windowed fetch.** `Listing<T>` per section; each page asks app-core for `PAGE+1 = 51` rows (`LIMIT/OFFSET`) to learn `has_more` without a COUNT. Data flows through the `bridge` free functions (`bridge::list_attestations` / `list_requests` / `spend_trail` / `attestation_detail` / `request_detail`, taking the `Arc<AppCore>` from `Stores::app_core()`) so the view owns its loading state in its own task slots. These window-scoped reads become a reader entity in a later step. Stub stores skip the fetch; tests install rows via `set_*_for_test`.
- **Virtualized listings + flat display model.** Each populated section renders through `uniform_list` (see [Virtualized lists](#virtualized-lists)), so frame work is O(visible), not O(loaded) — the wave-2 bug-3 fix (the window used to slow to a crawl as "Load more…" appended pages, because every row re-rendered every frame). To keep the `uniform_list` closure a dumb indexer, each `Listing<T>` precomputes a flat `Vec<DisplayRow>` (`Header(i)` / `Data(i)` / `LoadMore`) on every state change (`rebuild_flat_display` for attestations/requests; `rebuild_spending_display` for the grouped Spending view). **Spending group headers survive virtualization** because they are precomputed `Header` rows interleaved into the display model, not a render-time `prev_nonce` branch the windowed closure couldn't reconstruct. All rows — data rows, group headers, and the trailing load-more row — are normalized to one fixed height (`ROW_H`); the formerly taller spending group headers are slightly tighter now (even spacing carries the group rhythm instead of extra top padding — an intentional, documented change). **Load-more stays windowed:** the trailing `DisplayRow::LoadMore` is an explicit, quiet "Load more…" row that appends the next 51-row page; while a fetch is in flight it renders an honest "Loading more…" in-flight row (it maps to a real task, never an infinite spinner). The empty/loading/detail bodies stay in an ordinary `overflow_y_scroll` container (`scroll_wrap`); only a populated listing is the self-scrolling `uniform_list`.
- **Raw payloads are never redacted** (the user's own traffic on their own machine). Inline rendering is capped at 64 KiB with an honest note; the per-section **Copy** affordance always writes the *full* payload to the clipboard. Raw text renders selectable through `TextView::markdown` inside a code fence whose backtick run is computed to exceed any run in the content (`fenced`); the `TextViewStyle` mirrors `theme.mode.is_dark()` so the block ground tracks Circadian night.
- **Parse caching (no per-frame projection).** Opening a detail builds a `DetailCache` **once**: the raw-payload projection (pretty-printed JSON / UTF-8 / hex dump), the `fenced` + 64-KiB-capped inline string, and the full Copy string are all computed at open time and stored as `CachedPayload`s. The render path (`raw_section`) only reads the cache — it never re-projects per frame. This is the other half of bug-3: a large attestation document or response body used to re-run `serde_json::to_string_pretty` / `hex_dump` / `fenced` on every frame. **TextView itself does not re-parse per frame at our pin** (verified in `gpui-component@dadfca9`): `TextView::markdown(id, text)` resolves its `TextViewState` via `window.use_keyed_state` keyed on the element `id`, and `TextViewState::set_text` early-returns when the text is unchanged — so a *stable id + stable string* parses exactly once. The per-frame cost was always our own Rust-side projection, which the cache removes; passing the cached `fenced` string (identical bytes each frame) under the payload's stable `id` keeps TextView's parse a one-time cost. Perf is guarded by `record_frame_work_is_constant_in_loaded_rows` (behavior test: 1 page vs 10 pages — the visible-window render produces the same fixed row count and does not scale in time).
- **Space cross-link.** The request detail view includes a "Space" kv row when `RequestDetail.space_id` is set (a LEFT JOIN through `action → space` added to `db::get_request`). The row renders as a quiet link (`theme.link` color, hover underline) whose click defers `open_space_window(cx, stores, space_id)` — the same path the Library uses, so opening a linked space from the Record is a single click. The label is `space_title` when present, the bare id otherwise. Behavior test: `record_request_detail_exposes_space_link`.
- **Mono is for data, the UI font is for chrome** — `mono()` (Menlo 12/13px) wraps every hash, nonce, path, and payload; labels, timestamps and empty states stay in Newsreader. Timestamps are UTC and say so (`fmt_utc`, Hinnant `civil_from_days` — no chrono dependency).

## Virtualized lists

Fixed-height lists render through gpui's `uniform_list` (`docs/architecture/state.md` → "Lists"): the **Record** sections (attestations / requests / spending) and the **Library** index. The **space view**'s posts are variable-height and use their own height-cache virtualization instead (see [Space view → `layout.rs`](#space-view--tree-navigation-conversation-surface-srcspace_view-wave-6)). The `uniform_list` idiom (mirrors zed's project panel / pickers at our pin):

- **Item-range closure via `cx.processor`.** `uniform_list(id, count, cx.processor(|this, range, _window, cx| this.render_rows(range, cx)))` — the closure is a *dumb indexer*: it renders only `range` (the visible window), so per-frame work is O(visible), never O(loaded). Any structure the closure would otherwise have to reconstruct from a bare range (group headers, separators, a load-more affordance) is **precomputed into a flat display model** (`Vec<DisplayRow>` in the Record) so the closure stays a pure index→element map.
- **Fixed row height.** `uniform_list` measures one row and lays every row out at that height, so all rows in one list must be the same height. Rows are normalized to an explicit `.h(ROW_H)` (deterministic, not font-metric-coupled); variable content (multi-line sublines, depth) is truncated with the middle-ellipsis helpers and pushed into the detail view — the listing row is always fixed-height.
- **Stored scroll handle.** A `UniformListScrollHandle` lives on the view and is passed to `.track_scroll(&handle)` each frame (so scroll position survives re-renders and supports programmatic `scroll_to_item`).
- **Sizing.** `ListSizingBehavior::Auto` (the default) makes the list fill its flex parent and scroll internally — place it as a `flex_1` child (v_flex parent) or give it `.h_full()` inside a `flex_1().min_h_0()` parent (h_flex, e.g. the Library's centering wrapper). The list's own `overflow.y = Scroll` is set by `uniform_list`; do **not** wrap it in another `overflow_y_scroll` div (that nests two scroll surfaces and the inner list collapses).

## Edge-to-edge titlebar

`transparent_titlebar()` returns `TitlebarOptions { appears_transparent: true, title: None, traffic_light_position: Some(point(14, 11)) }`. macOS extends the content view under the traffic-light buttons and stops painting a separate titlebar background. Each view leaves room at the top so the lights don't land on real UI:

- **`space_view::TITLE_BAR_RESERVE`** (36px on macOS): vertical reserve, plus a `theme.background → transparent` linear-gradient overlay (the space view's title band, wired through `titlebar::make_draggable`) painted absolutely over the scroll area. Posts scrolling up under the band fade smoothly into the chrome instead of clipping at a hard edge. The band is pure chrome — identity rides in each post's gutter byline, and the model lives in the composer's action gutter (see Prose typography / the Space view section).
- **`settings::NAV_TOP_RESERVE`** (44px on macOS): the traffic lights sit over the sidebar nav band, so the band's first item starts below them.
- **`record::STRIP_LEFT_PAD`** (80px on macOS): horizontal pad on the Record's section strip, which doubles as the title bar — the lights live to its left. 80px matches gpui-component's own `TITLE_BAR_LEFT_PADDING`.

**Window dragging is wired explicitly** (`src/titlebar.rs`). With the transparent titlebar macOS no longer hands us a draggable strip, and gpui's `WindowControlArea::Drag` is a no-op there, so every window makes its reserve strip draggable in the gpui content view: arm on left mouse-down, call `Window::start_window_move()` on the first move while armed (so a plain click never starts a drag), and forward a double-click to `Window::titlebar_double_click()` for zoom parity. The armed flag is **element-owned state** (`window.use_keyed_state` inside `make_draggable`, keyed on the strip's id, holding a `Cell<bool>` mutated without an entity update so arming never re-renders): it survives any re-render landing between the mouse-down and the first move because element state persists while the element keeps painting, and the drag strip is unconditional window chrome — no view field or constructor plumbing. `titlebar::drag_band(id, height, window, cx)` builds a full-width transparent overlay band absolutely positioned over the reserve (used by About / Library / Settings / Onboarding, painted **last** so it wins hit-testing over the columns beneath); `titlebar::make_draggable(stateful_el, key, window, cx)` attaches the same gesture to an existing strip (Updates' top spacer, Record's section strip — whose tabs keep their own clicks since a plain click never arms — and `space_view`'s gradient title band, which now routes through the helper instead of inlining the gesture).

## macOS UX — menus, keybindings, action dispatch

All wired in `src/lib.rs::install_menus`, `install_keybindings`, `install_action_handlers`. **Order of those calls matters** — see [Ordering invariant](#ordering-invariant) below.

### Menus (`cx.set_menus`)

- **Eidola**: About / Check for Updates… / Get Started / Settings… / Hide / Hide Others / Show All / Quit
- **File**: New Space / Library… / Record… / Close Window
- **Edit**: Undo / Redo / Cut / Copy / Paste / Select All — Cut/Copy/Paste/Select All declared via `MenuItem::os_action(_, _, OsAction::*)` so they bind to the standard macOS selectors `cut:` / `copy:` / `paste:` / `selectAll:` and route through the responder chain to whatever has focus
- **Window**: Minimize / Zoom

`cx.set_dock_menu` adds "New Space" and "Library…" for the dock right-click menu.

**The "Window" menu name is special.** gpui_macos detects a menu literally named `"Window"` and calls `app.setWindowsMenu_(menu)` — which is how AppKit recognizes the app as a fully-wired macOS app and reliably dispatches menu key-equivalents in edge cases (no key window after ⌘Tab back, all windows closed). The Hide / Hide Others / Show All trio play the same "I'm a real app" signaling role.

### Keybindings (`cx.bind_keys`)

⌘, (Settings), ⌘N (NewSpace), ⌘L (OpenLibrary), ⇧⌘L (OpenRecord), ⌘W (CloseWindow), ⌘Q (Quit), ⌘H (Hide), ⌥⌘H (HideOthers), ⌘M (Minimize), plus the `SpaceView`-context ⌥⌘M (`ToggleModelPicker` → the request panel — distinct from global ⌘M; the handler no-ops without a composer to anchor to). The submit chords ⌘↩ (post & ask) / ⌘⇧↩ (post only) are **not** view bindings — they live in the `MarkdownEditor` context (`gpui_markdown_editor::init`) and reach `Send`/`PostOnly` via the editor's `PressEnter` event, routed by each draft's subscription (`space_view::composer::create_draft_node`) and by an edit session's subscription (`post.rs::begin_edit`); binding them on the view would shadow the editor (the composer is the inner focus). Esc (request-panel dismiss → draft deactivation, and edit cancel) routes through element key handlers rather than bindings, so it composes with the editor's focus without a parking dance.

### Ordering invariant

`install_keybindings(cx)` **must** run before `install_menus(cx)`. `cx.set_menus` snapshots the keymap when it builds NSMenuItems and attaches each item's `keyEquivalent` from `keymap.bindings_for_action(action)`. Setting menus before binding keys leaves the keymap empty at lookup time, no keystroke is attached, and macOS can't intercept the shortcut at the menu level — which then breaks ⌘N / ⌘Q etc. when no window has key focus (the only path that *requires* the menu-level intercept; with a window focused, gpui's per-window binding dispatch handles it independently). **Diagnostic signal**: items appear in the menu without their shortcut text on the right side.

### Action handlers (`cx.on_action`)

Most handlers are global (registered on `App`). Two notable patterns:

- **Window-targeting handlers** (`Minimize`, `Zoom`) capture `cx.active_window()` and call `cx.defer` to invoke `window.minimize_window()` / `zoom_window()` *after* the current update completes. Without `defer`, a direct `handle.update(cx, …)` on the same window we were dispatched inside fails (its slot is already taken), `.ok()` swallows the Err, and nothing happens.
- **`CloseWindow` is registered per-view**, not globally. Each view (the chat/space window included) does `.on_action(cx.listener(|_, _: &CloseWindow, window, _| window.remove_window()))` on its root, and `track_focus`es a handle that's `focus()`ed in the view's constructor (so the dispatch path reaches the listener even before the user clicks anything). The intentional consequence: `is_action_available` returns true only when a window with the listener is alive, so macOS auto-disables the "Close Window" menu item (and ⌘W) when no window is open.

### Lifecycle

- `cx.activate(true)` at launch: brings the app to the foreground from frame 0 so the menu bar is fully connected before the user interacts.
- `Application::on_reopen` (registered on the `Application` builder *before* `run()` — the method takes `&self` and returns `&Self`, while `run()` consumes by value, so it can't be chained inline; bind the application to a local first): when the dock icon is clicked with no windows open, opens a new chat window. Without this, closing the last window leaves the app running but unreachable.

## .app bundling — required, not cosmetic

A bare `cargo run -p eidola-gui` binary launches as a command-line tool from AppKit's perspective, not a real app. `setActivationPolicy(Regular)` papers over the common path (menu shows, items enable, mouse clicks dispatch), but **menu key-equivalents fail to dispatch when no window is key**, even with the keymap-ordering fix above. The diagnostic signal is the menu bar showing the binary name (`eidola-gui`) instead of the app name (`Eidola`).

The fix is a proper macOS bundle:

- `crates/eidola-gui/Support/Info.plist` — `CFBundleIdentifier = tech.m6i.eidola-gpui`, `CFBundleExecutable = Eidola`, `NSPrincipalClass = NSApplication`, `NSHighResolutionCapable = true`.
- `scripts/package-gui-app.sh` — copies `target/{debug,release}/eidola-gui` to `Contents/MacOS/Eidola` (renamed to match `CFBundleExecutable` — mismatch falls back to tool-mode), copies the Info.plist, ad-hoc codesigns. Output at `crates/eidola-gui/build/Eidola.app` (gitignored). This is the **dev path** — fast cargo iteration, ad-hoc signed for local launch only.
- `just build gui` runs `cargo build` then the package script on macOS. `just run gui` builds + `open`s the .app. Non-macOS falls back to `cargo run`.
- **Release path:** `nix build .#eidola-gui-macos-universal` (flake.nix) builds an aarch64 + x86_64 universal binary, zeros LC_UUID for reproducibility, and assembles the same `Eidola.app` layout into a Nix store output that's recorded as `eidola-gui-macos-universal` in `artifact-manifest.json` (Nix `narHash`, `darwin/universal` platform). Built locally via `just update-manifest` (alongside the CLI universal binary) and in CI by the `apple` job. Two reproducibility tricks make this work inside the Nix sandbox: (1) gpui's Metal shaders are compiled at app startup via `runtime_shaders` (passed through `gpui_platform/runtime_shaders` → `gpui_macos/runtime_shaders`) instead of via Apple's closed-source `metal` compiler at build time; (2) `flake.nix`'s `commonArgs.preBuild` stitches a missing `assets/assets/icons` sibling layout into the cargo-vendored gpui-component dep, working around an upstream packaging bug where the `icon_named!` proc-macro reads `../assets/assets/icons` relative to its `CARGO_MANIFEST_DIR` (a path that only resolves in the upstream workspace layout, not in `cargo vendor`'s flattened tree).

## Testing — two tiers

Both tiers run via `cargo test -p eidola-gui` (`crates/eidola-gui` has both `[lib]` and `[[bin]]` so the integration tests can import view modules). A third, non-gating tool — the interactive UI driver — sits alongside them for agent-led QA sessions; see [The UI driver](#the-ui-driver-examplesdriverrs--interactive-qa-sessions).

### Behavior tests (`tests/behavior.rs`) — the regression gate

Built on `gpui::TestAppContext` (mocked rendering, deterministic dispatcher) so they run on libtest's worker thread without AppKit. Pattern:

1. Build stub stores with `Stores::stub_with(StoresStub { … }, cx)` — a declarative fixture scene (config snapshot, balances, prices, spaces, …).
2. Open a window with the view under test (via `cx.open_window`).
3. Drive interactions through the view's `focus_handle()` — the same path keystrokes take in production.
4. Assert against the view's public state, or the store entities (`stores.account.read_with(cx, …)`), with `read_with`.

Stub stores have no backend, so `Stores::app_core()` returns `None`; views that hit that path early-return after the local state mutation, and store `refresh_*`/`request_*` are no-ops. The store *machinery* itself (supersede, the bus bridge's dispatch, the launch-order replay) is tested against a real tempdir-backed `AppCore` in `tests/stores.rs` (via `Stores::for_test`). HTTP-mocked tests (real `AppCore` against a `wiremock` server) are the natural next layer.

### Visual snapshots (`tests/visual.rs`) — local-only debug aid

**Not** a regression gate. Built on `gpui::VisualTestAppContext` (real Metal renderer, offscreen window at -10000,-10000, deterministic dispatcher). Configured as `[[test]] harness = false` so `fn main()` runs on the macOS main thread (libtest's worker-thread harness would SIGABRT inside AppKit).

Cases live in `tests/visual/cases.rs`; the harness in `tests/visual/harness.rs` wraps each user view in a `Root` and renders it **twice — once in Circadian Day, once in Circadian Night** — by calling `Theme::change` between renders. Each case writes/compares two files: `tests/snapshots/<name>-day.png` and `<name>-night.png`. Case build closures must be `Fn` (invoked once per mode); they construct fresh entities each call.

The PNGs are **gitignored** — pixels are platform- and machine-bound (Metal+CoreText vs wgpu+cosmic-text on Linux; font hinting differs across macOS minor versions), so committing them would mean false-positive regressions in CI and on every other developer's machine. Their value is local: agents/humans can `Read` a PNG to "feel" a view at a state, and a developer iterating on a UI change can re-render and eyeball-diff their previous run.

Behavior:

- Missing PNG → write it and report `written`.
- Mismatch against a previously-written local PNG → write `<name>-<mode>.new.png` for review and fail.
- `UPDATE_SNAPSHOTS=1` overwrites.

Recipes: `just render-snapshots` (verify/write), `just render-snapshots-update` (accept).

### Why both tiers?

Behavior tests catch logic regressions (clicking X must call `store.Y(z)`; an empty Send must be a no-op) and survive across platforms. Visual snapshots are the "did I accidentally change the layout?" check that's only meaningful to the dev making the change. Together they let agents make UI changes confidently: behavior tests gate the merge, visual snapshots let the agent verify the change *looks* right by reading the freshly-written PNG.

### The UI driver (`examples/driver.rs`) — interactive QA sessions

The third leg, sitting between the two tiers: a **long-running interactive session** ("Playwright for eidola-gui") that an agent drives over a JSON-lines stdin/stdout protocol. Run with `just driver` (→ `cargo run -p eidola-gui --example driver`; it's an *example* so cargo's dev-dependency unification gives it gpui's `test-support` feature outside `cargo test`). It boots a `VisualTestAppContext` — real Metal rendering into offscreen windows at (-10000,-10000), deterministic `TestDispatcher` underneath — installs the production keymap (`eidola_gui::install_keybindings`, made `pub` for exactly this), and then loops: one JSON request per stdin line, one JSON response per stdout line.

- **Commands**: `scenes` / `open` (a named fixture scene, optional width/height) / `windows` / `elements` (named click targets with painted bounds, from the probe registry — see [Accessibility & QA probes](#accessibility--qa-probes)) / `click` (by probe `target` or x/y, with alt/command/shift) / `type` / `keys` (gpui keystroke syntax, e.g. `"cmd-enter"`) / `modifiers` (hold/release — drives the real `ModifiersChangedEvent` path, so ⌥ reveals work) / `scroll` / `resize` / `screenshot` (PNG to a path the agent `Read`s) / `theme` (day|night) / `settle` (advance the test clock + park) / `close` / `quit`. Full protocol docs in the example's module comment.
- **Scenes** are stub-store fixtures mirroring `tests/visual/cases.rs` — onboarding welcome/plans, empty + populated chat (with a model list so the ⌥ reveal and picker are live), library, settings, updates, record. No backend, no network: store-backed flows stop at the stub guard exactly as behavior tests do, while all window-local interaction (composer editing, submit's local append, picker open/navigate/select, hover reveals, pane navigation) is fully live.
- **Why this exists**: snapshots show one state; behavior tests assert one transition. The driver lets an agent *converse* with the UI — act, look at the actual pixels, act again — closing the QA loop that previously required a human. It needs no Accessibility/Screen Recording permissions, shows nothing on screen, and parallel sessions across worktrees don't interfere.
- **Element staleness**: every `elements` call (and every by-name `click`) clears the window's probe entries, forces a fresh frame, and re-reads — so an unmounted element (a dismissed picker, a row scrolled out of a virtualized list) can never linger as a ghost target. Regression-tested in `tests/probe.rs`.
- **Limits (v1)**: app-global action *handlers* (⌘N/⌘L/Settings…) aren't installed — they need the real `AppGlobal`/backend; window-scoped actions and keybindings all work. Scenes are stub-backed; a real-`AppCore`-against-mock-upstream scene is the natural extension once the wave-4 chat harness lands. macOS-only, like the visual tier.

## Accessibility & QA probes

gpui has AccessKit integration (zed #56065, in our pin): elements opt in per node — an element appears in the platform accessibility tree only if it carries an `ElementId` (`.id(…)`) **and** a role, with labels and state via the aria-style builders on `StatefulInteractiveElement` (`.role(…)`, `.aria_label(…)`, `.aria_selected(…)`, …). On macOS this produces real `NSAccessibility` nodes via `accesskit_macos`.

Our annotation point is **`crate::probe::Probe`** — `el.id("…").probe(name, role, label)` — which does two things at once: sets the AccessKit role + label (always), and records the element's painted bounds into a process-global registry (only when probes are enabled — the driver's `elements`/`click target:` vocabulary). The pairing is the doctrine: **the accessible name is the driver's selector**, so the AT surface and the automated-QA surface are the same annotation and cannot drift apart. The registry is recorded via the public `canvas` idiom (an absolute, paint-nothing, hitbox-free child), because gpui keeps its own bounds maps (`debug_bounds`, the AccessKit tree) crate-private on real-rendering windows; probes are inert in production (the canvas child isn't even constructed when disabled, and the trait bound on `StatefulInteractiveElement` makes ".id() before .probe()" a compile error to forget).

Conventions:

- **Names** are slash-scoped lowercase paths: `space/composer`, `space/request-panel/row/{idx}`, `library/row/{idx}/archive`, `settings/nav/general`. Dynamic rows interpolate their index.
- **Labels** are what a screen reader should say — user-meaningful, not internal names; dynamic where the content is (`"Model: gemma4-31b"`, a library row's title).
- **Roles** come from `gpui::Role` (re-exported accesskit): Button, Link, Tab, ListBox/ListBoxOption, ListItem, TextInput, Alert, Group.
- **gpui-component widgets** (`Button`, `Input`) don't implement the probe traits and have no a11y annotations at our pin (upstream is working on it — longbridge/gpui-component#2407): wrap them in a shrink-wrapped probed `div`. Caveat: the wrapper *announces* correctly but doesn't wire `on_a11y_action`, so AT-initiated activation isn't connected yet — clicks (human or driver) work as always. Wiring `on_a11y_action` on our own clickable divs is the natural next increment.
- **New interactive UI must ship with probes.** When you add a clickable affordance, annotate it in the same change — it's one call, and it's what makes the element visible to both AT and the driver. Coverage is asserted in `tests/probe.rs`; extend it when you add probes to a new view.

Zed itself currently ships with AccessKit force-disabled after early teething (zed #57954) — that's about *Zed's* rollout, not the gpui API; our annotated elements are a much smaller, fixture-tested surface. If instability appears in the real app, `Application::new_inaccessible()` is the upstream kill-switch to reach for.

## gpui / gpui-component pinning

`gpui-component` (longbridge, rev `dadfca97fec7221acf3ce7047bccdc1eac0506b9`) pulls `gpui` and `gpui_platform` from `zed-industries/zed` without a rev. We mirror that exact spec in `Cargo.toml` so cargo unifies on a single `gpui` copy. `Cargo.lock` is the canonical pin for the resolved zed commit. gpui-component and gpui move in lockstep: a given gpui-component rev expects a matching gpui (e.g. the `flex_shrink_1`/`flex_grow_1` helpers it calls landed in gpui commit `8982fb17`), so bump both together.

**The zed pin is at `34cd17f` (2026-06-11).** The pin was previously held back at `969a67fc` because the commit after it (zed #57835) added a global action-timing profiler whose process-wide `ACTION_STATISTICS` spinlock panicked under libtest's parallel `gpui-markdown-editor` behavior tests. Upstream fixed the race (zed #58813) and then made the profiler opt-in behind the `gpui/profiler` feature (zed #58942, off by default — we don't enable it), so the hold is obsolete. The historical rule stands as practice: when advancing the pin, re-run the full editor behavior suite under default libtest parallelism before committing the lock. The pin also includes gpui's AccessKit integration (zed #56065, merged 2026-05-27) — see [Accessibility & QA probes](#accessibility--qa-probes).
