# measure-enclave — Agent Development Guide

The `measure-enclave` binary pre-computes the hardware attestation measurements a legitimate Tinfoil Container will produce. The measurement is a deterministic function of:

1. OVMF firmware (pinned from `tinfoilsh/edk2`)
2. CVM kernel + initrd (versioned from `tinfoilsh/cvmimage`, hash-verified)
3. Kernel command line (embeds dm-verity roothash + SHA-256 of the workspace `tinfoil-config.yml`)
4. vCPU count and type

Uses `sev` (with `crypto_nossl` — pure Rust, no OpenSSL) for SEV-SNP launch digest computation and `tdx-measure` for TDX RTMR1/RTMR2 runtime measurements. Both work natively on macOS. Output JSON matches the Tinfoil deployment manifest predicate (`snp-tdx-multiplatform/v1`): `{snp_measurement, tdx_measurement: {rtmr1, rtmr2}, cmdline}`.

**The measurement flow:** source → deterministic OCI build → server digest → `tinfoil-config.yml` (with digest) → cmdline (with config hash) → measurement → `releases/trust/server-enclave.json` → the cli build embeds it as its trust root → cli OCI digest / desktop `narHash` + `archiveSha256` → `artifact-manifest.json`. The `server-enclave.json` step breaks the otherwise-circular self-reference that would occur if the cli build COPYed the manifest containing its own digest; isolating the enclave fields gives the cli build a stable input while the manifest regenerates. All values are committed and verified by CI (see `.github/AGENTS.md`). Payload / archive vocabulary: `docs/verification.md`.

CVM artifacts are cached locally at `~/.cache/eidola/cvm/`. Both mutable-tag downloads are pinned by committed SHA-256 constants in `scripts/artifact-manifest.sh`: `OVMF_SHA256` pins the OVMF.fd asset, and `CVM_MANIFEST_VERSION`/`CVM_MANIFEST_SHA256` pin the CVM release manifest (which transitively pins kernel, initrd, and the dm-verity roothash). Cache hits are re-hashed, not trusted — a poisoned cache entry is discarded and re-fetched, and a fresh download that still mismatches fails hard. Bumping `cvm-version` in `tinfoil-config.yml` requires updating the manifest pin (the script refuses a version with no matching pin); an inline `cvm-version: X@sha256:HEX` pin in the config (the tinfoilsh/measure-image-action syntax) takes precedence. `ovmf-version` is deliberately absent from the config: Tinfoil's deploy infrastructure does not support the field yet, so the OVMF pin lives script-side only — and must track the firmware the `measure-image-action` release pinned in `tinfoil-build.yml` measures with, or the tag workflow's cross-check fails (open item: `crates/eidola-server-gateway/AGENTS.md` → Release checklist). Pass `--verify-attestations` to `scripts/artifact-manifest.sh` (used by CI) to additionally verify CVM manifest provenance via Sigstore (`gh attestation verify --deny-self-hosted-runners`); this fails hard on verification failure.

Because the config hash is bound into the measurement, **any change to `tinfoil-config.yml` produces a different enclave measurement** — regeneration is `just update-manifest` (release time only; see the top-level AGENTS.md conventions).

## TDX launch identity, IGVM model (`measure-tdx-igvm`)

A second binary in this crate emits the launch half of a verifier TDX pin (`tinfoil_verifier::TdxPin`) for the platform provider's IGVM launch model (cvmimage v0.15+). That model has no OVMF and no measured boot after launch, so its TDX identity is two registers rather than per-shape RTMRs:

- **MRTD** is recomputed from the release's TDX IGVM image (`tdx_igvm::mrtd_from_igvm`). It is a clean-room implementation of the TDX module's accumulation over `igvm`-parsed directives in file order. Measured page data gets `MEM.PAGE.ADD` plus sixteen 256-byte `MR.EXTEND` records. Unmeasured page data and inserted parameter areas get the add record only. Shared pages are skipped. Directives outside that model (large pages, non-normal page types, VP contexts) are refused rather than guessed at. Verified against the published v0.15.0-rc8 image: it reproduces the manifest's MRTD `5cfedb59…`. The `published_release_mrtd_known_answer` test reruns that check when `TDX_IGVM` / `TDX_IGVM_MRTD` point at a downloaded image. The image is not committed: it is ~9 MB of kernel and initramfs.
- **MRCONFIGID** is `sha256(tinfoil-config.yml bytes) ‖ 16 zero bytes`. A config's `cvm-version` (bare version, optional single `@sha256:<64 hex>` manifest pin) is read by `eidola_common::engine_deployment::parse_cvm_version`, the grammar the gateway's engine-pin check also uses.

`tdx_igvm::release_pin` ties the computation to a release and to the deployment. The config's `cvm-version` must name the manifest's release (`X` ↔ `vX`). When it carries the inline `X@sha256:<hex>` form, that hash must also be the manifest's. Otherwise a pin could combine one release's MRTD with a config that launches another, and it could never attest. The release manifest (`tinfoil-inference-<version>-manifest.json`) must match a pinned SHA-256, and its `igvm.format_version` must be 1. The image must hash to the manifest's `igvm.tdx`. The manifest's `tdx_launch` RTMRs must all be zero, and the recomputed MRTD must equal its `tdx_launch.mrtd`. Any disagreement is an error. The output (`cvm_version`, `igvm_sha256`, `mrtd`, `mrconfigid`) carries no machine policy (MR_SEAM, attributes, TCB floors): those describe the host, not the image.

This tool does not touch `releases/trust/server-enclave.json` or `scripts/artifact-manifest.sh`; the server's own enclave stays on the kernel-cmdline model until it moves to an IGVM release. Engine deployments use it through `measure-engine-enclaves` (below).

## Engine deployments (`measure-engine-enclaves`)

Eidola-hosted inference engines (`eidola-server-engine`) are pinned by the gateway the way the gateway is pinned by clients, one level down: engine image digest → `deploy/engine/<model-id>/<variant>/tinfoil-config.yml` → TDX launch identity → `releases/trust/engine-enclaves.json` → embedded in the gateway build. Engine deployments are Intel TDX on the platform provider's IGVM launch model, so this reuses `tdx_igvm::release_pin` above.

**Layout.** One directory per deployment, `deploy/engine/<model-id>/<variant>/` (both components `[a-z0-9][a-z0-9._-]*`; the variant names a host class, e.g. a GPU shape), holding:

- `tinfoil-config.yml` — deployed and measured exactly like the gateway's. Its `cvm-version` must carry the inline release-manifest pin (`X@sha256:<hex>`), so the config alone names the release it launches on. It uses only the keys an engine deployment needs (the typed mirror's fields, shared with the gateway's build: no `entrypoint`, `command`, extra volumes, networks or shim overrides), runs exactly one container, `eidola-server-engine` pinned by full digest (a companion or a tag would escape the measurement) with `runtime: nvidia` and `gpus: all` for the `cuda` executor, `GATEWAY_TOKEN` as its only secret, and a grant to the one model pack carrying the weights (`repo: <owner>/<name>@<revision>`, `mpk` pinned by root hash, mounted read-only at `/tinfoil/models/<name>`, where `EIDOLA_ENGINE_WEIGHTS_DIR` must point); its shim exposes exactly the node's routes; its VM shape is one the platform launches (`check_vm_resources`). That container's environment is the node's, and nothing else (`env::MEASURED`): model id, weights hash, `verified-readonly` storage, prompt-cache retention, the gateway token's Argon2id hash (the token itself is a secret).
- `deployment.json` — what the pin needs that the config does not determine: `weights` (`repo`, `revision`: where the weight files came from), `expected_gpus` (for the `cuda` executor, equal to the config's top-level `gpus`, which must be 1 or 8 — the shim collects exactly `gpus` evidence items — and absent for `cpu`; `engine_deployment::check_gpu_attestation`, shared with the gateway's build), and `tdx_policy` (a `tinfoil_verifier::TdxPolicy`: MR_SEAM allowlist, attributes, TCB floors, PCK flags — host facts, reviewed rather than derived).

**The file.** `engine-enclaves.json` (`schema_version: 1`): `models` maps each model id to its accepted deployments, each `{config, config_sha256, cvm_version, pin, weights: {sha256, repo, revision}, prompt_cache: {enabled, idle_ttl_secs, max_age_secs}}`. `pin` is exactly `tinfoil_verifier::AllowedMeasurement`'s shape — platform-tagged (`{"platform": {"tdx": {mrtd, mrconfigid, policy}}}`, or `{"sev_snp": {measurement}}`, which stays expressible though nothing measures one here yet) plus optional `expected_gpus` — so the gateway hands it to the verifier unchanged. An empty `models` object is valid and is the committed state while no engine is deployed.

**The engine config is parsed into a typed, deny-unknown-fields mirror of Tinfoil's schema and validated with a port of its validator; widening the allow-list means adding the typed field and its validation together** (`eidola_common::engine_deployment::deployment`; the gateway's `AGENTS.md` lists the ported rules). A pinned deployment runs the `cuda` executor, every allocation-driving size is capped, and its allocations must fit the VM and GPUs (the gateway's `AGENTS.md` → Eidola-hosted engines). Directory names under `deploy/engine/` must satisfy `engine_deployment::is_safe_component`, checked before anything is measured. **One check, shared with the gateway.** `deployment_entry` checks the deployment with `eidola_common::engine_deployment::deployment::check_deployment`, the function the gateway's build runs on every pinned deployment, and builds the entry from what it returns; it adds only the launch identity. **Measuring.** `cargo run -p measure-enclave --bin measure-engine-enclaves -- --release-dir <dir> --output releases/trust/engine-enclaves.json` walks `deploy/engine/*/*` in sorted order and, for each deployment, reads `tinfoil-inference-v<version>-manifest.json` and `tinfoil-tdx-v<version>.igvm` from `<dir>` for the version its config selects, then emits the entry (`engine_enclaves::deployment_entry`; the whole file via `render`, in canonical form). The manifest must hash to the config's inline pin, the image to the manifest's record, and the recomputed MRTD to the manifest's statement; any disagreement is an error. It downloads nothing. Like `just update-manifest` it is release-time work, run when a deployment is added or its config changes, never as a side effect of an unrelated change.

**What checks it, and when.** Every gateway build re-derives every value except MRTD from the committed files and requires every deployment directory to be pinned (`crates/eidola-server-gateway/AGENTS.md` → Eidola-hosted engines), so a hand edit or a stale pin fails the PR's cargo gates. `engine_enclaves::tests::the_committed_file_is_in_canonical_form` holds the committed bytes to this tool's rendering. MRTD needs the release image and is reproduced only by rerunning this tool.

**Open item: deploying from a subdirectory.** Whether the platform provider can deploy a `tinfoil-config.yml` from a path other than the repository root is unconfirmed. The gateway's AGENTS.md (same section) records what each answer means; the layout here does not depend on it, because the committed config is what every pin hashes.

**Proposal: recording engine deployments in `artifact-manifest.json`** (not implemented; the manifest schema is unchanged by this work). Once engines ship as release artifacts, the signed deployment record should carry each engine image's OCI `digest` and each deployment's launch identity alongside the server's enclave block, so a release's full serving set is one signed document. That is a manifest schema rotation and follows `releases/README.md`: first a release whose clients *accept* the new schema with the engine rows tolerated when absent (`SUPPORTED_MANIFEST_SCHEMA_VERSIONS`, `attested_claims`), then a later release that *emits* it (`MANIFEST_SCHEMA_VERSION` in `scripts/artifact-manifest.sh`, with `check-complete` and `check-manifest-determinism.sh` taught the new rows). Until then `engine-enclaves.json` is the record, bound into the gateway's measurement by being compiled into its image.
