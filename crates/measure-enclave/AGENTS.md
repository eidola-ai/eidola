# measure-enclave — Agent Development Guide

The `measure-enclave` binary computes, from public inputs, the launch identity a legitimate deployment of the Eidola server's Tinfoil Container will present: the record `releases/trust/server-enclave.json` holds and every client pins. The server runs on the platform provider's IGVM launch model (cvmimage v0.15+, every release of which is still an `-rc` pre-release): one firmware-less SEV-SNP image per release, no OVMF, no kernel command line chosen at launch, no measured boot after launch. Its SEV-SNP identity is three report fields:

1. **MEASUREMENT**, the launch digest, recomputed from the release's SEV-SNP IGVM image (`snp_igvm::launch_digest_from_igvm`). It is a clean-room implementation of `SNP_LAUNCH_UPDATE`'s `PAGE_INFO` chain over `igvm`-parsed directives in file order: an inserted parameter area is an unmeasured page at its address; page data is a normal page (contents digested; a page with no data is a page of zeros); secrets and CPUID pages contribute type and address only; a 2 MiB zero page is its 512 4 KiB zero pages, ascending; the boot processor's VMSA comes last, at `0xfffffffff000`. Hosts launch with `KVM_SEV_SNP_MEASURE_BSP_ONLY`, so exactly one VMSA (processor 0) is measured, and the processor count and RAM size (both host-supplied through unmeasured parameter pages) are not in the digest. Anything outside that model is refused rather than guessed at: unmeasured or shared page data, another page data type, a 2 MiB page carrying data or misaligned, a parameter area inserted after page data, a page after the VMSA, a VMSA for another processor or at another address, and an ID block (the verifier refuses ID-block launches). Verified against the published images, each reproducing its release manifest's `igvm.snp_launch.measurement`: v0.15.3-rc.1's CPU image (`d712705d…`) and GPU image (`605c0b29…`). `published_release_launch_digest_known_answer` holds both (file name, image SHA-256, digest) and reruns the check for each present in `SNP_IGVM_DIR` (images from `https://images.tinfoil.sh/cvm/<file name>`, not committed); it prints a skip without it. The digest code is also checked against `sev-snp-measure`'s reference vector (`the_digest_matches_the_sev_snp_measure_reference_vector`), with offline unit tests for each page kind, ordering, the 2 MiB expansion and every refusal.
2. **HOST_DATA**, `sha256(tinfoil-config.yml bytes)` (`snp_igvm::host_data`): the host passes it at launch, the firmware copies it into every report, and the guest's boot (`tinfoil/cmd/boot/config.go`, `confighash.go` in cvmimage) refuses to start unless the config it was handed hashes to it. Because the digest is the same for every deployment of an image, HOST_DATA is what makes the identity ours.
3. **POLICY**, the guest policy the image's IGVM initialization header asks for (`0x30133`: firmware ABI ≥ 1.51, SMT allowed, the must-be-one bit; DEBUG and MIGRATE_MA clear). It is not in the digest; the host chooses it at launch, so the verifier pins it.

`snp_igvm::release_pin` ties the computation to a release and to the deployment: the config's `cvm-version` must carry the inline `X@sha256:<hex>` manifest pin (`eidola_common::engine_deployment::parse_cvm_version`, the grammar the engine pins use) and name the release the manifest describes; the manifest must hash to that pin and have `igvm.format_version` 1; the image must hash to the manifest's `igvm.snp`; the recomputed digest must equal the manifest's `igvm.snp_launch.measurement`. The binary also refuses a `+`-tagged (GPU) image: the server attaches no GPUs. Its output is `{cvm_version, igvm_sha256, sev_snp: {measurement, host_data, guest_policy}}`; `sev_snp` is exactly `tinfoil_verifier::SevSnpPin`'s shape. No TDX identity is recorded for the server: it is pinned on SEV-SNP only, and a TDX presentation of it is refused before it is authenticated.

**The measurement flow:** source → deterministic OCI build → server digest → `tinfoil-config.yml` (with digest, and the release-manifest pin) → HOST_DATA (config hash) + launch digest (of the image the pin names) → `releases/trust/server-enclave.json` (`schema_version: 2`) → the cli build embeds it as its trust root → cli OCI digest / desktop `narHash` + `archiveSha256` → `artifact-manifest.json`. The `server-enclave.json` step breaks the otherwise-circular self-reference that would occur if the cli build COPYed the manifest containing its own digest; isolating the enclave fields gives the cli build a stable input while the manifest regenerates. All values are committed and verified by CI (see `.github/AGENTS.md`). Payload / archive vocabulary: `docs/verification.md`.

`scripts/artifact-manifest.sh` (`measure`, `verify-full`, `update`) downloads the release manifest (`https://github.com/tinfoilsh/cvmimage/releases/download/v<X>/tinfoil-inference-v<X>-manifest.json`) and the SEV-SNP image (`https://images.tinfoil.sh/cvm/tinfoil-snp-v<X>.igvm`) into `~/.cache/eidola/cvm/<X>/`, each verified against its pin before use (the manifest against the config's inline pin, the only pin there is; the image against the manifest); cache hits are re-hashed, not trusted. `--verify-attestations` (used by CI) additionally requires both files to carry a Sigstore build-provenance attestation from `tinfoilsh/cvmimage`'s `release.yml` at `refs/tags/v<X>` on a GitHub-hosted runner, failing hard otherwise. The tag workflow then cross-checks the recorded enclave against the provider's own measurer (`cvmc measure`, attested the same way) and the provider's statements of the digest and policy (`.github/AGENTS.md` → Releases).

Because the config hash is HOST_DATA, **any change to `tinfoil-config.yml` produces a different server identity** — regeneration is `just update-manifest` (release time only; see the top-level AGENTS.md conventions). Changing `cvm-version` also moves the launch digest, which needs the new release's image and is reproduced only by rerunning the measurement.

## TDX launch identity, IGVM model (`measure-tdx-igvm`)

A second binary in this crate emits the launch half of a verifier TDX pin (`tinfoil_verifier::TdxPin`) for the platform provider's IGVM launch model (cvmimage v0.15+, every release of which is still an `-rc` pre-release). That model has no OVMF and no measured boot after launch, so its TDX identity is two registers rather than per-shape RTMRs. Each release publishes two TDX images with different MRTDs, the CPU image (`tinfoil-tdx-v<X>.igvm`, manifest `tinfoil-inference-v<X>-manifest.json`) and the GPU image (`v<X>+gpu`, the same names with `+gpu` after the version); a `cuda` deployment names the GPU one (`cvm-version: X+gpu@sha256:<its manifest>`), and the tool reads whichever the config names:

- **MRTD** is recomputed from the release's TDX IGVM image (`tdx_igvm::mrtd_from_igvm`). It is a clean-room implementation of the TDX module's accumulation over `igvm`-parsed directives in file order. Measured page data gets `MEM.PAGE.ADD` plus sixteen 256-byte `MR.EXTEND` records. Unmeasured page data and inserted parameter areas get the add record only. Shared pages are skipped. A 2 MiB zero page (the `is_2mb_page` flag, no data) is the 512 4 KiB zero pages it holds, in ascending order: cvmimage's image compiler (`cvmc`, `compiler/src/image.rs`: `zero_run`, `zero_directive`) emits every 2 MiB-aligned run of zero pages that way and documents that a loader measures it as those pages; a misaligned one, or one carrying data (which the `igvm` parser reads only 4 KiB of), is refused. Other directives outside that model (non-normal page types, VP contexts) are refused rather than guessed at. Verified against three published images, each reproducing its manifest's MRTD: v0.15.0-rc8 (`5cfedb59…`), and v0.15.3-rc.1's CPU (`cc56391d…`) and GPU (`bf582997…`) images, the first releases with 2 MiB zero pages. The `published_release_mrtd_known_answer` test holds those three (file name, image SHA-256, MRTD) and reruns the check for each present in `TDX_IGVM_DIR` (or for any one image named by `TDX_IGVM` with `TDX_IGVM_MRTD`); it prints a skip without them. The images are not committed: each is ~9 MB of kernel and initramfs, from `https://images.tinfoil.sh/cvm/<file name>`. The 2 MiB expansion has offline unit tests (`a_2mb_zero_page_is_its_512_zero_pages`, `a_2mb_page_with_data_or_misaligned_is_refused`).
- **MRCONFIGID** is `sha256(tinfoil-config.yml bytes) ‖ 16 zero bytes`. A config's `cvm-version` (bare version, optional single `@sha256:<64 hex>` manifest pin) is read by `eidola_common::engine_deployment::parse_cvm_version`, the grammar the gateway's engine-pin check also uses.

`tdx_igvm::release_pin` ties the computation to a release and to the deployment. The config's `cvm-version` must name the manifest's release (`X` ↔ `vX`). When it carries the inline `X@sha256:<hex>` form, that hash must also be the manifest's. Otherwise a pin could combine one release's MRTD with a config that launches another, and it could never attest. The release manifest (`tinfoil-inference-<version>-manifest.json`) must match a pinned SHA-256, and its `igvm.format_version` must be 1. The image must hash to the manifest's `igvm.tdx`. The manifest's `tdx_launch` RTMRs must all be zero, and the recomputed MRTD must equal its `tdx_launch.mrtd`. Any disagreement is an error. The output (`cvm_version`, `igvm_sha256`, `mrtd`, `mrconfigid`) carries no machine policy (MR_SEAM, attributes, TCB floors): those describe the host, not the image.

This tool does not touch `releases/trust/server-enclave.json` or `scripts/artifact-manifest.sh` (the server is SEV-SNP, measured by the main binary above). Engine deployments use it through `measure-engine-enclaves` (below).

## Engine deployments (`measure-engine-enclaves`)

Eidola-hosted inference engines (`eidola-server-engine`) are pinned by the gateway the way the gateway is pinned by clients, one level down: engine image digest → `deploy/engine/<name>/<variant>/tinfoil-config.yml` → TDX launch identity → `releases/trust/engine-enclaves.json` → embedded in the gateway build. Engine deployments are Intel TDX on the platform provider's IGVM launch model, so this reuses `tdx_igvm::release_pin` above.

**Layout.** One directory per deployment, `deploy/engine/<name>/<variant>/` (both components `[a-z0-9][a-z0-9._-]*`; `<name>` is a label for people, the variant names a host class, e.g. a GPU shape; a deployment is identified by the weights hash it serves, never by its path), holding:

- `tinfoil-config.yml` — deployed and measured exactly like the gateway's. Its `cvm-version` must carry the inline release-manifest pin and name the release's GPU image (`X+gpu@sha256:<hex>`; `engine_deployment::check_cvm_image`), so the config alone names the image it launches on. It uses only the keys an engine deployment needs (the typed mirror's fields, shared with the gateway's build: no `entrypoint`, `command`, extra volumes, networks or shim overrides), runs exactly one container, `eidola-server-engine` pinned by full digest (a companion or a tag would escape the measurement) with `runtime: nvidia` and `gpus: all` for the `cuda` executor, `GATEWAY_TOKEN` as its only secret, and a grant to the one model pack carrying the weights (`repo: <owner>/<name>@<revision>`, `mpk` pinned by root hash, mounted read-only at `/tinfoil/models/<name>`, where `EIDOLA_ENGINE_WEIGHTS_DIR` must point); its shim exposes exactly the node's routes; its VM shape is one the platform launches (`check_vm_resources`). That container's environment is the node's, and nothing else (`env::MEASURED`): model id (which must equal the weights hash: a pinned node is named by the weights it serves), weights hash, `verified-readonly` storage, `EIDOLA_ENGINE_GPU_CC=required` (the node's own check of its GPUs' confidential-computing mode), prompt-cache retention, the gateway token's Argon2id hash (the token itself is a secret).
- `deployment.json` — what the pin needs that the config does not determine: `architecture` (an implemented `eidola_common::architecture::Architecture` name, e.g. `MimoV26Flash`; its shape drives the resource checks and its MTP layers bound the draft width, and a stub such as `MimoV26Pro` is refused), `weights` (`repo`, `revision`: where the weight files came from), `expected_gpus` (for the `cuda` executor, equal to the config's top-level `gpus`, from 1 to 8 — the shim collects exactly `gpus` evidence items — and absent for `cpu`; `engine_deployment::check_gpu_attestation`, shared with the gateway's build), and `tdx`, the machines: `platform_endorsements` (`release`, a `platform-vX.Y.Z` tag; `sha256`, the hash of that release's endorsements file; `policy`, one of its policy names) and the three PCK flags `dynamic_platform`, `cached_keys`, `smt_enabled`, which the endorsements do not carry. The machine policy itself is never written here: it is derived from the signed endorsements (Platform endorsements, below). The file is read with a typed parse (`engine_deployment::check_deployment`, shared with the gateway's build) that refuses unknown and repeated members at every level, the policy's included, and `null` for an optional member.

**The file.** `engine-enclaves.json` (`schema_version: 1`): `models` maps each model's weights hash to its accepted deployments, each `{config, config_sha256, cvm_version, pin, weights: {sha256, repo, revision}, prompt_cache: {enabled, idle_ttl_secs, max_age_secs}}`. `pin` is exactly `tinfoil_verifier::AllowedMeasurement`'s shape — platform-tagged (`{"platform": {"tdx": {mrtd, mrconfigid, policy}}}`, or `{"sev_snp": {measurement, host_data, guest_policy}}` with `host_data` the config's hash, which stays expressible though no engine deployment is SEV-SNP) plus optional `expected_gpus` — so the gateway hands it to the verifier unchanged. An empty `models` object is valid and is the committed state while no engine is deployed.

**The engine config is parsed into a typed, deny-unknown-fields mirror of Tinfoil's schema and validated with a port of its validator; widening the allow-list means adding the typed field and its validation together** (`eidola_common::engine_deployment::deployment`; the gateway's `AGENTS.md` lists the ported rules). A pinned deployment runs the `cuda` executor, every allocation-driving size is capped, and its allocations must fit the VM and GPUs (the gateway's `AGENTS.md` → Eidola-hosted engines). Directory names under `deploy/engine/` must satisfy `engine_deployment::is_safe_component`, checked before anything is measured. **One check, shared with the gateway.** `deployment_entry` checks the deployment with `eidola_common::engine_deployment::deployment::check_deployment`, the function the gateway's build runs on every pinned deployment, and builds the entry from what it returns; it adds only the launch identity. The pin is built as the attesting client's own `tinfoil_verifier::AllowedMeasurement` (`tinfoil-verifier` is a dependency of this release-time tool, never shipped) and compiled by `tinfoil_verifier::validate_pins`, the pin compiler the gateway's build and the client run, so a pin the client would refuse fails before the file is rendered; a sidecar naming a policy the release does not define, a hash that is not the vendored file's, a release that is not vendored, a malformed tag, or a policy member written by hand is refused there too (`a_deployment_that_cannot_be_measured_is_refused`). `render` groups the entries by the weights hash each serves and holds each group to `deployment::check_model_agreement` (every deployment serves that hash, with one provenance — repo, revision — one architecture and one prompt-cache policy), the per-model rule the gateway's build runs over the pinned file, so the tool never renders a file that build refuses (`the_variants_of_a_model_agree`). **Measuring.** `cargo run -p measure-enclave --bin measure-engine-enclaves -- --release-dir <dir> --output releases/trust/engine-enclaves.json` walks `deploy/engine/*/*` in sorted order and, for each deployment, reads `tinfoil-inference-v<version>-manifest.json` and `tinfoil-tdx-v<version>.igvm` from `<dir>` for the version its config selects, then emits the entry (`engine_enclaves::deployment_entry`; the whole file via `render`, in canonical form). The manifest must hash to the config's inline pin, the image to the manifest's record, and the recomputed MRTD to the manifest's statement; any disagreement is an error. It downloads nothing. Like `just update-manifest` it is release-time work, run when a deployment is added or its config changes, never as a side effect of an unrelated change.

**Platform endorsements (`platform_endorsements`, `vendor-platform-endorsements`).** A TDX pin's machine policy (MR_SEAM, TD_ATTRIBUTES, XFAM, TEE_TCB_SVN floor, QE vendor, collateral floor) and its `ppids` allowlist are derived from the platform provider's Sigstore-signed platform endorsements, never hand-written. A release is vendored at `releases/trust/platform-endorsements/<tag>/`: `platform-endorsements.json` (the release asset, verbatim) and `attestation.sigstore.json` (the GitHub artifact attestation's Sigstore bundle, as GitHub serves it). `platform_endorsements::tdx_policy` reads both and `releases/trust/sigstore-trusted-root.json`, verifies them offline with `tinfoil_verifier::platform_endorsements::verify` (the release workflow at exactly the sidecar's tag, the file's hash the sidecar's; `crates/tinfoil-verifier/AGENTS.md` → Platform endorsements), and derives the named policy with every machine mapped to it; the gateway's build makes the same two calls over the same committed bytes. Nothing in a build or a measurement reads the network. **Updating** is the maintainer's `just engine-platform-endorsements <tag>` (`scripts/engine-platform-endorsements.sh`): it downloads the release asset and GitHub's `attestations/sha256:<digest>` response into a fresh temporary directory as untrusted data and runs the `vendor-platform-endorsements` binary, which keeps the one bundle that verifies as that tag (a byte-identical file re-released under another tag carries that tag's bundle too, refused here; of two bundles for the tag, the first logged), writes the two files, reads them back and verifies them again, and prints the hash and the TDX policies with their machine counts. The output is a reviewable diff; a deployment adopts it by naming the new tag and hash in its `deployment.json`. `.github/workflows/platform-endorsements-drift.yml` reports, on a schedule, a provider release newer than the newest vendored one or than one a deployment names. Tests (`platform_endorsements::tests`) run over the real vendored `platform-v0.1.11`: it verifies and derives `tdx-b300-prod` exactly; real negatives from `tests/fixtures/platform-endorsements/` (an authentic attestation of the byte-identical file under `platform-v0.1.10`; a genuine attestation from `tinfoilsh/confidential-model-router`; that release's Rekor entry swapped in) and tampering (the file with its recorded hash moved, the signature, payload, SET, inclusion proof, certificate, log body and log index) are each refused. Two checks are defense in depth that no genuine input can reach alone, and were checked by removal to be covered only together with the check before them: the predicate-equals-file comparison (behind the subject digest) and the leaf-validity window on `integratedTime` (behind the Rekor entry-body binding).

**What checks it, and when.** Every gateway build re-derives every value except MRTD from the committed files and requires every deployment directory to be pinned (`crates/eidola-server-gateway/AGENTS.md` → Eidola-hosted engines), so a hand edit or a stale pin fails the PR's cargo gates. `engine_enclaves::tests::the_committed_file_is_in_canonical_form` holds the committed bytes to this tool's rendering. MRTD needs the release image and is reproduced only by rerunning this tool.

**Open item: deploying from a subdirectory.** Whether the platform provider can deploy a `tinfoil-config.yml` from a path other than the repository root is unconfirmed. The gateway's AGENTS.md (same section) records what each answer means; the layout here does not depend on it, because the committed config is what every pin hashes.

**Recording engines in `artifact-manifest.json`.** The engine *image* is an artifact row from manifest schema 4 (`eidola-server-engine`, `type: "oci"`): clients accept schema 4 with the row tolerated absent below it, and `scripts/artifact-manifest.sh` composes it (from CI's `oci-engine` build) once it emits 4 (`releases/README.md`). **Proposal, not implemented:** each deployment's launch identity alongside the server's enclave block, so a release's full serving set is one signed document; that is a further rotation, by the same accept-before-emit rule. Until then `engine-enclaves.json` is the record of the deployments, bound into the gateway's measurement by being compiled into its image. **Ordering at release time:** an engine config pins the image digest and the gateway compiles the configs in, so a new engine image is built first (`oci-engine`, or `just engine-image` locally), its digest written into each `deploy/engine/**/tinfoil-config.yml` that runs it, the deployments re-measured here, and only then the gateway built; nothing automates the stamping yet, since no deployment exists.
