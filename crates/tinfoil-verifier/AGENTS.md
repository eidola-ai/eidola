# tinfoil-verifier — Agent Development Guide

Exposes `attesting_client()`, a `reqwest::Client` that re-verifies enclave attestation on every new TCP+TLS handshake, and `pipe`, the same verification over a byte stream someone else dialed (below). Construction performs no network I/O and there is no verified-fingerprint cache: the first real request is the first attestation, every subsequent new connection re-attests independently, and policy changes take effect on the next handshake. Callers wanting startup readiness issue a trivial request immediately after construction.

## One check, two transports

**What is verified lives in one place: `attest.rs`, `AttestationCheck::attest_stream(io, peer_cert_der, now)`.** Both transports build their check from the same `AttestingClientConfig` (`AttestationCheck::from_config`: pins compiled, host derived from the base URL, the built-in Intel root) and the same TLS configuration (`attest::tls_config`: the caller's roots, ALPN pinned to HTTP/1.1), and both drive `attest_stream`; neither has a check of its own. A transport supplies only what it alone has: the stream after its TLS handshake (any tokio `AsyncRead + AsyncWrite`), the leaf certificate that handshake landed on, and the time. **The core never reads a clock** — `now` (Unix seconds) is a parameter, read by the transport just before the exchange — so it runs where `std` has none. Each transport bounds the exchange with `ATTESTATION_DEADLINE` on its own timer.

- **Native connector** (`attesting_client.rs`, not on wasm32): `AttestingConnectorLayer` wraps reqwest's connector; the peer certificate comes from reqwest's `TlsInfo`, the clock from `sevsnp_crl::unix_now`, the deadline from tokio.
- **Byte pipe** (`pipe.rs`, every target): a `Dialer` (implemented by whatever embeds the client — the mobile app's bridge to its shell's socket, or `TcpDialer` natively) opens a raw stream; this crate runs TLS over it (`tokio-rustls`, the process's rustls provider) and, through `AttestingPipe::handshake` → `Handshaken::attest(now)`, the check — the stream is released only by `attest`, so an attested endpoint cannot be reached unattested. `TlsPipe` is plain TLS to the caller's roots for endpoints that carry no attestation. The host moves ciphertext and decides nothing. Nothing in `pipe` keeps time, spawns, or frames application HTTP: the caller does (app-core's `transport::pipe`). The `Dialer` is `Send + Sync` everywhere; on wasm32 the futures and streams it returns need not be `Send` (`pipe::MaybeSend`, `pipe::BoxFuture`). Dial and handshake failures are `Error::Connect`.

`tests/pipe.rs` runs both transports against in-process `tinfoil-shim-mock`s over a `TcpDialer` and requires them to agree: a pinned enclave is attested and the stream then carries the application request through the shim; an unpinned measurement (`MeasurementMismatch`), a document endorsing another TLS key (`FingerprintMismatch`, the shim's `Misbinding::TlsKey`) and a report whose `REPORT_DATA` commits to another nonce (`ReportDataMismatch`, `Misbinding::ReportData`) are refused by each; a peer outside the TLS roots is refused at the handshake, before anything is attested.

## Per-handshake flow

After each TLS handshake the check generates a random 32-byte nonce and sends `GET /.well-known/tinfoil-attestation?nonce=<hex>` over the **same** HTTP/1.1 connection that will carry application traffic. Tinfoil's self-contained v3 envelope carries a fresh CPU quote, two base64-encoded endorsed sections, and vendor-signed collateral.

`bundle.rs` mirrors Tinfoil's strict envelope contract:

1. Reject unknown or duplicate JSON members recursively; require lowercase fixed-width hex, canonical standard base64, and unique item/collateral IDs. Require `collateral_format` to be the v3 collateral profile (see [Collateral](#collateral)). Identify the platform from `cpu_evidence.format` as soon as the envelope's own JSON is parsed. If the caller pinned no entry for that platform, refuse with `Error::PlatformNotPinned` before any section is decoded or any platform payload (CPU report, vendor collateral) is read (`bundle::parse_document_for`). An SEV-SNP-only client never runs the TDX parsers.
2. Hash the exact base64-decoded `crypto_material` and `device_evidence` bytes — never a re-serialization — and compare both hashes with `cpu_evidence.endorsed`.
3. Recompute `REPORT_DATA[0:32] = SHA-256("https://tinfoil.sh/report-data/v1" ‖ nonce ‖ crypto_material_hash ‖ device_evidence_hash)` with the remaining 32 bytes zero; compare it with `challenge.report_data`.
4. Require conventional `tls` (SPKI SHA-256) and `hpke` (X25519) crypto items, then compare the TLS fingerprint with the peer certificate from the completed handshake.
5. Select the caller's pinned entries for the evidence's platform. With none, refuse (`Error::PlatformNotPinned`, re-checking the gate from step 1) before the evidence is authenticated — see [Pins](#pins-are-platform-tagged).
6. For SEV-SNP, require the report to be exactly 1184 bytes and pass field hygiene (`sevsnp::check_report_hygiene`): version ≥ 3, guest policy with DEBUG and MIGRATE_MA off, VCEK-signed (`SIGNING_KEY=0`) with `MASK_CHIP_KEY` clear, no ID-block launch (and so GUEST_SVN, FAMILY_ID and IMAGE_ID zero, which only an ID block sets), and requested from VMPL 0. The guest policy is **not** part of the launch measurement — a relaunch of the pinned image with DEBUG=1 keeps the same measurement while giving the hypervisor `SNP_DBG_DECRYPT` access — so it is policed here and again, whole, against the pin (step 8).
7. Require CPU-subject `amd-vcek/v1` and `amd-crl/v1` endorsement collateral. Read the processor generation from the report's signed CPUID (`SevSnpGeneration::of_report`; see [SEV-SNP processor generations](#sev-snp-processor-generations)). Decode exactly ASK then ARK from the carried KDS chain and require byte identity with that generation's built-in AMD chain (or the explicit override chain), verify ARK → ASK → VCEK and the report signature, then bind the report to that VCEK: its `reported_tcb` must equal the SPL extensions of the VCEK certificate and its `CHIP_ID` the hwID extension (unless masked to zero), as `go-sev-guest` does. A VCEK is issued per chip and per TCB, and the certificate is collateral the document's author chooses, so without this a key leaked from an old TCB signs a report claiming a patched one and every floor below is enforced against the attacker's number. The KDS writes hwID untagged; a tagged OCTET STRING is tolerated. Tests: `vcek_binding_*` and the Turin cases in `sevsnp.rs`, on synthetic certificates (the Genoa ASK with replaced extensions). Every attestation source must therefore endorse its VCEK for the TCB and chip its reports claim; `tinfoil-shim-mock` does so in `vcek_binding_extensions`, and `mock_attesting_client_e2e` (env-gated, `MOCK_URL` + `MOCK_CERT_DIR`) is the check that it still does. Then verify the carried CRL entirely offline. It must be a complete direct v2 CRL (not delta, indirect, or scope-restricted), carry a CRL number and an AKI matching the pinned ARK's SKI, use exact supported signature parameters, contain no unsupported critical extensions, satisfy `thisUpdate <= now < nextUpdate`, and omit both ASK/VCEK serials. Authenticity comes from AMD's ARK signature, not the relay. A malicious relay can replay an older AMD-signed CRL only for the remainder of its signed validity interval; the verifier deliberately makes no AMD KDS request.
8. Enforce the SEV-SNP rollback/floor policy of the report's generation (`SevSnpTcbFloors`); select the entries whose launch digest **and HOST_DATA** both equal the report's (`appraise_snp_launch`: in the IGVM launch model the digest is a function of the image alone, the same for every deployment of a release, so HOST_DATA — the deployment config's SHA-256, which the guest checks against its config before booting — is what makes the match ours; neither alone selects); require the report's raw POLICY to equal the matched entry's `guest_policy` in every bit except the firmware ABI minimum (bits 0-15), which may be higher (`sevsnp::check_guest_policy`); require the SHA-256 of any config bytes a `tinfoil-config` collateral entry carries to equal HOST_DATA (on TDX, MRCONFIGID; `check_carried_config`); require the hardware report's signed `REPORT_DATA` to equal the recomputed envelope value; and finally apply the matched entry's device-evidence requirement. Tests: `sev_snp_launches_are_selected_by_digest_and_config_then_held_to_the_policy` (another config, a zero HOST_DATA, another image, DEBUG, MIGRATE_MA, CXL, an older ABI: each refused), `sev_snp_entries_sharing_a_launch_identity_are_alternatives_by_policy`, `the_guest_policy_must_equal_the_pin_but_for_a_higher_abi_minimum`, `hygiene_rejects_id_block_fields_and_lower_vmpls`.

For TDX, steps 6–8 are [the TDX path](#tdx-path) instead; steps 1–5, the carried-config check and the `REPORT_DATA` comparison are shared.

### Collateral

The envelope's `collateral_format` names the profile of its `collateral` array, which is also the verification policy Tinfoil's own SDKs (`tinfoil-go`'s `verify/document`, `tinfoil-js`'s `packages/verifier`) apply to it: `https://tinfoil.sh/predicate/attestation-collaterals/v2`, or the member absent, is the legacy profile (release provenance as `sigstore-code/v1` plus `sigstore-freshness/v1` witnesses); `…/v3` is the config profile (an `igvm-runtime/v1` runtime manifest, `sigstore-platform/v1` platform endorsements, `artifact-freshness/v1` approvals, an optional `tinfoil-config` entry). The pinned platform release's shim (cvmimage `0.15.4-rc.2`, `internal/attestationmaterial`, byte-identical to `0.15.3-rc.1`'s, as is `internal/attestation`, and linking the same `tinfoil-go`) accepts only a v3 response from the provider's collateral service and serves its format verbatim, so **only v3 is accepted**: absent, v2 or anything else is refused (`bundle::tests::collateral_format_must_be_the_v3_profile`). The entries themselves are assembled by that service, outside the pin; the release only shape-checks them.

Under v3, `bundle::decode_reference_values` decodes the reference-values entries as Tinfoil's v3 decoder (`collateral.Decode` and `decodeCollateral`, `tinfoil-go` v0.17.0-rc.7, which the release links) does, with this crate's strictness (every member required, unknown ones refused): every entry's `data` is a JSON object; the reserved IDs `runtime`, `runtime-freshness`, `platform-freshness` and `tinfoil-config` go with exactly their formats and the `reference-values` role; `sigstore-code/v1` and `sigstore-freshness/v1` are refused as legacy; an entry of a format this crate does not know is held to the entry shape and not read (`legacy_entries_are_refused_and_unknown_formats_only_shape_checked`). What each known entry states that can be checked is checked:

| Entry | Holds | Checked |
|---|---|---|
| `runtime`, `igvm-runtime/v1` | the release manifest the config's `cvm-version` pins: `repo`, `tag`, `digest`, `manifest_base64`, `sigstore_bundle` | repo `tinfoilsh/cvmimage`; tag a full `v`-prefixed semver, as Go's `x/mod/semver` writes it out; the manifest hashes to `digest`; the bundle is an object |
| `platform`, `sigstore-platform/v1` | a platform endorsements release: `repo`, `tag`, `digest`, `sigstore_bundle` | digest 32-byte lowercase hex; the bundle is an object |
| `runtime-freshness` / `platform-freshness`, `artifact-freshness/v1` | the provider's signed approval of that release: `sigstore_bundle` | the bundle is an object |
| `tinfoil-config`, `config/v1` / `config-endorsement/v1` / `v2` | the deployment config's exact bytes (`config_base64`; required but in `v2`), with a `sha256:` `endorsement_ref` and `sigstore_bundle` for the endorsement formats and an `issuer_certificate_der` in `v2` only | each format's member rules (`config_collateral_follows_its_format`); the bytes' SHA-256 must equal the authenticated report's config hash (step 8) |

**None of these is a trust input**, and no Sigstore bundle in them is verified: a pin names the launch identity directly, from this tree's own measurement of the release, so Tinfoil's provenance and freshness path is not consulted, and nothing in the collateral is covered by `REPORT_DATA`. The runtime manifest's contents and the platform endorsements' tag are not read. No committed deployment sets `security.include-config-in-attestation` or uses a registry config, so their documents carry no `tinfoil-config` entry. Engine documents are assembled by the same shim code and so carry the same profile, a TDX one with `intel-pcs/v1` in place of the AMD entries, and a runtime tag read from the config's `cvm-version` (`v…+gpu` for a GPU deployment, which the semver rule admits as build metadata); no engine deployment runs yet, so that shape is read from the source, not observed. The CPU endorsement entries (`amd-vcek/v1`, `amd-crl/v1`, `intel-pcs/v1`) are the same in both profiles and read per platform as steps 7 and [the TDX path](#tdx-path) describe.

**Fixture.** `tests/fixtures/tinfoil-gateway/` is a document from a test deployment of the gateway on platform release v0.15.3-rc.1 (provenance in its README), with its TLS certificate and config, and `expected.json`, the record made at capture: the release and its manifest's SHA-256, the nonce, the capture time, and the SEV-SNP launch identity (launch digest, HOST_DATA, guest policy). **A fixture never depends on a deployment or on the tree's current pins**: `attest::tests::a_captured_gateway_document_verifies_against_its_recorded_launch` runs the document through the whole handshake verifier at its capture time against the recorded identity, so a release bump or a config change moves no fixture and needs no recapture. `the_gateway_capture_record_is_the_release_it_names` holds the record to the fixture's own bytes (the document's runtime entry carries the release manifest, which must be the recorded release, hash to the recorded pin and state the recorded launch digest; the recorded HOST_DATA is the fixture config's hash) and requires the release to be a row of the rebuilt-releases table in `docs/contributing/rebuilding-platform-images.md`. The `bundle::tests` mutate the document entry by entry; a document shape a later release introduces is tested by mutating this one, and the capture stays the real-world fixture. The env-gated `live_gateway_matches_its_release_pin` (`LIVE_GATEWAY_ORIGIN`) is what runs a deployed gateway against the current `server-enclave.json`.

### SEV-SNP processor generations

Two AMD EPYC generations are accepted, Genoa and Turin, each with its own ARK and ASK, both the `sev` crate's built-ins (`builtin::genoa`, `builtin::turin`; `sevsnp::tests::the_builtin_chains_are_amds_genoa_and_turin_certificates` pins each certificate's SHA-256, and the Turin pair is byte-identical to the one `go-sev-guest` embeds from AMD's KDS). **The chain is the one the report names, never found by trying each**: `SevSnpGeneration::of_report` reads the CPUID family and model from the signed report body through the `sev` crate's own `Generation::identify_cpu`, the mapping its parser used to choose the report's TCB_VERSION layout, so the chain, the layout and the floor all follow one field. Any other generation (Milan, Venice, unknown) is refused, as is a report whose parsed TCB layout contradicts its CPUID: an FMC byte on Turin only, and a bootloader and microcode SVN on both, since Venice's layout drops them (the `sev` crate reads them as `Option` from 9.0, and `SevSnpTcbSvns` is `TryFrom` its `TcbVersion`, refusing one without them, so no floor or binding is ever held to a missing SVN). A version-2 report has no CPUID fields and is refused by hygiene on every generation (step 6), so the `sev` crate's CHIP_ID-shape guess for v2 reports is never reached. `attest::tests::sev_snp_chain_is_the_one_the_reports_generation_names`: a Turin report carrying the Genoa chain, and the reverse, are refused at the chain.

What the generation fixes besides the chain:

- **TCB layout and FMC.** Turin's TCB_VERSION is `[fmc, bl, tee, snp, 0, 0, 0, ucode]` (Genoa's `[bl, tee, 0, 0, 0, 0, snp, ucode]`). A Turin VCEK must carry the fmcSPL extension (`1.3.6.1.4.1.3704.1.3.9`), compared with the report's FMC like the other four; a Genoa VCEK carrying one is refused. The rollback rule and the floor cover FMC.
- **Chip identity.** The hwID extension is 64 bytes on Genoa and 8 on Turin; any other length is refused. CHIP_ID is always compared whole, as the hwID followed by zeros (how Turin firmware writes it, and how the provider's endorsements list Turin chips), so a Turin CHIP_ID whose trailing 56 bytes are not zero is refused. Only a wholly zero CHIP_ID is treated as masked, on either generation.
- **Floors.** SVNs are numbered per generation, so `SevSnpTcbFloors` holds one `SevSnpTcbPolicy` each. The defaults (`SevSnpTcbPolicy::genoa`, `::turin`) are the `minimum_tcb` of the provider's `amd-genoa-prod` and `amd-turin-prod` SEV-SNP policies in the vendored signed endorsements, copied by hand: this crate does not read the endorsements' SEV-SNP blocks. Every consumer passes `snp_min_tcb: None`.

**Override.** `trusted_ark_der` / `trusted_ask_der` (app-core's `hardware_root_ca` / `hardware_intermediate_ca`, the mock shim's chain) replace the built-in certificate for every report, whatever generation it names: an override is one chain, never one added beside AMD's two, and AMD's own chain is refused while it is set. The generation still fixes the layout, the binding and the floor. No local-database change: each column still holds one certificate.

**Fixtures.** No genuine Turin report or VCEK is in the tree (the provider's conformance vectors carry no licence), so every Turin case runs on constructed reports and unsigned synthetic VCEKs (`sevsnp::tests` module doc). That a genuine Turin VCEK carries exactly the extensions assumed (fmcSPL at `.3.9`, an 8-byte hwID) follows `snpguest`'s reading of AMD's KDS and is not observed here; nor is a Turin CRL. `tinfoil-shim-mock` emits Genoa reports only.

Parsing and challenge checking alone authenticate nothing. Only the signed hardware report makes the endorsed sections trustworthy. There is no document-level ECDSA signature in v3 and no ATC, AMD KDS, or Intel PCS network fallback. Collateral is untrusted transport authenticated by vendor signatures.

## Pins are platform-tagged

`AttestingClientConfig::allowed_measurements` is a list of `AllowedMeasurement`, each naming one platform (`PlatformMeasurement::SevSnp` or `::Tdx`) plus an optional `expected_gpus`. **Acceptance is pin-driven, never document-driven**: the document's `cpu_evidence.format` picks the platform, the verifier consults only entries of that platform, and a platform with no entry is refused before its evidence is touched. A document author cannot select a softer branch than the caller pinned — the attack an entry carrying both platforms would open. Pins are validated and decoded once in `attesting_client()` (`measurement::compile_pins`, `Error::InvalidPin`), and `validate_pins` runs the same compilation without building a client, for a consumer that refuses bad pins where they are authored (the gateway's build checks its engine pins with it, and `measure-enclave` every engine pin it emits); a TDX pin whose `td_attributes` allows DEBUG or lacks `SEPT_VE_DISABLE`, or that lists no machine in `ppids`, is refused there.

A SEV-SNP pin (`SevSnpPin`, IGVM launch model) is `{measurement, host_data, guest_policy}`, every member required and nothing else accepted; `compile_pins` refuses a malformed width, a policy spelled any way but `0x` + lowercase hex with no leading zeros, and a policy with DEBUG or MIGRATE_MA set or the must-be-one bit 17 clear (`compile_rejects_malformed_and_unsafe_sev_snp_pins`). App-core's client → gateway connection pins the gateway's record (`releases/trust/server-enclave.json`'s one platform block, `sev_snp` as deployed today, or `tdx`) and nothing else, so it accepts only the TEE its release names, by construction. **Not pinned on SEV-SNP:** the machine. PLATFORM_INFO (SMT, TSME, ciphertext hiding, alias check), the launch TCB and firmware build/API floors, and which chips (CHIP_ID) may serve are not appraised; the TCB floor is the operator's `SevSnpTcbPolicy`, and any genuine Genoa or Turin chip at or above its generation's floor is accepted. The provider's signed platform endorsements carry SEV-SNP policies and chip allowlists that this crate does not read yet (Platform endorsements, below). The gateway's engine pins (`releases/trust/engine-enclaves.json`) are stored in `AllowedMeasurement`'s own serde shape, each on the TEE its deployment names (the committed ones TDX), so the client its engine router builds for each upstream, over that upstream's model's pins, accepts only the TEEs those pins name, by the same construction; an SEV-SNP engine pin is the gateway's shape, held to the same SEV-SNP path and default floors. Entries sharing a launch identity are alternatives: the first whose policy and device requirement both hold is the match (`first_passing`).

## TDX path

Only the IGVM launch model (Tinfoil CVM v0.15+, pre-release at Tinfoil so far) is accepted; the legacy kernel-cmdline RTMR1/RTMR2 model is accepted nowhere. `tdx.rs` has two steps that cannot be applied apart:

1. **`authenticate`** — `dcap-qvl` (`=0.7.1`, RustCrypto backend, `default-features = false`) verifies the v4 quote offline at the handshake's wall-clock time: PCK chain (the one embedded in the quote, certification data type 5) to the built-in Intel SGX root with the PCK and root CA CRLs (`UnknownStatusPolicy::Deny`), TCB Info and QE Identity signatures (each signing certificate issued directly by the root) and issue/next-update windows, QE report signature and attestation-key binding, quote signature, and platform/QE/TDX-module TCB matching. Around it: only v4 TDX quotes, reserved header bytes zero, nothing but zero padding after the signature data, and each CRL's `thisUpdate <= now < nextUpdate` (the library checks only `nextUpdate`). Collateral is `intel-pcs/v1`: captured Intel PCS responses (`url`, `headers`, `body_base64`). Each response is classified by exact Intel host + path into one of four resources (PCK CRL, TCB Info, QE Identity, root CA CRL); each must appear exactly once, and anything else is refused. Issuer chains come from the percent-encoded headers. The `tcbInfo` / `enclaveIdentity` members are taken as the exact served bytes (`serde_json` `raw_value`), never re-serialized, because Intel signs those bytes. The URL only classifies; nothing in it is trusted.
2. **`appraise`** against the selected `CompiledTdxPin`: MRTD and MRCONFIGID (selection), RTMR0–3 all zero, MROWNER/MROWNERCONFIG zero, MR_SERVICETD zero (the launch is an unbound TD; a pin that ever needs a service-TD binding gets an explicit policy field then), exact TD_ATTRIBUTES and XFAM, MR_SEAM in the allowlist, TEE_TCB_SVN component-wise at or above the floor, QE vendor id, platform/QE/merged TCB status all `UpToDate` (matching Tinfoil's own verifier), `tcbEvaluationDataNumber` of the TCB Info and of the QE Identity each at or above the floor (the TCB Info number is read from the bytes its Intel signature covered; the refusal names the stale document), the machine's PPID in the pin's allowlist, and the three PCK platform flags equal to the pin's.

**Machines are pinned by PPID** (`TdxPolicy::ppids`, required and non-empty). The PPID (Platform Provisioning ID, 16 bytes) is a member of the Intel SGX extension (`1.2.840.113741.1.13.1`) of the PCK certificate, OID `1.2.840.113741.1.13.1.1`, per Intel's SGX PCK Certificate and CRL Profile Specification (`tdx::PPID_OID`). `dcap-qvl` reads it from the leaf of the chain it has just verified to the Intel root, so the value is Intel-signed; `authenticate` requires exactly 16 bytes. `tdx::tests::the_ppid_is_the_pck_certificates_sgx_extension_member` re-reads the fixture certificate's PPID independently of `dcap-qvl` (the quote's PEM chain, `x509-cert`, a minimal DER walk) and holds the two equal. There is no FMSPC allowlist: a PPID names one registered platform, and a platform's FMSPC (family, model, stepping, platform type, SKU) is fixed, so an FMSPC allowlist would refuse nothing a PPID allowlist admits. The FMSPC is still logged on every TDX handshake, beside the PPID.

**PCK platform flags are required, explicit pin fields** (`TdxPolicy::{dynamic_platform, cached_keys, smt_enabled}`, each `PckFlag::{True, False, Undefined}`, no serde default). They come from the Intel-signed PCK certificate, and `Undefined` is what a single-package (Processor CA) platform's certificate carries. The pin author states each one, so accepting a host with a weaker property is a visible decision and never an omission. A quote whose flag differs either way is refused.

- `DynamicPlatform`: the platform can add or replace CPU packages after its platform keys were registered with Intel. A host operator could then swap a package without that change being tied to a new registration event visible to us.
- `CachedKeys`: Intel's registration service keeps the platform root keys, so a replaced package can recover them without the original packages present. Key custody then extends to Intel's registration backend.
- `SMTEnabled`: hyperthreading is on. A TD's core shares microarchitectural state with whatever the host schedules on the sibling thread, which is the precondition for most cross-thread side channels. These are outside the measurement — see `docs/threat-model.md`.

dcap-qvl's strict policy refuses `True` for all three. The sample real host (`tests/fixtures/dcap-qvl/`) asserts all three, as multi-package cloud TDX hosts commonly do. That is why the verifier asks the pin rather than defaulting to strict: strict would refuse such hosts outright, and lenient would accept them silently.

**Every other claim dcap-qvl returns is enforced or deliberately left out.** `verify_with_policy` runs with `QuotePolicy::claims_only`, so nothing on the claims is appraised unless listed here:

| Claim | Disposition |
|---|---|
| `header.version`, `tee_type`, reserved `qe_svn`/`pce_svn`, `attestation_key_type` | Enforced (`parse_quote`; key type by dcap-qvl) |
| `header.qe_vendor_id` | Pinned |
| `header.user_data` | Not appraised: QE-defined bytes outside the TD's measured state |
| `tcb.status`, platform and QE `tcb_level.tcb_status` | `UpToDate` required (Revoked is refused by dcap-qvl regardless) |
| `tcb.advisory_ids`, level advisory lists | Not appraised: `UpToDate` is Intel's statement that the level carries every mitigation it requires. An advisory denylist would be additive. |
| `tcb.eval_data_number`, `qe.tcb_eval_data_number` | Floor pinned, applied to each document separately |
| `platform.tcb_date_tag`, QE `tcb_date`, grace periods | Not applicable: they only matter for `OutOfDate` statuses, which are refused |
| `pck.ppid` | Pinned: allowlist (`ppids`) |
| `pck.fmspc` | Logged, not pinned: fixed for each machine the PPID allowlist names |
| `pck.dynamic_platform`, `cached_keys`, `smt_enabled` | Pinned, required |
| `pck.cpu_svn`, `pce_svn` | Enforced through TCB-level matching, which determines the status |
| `pck.platform_instance_id` | Not appraised: the PPID already names the platform |
| `pck.pce_id`, `platform_provider_id` | Not appraised: identifiers, not security state (`platform_provider_id` is never populated) |
| `pck.sgx_type` | Not appraised: it describes SGX enclave-page protection for the quoting enclave, a property of the platform, which the PPID allowlist names. TD memory protection is TDX's own. |
| `platform.root_key_id` | Equal to the pinned root by construction (chain verification) |
| `pck_crl_num`, `root_ca_crl_num` | Not appraised: no monotonic CRL state is kept, so replay within the validity window remains (`docs/gaps.md`) |
| `earliest_issue_date` … `qe_iden_earliest_expiration_date` | Enforced per source: dcap-qvl checks every certificate's, TCB Info's and QE Identity's window at `now`; this crate adds both CRLs' `thisUpdate` |
| `qe.report` | Enforced by dcap-qvl against the signed QE Identity (MRSIGNER, ISVPRODID, attributes, MISCSELECT, ISVSVN) |
| `report` (TD report body) | Every field is accounted for. Appraised above: TEE_TCB_SVN, MR_SEAM, TD_ATTRIBUTES, XFAM, MRTD, MRCONFIGID, MROWNER, MROWNERCONFIG, RTMR0–3, REPORT_DATA. MRSIGNERSEAM and SEAMATTRIBUTES are matched by dcap-qvl against the signed TCB Info's TDX-module identity. The TD 1.5 additions arrive only in v5 quotes, which are refused. A TD 1.5 body is also refused after verification. MR_SERVICETD is recorded as zero for the accepted TD 1.0 body, and appraisal requires zero, so admitting TD 1.5 later cannot silently admit a service-TD binding. dcap-qvl also refuses a non-zero MR_SERVICETD unless the caller opts in, which this crate never does. TEE_TCB_SVN2 must join the SVN floor before TD 1.5 bodies are accepted. |

Then the shared `REPORT_DATA` comparison and the device requirement. The Intel root is `src/intel_sgx_root_ca.der`, pinned by SHA-256 in `tdx::tests::pinned_intel_root_is_the_published_certificate`; production has no override (the struct field exists only so this module's tests can construct a checker). `dcap-qvl`'s `std` feature is off on purpose: it enables `serde_json/preserve_order`, which would change `serde_json::Value` key order in every binary linking this crate.

**The `dcap-qvl-webpki` fork.** `dcap-qvl` verifies chains and CRLs with its own rustls-webpki fork, under a crate name RustSec never flags. At `=0.7.1` it pins `dcap-qvl-webpki =0.103.15+dcap.1`. That fork is upstream `rustls-webpki` 0.103.15 — past the 2026 CRL distribution-point, name-constraint and CRL-parsing-panic fixes (RUSTSEC-2026-0049/-0098/-0099/-0104, all patched by 0.103.13) — plus three additive changes: a single-certificate CRL check used only for the self-signed root, CRL-signature caching keyed by issuer SPKI, and RustCrypto algorithms. It lacks 0.103.16's fix for RUSTSEC-2026-0382, a denylist of distrusted emSign intermediate keys, which cannot matter here: every chain `dcap-qvl` builds ends at the one pinned Intel SGX root, which no emSign certificate chains to. **Any `dcap-qvl` bump must re-diff the fork against the matching upstream release** before it lands.

**Device evidence** (`device.rs`, platform-independent): an entry with `expected_gpus: Some(n)` requires exactly `n` `nvidia-gpu-evidence/v1` items (kind `gpu`, vendor `nvidia`, strict `{arch, certificate, evidence, nonce}` payload), each with `nonce` equal to the handshake nonce. That member is the label the measured attestation shim writes beside NVIDIA's report; the nonce inside the signed SPDM report is not read. Any `gpu`-kind item in another format is refused, so it cannot ride along uncounted. Other devices (e.g. NVSwitch) pass untouched. The check runs only after `REPORT_DATA` authenticated the device section. Nothing NVIDIA-signed is appraised.

**Fixtures and tests.** `tests/fixtures/dcap-qvl/` holds a real TDX quote and the Intel collateral it verifies against, verbatim from `dcap-qvl`'s samples (MIT; provenance in that directory's README). The tests reshape that collateral into captured-PCS-response form, keeping Intel's signed bytes, and run at a fixed time inside its windows. The quote was produced under a measured-boot launch with RTMR0 extended, so it authenticates and is then refused by appraisal on RTMR0 — the real-hardware negative. Field-by-field policy cases run on synthetic authenticated quotes (`tdx::tests::appraisal_refuses_each_field_that_differs_from_the_pin`); on the real quote, authenticated and with its RTMRs cleared, an unlisted PPID and floors above its TEE_TCB_SVN and collateral number are each refused (`a_real_quote_from_an_unlisted_machine_or_below_a_floor_is_refused`). Collateral and quote tampering cases are in `tampered_missing_or_stale_collateral_is_refused`. The platform-branch attack — a genuine TDX quote against SEV-SNP-only pins, such as the gateway pin — is `attest::tests::tdx_evidence_against_sev_snp_only_pins_is_refused_before_authentication`. The pin-side half of the launch identity (MRTD from the IGVM image, MRCONFIGID from the config) is `measure-enclave`'s `measure-tdx-igvm` — see `crates/measure-enclave/AGENTS.md`.

## Platform endorsements (`platform_endorsements`, feature `platform-endorsements`)

Pin-authoring code, never on a handshake: it is behind a feature that only `measure-enclave` and the gateway's build script (and tests) enable, so neither the runtime gateway nor the client links it. The platform provider publishes Sigstore-signed platform endorsements, `platform-vX.Y.Z` releases of `tinfoilsh/cvmimage`: `platform-endorsements.json` (format `https://tinfoil.sh/predicate/platform-endorsements/v2`) maps each machine, TDX ones by PPID, to a named policy (`mr_seam`, `td_attributes`, `xfam`, `minimum_tee_tcb_svn`, `qe_vendor_id`, `minimum_tcb_evaluation_data_number`), and `.github/workflows/platform-release.yml` signs it as a GitHub artifact attestation whose predicate is the file itself.

`platform_endorsements::verify(file, bundle, trusted_root, tag, expected_sha256)` runs offline with no wall clock:

1. The tag is `platform-vX.Y.Z` (the workflow's own pattern), read by `eidola_common::platform_release`, the one parser of it that the sidecar check and `measure-enclave` read tags with too (so this feature depends on `eidola-common`, which its every user already does), and the file hashes to the hash the caller recorded.
2. The bundle (`sigstore` submodule): media type exactly `application/vnd.dev.sigstore.bundle.v0.3+json`; the leaf chains to a Fulcio CA of the committed trusted root valid at the leaf's issuance (issuer names and signatures, to the CA's self-signed root); its identity exactly `https://github.com/tinfoilsh/cvmimage/.github/workflows/platform-release.yml@refs/tags/<tag>` (the SAN as its only name, and Fulcio's build-signer URI), source repository `https://github.com/tinfoilsh/cvmimage`, source ref `refs/tags/<tag>`, runner `github-hosted`, OIDC issuer GitHub Actions'; the DSSE envelope's one signature over `PAE(application/vnd.in-toto+json, payload)`; one Rekor `dsse` 0.0.1 entry whose body names this payload's hash, this signature and this certificate, whose SET verifies under a log key of the trusted root valid at its `integratedTime`, whose inclusion proof reaches its stated root, and whose `integratedTime` is inside the leaf's validity. The Fulcio SCT and the Rekor checkpoint signature are not checked, as in the updater's verifier (`docs/gaps.md`).
3. The signed Statement: in-toto v1 of the v2 predicate, exactly one subject, `platform-endorsements.json` with the file's SHA-256 and no other digest, and a predicate equal (as JSON) to the file.
4. The file, strictly: the top level and every TDX policy refuse unknown members (a member the provider adds to a TDX policy may be a constraint, and is reviewed, not ignored), maps refuse repeated keys, the format is the v2 predicate, and every machine names a defined policy. SEV-SNP policy blocks are not read.

`VerifiedEndorsements::tdx_policy(name, flags)` then returns the [`TdxPolicy`] for one TDX policy: its fields (each lowercase hex of its exact width), `mr_seam` as a one-element list, and `ppids` = every machine the file maps to that policy, in order (none is an error), with the caller's PCK flags. The tests that run it over the real vendored release, with real negatives (an authentic attestation of the byte-identical file under another tag; a genuine attestation from another repository of the same provider; a genuine Rekor entry of another signing swapped in), live in `measure-enclave` (`src/platform_endorsements.rs`), because a test here would compile only with the feature on.

ALPN is pinned to HTTP/1.1 so the inline attestation and application request share one connection lifecycle. Pooled keepalive requests inherit the binding established for that connection. On the native connector TCP keepalive is set explicitly (`TCP_KEEPALIVE`, 15 s idle and between probes, `TCP_KEEPALIVE_PROBES` 3, `reqwest`'s defaults pinned so a dependency bump cannot drop them), so a peer that vanishes without closing an idle or long-waiting connection is a connection error within a minute; nothing here bounds how long a request waits for its answer, which only its caller knows (the gateway bounds a stream's headers and silence itself). TLS roots are caller-supplied and authenticate only the inference endpoint; hardware roots are separate and never enter WebPKI. A pipe's socket is the host's, and so are its keepalive settings. Keep the implementation pure Rust.

The attestation response is read by hand (`attest::read_http1_response`) from a peer nothing has authenticated yet, so its bounds are checked without arithmetic the peer controls: the release profile builds with `overflow-checks = false`, where `body.len() + size` for a peer-declared chunk size wraps past the bound into a panic. Compare the peer's number against the remaining room instead (`size > MAX_BODY - body.len()`). Test: `a_chunk_size_past_the_body_bound_is_refused_not_wrapped`. Nothing may follow the body under either framing: bytes after a `Content-Length` body, and anything after the last chunk but its final CRLF (trailers included), are refused (`bytes_after_the_body_are_refused`).

## Threat-model note

The nonce defeats stale-document replay and the quote authenticates the peer certificate's long-lived SPKI. It does **not** bind the live TLS session. An attacker holding an exfiltrated TLS private key can terminate TLS outside the enclave while relaying a fresh nonce-bound document from a genuine enclave. Closing that gap requires channel binding, such as committing TLS exporter material to `REPORT_DATA`; Tinfoil's current v3 implementation does not do this.

## Redirects

The client **follows no redirect** (`redirect::Policy::none()`); a `3xx` is handed back as the answer. Per-handshake attestation is not an origin pin: a redirect opens a fresh connection that is attested in its own right, so a cross-origin `Location` is refused only when the new peer cannot prove an allowed measurement over its own TLS key — every plain `http://` target fails (no TLS info), as does every host that is not an enclave running a pinned measurement — while another enclave running a pinned measurement under a different hostname would pass and receive the replayed body. Refusing every redirect keeps each request at the origin it was made to, and turns what would have been an attestation failure into the upstream's own status. There is no same-origin exception. Every consumer inherits this: app-core's chat turns and the gateway's engine client alike.

## Targets

The crate compiles for `wasm32-unknown-unknown` too, for the mobile app (`crates/eidola-app-core/AGENTS.md` → Targets and features). **What is verified is the same on every target**: the check (`attest`), the byte-pipe transport (`pipe`), the document parser, the SEV-SNP and TDX verifiers and the pins compile everywhere, over `tokio` with `io-util` alone, `tokio-rustls` and `httparse`. Only the reqwest connector is native: `attesting_client`, the `attesting_client()` entry point, `bundle::fetch_well_known`, `Error::Fetch`, `pipe::TcpDialer`, `sevsnp_crl::unix_now` (the system clock) and their dependencies (`reqwest`, `hyper`, `hyper-util`, `tower`, `http`, tokio's runtime and `net`) are `cfg(not(target_family = "wasm"))`, so wasm32 links no reqwest and cannot reach the browser's `fetch`. The TDX path classifies Intel PCS URLs with `url::Url`, the parser `reqwest::Url` re-exports. wasm32 adds the browser's randomness (getrandom `wasm_js`/`js`) and clock (`rustls-pki-types/web`) as target dependencies. CI's wasm32 clippy builds the crate with app-core (`.github/AGENTS.md`).
