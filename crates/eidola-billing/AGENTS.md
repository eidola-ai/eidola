# Billing — shared account operations

This crate owns the account billing behavior used by the gateway and the private `eidola-billing-cli`. Neither surface has its own refund or chargeback algorithm. Read [anonymous-credit doctrine](../../docs/anonymous-credits.md) for every change: these tables belong to the linked account surface. No ACT spend, nullifier, recovery key, inference request or client spend trail belongs here.

## Boundaries

- `stripe.rs` owns the pinned provider transport and normalized observations. A webhook is a wakeup, not an instruction to credit or debit its payload. A provider error carries its HTTP status and Stripe's error type resolved against a fixed list, never the body's free text (`stripe_error`). Every request goes through `StripeClient::send`, which names its operation (`STRIPE_OPERATIONS`: resource and verb, the way a restricted key's permissions are named; `every_stripe_operation_is_listed` holds the list to the call sites), counts and times it, and logs a 401 or 403 once per operation per process, naming the operation, so a restricted key's missing permission is identifiable.
- `service.rs` owns provider reads and the durable prepare → submit → observe workflow. The CLI connects directly to PostgreSQL and Stripe with its caller's credentials. The gateway requests account-scoped reconciliation through the database and reads its durable status; it never executes repair workflows.
- `store.rs` owns transactions and `schema/billing.sql` owns allocation functions. The latter is embedded verbatim between the shared-billing markers in the gateway's fresh baseline, `../eidola-server-gateway/schema/schema.sql`. `gateway_and_library_share_exact_billing_schema` checks the copies and that there is exactly one debit and balance function. Update both copies together. There is no historical-data migration requirement for this pre-production baseline; do not add a lossy backfill or a compatibility mutation path.

## Concurrency and identity

Every balance mutation takes the same account row lock as credential issuance. `record_credential_issuance` answers its stored idempotent response first, then checks the issuer key and account state under that lock. Closing is irreversible: a new issuance returns `closed`, while retries of paid issuances still recover.

Purchases are identified by their immutable provider source, never an event ID. Each purchase records the actual amount paid, currency, credits, expiry and charge/invoice/PaymentIntent references. Equal expiration dates do not merge purchase prices. Ledger foreign keys bind an allocation to its purchase, account and original expiry; payment effects also name a durable billing operation.

Provider reads and their application use `ReconciliationGuard`. It holds a session advisory lock on a detached connection; snapshot transactions commit on that same connection. A lost lock connection cannot apply a stale snapshot through another one. Dropping the guard closes the connection instead of returning a held lock to the pool, and a process-wide semaphore bounds the detached connections. Production provider observations go through guard methods. The standalone store mutation helpers are useful for explicitly supplied administrative provenance and database tests, not a substitute for the provider read lock. Session advisory locks need a server session of their own, so billing processes connect to PostgreSQL directly, never through a transaction-pooling PgBouncer.

`apply_observations` commits a related snapshot atomically. A purchased grant must never become issuable in an intermediate commit before its known dispute is deducted. Unknown financial objects are retained without guessing credit value; unrelated verified purchases can still reconcile.

Inbox selection is only a candidate list. `claim_event` acquires a separate session advisory lock on a detached connection and rechecks eligibility before returning `EventGuard`. Completion and failure use that same connection; cancellation or connection loss releases ownership without a lease timer, and a stale guard cannot finish through a replacement connection. Different jobs for one account still share the reconciliation lock with direct CLI operations and checkout. Candidates are ordered by next attempt time so a repeatedly requested repair returns behind other due work after each generation. No SQL transaction spans provider I/O. These are retryable operations, not an exactly-once execution guarantee: durable refund identity and provider reconciliation remain necessary after an uncertain network outcome.

Account repairs use one inbox row per account (`billing.reconcile:<uuid>`). Each accepted request advances its generation. A worker captures that generation at claim time and acknowledges only that generation; a request arriving during provider reads remains pending. Status carries both requested and completed generations, the completed generation's report, and a fixed failure category. A previous report is never evidence that the latest generation completed. Repeated requests preserve an existing retry delay and occupy one row. An incompatible or malformed existing repair record must be refused, never presented as idle.

`billing_protocol` separates the stable ingress contract from executor semantics. Receivers, repair producers/status readers, and gateway checkout check `ingress_version`; workers and direct operator execution check `execution_version` at startup and again when acquiring work/account locks. `CheckoutGuard` uses the same account lock but exposes no billing mutation methods. Provider writes also recheck the owning account connection. Unsupported inbox kinds and per-item protocol versions remain pending with visible review failures. An incompatible executor rollout must quiesce old executors before changing the execution version or schema; these checks reject incompatible admission, not a substitute for coordinating schema changes with already-running work. Compatible old ingress producers need no worker release embedded in them.

## Refunds

Ordinary refunds reserve exact eligible credits before contacting Stripe. A goodwill refund has an explicit cash amount and zero credit effect. Provider refunds without an internal operation are cash observations only: they never invent an account debit. All observed cash returns still reduce the money that can be refunded again and the loss attributable to a chargeback.

Cash rounding is cumulative within a purchase, capped by the remaining payment. It does not cancel extra credits to obtain a whole cent. Canceling remaining credits after a previous cash-only refund can consequently return zero cash; that operation completes locally and must not call Stripe with zero.

The operation's first submission time is immutable. Safe retries compare it with the database clock, never the operator device's clock. A lost response leaves an ambiguous submission, never a releasable failure. An HTTP rejection can establish failure only on the first submission: a rejected retry does not resolve an earlier unknown outcome, and must preserve `submitting` until the provider's refund object resolves it. A definitive failure retains its hold. `retry_refund` transfers that entitlement to a new operation and Stripe idempotency key without releasing credits, even after the original expiry. Released/superseded attempts remain recordable when Stripe repeats their failed or canceled state. An alternate payout is an explicit operator attestation with a unique reference; it is forbidden while a Stripe submission is ambiguous.

Do not release an expired hold into already-expired credits and silently erase the customer's frozen refund entitlement. Complete it by another attempt or an explicitly recorded alternate payout. Delayed support requests that were not recorded while eligible require receipt/ledger review and the discretionary path.

An alternate payout is final for its operation: repeated failed/canceled Stripe observations do not regress it. Unexpected provider money after that payout is recorded separately and flagged for review, so both returns reduce the cash available for further refunds. Local release and alternate settlement wake closure in their transaction when the account is not open, advancing the closure job's generation so an older worker completion cannot lose the wakeup.

## Disputes and closure

Chargebacks collect cash value at each affected purchase's actual price, in the same currency. Uncovered value is durable monetary debt, never an at-par or expiring credit overdraft. Free credits have no cash value and remain usable. `available_balance` reports a negative credit equivalent only when no positive credits remain; the API also reports currency debt explicitly.

Only successful refunds reduce a chargeback's target. Pending refunds reserve cash against new refund requests but cannot expose credits before cash returns. Targets are capped by the purchase price after prior returns and other disputes. A win undoes recorded allocations with their original expiries. Restored paid credits first satisfy any other outstanding debt under the same account lock. Integer credit allocation rounds down, retaining any fractional monetary residue.

Closure freezes eligibility when requested and stops new checkout/issuance. Provider cancellation, refunds and closure finalization remain resumable. A paid invoice can legitimately be collected after its service period ends: keep that actual expiry and cash provenance. A payment collected after closure is eligible for the closure refund even if its service period ended earlier.

Webhook events and local refund/closure intents are durable work items with bounded retry backoff. Creating a hold or beginning closure creates its local work item in the same transaction, so a process crash needs no new webhook to resume the operation. Retry work does not independently poll Stripe accounts.

Webhook authentication accepts at most five minutes of clock skew in either direction, including all valid `v1` signatures during secret rotation. The receiver accepts only Stripe's thin event notifications (`object: "v2.core.event"`), which carry an event's ID, type and related object's ID but never that object's contents; an authenticated snapshot event is refused with 400. After authentication, unsupported thin types are ignored before requiring a related object, which some types lack; supported types still require valid event and related-object IDs. The inbox stores the type exactly as Stripe names it (`v1.refund.updated`), and `BILLING_EVENT_TYPES`, the worker's dispatch and `event_object_kind` use that one spelling. Stripe's `v1.` namespace and the inbox's own `billing.` job kinds never meet. `billing_event` holds identities and scheduling state only; its column comments in `schema/billing.sql` say what each holds, and `report` is constrained to account repair rows.

## Telemetry

`metrics.rs` holds the instruments for Stripe calls and the worker's workflow. They record through the global meter, so they are no-ops in a process that installed no meter provider (support commands), carry the billing worker's service name in the worker, and the gateway's in the gateway, which reports its own Stripe calls this way. Billing is the linked surface and Stripe holds all of it, but metrics still carry **no identifier and no per-object amount**: no account, customer, subscription, price, product, event, charge or refund ID, no email, no Stripe-authored text. Every label value is a literal in this crate or a provider value resolved against a fixed list with a catch-all (`job_type_label` → `unsupported`, `currency_label` → `other`, Stripe's error type → `other`/`unparseable`). Money appears only as a counter summed over every purchase.

- `stripe.requests{operation, status, error_type}` and `stripe.request.duration{operation, status}` (seconds). `status` is `2xx`, one of `400 401 402 403 404 409 429`, else `4xx`/`5xx`/`other`, or `timeout`/`network` with no response; `error_type` is `none` or Stripe's type from the fixed list. One per HTTP request, so a paginated list counts each page.
- `billing.jobs{job_type, outcome}` and `billing.jobs.retries{job_type}` — each claimed inbox job, `outcome` `completed` or the failure category it stays pending with (`BillingError::class`, `unsupported_kind`, `unsupported_protocol`); a retry is a job claimed again after a failed attempt.
- `billing.reconciliations{outcome}` — each full read and application of one account's Stripe state (`reconcile_locked`), `ok` or the error class.
- `billing.purchases{sale, currency}` and `billing.purchases.amount{sale, currency}` (minor units, summed) — purchases recorded for the first time; `sale` is `one_time`, `subscription_start` or `subscription_renewal` (an invoice with `billing_reason: subscription_cycle`, carried only on `PurchaseSnapshot::renewal`).
- `billing.refunds{status, origin}` — a refund's Stripe status first seen or changed (`pending`, `requires_action`, `succeeded`, `failed`, `canceled`), or `rejected` for a first submission Stripe refused outright; `origin` is `operation` (ours) or `external`.
- `billing.disputes{outcome}` — `opened`, then `won`, `lost` or `warning_closed` when it closes.
- `billing.account.closures{stage=requested|closed}` — the transitions out of `open` and into `closed`.
- Gauges from `Store::backlog`, read on the worker's timer (`metrics::backlog`, zeros recorded for every absent label so a cleared backlog reads zero): `billing.work.pending{job_type}`, `billing.work.failing{job_type}`, `billing.work.oldest_age{job_type}` (seconds since the oldest pending row was first received; repair and closure rows are reused, so theirs is the account's first request), `billing.refunds.open{state}`, `billing.refunds.submitting.oldest_age` (alert well before the 23-hour safe retry window), and `billing.review.open{source=unmatched_refund|unmatched_dispute|job}`.

Counted effects are post-commit: the store's private observation functions collect what a transaction changed into `Applied` (a purchase the first time it is recorded, a refund status that is new or changed, a dispute opening or closing), the guard returns it after the commit, and the service counts it. A rolled-back transaction counts nothing, and reapplying an unchanged snapshot counts nothing (`a_commit_reports_only_what_it_changed`). `begin_close`/`finalize_close` return whether they made the transition for the same reason.

The service logs only conditions: pending work of an unsupported kind or ingress protocol version, once per process each (`warn_unsupported_once`). Routine outcomes are counters.

## Validation

`tests/store.rs` exercises real PostgreSQL in unique schemas of the explicitly supplied disposable `BILLING_TEST_DATABASE_URL`, over verified TLS like every connection (`connection.rs`: `sslmode=disable` is refused; `DATABASE_SSL_CERT` names the test database's root, which `just test-billing` takes from `.dev-certs/postgres/` when unset); run its ignored tests too. Cases cover purchase identity, price/expiry provenance, refund versus issuance, failed and expired holds, alternate payouts, external refunds, cumulative cash rounding, partial refund/dispute overlap, negative debt, free credits, crossed disputes, out-of-order purchase discovery, atomic rollback, closure and guard cancellation. Queue cases cover cross-connection claims, stale selection, killed lock connections, new repair generations during processing, bounded request coalescing, retry delay and fairness. `tests/service.rs` exercises the provider workflow with local HTTP fixtures, a rejected retry followed by delayed provider completion, definitive first-submission rejection, independent worker instances, direct-CLI contention, unknown work retained for review, and executor mismatch before any provider call while stable ingress remains available. The gateway tests cover the authenticated public boundary.

Never substitute unit arithmetic tests for these database races. Never use real Stripe credentials or a production database for fixture-driven tests.
