# eidola-engine

The serving core of Eidola's purpose-built inference engine for the MiMo-V2.6 family: the executor seam, paged KV manager, salted prefix cache, scheduler, speculative-decoding control flow, and the CPU reference sampler. It knows nothing about weights, numerics, tokenizers, or HTTP; it speaks token ids to an [`Executor`](src/executor.rs) and events to its caller. AGPL-3.0-only. Workspace conventions live in the root `AGENTS.md`.

| Module | Contents |
|---|---|
| `executor.rs` | The seam: `Executor` trait, `StepInput`/`StepOutput`, `Maintenance`, `TableUpdate`. Its module doc is the normative contract. |
| `spec.rs` | `ModelSpec` the executor reports: KV groups, block size, buckets, draft width, slots. |
| `kv.rs` | Block pools, per-sequence block tables, salted prefix cache, expiry, zero-on-free, encryption of idle blocks, the host tier idle entries are demoted to. |
| `kv_cipher.rs` | The idle-KV cipher every executor reproduces byte for byte: ChaCha20 (RFC 8439) as a bare stream cipher, a block's image and keystream rule, `KvNonce`, `KvKeystream`. |
| `engine.rs` | Scheduler and request lifecycle. |
| `sampling.rs` | Reference sampling semantics and chain speculative acceptance. `SamplingParams` is valid by construction (private fields, checked `new`): a NaN or negative temperature, `top_p` outside `(0, 1]` or `min_p` outside `[0, 1]` cannot reach a sampler. |
| `secret.rs`, `hash.rs` | Cache keys, salts, idle-KV keys and the lineage that pairs them, boot key; the block-hash chain and each sealed block's nonce. |
| `mock.rs` | Deterministic mock executor and the dense reference it must reproduce. |

## The seam

The executor owns all device memory (KV pools, per-slot block tables, per-slot model state) and the host tier's memory; the host owns every allocation decision. A step is: maintenance in the order given (as the KV manager queues it: demotions, then zeros and slot resets, then promotions, encryptions and decryptions, then host zeros), then table updates in order, then the forward, then on-device sampling (and, for speculative rows, draft → verify → accept), with no host interaction in between. The batch is padded to a captured bucket; block tables persist on the device indexed by slot and change only through explicit updates; so a pure-decode step (one host token per row, uniform drafts) can replay one CUDA graph per bucket. Under confidential computing a kernel launch costs on the order of 12 µs and every synchronous device-to-host copy is expensive, which is why drafting and acceptance live inside the step rather than in the host.

**Determinism contract.** The KV an executor writes for a position, and the logits for a query, depend only on the token prefix — never on batch composition, chunking, slot, or physical block. Recompute preemption and prefix-cache reuse are exact only because of this. Every executor meets it bit for bit: the CPU reference by construction, the CUDA executor by a batch-invariant forward (`eidola-engine-cuda/AGENTS.md` → Batch invariance). So a request's outputs do not depend on the requests it was scheduled with — isolation — and determinism follows:

- **Guaranteed**, on one kernel build and one kind of device: a request's logits at every position, and so its greedy tokens and its seeded samples at a fixed draft width, are the same bits alone or beside any other requests, under any prefill chunking or step budget, whether its prefix was cached, copied or recomputed, after a preemption, in any slot or block, and with decode graphs replaying or not. Greedy output is also the same at every draft width (drafting never changes a greedy token).
- **Not covered:** timing (step latency still follows the step's load, and what the node lets an observer see of it is the gateway's padding and pacing, not this contract); seeded sampled rows across draft widths (a drafted row's tokens come from the acceptance and residual streams, a plain row's from the sample stream, so the same seed gives different, equally distributed tokens at `k = 0` and `k > 0`; with drafting on, a seeded request's tokens therefore change when a step it is in drafts nothing, which the scheduler decides under KV pressure that other requests cause, until the sampler couples the streams); and anything across kernel builds, image architectures (`sm_100a`, `sm_103a`, `sm_100f`), GPU models or executors (the CPU executor agrees with the CUDA one only within the quantization tolerance `eidola-engine-cuda/AGENTS.md` → Numerics documents).

**Sampling is defined down to rounding.** The `sampling.rs` semantics are the contract, not one implementation of it: the `(seed, position, stream)` counter RNG and its streams, the filters, chain acceptance, and the arithmetic itself, all `f64`, with exponentials from `det_exp` (correctly rounded `+ - * /` only, never the platform `exp`), every vocabulary sum in the pinned chunked order (`pinned_sum`), top-p prefix masses as vocabulary-order sums of the rank prefix, and draws by the chunked prefix sums. Any executor, CPU or device, reproduces them bit for bit given equal logits. This also makes the reference itself host-independent: the platform `exp` differs between C libraries in the last bit (macOS's and glibc's on about 0.2 % of softmax-range arguments).

**Padded vocabulary.** A model's head can be wider than its tokenizer (MiMo: 152,576 rows, 151,675 tokens). `ModelSpec::sampleable_vocab_size`, supplied by whoever loads the tokenizer, is the set of ids a step may return. It is step 0 of the `sampling.rs` semantics, not a separate mask: every sampler input is a `Logits` (the sampleable prefix of a row, built by `ModelSpec::logits`), so target sampling, drafting, acceptance and the residual cannot return a padded id by construction. The engine also refuses a prompt containing one (`SubmitError::InvalidToken`) and fails a step that returns one.

**Groups.** MiMo has three KV kinds, each a group with its own pool and block table: global-attention layers (`AttentionKind::Full`), sliding-window target layers (`Sliding { window }`), and drafter context KV (`KvRole::Drafter`: an MTP head's sliding-window layers, or a block drafter's context projected from target hidden states). All groups share one block size, so logical block `i` of a sequence means the same positions everywhere. `window` counts visible positions including the query's own; attention-sink logits need no KV.

**Block invariant.** Every block in every KV group depends only on the tokens that block covers (and those before it). That is what makes prefix caching exact for target and drafter groups alike: a block is sealed as soon as it is full and shared with any sequence whose salted chain matches through its end. There is no lag allowance.

**Drafter rows (MTP).** A drafter row is indexed by the token it consumes: MTP depth `d`'s row at position `s` consumes the token at `s` and the **target's** hidden state at the anchor `s - 1 - d`, uses RoPE position `s - 1 - d`, writes its KV at `s`, and predicts `s + 1`: every depth conditions on the target, never on another depth's output, as the model vendor serves its MTP layers (layer `d` at anchor `x` combines `h_x` with `t_{x+d+1}` and predicts `t_{x+d+2}`; SGLang's multi-layer MTP worker, `eidola-engine-cpu/AGENTS.md` → MTP row layout). The draft for `p + 1 + i` is depth `i`'s prediction at `p + i`, so speculative drafter rows land in the positions reserved for drafts. Indexing by the hidden state instead (`(h_p, t_{p+1})` at `p`) would make a block's last drafter row depend on the next block's first token, outside the block's cache key. Resuming at a block boundary `c` needs the drafter's state at `c - 1`, so executors store a **boundary tap** (the levels at the block's last position) in every drafter block, zeroed and copied with it. The CPU reference executor (`eidola-engine-cpu`) implements this and is its oracle; the CUDA executor implements it on the device, drafts and acceptance inside the step (`eidola-engine-cuda/AGENTS.md` → Drafting); the normative text is in `executor.rs`.

**Block drafters (DFlash shape).** A block drafter drafting `k` tokens per step uses the same row shape (`num_drafts = k`), keeps its context KV in a `Drafter` group (window 1024 for MiMo's), and keeps target hidden-state taps in per-slot state. Its context KV at `s` is projected from target hidden states at `s`, so it meets the block invariant directly; the taps it resumes from at a block boundary are stored like MTP's boundary taps. Its in-block bidirectional KV is step-local scratch and is never paged.

## KV and prefix cache design

**Paged sliding window, not a ring.** Sliding-window layers are paged exactly like global layers, and a sliding block is released once it is behind the window of the sequence's newest *sealed* boundary. A per-sequence ring buffer would be simpler on the device but cannot share blocks between sequences, so a prefix-cache hit could never supply the window. This follows vLLM's hybrid allocator; unlike vLLM, every group has its own pool, because MiMo's global and sliding layers have different KV head counts and so different bytes per block.

**Hit points.** A hit of `m` blocks is accepted only if every full-attention block `0..m` is cached **and** every sliding group has the blocks covering the window before position `m * block_size` attached. Hits are therefore always correct. A keyed sequence retains its windows at three points, each a boundary a later request under the same key resumes from:

- **branch**: the deepest boundary its chain matched in the cached trie at admission, when that boundary's window was not attached. This is where a request that shares a prefix with earlier ones (a system prompt and tool definitions) diverges from them;
- **regeneration**: the last full block of the prompt before its final token, where a regeneration of the same prompt resumes;
- **continuation**: its last sealed boundary, where a continuation of the conversation resumes.

Branch and regeneration windows are attached to their entries as soon as the boundary is sealed (before the window slides past it), so requests that arrive while the sequence still runs hit them; the continuation window is attached at release. For a shared prefix with divergent turns, the first request seals the prefix's full-attention blocks, the second finds them without a window, recomputes and keeps the window at the branch, and every later one hits there. Retention costs at most `ceil((window - 1) / block_size) + 1` blocks per sliding group per point, three points per sequence, from the same pools and under the same eviction, expiry and zero-on-free as every other cache block. A boundary that is none of these (an edit in the middle of a conversation the first time it is made) falls back to the nearest retained point or recomputes.

*Why the branch point, and not the alternatives.* The rule is one invariant (windows are kept only where a request under the key has resumed or diverged) with memory bounded per sequence, and needs nothing from the caller.

- *Every sealed boundary* would keep each sequence's whole sliding history, so cached sliding groups would cost as much as full ones (on MiMo most layers are sliding) and push useful entries out.
- *A fixed stride* (every `n`th boundary) keeps windows on every sequence whether or not anything ever branches there, and a hit loses up to `n - 1` blocks; the stride would be a tuning knob between the two.
- *Caller-marked boundaries* (message or turn ends) would make the engine depend on chat structure the seam does not carry, and the branch is not always at a marked boundary.

The price of the branch rule is that the second request sharing a prefix recomputes it once.

**Eviction.** Entries form a tree (each chains its parent). Under pressure the least recently used unreferenced leaf goes first, then ancestors that became unreferenced leaves and are not valid hit points themselves. Eviction is not group-targeted: freeing a block in one group may evict an entry whose other blocks were not needed.

**Host tier.** An executor may keep a second, larger pool per group in host memory (`KvGroupSpec::host_blocks`; the confidential VM's own RAM, page-locked, never durable media). Under device pressure the KV manager **demotes** instead of dropping: the least recently used unreferenced entry holding a device block of the group that needs room, whose blocks are all ciphertext on the device as the step begins, has every device block copied to a host block (`Maintenance::Demote`) and freed (zeroed) like any other. It stays in the tree; each of an entry's slots is held on the device or on the host. A lookup that hits a demoted block **promotes** it: a fresh device block, the ciphertext copied back (`Maintenance::Promote`), the host block freed (`Maintenance::ZeroHost`); mapping it then queues its decryption, which runs after the copy. Only the blocks a hit maps come back (every full-attention block, a sliding group's window); the hit is shortened if the device cannot take them, though protecting the chain while promoting means that only happens when running sequences hold the whole pool. Under host pressure the least recently used unreferenced entry holding a host block of the group is dropped (a leaf with the eviction cascade, otherwise its subtree); if the host tier cannot take an entry, the device drops one as it would without a tier. Expiry, sweeps and purges remove entries wherever their blocks are. The tier exists only when every group has one and the prefix cache is on; the node sizes it from `EIDOLA_ENGINE_KV_HOST_BYTES` (`eidola-server-engine/AGENTS.md`).

*Why demote whole entries and promote only what a hit maps.* Demotion is the eviction decision, and entries are what LRU orders; promoting a whole entry would bring back sliding blocks no hit at this point reads, and spend device blocks under the very pressure that demoted them.

*Ordering within a step* is what keeps every copy honest, and is the KV manager's (`take_pending`): demotions first (they read blocks encrypted by an earlier step; a block with an encryption or promotion still queued is not demoted), then zeros (a demoted block's among them), then promotions (into blocks zeroed above, or fresh), then encryptions and decryptions (a promoted block's decryption after its copy), then host zeros (after the promotions that read those host blocks). A host block freed by a promotion is not reused until the step that zeroes it has been taken; one freed by a drop may be reused at once by a demotion, which overwrites every byte, and its zero is cancelled.

**Preemption** is recompute-based: the newest-arrived running sequence is released (its sealed prefix stays cached) and later re-admitted with prompt plus output, normally hitting its own blocks. Sampling draws are keyed by `(seed, position, stream)`, so its output is identical to an uninterrupted run.

## Privacy invariants and where they are enforced

1. **No unsalted namespace.** `BlockHash::root` is the only way to start a chain and it takes an `EngineSalt`. A request without a client key gets `CacheScope::Private`: a fresh random salt, and every entry it sealed is purged when it finishes (`kv.rs`, `Release::Finish`). It can still hit its own blocks after a preemption.
2. **Lineage derivation.** One client key yields a lineage (`secret::Lineage`), its two halves domain-separated under a random per-process `BootKey` (`secret.rs`): `engine_salt = HMAC-SHA256(boot_key, "eidola/kv/v1" ‖ client_key)` names the lineage's cache entries, and `kv_key = HMAC-SHA256(boot_key, "eidola/kv-enc/v1" ‖ client_key)` is what its idle KV is encrypted under. Neither yields the other or the client key. `Lineage` has no constructor but the deriver and `Lineage::fresh` (both halves random, for a request without a key), so the entries a salt finds are always the ones its key decrypts. Both mean nothing after a restart, exactly as the cache does not survive one.
3. **Secrets are content.** `CacheKey`, `EngineSalt`, `KvKey`, `Lineage`, `BootKey`, `SaltDeriver`, `BlockHash` and `KvNonce` print only a redaction marker in `Debug`, have no `Display` or serialization, and (but for the two an executor needs, below) expose no bytes outside the crate. The crate does no logging. `Stats` are content-free counters.
   - **Secrets** (`CacheKey`, `EngineSalt`, `KvKey`, `BootKey`) keep their bytes in one fixed heap allocation that is zeroed on drop. A move (into a request, through a `HashMap` rehash or `Vec` growth) moves only the pointer, so the collections that hold salts leave no stale copies (`secret.rs`, tested). Not covered: the caller's own copy of a `from_bytes` argument (a server parsing client keys uses `CacheKey::from_buffer`, which scrubs the caller's buffer), and the HMAC's transient stack state during derivation.
   - **What leaves the crate for an executor**: a `KvKey`'s words (`KvKey::words_into`, into the caller's buffer, which the executor scrubs) and a `KvNonce`'s (a content-free tag like the hash it comes from). `KvKeystream` writes the key words straight into one heap allocation of its own, beside its buffered keystream, so a move copies neither, and zeroes both on drop; not covered, as for the HMAC, is the cipher's transient register and stack state while it computes a keystream block.
   - **Lifetimes.** The client key never reaches the engine: the node derives the lineage and drops the key before submitting (`eidola-server-engine`'s `pipeline::prepare`). A lineage lives with its request (`Engine`'s record, the KV manager's sequence) while the request is waiting or running, and a copy of its key with the step that runs the encryptions and decryptions that request queued; every one is dropped when the request ends and that step has run, which the node does at once when the last request ends (`Engine::flush`). `Engine::kv_keys_held` counts them (tested to reach zero after a finish, a cancel while running and a cancel while waiting). Salts live exactly as long; neither outlives the requests of its lineage. Block hashes do, by design (below), and say nothing about either.
   - **Block hashes** are salted, content-free linkage tags, not secrets. They live in growable collections (the cache map's keys, each sequence's chain), where rehashing and reallocation leave copies no type can reach, so they are **not** guaranteed scrubbed from host process memory. That memory is inside the encrypted confidential VM, and a hash never leaves the process.
   - The retention promises below (zero on free, idle ciphertext, bounded TTL) are about **KV contents**, not these tags.
4. **Zero on free.** `KvManager::decref` is the single place a block's refcount reaches zero, and it always queues `Maintenance::Zero`. Freed by a finishing sequence, a sliding window, a speculative rollback, a preemption, cache eviction, or a demotion to the host tier — every free block is zero once the next step's maintenance has run. A host-tier block an entry stops holding (promoted, dropped, expired, purged) gets `Maintenance::ZeroHost`, done before that step returns, unless a demotion in the same step overwrites all of it. Released slots get `Maintenance::ResetSlot`, which also scrubs per-sequence model state.
5. **Idle KV is ciphertext.** A block a cache entry holds and no sequence maps is encrypted under its lineage's `KvKey` (`kv_cipher.rs`: ChaCha20, the nonce from the block's salted hash and group): `KvManager` queues `Maintenance::Encrypt` when the last sequence mapping a held block lets go of it (finish, preemption, or its window sliding past a retained point) and `Maintenance::Decrypt` when a sequence maps an idle block again, before the step's forward reads it; concurrent requests of one lineage share plaintext while any of them runs. Every retained kind is covered, since it is per block and every group's blocks are held the same way: full-attention blocks, the sliding-window blocks attached at branch, regeneration and continuation points, and the drafter group's blocks (the MTP depths' KV with their boundary taps). Per-slot model state is never retained (`ResetSlot` at release), and private requests' entries are purged at finish, though their blocks held across a preemption are ciphertext too (under a fresh random key). Between requests, therefore, an idle entry is ciphertext under a key nothing in the engine holds; the key arrives only with the lineage's next request, whose prompt already holds the cached content. A memory reader between requests learns no KV, and cannot use idle entries as an oracle (attach their blocks to a forged sequence and decode): without the key they are noise. Integrity is out of scope (`kv_cipher.rs` says why). The executor holds keys only for the step (`executor.rs` → Idle encryption). Expiry or eviction of an encrypted entry zeroes its blocks like any other free (a zero cancels a queued encryption or decryption), and an entry detached while in use is zeroed when its last user releases it, never encrypted and kept. Exposure remains while a request of the lineage is in flight and, after its release, until the next step runs the encryptions (the node runs it at once when the engine goes idle). **The host tier only ever holds this ciphertext**: a block is demoted only once it is encrypted on the device (never with an encryption still queued), promoted back as ciphertext, and decrypted on the device only when a sequence of its lineage maps it; nothing on the host decrypts, and no key goes there. A memory reader of the host tier between requests learns what it would from the device pools: nothing.
   - **Step scratch.** Besides KV, a step leaves its working data in executor memory: token ids and positions, hidden states, attention outputs, logits and distributions, drafts. The CUDA executor zeroes all of it at the first maintenance-only step after a step with rows, which the node runs as soon as the engine goes idle, and zeroes its whole device memory, live KV included, before freeing it on drop, which is when the node's worker drops an engine whose executor failed (`eidola-engine-cuda/AGENTS.md` → Idle scrub). So between requests a memory reader of the GPU learns no prompt-derived data from it either. Not covered: the CPU reference executor's per-step scratch, host heap it frees unzeroed (its KV pools, host tier included, are zeroed before they are freed).
6. **Bounded retention.** An unreferenced entry idle for `idle_ttl_ms` (default 15 min) or any entry older than `max_age_ms` (default 2 h), on the device or on the host tier alike, is never hit: lookups check expiry inline, and `KvManager::sweep` removes expired subtrees. Until then its blocks are held as ciphertext (invariant 5); then they are zeroed. `Engine::sweep` runs a maintenance-only step when zeros are pending, so scrubbing never waits for traffic; retention of ciphertext is bounded by the policy plus the caller's sweep cadence. An entry in use past its max age is detached at once and its blocks are zeroed when the last user releases them.
7. **Nothing persisted.** The crate performs no I/O; KV lives only in executor memory, the host tier included: the executors lock it into RAM (`cuMemHostAlloc`, `mlock`), and the node refuses to boot on a guest with active swap (`eidola-server-engine`'s `swap.rs`), which also leaves hibernation nowhere to write.
8. **Price never depends on hits.** Nothing here prices. `Event::cached_prompt_tokens` is a usage detail for the client only and must never feed billing.

## Scheduling policy

Strict FCFS by arrival. Running sequences are served oldest first; a decoding row costs `1 + k` query tokens; prefill is chunked by `max_prefill_chunk` and the step's remaining budget. Waiting requests are admitted only in steps that preempted nothing, and the first one that does not fit blocks those behind it, so long prompts cannot starve. **Under KV pressure** (`Engine::allocate_row`), optional reservations are shed in a fixed order, retrying after each, before anything is preempted or finished:

1. **Drafts, across the whole step.** The first time a row does not fit, every row already planned gives back its draft reservation (`KvManager::shrink`), and that row and every later row in the step plan with none. A row drafts `k` or nothing (never a partial count), so a step under pressure is a uniform plain decode.
2. **The prefill chunk**, cut to the row's minimum progress unit: the tokens up to the next block boundary, at most one new block per group, after which the block seals and sliding windows recycle behind it. A decode row's unit is its one host token.
3. **The sequence's own branch and regeneration retention** (`KvManager::unpin`): the windows it attached at those points, kept only so later requests could hit them; points not yet sealed are forgotten, and attached windows already behind its own window are freed.

Only then is the newest peer preempted (and the row retried), and a sequence that is alone ends with `FinishReason::Length`. So `Length` means exactly: the sequence cannot make its minimum progress even holding every reclaimable block (evictable cache entries are reclaimed by `KvManager::allocate` itself). Retention points are taken only for keyed sequences with caching enabled, since nothing else can use them. Drafts are uniform `k` except near the model length, under KV pressure (0), and at position 0 (0). Stop strings are the caller's job: it cancels.

**Draft width.** A step's width is the configured `k`, never narrowed to keep the step under a token count. Narrowing paid only while a GPU step past 128 tokens fell off a cliff: under DeepGEMM's per-row contiguous expert layout a B300 took 41-44 ms a step for 64 decode rows drafting two or three tokens against 15 ms drafting one. With the psum layout (`eidola-engine-cuda/AGENTS.md` → Expert layouts) the cost is nearly flat in the width: 64 rows at context 1,024, graphs replaying, took 30.5 ms at `k = 2` (192 tokens) against 30.6 ms for 126 tokens, and 33.3 ms at `k = 3` (256 tokens) against 31.0 ms for 128. At the measured acceptance (0.95, 0.94 and 0.92 for drafts 1-3, each conditional on the earlier ones) a row yields about 1.95, 2.83 and 3.65 tokens a step at widths 1, 2 and 3, so the full width gives the most tokens per second; a depth that stops paying for itself is dropped by lowering `k`, the operator's setting. Pinned deployments draft `k = 3`: greedy output is the same at every width (*Determinism contract*, above), so the width is purely a speed setting.

The executor's buckets form a ladder, nondecreasing in both sequences and tokens (`ModelSpec::validate`), so the last bucket bounds every step; trade-off shapes are refused rather than half-used. `Engine::new` refuses (`ConfigError`) any configuration under which a sequence could be planned and skipped forever: a step must seat at least one sequence, a prefill chunk must be at least one token, and the token budget (`max_batched_tokens` capped by the largest bucket) must hold one decode row at its full `1 + k` cost. Speculation is never silently disabled to make a configuration fit.

## Testing

`tests/engine.rs` drives the engine over `MockExecutor`, whose fake LM really pages KV through the tables it receives and panics on reads of unmapped, zeroed, or foreign slots and on writes to shared blocks. Every completed request is compared with `mock::reference_generate`, the dense oracle. Covered: chunked versus unchunked prefill, preemption and resume, greedy speculation exactness at every agreement rate, a chi-square test that speculative sampling preserves the output distribution, salt isolation and sharing, sliding-window hit validity, divergent turns after a shared prefix hitting at the branch (including requests that arrive while the branching one still runs, exact retention accounting per group, expiry and zeroing of branch windows, and a small pool that evicts them), idle-TTL and max-age eviction zeroing exactly the evicted blocks, cancellation, bucket choice, padded vocabulary rows never emitted (and refused at submission and from a lying executor), scheduler configurations that cannot progress, and a randomized workload checking `KvManager::check_invariants` (exact refcounts, no leak, no double free, LRU and tree consistency) plus "every free block is zero or has a zero queued" after every step. Each of these was checked to fail under a deliberate bug (no zero on free, disabled window check, unsalted root hash, no rollback, eager sliding, TTL off by one, biased acceptance, residual ignoring `q`, no branch point, branch windows attached only at release, `unpin` keeping attached windows, …); keep that true when changing the tests.

The mock really XORs a block's entries with the `kv_cipher` keystream, so reading a block left encrypted fails like reading a zeroed one, and it records which key encrypted each block (a keystream fingerprint, not the key) and fails a decrypt under another key, a decrypt of plaintext and a double encryption. After every step the harness checks the executor against the manager: every idle block encrypted and every mapped one plaintext, once the queued operations run. `tests/idle_encryption.rs` covers a finish leaving every group's cached blocks encrypted and a hit decrypting exactly what it maps (output equal to the reference), another lineage missing and never decrypting the first one's blocks (each lineage under its own key), concurrent requests of a lineage decrypting each block once, expiry and eviction of encrypted entries zeroing them without a decrypt, an entry detached in use zeroed and never encrypted, branch and regeneration windows (sliding and drafter groups) encrypted and decrypted for the branch hit, preemption encrypting while waiting and resuming on its own blocks (keyed and private), `Engine::kv_keys_held` reaching zero after a finish and after cancels while running and while waiting, and a randomized workload; `kv_cipher.rs` checks the cipher against RFC 8439's vectors and RustCrypto's `chacha20`, and that moving a keystream leaves its key words where they were written. Each was checked to fail under a deliberate bug: no encryption queued when a block goes idle, no decryption queued on a hit, `release` not settling its blocks, a zero leaving a queued crypt in place, the nonce ignoring the group.

With a host tier (`mock::with_host_tier`) the mock keeps a second memory per group, refuses to demote a block that is not encrypted, and refuses to promote from a host block holding no ciphertext or into a device block that is not zero; the harness checks after every step that every free host block is zero (or has a zero queued) and every held one holds ciphertext. `tests/host_tier.rs` covers device pressure demoting instead of dropping (every group, nothing dropped, the hit unchanged), the round trip (ciphertext on the host word for word, back word for word, decrypted to the plaintext the prompt determines), a host hit equal to a device hit and to a recompute (greedy and seeded, with and without drafting), no plaintext KV value anywhere in the host tier under randomized pressure, host pressure dropping the least recently used conversation and zeroing it, idle TTL and max age in both tiers (sweep and lookup), another lineage never promoting a demoted entry, branch windows surviving demotion, and a randomized workload; `KvManager::check_invariants` also checks the tier's holders, free lists and indexes. Each was checked to fail under a deliberate bug: no host zero, a promoted block marked plaintext (no decryption), a demotion with its encryption still queued, promotions before zeros, dropping instead of demoting.

## Extending

- **A real executor** implements `Executor`, honours the module contract in `executor.rs`, and samples with `sampling.rs` semantics bit for bit (see *Sampling is defined down to rounding* above). Validate it by running the simulation tests' workloads against it and the model's dense reference.
- **GPU sampling is an Eidola kernel.** The `(seed, position, stream)` counter RNG, its separate Sample / Draft / Accept / Residual streams, the filters, and chain acceptance with its residual are the contract, not an implementation detail: recompute preemption and the CPU oracle depend on the exact draws. Third-party samplers (FlashInfer's Philox kernels and the like) cannot reproduce them and are not used. The device sampler, speculative accept and residual included, must reproduce `sampling.rs` bit for bit given equal logits (`eidola-engine-kernels/AGENTS.md`).
- **A new KV kind** is a new `KvGroupSpec`; if it is neither full nor a sliding window, `AttentionKind::first_visible` and the hit-point rule must learn it.
- **Changing the hash format** changes the domain label in `hash.rs`.
- **Pipelining.** The trait is synchronous: one step in, one result out. Overlapping host scheduling of step `t + 1` with device execution of step `t` would split `execute` into submit and collect; the data shapes need not change.
