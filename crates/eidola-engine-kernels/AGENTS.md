# eidola-engine-kernels — Agent Guide

The engine's GPU kernels, compiled ahead of time from open source on a GPU-less Linux builder, and the manifest that pins their bytes. Targets are NVIDIA Blackwell datacenter parts: `sm_100a` (B200), `sm_103a` (B300), and the `sm_100f` family target (runs on any CC 10.x part). Workspace context: root `AGENTS.md`.

## The closed-tool boundary

Every kernel comes from source we fetch by hash and compile ourselves: **CUTLASS** (BSD-3-Clause), **DeepGEMM** device headers (MIT), **FlashInfer** headers and templates (Apache-2.0), and our own CUDA. Nothing upstream is committed here; the FlashInfer prologue is rendered from the pinned tree at build time, so no third-party text enters this directory.

The only closed software in the build is NVIDIA's CUDA 13.2 toolkit, at build time only: `nvcc`, `cudafe++`, `cicc` (libnvvm), `ptxas`, `fatbinary`, plus `cuobjdump`/`nvdisasm`/`cu++filt` for inspection. `nix/default.nix` admits exactly those components (and the cudart/crt/curand/cccl headers) through `allowUnfreePredicate`; adding any other NVIDIA package must be an explicit edit to that list.

Never, in this crate or anything it feeds:

- **trtllm-gen or any other prebuilt cubin.** We cannot rebuild them, so we cannot pin them to source.
- **Runtime compilation.** No nvrtc, no driver PTX JIT, no DeepGEMM/FlashInfer JIT. Images are SASS for the exact target; there is deliberately no PTX in them, so the driver has nothing to JIT.
- **The CuTe Python DSL** (closed compiler) or Python anywhere in the build.

## Toolchain pins

- **nixpkgs** `78e9c786…` — the root flake's revision, so one nixpkgs serves the repository.
- **CUDA 13.2.51** (`cudaPackages_13_2`). `sm_100a`/`sm_103a`/`sm_100f` need ≥ 12.9; CUTLASS 4.8 and current DeepGEMM/FlashInfer are developed on 13.x; 13.3 is the newest in this nixpkgs but its CCCL is marked unsupported there. Moving the toolkit moves every byte: rebuild and `--update` in the same change.
- **Host compiler** gcc 15.3.0 (`cudaPackages.backendStdenv`). nvcc uses it to preprocess device code, and `cicc` is told its version; swapping in gcc 14 produced byte-identical cubins, but the version stays pinned and recorded.

**Sampling never comes from upstream.** The serving core (`eidola-engine/src/sampling.rs`) defines what a sample is: draws from a SplitMix-based counter RNG keyed by `(seed, position, stream)`, with separate streams for target samples, drafts, speculative acceptance and the residual, its own filtering, CDF walk and chain acceptance, and pinned `f64` arithmetic (its own `exp`, sums in a fixed chunked order). Recompute preemption and the CPU oracle depend on those exact draws. FlashInfer's sampling kernels draw from Philox with a caller-supplied seed and offset and cannot reproduce them. `sampling.cu` performs the core's operations in the core's grouping with explicit round-to-nearest intrinsics (nvcc never contracts those into FMAs; the `DFMA`s in its SASS belong to the correctly rounded division routine), so it returns the same probabilities and tokens bit for bit given equal logits; `eidola-engine-cuda`'s `tests/sampler.rs` checks every probability and token against the core on both device images. Qwen3.8's `qwen_sampling.cu` performs the same operations in the same groupings, spread over the GPU (Qwen3.8, below); `tests/qwen_ops.rs` checks it the same way.

**The idle-KV cipher is defined in the serving core.** `eidola-engine`'s `kv_cipher.rs` defines the cipher idle prefix-cache blocks are held under (ChaCha20's block function, a 32-bit counter, a 96-bit nonce, no Poly1305) and how a block's ranges take the keystream; `kv_cipher.cu` transliterates it. It is additions, funnel-shift rotations and XORs on 32-bit words, with no table and no secret-dependent address or branch, so it is constant-time on the device. One launch takes a device list of 64-byte items (range address, words, starting counter, key, nonce); the host zeroes the list on the stream right after the launch, and the kernel keeps the key and the keystream block in registers (its resource report shows no stack frame and no local memory; the tail of a range is an unrolled loop with constant indices so the keystream array is never indexed dynamically). A thread computes one 64-byte keystream block and XORs it as four 16-byte vectors when the range is 16-byte aligned, word by word otherwise. `eidola-engine-cuda`'s `tests/kv_cipher.rs` checks it against the core byte for byte on both device images.

**Draft ids are bounded on the device.** A drafted step's drafts are drawn by `eidola_sample` and read by the next forward's embedding and by `eidola_chain_accept` without passing through the host, so the two kernels bound them: `eidola_sample` writes no token id at or past the sampleable vocabulary `n` (none can arise: every argmax and draw it makes is below `n`; it would write 0 and raise `kStatusBadToken`, status bit 2), and `eidola_chain_accept` checks every draft id against `n` before reading a distribution through it (raising the bit and ending the row with no tokens). Acceptance reads draft `i` of row `r` at row `draft_row[r] + i × draft_step` of the draft distributions and of the ids: contiguous per row with a step of 1 (a host plan), or one depth's drafts of every row together with a step of the row count (the drafter's lanes). The arithmetic is unchanged. Qwen's sampler bounds its tokens the same way, and its acceptance checks the ids in `eidola_qwen_accept_decide`, before the other two acceptance kernels read anything through them.

Every kernel is built for all three targets; each fatbin bundles the `sm_100a` and `sm_103a` cubins so the driver picks the exact match. Instantiation choices (tile shapes, stages, thread counts) mirror what the upstream host dispatchers pick for these shapes; each source file explains its own.

### Batch-invariant attention

`flashinfer_fa2_sink_paged.cu` instantiates FlashInfer's paged prefill template at one KV shape (`NUM_WARPS_KV` 1, `NUM_MMA_KV` 4: 64-key tiles) for every query tile, rather than the shape FlashInfer's dispatcher derives from the query tile, so a row's softmax is reduced in the same order whichever tile it lands in, as long as the tile lies inside one 64-key KV tile (the host cuts every request so: a CTA walks KV tiles to its last row's, and its rescale after a fully masked trailing KV tile is not exactly 1 under `-use_fast_math`). Global-layer instances use FlashInfer's `AttentionSink` and run split: each work item one 1,024-key chunk (the host's `kv_chunk_size`), the sink added in chunk 0 only, the partials merged by the merge instance in chunk order. Sliding-layer instances use `AnchoredSink`: `AttentionSink` with each query tile's keys started at a multiple of 64 from the first listed key (a widened window), and the true window enforced per key in `LogitsTransform` (the kernel masks only the iterations it predicts need it); it refuses to run split. Every entry walks its work list from its block index in steps of the grid up to a count it reads from device memory, presenting each item to FlashInfer's device function as that CTA's (`ItemParams` carries the item to the variant), so a launch with a fixed grid can serve a work list whose length is device data. `eidola-engine-cuda/AGENTS.md` → Batch invariance gives the host side and the guarantee.

### The decode path's small kernels

At one decode row these launch per layer, so their geometry is chosen for small token counts first; every launch's shape is a function of the token count alone (a decode graph's rung). The ones whose work grows with a prefill's tokens (the fused QKV, the f32-scale quantization, the gather, both SwiGLUs, the combine) move 16-byte vectors per thread, so a mixed or prefill step's hundreds to thousands of tokens stream at a large share of memory bandwidth rather than being bound by one scalar load chain per element. Flash: hidden 4096, 256 experts, top 8, expert intermediate 2048, dense intermediate 16,384; per attention layer 4 rank chunks of 16 query heads and 1 (global) or 2 (sliding) KV heads.

The executor picks the form by the step's token count (`eidola-engine-cuda`'s `engine_ops.rs`, `executor_router`; `ROUTER_PER_TOKEN_MAX`'s comment records the measurements behind the bound): the one-token form at up to 15 tokens, the two-launch form above. The one-token form puts a token's whole expert dimension on one 8-block cluster and selects on its rank 0, so each cluster reads the whole 2 MiB router weight for its token; on a B300 it costs 20.5–22.4 µs a layer at 1 to 15 tokens, 4–6 µs under the two-launch form, and then grows in steps once its clusters no longer all run at once (37.7–38.9 µs at 16, 93.3 at 64). The two-launch form spreads the expert dimension over 16 blocks per 8 tokens, without a cluster barrier, and selects with one warp per token; it costs 25.6–27.6 µs from 1 to 64 tokens.

**Why the expert SwiGLU is one block per pair.** The SwiGLU is the one glue kernel with real arithmetic per element: the reference's exact `expf` (a `MUFU.EX2` and seven FP32 instructions) and an IEEE division (`MUFU.RCP`, five dependent `FFMA`s and an `FCHK` guarding a slow-path call, so each element's division is its own reconvergence region), the dense form a second division by the scale. Its 16-byte form (a block per pair and 1024 elements) ran only 1.2–1.5× its reference, where the memory-bound gather and fused QKV ran 2.6–3.7×. A form in which each warp walked 256-element items of the pairs, loading the next item (and the row index of the one after) before computing the current one, over a grid of 8 blocks of 4 warps an SM, computing a lane's eight exponentials before its eight divisions, was modelled as issue-bound (about 360 instructions a warp per 256 elements, roughly 40 µs of issue at 2,048 tokens against roughly 24 µs of memory) and expected near 2×; on a B300 it ran 0.79–0.87× of the block-per-pair form from 128 tokens up (95.6 against 75.8 µs at 2,048 tokens). The model was wrong: the kernel is bound by the latency of each warp's dependent chains (an element's division alone is six dependent instructions behind a `MUFU.RCP`, and the eight divisions run one after another), not by issue. The block-per-pair form keeps 64 warps resident an SM (32 registers), the walking form 32 (55 registers, and the grid sized for 8 blocks an SM), and halving the warps that hide those chains cost more than prefetching the loads saved. So the expert SwiGLU stays one block per pair. The dense SwiGLU walks items in that form anyway: its reference ran 32-thread blocks of scalar loads, and walking measured 1.16–1.50× faster from 32 rows up; at 1 to 4 rows (16 to 64 warps on as many SMs) it is about 1 µs slower than its reference (6.2 against 5.1 µs), on the one dense layer and the MTP layers, which is left as it is rather than carry a second dense kernel. Raising resident warps (fewer registers) or splitting each lane's divisions over more lanes are the levers left for the expert SwiGLU; neither has been measured.

**The numerics are the reference forms'**, bit for bit; the geometry only moves where the arithmetic runs:

- **Router.** A logit is lane `l`'s sequential fused multiply-add over `i = l, l + 32, …` in ascending order, then the xor butterfly over the warp, then `1 / (1 + expf(-x))`; the selection takes, per round, the untaken expert a scan in expert order keeping the first strictly greater choice would take. Under the order (choice greater, or equal and lower id) that is the maximum over non-NaN choices, unless the lowest untaken expert's choice is NaN, in which case that expert; the warp computes exactly that, and the order is total, so the shuffle tree cannot change the result. The weight sum runs over the selection in ascending id order, as before. The two-launch form keeps every chain as it is: their lane `l` runs the same residue class in the same ascending order for each (token, expert) it owns (the chunks are consumed in order), the butterfly is the same `warp_sum`, lane 0's sum is the one used, and the sigmoid's SASS matches the one-token form's (the same `FFMA` contraction of `1 + expf(-x)`, then the reciprocal). Only which thread runs a chain and how its operands reach shared memory change. The two-launch form's selection runs the one-token form's rounds over the same choices, read from global memory instead of distributed shared memory; the picks are distinct, so the sorting network orders them as the insertion sort did, and the weight sum runs over them in that ascending order. The reference form ran 32 experts per warp on one block per token, its dot products bound by one load round trip per eight elements, and the selection on one thread.
- **Quantization, gather and SwiGLU** compute each row (each routed row, for the gather and the expert SwiGLU) exactly as the per-row reference does: each element with the same expressions, each group's amax a maximum (which no reduction order changes; NaN never wins `fmaxf`). The f32-scale forms keep the reference's IEEE division by the scale (`x / scale`, not a reciprocal), and the dense SwiGLU its `x / (1 + expf(-x)) * u` (computing a lane's eight denominators first only reorders independent work; the SASS keeps the same `+ 1` contraction into the exponential's last `FFMA`). The reference forms of the f32-scale quantization and dense SwiGLU are the kernels they replace, and compile to the same SASS. The gather quantizes a token's word once for all its pairs, which carry the same row. The gather and the expert SwiGLU do not touch the layout's padding rows: the reference forms launch over every row of the layout (every pair plus up to 127 padding rows per expert reached), zero-filling them in the gather. The grouped GEMMs compute each output row from its own A row and scales only, and the combine reads only the rows `row_of` names, so a padding row's contents reach nothing the executor uses.
- **Placement.** `eidola_moe_permute` has no arithmetic; its host form is `eidola-engine-cuda`'s `mimo::engine_ops::expert_placement` (pairs in order within an expert), which `tests/mimo_moe_ops.rs` compares with the kernel word for word. Blocks, warps and lanes cover the pairs in order, and each block's first row in an expert's run is that expert's count in the blocks before it, so the multi-block form places every pair where the one-block form did. Above 5,120 pairs the counts cross blocks only through the boundary between its two launches, so no block ever waits for another and nothing assumes the grid is resident at once (a grid barrier would hang on a part, a profiler or a shared device that left a block unscheduled).
- **Combine.** Each element is `acc = 0`, then `acc = fma(w_j, d_j, acc)` for slots `j` ascending: the contraction the reference's `acc += w * d` compiles to (its SASS is that `FFMA` chain from `RZ`), written out. The reference ran one 256-thread block per token, each thread walking 16 elements with the slots' loads serialized behind each other.
- **Fused QKV.** Each output element is computed by one thread with the reference's expressions; the rotation is written as the contraction the reference compiles to (`fma(x1, cos, -(x2 · sin))` for the first half, `fma(x2, cos, x1 · sin)` for the second: the rounded product is the second one in both). The reference ran one 256-thread block per token, about 58 serial steps a thread, each step's loads ordered behind the previous step's stores.

**Row copies** (`eidola_copy_rows`): the drafted step's gathers and scatters of hidden states, drafter state, boundary taps and token ids. One launch copies items of `width` 32-bit words between up to eight buffers (a by-value `EidolaCopyArgs` of 176 bytes: the buffers' addresses and row counts, the four item arrays, the status word), item `i` row `src_row[i]` of buffer `src_buf[i]` to row `dst_row[i]` of buffer `dst_buf[i]`; every buffer and row index is bounded by the kernel against the buffer's rows, and an item out of range copies nothing and raises `kStatusBadIndex` (bit 4). Grid (items, ⌈width / 256⌉), a thread per word. Items must not overlap (the host plans them so). A copy has no arithmetic, so its reference form is the host gather itself: `eidola-engine-cuda`'s `tests/mimo_copy_rows.rs` compares word for word.

`eidola-engine-cuda`'s `tests/mimo_moe_ops.rs` checks the router (both forms), gather, SwiGLU and combine against the reference image bit for bit from 1 to 8,192 tokens (ties, NaN and infinite choices and rows, scale-range extremes), `tests/quant_ops.rs` the f32-scale quantization and dense SwiGLU, `tests/qkv_rope_kv.rs` checks the fused-QKV kernel's Q and every pool byte for both KV head counts, and the `mimo_moe_kernel_bench` example times each against its reference form, and the router in every form, per token count.

`tests/manifest.rs` holds the SASS facts above as assertions on the manifest, so a source or toolkit change that silently drops a GEMM off tcgen05 fails `cargo test`.

## DeepSeek-V4.1 numerics and ABI

The second model's kernels must equal `eidola-engine-model`'s DeepSeek reference bit for bit (that crate's `AGENTS.md` → Numerics contract). Three files carry what they share, and every kernel of the forward is built from them: the scalar kernels (*The scalar kernels*), the attention, index and selection kernels (*DeepSeek-V4.1 attention, index and selection*), and the probe. `eidola-engine-cuda`'s `DsCudaExecutor` launches them (that crate's `AGENTS.md` → DeepSeek-V4.1).

### The numerics core (`csrc/ds_numeric.cuh`)

Every rounding point, scale rule, exact block product, pinned order and transcendental of the reference, each function naming the Rust one it reproduces: `bf16_round`; the E4M3, E2M1 and E8M0 decodes; the casts to E4M3 and E2M1 as stored codes (nearest, ties to the even code, saturating; integer arithmetic on the f32's bits, not a table search); `round_scale` and the three block scales with their floors; the quantiser blocks; the FP8 × FP8 and FP8 × FP4 block dots as integer sums rounded once; the quantised GEMM's accumulation step; `pinned_dot` and `pinned_sum`; `det_exp`, `det_ln`, `det_sin_cos` and the f32 functions over them (`exp32`, `sigmoid32`, `silu32`, `softplus32`, `pow32`, `rsqrt32`) in f64 where the reference uses f64; RMS norm's factor, the RoPE rotations, the SwiGLU element; the top-k order as a key and a comparison.

- **Plain C++, one source for device and host.** The arithmetic is IEEE `+ - * /`, `sqrtf`, `floor`, conversions and bit casts, with no rounding intrinsic, so the header compiles for a kernel and for the host check unchanged. It is right only if nothing fuses or reorders, which the `exact` profile holds on the device and `-ffp-contract=off` on a host.
- **Do not use `engine_ops_common.cuh`'s casts or scale recipe** in a DeepSeek kernel: `f2e4m3` leaves ties to the toolkit and `ue8m0_for` calls `log2f`.
- **Where it departs from the reference's expression, the result is the same and the vectors hold it.** A power-of-two quantiser multiplies by the scale's reciprocal (`act_scale_recip`) where the reference divides: both round the same real number once. The FP8 × FP8 block dot is an `i64` sum in units of 2^-18 where the reference adds f64 products, both exact.
- **Activation scales are one byte**, the f32 scale's exponent field (`act_scale_byte`): E8M0 for every finite activation, and 255 for the infinite scale of a block holding an infinite activation (`act_scale_decode` returns infinity there; a weight's E8M0 has NaN at 255).
- **A NaN casts to code `+0`**, whatever its sign and payload, in both casts, as in the reference: which NaN an invalid operation returns differs between processors (x86 returns a negative one where Arm returns a positive one), and a quantiser reaches one whenever a block holds an infinite activation (the infinite element times the infinite scale's zero reciprocal). A NaN that stays a NaN (`bf16_round`, a dequantised `0 · ∞`, a transcendental) has no specified sign or payload; the vectors record one canonically.
- **A NaN score ranks as negative infinity** in every top-k (`topk_key`), whatever its sign and payload, and **a stored BF16 result that is NaN is `0x7fc0`** (`bf16_store`, which every kernel stores a computed BF16 through): `f32::total_cmp` would rank a NaN by its sign, the top 16 bits of a NaN whose payload sits in the low 16 are an infinity, and which NaN an operation returns differs between processors. The Engram gate's product, when NaN, counts as `+0` for the same reason (`dsk::inject_gate`: the gate takes its sign). The vectors hold each rule: top-k over NaNs of both signs and several payloads, and Engram cases with a NaN key.
- **Preconditions are the reference's**: `det_ln` takes a positive normal, `det_sin_cos` a magnitude under about 1.6e6, `softplus32` no NaN, and the block dots no NaN code (a loader refuses a weight holding one).

### The `exact` profile

`-std=c++17 -O3 --fmad=false`, for every translation unit that includes the numerics core.

- `--fmad=false` stops nvcc contracting a multiply and an add or subtract into a fused multiply-add: every such operation reaches PTX with an explicit round-to-nearest mode (`mul.rn`, `add.rn`), which ptxas does not fuse.
- No `-use_fast_math` and no other floating-point option: without one nvcc keeps IEEE division and square root, does not reassociate, and does not replace a division by a reciprocal multiply.
- `-std=c++17 -O3` are the `own` profile's.

**How it is held.** The build compiles each source of a profile carrying `--fmad=false` to PTX as well (`inspect/<name>.<arch>.ptx`) and records in the manifest, per cubin, `float_ops`: `fma` instructions in the PTX, floating-point multiplies, adds and subtracts without a rounding mode, those with one, and the `FFMA`/`DFMA` count of the SASS. `tests/manifest.rs` (`exact_profiles_fuse_no_multiply_add`) requires the first two to be zero for every such cubin. The SASS count alone cannot be required to be zero: ptxas expands a division, a reciprocal and a square root into fused multiply-adds of its own (the full probe's 179, from 17 f32 and 5 f64 divisions, two reciprocals and a square root). `ds_probe_nodiv` is the probe without those ops, and its SASS must hold none: 989 rounded operations (the exponential's and the sine's Horner steps, the pinned dot, the rotations, the GEMM accumulation), zero fused. A kernel of the forward that does not divide can be asserted the same way.

**Control.** The two probe sources built with `--fmad=true` in place of `--fmad=false`, counted the same way: 334 and 219 `fma` in the PTX, 654 and 551 multiplies, adds and subtracts without a rounding mode and none with one, and 223 fused multiply-adds in the division-free probe's SASS (ptxas fuses four more than nvcc). Every other cubin of the set is byte-identical in that build. Repeat the control when the toolkit moves.

### The host check and the vectors

`eidola-engine-model`'s `tests/deepseek_numeric_vectors.rs` emits `tests/data/ds_numeric.vectors` from the reference's public functions and fails when the committed file is not what it emits (`EIDOLA_UPDATE_DS_VECTORS=1` rewrites it); its header documents the format. The file holds explicit cases (every decode; every E4M3 and E2M1 code point, tie and saturation edge with both neighbours and both signs; scales either side of every power of two and at the floors; quantiser blocks at the floors, with zeros of both signs, and with NaNs of both signs and several payloads beside finite and infinite elements; block dots at the extremes; the transcendentals at their pinned arguments, cut-offs and reduction boundaries; RoPE powers and table entries of the released configuration; pinned orders at every length around a chunk; top-k with ties, signed zeros and NaNs) and seeded sweeps as digests: 2^22 inputs for each one-argument function and `round_scale`, 2^20 to 2^21 for the others in f64 and the element-wise composites, 2^16 to 2^18 blocks for the quantisers (once plain and once with infinities, NaNs and zeros mixed in), block dots, pinned orders, RMS norm and top-k, and 2^13 whole `lin8` and `lin4` products of up to 40 rows and 4 blocks. `ds_numeric.exhaustive` holds a digest over all 2^32 f32 inputs of each one-argument function (`bf16_round`, both casts, `exp32`, `sigmoid32`, `silu32`, `softplus32`, `rsqrt32`), emitted by the ignored `exhaustive_digests_are_current`. A NaN result is recorded canonically, since processors differ in which NaN they return.

`oracle/ds_numeric_host.cc` includes the two headers, mirrors the sweep generators, and checks every record:

```sh
cargo test -p eidola-engine-kernels --test deepseek_numeric_host                 # the vectors, at -O2 and -O0
cargo test -p eidola-engine-kernels --test deepseek_numeric_host -- --ignored    # and every f32 (about two CPU-minutes)
```

`tests/deepseek_numeric_host.rs` compiles it with `$CXX`, else the system `c++`, at `-ffp-contract=off`, and passes with a message on stderr when there is no compiler. The system compiler was chosen over the pinned one of the Nix environment because the check has to run in a plain `cargo test` on a developer machine and in CI, where that environment exists only inside the kernel builder's container; nothing depends on which compiler or processor it is, since the header uses only operations IEEE fixes and lets no NaN's sign or payload reach a code (it passes under Apple clang on arm64 and GCC 13 on x86_64, at `-O0` and `-O2`). With contraction left on (`-ffp-contract=fast`) 28 records fail, so the vectors do detect a fused multiply-add. The check shows the header's arithmetic is the reference's. What nvcc emits for it is held by the profile above and, on a GPU, by replaying the same vectors through `eidola_ds_probe` (`DsProbeParams`: an item per thread, words laid out as the vector file's records).

### The ABI (`csrc/ds_abi.cuh`)

The by-value parameter struct of each kernel family of the forward, with every field's meaning, and the conventions they share; `eidola-engine-cuda`'s `src/deepseek/abi.rs` mirrors it. Both sides assert every struct's size, alignment and field offsets at compile time (the header's assertions also compile in the host check). The header is normative; change both files together.

Decisions the structs fix:

- **BF16 between kernels is 16 bits on the device**; f32 arrays are only what the reference keeps in f32. **A fake-quantised vector exists only as codes and scales**, in the pools and in scratch alike: a code times its scale is the reference's BF16 value exactly, so every consumer dequantises on load (`ds::dequant_*`) and no widened copy is kept.
- **Rows are prefixes.** The executor orders a step's positions deepest-computed first, so the positions a layer computes are rows `0 .. rows` of every array and no kernel takes a row list. A window-chain layer runs its KV write over the rows it computes and its attention onward over the shorter prefix the next layer computes.
- **KV blocks are contiguous**, each layer's (or bank source's) planes back to back in the order the header gives, which is also the order a block is zeroed, copied and enciphered. An entry is `block id · entries per block + offset`; `DsKvPlane` turns it into two addresses. Window entries are FP8 (`width` codes, a scale byte per 32), global KV entries FP4 with an E4M3 scale per 16, index keys FP4 with a power-of-two scale per 32.
- **A slot list is data**: per query, `a_slots` entry indices into one plane then `b_slots` into another, `DS_SLOT_EMPTY` for an empty slot, a slot's index fixing its 64-slot block. The window words are the same for every layer of a group (built once a step, on the host or by the `DsWindowSlotsParams` kernel); the global words are rewritten only by a layer that selects (`DsSelectParams`) and reused by the layers after it. Unused trailing slots are empty, which changes nothing. A drafter block lists its window in ring order and then the draft slots' KV from scratch, through the same struct under `DS_ATTN_PACKED`: the reference's drafter list has no slot for a position a short sequence has not reached, so the draft slots follow the last listed window slot, and a fixed place for them would put them in another 64-slot block until the window is full.
- **A BF16 result that is NaN is stored as `0x7fc0`** (`ds::bf16_store`), by every kernel that stores a computed BF16; a copy (the embedding, a gathered row) keeps its bits.
- **The grouped projection (`wo_a`) keeps its stored FP8 weight** and dequantises it on load, like its input; the product is the pinned dot of the two.
- **The router writes a row's experts in ascending id** with their weights, after normalising with the sum taken in selection order; placement, the SwiGLU's weights and the combine all read that order.
- **The expert layout** is expert-major with each run started on a multiple of `row_align`; `DsPlaceParams` also scatters each pair's routing weight to its layout row. Activation codes and their scale bytes reach the layout through `DsPlaceRowsParams`, a byte copy by the placement's `row_of` (a scale row is `width / 32` bytes, not whole words, so MiMo's word-wise row copy does not serve). Gate and up outputs are two pointers and a stride, so the two weights may be stored fused or apart.
- **Engram rows are gathered as stored** (codes and E8M0 scales), which is also what crosses between devices; the quantiser takes stored FP8 rows as an input format and dequantises them as the reference reads them.
- **Candidate blocks** are a bit per block of `block_entries` entries.
- **Pooling is ratio 2**: two members per entry, named by row index, so an open pair kept in per-slot state is one more row.
- **Status bits** `DS_STATUS_BAD_TOKEN` (0x100) and `DS_STATUS_BAD_INDEX` (0x200) are apart from the sampler's and the row copy's, so one status word can serve a whole step.
- **The tensor-core GEMMs take the scalar forms' structs** (`DsLin8Params`, `DsLin4Params`) and layouts unchanged, `lin4` at any `row_align`; the scalar forms are the definition they are held to.

### The scalar kernels

Every kernel of the forward that is not attention, selection or a tensor-core GEMM. `csrc/ds_ops.cuh` holds each kernel's body as plain functions of its parameter struct and the thread's place in the launch, written from `ds_numeric.cuh` and IEEE `+ - * /` in the reference's order; a `.cu` file only places a body on a grid. The same header compiles for the host check, so what is checked on a host is the source the device runs.

Two shapes of kernel:

- **A thread computes a whole unit**: an element, a 32-wide block (its 32 loads, its amax, its 32 codes and its scale), one output of a quantised GEMM. `<kernel>_thread` is the entire kernel.
- **A pinned-order dot or sum runs on 16 threads** (half a warp), thread `j` holding lane `j` of `tensor::dot`: the terms `i ≡ j (mod 16)` of the full chunks, added in ascending `i` from +0. The group's first thread collects the 16 lane sums (`ds_shuffle.cuh`: 16 warp shuffles, the one device-only step) and finishes with `ds::pinned_reduce` and the tail. A lane thread carries several independent chains at once: 4 outputs of one row in the plain product and the grouped projection, 8 rows of one weight row in the head.

**Why each equals its reference bit for bit.** Every floating-point operation is a function of `ds_numeric.cuh` (held to the reference by its own vectors) or an IEEE operation written in the reference's order, and the `exact` profile fuses and reorders nothing. What the layout adds:

- **A maximum has no order** (`amax` of a block, a row's softmax maximum), so one thread's loop is the reference's fold.
- **A lane is one chain** of the pinned dot, so 16 threads are its 16 partial sums, and `ds::pinned_reduce` over the collected sums is its tree and tail. Chains of different outputs share nothing.
- **Selection is comparisons.** The router's round `r` takes the best expert ranked after round `r - 1`'s under `ds::topk_before`; the order is total and strict, so that is the best not yet taken, as the reference's sort gives. Weights are normalised in selection order and then written in ascending expert id.
- **The grouped projection** reads `ds::dequant_e4m3` of its input codes and `bf16(e4m3 · e8m0)` of its weight codes, the values the reference holds in BF16, and takes their pinned dot. It may later be defined as a block product; until then it lives beside the reference GEMMs.
- **Placement is integers**: a group's first row is the previous group's end rounded up to `row_align`, from the counts the first launch wrote; the two launches meet only at that boundary.

**Why a row's result is its own.** A thread reads its own row's arrays (and the weights) and writes its own row's outputs; no value of the launch's shape enters any arithmetic; a grid dimension is a function of the row count and the widths alone. The lane kernels exchange values only inside a lane group, which belongs to one row (the head's group to one weight row, each of its chains to one row). Two kernels read across rows by design, through data the host or another kernel wrote: the placement (a group's pairs come from every row; its result is the layout, defined over the step) and the kernels that follow `row_of` or `x_rows`. A kernel that may write over its input (`rms_norm`, `expand`, `engram_inject`) finishes every read of a unit before its first write, behind a block barrier where another thread's sum needs the row.

**Division-free images.** `ds_ops`, `ds_reference` and `ds_head` hold no division and no square root, and `tests/manifest.rs` (`ds_scalar_kernels_fuse_nothing`) requires their SASS to hold no fused multiply-add on every target: 730, 95 and 233 rounded operations, zero fused. The kernels that divide or take a square root are apart in `ds_ops_div` (its 1,182 fused multiply-adds are ptxas's expansions of its divisions; its PTX is held like every exact image's). That is why the global KV's fake quantisation (`DS_KV_FP4_E4M3`, two IEEE divisions) has its own entry beside `rot_quant`.

**The host check.** `eidola-engine-cuda`'s `tests/deepseek_cases` draws each kernel's inputs from a seeded generator, computes the outputs with the model crate's functions, and emits one digest per sweep to `tests/data/ds_ops.vectors` and `ds_gemm_ref.vectors` (512 cases of small random shapes, so every grid remainder occurs, and 2 at the released widths, per kernel; `vectors_are_current` in that crate's `tests/deepseek_ops.rs` and `tests/deepseek_gemm_ref.rs`, rewritten under `EIDOLA_UPDATE_DS_VECTORS=1`). `oracle/ds_kernels_host.cc` repeats the draws, runs each kernel's body thread by thread over its grid (blocks and threads in descending order; lane sums collected as the shuffles would), and must reproduce every digest:

```sh
cargo test -p eidola-engine-kernels --test deepseek_kernels_host   # at -O2 and -O0
```

The `lin8` cases run the quantiser and then the product, the `lin4` cases the placement launches too. No case's output is a NaN and none holds an infinity: which NaN an operation produces differs between processors. One Engram case in four holds a NaN in a key, whose gate is the one a `+0` product gives. With contraction left on (`-ffp-contract=fast`) 8 sweeps fail; reversing the combine's or the stream mean's order, dropping the router's normaliser floor, the addend, a run's alignment or a padding row's test each fails at least one. Where the reference has no function of its own for a kernel's step (the pooling and the feed-forward sum are inside larger functions, the FP4 codes inside `fake_quant_fp4_*`), the cases compose it from the reference's public functions by the rule the reference states, and check the composition against the public function where one exists (the fake quantisations' values; `engram::inject`). The check shows the bodies and the grids are right; what nvcc emits is held by the profile, the SASS assertion and the device tests (`eidola-engine-cuda/AGENTS.md` → DeepSeek-V4.1).

## DeepSeek-V4.1 attention, index and selection

Four kernels, each bit-identical to a function of `eidola-engine-model`'s `deepseek::attention`: no tensor cores, every operation the reference's in the reference's order. The sources are the reference's steps transliterated; this section gives the structure, what makes each batch-invariant, and how they are checked.

### One body for the device and the host (`csrc/ds_body.cuh`)

A kernel whose threads cooperate is a function template over a phase runner: a sequence of `par.run([&](uint32_t t) { … })`, thread `t`'s share of one phase, with every value that crosses a phase kept in the block's shared struct. On the device each thread runs the body, executes a phase for its own index and meets a block barrier; on a host the runner calls the phase for every index. The device entries in the `.cu` files are a few lines; the bodies in the `.cuh` files compile unchanged for the host check, which therefore runs the kernels' real thread decomposition (lanes, per-thread runs, histograms), not a second implementation. The two agree when no thread reads in a phase what another writes in it, and when everything outside a phase is a function of the parameters and of shared memory read after a barrier. The host check runs every body in ascending and descending thread order over shared memory that starts as garbage, which exposes a read inside a phase or of unwritten memory; it cannot expose every race, so **keep phases free of cross-thread reads by construction** when editing.

**Never call a `constexpr` helper of `ds_abi.cuh` from device code** (`ds_kv_code_bytes`, `ds_kv_scale_bytes`, `ds_mix_words`). They are host functions; without `--expt-relaxed-constexpr` nvcc compiles a device call of one silently into a trap and drops the code after it. The first device run showed it: the stores behind a plane's address were gone, so index scores were all +0 and attention read unset addresses, while the host check, which compiles the same source for a host, passed. Device code uses `ds::kv_code_bytes` and `ds::kv_scale_bytes` (`ds_body.cuh`); `tests/deepseek_attention_manifest.rs` refuses a device source that calls the header's.

### The kernels

| Entry | Reference | Geometry |
|---|---|---|
| `eidola_ds_attn` | `sparse_attend` of every row over its slot list | Grid `(x, rows)`, 512 threads, 96,408 bytes of dynamic shared memory. Block `(bx, row)` computes heads `bx · g ..` of the row, `g = ceil(heads / x)` at most 8. Per 64-slot block of the list: the entries' addresses (a thread per slot), their values dequantised into shared memory as BF16 bits (a thread per element, once for all the block's heads); then per head the scores (thread `t` adds lane `t % 16` of slots `t / 16` and `t / 16 + 32`, ascending, and a thread per slot runs the halving tree), the block's maximum, `exp32` and the BF16 weight per slot, and the value sum (a thread per element, the slots in order). `head_dim` a multiple of 16 up to 512 |
| `eidola_ds_window_slots` | the canonical window of `forward.rs` (right-aligned, position order) and `drafter::ring_order` | Grid `(ceil(window / 128), rows)`, a thread per slot |
| `eidola_ds_index_score` | `index_score` of every visible entry | Grid `(x, rows)`, 256 threads, 21,792 bytes of shared memory. A block dequantises its row's index queries once, then walks the passes `bx, bx + x, …`: 8 entries a pass, a warp per entry, a lane per index head running the whole pinned dot of that head, lane 0 the pinned sum over heads. At most 32 heads of at most 128 |
| `eidola_ds_select` | `top_k` (score descending, index ascending), `candidate_mask`, and the selection appended ascending to the slot lists | Grid `rows`, 512 threads: one block per row. A BF16 score's rank key (`ds::topk_key`) has 16 significant bits, so two 256-bucket counting passes over the visible entries find the k-th best key; every candidate above it is selected and, of those equal to it, the first in index order. A third pass counts each thread's contiguous run, one thread prefixes the 512 counts, and a last pass writes each selected entry at its rank: the output is ascending with no sort. The candidate blocks run the same four passes over block scores (a block's best entry, +inf for the newest) and write a bit per block |

**What the selection is defined by.** Only comparisons: `-0` and `+0` are one key, a NaN of any sign and payload ranks as negative infinity, a block of NaN or -inf alone scores -inf and is never kept, and fewer candidates than `k` selects them all and leaves the rest of the slots empty. The candidate source passes `mask_out` and no `mask_in` (it selects over everything it sees and only publishes the blocks); a later index source passes `mask_in`.

**What the host must keep.** Slot words inside their planes; `visible` at most `score_stride` (past it the kernels clamp and raise `DS_STATUS_BAD_INDEX`); table rows covering what a row lists (a negative word raises the bit, giving an empty slot or a score of +0).

### Batch invariance

A step's launches have **data-independent geometry**: each grid is a function of the row count and of configuration (head counts, the window, the capacity of a score row), never of positions, visible entries, slot contents or scores, which are device data. That is what lets a decode step be captured once and replayed.

- **Attention.** A (row, head)'s output is computed by one block from that row's query, slot words and the entries they name, by a fixed sequence of operations per slot block. The grid's width only decides how many heads share a block's dequantised entries; a head's operations do not depend on which other heads or rows are in the launch.
- **Window slots.** A slot word is a function of its row's position, first position and table.
- **Index scores.** An entry's score is computed by one warp from the row's queries and that entry's key; which block and pass reaches it depends on the grid, its arithmetic does not.
- **Selection.** One block per row, reading only that row's scores, mask and table. The counts are integers, so the order the threads add them in cannot matter.

### Verification without a device

- `eidola-engine-model`'s `tests/deepseek_attention_vectors.rs` emits `tests/data/ds_attention.vectors` from the reference (attention over packed entries in every format and layout, window slots in both orders, index scores, selections with ties, signed zeros, NaNs and masks) and fails when the committed file is not what it emits (`EIDOLA_UPDATE_DS_VECTORS=1` rewrites it). `tests/deepseek_attention_host.rs` compiles `oracle/ds_attention_host.cc` with the system C++ compiler (as *The host check and the vectors*) and requires every record to match at `-O2` and `-O0`, at every grid width.
- The same program runs **jobs**: `eidola-engine-cuda`'s `tests/deepseek_attention.rs` and `tests/deepseek_index.rs` build each GPU case as parameter structs over one buffer and, in a plain `cargo test`, run it through the host bodies, so the cases, the parameter structs and the expected bytes of the GPU tests are exercised without a GPU. Those tests carry the volume: seeded sweeps, the released shapes, 1 to 131,072 visible entries, and a layer's whole chain.
- **The pinned orders need adversarial inputs.** The operands are BF16 values times 4-bit codes, so most products and many sums are exact and an implementation with another summation order passes ordinary inputs. The vectors and the sweeps therefore include cases whose large terms cancel exactly, within a lane and across lanes (`deepseek_attention_cases::cancelling`), leaving a score that is the rounding residue: another lane order, a sequential tree or a sequential head sum then changes the output (each was checked by mutation). For the same reason a fused multiply-add changes almost nothing here: only `den · r + block_sum` could differ, by one ulp of a value that reaches the output through a division and a BF16 rounding, and no test detects that. On the device it is held by the `exact` profile, not by the vectors.
- `tests/deepseek_attention_manifest.rs`: both images are `exact`, hold their entries and no fused or unrounded operation in PTX; `ds_index` has no division and no fused multiply-add in its SASS at all; `ds_attention`'s 37 are its one division's expansion (five per inlined `values / normaliser` site, the rest the slow path).

## DeepSeek-V4.1 tensor-core GEMMs

`ds_gemm_tc.cu` computes `lin8` and `lin4` (`DsLin8Params`, `DsLin4Params`: per row and output, the 32-wide blocks ascending, `acc = acc + (dot · activation scale) · weight scale` in f32 with `dot` the block's exact dot product rounded once, then BF16) with the block products on the tensor cores. `ds_gemm_tc.cuh` holds every piece a thread computes (staging copies, fragments, conversions, bands, the block contributions, the accumulation and the store) as plain functions, which the host check runs too. Everything after a block's dot product is the reference's own arithmetic (`ds::gemm_accumulate`'s operations, `bf16_round`, `bf16_store`).

**The block product.** `sm_100a` and `sm_103a` have no warp-level FP8 MMA: an E4M3 `mma.sync` compiles to conversions to F16 and two `HMMA.16816.F32`. The kernels do that themselves: each code is converted once (`cvt.rn.f16x2.e4m3x2`; FP4 weights by `cvt.rn.f16x2.e2m1x2`, `F2FP.F16.E2M1.UNPACK_B`, on the host by a `prmt` table), exactly, since every E4M3 and E2M1 value is an F16 value, and a block's product is two chained `mma.m16n8k16` (F16 operands, f32 accumulator) from zero. The operands are swapped (A is 16 weight rows, B 8 activation rows), both K-contiguous as stored, and lane `q` takes four consecutive codes per row and half of the block: a dot product does not depend on which slot of K holds which `k`, as long as A and B agree.

**Two forms.**

- **Banded (exact).** Codes are split by exponent field into bands (a code outside a band is +0 there): FP8 weights `{[0, 8], [9, 15]}` against activations `{[0, 5], [6, 10], [11, 15]}` (six block products a block), FP4 weights unbanded against activations `{[0, 8], [9, 15]}` (two). The cut is a compare of each F16 half's magnitude against a threshold exponent (`at_least`), one mask per cut. Within a pair every product is an integer multiple of one power of two and the 32 products' magnitudes sum below 2^24 of it (`32 · 1,920 · 240` for FP8 × FP8, `32 · 1,920 · 12` for FP8 × FP4), so every partial sum in any order is an f32 value, and an adder that is exact on exactly representable sums returns the pair's exact sum whatever its order, alignment or internal width above 24 bits. The pairs' sums are combined exactly in f32 and rounded once (`pair8` / `pair4`, `block_dot8` / `block_dot4`): each pair's sum `p` is split into `r · 2^c` with `r` the nearest integer to `p / 2^c` (by adding and subtracting 1.5 · 2^23) and the remainder `p - r · 2^c`; the integer parts and the remainders each add exactly (the block's whole magnitude is below 2^23 for FP8 × FP8, 2^17 for FP8 × FP4), and the dot is `hi · 2^c + lo`, one IEEE addition of two exact values: `ds::fp8_fp8_block_dot` / `fp8_fp4_block_dot` bit for bit. All FP32 additions and multiplications by powers of two: no 64-bit integer conversion, which on these parts runs on the FP64 pipe. A band empty across a warp's operands is skipped (it would add exact zeros).
- **Tolerance.** One block product of the whole codes: the hardware's 32-term dot, then the reference's accumulation.

**On a B300** (the `sm_103a` and `sm_100f` images) the probe ran 8.59 billion dot products per case: every banded case (the six FP8 pairs and two FP4 bands, each uniform, extremes, carries and cancellation) returned the exact sum every time, and no element's bits moved with its place in the fragment in any case. Whole blocks are not correctly rounded: unbanded FP8 differed in 4.7 billion uniform, 1.1 billion extreme and 3.4 billion cancelling dot products; FP4 in 1 uniform, 71 million extreme and 9.3 million cancelling ones; neither in carries. The records show sums aligned to the largest term and truncated (a cancelling sum of 0.00635 returned as 0). So the tensor cores return exactly representable sums exactly and the banded form is exact on the device; the tolerance form's block products are truncated where they do not fit.

**Block shapes.** Grid `(ceil(n / features), ceil(rows / tokens))`, 128 threads (four warps); `lin4` takes its layout's rows:

| Suffix | Rows × outputs | How |
|---|---|---|
| `_s8` | 8 × 16 | The split block, 256 threads: each of its eight warps takes 4 consecutive blocks of every chunk of K (2 in the banded form, whose band arithmetic needs the registers), reads their operands straight from global memory into registers, each loaded value in its own register until it is used (the words the tiles' fragment loads would read, and the scale bytes its elements need; no staging), computes their block products and writes each block's contribution `(dot · activation scale) · weight scale` to shared memory (16 KB). Thread `t < 128` then adds output `t / 8`'s contributions to row `t % 8` in ascending block order: the reference's accumulation, the same rounded operations in the same order, only the products computed apart. The next chunk's operands are loaded while the sums run. Held to three blocks an SM (80 registers a thread; a few spill to local memory) |
| `_t8` | 8 × 64 | Each warp 16 outputs, every block of every step, accumulating in registers with the block's scales decoded once; steps of 4 blocks staged through shared memory, double-buffered |
| `_t32` | 32 × 128 | The same, 32 outputs a warp (up to 207 registers a thread) |

The tiles stage through `cp.async` (16-byte copies, zero-filled past `n`, past `k` and outside the pass's rows; rows padded so a fragment load touches 32 banks), the step's scale bytes beside them as 4-byte `cp.async` copies of 4 blocks' bytes (zero-filled where nothing reads them) whenever every scale row starts on a multiple of 4 (`k / 32` a multiple of 4, as at every released shape, and both scale arrays 4-byte aligned); otherwise byte by byte, each byte loaded before it is stored, which puts a load's latency into every step. FP8 tile scales are expanded per output row as they are staged. `lin4` makes one pass over K per group whose run meets its block's rows, each computing that group's rows against that group's weight, so any `row_align` is served; a `row_align` that is a multiple of 8 gives an 8-row block one group. Padding rows are not written.

**Batch invariance.** A row's output is computed from that row's codes and scale bytes and the weight by a fixed sequence of rounded operations: its blocks in ascending order, each one block product per band pair and the reference's accumulation, whichever block shape, column of an MMA or launch carries it. No value of the launch's shape enters the arithmetic. The split block divides K among warps only for the block products, which are independent; the accumulation over blocks is one thread's, in order. What it rests on in the hardware is that an MMA's element is a function of its own row and column; the probe's rotation check holds that, and the device suite holds every shape's outputs to each other bit for bit in both forms.

**The probe** (`eidola_ds_gemm_probe`, `DsGemmProbeParams` in the header). Each warp runs trials of a 16 × 32 A and a 32 × 8 B drawn from a counter-based generator of the seed, the warp and the trial, converted and multiplied exactly as the kernels do, and compares every element with the exact integer sum rounded once; families of operands: uniform over a band, each code the band's largest or smallest magnitude (the widest alignment), every code the largest positive one (every carry), and pairs of large products cancelling to a residue. It also reruns each trial with A's rows and B's columns rotated and requires every element's bits where they moved. It counts the elements checked, those differing, those whose bits moved, the largest distance in f32 units in the last place, and records the first differing elements.

**Verified without a device.** `oracle/ds_gemm_tc_host.cc` (`tests/deepseek_gemm_tc_host.rs`, at `-O2` and `-O0`) runs the kernels' staging, fragment, band, contribution and block code on the host around an emulated `mma.m16n8k16` laid out as CUTLASS's `SM80_16x8x16_F32F16F16F32_TN` traits, in every block shape (the split block's warps in descending order and its contributions starting as garbage, its operands read per lane by the same function the device runs), against `dsk::lin8_thread` / `lin4_thread`: both conversions over every code, the cuts partitioning every word with every pair's sum below 2^24, and about 14 million outputs of both products (small random shapes, K not a multiple of a step, layouts with empty groups at row alignments 1, 3, 8, 16 and 32, arbitrary and model-like codes, a quarter of the cases over every finite scale, and blocks of every code at 448, the largest dot) under an MMA that rounds the exact sum once and one that adds in a random order with a rounding after every addition. Every banded output equals the reference. Overlapping bands, a slot of K assigned to the wrong register, a band boundary off by one, a wrong F16 exponent for E4M3 subnormals, the split block's sum in descending block order, and its contribution scaled by the product of the two scales each fail it. `tests/manifest.rs` (`ds_gemm_tc_runs_on_tensor_cores_and_fuses_nothing`) holds the image to `HMMA`, no tcgen05, no fused multiply-add in its SASS on any target, and its entries. `eidola-engine-cuda`'s `tests/deepseek_gemm.rs` and `examples/deepseek_gemm_bench.rs` are the device side, with the measurements (`eidola-engine-cuda/AGENTS.md` → DeepSeek-V4.1).

## Qwen3.8

Every Qwen3.8 kernel but the CUTLASS GEMMs, FA2, `qwen_fast` and `qwen_fast_deltanet` is ours, built in the `exact` profile and bit-identical to a function of `eidola-engine-model`'s `src/qwen/`. `eidola-engine-cuda`'s `QwenCudaExecutor` launches them (that crate's `AGENTS.md` → Qwen3.8).

**Numerics are DeepSeek's header, unchanged.** The Qwen numeric module is a subset of DeepSeek's, function for function (`bf16_round`, the E4M3 cast, `det_exp`, `det_ln`, `det_sin_cos`, `exp32`, `sigmoid32`, `silu32`, `softplus32`, `pow32`, `rsqrt32`, the pinned sums), so `qwen_ops.cuh` includes `ds_numeric.cuh` and `ds_body.cuh` as they are and adds only what Qwen alone has: the 128-wide exact block dot (`block_dot128`: an `int64` sum of `e4m3_times_512` products, rounded once to f32, as the reference's f64 sum) and the f32-scale quantiser (`amax / 448`, IEEE division per element). The quantiser's kernel is a warp per 128-wide block (four elements a lane, an 8-byte load and a 4-byte store a row, the lanes' amaxes combined by a butterfly of integer-max shuffles) and one row a CTA, or up to four rows a CTA with every row's load issued before any row's arithmetic (a row past the CTA's reads its first one and is dropped, so no branch separates the loads), as its grid's y says (`eidola-engine-cuda`'s `quant_grid` groups four once that still leaves 1,024 CTAs: decode-size launches want the CTAs, prefill-size ones the loads in flight), equal bit for bit to its reference form `quant_thread`, and without a branch in its arithmetic: the amax is taken on the BF16 magnitudes' bits as integers with a NaN's as 0 (magnitudes order as their bits, so this is the reference's `max32` fold from +0 in any order); each code is `e4m3_code`, `ds::e4m3_encode` rewritten without branches (below 2^-6 the magnitude plus 2^14, whose last place is E4M3's subnormal step, rounds it to nearest even; above, the bits rebiased and rounded to their top eight, saturating at 0x7e; equal over every f32, checked on the host); and each quotient is the element times the scale's reciprocal, rounded once, wherever that provably gives the reference's code (more than 8 units in the last place from an E4M3 midpoint, outside 2^-11 to 2^-6, under a normal scale; the bound is written beside it), the lane dividing as the reference does otherwise. The norm stages a unit's inputs (after the residual add) in shared memory, up to 8,192 wide, before its 16 serial sums in the reference's order; a unit wider than 1,024 takes a CTA of 256 threads, a narrower one (the query and key heads) a warp, eight to a CTA with no block barrier (`WarpPar`, phases met by `__syncwarp`). A thread moves 16-byte vectors where the unit's strides and arrays allow (else elements), issuing a batch of three vectors' loads (a 5,120-wide unit's whole share; or eight elements') before any store, in the staging phase and the output phase (which loads the weights first); a rotated unit stages its normed values back into the buffer as BF16 (each is BF16-valued, and a NaN stays a NaN) before the rotation reads their partners. Load-add-store per element would serialise the loads: the compiler cannot move a load above a store that may alias it, so a 5,120-wide unit would take twenty dependent memory round trips a phase (that form measured about 18 µs a launch on a B200, at any row count); holding a thread's 32 elements at once takes 122 registers, two CTAs an SM (measured 77 to 87 µs a launch at 2,048 rows); the batches take 48, five CTAs an SM. The DeltaNet's gated norm is a warp a (row, head), four to a CTA, staging the head's 128 outputs in shared memory (a lane's four in one 16-byte load where aligned) before its 16 lanes sum them, and its preparation computes a thread's value convolutions four at a time before storing them, and the L2 norms' sums of squares a lane a thread (sixteen for the queries, sixteen for the keys) before one thread takes each through the tree: the reference's lanes and order, in parallel. With `log_decay` (the fast profile) the preparation writes the log decay `g` where it otherwise writes `α = exp(g)`. The widening takes eight elements a thread, one 16-byte load and two 16-byte stores where the rows allow. Each of these has a plain form beside it as its reference form (`norm_reference_block`, `dn_norm_reference_block`, `widen_thread`: a CTA or a thread a unit), compiled for the host check and the device test, which hold the kernel to it bit for bit; where the loads sit and who computes which element is all that differs.

**The ABI** (`csrc/qwen_abi.cuh`, mirrored by `eidola-engine-cuda`'s `src/qwen/abi.rs` with size and offset assertions on both sides): BF16 between kernels as 16-bit values; FP8 activations as codes `[rows, k]` with f32 scales `[k / 128][m_pad]` and FP8 weights as codes `[n, k]` with f32 scales `[k / 128][n / 128]`, the CUTLASS blockwise kernel's SFA and SFB layouts, so the fast profile's GEMM reads what the exact one reads; a paged KV block holds, per layer, keys `[block, width]` then values; a state image is the reference executor's (per DeltaNet layer its conv history then `S[h][i][j]`, f32).

|---|---|---|

The state stores' addresses pass through an empty `asm volatile`, or the compiler hoists all 32 of them out of the token loop and spills. **Geometry is simple by design**, a whole unit to a thread, a warp, or a block of phases (`ds::Par`), so the bodies run unchanged on a host (a warp's shuffles by the same butterfly there): tuning (the recurrence's slicing of a head over threads and blocks, the linears' tiles) follows the GPU's profiles. The general recurrence uses 135 registers and no stack, its short form 80 and a 16-byte stack (a few scalars a position, in L1); FA2 d256 at query tile 16 spills 200.

**The sampler** (`qwen_sampling.cu`, profile `own`, both profiles' executor). The serving core's sampler, operation for operation in its groupings as `sampling.cu` is (every f64 operation an explicit round-to-nearest intrinsic, exponentials from `det_exp`, every sum of probabilities its pinned grouping: chunks of 1,024 ids left to right from +0, then the chunk sums left to right), with the work spread differently. A sample is four launches over a work area of a `QwSampleWork` (20,608 bytes) a row: `_top` (a block a row: the lowest-id argmax of the logits, the non-finite check, a greedy row's token, the histogram cleared); `_exp` (a block a chunk of a row: `e_i = det_exp(l_i / t - l_top / t)` into the distribution, the chunk's sum by one thread from shared memory); `_norm` (a block a chunk: the chunk sums added in order, `p_i = e_i / sum` in place or a greedy row's one-hot, the chunk's sum of p, and a filtering row's histogram of p's bits 61..50 into the work area by shared-memory counts then one atomic a bin); `_pick` (a block a row). An unfiltered row's draw adds the chunk sums of p in order to find the chunk where the inverse CDF's target falls and scans that chunk alone, staged, by one thread; failing (by rounding) it goes on as the reference's loop does, and failing everything takes the last positive id. A filtering row selects: top-k, top-p and min-p each keep a prefix of the order (p descending, id ascending), and non-negative doubles order as their bits do, so a prefix is every key at or above a threshold. For top-k the threshold is the fewest histogram bins holding k keys, refined twelve bits at a time over the boundary bin (bits 49..38, 37..26, 25..14, 13..2, 1..0) until at most 2,048 keys (`kCap`) are at or above it, or, at a tie on one value of p, those above it and the lowest ids of that value (an ordered compaction); for top-p alone, the fewest bins whose complement's mass is bounded (a bin's count times its upper edge, summed) below `1 - top_p` of the whole by a margin; for min-p alone, every bin at or above the floor's. The candidates are gathered, sorted by key and again by id (bitonic, in shared memory), and the reference's own steps run over them: a rank prefix's mass is its pinned sum, computed over the candidates in id order (each chunk's kept ids left to right from +0, the chunks in order, a chunk with none adding +0: exactly the reference's sum, whose other terms are zeros), top-p's shortest prefix by the reference's binary search over those masses, min-p's floor from rank 0, the renormalisation, the distribution written (zeros, then the kept values), and the draw scanning the kept ids in vocabulary order with the same chunked prefix sums. Top-p alone checks its candidates reach the target before relying on them. A top-k past 2,048, a top-p whose candidates pass 2,048 or fall short, and a top-k at or past the vocabulary alone (a renormalisation of every id) take `sampling.cu`'s bitwise search, kept here unchanged (`slow_filter`), exact and slow. Chain acceptance is `_decide` (a thread a sequence: the draft ids bounded, the accept tests, the accepted drafts written, the outcome), `_sums` (a block a chunk of a sampled sequence: the pinned chunk sums of the one distribution it then draws from, the residual `max(0, p_i - q_i)` at its rejection or the bonus row) and `_finish` (a block a sequence: the residual's draw if its sum is positive, else p's (its sums by the slow form), the bonus draw, or a greedy argmax; the count). The vocabulary is at most 256 chunks (262,144 ids).

**The fast profile's own images.** `cutlass_fp8_blockwise_swap` instantiates the blockwise FP8 GEMM with CUTLASS's A the weight (row-major `[N, K]`, its scales per 128 × 128 as CUTLASS's SFA with granularity (128, 1, 128)), B the activation rows (column-major `[K, M]`, scales per row and 128 of K as SFB) and D column-major `[N, M]`, which is `[M, N]` row-major: the same operand and scale arrays as the unswapped kernel, so the executor's buffers serve both. Its tiles are 128 weight rows by 16, 32 or 64 activation rows (one entry each): at a few rows a K block then promotes a 128 × 16 (32, 64) accumulator rather than 128 × 128, and a pipeline stage is a 16 KiB weight block and a sliver of activations, so more stages are in flight. Per output the mainloop computes what the unswapped kernel does (per K block the MMA's dot from zero, then `acc += (s_a · s_w) · dot` in K-block order, the scale product commuting exactly); whether the tensor core's dot of a row pair is the same whichever operand is which and whatever the MMA's N is the hardware's, held by `eidola-engine-cuda`'s `fast_fp8_configs_agree`. `qwen_fast` (profile `own`) holds the small-N BF16 GEMM, a warp per output for four rows, lane `l` summing its 16-byte chunks `l, l + 32, …` of K by fused multiply-adds, then an xor butterfly (a BF16 product is exact in f32, so fusing changes nothing; the order fixes the bits), and its tiled form for prefill sizes (`eidola_qwen_fast_gemm_bf16_tiled`: a warp eight rows by four outputs, the CTA's four warps sharing their rows, every (row, output) summed in that same order and combined by the same butterfly, two rows' sums a paired `fma.rn.f32x2`, `FFMA2` in SASS, each half rounded once), whose bodies `qwen_fast.cuh` are also compiled for the host check (the host's tiled form takes each sum's fused multiply-adds one at a time); the gates in f32 (`g / (1 + exp(-g))` and `1 / (1 + exp(-g))` with the hardware exponential, then the exact gates' BF16 roundings), 8 elements a thread with 16-byte accesses where the strides allow, element by element otherwise; and the split FP8 GEMM's sum (`eidola_qwen_fast_split_sum`: each output's partials added in split order from the first by `__fadd_rn`, rounded once to the nearest BF16, a NaN as the one quiet NaN; 4 outputs a thread, 16-byte loads where the arrays allow). None is equal to the model crate; each computes an element from its own row and the weights only. `cutlass_fp8_blockwise_split` instantiates the blockwise GEMM again with an f32 D and no rounding, swapped as `cutlass_fp8_blockwise_swap` is at 16, 32 and 64 activation rows and unswapped at 128 × 128: the host runs a GEMM's K split into `S` ranges as one launch of `S` batches (CUTLASS's L mode, each batch a range's columns of the same rows and its run of scale blocks, its output its own f32 array), so per output and range the mainloop's arithmetic is the BF16 kernels' over that range from zero, and `eidola_qwen_fast_split_sum` adds the ranges. Its instances differ from the BF16 ones only in the epilogue's element type (and the stage count that follows from the epilogue's shared memory), so a range's sums are the same in every instance, held by `eidola-engine-cuda`'s `fast_fp8_split_forms`.

**The fast profile's DeltaNet in blocks** (`qwen_fast_deltanet`, profile `exact`: no contraction, so every scalar step rounds as written, here and in the host check). The definition is in `qwen_fast_deltanet.cuh`'s header: a run starts at a block boundary (blocks of `chunk` positions, at most 16, at absolute positions), and each block is computed in its chunked form from the state at its start: the cumulative log decay, the strictly lower `A = β (k kᵀ) ⊙ exp(Gᵣ − Gⱼ)`, `T = (I + A)⁻¹` by forward substitution a column at a time, `W`, `U` and the decayed `q kᵀ` (`P`), each row's sums in index order from +0 and the dots `pinned_dot`s; then `Δ = U − W S` and `q S` on tensor cores, `o = exp(G) · (q S) + P Δ` (`ztree`: four partial sums over the tile's 16 rows, then a pairwise tree; `P` is +0 past the row, so those terms add exact zeros to sums that start at +0), and for a whole block `S' = S · exp(G_{L−1}) + Kᵀ (exp(G_{L−1} − G) · Δ)` with `Kᵀ Δ′` on tensor cores. Every tensor-core operand is rounded to TF32 (`cvt.rna`) and accumulates in f32; `S` is f32 between blocks. A block's tile is always 16 rows, the positions past the block's end zero in every operand, and row `r` of every quantity reads rows `≤ r` only, so a row's bits do not depend on how many of its block's positions are present, and the state, updated from whole blocks only, is a function of the token prefix; no position-wise reduction runs on a tensor core but the update of a whole block, so nothing rests on how a tensor core adds an exact zero.

- `eidola_qwen_fast_dn_intra`: a CTA per block and key head, all its value heads at once (at most four), in phases of `ds::Par`, so its body is the host check's bit for bit. A block's rows before its run's `out_from` are cached: their keys, values, write strengths, cumulative decays and rows of `T` are read from the tail cache (`QwDnChunkParams::tail`; an entry per position, `qwd::entry_floats`), and every loop over rows runs over the new ones, so a decode step's block costs its new position. The key and query rows are 129 floats apart, so a pair's dot reads distinct banks. It writes what the state kernel reads: each block's new rows of `W` (16 × 128, rounded to TF32) and `U`, `P` (16 × 16) and factors (`exp(Gᵣ)`, `exp(G_{L−1} − Gᵣ)`, `exp(G_{L−1})`) per value head, the new rows of the queries rounded to TF32 per key head, and the keys rounded to TF32 only for a whole block; and, for the keep kernel, the new rows' keys, rows of `T`, write strengths and decays. 80 registers, no spill.
- `eidola_qwen_fast_dn_state`: a CTA per run, value head and 64 value columns, a warp per 16 of them. The columns are independent, so their slicing changes no bit. A warp keeps its 16 columns of the state in registers across the run's blocks, transposed (`Sᵀ`) in the m16n8k8 accumulator layout, and reads them straight from there as the left operand of `Sᵀ Wᵀ` and `Sᵀ qᵀ`; the left operand's columns `t, t + 4` of a K-step carry the accumulator's `2t, 2t + 1`, and the right operand's rows are read to match.
  - A block's products give each position from its own column of the right operand.
  - Its operands are copied in with `cp.async`, the next block's while the current one finishes (three barriers a block), the first block's while the state loads. The rows of `W`, `q` and `U` outside a block's new ones are zero-filled rather than read, and the keys are copied only for a whole block, so a decode step reads its state and little else.
  - `Δ = U − X` goes to the warp's shared rows for `ztree`, a cached row's taken from the tail cache (copied in with the operands) and a kept new row's written there, and `Δ′ᵀ` is the left operand of the update, read from there.
  - 128 registers a thread (four CTAs an SM); it spills 88 bytes, in its copies' addresses.
- `eidola_qwen_fast_dn_keep`: a CTA per block and key head, after the state kernel: the kept new positions' keys, values, rows of `T`, write strengths and decays into the tail cache. It runs after both kernels that read the cache, since a long run's cached and kept positions can share a ring row, and a CTA of the state kernel then never waits on a load at its end.
- `eidola_qwen_fast_dn_fused`: the three in one launch, for a launch whose every run is at most the tail cache ring's positions (a decode step's: no position it keeps is one another CTA of it reads). The state kernel's grid; each block's intra body for the CTA's value head and its 64 columns of `U` into shared memory (`qwd::fused_intra`), the state kernel's block on it, then the block's kept positions into the tail cache (`qwd::fused_keep`). The intra body is one function (`qwd::intra_body`) over a span of value heads and columns and an output target, which both kernels call, and the state step's code is shared too, so each element is the same arithmetic: its bits are the unfused form's (the host device holds its intra body to the unfused scratch bit for bit; the device test holds the whole launch to it).

A run's blocks are numbered among the launch's by its `QwDnSeq::tile`; a state is stored only at block boundaries. The state kernel's host form (`dn_state_host`) runs the same arithmetic with each tensor-core K-step read as the products of TF32 operands summed in K order; the device's tensor cores sum a K-step their own way, so device and host agree within a bound, held on the device.

**FA2 at head dim 256** reuses the rendered sink configuration (`generated/flashinfer_sink`): its `PagedParams` and `AttentionSink` do not depend on the head dimension, which is a template argument of the kernel traits, so no render step or recipe changed. Query tile 128 is not built (FlashInfer refuses it at d256 with four query warps).

**Verified without a device**: `eidola-engine-cuda`'s `tests/qwen_kernels_host.rs` compiles the bodies for the host (`oracle/qwen_launch_host.cc`, threads in descending order, shared memory starting as garbage) and holds every family to the model crate bit for bit, the bodies arranged for speed to their reference forms over random and edge inputs, the quantiser's warp form to `quant_thread` over edge blocks and over every BF16 value under 96 block maxima, `e4m3_code` to `ds::e4m3_encode` over every f32, and the small-N GEMM's two forms to the order it documents and to each other, and the blocked DeltaNet's intra body and state host form to its definition written out in Rust bit for bit, to the token recurrence within a bound and to reproducibility (the row copy and the sampler have no host body: the host device reads them as `eidola-engine-cuda/AGENTS.md` → Qwen3.8 says); `tests/manifest.rs` (`qwen_kernels_fuse_nothing`, `qwen_fa2_d256_is_the_mma_sync_path`, `qwen_fast_images_hold_their_entries` (the sampler's and the split GEMM's images among them), `qwen_fast_deltanet_is_unfused_on_mma_sync`, and the swapped and split GEMMs' tcgen05 path in `sass_uses_the_intended_tensor_core_path`) holds the images' profile, entries and SASS facts; `eidola-engine-cuda`'s `tests/mimo_cutlass_params.rs` holds the swapped and split GEMMs' Params, built in Rust, to CUTLASS's own host path.

## How a host uses the images

Cubins and fatbins are loaded through the CUDA driver API (`cuModuleLoadData`, e.g. via `cudarc`); there is no host-side object code and no CUDA runtime library involved.

- **Load through `ArtifactDir`.** It reads an image from a build output and returns the bytes only if size and SHA-256 match the compiled-in manifest.
- **Entries by symbol.** Kernels we wrap are `extern "C"`. Upstream template kernels keep their mangled names, which the manifest lists with their demangled forms. Template instances, DeepGEMM's `__global__ static` kernels and every `_meta` global have local binding (`STB_LOCAL`) in a whole-program cubin. `cuModuleGetFunction` / `cuModuleGetGlobal` resolve them by name (observed on a B300, R580 driver; `eidola-engine-cuda`'s smoke tests cover every entry and record).
- **Launch contract in the image.** Each entry has a launch-contract device global (`EidolaKernelMeta`, 32 bytes), named by the entry's `meta` field in the manifest. For an entry we name ourselves it is `<entry>_meta`. A mangled template instance cannot carry a matching name, so its record has a readable alias (`eidola_deepgemm_fp8_fp4_psum_gate_up_meta`, …) and `meta_aliases` in `csrc/kernels.json` binds the alias to the mangled symbol. The build fails unless every entry resolves to exactly one record and every record to exactly one entry, `Manifest::parse` re-checks that correspondence, and `Cubin::entry` / `Cubin::entry_for_meta` look it up in either direction. The record holds:
  - block shape,
  - dynamic shared memory,
  - cluster shape,
  - the size of its by-value parameter struct.

  Read it with `cuModuleGetGlobal` plus a 32-byte copy, and decode it with `KernelMeta::from_bytes`. Launches above 48 KiB of dynamic shared memory must first set `CU_FUNC_ATTRIBUTE_MAX_DYNAMIC_SHARED_SIZE_BYTES`. Cluster launches need `cuLaunchKernelEx` with the cluster attribute.
- **Parameters.** These are what the host must build to call each kernel:
  - **FlashInfer attention:** `EidolaAttnParams` (304 bytes): FlashInfer's plain `PagedParams` struct (296 bytes) and the address of the work-item count; the split-KV merge takes a plain argument list.
  - **DeepGEMM:** five `CUtensorMap`s, which the host encodes with `cuTensorMapEncodeTiled`.
  - **CUTLASS GEMMs:** their 2048-byte `GemmUniversal::Params`, including TMA descriptors that CUTLASS builds in host C++. `eidola-engine-cuda` builds the same bytes in Rust (`src/mimo/gemm.rs`), pinned against CUTLASS's own host path by a dev-only oracle.
- **DeepGEMM SM count.** The persistent scheduler bakes in the SM count (148). The grid must be exactly that, and the part must have at least that many SMs. The B300 has 148 (measured), the same as the B200.

## Determinism doctrine

The kernel bytes are a function of the inputs listed in the manifest: the sources, the flags, and the toolchain. They do not depend on the build directory, parallelism, clock, `SOURCE_DATE_EPOCH`, or the builder's CPU architecture. Two runs of an aarch64 builder produce identical manifests, and so do an aarch64 and an x86_64 builder (emulated on Apple Silicon). The rules that make this hold, each learned by breaking it:

- **Pin the source path nvcc sees.** `cicc` names internal-linkage device symbols (`_INTERNAL_<hash>_…`) after a module ID derived from the absolute source path.
  - The symptom: the same source in two directories gives different cubins for every kernel that has such symbols. Only RMSNorm was unaffected.
  - Why it matters here: Nix 2.32 builds in a randomized `/nix/var/nix/builds/nix-<pid>-<rand>` directory, so without the pin the build is not reproducible even run to run.
  - The fix: every compile passes `-Xcicc --orig_src_path_name -Xcicc crates/eidola-engine-kernels/csrc/<file>`. This is an undocumented `cicc` option; nvcc's own `-frandom-seed` does not affect it.
- **No `-lineinfo`, no `-G`.** Both embed source paths, and builds from two directories then differ.
- **No `-split-compile`.** With it, three compiles of the same file in the same directory produced two different `.text` sizes. This is code-level nondeterminism, not metadata.
- **One arch per compile.** CUB's ABI namespace embeds the list of target archs in the translation unit (`cub::_V_300200_SM_1000…`). The same source compiled for `sm_100a` alone and for `sm_100a`+`sm_103a` together therefore yields different `sm_100a` cubins. Per-arch compiles keep each cubin independent of the target set.
- **Explicit fatbin settings.** The nixpkgs nvcc setup hook would prepend `-Xfatbin=-compress-all`. The derivation disables the hook (`dontSetupCUDAToolkitCompilers`), and the build script runs `fatbinary --compress=false` directly. The compressor itself was observed to be deterministic, but uncompressed images let a reader check that the fatbin holds the cubins byte for byte.
- **No ambient flags.** The build script unsets the following before calling nvcc, so nothing reaches nvcc or its preprocessor that the manifest does not list:
  - `NVCC_PREPEND_FLAGS`
  - `NVCC_APPEND_FLAGS`
  - `NIX_CFLAGS_COMPILE`
  - the hardening variables
- **`-DNDEBUG` everywhere.** Device `assert` would embed `__FILE__` strings.
- **Pin addresses whose placement varied by builder architecture.** The split GEMM block computes each lane's row addresses and its shared-memory pointers once and passes them through an empty `asm volatile` (`split_rows` in `ds_gemm_tc.cuh`, `split_pass` in `ds_gemm_tc.cu`). Without it the x86_64 and aarch64 builds of the same toolkit placed those computations differently among the loads (the PTX of two entries differed, and the cubins by 224 bytes), while builds on one architecture were identical. The control experiment is removing the barriers and building with `--platform linux/amd64 --verify` against an aarch64 manifest.

Each rule has a control experiment: build with the rule broken, from two directories, and compare. Keep that discipline when changing flags.

## Building and verifying

```sh
crates/eidola-engine-kernels/scripts/build-in-docker.sh --verify          # build, compare to kernels.manifest.json
crates/eidola-engine-kernels/scripts/build-in-docker.sh --check --verify  # also rebuild and require identical bytes
crates/eidola-engine-kernels/scripts/build-in-docker.sh --platform linux/amd64 --verify  # the other builder arch
crates/eidola-engine-kernels/scripts/build-in-docker.sh --update          # after an intended change
crates/eidola-engine-kernels/scripts/build-in-docker.sh --cores 5 --update  # in a Docker VM of 16 GB
```

`--cores` bounds the compiler invocations at once (`nix.conf`'s `cores`, which the build script runs that many of): every core the container sees runs out of memory in a 16 GB Docker VM, where five finish in under two minutes once the toolkit is in the volume. The output does not depend on it.

The first run downloads the toolkit into a named Docker volume (`eidola-kernels-nix-<arch>`). The x86_64 toolkit is also unpacked and patched locally, because unfree packages are not in the public cache. After that, a build takes under a minute natively. Output lands in `target/engine-kernels/<arch>/`:

- the cubins and fatbins,
- full SASS and register/shared-memory usage under `inspect/`,
- the rendered FlashInfer config,
- `manifest.json`.

Inside the container Nix runs with `sandbox = false` and `filter-syscalls = false`. The container is the isolation boundary, Nix's sandbox needs privileges it lacks, and the seccomp filter cannot load under amd64 emulation. Purity still holds: every input is fixed by hash, and the build script removes the build directory from the output.

`cargo test -p eidola-engine-kernels` needs no toolkit. It checks that the committed manifest still describes the committed sources:

- every file under `csrc/` and `nix/` (the sources and the whole build recipe: `default.nix`, `sources.nix` and both scripts, all in the derivation's source set) hashes as recorded, and no new file has appeared in either;
- the pins agree with `nix/sources.nix`;
- the kernel × arch matrix and flags agree with `kernels.json`;
- the SASS facts above hold;
- no cubin of a profile without contraction fuses a multiply-add (*The `exact` profile*), and the division-free DeepSeek images hold none in their SASS;
- every entry is bound to exactly one launch-contract record, and the aliases are exactly the bindings that differ from `<entry>_meta`.

Editing a kernel or the build recipe without rebuilding fails here.

`tests/deepseek_numeric_host.rs`, `tests/deepseek_kernels_host.rs`, `tests/deepseek_attention_host.rs` and `tests/deepseek_gemm_tc_host.rs` are the tests that use a compiler (the host's C++ compiler, skipped without one): *The host check and the vectors*, *The scalar kernels*, *DeepSeek-V4.1 attention, index and selection*, *DeepSeek-V4.1 tensor-core GEMMs*.

## Adding a kernel

1. Write `csrc/<name>.cu`. Give each entry point an `extern "C"` wrapper where the upstream code has a `__device__` body to call, or explicitly instantiate the upstream `__global__` template with its full signature. Add an `EIDOLA_KERNEL_META` record for each entry: `<entry>` for an `extern "C"` entry, a readable alias for a mangled one. Do not use `assert`-dependent or path-dependent constructs.
2. Add it to `csrc/kernels.json` with a flag profile, and a `meta_aliases` entry (`"<alias>_meta": "<mangled symbol>"`) for every aliased record; the first build prints the mangled symbols if you do not have them yet. Add a new profile only when the upstream project's own build flags differ. A kernel that includes `ds_numeric.cuh` takes the `exact` profile.
3. Run `scripts/build-in-docker.sh --check --update`, inspect `inspect/<name>.<arch>.sass` / `.res-usage` (register spills show as `STACK`), and commit the source and manifest together.
4. If the kernel exists for a particular tensor-core path, assert it in `tests/manifest.rs`.

## Repository integration

**The kernel image.** `oci/eidola-engine-kernels/Containerfile` runs this directory's expression (`nix-build nix`, with its own pinned nixpkgs, the flake's revision) inside the pinned `nixos/nix` container, fails unless the build's `manifest.json` equals `kernels.manifest.json` byte for byte, and ships `cubin/`, `fatbin/` and that `manifest.json` in a `FROM scratch` image, `ghcr.io/eidola-ai/eidola-engine-kernels` (bake `engine-kernels` / `ci-engine-kernels`; CI's `oci-engine` job builds it and pushes it on push events). Its digest is a function of this crate's committed files, and its build copies only those the expression reads (`csrc/`, `nix/`) and `kernels.manifest.json`, so an edit to the crate's Rust code does not rebuild the kernels. The inference node's image (`oci/eidola-server-engine/Containerfile`, `crates/eidola-server-engine/AGENTS.md` → The image) names it by digest on its `AS kernels` line and copies the images from it into `/opt/eidola/kernels` after checking that the image's `manifest.json` is the committed one and that every cubin and fatbin it lists has its recorded size and SHA-256, and no other. Every node image build therefore is an x86_64 `--verify` of this crate. **Changing a kernel or the build recipe moves that pin**: after `--update`, `just engine-kernels-image` builds the kernel image as CI does and prints its digest, which goes on the node Containerfile's `AS kernels` line in the same commit; a node build (`just engine-image`, CI) fails while the two disagree. Its `eval` stage is built on PRs (`scripts/check-oci-stub-workspace.sh`), so a file the expression reads that the image does not copy fails before `main`.

**The flake.** The root flake imports the derivation unchanged, with its own nixpkgs, so the toolchain record the build writes is the one the committed manifest holds:

```nix
engineKernels = import ./crates/eidola-engine-kernels/nix {
  nixpkgsSrc = nixpkgs;
  nixpkgsRev = nixpkgs.rev;
  inherit system;
};
```

It is `packages.x86_64-linux.eidola-engine-kernels`. Any import must pass the root's own nixpkgs revision, or the manifest's toolchain record changes; the standalone default (what `build-in-docker.sh` and the kernel image run) pins the same revision, so a `flake.lock` bump moves it too.
