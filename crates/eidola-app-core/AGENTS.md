# eidola-app-core — Agent Development Guide

The GUI app and CLI share this crate as a normal Rust library — no FFI layer. All business logic lives here: config management, the local database, HTTP client construction, account operations, wallet/credential management, chat inference, participants, agent memory, and local models. Consumers construct an `AppCore` and call its methods directly.

Ground rules:

- **`AppCore::new` is fallible** (`Result<AppCore, AppError>`): it takes the process-lifetime exclusive advisory lock on the local database before building anything else, so a second opener is refused with `AppError::DatabaseInUse` (see Local Database below).
- **State & async doctrine** for consumers (domain stores, the invalidation bus, task ownership, atomicity rules) is governed by `crates/eidola-gui/STATE.md`. All state-touching code follows it; do not invent parallel patterns.
- **Any change to the chat path must extend the test harness** (see Chat-path test harness at the end): a new exit point or emission gets a `tests/chat_path.rs` / `tests/participants_orchestration.rs` test and a row in `tests/bus.rs`'s exit-point table.

## Change bus (`changes.rs`)

`Change` enum with eleven domain variants: `Config`, `Account`, `Wallet`, `SpaceIndex`, `Space(SpaceId)`, `Record`, `UpdateState`, `LocalModels`, `Backends`, `Participants`, `Templates`. `Participants` (a space's membership/config changed) and `Templates` (the template registry changed) are deliberately split because they map to two GUI surfaces — the STATE.md 1:1 variant↔store rule. `ChangeSource` is the narrow seam for a future Turso-CDC implementation; `BroadcastSource` is the v1 in-process `tokio::sync::broadcast` (capacity 256). `AppCore::subscribe_changes()` hands out independent receivers; a lagged receiver gets `RecvError::Lagged` and should refresh everything.

Emission doctrine:

- Every durable commit emits **after** the write succeeds. Pure errors with no durable side effects never emit.
- `chat`/`chat_stream` **post first**, unconditionally: the user's turn (and, for a space-less call, the space itself) is committed before any credential is acquired, so a funding failure leaves the saved thought rather than swallowing it. Its `Change::Space(id)` + `Change::SpaceIndex` are emitted at that commit like any other.
- Once a space is persisted, partial-failure paths emit on every explicit error exit, mirroring the success path (`Change::Wallet` as soon as a credential enters `spending`; `Change::Space(id)` + `Change::SpaceIndex` when a new/auto-titled space committed a user turn; `Change::Record` where a request row committed). Plain `?` on intervening local-DB inserts stays unemitted (internal-consistency failures).
- The full exit-point → emissions table lives in `tests/bus.rs`'s doc module. Keep it current.

## Backend registry (`backends.rs`)

The `backend` DB table holds configured inference destinations — where an ask can be routed. Four kinds:

- `eidola` — the confidential service (singleton). The row owns the whole connection + trust bundle: `base_url`, `trusted_measurements` (JSON overrides), `hardware_root_ca` / `hardware_intermediate_ca` (PEM ARK/ASK overrides) — each NULL = the embedded trust-root pin.
- `local` — Eidola-managed on-device models (singleton).
- `openai` — any user-configured OpenAI-compatible server (base_url + optional api_key).
- `llamacpp` — a user-owned llama.cpp install: Eidola scans its `models_dir` and starts/stops engines but never downloads/deletes files. Two extra columns, refused on other kinds: `engine_path` (explicit `llama-server` path; `None` = discover) and `auto_start` (default `1`; when `0` a request may not start an engine on demand — it must be pre-loaded explicitly).

Singletons are enforced by a partial unique index on `kind` and seeded idempotently at every DB open (`ensure_default_backends`); they can be **disabled** but not removed — disabling `eidola` is exactly the "no account, on-device only" configuration. External backends soft-remove (`removed_at`) so the forensic `request.backend_id` reference stays resolvable forever; re-adding the same id revives the row.

**Model references:** one rule uniformly — `<model>@<backend-id>` (split at the last `@`; ids validated to `[a-z0-9-]{1,32}`, so Ollama `name:tag` and HF `org/model` ids survive), with a single sugar: `eidola`, being the default backend, may be written bare, and `qualified_model_id` keeps the bare form canonical. Every other backend's models are spelled qualified, the local singleton included (`<slug>@local`). `parse_model_ref` / `qualified_model_id` are the unit-tested pair.

Because "OpenAI-compatible" does not guarantee `GET /v1/models` (Azure, scoped gateway keys, partial proxy listings), each backend carries nullable `model_overrides` (a pinned JSON list replacing the fetch); `backend_models(id)` resolves per kind — eidola → the attested catalog, openai → overrides-or-listing, local/llamacpp → the loaded engines.

`update_backend` does per-kind field validation: the `eidola` row accepts only its connection + trust bundle (each clearable back to NULL = pin) and refuses external fields; `local` refuses everything (enable/disable only); `openai`/`llamacpp` accept their own fields but never the trust bundle. The eidola-trust setters (`set_base_url` / `clear_base_url_override` / `set_hardware_root_ca` / `set_hardware_intermediate_ca` / `trust_measurement` / `untrust_measurement` / `clear_trusted_measurements`) are thin wrappers over `update_backend` on the eidola row. **Every member of the bundle has an unconditional clear-to-pin verb**, `trusted_measurements` included: reverting by key (`untrust_measurement`) leaves the column non-NULL, and a non-NULL list that omits the pinned measurement rejects the real enclave — so a caller reverting the bundle would have had to know every key it ever trusted. All CRUD emits `Change::Backends` (not `Change::Config`). Tests: `tests/backends.rs`.

## Spaces, posts, and edits (`lib.rs`)

`AppCore` holds all high-level operations and DTO record types (`ConfigState`, `ChatResult`, `PostResult`, `PriceInfo`, `SpaceInfo`, …).

- `list_spaces(include_archived)` returns title + first-message snippet + last-activity + message-count for the GUI's Library. `chat`/`chat_stream`/`post` auto-title an untitled space on its first exchange from the first line of the user's prompt (local heuristic, no model call).
- **`create_space(title)` / `create_space_with_id(space_id, title)`** instantiate the default template into a new empty space (the same door `post` takes for a space-less save) and emit `Change::SpaceIndex`. The second exists for a client that must **name the space before the row exists**: `new_space_id()` (a free function — minting an id is not a database operation) hands out the UUIDv7, so the GUI opens a ⌘N window addressed by a real id on the frame the keystroke lands and commits the row behind it.
- **`rename_space` decides the space's existence at its own write**: `db::update_space_title` answers whether a row took the title, and zero is the refusal. A space can stop existing between a read and the statement that follows it — an untouched one is disposed of when its last window closes — so a rename that reported success for a title no row took would leave the caller's optimistic edit standing over a database that never agreed to it. The doors that have no rows-affected to read (`add_space_participant`, `add_global_participant`, `grant_space_membership`) are refused by the foreign key and then *named* by `Inner::name_missing_space`, a read that only explains a write which already failed. Tests: `db::tests::a_write_into_a_space_that_has_just_gone_refuses_rather_than_reporting_success`, `every_configuration_door_refuses_a_space_that_is_gone`, `a_refusal_names_the_missing_space_rather_than_its_constraint`.
- **`discard_if_pristine(space_id) -> bool` disposes of a space nothing was ever done with** — see Disposing of untouched spaces below. The app's one real delete.
- **`post(space_id, prompt)` is the save side of the save-vs-request split:** persists a `user_input` action (fresh gen-0 item) with no credential, no account, no HTTP — creating the space if new, auto-titling, linking a `reply` antecedent edge to the prior tail — and emits `Change::Space(id)` (+ `Change::SpaceIndex` for new/auto-title). Tested in `tests/bus.rs` (no HTTP).
- **`post` refuses an agent-spawned sub-space the human has not joined** (`AppError::NotJoined`, zero-trace, inherited by `chat`/`chat_stream`) — see Agent-spawned sub-spaces; every other space is unchanged, notebooks included.
- **`edit_post(action_id, new_prompt)`:** appends a new `user_input` generation of the action's item (append-only — supersedes the tip, replicates its `reply` edge, prior generation preserved), so `item_current` resolves to the edit; emits `Space` + `SpaceIndex`.
- **`edit_post` and `regenerate` each require the kind of tip they produce** (`Inner::require_post_kind` → `AppError::WrongPostKind`): an edit needs a `user_input`, a regeneration an `inference`. Aimed at anything else they do not amend a post, they replace it with a different kind of thing — under the original author's byline for every prior generation, and for a regeneration at the cost of a billed turn written without seeing what it replaces.
- `list_spaces`/`first_user_text` count and snippet **current generations of post-bearing types only** (a tip filter plus `POST_ACTION_TYPES_SQL`), so editing replaces in the default view without inflating `message_count`, and traces/decisions/summaries never move a space's Library signals.
- **Reply targeting:** `post`/`chat`/`chat_stream` link to the space tail by default; `post_reply` and `chat_stream_reply` take an explicit `reply_to` so a reply to a non-tail post **branches** the thread there (additive signatures — the originals are unchanged).

**`get_space_tree(space_id)` is the threaded-post render DTO:** resolves each item to its current generation, keeps only post-bearing types (`user_input`/`inference`), and flattens the `reply` DAG into a `Vec<PostNode>` of render rows (so `list()` virtualization survives). The flattener (`build_post_tree`, pure + unit-tested) encodes the spine-vs-branch rule: the spine follows the first (chronological) reply at the same `depth`; later replies become indented branches; regenerations are generations (resolved to the tip), never branches. **Reply threading follows item identity:** each reply edge resolves to the current tip of its antecedent's item, so a reply to a since-edited post threads under the edit; render order sorts by the item's *origin* (first generation), never the tip's `created_at`. The raw antecedent action id is preserved on the edge (causality is action ids; intended logical flow is item ids). Regression: `edit_post_keeps_tree_position_and_rethreads_replies` in `tests/bus.rs`. `get_space_messages` remains as the flat whole-space convenience view (tests + external callers) — turns don't send it upstream.

### Disposing of untouched spaces

A space is created when its window opens, so an abandoned new window — and every launch that opens a blank one — would leave a durable empty conversation in the Library forever. Two doors reap them, under one law: **reap only what is provably pristine; when unsure, keep.** A wrongly-kept orphan costs a Library row; a wrongly-reaped space costs someone's work, so every mechanism below is arranged so the safe error is the one a mistake makes.

**Pristine is two legs**, both asked inside the deleting transaction: no `action` row in the space (every post, answer, trace, decision, memory revision and branch summary is its own witness, which is why the action write path carries no stamp), and `space.touched_at IS NULL` — nothing has ever changed the space's **configuration footprint**: its own row (title, cascade limit, router, archival), its `space_participant` rows, or the `participant` rows it owns. So a space with participants configured and zero posts is **kept** — the reader invested work. **Notebooks are excluded outright** (`notebook_participant_id IS NOT NULL`), on top of being born stamped: a notebook exists only for its agent and is the residence of that agent's `core` memory. An **agent-spawned sub-space** is kept by the first leg instead (its brief commits in the spawning transaction) and is born stamped besides — see Agent-spawned sub-spaces for the whole interaction, including why the predicate's `parent_space_id` clause over-protects a parent rather than under-protecting it.

**The stamp is written by the db-layer write functions themselves**, so the enumeration lives where the writes live rather than in a caller's memory — `touch_space` / `touch_space_of_participant` (the latter deriving the space inside its own statement, the module's derive-authority-at-the-write idiom), folded into the statement wherever one already targets the `space` row. Two rules make it honest:

- **Stamp no later than the write it describes** — in the same statement where possible, inside the same transaction where there is one, otherwise immediately *before* the write. turso autocommits each statement, so stamping afterwards leaves a window in which an edit is durable and its space still reads as untouched: a disposal interleaving there takes the space and the edit together, and the stamp that follows updates nothing. Stamping first can only over-mark (a refused write leaves a space nothing changed looking touched), and that costs a Library row. **The order is pinned, not just documented**: `a_stamp_is_written_before_the_statements_it_covers` fails on any db-layer function that runs a statement before it calls `touch_space*`, and `db::tests::a_failed_participant_insert_still_marks_its_space` is the behavioral end of it — a refused insert leaves its space marked, which is observable exactly when the stamp precedes the statement.
- **Instantiation is a birth, not a change.** `instantiate_template` writes `touched_at` **last, inside its own transaction**, resetting whatever its copies stamped. The one thing it carries that is not birth is a caller-supplied `title` — a human saying what this conversation is for — so a titled creation is born stamped and an untitled one is not. Both GUI creation doors (⌘N and New Space from Template) pass `None`, which is what makes the rule uniform across them; the CLI's titled `create_space` is kept.

**The primitive** is `AppCore::discard_if_pristine(space_id) -> bool` → `db::discard_space_if_pristine`: `BEGIN IMMEDIATE`, re-ask the whole predicate (never trusting the caller's earlier reading — that is what closes the check-then-delete window), then delete the space's `space_participant` rows, the `participant` rows it **owns**, and the `space` row. **Nothing shared is reachable from there**, and the graph is stated at the function: the inbound edges of `space(id)` are `space.parent_space_id`, `participant.owner_space_id`, `space_participant.space_id`, `action.space_id` and `memory_block.space_id` — the last two empty by the predicate, the first checked explicitly, the middle two what this deletes; the inbound edges of a space-owned `participant` are `action` and `memory_block` (both checked), since the two reference tables are CHECK-pinned to globals and `space.notebook_participant_id` names only a global. FK enforcement is on for every connection, so anything that reasoning missed aborts the transaction and the space is kept. Emits `Change::SpaceIndex`, and only when it deleted — no `Participants` (the roster belonged to a space that no longer exists) and no `Space(id)` (there is no space to announce).

**Two triggers.** The GUI calls the primitive when the last window on a space closes (`crates/eidola-gui/AGENTS.md`). The **startup sweep** (`Inner::sweep_pristine_spaces`) applies it to every pristine space **inside `Inner::db_conn`'s `OnceCell` initializer** — the local database opens lazily, so that is the earliest moment in the process that can touch it, and every read in this process is still waiting behind the initializer when it runs. That placement *is* the liveness argument: the exclusive database lock means no other Eidola holds the file, and the space a ⌘N is about cannot exist yet, because creating it is itself a call that has to get past this point first. A failed sweep is warned about and swallowed — reaping is housekeeping, and refusing to open the database would cost the reader everything.

**The sweep test is load-bearing, and there are two of them** (`tests/reap_pristine.rs`). `every_door_that_changes_a_space_stops_it_being_reaped` is one parameterized test over the `AppCore` doors (post, edit, title, archive, cascade, router, roster add/edit/override/remove, membership grant, promotion), each asserting its space is no longer reapable — so a door added without stamping fails on the row that names it. `the_stamp_ledger_covers_every_space_write` is the completeness half: it scans `db.rs` for statements against `space` / `space_participant` / `participant` (including any whose table name is interpolated, which cannot be decided lexically and is therefore declared) and fails on one inside a function `STAMP_LEDGER` does not account for. The ledger pins *coverage*; `a_stamp_is_written_before_the_statements_it_covers` pins the *order*, which is the half that decides whether a mark is worth anything. Beside them: the footprint delete, the shared library surviving it, the configured-but-unposted case, the titled-vs-untitled creation rule, notebooks, the write-lands-first race, and both sweep arms. Test seams: `test_space_footprint` (raw row counts — every ordinary read is keyed on the space and answers "empty" once the row is gone, which is exactly the difference a delete has to be held to) and `test_space_is_pristine`.

## Turns (`lib.rs`: `run_turn`, `prepare_turn`, `persist_turn`)

**`run_turn(space_id, model, target_action_id, mode, budget)` is the request side:** provisions a credential, assembles the turn's upstream thread as context, calls the model, and persists the inference + request rows + refund. `prepare_turn`'s first read of the space refuses a missing **or archived** one before any of that (see Archival stops new work, under Participants v1).

- `get_upstream_context` walks the target's reply ancestry, each hop resolved to the antecedent item's current tip (an edited upstream post contributes its latest text). `Reply` walks from the post being answered *inclusive* (whole conversation on a linear thread; exactly the target's branch on a branched space — sibling branches never leak). `Revise` (regenerate) walks from the generation being replaced *exclusive* (the model never sees its own prior output or anything downstream).
- `chat` = `post` + `run_turn(Reply)` (post-first: a funding failure leaves the saved post; onboarding gates at *request* time). `regenerate(action_id, model)` = `run_turn(tip, Revise)`. `chat_stream` = `post` + `run_turn_stream(Reply)` — the streaming twin, same contracts, differing only in SSE transport and refund-via-recovery-endpoint.
- **The twins share one implementation:** `prepare_turn` builds a `TurnPrep` (attested client, attach plan, upstream context, charge estimate + budget gate, spend proof + pending refund, ACT header — the `Wallet` "spending" emission happens here) and `TurnPrep::persist_turn` writes the durable rows; the transports are thin.
- Emissions: `Wallet` at spend start, `Space`+`Record` on non-2xx, `Space`+`Wallet`+`Record` on success — never `SpaceIndex` (`post` owns new/auto-title).
- **`respond_stream(space_id, model, target_action_id, sender)`** requests a streaming response to an already-persisted post (the saved user turn a failed ask leaves behind) without re-posting — `run_turn_stream(Reply)` minus the leading `post`. Backs the GUI's Retry affordance. `respond_stream_as(space_id, participant_id, …)` is the participant-aware analog (an explicit ask that bypasses the cascade guard and router).

**Charging:** the prompt side of the estimate is the shared `eidola-common::prompt_charge` contract — literally the same function the server computes over the same `messages`/`tools` arrays, so hold ≥ charge is structural. It counts every message's `content`, every `tool_calls` entry's compact JSON serialization (the whole entry — the proxy can't know which fields a chat template renders), and every advertised tool schema's compact serialization once per request. Message-level scalar framing (`name`, `tool_call_id`) is covered by the per-message allowance. `budget` caps the charge of each round.

### The bounded tool loop (task 20)

A turn is a bounded agentic loop. Each iteration is one HTTP request: the model either answers (loop ends, `inference` persisted) or returns `tool_calls` — the round is persisted, executed, appended to the in-flight messages, and the next round runs.

- `MAX_TURN_ROUNDS = 8` caps model **rounds** per turn (a fixed constant bounding one ask's worst-case spend, not a setting). One request a turn may issue is not a round: the tool-capability probe a rejecting endpoint costs, so the worst case is `MAX_TURN_ROUNDS + 1` requests. Exactly one — the degrade fires only on round 1 with the turn's own tools attached and withdrawing them clears that latch — and it is uncounted because the endpoint rejected it before doing any work, so its hold refunds in full and the spend the constant bounds is unaffected. Reaching it with the model still asking for tools ends the turn with `AppError::ToolLoop`; the capped round's tools are deliberately not executed (their results could never be sent). An empty registry means one iteration max, so the single-inference path is untouched.
- **Wire format:** `tools` carries the OpenAI function schema; `tool_calls` are read off the blocking body's `message` and assembled incrementally from SSE `delta.tool_calls` (per-`index` accumulators concatenating id/name/arguments). The follow-up request replays the model's call objects **verbatim** (ids and provider fields intact) in an `assistant` message with `content: null` — for streamed calls the accumulator carries non-canonical keys through reassembly (shallow, last-non-null-wins; the streaming-only `index` framing key is not replayed) — followed by one `tool` message per result, **raw, with no header** (a tool result is neither a post nor authored by a participant). The outer request body is built by `eidola_common::chat_completion_request_body`; `eidola-server::types` deserializes that same body in a regression, so an added client field cannot silently outrun the strict server request type.
- **Per-round holds, not hold reuse:** the ACT protocol consumes a credential per request, so each round re-estimates over the grown messages array, re-checks `budget`, and acquires its own hold under `spend_gate` (`Change::Wallet` fires per round; `ChatResult::credits_charged` is the sum). `TurnPrep.tool_schemas` is serialized once at preparation so every round's estimate and wire request read one array.
- **Persistence:** a round writes a `tool_call` action (`tool_use` blocks with `tool_name` + `tool_call_id` + raw argument string, plus any `thinking`/`text` produced alongside, and the round's tokens/credits) and a `tool_result` action (`tool_result` blocks keyed by call id; no model, no credits; status `error` if any tool failed). Both chain off **the post the turn answers**, never the inference (a cap/budget exit ends the turn without an inference; hanging the trace there would leave it parentless) — and because `get_space_tree` keeps only post-bearing types, the chain collapses out of the render while staying resolvable in the Record. `db::last_action_in_space` is the last **post** for the same reason.
- **Model mistakes are results, not failures:** an unknown tool name, unparseable `arguments`, or a tool's own error become the tool *result* text the model reads next round. Only structurally unusable values fail the turn (raw exchange recorded, no action attached): a call with no id / no function name, or a `tool_calls` that is present and non-null but **not an array** (blocking or SSE alike — reading that as "no tools" would persist an often-empty completion as a successful answer). An absent or explicitly `null` `tool_calls` *is* "no tools" and stays an ordinary completion.
- Streaming: tool rounds are **invisible pauses** in v1 — no new `ChatStreamEvent` variants; content deltas are forwarded verbatim in every round, so pre-tool narration streams and then persists on the round's `tool_call` action (where the render collapses it).

**Reasoning ("thinking") is durable.** Both transports recover the model's reasoning from the same provider extensions (streaming `delta.reasoning_content` / `delta.reasoning`; blocking `message.reasoning_content` / `.reasoning`) and `persist_turn` writes it as a `thinking` content block at ordinal 0, ahead of the answer's `text` block (no schema change). It is **never replayed upstream and never part of the readable transcript**: both context queries join content blocks `ON cb.block_type = 'text'`, so a persisted thinking block is render-side disclosure only — what makes the GUI's "Thinking…" disclosure survive a reload.

### First-person traces (task 33)

A turn's tool rounds are replayed to the **responding participant** on later turns and to nobody else. `render_messages` renders only `user_input`/`inference` as posts; `prepare_turn` splices each spine inference's own rounds in *before* it, in the wire shape the model produced them (built by the same `assistant_tool_call_message`/`tool_result_message` helpers the live loop uses, so live and replayed bytes cannot drift).

**Attribution is the context assembly, not the reply DAG:** a trace chain hangs off the *post* the turn answered, so nothing structural links it to the answer — but the writing turn recorded exactly its own rounds as fed context (`db::assembly_trace_blocks`), making the rule *you see the traces of the turns whose posts you can see* — branch-correct and regeneration-correct by construction. A turn also records the traces it **replayed** in its own assembly; the reader dedupes first-on-spine-wins, so each trace renders once, at its producing turn. **The assembly is the ordered composition of the prompt:** `prepare_turn` builds `TurnPrep.context_action_ids` in the same loop that builds `messages`, so a replayed trace occupies its wire position. **No sliding-window elision:** traces stay inline until an explicit future consolidation event, so a participant's trunk is append-only — every request's `messages` is a literal prefix of every later one's. One fidelity limit: only `(id, name, arguments)` are persisted, so a replayed call is reconstructed canonically and provider extension fields on a call don't outlive their turn. Trace bytes ride the messages array, so `prompt_charge` covers them on both sides.

### Thread map + navigation tools (task 21)

`get_upstream_context` scopes a turn to its branch, so without help a model can't know sibling branches exist. `prepare_turn` builds a per-turn `ThreadSnapshot` — from exactly the GUI's materials (`db::get_space_tree_data` → `build_post_tree`), one path for threading and rendering — and appends a trailing `<thread-map>` block naming every fork point on the turn's spine and the branches off it, anchored to handles (`at #h12`), each entry `#handle · author · posts · last activity — opening line` (opening via `derive_space_title`; relative times are coarse buckets so bytes don't churn), plus a `· you participated, N posts` segment for branches the responding participant posted in (per-participant is free because the map is the volatile tail). **No silent stripping:** every branch gets a line.

- **Placement is pinned after the post being answered**, in a trailing message that closes with an explicit `Respond to #h.` pointer — keeping exactly one message volatile so a re-request of the same turn reuses the whole prefix including the post it answers. The pointer belongs to the *message*, not to the map (task 64's roster shares that message); see Identity, roster, and post timestamps.
- **Cache doctrine holds structurally:** branch metadata is never interleaved inline, and the map's data never enters the system prompt — the only system-message change is the static `TRAILING_BLOCK_NOTE` + `THREAD_MAP_NOTE` (+ `THREAD_MAP_TOOLS_NOTE` when tools attach), each of which flips once — the first when the space grows a trailing message at all, the other two at first branch — and is byte-stable after. Task 21 additionally held that a **linear space is byte-identical to pre-task-21** — no map, no note, no `tools` field. **That is the record of a past decision, not a standing invariant** (Mike, 2026-08-11): it was chosen under task 21's own constraints and does not bind new work, and task 64 deliberately broke it (an identity line in every space, a roster beside the map). **The surviving rule is stable-but-larger is fine; per-turn-varying is costly** — a feature may add bytes to a space that does not use it, provided it flips once and is byte-stable after. A *churning* prefix invalidates the upstream cache on every turn rather than once, and that is the cost worth vetoing. "It would add bytes" is a thing to weigh, never a reason on its own to refuse a feature.
- A `Revise` turn's map excludes the generation being replaced *and its subtree*, mirroring what `get_upstream_context` withholds.
- The map rides `messages`, so `prompt_charge` covers it and the hold grows with it — the accepted cost of no-stripping.
- Key regressions in `tests/chat_path.rs`: `a_linear_space_sends_no_thread_map_and_no_tools`, `a_branched_space_appends_a_thread_map_as_the_last_message`, `sibling_branch_turns_send_identical_trunk_bytes` (the cache invariant as explicit byte equality), `navigation_tools_round_trip_through_the_turn_loop`. Pure `ThreadSnapshot` behavior is unit-tested in `lib.rs`.

### Quoted references — the ordinal seam

The schema's `action_antecedent` `relation='reference'` rows (ordinal-keyed PK, `content_block_id` + byte `range_start/range_end` + `annotation`) are written and read end-to-end, designed as one seam with the `gpui-markdown-editor` embed-block plugin (see that crate's AGENTS.md). **The ordinal is the shared key:** `action_antecedent.ordinal` ↔ the body's `{{ embed N }}` marker ↔ the editor's embed-map key ↔ the footnote index. Ordinal 0 is reserved for the structural `reply` edge; reference edges take `1..=N` in supplied order, stable across generations (gaps after removal are fine).

- **Write:** `post_with_references(prompt, space_id, reply_to, Vec<ReferenceSpec>)` — a spec names the **concrete generation** quoted (references never remap to tips) plus `content_block_id` and a byte range. Every spec is validated **before any write** (antecedent exists — any space; block belongs to it; range maps honestly per the shared `quote_snippet` gate), so a bad reference leaves zero trace. Reference writes ride post's existing emissions.
- **Edit interplay:** `edit_post` replicates the tip's references onto the new generation at their original ordinals; `edit_post_with_removals(action_id, new_prompt, remove_ordinals)` drops named reference ordinals from the new generation only. Naming ordinal 0 or a non-reference ordinal is a typed error before any write — the reply edge is not removable through this surface.
- **Read:** `PostNode.references` (each with `content_block_id` + resolved `snippet` — `None` when the stored range no longer maps, never truncated/remapped), `PostNode::embed_map()` (ordinal → snippet, fed to `MarkdownEditorState::set_embeds`), `PostBlock.id`, and `references_to(action_id)` — the reverse index (every current-generation post referencing that concrete generation, with ranges).
- **Upstream — one rendering, every path a model reads (task 63):** a post says the same thing about its references whether a model reads it in the turn's own context, through `read_thread`, through `read_post`, or through `read_post(quote: N)` after following one (`tools::render_followed_post` — a followed post quotes things too, and handing the model a literal marker there would reintroduce the whole defect one call past the fix). `render_post_for_model` is that rendering and `ReferenceEntry` its unit: `[N] #<handle> · <author> — <annotation>` over the passage as a blockquote, splicing in at the marker and listing what the body never embedded under `Passages this post quotes:`. **Marker-less references reach the model** — the state is reachable by two designed routes (a draft whose marker was deleted; `edit_post` replicating an edge onto a body that no longer embeds it) and the human's footnote rail has always shown them, so `prepare_turn` reads the edges of *every* context post, not only marker-bearing ones (one indexed query per hop, beside the two `get_upstream_context` already walks). **The quote is attributed** because a bare blockquote inside another participant's post reads as that participant's own prose; `[N]` doubles as the `read_post(quote: N)` argument, so the inline passage is addressable for the first time. **A cross-space passage is attributed by its source space** — the label join in `db::reference_antecedents` is on `ant.space_id`, since a per-space override is that space's name for the participant and the reading space's override would misattribute. **A handle is offered only where it resolves to the passage being read**, and exactly one thing answers that: `ThreadSnapshot::node_for_action` — the turn's own snapshot, which *is* what `read_post` answers from, so the byline and the tool cannot disagree. **Every name comes from the snapshot when the snapshot has one**: a resolved node is a post of the turn's own space, so its handle *and* its label are read together and are already that space's effective ones; and an unaddressable target — which the snapshot cannot name directly — is named from the **referencing** post's own captured copy of the edge (`PostReference::antecedent_author_label`), which is what `read_thread` and `read_post` render from, so the context and the tools cannot attribute one passage two ways. The edge row's label answers only when even that is missing. A post's reference edges are written once with the post, so the captured copy and a fresh read describe the same edges and can differ in nothing but the label each joined. The edges themselves stay a database read deliberately — they are what *that generation* quotes, and taking them from the snapshot would drop a post's passages entirely when an edit lands between the two reads, instead of degrading only their naming. The edge row deliberately carries nothing that could answer it a second way: a row-derived predicate is a **separate read at a separate moment** (`get_space_tree_data` builds the snapshot, `reference_antecedents` reads the edges, nothing makes them atomic, and two windows share one `AppCore`), so an edit landing between them printed a handle whose `read_post` returned the edited text under the old excerpt. The snapshot is therefore read **before** the references are rendered and passed down. Being in it is the whole test, and it covers every case the row predicate used to enumerate: another space, a superseded generation, a trace/memory/decision action, a failed or in-flight generation — none of them is in the tree. Everything else is *named* — `<author> (a post outside this space, or an earlier version)` — and the addressable space is always the *turn's* space, including when the post being rendered was followed into another one. **The author survives that naming on every path**, which is why `PostReference` carries `antecedent_author_label` (the source space's effective label, joined on `ant.space_id` in `get_space_tree_data` as well as `reference_antecedents`): a **sibling branch is absent from the turn's context**, so `read_thread`/`read_post` is a model's *only* view of a post there, and a cross-space passage cannot be attributed from anything the reading space knows. **And it carries the author's `kind` beside it** (`antecedent_author_kind`, the same join, `get_space_tree_data` only — the model-facing renderings here want the source space's *words*, not a reader's): a label alone is not renderable, because "override to empty" is a real state and what to say instead — the one human is "You", an unnamed agent is "Eidola" — depends entirely on the kind. Reading only the label, the GUI's footnote rail had no second source for a blank one and fell back to "another space", so a cross-space quote of an unnamed author *still* changed attribution the moment it persisted (Codex review, PR #292; regression `a_cross_space_quote_carries_its_authors_kind_beside_its_label` in `tests/cross_space_references.rs`, which also pins that the join follows the **antecedent's** participant rather than the referencing post's). **A preview is neither rendering.** The thread map's opening line and `list_branches` summarize a post as chrome, so they elide the recognized markers and show the branch author's own prose (`strip_embed_markers`): expanding there would lead the teaser with a byline instead of the subject, and quoting the bare passage would attribute another participant's words to the branch author on a line that has just named them. It is the rule the GUI already applies to its own previews (`space_view::references::strip_embed_blocks`), with the same degradation — an unmapped or fence-defused marker stays literal on both surfaces — and a post with no resolvable reference is byte-identical. A label overridden to empty (the schema's non-NULL "override to empty", which `set_space_participant_override` deliberately allows) degrades on **both** arms: no author beside the parenthetical, and a bare `#handle` where a byline would otherwise trail the header separator into nothing. `message_header` itself keeps emitting the separator for a blank label — `is_header_line` keys on it, so a post header that dropped it would stop being stripped on receipt. **An entry carries state, not prose:** `ReferenceTarget` (addressable / elsewhere) × `ReferenceBody` (passage / unresolved range / backlink) decided at construction, rendered once in `ReferenceEntry::render`, so a new case is a compiler error at every construction site rather than a fourth site to get wrong. The three bodies are exactly the footnote rail's three rows — a **range-less edge is a backlink**, a pointer to a post rather than a quote of one (`ReferenceSpec`'s ranges are "both present or both absent"), and describing one as a quote whose range broke would be a plain untruth about an ordinary edge. All of it lands **before** the charge estimate, so the hold covers the bytes.
- **The chore prompts read it too (task 67):** the may-decline router and the branch summarizer are not turns, but they are model-facing, and both used to copy raw text — literal `{{ embed N }}` markers, un-embedded references dropped. Both now read `ThreadSnapshot::post_body`, so a quoted passage reaches them exactly as it reaches `read_thread`. **Expansion, not the preview elision**, on both, and for the same reason: a preview places a post's bytes on a line that has just named its author, while these two *read* the branch — eliding would take the noise and the meaning together, and a post whose point is what it quotes would route to nobody and summarize to nothing. Attribution is what makes expanding safe. The summarizer was free (`branch_slice` already sits on the snapshot); the **router** buys it with one whole-space read per triggering post, taken only for a space with a router model and never on the writer's path (the post is committed and emitted before refinement starts) — deliberately *one* read rather than the turn path's per-hop edge query, because the router needs the rendering, not this-exact-generation fidelity: a generation the snapshot no longer has falls back to the raw body, which is what that path sent before. Folding an action's blocks into one line also made `THREAD_SLICE_POSTS` count what it says. Prompt cost is unchanged in shape — both slices were already byte-clipped per post, so expansion changes *which* bytes the model sees, not how many it may. It does change **which end they come from**, and that is the one budgeting rule both chores now share (`utility::clip_middle`, replacing head-first `clip` at both call sites): a passage is a range its author chose and *nothing bounds its length*, so a marker standing before the post's own words (`{{ embed 1 }}\n\nHave the legal reviewer assess this`) expands into a quotation that can fill the whole per-post budget by itself — the router would then pick a participant without ever seeing the ask, and the summarizer would describe the source passage while dropping the branch author's disagreement with it, in a summary that stays cached and displayed until the branch changes. **Eliding the middle** is the cure because it needs no arithmetic about how a rendering will lay out: the expansion sits *between* the author's words in every shape that matters, so both ends are paid for before the quotation gets the remainder. It is also the rule the summarizer already applied one level up, where an over-cap branch is sliced head + tail. Prose sandwiched between two long quotations is the case it cannot save, and it loses its middle like any other over-budget text. Tests: `the_router_reads_a_quoted_passage_not_its_marker` (`tests/participants_orchestration.rs`), `the_summarizer_reads_quoted_passages_not_their_markers` (`tests/branch_summaries.rs`), plus `a_long_quote_does_not_evict_*` beside each prompt builder and `clip_middle`'s own unit tests in `utility.rs`.
- **One byline per post:** every author-label read returns the effective label (`COALESCE(space_participant.override_label, participant.label)`), `db::get_space_tree_data` included — it was the one read that did not, so a renamed participant answered to their base name in `read_thread`/`read_post`/the thread map (and in the GUI's post bylines) while the transcript used the override. The join stays plain, with no liveness filter: who wrote a post goes on being named after retirement.
- **Marker recognition** is `eidola_common::embed::embed_marker_spans` — the shared structural contract with the editor plugin: only a marker standing as its own blank-line-delimited top-level paragraph, outside fenced-code/block-math regions, expands — exactly the set the editor renders as embed blocks, so the UI and the wire never disagree. A marker whose passage did not resolve stays literal (the editor's degradation) and is footnoted instead. The editor keeps its own parser-driven recognition (it can't depend on eidola-common); lockstep is held by the corpus test `crates/eidola-gui/tests/embed_lockstep.rs` plus identical lexical cases in all three crates.
- **GUI wave 2** (surfaces + doctrine in `crates/eidola-gui/AGENTS.md`): Quote / Quote in Reply, the footnote rail, source highlights. Backing reads: `submit_with_references` and `action_location` (a persisted action's `(item_id, space_id)` — the item id is load-bearing: a quoted generation later edited/regenerated is absent from the current-tip tree, and the item lets the GUI select the superseding tip rather than opening a duplicate window). Draft ordinals may gap; the gap reconciles exactly once, at post time (specs compacted + markers rewritten together; the editor's `insert_embed_marker`/`remove_embed_marker` are the marker-byte owners).
- Tests: `tests/bus.rs` (rows, snippets, emissions, zero-trace failures, replication/removal), `tests/chat_path.rs` (`upstream_context_expands_embed_markers_into_quotes` — attributed expansion, a footnoted un-embedded ordinal, fence-defused markers going upstream literal; `a_reference_whose_marker_an_edit_removed_still_reaches_the_model`; `navigation_tools_round_trip_through_the_turn_loop` for `read_thread` parity), `a_per_space_rename_reaches_the_tools_as_well_as_the_transcript`; `a_quote_of_a_since_edited_post_is_not_offered_its_handle`; `a_reference_that_names_no_range_reads_as_a_backlink_not_a_broken_quote`; `a_quote_whose_author_has_no_name_here_keeps_a_clean_handle`), `tests/cross_space_references.rs` (`a_cross_space_passage_is_attributed_by_the_space_it_was_written_in`, `a_followed_post_renders_its_own_quotes_like_every_other_post`, `an_unvalidated_reference_to_a_non_post_is_withheld_by_every_read` — the edge is named, never addressed; `a_sibling_branchs_cross_space_quote_keeps_its_author_through_read_thread`, which pins the absent-sibling premise alongside the byline), plus the pure rendering in `lib.rs`/`tools.rs` and the addressability predicate in `db.rs`.

### Cross-space references — the permission model (task 37)

One sentence governs it: *you may quote what you can read; quoting **copies** the excerpt to the new audience; the link itself is not a capability.* **Membership is the ACL** (`db::is_space_member`: owned row ∪ live reference row, deliberately not filtered on `archived_at`) — and **membership means *live* membership: a live row and a live participant**. Retirement soft-removes the participant and leaves its `space_participant` rows standing on purpose (the trail records where the agent worked), so a question asked only of the row went on answering "member" for an agent just taken out of service — and since a turn binds its tools to the responding participant at the start, a retirement landing between two rounds left a live `read_post` still opening those conversations, and `list_my_spaces` still listing them (Codex review, PR #279). The rule is enforced **where membership is asked** (`is_space_member`, `participant_spaces`) rather than by sweeping `left_at` onto every row at retirement: one rule at the boundary that covers any future availability-ending state, that leaves the historical record undisturbed, and that no racing grant can slip past (`add_global_participant` already refuses a retired participant, and a row created anyway still would not answer). `space_participants` — the roster, and so planning and model→participant resolution — already read membership this way; the two ACL predicates had drifted from the definition their own docs claimed. **Author-label rendering paths keep their plain `space_participant` joins**: "who wrote this post" must go on naming retired authors — which is exactly why the *write* side has to be guarded too, and is (see the config-write contract above): a stale save that renamed a retired participant would have rewritten those bylines. Tests: `a_retirement_mid_turn_closes_the_passage_it_had_opened` (`cross_space_references.rs`), `a_retired_agent_discovers_no_spaces_mid_turn` (`global_agents.rs`) — both drive the real turn loop with a tool that retires the responder mid-turn.

- **Create:** `validate_reference_spec` refuses a spec whose antecedent lives in a space the authoring participant is not a member of — inside the same pre-write loop (zero trace, no emission). The author today is always the shared human, referenced into every space by the default template, so the single-user case is untouched; the one space it's not a member of is an agent's **notebook** — exactly the privacy the rule exists for. `edit_post`'s replication is deliberately not gated (quoting copies; the passage is already public here). Branch summaries and `remember` provenance write `db::insert_reference_antecedent` directly — the gate lives at the *post-authoring* seam.
- **What a reference may name** (PR #261 review — a real leak, closed): membership answers *whose* material; this answers *what kind*. `validate_reference_spec` refuses a non-post antecedent and any block that isn't `text` (`db::POST_ACTION_TYPES` / `QUOTABLE_BLOCK_TYPE`) — otherwise a quote could name another participant's `tool_call`, a `decision`, a `memory` block, or any post's `thinking` block, and the upstream embed expansion would have expanded it into the next responder's context. **All three read paths re-apply the rule** for edges written below that seam: the expansion skips it (marker stays literal), `build_post_tree` resolves its `snippet` to `None` (edge renders — existence is public — passage withheld), and `db::referenced_post` reads post types only. The filters live in the *readers*, never in `db::reference_antecedents` (edit replication must not silently drop edges — that would rewrite history). The `#[doc(hidden)]` `test_insert_unvalidated_reference` seam exists only for the regression test.
- **Follow:** `read_post` gained an optional `quote: N` argument (`tools.rs`) that reads the post a quoted passage came from, membership-checked **per call** against the responding participant — so blocked → grant → retry needs no machinery, just the grant below. **Cross-space addressing goes through the reference edge, never a handle** (handles are global but a snapshot knows only this space's): the model can name only this post's quote number, so the reachable set is exactly "what someone here already quoted" — guessing is unrepresentable.
- **Denial leaks nothing** (`AppError::NotAParticipant`, `tools::FOLLOW_DENIED`): may confirm existence (public within the referencing space); carries no space id, title, participant, or content — it renders both into a model-read tool result and into UI a non-member sees.
- **The human arm of rule 4 is the same rule, asked at the same place** (wave 2): `action_location(viewer, action)` — the read the GUI resolves a quoted post's home with before navigating — takes the viewer as a **required** argument and refuses a non-member with `NotAParticipant`. A second, ungated entry point was considered and rejected: it would have opened an agent's notebook window to a reader who is not in it, which is the one space the shared human genuinely is not a member of. An unknown action still answers `Ok(None)` — conflating "no such action" with "not yours" would make the read a membership oracle.
- **Grant:** membership, and for a space-owned agent the promotion that must precede it, travel as **one transaction**: `promote_participant(id, persona, grant)` takes an optional `SpaceGrant { space_id, role }` written inside `promote_participant_tx` (`db::MembershipGrant`), and `add_global_participant` takes an optional `MembershipRole` for the already-shared case (`Observer` is what a read-only grant is *called* — roles are descriptive; membership itself is the ACL). **And *which* of those two a grant needs is itself decided at the write** — `AppCore::grant_space_membership(space, participant, role)` → `db::grant_space_membership_tx`, the door the invite form uses: it reads the scope under its own `BEGIN` and either promotes-with-grant, joins (insert-or-revive), or reports `AlreadyAMember`. A caller branching on the *picker's* snapshot asked for a promotion of a row another window had already shared — refused, for a membership that would have been added without complaint, and (when the competing promotion granted this very space) reporting failure about a state that already held (Codex review, PR #280). It is the decide-at-the-write family applied to the **choice of verb** rather than to a write's arguments (PR #279's persona). It is deliberately **not** `promote_participant` learning to tolerate an already-global row: that refusal is the *Share* affordance's, and its copy ("promotion is one-way and there is no demotion") is what a reader who pressed Share needs; a grant is a different request and only it may be satisfied by a row that is already shared. Each branch still carries its own premise into its own statement, and the typed refusals (unknown space, retired, non-agent, the human, Eidola) stay in front of the transaction where a message belongs rather than a rollback. **And deciding at the write means reserving the writer**: every transaction here opens through `db::begin_write` (`BEGIN IMMEDIATE`), because a deferred `BEGIN` reserves nothing and these transactions all read before they write. Measured on turso at our pin with two live connections on one `Database` — `db_conn` mints a fresh connection per call, so this is an in-process race, not merely a cross-process one — a deferred `BEGIN` lets both sides read the old state and answers the second write `BusySnapshot("database snapshot is stale, rollback and retry the transaction")`, which `busy_timeout` cannot rescue (a stale snapshot is not something you can wait out); `BEGIN IMMEDIATE` makes the loser **wait** for the winner's commit and then read *its* state, which is how the grant takes the join branch instead of failing (Codex review, PR #280). **And the result reflects the commit point**: the membership a grant answers with is read *inside* its transaction and handed back (`db::GrantOutcome`), never re-read after it — between the commit and a second read another window can end that membership or retire the agent, and the call would then report failure for work that committed, including the irreversible promotion. That is the failure-message-beside-a-committed-write state the transaction exists to prevent, reintroduced one line past it. `add_global_participant` had the same window (its join and the roster read that described it shared no transaction) and now goes through `db::join_space_participant_tx`. The rest of the family is clean by construction and was re-checked: `promote_participant` assembles `PromotionOutcome` from its *inputs* (the argument, the row read before the transaction, the uuid it minted, the grant it was handed); `retire_participant` answers `()`; `remove_space_participant`'s `bool` comes from the transaction's own `SpaceRemoval`, and its one post-transaction read is on the refusal branch, where nothing committed and the label already degrades honestly. Regressions: `tests/tx_contention.rs`. Test: `a_grant_decides_from_the_row_it_finds_not_from_the_pickers_snapshot`; the canonical blocked → grant → retry loop now goes through this door. Two calls were the wrong shape for the same reason the persona was (Codex review, PR #279), only sharper: **promotion is one-way**, so a grant refused after the promotion committed leaves an irreversible change nobody asked for standing beside a failure message. A grant naming the promotion's own home space is *satisfied* (the promotion joins it) rather than refused; an unknown space is refused before the transaction opens. `list_grantable_agents(space, viewer)` is the picker's read — live agents not already members, viewer-scoped so a space-owned agent is listed only where the viewer takes part in the space that owns it (a listing is a read, and obeys the same ACL its rows are about). **"Not already a member" means not *live*ly one, so an agent that left is offered again — and the write has to honour what the picker offers**: leaving is soft (`left_at`), the row stays on the space's primary key, and the insert-only join struck nothing, so the roster read that followed found no member and told the reader the *live* agent "has been retired and cannot rejoin a space" — the wrong sentence, and permanent, since every retry took the same path (Codex review, PR #280). `db::ensure_space_participant` is therefore **insert-or-revive**: one guarded statement whose `ON CONFLICT … DO UPDATE` clears `left_at` and applies the role being asked for, under `WHERE left_at IS NOT NULL` so a **live** membership is never rewritten (which is what the template instantiation's copied human reference — inserted moments earlier with the template's own role and overrides — depends on). The `WHERE EXISTS` liveness premise guards both paths for free: a `SELECT` that yields no row conflicts with nothing, so a retirement that wins the race revives nothing either. It answers whether the membership *changed*, which is what `add_global_participant` emits on: a fresh join or a revive emits `Change::Participants`; a re-add of a live member writes nothing and says nothing. Promotion's own grant (`db::insert_space_participant`, inside `promote_participant_tx`) needs none of this and deliberately keeps its plain insert: its candidate is space-**owned**, so it has no membership row anywhere but its home space, and a collision there is a bug the whole transaction should fail on. Tests: `an_agent_that_left_can_be_invited_back` (`cross_space_references.rs`), `a_membership_that_left_is_revived_and_a_live_one_is_left_alone` (`db.rs`).
- **Inbound:** `references_to_visible_to(action_id, viewer)` filters the reverse index to referrers in spaces the viewer takes part in ("can see" = "can open"); the unfiltered `references_to` remains available, but **the GUI reads the filtered one** (wave 2 — the recorded lean, implemented: the app never paints a backlink whose click it would refuse). Same-space backlinks are unaffected wherever the viewer is a member of the space being read; the one place they are not is a **notebook** opened from Settings ▸ Agents, where the human can read the conversation but is not a member — so its own highlights are withheld. Inbound references are deliberately not added to upstream turn context in this wave.
- **Known wave-1 limit:** the follow affordance rides the navigation-tool gate (`has_map && backend_accepts_tools`), so a linear space containing a quote gets no `read_post` — on any backend. Widening the gate to linear spaces is coherent but changes wire bytes for spaces that send none today — the GUI wave's call.
- Tests: `tests/cross_space_references.rs` (the permission matrix; plus `a_share_whose_grant_is_refused_shares_nothing`, `a_grant_naming_the_home_space_is_satisfied_by_the_promotion`, `the_grant_picker_offers_only_agents_that_could_join_and_only_ones_you_know_of`, `a_human_following_a_quote_into_a_space_they_are_not_in_is_refused` — the denial leak-checked on both arms) + `tools.rs` unit tests.

## Agent-spawned sub-spaces (`subspaces.rs`)

An agent that needs work done elsewhere spawns a **sub-space**: a new space with **no human participant**, holding the spawning (owning) agent and the sub-agents it delegates to, opened by a *brief* the owner writes. Nothing is copied — the room starts fresh, and the parent hears back through an ordinary cross-space reference rather than a merged transcript.

**Ownership needs no column.** It is `space.parent_space_id` (documented navigational since the schema was written, NULL until this door) plus the owner's `role = 'owner'` membership row. That is the notebook lesson in reverse: a notebook needed `notebook_participant_id` because its consumers ask *whose* it is **without** membership, while a sub-space's owner is definitionally a member, so the membership row can carry it. `db::SUBSPACE_OWNER_SQL` is the one fragment every read resolving an owner shares, so "who owns this" cannot be answered two ways.

**Which makes that membership structural, and it is held so at every write that could move it — three of them, and the set is the point.** One row records who is answerable for a delegation, whose live-room quota it counts against, and who its report will go to, so ordinary roster work must not be able to end it, add a second one, or leave it pointing at somebody who is gone: **the leave is refused, a second owner is refused, and retirement archives.** The third is not a fourth guard of the same kind — retirement writes neither of those rows (it soft-removes the participant and leaves its memberships standing, after which every membership *question* answers "no"), so nothing the first two do can reach it, and no door could repair what it leaves: a replacement owner is exactly what the second guard refuses, correctly, because ownership is not transferable. `db::retire_participant_tx` therefore archives every live sub-space the agent owns in the same transaction as the soft-remove, **owner-scoped rather than by descent** — so it reaches that agent's rooms at every depth and nobody else's. Archiving rather than refusing the retirement: one stuck delegation must not make a shared agent unretirable, and the notebook arm standing beside it in that same function already made the choice. The room stops being live, so it holds no quota, stops being a Library row promising work that cannot happen, and — because archival is what stops new turns anywhere (see Archival stops new work) — schedules nothing and refuses any turn already planned in it; the transcript survives whole, because archival is a visibility choice and neither membership nor the human read bypass filters on it. **A sub-space another agent spawned from one of these is left live** — its own owner is still answerable for it — with its parent link pointing at an archived room, which nothing reads to decide anything about a child. Emissions follow the listing, not the archival: `Change::Participants` always, and `SpaceIndex` exactly when the transaction archived a space the Library lists (a sub-space is one; a notebook has never been), counted inside the write and returned as `db::Retirement`. In detail: `remove_space_participant` refuses the owner **in the leave's own `WHERE`** (`SpaceRemoval::RefusedSubspaceOwner` — the notebook owner's rule applied to the other structural membership, and guarded in the statement for the same reason: a spawn mints the room and the membership in one transaction, so a removal that read the space a moment earlier saw an ordinary conversation), and both granting doors ask `db::subspace_owner_of` **inside their own transaction** before writing a `role='owner'` membership (`db::refuse_second_subspace_owner`, reached by `grant_space_membership` and by `add_global_participant`, which takes a role too — and defaults it to the agent's own, which can be `owner`). An ordinary space is untouched: `role` stays descriptive there. With both guards in place a departed or duplicated owner is unrepresentable, so `SUBSPACE_OWNER_SQL`'s `left_at IS NULL` filter and its total ordering are belt to that brace — if one ever appeared the read answers "no owner" (a sub-space that stops being one, which every consumer already handles) rather than resurrecting an ended membership, and answers the *older* of two rather than whichever the planner reached first.

**The door is `db::spawn_subspace_tx`, one `BEGIN IMMEDIATE` transaction that decides every guard at the write.** Each guard reads state a concurrent window can change (a membership, a retirement, another spawn, an archival), so asking before the writer is reserved would let two spawns pass a limit only one may. In order: the parent exists; the spawner is a **live global agent** and a live member of the parent (global because a space-owned participant cannot be referenced into another space at all — the rule that lets an agent own a room elsewhere is the same rule that lets it join one, which is what will make a `scope=='global'` gate on the tool that exposes this door structural rather than a second opinion); depth ≤ `MAX_SPAWN_DEPTH`; live sub-spaces owned < `MAX_LIVE_SUBSPACES_PER_OWNER`; requested capabilities ⊆ the parent's; every requested sub-agent is a live global agent (the `add_global_participant` rule, asked here so the refusal is the spawn's). Then, in one commit: the space row (parent link, the parent's `cascade_limit` and `router_model`, **born stamped**), the owner's `owner` membership, each sub-agent as a `member` with `override_notify_policy='all'`, the brief, and the capability rows. **No human membership row** — this is a new creation path, not `instantiate_template` (which joins the shared human unconditionally and whose template agents have nothing to do with a delegation). Refusals are `AppError::SpawnRefused` carrying a typed `SpawnRefusal` whose `Display` is model-facing prose, so the tool that exposes the door renders a refusal as a correctable tool result rather than failing a turn.

**`override_notify_policy='all'` on the sub-agents is what makes a human-less room live**: the seeded policies fire only on human-authored posts, and there will never be one here. The override is per-membership, so the agents' global rows are untouched (pinned in `subspaces.rs`'s roster test, which also asserts the parent membership is unchanged). The **owner keeps its own policy** deliberately — giving it `all` too would make every sub-agent answer bounce back, bounded only by `cascade_limit`.

**Guards are constants, not schema** — `MAX_SUBAGENTS_PER_SPAWN = 8` (every seat is written with notify-all, so each sub-agent answers every post *and* each answer notifies all the others: one spawn's scheduled work grows with the square of the roster, and the cascade guard is the only thing that ever stops it — a panel is the point, but a panel is small), `MAX_SPAWN_DEPTH = 3` (a space nobody spawned is depth 0, so great-grandchildren are admitted and their children refused; `db::space_depth` walks the chain and is cycle-guarded, because the column is a self-referencing FK with no cycle constraint and this is the one place a cycle becomes a hang) and `MAX_LIVE_SUBSPACES_PER_OWNER = 8` (archiving one frees a slot, which is also the stated remedy for a delegation someone regrets). `cascade_limit` inherits the *parent's* value — attenuation-flavored: a delegation never gets a looser runaway guard than the room it came from.

**Capability attenuation is a snapshot, and a grant is copied rather than composed.** `space_capability(space_id, name, config)` is written inside the spawning transaction and immutable afterwards; **absence of a row is absence of the capability**, so "a sub-space holding a grant its spawner lacked" is an invalid state checked once, at mint, against data. The only source a spawn may draw from is **its own parent's snapshot**, which is why a chain attenuates without anyone walking it: what B may give C is what B was given, and a capability B's *grandparent* holds is simply not there (`attenuation_holds_down_a_chain_a_grandparent_cannot_reach_through`). A spawn also refuses to seat a participant — the owner included — with **no model in its own row**, because a sub-space sees each participant's *base* configuration (nothing but the notify policy is overridden into one, so a model supplied by an override in the parent does not travel) and a model-less agent is skipped by every planner: seating one would report a room that scheduled nothing. A request names capabilities by name only — the `config` is copied from the parent's row byte for byte, so nothing can be widened on the way down; narrowing a config is a future refinement, not a v1 hole. The table is **empty in practice today** (tool availability is fully derived: registry + `has_map` + backend probe + `scope=='global'`); the shape is the point, so VM sandboxes and web search arrive as rows flowing through this gate rather than as new security surfaces. Because nothing in production grants a capability, the gate could otherwise only be tested on its refusals — hence the `test_grant_space_capability` seam, which seeds the root of a chain. **That seam is compiled out of release builds** (`#[cfg(any(test, feature = "test-support"))]` on the db half as well as the `AppCore` one), unlike the read seams beside it which carry `#[doc(hidden)]` alone: a read cannot forge state, while this one mints the very thing the model exists to make unmintable, and `#[doc(hidden)]` gates documentation and nothing else. `only_a_spawn_can_mint_a_capability` pins both that cfg and the fact that no other function in `db.rs` writes the table.

**The brief is a `brief` action — a fourth post type.** An agent-authored post outside a turn is neither `user_input` (which every display path maps to the human's role) nor `inference` (which claims a model call and a spend that never happened), so the vocabulary gained one entry rather than one of the two gaining a lie. The cost measured before choosing: the schema CHECK, `db::POST_ACTION_TYPES{,_SQL}`, `mechanical_plan`'s post gate and `render_messages`'s two matches — all additive, and the last three now read `db::is_post_action_type` / `db::is_agent_post_action_type` instead of inline literals, so a fifth type is one constant away. The upstream role split was already participant-derived and needed nothing. The GUI's `SpaceView::from_post` falls through to `assistant`, which is the truthful render. Reusing `user_input` would have cost nothing to write and would have attributed an agent's post to the human on every surface that maps by type, including `first_user_text`, whose "the first `user_input` item" contract the sub-space's brief would have quietly become.

**Billing is unchanged, and confirmed rather than assumed**: the pricing contract inspects only message/tool JSON shape, and holds are minted from the process's single configured account — nothing assumes a human at the root of a thread. A sub-space turn spends like any turn; the human authorized it by authorizing the owning agent's turn.

**Reads for a driver:** `subspaces_of(parent)` (every sub-space of a parent, archived included — a parent's history of delegations does not shorten), `live_subspaces_owned_by(owner)` (the rooms an agent is answerable for; also what the per-owner guard counts), `subspace(id)` (parent + owner from a sub-space id, `None` for an ordinary space — the "where does the report go and who writes it" read), and `space_capabilities(id)`.

**Reaper interaction: a sub-space is never pristine.** Its brief commits in the spawning transaction, so it has an `action` before it has existed for anyone, and the disposal's first leg refuses it whatever else is true; it is also born stamped, the way a promotion's notebook is. The predicate's `parent_space_id` clause protects the **parent**, and over-protects it: spawning requires the owner to be mid-turn in the parent, so a space that owns a sub-space has actions and was never reapable. `space_capability` is a sixth inbound edge of `space(id)` and is deliberately **not** deleted by the disposal — it is empty for anything reapable, and if that ever stopped being true the FK aborts the transaction and the space is kept, which is the direction the whole feature errs in. The ledger row is `spawn_subspace_tx_body` (stamp folded into the insert, so there is no ordering to get wrong). Tests: `tests/subspaces.rs`.

**A sub-space is always titled.** It sits in the Library beside every other conversation and the reader has no prompt of their own to recognize it by — and no snippet either, since a `brief` is not what `first_user_text` reads. An explicit title wins; otherwise the brief's opening line names it through the same `derive_space_title` an untitled space's first post gets; and a brief that yields no line at all (pure markdown scaffolding) is named `Delegated by <owner label>` inside the spawning transaction, where that agent's row is already read. Refusing such a brief was the alternative and was rejected: it punishes a model for its formatting, and the row still has to be findable.

**Writing into a sub-space is not reading one.** `post` refuses when the shared human is not a live member of a **sub-space** (`AppError::NotJoined`, carrying the space id, decided before any write so the refusal is zero-trace; `chat` and `chat_stream` inherit it, since they post first). The roster the models are shown has to stay truthful about who is in the room, and the `human` notify policy would otherwise fire in a space whose whole premise is that it has none. The Library lists sub-spaces and every listed row has a composer, so this is reachable rather than theoretical. The refusal names the join that would satisfy it; the GUI slice that ships the join turns this refusal into that explicit act, at which point the message is what changes. **A notebook is deliberately outside this rule** — the human has always been able to write in their own agent's notebook from Settings ▸ Agents, and narrowing that is not this door's business.

**A brief is neither editable nor regenerable** (`AppError::WrongPostKind`). Both writers claim a post's *item* — `edit_post` appends a `user_input` generation authored by the human, `regenerate` appends an `inference` one — so aimed at the wrong kind they do not amend a post, they replace it with a different kind of thing. `Inner::require_post_kind` is the shared gate, and it is symmetric: an edit needs a `user_input` tip, a regeneration an `inference` one. The brief is what made this reachable (it renders in the assistant slot, so a surface offering Regenerate by role would offer it) and it is the sharpest case: a regeneration is billed, `Revise` withholds the generation being replaced from the context, and the brief is the contract the room's participants are working from — so the model would be paid to guess at text it is not shown, and the room's premise would be overwritten with the guess.

**Humans read a sub-space without being in it.** `db::may_read_space` is the read-side widening of membership and the only one: a live member, **or** a human viewer, **never** into a notebook. It backs exactly two surfaces — `action_location` and `references_to_visible_to` — and every model-facing gate goes on asking `is_space_member` (`read_post`'s per-call follow check, the reference-authoring gate, `participant_spaces`; `FOLLOW_DENIED` unchanged). The justification is oversight: a sub-space has no human member by construction, so under membership alone the rooms an agent opens on the human's behalf, spending the human's account, would be the one thing the human could not see. The **notebook clause is the boundary that keeps the bypass about oversight rather than access** — an agent's own residence is the privacy the cross-space permission model's gate was built for, and its backlinks were already withheld from the human who opens it from Settings. So: a human may read any conversation their agents are having *with each other*, and none an agent is having *with itself*. Writing will still mean joining, so the roster the models see stays truthful. Regression for the boundary: `a_human_following_a_quote_into_a_space_they_are_not_in_is_refused` (`tests/cross_space_references.rs`). Read and write part company here: the bypass opens the room, and `post` still refuses it.

## Participants v1

**Scope-owned model** (schema detail under Database below): every `participant` row has exactly one `scope` — `global` (shared library; the human `User` = `HUMAN_PARTICIPANT_ID`), `space` (owned by one space), or `template`. Config columns live **only** on `participant`; reference tables (`space_participant`, `space_template_participant`) reference **globals only** with per-membership override columns (**NULL = inherit; `''` = override to empty**). A space's participants = owned rows ∪ referenced globals (`db::space_participants` returns the unified effective view).

**API surface:** DTOs `ParticipantInfo` (its `reference` carries base config + raw override values so the GUI renders the edit-everywhere-vs-override-here fork honestly), `NewParticipant`, `ParticipantUpdate`, `ParticipantOverride`, `SpaceTemplateInfo` (owned agents + `referenced` globals with effective config), `TemplateParticipantInfo`, `NewTemplateParticipant`. Per-space CRUD: `list_space_participants` / `add_space_participant` / `update_space_participant` (edit everywhere) / `set_space_participant_override` (override here; `None` reverts a field) / `remove_space_participant` (the shared human can't be removed) — all emit `Change::Participants`. **Configuration writes carry the premise they were composed under.** Liveness is one half — `db::update_participant_config` writes `WHERE id = ? AND removed_at IS NULL` — and `db::ScopePremise` (surfaced as `ExpectedScope`, a required argument of `update_space_participant`) is the other: `SpaceOwned { space_id }` for an editor opened on a space's own row, `Global` for the library and the inspector's "Everyone", `Any` where the caller has no premise. Save and Share are the same control on one row, so the second replaces the first's gpui slot — sanctioned last-wins — but a replaced write's *core* call keeps running, and the two do not share a premise: a Save composed against the owned row would otherwise land after promotion and republish the old persona to every space the agent has since joined (Codex review, PR #279). Carried into the statement, the expired premise makes the stale write strike nothing, and `refuse_dead_participant` then names which half expired. The mirror needs nothing: a *referenced* write is either `Global` (and promotion is one-way, so it cannot expire) or an override, whose membership row only exists for referenced rows at all. **Configuration writes carry their own liveness, so retirement wins terminally**: `db::update_participant_config` writes `WHERE id = ? AND removed_at IS NULL` and `db::update_space_participant_override` writes only onto a **live membership of a live participant** — the same definition `is_space_member` reads, now asked of a write. Save and Retire are independent operations in independent GUI slots, and a `bridge`d core call runs to completion after its gpui task is replaced, so a Save from another window can commit *after* a retirement; updating by `id` alone let it rename a retired participant, and since the trail renders an author's byline by joining that row, the record retirement promises to leave alone changed silently underneath it (Codex review, PR #279). The predicate is in the statement rather than a caller's earlier read because no interleaving can then put a live read in front of a write that lands later; a zero-strike is explained afterwards (`refuse_dead_participant`) but never *decided* there, and a refusal is zero-trace — nothing written, nothing emitted. The same rule reaches the two doors that write *new* state rather than editing a row: **`remember` asks the owner's liveness inside the transaction that carries its writes** (a memory write is several statements and cannot carry the predicate in one, so the transaction is where the question becomes unanswerable-by-interleaving; a retired owner gets `MemoryRefusal::OwnerRetired`, which the tool narrates, and nothing is written), and **`ensure_space_participant` carries it in the insert** (`INSERT … SELECT … WHERE EXISTS (live participant)`, still `OR IGNORE` so the join stays idempotent) — where a read-then-insert had left a durable membership joined *after* a retirement, plus an invalidation and an `Internal` error where a typed refusal belonged. `PersonaWrite::apply` rides the same door and inherits the guard; inside `promote_participant_tx` it targets a row that transaction has just proven live, so the clause can never turn a valid promotion into a failure. It is the idiom `update_backend` already used. Test: `a_save_that_lands_after_retirement_is_refused`. **`remove_space_participant` decides at the write, not from a read**: soft-removing this space's own row and ending a reference membership are different acts, and choosing between them from a `get_participant` taken a moment earlier is a window promotion walks through — the stale soft-remove would set `removed_at` on a row that had just become **global**, retiring a freshly shared agent from the library and orphaning the notebook promotion created (only retirement archives it), with both callers reporting success. So the ownership test rides in the soft-remove's own `WHERE` (`scope = 'space' AND owner_space_id = ?` and still live) and zero rows falls through to the leave — which after a promotion is exactly the reference row it left behind. `db::remove_space_participant_tx` owns that decision and reports it as `SpaceRemoval::{SoftRemoved, Left, NothingToDo}`; the emission is unchanged either way. The mirror guard sits on the other side (`promote_participant_tx`), so whichever transaction commits first the loser refuses cleanly (Codex review, PR #279; `db::tests::a_removal_decided_before_a_promotion_cannot_retire_the_shared_agent`, `removing_a_shared_agent_from_a_space_is_a_leave_not_a_retirement`). Template CRUD: `list_space_templates` / `create_template` / `template_from_space` / `update_template` / `remove_template` (soft; the built-in Default can't be removed) — all emit `Change::Templates` — plus `set_default_template` (emits `Config` + `Templates`) and `create_space_from_template(template_id, title)` (emits `SpaceIndex`). **New spaces are instantiated from the live default template** (`Inner::instantiate_default_space`), so every space carries its participants (the referenced-global human + owned agent copies) from birth; a config pointing at a removed template falls back to the seeded default. **Instantiation is one transaction** (`db::instantiate_template` → `BEGIN IMMEDIATE` around the whole body, the `promote_participant_tx` shape): the space row, the owned-agent copies, the reference copies and the human's membership commit together or not at all, and the template's liveness is read inside it — decided at the write like every other guard. A space without its participants is not a space, and turso autocommits each statement, so before this a failure partway left a durable half-populated row while every caller's error handling read the refusal as "nothing was written". Fixed at the shared door, so all three callers inherit it (`create_space` / `create_space_with_id`, `post`'s space-less branch, and `create_space_from_template`). Regression: `db::tests::a_failed_instantiation_leaves_no_space_at_all`. `create_space` / `create_space_with_id` therefore emit `Participants` and `Space(id)` beside `SpaceIndex` — one per thing the instantiation wrote — because a caller holding the id **before** the row exists (the GUI's ⌘N window) reads that space's roster and settings on the way, and only an announcement takes an early "empty" / "no such space" answer back.

**Turns are participant-aware.** `run_turn`/`run_turn_stream`/`prepare_turn` take a `TurnSelector`: `Participant(id)` resolves the member's effective config (COALESCE(override, participant config)); `Model(m)` is the model-picker compatibility path (CLI/GUI `chat`/`chat_stream`/`regenerate`/`respond_stream`) — resolves the space's agent whose canonicalized effective model matches, **minting a fresh space-owned agent when none matches** (`resolve_or_mint_agent_by_model`; the seeded default agent is the common match). The responding participant's effective system prompt is prepended as a leading `system` message — riding the same array the estimate and wire request use, and **not persisted** (forensics never resolve mutable participant config).

**Participant-aware upstream rendering** (`actions_to_upstream_messages`):

1. **Role split:** only the responding participant's own prior posts render as `assistant`; every other participant's — human and agent alike — render as `user` (mapping every `inference` to `assistant` showed a model another agent's words as its own).
2. **Headers:** every message opens with the one-line header `#<handle> · <label> · <stamp>`, blank line, then text — in-content, deliberately not the OpenAI `name` field (inconsistent chat-template support). **Handles are derived, never persisted:** `post_handle(item_id)` = first 7 chars of lowercase base32 over `SHA-256(item_id)` — the *item* id so handles survive edits/regenerations, hashed because UUIDv7 prefixes of near-in-time posts would collide pathologically. **Strip-on-receipt:** models mimic scaffolding, so `strip_leading_header` removes a leading header-shaped line from output at persist time **and `LeadingHeaderFilter` removes it from the live stream** — one predicate (`is_header_line`) behind both, so what a reader watches arrive is what lands durably (a header that showed while streaming and vanished on reload was task 46, bug 1). The filter holds back only the undecided first line and releases ordinary prose on the first delta. `HEADER_PROTOCOL_NOTE` (appended to the system message, unpersisted) instructs against emitting one. **The stamp is absolute UTC, RFC 3339, seconds precision, `Z`-suffixed** (`post_stamp`, hand-rolled so the dependency surface is unchanged) — see Identity, roster, and post timestamps below for which time it names and why it has to be absolute. A **citation** byline is not a header and carries no stamp: `post_byline` renders `[N] #<handle> · <author>` for a quoted post, whose own header stamps it where the model reads the post itself.
3. **Labels are one-line by construction:** a label with a line break would inject a second paragraph attributed to that author (prompt injection via rename). `validate_label` (trim; refuse empty, control chars, U+2028/9) gates every label write seam, and `message_header` sanitizes anyway.

`ChatResult` carries `response_action_id` (the persisted inference id, for cascade re-planning) and `declined: Option<DeclineOutcome>` — mutually exclusive by construction: a decline wrote no post, so the `decision` action id rides in `DeclineOutcome`, keeping "cascade off a decision" unrepresentable.

**`submit(text, space_id, reply_to)`** = `post` + `plan_notifications(space_id, post_action_id)`, returning `SubmitResult { post, plan }`. The post commits and emits *before* planning, so the router can never delay or fail a submit. **`plan_notifications` is plan + router refinement and the only planning entry point that drives turns** (refinement is not opt-in — a cascade re-plans every hop, and one unrefined hop would notify agents the router filtered out). The unrefined mechanical computation is a pure read reachable only via `mechanical_notification_plan` (tests/inspection): notify set over the space's participants — `all` → always; `human` → only when the post's author is human; `explicit` → never — excluding the post's author and model-less agents; refuses to plan off a non-post action (zero turns). Turn driving stays caller-driven: one `respond_stream_as` per `PlannedTurn`, re-planning on each resulting post.

**Archival stops new work, at two gates and on one read each.** An archived space is not hidden, deleted or departed — every membership stands and every read still works — but it **takes no new turns**: `mechanical_plan` yields zero turns for one, and `prepare_turn` refuses one with `AppError::SpaceArchived`. Both decide from the *same statement* that was already reading the space's own row (`db::get_space`, which is why `SpaceRow` carries `cascade_limit` and `archived_at`: existence, availability and the budget arrive together, so no interleaving can put "it is there" in front of an archival that has landed). Two gates because one cannot close the race alone: planning refuses *after* an archival, `prepare_turn` refuses *in between* a plan and its driving. The gate is in the shared preparation, so every entry point inherits it — `chat`/`chat_stream`, `regenerate`, `respond_stream`, and the participant-aware `respond_stream_as` a cascade is driven through. **A turn already past that gate completes and persists**: the request was made and the tokens were spent, and dropping the answer would bill for nothing — but every hop re-plans, so its completion is where the cascade stops. `post` is deliberately not gated (the save side spends nothing, and post-first means a `chat` into an archived space keeps the thought and refuses the turn, exactly as a funding failure does). This was general and pre-existing — `archive_space` never stopped anything — and it became load-bearing when retirement started archiving rooms whose whole purpose is agents answering each other with no window open. Tests: `an_archived_space_plans_no_turns_and_starts_none` (`tests/participants_orchestration.rs`), `retiring_an_owner_stops_the_helpers_mid_cascade` (`tests/subspaces.rs`).

**Cascade guard (data-derived, no schema state):** `db::agent_cascade_depth` counts consecutive agent-authored posts in the reply ancestry back to the last human post (branch-scoped, item-tip-resolved; authorship is stable across generations); at the space's `cascade_limit` (default 4) `plan_notifications` returns `NotificationPlan::Paused` instead of turns. Explicit asks never consult the guard.

**Space consistency is an app-layer guard** (`Inner::require_action_in_space`): the schema doesn't constrain an edge or target to one space, so a mismatched (space, action) pair could splice threads across spaces. `plan_notifications`, `prepare_turn` (both modes), and `post` (`reply_to`) all reject a foreign/missing action with typed `AppError::NotConfigured`; a foreign participant is rejected by `resolve_explicit_participant`.

**ACT provisioning queue:** `Inner::spend_gate` (a `tokio::sync::Mutex`) serializes credential acquire → spend-proof → flip-to-`spending` across concurrent turns, so a fan-out never double-spends one credential. The second turn finds another active credential, auto-allocates from balance, or **waits bounded for an in-flight refund** (typed `AppError::ProvisioningTimeout` on deadline) — but only when a mid-spend credential whose face value covers the charge exists (a smaller one's refund can never fund the turn → immediate `InsufficientBalance`). The verdict is **instant-consistent**: the whole function runs under `spend_gate` and the only active→`spending` flip is under the same gate, so the covering-`spending` set only shrinks (via settlement — a single atomic insert) between reads; a re-read of `find_spendable_credential` before any terminal verdict observes a settled successor. It cannot be a false negative from an in-flight sibling refund; it does not (and cannot) cover funding arriving later from exogenous writes — an ordinary post-read TOCTOU the recoverable error routes the caller to retry. turso is single-writer, so `db::connect` sets `PRAGMA busy_timeout` — concurrent per-turn writes block-and-retry instead of erroring.

Tests: `tests/participants_orchestration.rs` (fan-out planning, system-prompt prepend, multi-agent role split with pinned bytes, cascade pause + explicit bypass, concurrent turns with real credentials) and `tests/chat_path.rs` (byte shapes, header derivation/stripping unit tests in `lib.rs`).

### Identity, roster, and post timestamps (task 64)

A model was never told **which participant it is**, nor who else is in the space: the default charter is "You are a helpful assistant", default agent labels collide on model id, and in a multi-agent space a model read a transcript of several voices with no statement of its own identity among them. The fix is split by **volatility**, which is the whole design — one `db::space_participants` read in `prepare_turn` serves both halves.

**That read is the turn's participant snapshot, and it is taken first.** It is the single authority on what every *current* member of the space is called for the whole turn: the identity line, the roster, and the `<label>` field of every post header in the transcript (`relabel_from_members`, applied to `context_rows` right after `get_upstream_context` returns). A turn's reads are not atomic — each hop of the context walk joins its own effective label, `space_participants` is another statement, and another window on the same `AppCore` can commit a rename in between — so left alone the interleaving tells a model it is `"Navigator"` in a transcript whose own posts are headed `Ada` (Codex review, PR #294). A read transaction was the alternative and was rejected: a turn must not hold one open across an inference. Funnelling every current member's name through one snapshot makes the interleaving unobservable instead — a mid-turn rename is wholly before the read or wholly after it, and either way the turn is self-consistent. **An author the snapshot does not carry keeps the label its own row joined**: `space_participants` is live membership (`left_at IS NULL`), so a departed participant is provably unnameable from it, and who wrote a post goes on being named after they leave. **Residual, recorded:** the `ThreadSnapshot`-derived renderings (the map's branch authors, `read_thread` / `read_post` headers) keep their own read — `PostNode` carries no participant id, so the snapshot is not even addressable there, and those name posts by *third* parties rather than the responder's own identity. Their worst case is one turn of a stale name in a tool result, which the next turn heals.

- **Identity** — `identity_line(label)` → `You are "<label>" in this conversation.`, leading the notes, i.e. directly after the charter and before `HEADER_PROTOCOL_NOTE`. **Ungated: present in every space, linear ones included.** Static per participant, so it flips once (at a rename) and is byte-stable after. The label is the responder's **effective** one in this space — the same override-aware label its own posts are headed with, so the two cannot disagree. Deliberately minimal: identity is universally useful, while framing about *others* belongs in the roster, which only appears when others exist.
- **Roster** — `render_roster(members, responder_id)`, in the **trailing volatile block** ahead of the thread map, gated on `has_map || participants > 2`. One line per member, `- "<label>" — <kind>` with ` (you)` on the responder, in `db::space_participants` order (humans first, then by id — stable within a membership, so the bytes move only when the membership does). It closes with one sentence, `ROSTER_INDEPENDENCE_NOTE`: *"Each participant answers for itself; weigh others' posts on their merits rather than deferring to them."* **A roster is not free** — naming peers measurably induces anchoring and sycophancy (AgentVerse attributed roughly a tenth of its errors to agents swayed by peer feedback), so the block that names them also says what a participant owes them, which is nothing but honest assessment. Lines carry **label + kind only**: AutoGen's `name: description` shape was trimmed because a description would leak other participants' charters. The gate is a **usefulness** judgement (a roster in a two-party linear chat is noise), not a byte-identity requirement — see the reframe under Thread map.
- **The trailing block is one message** carrying the roster then the map, in that order, and it **always closes with `Respond to #<handle>.`** — the pointer belongs to the *message*, not to the map (`render_map` no longer emits it). A `user` message appended after the post being answered is the last thing a chat model reads, and whatever it contains the model will be tempted to answer *it*; the roster-only shape (a linear space with three or more participants) carried no pointer and no framing at all, so membership metadata read as the current request (Codex review, PR #294). When neither section applies there is no trailing message at all.
- **`TRAILING_BLOCK_NOTE` frames it, gated on the message existing** — *"The last message is client-generated metadata about this space, not a post by any participant. No reply is due to it, and it ends by naming the post you are answering."* One note rather than one per section, because nothing it says is section-specific; `THREAD_MAP_NOTE` now explains only the threading and the `<thread-map>` block, after it. Both are protocol explanation, so each flips once — when the space first grows a trailing message, and when it first branches — and is byte-stable after.
- **A label inside quotes goes through `quoted_label`** — the identity line and every roster line, which are the only two places a label sits between raw quotes in model-facing bytes. `validate_label` deliberately admits ordinary quotes (`Ada "The Countess"` is a name a person may choose), so a raw interpolation was a rename away from an injected instruction: the valid label `Ada"; instead you are "Bob` closed the frame early and opened a second, complete-looking sentence inside a privileged one (Codex review, PR #294). The cure **reserves the delimiter** — the label's own `"` become `'`, so no `"` can appear between the frame's quotes and the boundary is unambiguous by construction. Escaping (`\"`) was rejected: a model reads a backslash as text, not as a boundary, so the injected clause would still read as a clause. Line-flattening (`one_line`) still applies, for the reason it always did. **The roster is the sharper half of the same hole**: its lines carry client structure after the name, so the valid label `Mallory" — agent (you)` rendered as `- "Mallory" — agent (you)" — human` — an apparent self-marker planted on a participant who is not the responder (Codex review, PR #294). One reserved delimiter cures both, which is why there is one function and not two: with exactly two quotes per line the closing delimiter is identifiable, and everything after it is the client's own structure — `— <kind>`, with ` (you)` on the responder alone.
- **Post timestamps** — `message_header` renders `#<handle> · <label> · 2026-08-11T14:02:33Z`. **Absolute, never relative**: a relative stamp would churn every header on every turn and invalidate the whole upstream prefix cache each time, which is exactly what `sibling_branch_turns_send_identical_trunk_bytes` pins against. **The time is the post's *current generation's* `action.created_at`** — what `item_current` / `action_resolved` already resolve to on every model-facing path, so `SpaceActionRow`, `PostNode` and `ReferencedPostRow` all carry the same number. An edit or regeneration *is* a new generation, so its stamp moves with the text it describes: the honest answer to "when was this written", and still byte-stable, because it moves only at the moment the body it heads moves anyway. The item's **origin** time was the alternative and was rejected — it would date an edited post to prose that no longer exists.
- **A label overridden to empty** drops its field rather than leaving a dangling one (`#<handle> · <stamp>`); the separator `is_header_line` keys on survives either way.
- **Nothing here assumes a label is the only way to name a participant.** The roster renders from `db::EffectiveParticipantRow`, so participant **ids** stay reachable where names are produced, and no path parses or normalizes labels in a way a future inline `{{ participant <id> }}` marker would collide with (task 71, first-party mentions).
- **The seeded human's label is `User`, not `You`** — viewpoint-neutral on the wire, because in a multi-party roster a line reading `"You" — human` would read as *the reader* to every model while a different line carried the self-marker. Display is unchanged **on every human-facing surface**, not only post bylines: the GUI's `byline_for_participant` maps a human labelled `user` (case-insensitive) or blank to "You", and `space::display_name_for_participant` is the roster-row wrapper every surface naming a participant row reads (Codex review, PR #294 — see `crates/eidola-gui/AGENTS.md`). A human renaming their participant overrides it per space as before. The seed is `INSERT OR IGNORE` in `db::ensure_default_participants`, so **an existing dev database keeps `You`** — no schema change, no `LATEST_VERSION` bump; delete the dev database (or rename the participant) to pick the new label up.
- Tests: `tests/chat_path.rs` → `every_turn_states_which_participant_the_model_is`, `the_identity_line_names_the_participants_effective_label`, `the_roster_appears_only_once_a_space_is_multi_party` (which also pins the roster-only shape's response pointer and its framing note), `a_branch_turns_the_roster_on_in_a_two_party_space`, `post_headers_carry_a_stable_absolute_stamp`; pure renderings unit-tested in `lib.rs` (`message_header_shape_is_pinned`, `post_stamp_is_rfc3339_utc_seconds`, `a_reference_byline_carries_no_stamp`, `identity_line_is_pinned`, `roster_block_is_pinned`, `a_quoted_label_cannot_escape_its_frame`, `a_roster_label_cannot_forge_another_participants_self_marker`, `one_snapshot_names_every_current_member`).

## Global agents and in-place promotion (task 36)

`promote_participant(id, persona)` turns a space-owned agent into a **global** one on the *same row*, so authorship, provenance, and memory continuity are structural (copy-projection was rejected: it fragments identity). One transaction (`promote_participant_tx`, taking a `db::Promotion`): `owner_space_id → NULL` + `scope → 'global'` (the pinned scope echo on every past `action` and `memory_block` follows via `ON UPDATE CASCADE`), the optional persona, a `space_participant` reference row for the former owner space with NULL overrides (persona preserved byte-identically), and the agent's private **notebook space** (named for the agent, so a renaming persona names it too). `add_global_participant(space, id)` is the other half (idempotent; refuses space-owned, retired, and Eidola-the-system). **The notebook owner's membership is structural and cannot be ended**: the space exists only for that agent and is the residence of the `core` memory it writes, and nothing can grant a notebook membership back — so `remove_space_participant` refuses it (`SpaceRemoval::RefusedNotebookOwner` → a typed `AppError::Config` naming the agent). Guarded in the *leave's own `WHERE`* for the same reason the soft-remove is: a promotion mints the notebook and its membership in one transaction, so a removal that read the space a moment earlier saw an ordinary conversation; the follow-up read only explains a write that struck nothing. `SpaceSettings.notebook_participant_id` (via `db::notebook_participant_of`) carries the fact to the GUI so the roster can withhold an affordance that could only be refused — the courtesy; the refusal is the guarantee. Overrides on that row stay offered: a notebook's owner tuning how it behaves in its own notebook is ordinary per-space configuration, and reversible. Test: `a_notebook_owner_cannot_be_removed_from_its_own_notebook`. `PromotionOutcome` carries the id + home and notebook space ids; `notebook_space_id` is the GUI's door to inspection.

- **Promotion is one-way, enforced by absence:** no update surface writes `participant.scope`, so demotion is unrepresentable rather than guarded.
- **`persona` exists because a surface shares what it is *showing*, and that must not be a second write** (Codex review, PR #279). The GUI's "Share this agent…" sits inside an open editor, so the values it promotes are the visible ones — but an `update_space_participant` *then* a promotion is two transactions, and two windows share one `AppCore`: let the agent be shared or removed in between and the edit commits on a row that is by then **global** (so in every space that follows it) while the promotion is refused, telling the reader nothing happened. Carrying it here makes the pair atomic: the `ParticipantUpdate` is validated by the shared `validate_persona` (with `update_space_participant`, so an edit and a promotion cannot drift on what an update means) **before** the transaction opens, then applied inside it behind the same guard as the scope flip — which now reads `scope = 'space' AND removed_at IS NULL`, the transaction's own gate rather than a repeat of the caller's, so a lost race rolls the persona back with everything else. Still exactly **one** `Change::Participants`, persona or not.
- **Emissions: `Change::Participants` only** — not `SpaceIndex`, since the created notebook is excluded from `list_spaces` (the Library provably didn't change).
- **Memory needs no migration:** blocks keep owner, name, scope label, residence; the loading rule simply starts spanning spaces. The one new rule: a `core` block a global writes resides in its notebook (`memory.rs`).
- **Templates compose for free:** `template_from_space` projects a reference row, so every space instantiated from such a template gets the *same* colleague.
- **The library reads through `list_global_agents`** (`db::list_global_agents`): the live `scope='global'` **agents**, each with its notebook space id joined in — `kind = 'agent'` is what keeps the two seeded non-agent globals (the shared human, Eidola-the-system) out, and the join is there because the only consumer is a roster that offers the notebook door on every row. Ordered by label, the name the reader sees. Pure read, no emission.
- **`retire_participant(id)` is the library's other write, and not promotion's inverse:** one transaction (`db::retire_participant_tx`) doing the `participant.removed_at` soft-remove **and** archiving every space that existed only because of the agent — "archival tied to retirement". Its notebook, because the notebook exists only for it (a live notebook with no agent owns nothing; an archived one beside a live agent takes away the residence its next `core` block needs), and every **live sub-space it owns**, for the first of those reasons sharpened by what ownership carries — see Agent-spawned sub-spaces, where this is the third of the three write boundaries around ownership. The row keeps its id and its **scope**, so the trail still resolves it and demotion stays unrepresentable; what ends is availability. Refusal-first: unknown, already retired, the shared human, a space-owned participant (removed per space instead), a non-agent. Emits **`Change::Participants`, plus `SpaceIndex` exactly when it archived a space the Library lists** — never for the notebook (the listing excludes those on both axes, the same argument promotion makes), always for a sub-space (an ordinary Library row, which is also why `archive_space` emits `SpaceIndex`). The count comes back from inside the transaction (`db::Retirement`) rather than from a read after it. Nothing per-space is emitted: no store reads a single space's `archived_at`, so a `Change::Space(id)` would announce what no subscriber can observe.

Tests: `tests/global_agents.rs` — including the mid-turn promotion races (`a_promotion_mid_turn_does_not_lose_the_response` / `…does_not_strand_a_memory_write`), which pin the derive-scope-in-insert idiom (see Database); `the_agent_library_lists_shared_agents_with_their_notebooks`, `retiring_a_shared_agent_archives_its_notebook_and_keeps_its_trail`, `retirement_refuses_everything_that_is_not_a_shared_agent` (the sub-space arm is `retiring_an_agent_archives_the_rooms_it_owned_and_keeps_their_transcripts` in `tests/subspaces.rs`), `a_persona_travels_into_the_promoting_transaction` (the persona adopted, and both up-front refusals leaving zero trace); plus `bus.rs`'s `promote_and_retire_emit_participants_only` (which also pins the one-signal claim for a persona-carrying promotion). Two facts have no production observer, so each has a seam: the notebook's archival (`test_space_archived`) and a notebook's title (`test_space_title`) — `list_spaces` excludes notebooks on both axes.

## Record queries and trace visibility

**Record query APIs** — read-only, newest-first, `LIMIT/OFFSET`-windowed SELECTs over the local trail for the GUI's Record window: `list_attestations` / `attestation_detail`, `list_requests` / `request_detail`, `spend_trail`, `wallet_lifecycle`. Pure SELECTs, no schema changes.

**`space_traces(space_id)` (task 34)** is the parallel view of the actions `get_space_tree` collapses out, so a GUI can disclose what a turn did without leaving the space. One additive read (`db::space_trace_rows` + pure `assemble_post_traces`) returning `Vec<PostTrace>`, each **anchored to a post the tree already renders** (keeping `PostNode` untouched). Two anchors: a turn that produced an answer anchors on its **inference** (attribution via the turn's context assembly; earliest-inference-wins so replays don't double-render); a turn that produced **no post** (decline, cap, failure) anchors on the post it answered, resolved to the current generation — the audit value of a decline is that the non-event is visible where the answer would be. **An anchor is not an identity:** several turns routinely land on one post, so each `PostTrace` carries its own durable `id` (the inference, or the trace-chain root). A `decision` is threaded to the post it declines, so the decline checkpoint writes a `reference` edge to its chain root at `db::DECLINE_TRACE_ORDINAL` — turn identity as a real relation (keying on `(anchor, participant)` would merge repeat asks; found in review). `TraceEntry` is `Tool { name, arguments, result, request_id, … }` (result `None` = never executed, which the cap does deliberately) or `Declined { reason }`; `request_id` links to the Record. Pure read — commits nothing, emits nothing. Tests: `tests/chat_path.rs`, `tests/participants_orchestration.rs`, grouping rules unit-tested in `lib.rs`.

## Tool registry (`tools.rs`)

v1 tools are **harness-internal only** — a `Tool` implementation in-process (no external/MCP surface yet). A `ToolRegistry` (name → impl, last registration wins) is held on `Inner`, **empty by default**, mutated via `AppCore::register_tool`. Two load-bearing properties:

- **Empty is invisible:** `TurnPrep::request_body` omits `tools` entirely when the turn's snapshot is empty, so a registry-less install sends no `tools` field at all — one flip when a tool is first registered, byte-stable after (the stable-but-larger rule under Thread map; not a byte-identity obligation).
- **Names are the key:** an unknown name is a tool *result*, not a turn failure — a model mistake it can correct.

`prepare_turn` snapshots the registry once per turn. `EchoTool` ships for end-to-end exercise; nothing registers it in production.

**Navigation tools:** `list_branches`, `read_thread(handle, limit?, offset?)`, `read_post(handle)` — `pub(crate)` impls over the turn's `Arc<ThreadSnapshot>`. Read-only over a snapshot (stale-ok), so no DB handle or synchronization; a handle the snapshot doesn't know is answered honestly in the result. `read_thread` renders via `with_header` over `render_post_for_model` (the exact wire format and the exact reference rendering — one path each, so `read_thread`, `read_post` and the turn's own context cannot tell three stories about one post) and states window bounds rather than truncating silently. `read_post` is the one exception to snapshot-only: its `quote: N` argument carries a `Weak<Inner>` + the responding participant and re-checks membership per call (task 37), and reads the followed post's own reference edges so it renders through the same unit as everything else.

**Reserved names** (`tools::RESERVED_TOOL_NAMES` — the three navigation tools plus `remember` and `list_my_spaces`): `register_tool` returns `Err` for them. Without that, a consumer's `read_thread` would work on linear turns and be silently replaced by the built-in the moment a space branched. These are protocol surface: the map's system note promises the names, and each reads the turn's own snapshot, which a process-scoped registration structurally cannot supply. `ToolRegistry::register` keeps raw last-write-wins; the reservation lives at the one seam reaching the process registry.

**Attachment is per turn, in `prepare_turn`**, gated on the space **having branches** (so the field appears when the affordance does, and flips once) **and** the endpoint being able to carry a `tools` field. **No backend kind is consulted** — capability is **discovered, not assumed**, `eidola` included (llama.cpp 500s without `--jinja`, and with it still 500s on some models' template filters; a generic endpoint may refuse the field; a deployed enclave older than the server's tool wire types refuses it as an unknown member). The round loop **degrades on rejection** — if round 1 fails with `AppError::Server` and the turn attached the tools itself, it withdraws them, acquires a fresh hold, and retries once. The blocking transport returns *before* persisting the error inference in that case (an error generation would consume the turn's item identity and the retry couldn't write its answer); the rejected request row is still committed. An endpoint whose toolless retry **succeeds** is memoized in-process (`Inner::tool_incapable_models`) — recorded only on retry success (a round failing both ways was failing for another reason). **The memo's key is the `(backend_id, wire_model)` pair** (`ToolEndpoint`), because a backend is a host and not a capability: eidola's catalog and a llama.cpp install each serve many models, and one model's refusal must not disarm its siblings. The memo is an observation, not configuration: no column, re-probed after restart; per-model capability metadata is the durable successor (task 60). Only turn-attached tools are withdrawn; consumer registrations fail honestly.

**A response is classified by its status, never by whether its body parses.** The blocking transport requires JSON only of a **2xx** (a 2xx that is not a completion is a genuine protocol failure, and still fails as `AppError::Network` — after a refund recovery, since nothing downstream runs to settle that round's hold). A non-2xx body is an *error document* and is read leniently, because the shape that matters most is not JSON: the server's request type is `deny_unknown_fields`, so an unknown member fails in the `LoggedJson` extractor, and axum renders that `JsonRejection` as a **plain-text 422**. Deciding from the body would file exactly that response as `Network`, and the degrade keys on `Server` — so a server too old for a field the turn sent would fail every branched turn instead of retrying without it. The streaming transport already checked status first and never had the ordering. Both shapes are fixtures: `RejectTools` (llama.cpp's JSON 500) and `RejectToolsUnparseable` (the enclave's plain-text 422), the latter pinned on both transports.

**The degrade retry spends.** On the eidola backend the rejected attempt burns a hold, so before the retry the round settles it (no inline refund rides a rejection, so it recovers one through `/v1/credentials/refund`) and `begin_next_round` acquires a fresh, *smaller* hold — re-estimated over the array the retry will actually send, tool schemas withdrawn. `ChatResult::credits_charged` is the sum of the holds the turn took, the rejected one included. Pinned end to end by `a_rejected_tools_field_on_a_spending_backend_settles_both_holds` (`tests/chat_path.rs`): distinct credentials, both reaching `spent`, none left `spending`, and the wallet total unchanged.

**A hold is never abandoned to take another one.** `prep.spend` is the only in-memory handle to the materials that mint a hold's successor credential, so replacing it while unsettled leaves that credential `spending` and its face value locked out of the wallet until an explicit recovery. `begin_next_round` — the one place `spend` is replaced — therefore refuses to proceed past an unsettled hold, taking one last recovery attempt and otherwise ending the turn (`AppError::Credential`, joining budget and provisioning as that call's failure modes). The guard lives at the write rather than at each call site, so neither the tool loop nor the degrade retry nor a future third caller has to remember it; `TurnPrep::spend_settled` is what it reads. Test: `a_retry_will_not_take_a_hold_while_the_last_one_is_unsettled`.

## Decline checkpoint (`decline.rs`)

An orthogonal *quality* valve, not gating: by the time it fires the prefill is paid for (the cheap filter is `router.rs`). `DeclineTool` is an ordinary `Tool` (`decline`, optional `reason`); the checkpoint is one seam in both round loops, after the round's `tool_call` persists and **before** the round cap. When a round's calls include `decline` **and the registry actually holds it**, `Inner::decline_checkpoint` executes the round's tools as usual (honest trace), writes a **`decision` action** off the post the turn answers, carrying the reason as `text` plus a `reference` edge (`DECLINE_TRACE_ORDINAL`) naming its trace-chain root, and ends the turn with **no inference**: `response_action_id` is `None`, `declined` carries the `DeclineOutcome`. Emissions: `Space` + `Record` (+ `Wallet` when spent), never `SpaceIndex`. Nothing registers it by default (a model inventing the name gets the unknown-tool result). `get_space_tree` collapses `decision` out like traces; rendering "saw this, declined" is a GUI follow-up. Three layers keep a decline from being mistaken for a post: the result type, `plan_notifications` returning zero turns for non-posts, and the GUI turn runner dropping the declined turn's captured reasoning. Tests: `tests/participants_orchestration.rs` + a `tests/bus.rs` row.

## May-decline router (`router.rs`)

One cheap model call filtering the mechanical notify set, between planning and turn-driving. `plan_notifications` sends the triggering post's upstream slice (last 6 posts, clipped) plus one **candidate card** per planned participant (label, persona digest, policy) to a small model and keeps only the subset it names. Candidates are addressed by **1-based index**, not UUID (echo failure mode); the reply is strict `{"notify": [n, …]}` read by pure `parse_router_selection` (tolerant of surrounding fences/prose, strict about the object; empty list = valid "nobody responds").

- **Failure doctrine: degrade, never block.** Unset router model (**the default — off**), unreachable router, or unparseable output return the mechanical plan unchanged with a stderr warning: the failure mode is *extra* notifications, never lost ones. Non-selections are not persisted. Explicit asks bypass entirely; a `Paused` plan short-circuits before any call.
- **Settings:** `space.router_model` / `space_template.router_model` (copied at instantiation like `cascade_limit`), a qualified reference written via `set_space_router_model` (emits `Space`) / `set_template_router_model` (emits `Templates`) — deliberately their own setters. The per-space pair is read together by `space_settings` (the inspector's read: `SpaceSettings { cascade_limit, router_model }`, erroring on a space that does not exist), and `set_space_cascade_limit` (floor 1, emits `Space`) is its sibling write. Both validate the backend up front; `validate_router_model` exposes the check as a pure read for create-then-set flows.
- **The call is not a turn:** no actions, no request rows, no attestation records. It runs through the chore runner (`utility.rs`): engine-backed references are genuinely free; a remote `eidola` reference **bills a normal inference per triggering post** (spends and settles, `Change::Wallet` included) — settings surfaces must say so plainly.
- **No caller can forget it:** no public API returns an unrefined plan for driving.
- **The slice is rendered, not raw** (task 67): posts arrive as `ThreadSnapshot::post_body` — quoted passages attributed and spliced in at their markers — because the router picks *who answers* and a post whose meaning lives in what it quotes read as near-empty. `POST_MAX_BYTES` is therefore spent from **both ends** (`clip_middle`), so an unbounded passage cannot take the post's own routing cue with it. See the reference-rendering section above for the cost, the fallback, and why eliding the middle is the shared rule.
- GUI: both router pickers have landed — the Templates pane's and the **space inspector's** (default reads **Off**; the mandatory per-call cost copy inline for eidola refs, worded per surface), over the shared `participants::router_field`.
- Judgment-tier evals are explicitly out of CI (offline eval over a golden set, never `tests/`). Tests: `tests/participants_orchestration.rs` over the harness's `RouterBehavior`.

## Chore runner (`utility.rs`)

One cheap model call that is deliberately not a turn; extracted when the branch summarizer became `router.rs`'s second consumer. Two phases, and the split is the point: `resolve_utility_target` answers *where would this go* from the registry alone (no engine start, no network — broken references degrade before anything starts); `utility_completion` opens the route (engine lease/start, attesting or plain client, hold for remote), makes one non-streaming completion, settles the refund. Zero-spend for `local`/`llamacpp`/`openai`; spend-and-settle for `eidola` with the same body-read-failure discipline as the chat transports (a hold is never stranded in `spending`). Persists nothing. `clip` (char-boundary-safe truncation) lives here, shared by chores rendering conversation text.

## Branch summaries (`summaries.rs`)

LLM-written précis lines under thread-map entries — a progressive enhancement; everything can fail or be off and the map is exactly what it was. **Cache keyed on the branch tip** (newest of the branch's resolved current generations), so a summary regenerates when the branch grows and never otherwise; reading tips off resolved generations makes an edit anywhere in the branch move it. A stored summary renders even once the branch grew past it (a snapshot beside fresh structural counts).

**Storage is a versioned item:** an `action_type = 'checkpoint'` action, `intent = 'branch_summary'`, authored by `db::SYSTEM_PARTICIPANT_ID` (Eidola on its own behalf — attributing it to a human or agent would lie in the Record), text as its one block, and two `reference` edges: ordinal 1 → the branch root (its *item* is the stable identity), ordinal 2 → the tip it read. Ordinal 0 stays empty (not part of the thread). Regeneration supersedes within one item. `checkpoint` is not a post type, so every render/context/planning path collapses it for free — no schema change.

**Model:** v1 shares the space's `router_model` as its utility model; a remote one bills as it does for routing. Bounds are structural, not policy: lazy generation, the tip cache, a `MIN_BRANCH_POSTS` floor, at most one call per branch that actually grew — each with a *different* prompt, because an over-cap branch is sliced head + tail (elision stated) rather than oldest-N. Unset or unresolvable ⇒ structural lines only, silently. The slice's posts are rendered (`post_body`), not raw and not preview-elided (task 67): the summarizer reads the branch, and its output is **written down** and read for as long as the branch lives. That is also why the per-post budget is spent head + tail (`clip_middle`) exactly as the branch slice is — a quotation longer than `POST_MAX_BYTES` would otherwise carry off the author's own response to it, and the misleading summary would stay cached until the branch changes.

**Scheduling never touches a turn:** `spawn_branch_summaries` is fire-and-forget after every branch-moving write commits *and emits*, with per-space trailing debounce + a one-pass-at-a-time gate (cache re-read inside); a pass with nothing stale makes no request. Each committed summary emits `Change::Space`; a pass generating nothing emits nothing. Tests: `tests/branch_summaries.rs` (driven via the `test_refresh_branch_summaries` seam — the production trigger is debounced).

## Agent memory (`memory.rs`, task 35)

The second of three participant layers — charter (human-owned config), **memory** (agent-owned, self-revised, human-inspectable), experience (transcript + traces). Charter/memory separation is deliberate: the human's instructions stay authoritative, and each layer is more credible to a model than one blob.

- **A block is an item** (the branch-summary precedent): each revision is a generation (`action_type = 'memory'`, supersedes the tip) — append-only history, diffable trail, and a **structural** self-revision vs human-correction distinction (every generation records its author). Not a post type, so render/context/planning collapse it for free. Revisions may carry `reference` edges (ordinals `1..=N`) naming the posts learned from, with annotation — provenance a string-blob store cannot do.
- **Ownership vs scope (promotion-critical):** `memory_block` carries one **owner** (pinned by the same composite echo `action` uses), a scope *label* (`core` = loads wherever the owner goes; `space` = loads in its residence only), and a **residence** `space_id`. Scope is addressing, never co-ownership — what makes in-place promotion a memory no-op. Residence is decided once at creation: the space the agent stands in, except a `core` block a **global** writes resides in its notebook. Names are unique per owner.
- **Loading rule:** per turn, the responding participant's core blocks + blocks about the current space — nobody else's, ever — render at the **head**, inside the system message, after the charter and static notes (keeps the charter+notes prefix byte-stable; a memory edit invalidating that participant's cache is correct — CLAUDE.md semantics). Slow memory at the head, volatile thread map at the tail; all bytes ride `messages`, so `chargeable_prompt_tokens` covers them.
- **The tool seam is turn-scoped** (the navigation-tool precedent): `remember(block, text, scope?, sources?, annotation?)` binds to *this* turn's responding participant, residence space, and `ThreadSnapshot` — none of which the process registry's `Tool` trait can carry. Name reserved; constructed in `prepare_turn`.
- **Off by default:** the whole feature (loading read *and* tool) gates on `AppCore::set_memory_enabled` (process-scoped consumer opt-in, like `register_tool`) — an install that never enables it never reads, so it costs no query and no bytes. The opt-in is a consumer decision about the *feature*, not a byte-identity obligation (see Thread map). Past that opt-in `remember` attaches wherever the navigation tools do, on the same learned per-`(backend, wire_model)` capability (see Tool registry) — **no backend kind is excluded.** An endpoint that turns out to refuse a `tools` field has `remember` withdrawn with the rest by the degrade retry and keeps `MEMORY_NOTE`: such a turn still *reads* its memory and cannot revise it, which is a property of that endpoint, learned, and re-probed next restart — not of any backend.
- **Hygiene** is revision-shaped, plus guard rails — `MAX_MEMORY_BLOCKS` (8) per owner, `MAX_MEMORY_BLOCK_BYTES` (2000) per block — refused as *tool results* (correctable model mistakes), honest about the limit, decided before any write (zero trace). A committed block emits `Change::Space(residence)` — safe mid-loop because `memory` is not a post type.
- Inspection: `memory_blocks(participant_id)` (pure read; full revision trail with contents, author, provenance).
- Tests: `tests/agent_memory.rs`; the loading rule's SQL in `db.rs` (`participant_memory_loads_core_everywhere_and_space_blocks_only_at_home`). Memory *quality* is offline-eval material, never CI.

## Cross-space discovery (`discovery.rs`, task 36)

`list_my_spaces` — the space-level analog of `list_branches`. A turn's context is branch-scoped, so a promoted agent can't otherwise know its other conversations exist. **Bounded by membership:** reads `db::participant_spaces` and nothing else, takes no arguments (no id or filter could reach a non-member space; removal takes effect the moment the human removes it — the boundary is the query, not a check a caller could forget). Reports *what and where*, never contents, and says so in the result. Turn-scoped and reserved like `remember`. **Its gate is structural, deliberately not the memory opt-in:** attaches only when the responding participant is a `global` agent — which exists only because a human promoted one — so the tool and its note appear exactly when the capability does, flipping once at promotion. (Riding the memory opt-in was rejected both ways: it would blind a promoted agent until memory was enabled, and switch on unasked-for cross-space visibility when it was.) `GLOBAL_AGENT_NOTE` joins the system message on the same terms: flips once at promotion, byte-stable after. Renderer unit-tested in-module; round trip in `tests/global_agents.rs`.

## Local models (`local_models.rs`)

On-device inference via llama.cpp in server mode: a managed `llama-server` subprocess per loaded model, bound to `127.0.0.1` on an ephemeral port, speaking the same OpenAI-compatible HTTP — so the chat path treats a loaded local model as just another upstream.

**Routing is by backend kind, not model-id prefix:** `prepare_turn` resolves via `parse_model_ref`; engine-backed kinds (`local`, `llamacpp`) swap the attested client + credential spend for a plain loopback client with `TurnPrep.spend = None` — no charge, no ACT header, no refund machinery, no `Wallet` emissions, `credits_consumed = NULL`, provider `(<backend-id>, "inference")` — so local inference needs zero onboarding. `openai`-kind turns take the same no-spend path over HTTPS with the backend's key as `Bearer` (`TurnPrep` carries `backend_id`, recorded on request rows, and a `wire_model` distinct from the canonical qualified id, which actions record and `ChatResult` reports). Everything downstream (SSE parsing, context assembly, `persist_turn`, emission placement) is shared.

**Storage is the filesystem:** the managed `local` singleton owns `<data_dir>/models/` (one `.gguf` per model + optional `.meta.json` sidecar; downloads stream to `.part` and rename; a manually dropped `.gguf` is picked up on scan); each `llamacpp` backend scans its user-owned `models_dir` (load/unload only — download/delete refused). **Runtime state** (in-flight downloads, engine supervisors) lives in `LocalRuntime` on `Inner`, engines keyed by `(backend_id, slug)`; every transition emits `Change::LocalModels` (progress throttled ~2.5 Hz); consumers re-snapshot via `local_models_state()` (carries `external: Vec<ExternalEngineBackend>`). **Not every row in that snapshot is a file**: the managed store *synthesizes* a `LocalModelInfo` for an in-flight download (streaming to `.part`, so no `.gguf` exists yet) and for a standing failure that left nothing on disk, both only when the scan found no file for the slug. `LocalModelInfo::on_disk` is the discriminator — true exactly for the rows `scan_engine_dir` produced (so external backends' rows always are) — and status is *not* a substitute: a failure row is `Available`, the same status a scanned idle file carries. Any consumer reasoning about **file presence** rather than about what to show must read `on_disk`. **Selectable and installed are not visible** — the *listing* keeps both kinds of row, which is where the progress and the error are read; every surface that instead asserts a file joins on `on_disk`, and three review rounds swept the class to these four (each was wrong in the same way, and each has a regression):

1. **`backend_models`, the selectable surface** — filters on `on_disk` alone, because a picker offers files: a failed-download row read as `Available` was offered as a model and could only fail at load time (`a_failed_download_is_listed_but_never_selectable`, `tests/local_models.rs`). The GUI's `LocalModelsStore::selectable_models` / `external_selectable_models` take the identical test.
2. **The CLI's orphaned-engine flag** — a re-download of a deleted-out-of-band slug otherwise erased `— backing file missing` while a running engine still served the vanished file (`crates/eidola-cli/AGENTS.md` → `model`).
3. **The macOS status menu's `(file missing)` marker** — the same erasure in the menu bar; there the *naming* join stays permissive and only presence tightens (`crates/eidola-gui/AGENTS.md` → App lifecycle).
4. **The catalog's installed marker**, joined on `file_name` rather than id — CLI `catalog_installed` and Settings → Backends → Local, where "Installed" *replaces* the Download verb, so a failed download hid its own retry.

The remaining `state.models` joins are safe by construction and were checked: display-name lookups (`SpaceView::model_display`, `participants_view`) make no claim about a file, and joins keyed on `Loaded`/`Loading` status can only match rows the scan produced.

**Engines load on demand, managed as a memory pool.** A request triggers the load: `prepare_turn`'s engine arm leases a ready engine (`lease_engine` — LRU bump + in-flight counter; the `EngineLease` on `TurnPrep` releases on drop) or calls `load_local_model`, with one gate: a `llamacpp` backend with `auto_start = 0` refuses request-triggered loads before any spawn (typed `NotConfigured`); the managed `local` backend always auto-starts; explicit `load_local_model` ignores `auto_start`. `load_local_model` is idempotent — ready → return, warming → join that load, absent → load. Before spawning, the pure eviction planner (`plan_evictions`) makes room inside the **memory budget** (4/5 physical RAM; test-overridable) using estimated footprints (file size + 1 GiB overhead heuristic — estimates only decide evictions; a genuinely-too-big load fails at the engine honestly): LRU engines that are neither pinned, serving an in-flight turn, nor warming are unloaded until the model fits; if that can't free enough, the load is refused *without unloading anything*, naming what holds the memory. Planning + inserting the warming entry happen in **one critical section** (`reserve_engine`) so concurrent loads can't double-book; a `ReservationGuard` rolls back on error. **Pinning** (`set_local_model_pinned`) is runtime state — protection from automatic unloading only.

Engine lifecycle: spawn `llama-server -m <gguf> --port <free> --alias <selection-id> -c 8192 --jinja --no-webui -ngl 999` (alias = selectable id so chat bodies match verbatim), poll `/health` until ready (5-min budget, stderr tail captured into failures); a supervisor task owns the child — unload signals it, unexpected exit records + emits, `kill_on_drop` reaps on process death.

**`shutdown_engines` is the quit-path teardown** (the GUI's `on_app_quit` hook): synchronous, infallible, reading the **engine registry** — drains the map and signals every supervisor, touching no filesystem or database. It exists separately from looping `local_models_state` because that snapshot is reconstructed by *scanning* the model directories, so an engine whose backing file was renamed/deleted mid-session is invisible to it while its subprocess is alive — and on macOS `[NSApp terminate:]` ends in `exit()` (no `kill_on_drop`), which would orphan it to launchd. **`running_engines` is its read-only sibling** and exists for the same reason from the other direction: any surface that *reports* what is running must take **membership** from the registry, in both directions — the scan-based snapshot loses an engine the moment its backing file does (or its backend row is removed, or its directory goes unreadable) while the subprocess keeps its memory, and it equally *keeps* a stopped engine's row alive whenever a rescan fails and the previous snapshot is preserved. It is synchronous, infallible, ordered by the `<slug>@<backend>` id, and carries only what the registry itself knows — **no display name**, since that lives in the `.meta.json` sidecar beside the file that may be gone; a caller joins `LocalModelsState` on `RunningEngine::id` for a pretty name and falls back to the slug. (First consumer: the GUI status menu's engine readout, which had exactly this defect — see `crates/eidola-gui/AGENTS.md` → App lifecycle.) The drain also sets a one-way **shutdown latch** — inside the same `engines` lock the reservation takes, checked at both write points under that lock (`reserve_engine`, and again immediately before `command.spawn()`, since a reservation accepted a moment before the latch flipped can first-poll after the drain) — the authority read at the write point, never captured. A quit is also the one time nothing on this path emits: the GUI's bus bridge would panic ("Can't spawn on main thread after on_app_quit"), so **every** supervisor emission goes through one gate silent while the latch is set (gated on the latch, not the shutdown arm — an ordinary unload still emits). The latch also fixed a second swallow: the warming loop's `/health` probe was awaited outside its `select!`, so the shutdown oneshot wasn't polled for the probe's duration — and warming is exactly when `/health` hangs (socket accepted while a multi-GB model loads, no request timeout); the probe now races the signal. Regressions in `tests/local_models.rs` (`shutdown_reaches_an_engine_the_model_scan_cannot_see` and its read-only twin `running_engines_reports_an_engine_the_model_scan_cannot_see`) + in-module.

The curated catalog (`LOCAL_MODEL_CATALOG`) lists Google's five official Gemma 4 QAT Q4_0 GGUFs; `normalize_model_url` also accepts any direct `.gguf` URL or HF file page (`/blob/` → `/resolve/`). **Engine resolution is split by kind** (both halves pure, unit-tested): the `local` engine is the **bundled sidecar** — `resolve_local_engine` tries the `llama_server_path` config override, then `EIDOLA_LLAMA_SERVER` (set by the Linux GUI wrapper), then **one exe-relative rule on every platform: a `llama-server` sibling of the running executable** (CLI/Nix/dev builds, and the macOS `.app`, whose sidecar ships at `Contents/MacOS/llama-server` next to the main binary — so app-core knows nothing about `.app` internals; the layout is owned by `flake.nix` + `scripts/package-gui-app.sh`) — **no `$PATH` scan**, so a missing engine surfaces the honest "this build doesn't include the bundled engine" state; `llamacpp` backends use `resolve_external_engine` (explicit `engine_path`, else `$PATH` then Homebrew/system dirs). On macOS both resolvers reject a binary with no executable Mach-O slice (`usable_engine_binary` — the universal `.app` ships the arm64-only sidecar to Intel Macs, where mere existence must not advertise an engine that can only exec-fail). Engines are per-process; every on-disk model is selectable — the request loads the engine. Tests: `tests/local_models.rs` (wiremock downloads, credential-free chat rows, pin round-trip, eviction wiring against `/usr/bin/false`) plus in-module resolver tests — including `the_bundled_engine_rule_is_a_sibling_and_nothing_else`, which asserts the *absence* of any `Contents/Resources/bin` candidate so the retired bundle layout cannot quietly come back; the real subprocess lifecycle is exercised manually.

## Database (`db.rs`) and migrations

Embedded [Turso](https://crates.io/crates/turso) (pure-Rust libSQL) database at `~/Library/Application Support/eidola/eidola.db`. Three-layer schema (wallet, transport, semantic) in `schema/schema.sql`.

**One writer, loudly (`db::DbLock`):** turso is single-writer, and two processes on one file (open GUI + a CLI invocation) used to contend silently. `AppCore::build` takes an exclusive advisory lock (`flock` via `fs4`) on `<data_dir>/eidola.db.lock` **before** building anything; `Inner` holds it for the process lifetime; a second opener gets `AppError::DatabaseInUse` naming the holder's pid. **Keep it `flock`, not a pidfile-existence check:** the lock lives on the open file description, so the kernel releases it however the process exits — a crash cannot wedge it; a leftover lockfile means nothing (regression-tested). The file contents are just the holder's pid (unreadable stamp still refuses, `pid: None`). Keyed on the **data** dir, so disjoint dirs never contend (what keeps tempdir tests parallel-safe). Two `AppCore`s in one process are refused like two processes; restart-modeling tests drop the first core first. The CLI parses argv before building the core; the GUI aborts with the honest message (a real dialog is a follow-up). Tests: `tests/db_lock.rs`.

**Schema management — fresh-start, no migrations:** `schema.sql` is the whole baseline (pre-release history collapsed; no real users). Fresh installs (`user_version == 0`) apply it via `execute_batch` and set `LATEST_VERSION`; a database already at `LATEST_VERSION` just re-runs idempotent seeds; **any other version is refused** with an honest "delete your dev database" error. Changing the schema: (1) edit `schema.sql` to the new desired state — this IS the change; (2) bump `LATEST_VERSION` in `db.rs`; (3) `cargo test -p eidola-app-core` (`migrations_match_schema` stays trivially green). **`LATEST_VERSION` is 7.** Limitation: no `ALTER TABLE ALTER COLUMN`; a `NOT NULL` column still needs a `DEFAULT`.

**FK enforcement is real:** turso defaults `foreign_keys` **OFF** (every FK is unenforced documentation until enabled, per connection), so `db::connect()` sets `PRAGMA foreign_keys = ON` on every connection (`Inner::db_conn` and `open()` route through it), plus `PRAGMA busy_timeout` (concurrent per-turn writes block-and-retry instead of erroring). `turso_enforcement_smoke` pins the observed behavior: single-column FKs, composite FKs, MATCH-SIMPLE NULL-skip, CHECKs, and **`ON UPDATE CASCADE` on a composite FK** (task 36's in-place promotion rests on it — proven before anything was built on it). When adding tables, respect insertion/seed order.

**The `space` row carries `touched_at`** — the nullable pristineness stamp (see Disposing of untouched spaces). NULL means nothing has ever changed this space's configuration footprint since it was instantiated; actions deliberately do not write it.

**Scope-owned participant schema:** config columns (`kind`/`label`/`model_ref`/`system_prompt`/`notify_policy`, `role`, `removed_at`) live ONLY on `participant` — drift is impossible rather than managed. Reference tables carry a pinned `participant_scope = 'global'` CHECK echo + composite FK `(participant_id, participant_scope) → participant(id, scope)`, making "may only reference a global" declarative. `action` carries the same pinned echo (`IN ('global','space')`), so template-owned authorship is unrepresentable. `space` has `cascade_limit` (default 4), `router_model` (NULL = router off), and nullable `notebook_participant_id` (partial-unique — one notebook per agent; chosen over a `kind` column because consumers need *whose*: `list_spaces` excludes notebooks unconditionally, `notebook_space_for` opens one). `space_capability` (`(space_id, name)` PK + JSON `config`) is the sub-space attenuation snapshot — written only by the spawn door, immutable after, empty in practice today. `space_template` is a soft-remove registry. Schema integrity: an item's tip is provably unique (`idx_one_successor_per_action` + `idx_one_root_per_item`).

**The scope echo is never carried by a caller.** A turn spans HTTP round trips, so a scope captured at `prepare_turn` time can go stale — a promotion landing mid-flight made the next `insert_action` fail the composite FK, losing the response (found in review, reproduced, fixed). `insert_action` and `insert_memory_block` **derive the echo inside their own single statement** (`(SELECT scope FROM participant WHERE id = ?)`), and `ActionEntry` / `NewMemoryBlock` have no scope field at all: turso is single-writer, so nothing can interleave within the statement, and with nothing captured there is no read-then-write window. The column is `NOT NULL`, so an unknown participant fails loudly rather than writing a NULL echo MATCH SIMPLE would skip. Pinned by `a_scope_echo_can_be_derived_inside_the_insert`. Apply this idiom (derive authority at the write point) to any future echo column.

**Seeds:** idempotent at every open — the singleton backends, the **global** human `User` (`HUMAN_PARTICIPANT_ID`), `SYSTEM_PARTICIPANT_ID` ("Eidola", `kind='system'`, never referenced into any space, member nowhere), and the "Default" template (`config::DEFAULT_TEMPLATE_ID`) owning one template-scoped agent. **A seed makes a fresh database usable and never re-asserts state over a user's later edits** (task 41): `INSERT OR IGNORE` on a well-known id only distinguishes "never existed" from "user removed it" for rows nothing can hard-delete — false for the Default template's owned agent, which `update_template_tx` replaces wholesale with fresh ids. The seeded agent is therefore written **only in the same call that creates the template row** (the `INSERT OR IGNORE` rows-changed count is the creation signal): after first open, no seed path can touch a template's participants — re-injection is unrepresentable rather than guarded. **The template + agent pair is one transaction** (`ensure_default_template_tx`): `conn.execute` autocommits, so a process exit between the writes would commit the template row alone and consume the creation signal, permanently skipping the agent — and the post-crash state is indistinguishable from a deliberately emptied template, so rollback makes it unrepresentable instead of detected. Nothing ever backfills an existing database. Regressions in-module + `tests/template_seed.rs`.

**Projections** are row copies switching owner columns: `instantiate_template` (template-owned → fresh space-owned rows; references → space references with overrides; ensures the human) and `template_from_space` (the reverse). Replacing a template's owned agents runs in one transaction (`update_template_tx` — `BEGIN … COMMIT`, `ROLLBACK` on error) so concurrent instantiation never observes a partial set.

**Doctrine:** forensic Record queries never resolve mutable participant config (they read model/credits from `action`/`request` rows); "don't add a removed global to a space" is an app-layer typed error. Notable reads referenced elsewhere: `agent_cascade_depth`, `action_author`, `participant_spaces`, `is_space_member`, `action_space_and_type`, `referenced_post` (post types + `text` blocks only), `current_branch_summaries`, `participant_memory`, `memory_blocks_owned`, `memory_revisions`, `assembly_trace_blocks`, `post_authors`, `space_trace_rows`, `raw_space_actions` (the unfiltered test read). `ReferenceEdgeRow`/`AntecedentEdgeRow` carry the antecedent's action type + block type so *readers* apply the quotable rule without queries dropping rows.

## Errors (`error.rs`)

`AppError` enum; request error classification (attestation vs network vs server); typed variants UIs route on (never strings):

- `NoAccount`, `InsufficientBalance { available, required }`, `ProvisioningTimeout { message }` — onboarding/funding.
- `ToolLoop { message }` — the bounded tool loop couldn't finish honestly (round cap with the model still asking, or structurally unusable `tool_calls`); everything that happened is committed first.
- `DatabaseInUse { pid, message }` — another process holds the DB lock (`pid` best-effort).
- `NotAParticipant { participant_id, action_id }` — the cross-space ACL; non-leaking by construction (names only what the caller supplied).
- `SpaceArchived { space_id }` — a turn was asked for in an archived space. Archival closes a conversation, so it takes no new turns; it does not abort one already streaming, and it hides, deletes and forbids nothing else.
- `NotJoined { space_id, message }` — the human wrote into an agent-spawned sub-space they have not joined. Reading one is unconditional and writing into one is membership; this is where the two part. Carries the space id the caller already named, so the surface can offer the join that would satisfy it.
- `WrongPostKind { message }` — an edit aimed at something that is not the human's own input, or a regeneration aimed at something that is not an agent's inferred answer. Typed so a surface can withhold the affordance rather than discover it by writing.
- `SpawnRefused { refusal }` — a sub-space spawn turned down by a guard, the attenuation gate, or an ineligible participant. The payload is a typed `SpawnRefusal` whose `Display` is the model-facing sentence, so the tool exposing the door renders a correctable result instead of failing a turn. Nothing was written.

Chat errors are returned **as themselves**: a turn's failures are the typed variants above, unwrapped, so every consumer routes on the variant it sees. The `ChatFailed { space_id }` wrapper that used to carry a persisted space id back to the caller is gone with the client state that read it — the GUI creates a space when its window opens, so it never has to learn an id from a failure (see `crates/eidola-gui/AGENTS.md`). A caller that lets `post`/`chat` create the space for it (the CLI's one-shot `chat`) and needs the id after a failure reads `list_spaces`.

## Account reads (`lib.rs`)

`account_show` / `account_prices` / `account_balances` / `account_checkout` / `account_subscription` are thin authenticated reads over the server's linked surface. **They persist nothing and emit no `Change`**: there is no durable commit to announce, and what they carry is the payment processor's state rather than ours — so nothing on the bus can invalidate them, and the consequence lands on the consumer: a surface showing one asks for it when the reader arrives, and offers a way to ask again (the GUI's Account pane does both — see `crates/eidola-gui/AGENTS.md`).

`account_subscription` answers a three-value `SubscriptionState` — `NoCustomer` (never transacted), `Inactive` (a payment relationship, nothing in force), `Active` — because those are three different surfaces, not two. "In force" is the *server's* definition (Stripe `active` / `trialing` / `past_due`), and it is the same predicate checkout refuses to double-subscribe over, so the app can never be told "no subscription" by one call and "already subscribed" by the next. A state string this version does not recognize is refused rather than guessed at: both guesses are harmful, and client and server ship together. It carries no portal link: minting one is `account_portal()` over its own endpoint, called at the moment the reader opens it, because the session is short-lived and minting it is a write the standing read has no reason to pay for.

## Automatic credential provisioning

Turns resolve their spend credential via `Inner::ensure_spendable_credential`, called under `spend_gate`: an active credential covering the estimated charge is used directly; otherwise app-core auto-allocates `min(available, max(DEFAULT_ALLOCATION_CREDITS, charge))` from the account balance transparently. `DEFAULT_ALLOCATION_CREDITS = 1_000_000` (credits are micro-USD; ≈ $1.00 ≈ 30 worst-case per-turn holds; sizing rationale in the doc comment). As a bounded retry loop under the gate, a concurrent turn finding balance committed waits for an in-flight refund rather than double-booking (see the ACT provisioning queue above for the exact wait conditions). Failures are typed: `NoAccount` / `InsufficientBalance` / `ProvisioningTimeout`. The explicit `account_allocate` path is unchanged; GUI and CLI get silent provisioning for free.

## Chat-path test harness (`tests/chat_harness/`)

The full `chat`/`chat_stream` HTTP paths are exercised by `tests/chat_path.rs` on an in-process mock upstream. The harness injects a plain-HTTP `reqwest::Client` via the `#[doc(hidden)]` seam `AppCore::with_test_http_client` (bypassing per-handshake attestation) and serves a raw tokio HTTP/1.1 upstream that mints *cryptographically real* anonymous credentials using the same `anonymous-credit-tokens` primitives as the server — issued credentials actually decode and spend.

Every test seam — `with_test_http_client`, the `Inner::http_override` field and each branch reading it, and the `test_*` methods below — is compiled only under the non-default `test-support` cargo feature, enabled for this crate's own test builds via the `[dev-dependencies]` self-reference in `Cargo.toml`. Release builds of downstream crates (cli, GUI) therefore contain no attestation-bypass path at all; the feature must never appear in a `[dependencies]` entry. A downstream crate's *tests* may enable it via its own `[dev-dependencies]` on `eidola-app-core` — never its `[dependencies]`.

- Per-test `ChatBehavior` selects blocking / streaming / mimicked-header (whole, and split across deltas) / non-2xx / mid-SSE-abort / connection-drop, plus tool arms: `ToolRoundsBlocking(n)` / `ToolRoundsStreaming(n)` (the SSE arm splits one call across four deltas so the per-index accumulator is genuinely exercised) / `ToolRoundsStreamingWithExtras` / `ToolCallMalformed` / `ToolCallBadArguments` / `ToolCallsNotAnArray(+Streaming)` / `ToolCallsNull` / `ToolScript` (interior-mutable — navigation-tool arguments are handles that only exist once the fixture space is built) / `RejectTools` (500s any request carrying `tools` with llama.cpp's verified error shape) / `DeclineBlocking` / `DeclineStreaming`.
- `blocking_and_streaming_dispatch_use_the_shared_request_body` compares ordinary and tool-follow-up bodies from both real transports with `eidola_common::chat_completion_request_body`, asserts their independently expected stream modes, then invokes the server's feature-gated test-only deserialization bridge on the same bodies. This catches both post-builder outer fields and nested message drift while the server's `types.rs` regression separately covers the shared-builder matrix.
