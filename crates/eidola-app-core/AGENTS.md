# eidola-app-core — Agent Development Guide

The GUI app and CLI share this crate as a normal Rust library — no FFI layer. All business logic lives here: config management, the local database, HTTP client construction, account operations, wallet/credential management, chat inference, participants, agent memory, and local models. Consumers construct an `AppCore` and call its methods directly.

Ground rules:

- **`AppCore::new` is fallible** (`Result<AppCore, AppError>`): it takes the process-lifetime exclusive advisory lock on the local database before building anything else, so a second opener is refused with `AppError::DatabaseInUse` (see Local Database below).
- **State & async doctrine** for consumers (domain stores, the invalidation bus, task ownership, atomicity rules) is governed by `crates/eidola-gui/STATE.md`. All state-touching code follows it; do not invent parallel patterns.
- **Any change to the chat path must extend the test harness** (see Chat-path test harness at the end): a new exit point or emission gets a `tests/chat_path.rs` / `tests/participants_orchestration.rs` test and a row in `tests/bus.rs`'s exit-point table.

## Change bus (`changes.rs`)

`Change` enum with eleven domain variants: `Config`, `Account`, `Wallet`, `SpaceIndex`, `Space(SpaceId)`, `Record`, `UpdateState`, `LocalModels`, `Backends`, `Participants`, `Templates`. `Participants` (a space's membership/config changed) and `Templates` (the template registry changed) are deliberately split because they map to two GUI surfaces — the STATE.md 1:1 variant↔store rule. `ChangeSource` is the narrow seam for a future Turso-CDC implementation; `BroadcastSource` is the v1 in-process `tokio::sync::broadcast` (capacity 256). `AppCore::subscribe_changes()` hands out independent receivers; a lagged receiver gets `RecvError::Lagged` and should refresh everything.

**A subscriber receives a `ChangeEvent`: the `Change`, a `ChangeOrigin` saying whether anyone is waiting on the write, and a `seq` saying where it falls in this process's one stream of durable writes.** A consumer that owns an operation's truth while it runs defers invalidations for the surface it is busy writing to, because its own exit re-read covers *some* of them — and which ones is what `seq` answers. `Unattended` is work app-core drives on its own (the branch summarizer, the sub-space turn driver), where no call is outstanding and nothing else will read the write in, so a consumer must defer it whatever else is true. **`Caller` says attendance, and attendance was mistaken for ownership**: it means *a* call was outstanding, never that the call was the reading consumer's — so a caller-stamped write from somewhere else (another window archiving the conversation this one is streaming in) was dropped as though some read of the reader's covered it, and nothing did. Ownership was only ever a proxy for the real question, and a wrong one in both directions: another consumer's write that committed before this consumer's read *is* covered, and this consumer's own write landing during that read is not. **`seq` answers coverage exactly.** It is assigned at emission, which follows the commit, so a consumer that samples `ChangeSource::current_seq` immediately before a read may claim every event numbered below it: that write was durable when the read began. Anything at or above may have landed mid-read and is re-read — the conservative direction, and the same answer for an event that merely raced the sample. The GUI's conversation entity is the worked example (`crates/eidola-gui/AGENTS.md`): it defers every signal while busy and discharges the decidable ones by comparison, so an own write still costs no extra read. **The origin is ambient, not an argument**: `changes::with_origin` scopes a future and `BroadcastSource::emit` stamps whatever is in force, so none of the ~30 emission sites changed and no future write inside an unattended chore can be mis-stamped by omission. Work moved onto a *new* task inside a scope starts outside it and falls back to `Caller` — the safe direction, since a wrong `Unattended` costs one redundant re-read while a wrong `Caller` is a lost invalidation. The `Change` enum itself is untouched; only the delivery envelope grew.

Emission doctrine:

- Every durable commit emits **after** the write succeeds. Pure errors with no durable side effects never emit.
- `chat`/`chat_stream` **post first**, unconditionally: the user's turn (and, for a space-less call, the space itself) is committed before any credential is acquired, so a funding failure leaves the saved thought rather than swallowing it. Its `Change::Space(id)` + `Change::SpaceIndex` are emitted at that commit like any other.
- Once a space is persisted, partial-failure paths emit on every explicit error exit, mirroring the success path (`Change::Wallet` as soon as a credential enters `spending`; `Change::Space(id)` + `Change::SpaceIndex` when a new/auto-titled space committed a user turn; `Change::Record` where a request row committed). Plain `?` on intervening local-DB inserts stays unemitted (internal-consistency failures).
- The full exit-point → emissions table lives in `tests/bus.rs`'s doc module. Keep it current.

## Backend registry (`backends.rs`)

The `backend` DB table holds configured inference destinations — where an ask can be routed. Four kinds:

- `eidola` — the confidential service (singleton). The row owns the whole connection + trust bundle: `base_url`, `trusted_measurements` (JSON overrides), `hardware_root_ca` / `hardware_intermediate_ca` (PEM ARK/ASK overrides) — each NULL = the embedded trust-root pin.
- `local` — Eidola-managed on-device models (singleton).
- `openai` — any user-configured OpenAI-compatible server (base_url + optional api_key).
- `llamacpp` — a user-owned llama.cpp install: Eidola scans its `models_dir` and starts/stops engines but never downloads/deletes files. Two extra columns, refused on other kinds: `engine_path` (explicit `llama-server` path; `None` = discover) and `auto_start` (default `1`; when `0` a request may not start an engine on demand — it must be pre-loaded explicitly).

Singletons are enforced by a partial unique index on `kind` and seeded idempotently at every DB open (`ensure_default_backends`); they can be **disabled** but not removed — disabling `eidola` is exactly the "no account, on-device only" configuration. External backends soft-remove (`removed_at`) so the forensic `request.backend_id` reference stays resolvable forever; re-adding the same id revives the row.

**Model references:** one rule uniformly — `<model>@<backend-id>` (split at the last `@`; ids validated to `[a-z0-9-]{1,32}`, so Ollama `name:tag` and HF `org/model` ids survive), with a single sugar: `eidola`, being the default backend, may be written bare, and `qualified_model_id` keeps the bare form canonical. Every other backend's models are spelled qualified, the local singleton included (`<slug>@local`). `parse_model_ref` / `qualified_model_id` are the unit-tested pair.

Because "OpenAI-compatible" does not guarantee `GET /v1/models` (Azure, scoped gateway keys, partial proxy listings), each backend carries nullable `model_overrides` (a pinned JSON list replacing the fetch); `backend_models(id)` resolves per kind — eidola → the attested catalog, openai → overrides-or-listing, local/llamacpp → the loaded engines.

`update_backend` does per-kind field validation: the `eidola` row accepts only its connection + trust bundle (each clearable back to NULL = pin) and refuses external fields; `local` refuses everything (enable/disable only); `openai`/`llamacpp` accept their own fields but never the trust bundle. The eidola-trust setters (`set_base_url` / `clear_base_url_override` / `set_hardware_root_ca` / `set_hardware_intermediate_ca` / `trust_measurement` / `untrust_measurement` / `clear_trusted_measurements`) are thin wrappers over `update_backend` on the eidola row. **Every member of the bundle has an unconditional clear-to-pin verb**, `trusted_measurements` included: reverting by key (`untrust_measurement`) leaves the column non-NULL, and a non-NULL list that omits the pinned measurement rejects the real enclave — so a caller reverting the bundle would have had to know every key it ever trusted. All CRUD emits `Change::Backends` (not `Change::Config`). Tests: `tests/backends.rs`.

## Spaces, posts, and edits (`lib.rs`)

`AppCore` holds all high-level operations and DTO record types (`ConfigState`, `ChatResult`, `PostResult`, `PriceInfo`, `SpaceInfo`, …).

- `list_spaces(include_archived)` returns title + first-message snippet + last-activity + message-count for the GUI's Library. `chat`/`chat_stream`/`post` auto-title an untitled space on its first exchange from the first line of the user's prompt (local heuristic, no model call).
- **`create_space(title)` / `create_space_with_id(space_id, title)`** instantiate the default template into a new empty space (the same door `post` takes for a space-less save) and emit `Change::SpaceIndex`. The second exists for a client that must **name the space before the row exists**: `new_space_id()` (a free function — minting an id is not a database operation) hands out the UUIDv7, so the GUI opens a ⌘N window addressed by a real id on the frame the keystroke lands and commits the row behind it.
- **`rename_space` decides the space's existence at its own write**: `db::update_space_title` answers whether a row took the title, and zero is the refusal. A space can stop existing between a read and the statement that follows it — an untouched one is disposed of when its last window closes — so a rename that reported success for a title no row took would leave the caller's optimistic edit standing over a database that never agreed to it. The doors that have no rows-affected to read (`add_space_participant`, `add_global_participant`, `grant_space_membership`) are refused by the foreign key and then *named* by `Inner::name_missing_space`, a read that only explains a write which already failed. Tests: `db::tests::a_write_into_a_space_that_has_just_gone_refuses_rather_than_reporting_success`, `every_configuration_door_refuses_a_space_that_is_gone`, `a_refusal_names_the_missing_space_rather_than_its_constraint`.
- **`discard_if_pristine(space_id) -> bool` disposes of a space nothing was ever done with** — see Disposing of untouched spaces below. The app's one real delete.
- **`post(space_id, prompt)` is the save side of the save-vs-request split:** persists a `user_input` action (fresh gen-0 item) with no credential, no account, no HTTP — creating the space if new, auto-titling, linking a `reply` antecedent edge to the prior tail — and emits `Change::Space(id)` (+ `Change::SpaceIndex` for new/auto-title). Tested in `tests/bus.rs` (no HTTP). **Its writes are one transaction** (`db::post_tx`), because a post is one thing: written as separate autocommitted statements the action row landed first and the words, the thread position and the quotations followed, so for as long as that took the post existed and said nothing — a state every reader keyed on the action could see, and one of them *acts* on it (the sub-space driver's refill takes posts by commit order, so it could plan and bill a turn against an empty post, and by the time the writer's own change event armed the room again the driven reply might have settled it). It is the cure `instantiate_template` took for the same class of defect one table over. Nothing on this path spends or calls out, which is what makes the writes adjacent enough to wrap; the validations stay in front of the transaction, where a refusal belongs, so a refused post still writes nothing and now cannot half-write either. The space's own instantiation stays its own transaction ahead of it (a transaction cannot nest, and what a failure between them leaves is a pristine space the reaper takes). **The rule covers every multi-statement action writer**: `edit_post` takes it through `db::edit_post_tx` — the sharper case, because an edit's new row *supersedes* the tip the moment it lands, so a piecewise edit left the item's **current** generation wordless — and the turn's persists (`TurnPrep::persist_turn`, the tool-round pair, the decline's decision) each wrap their rows in the same `BEGIN IMMEDIATE` on the turn's own connection. The refill can therefore never observe a half-written generation of any post kind (the brief's spawn transaction already guaranteed the third), and no crash leaves an action without the edges and blocks that explain it. Tests: `db::tests::a_post_is_written_whole_or_not_at_all`, `db::tests::an_edit_lands_whole_or_not_at_all`.
- **`post` refuses an agent-spawned sub-space the human has not joined** (`AppError::NotJoined`, zero-trace, inherited by `chat`/`chat_stream`) — see Agent-spawned sub-spaces; every other space is unchanged, notebooks included.
- **`edit_post(action_id, new_prompt)`:** appends a new `user_input` generation of the action's item (append-only — supersedes the tip, replicates its `reply` edge, prior generation preserved), so `item_current` resolves to the edit; emits `Space` + `SpaceIndex`.
- **`edit_post` and `regenerate` each require the kind of tip they produce** (`Inner::require_post_kind` → `AppError::WrongPostKind`): an edit needs a `user_input`, a regeneration an `inference`. Aimed at anything else they do not amend a post, they replace it with a different kind of thing — under the original author's byline for every prior generation, and for a regeneration at the cost of a billed turn written without seeing what it replaces.
- `list_spaces`/`first_user_text` count and snippet **current generations of post-bearing types only** (a tip filter plus `POST_ACTION_TYPES_SQL`), so editing replaces in the default view without inflating `message_count`, and traces/decisions/summaries never move a space's Library signals.
- **Reply targeting:** `post`/`chat`/`chat_stream` link to the space tail by default; `post_reply` and `chat_stream_reply` take an explicit `reply_to` so a reply to a non-tail post **branches** the thread there (additive signatures — the originals are unchanged).

**`get_space_tree(space_id)` is the threaded-post render DTO:** resolves each item to its current generation, keeps only post-bearing types (`user_input`/`inference`), and flattens the `reply` DAG into a `Vec<PostNode>` of render rows (so `list()` virtualization survives). The flattener (`build_post_tree`, pure + unit-tested) encodes the spine-vs-branch rule: the spine follows the first (chronological) reply at the same `depth`; later replies become indented branches; regenerations are generations (resolved to the tip), never branches. **Reply threading follows item identity:** each reply edge resolves to the current tip of its antecedent's item, so a reply to a since-edited post threads under the edit; render order sorts by the item's *origin* (first generation), never the tip's `created_at`. The raw antecedent action id is preserved on the edge (causality is action ids; intended logical flow is item ids). Regression: `edit_post_keeps_tree_position_and_rethreads_replies` in `tests/bus.rs`. `get_space_messages` remains as the flat whole-space convenience view (tests + external callers) — turns don't send it upstream.

### Disposing of untouched spaces

A space is created when its window opens, so an abandoned new window — and every launch that opens a blank one — would leave a durable empty conversation in the Library forever. Two doors reap them, under one law: **reap only what is provably pristine; when unsure, keep.** A wrongly-kept orphan costs a Library row; a wrongly-reaped space costs someone's work, so every mechanism below is arranged so the safe error is the one a mistake makes.

**Pristine is two legs**, both asked inside the deleting transaction: no `action` row in the space (every post, answer, trace, decision, memory revision and branch summary is its own witness, which is why the action write path carries no stamp), and `space.touched_at IS NULL` — nothing has ever changed the space's **configuration footprint**: its own row (title, cascade limit, router, archival), its `space_participant` rows, or the `participant` rows it owns. So a space with participants configured and zero posts is **kept** — the reader invested work. **Notebooks are excluded outright** (`notebook_participant_id IS NOT NULL`), on top of being born stamped: a notebook exists only for its agent and is the residence of that agent's `core` memory. An **agent-spawned sub-space** is kept by the first leg instead (its brief commits in the spawning transaction) and is born stamped besides — see Agent-spawned sub-spaces for the whole interaction, including why the predicate's `parent_space_id` clause over-protects a parent rather than under-protecting it.

**The stamp is written by the db-layer write functions themselves**, so the enumeration lives where the writes live rather than in a caller's memory — `touch_space` / `touch_space_of_participant` (the latter deriving the space inside its own statement, the module's derive-authority-at-the-write idiom), folded into the statement wherever one already targets the `space` row. Two rules make it honest:

- **Stamp no later than the write it describes** — in the same statement where possible, inside the same transaction where there is one, otherwise immediately *before* the write. turso autocommits each statement, so stamping afterwards leaves a window in which an edit is durable and its space still reads as untouched: a disposal interleaving there takes the space and the edit together, and the stamp that follows updates nothing. Stamping first can only over-mark (a refused write leaves a space nothing changed looking touched), and that costs a Library row. **The order is pinned, not just documented**: `a_stamp_is_written_before_the_statements_it_covers` fails on any db-layer function that runs a statement before it calls `touch_space*`, and `db::tests::a_failed_participant_insert_still_marks_its_space` is the behavioral end of it — a refused insert leaves its space marked, which is observable exactly when the stamp precedes the statement.
- **Instantiation is a birth, not a change.** `instantiate_template` writes `touched_at` **last, inside its own transaction**, resetting whatever its copies stamped. The one thing it carries that is not birth is a caller-supplied `title` — a human saying what this conversation is for — so a titled creation is born stamped and an untitled one is not. Both GUI creation doors (⌘N and New Space from Template) pass `None`, which is what makes the rule uniform across them; the CLI's titled `create_space` is kept.

**The primitive** is `AppCore::discard_if_pristine(space_id) -> bool` → `db::discard_space_if_pristine`: `BEGIN IMMEDIATE`, re-ask the whole predicate (never trusting the caller's earlier reading — that is what closes the check-then-delete window), then delete the space's `space_participant` rows, the `participant` rows it **owns**, and the `space` row. **Nothing shared is reachable from there**, and the graph is stated at the function: the inbound edges of `space(id)` are `space.parent_space_id`, `participant.owner_space_id`, `space_participant.space_id`, `action.space_id` and `memory_block.space_id` — the last two empty by the predicate, the first checked explicitly, the middle two what this deletes; the inbound edges of a space-owned `participant` are `action` and `memory_block` (both checked), since the two reference tables are CHECK-pinned to globals and `space.notebook_participant_id` names only a global. FK enforcement is on for every connection, so anything that reasoning missed aborts the transaction and the space is kept. Emits `Change::SpaceIndex`, and only when it deleted — no `Participants` (the roster belonged to a space that no longer exists) and no `Space(id)` (there is no space to announce).

**Two triggers.** The GUI calls the primitive when the last window on a space closes (`crates/eidola-gui/AGENTS.md`). The **startup sweep** (`Inner::sweep_pristine_spaces`) applies it to every pristine space **inside `Inner::db_conn`'s `OnceCell` initializer** — the local database opens lazily, so that is the earliest moment in the process that can touch it, and every read in this process is still waiting behind the initializer when it runs. That placement *is* the liveness argument: the exclusive database lock means no other Eidola holds the file, and the space a ⌘N is about cannot exist yet, because creating it is itself a call that has to get past this point first. A failed sweep is warned about and swallowed — reaping is housekeeping, and refusing to open the database would cost the reader everything.

**The sweep test is load-bearing, and there are two of them** (`tests/reap_pristine.rs`). `every_door_that_changes_a_space_stops_it_being_reaped` is one parameterized test over the `AppCore` doors (post, edit, title, archive, cascade, router, roster add/edit/override/remove, membership grant, promotion), each asserting its space is no longer reapable — so a door added without stamping fails on the row that names it. `the_stamp_ledger_covers_every_space_write` is the completeness half: it scans `db.rs` for statements against `space` / `space_participant` / `participant` (including any whose table name is interpolated, which cannot be decided lexically and is therefore declared) and fails on one inside a function `STAMP_LEDGER` does not account for. The ledger pins *coverage*; `a_stamp_is_written_before_the_statements_it_covers` pins the *order*, which is the half that decides whether a mark is worth anything. **Both scans attribute a statement to the function it sits in by matching declaration prefixes, so that list has to hold every form a declaration takes** — `pub(crate)` was missing, and a write inside a `pub(crate) fn` was silently credited to the function above it, which is a ledger entry that proves nothing about the write it names. Add a form to those lists whenever one appears in `db.rs`. Beside them: the footprint delete, the shared library surviving it, the configured-but-unposted case, the titled-vs-untitled creation rule, notebooks, the write-lands-first race, and both sweep arms. Test seams: `test_space_footprint` (raw row counts — every ordinary read is keyed on the space and answers "empty" once the row is gone, which is exactly the difference a delete has to be held to) and `test_space_is_pristine`.

## Turns (`lib.rs`: `run_turn`, `prepare_turn`, `persist_turn`)

**`run_turn(space_id, model, target_action_id, mode, budget)` is the request side:** provisions a credential, assembles the turn's upstream thread as context, calls the model, and persists the inference + request rows + refund. `prepare_turn`'s first read of the space refuses a missing **or archived** one before any of that (see Archival stops new work, under Participants v1).

- `get_upstream_context` walks the target's reply ancestry, each hop resolved to the antecedent item's current tip (an edited upstream post contributes its latest text). `Reply` walks from the post being answered *inclusive* (whole conversation on a linear thread; exactly the target's branch on a branched space — sibling branches never leak). `Revise` (regenerate) walks from the generation being replaced *exclusive* (the model never sees its own prior output or anything downstream).
- `chat` = `post` + `run_turn(Reply)` (post-first: a funding failure leaves the saved post; onboarding gates at *request* time). `chat_stream` = `post` + `run_turn_stream(Reply)` — the streaming twin, same contracts, differing only in SSE transport and refund-via-recovery-endpoint.
- **Regeneration has two transports and one contract.** `regenerate(action_id, model)` = `run_turn(tip, Revise)` and `regenerate_stream(action_id, model, sender)` = `run_turn_stream(tip, Revise)`; both go through `Inner::begin_regeneration`, which resolves the target item, applies the space's gate (the human's verb — `require_human_joined`), takes the in-flight claim, and then reads the item's current tip and gates on its kind (an agent's *inferred* answer — `require_post_kind`). Neither the target resolution nor the `Revise` context rule is written twice. A surface with a reader in front of it takes the streaming door: a reasoning model can run for many minutes, and a blocking regeneration shows nothing at all until it lands.
- **One regeneration per item, process-wide** (`RegenerationGuard`, keyed by *item* — two callers naming different generations of one post are still two regenerations of the same thing). Claimed after every free refusal and **before the credential**, released on drop, so an early `?`, a dropped consumer and a panic all release it. It is process-scoped rather than per-caller because the core-side turn runs to completion even when its consumer goes away: a window closed and reopened mid-regeneration meets a fresh view with no memory of the one still running. The durable `idx_one_successor_per_action` is not a substitute — it rejects the loser only after both have paid. A refused second ask is `AppError::RegenerationInFlight` and writes nothing. **The tip is read inside the claim, and that ordering is what the claim is worth** (Codex review, PR #330): the claim makes one regeneration of an item run at a time, and the tip is exactly what a regeneration of that item moves — so a tip resolved *before* claiming can be superseded by the regeneration the claim is waiting behind, and the caller then acquires and spends a credential on a turn whose successor the durable index is already certain to refuse. That is the paid loser the guard exists to eliminate, wearing a stale tip; nothing naming the item's current generation may be read outside the claim. A caller that waited revises whatever is there when its turn comes. Regression: `a_regeneration_that_waited_for_the_claim_revises_the_generation_it_finds`, staged through `AppCore::test_open_regeneration_claim_window` — a rendezvous in exactly that window, the `anchor_window` shape.
- **The claim is announced on both sides** (Codex review, PR #330). A refused caller learns the item is claimed from `AppError::RegenerationInFlight`; it learns the claim has *ended* by awaiting `AppCore::regeneration_settled(item_id)` — the same fact read the other way round, not a second source of truth. It exists because **a regeneration that fails leaves nothing to notice**: one that succeeds writes a new generation, but a network error writes nothing at all and a `ResponseTruncated` writes only a Record entry attached to no action, so a surface that had been refused could never tell "still running" from "failed" and would go on saying the answer was being regenerated for the life of the window. The registry is therefore `item id → watch::Sender` rather than a set, and **the sender's liveness *is* the claim**: `RegenerationGuard::drop` removes it, which wakes every waiter's `changed()` with the closed-channel error, so the release and its announcement are one act and a turn that ends by `?`, by cancellation or by panic announces itself exactly as one that ends by succeeding. Asking about an unclaimed item resolves immediately, so a caller that asks after the release is not left waiting for an event that is past; the window it cannot close is a *later* regeneration of the same item claiming in between, where "one is running" is the honest answer. A wait, never a poll. Regression: `a_failed_regeneration_still_settles_its_claim` — a regeneration truncated at the ceiling, asserting the transcript is byte-identical afterwards *and* that a waiter parked while the claim was held is woken by its release.
- **The claim covers regenerating, not replying — and that boundary is deliberate** (Codex review, PR #330). A reply written while a post is being revised is accepted, spends, and commits; reply threading then resolves its edge to the item's new tip, so it renders beneath an answer it was never written against. Refusing every reply to a claimed item would be a **partial fix that looks total**: the incoherence is caused by *supersession*, and only one of the two verbs that supersede takes a claim — an edit takes none, so the same reply-under-a-generation-it-never-saw would remain reachable through `edit_post`. Re-threading is what keeps a reply from dangling when *any* writer supersedes its antecedent (a second window, a delegated room's driver, a CLI post), so the refusal would also take that asynchrony from every one of them to solve one surface's affordance problem. The surface offering both verbs is the one that knows the reader pressed them a second apart, and that is where the exclusivity lives (`crates/eidola-gui/AGENTS.md` → `Space::mutation_in_flight`). Pinned as current behaviour by `a_reply_written_during_a_regeneration_rethreads_onto_the_answer_it_never_saw`, so a future decision to move the gate down here changes a test that states the trade rather than discovering it.
- **The twins share one implementation:** `prepare_turn` builds a `TurnPrep` (attested client, attach plan, upstream context, charge estimate + budget gate, spend proof + pending refund, ACT header — the `Wallet` "spending" emission happens here) and `TurnPrep::persist_turn` writes the durable rows; the transports are thin.
- Emissions: `Wallet` at spend start, `Space`+`Record` on non-2xx, `Space`+`Wallet`+`Record` on success — never `SpaceIndex` (`post` owns new/auto-title).
- **`respond_stream(space_id, model, target_action_id, sender)`** requests a streaming response to an already-persisted post (the saved user turn a failed ask leaves behind) without re-posting — `run_turn_stream(Reply)` minus the leading `post`. Backs the GUI's Retry affordance. `respond_stream_as(space_id, participant_id, …)` is the participant-aware analog (an explicit ask that bypasses the cascade guard and router) — and the door the sub-space turn driver takes internally, with no consumer to stream to.

**Charging:** the prompt side of the estimate is the shared `eidola-common::prompt_charge` contract — literally the same function the server computes over the same `messages`/`tools` arrays, so hold ≥ charge is structural. It counts every message's `content`, every `tool_calls` entry's compact JSON serialization (the whole entry — the proxy can't know which fields a chat template renders), and every advertised tool schema's compact serialization once per request. Message-level scalar framing (`name`, `tool_call_id`) is covered by the per-message allowance. `budget` caps the charge of each round.

### The bounded tool loop (task 20)

A turn is a bounded agentic loop. Each iteration is one HTTP request: the model either answers (loop ends, `inference` persisted) or returns `tool_calls` — the round is persisted, executed, appended to the in-flight messages, and the next round runs.

- `MAX_TURN_ROUNDS = 8` caps model **rounds** per turn (a fixed constant bounding one ask's worst-case spend, not a setting). One request a turn may issue is not a round: the tool-capability probe a rejecting endpoint costs, so the worst case is `MAX_TURN_ROUNDS + 1` requests. Exactly one — the degrade fires only on round 1 with the turn's own tools attached and withdrawing them clears that latch — and it is uncounted because the endpoint rejected it before doing any work, so its hold refunds in full and the spend the constant bounds is unaffected. Reaching it with the model still asking for tools ends the turn with `AppError::ToolLoop`; the capped round's tools are deliberately not executed (their results could never be sent). An empty registry means one iteration max, so the single-inference path is untouched.
- **Wire format:** `tools` carries the OpenAI function schema; `tool_calls` are read off the blocking body's `message` and assembled incrementally from SSE `delta.tool_calls` (per-`index` accumulators concatenating id/name/arguments). The follow-up request replays the model's call objects **verbatim** (ids and provider fields intact) in an `assistant` message with `content: null` — for streamed calls the accumulator carries non-canonical keys through reassembly (shallow, last-non-null-wins; the streaming-only `index` framing key is not replayed) — followed by one `tool` message per result, **raw, with no header** (a tool result is neither a post nor authored by a participant). The outer request body is built by `eidola_common::chat_completion_request_body`; `eidola-server::types` deserializes that same body in a regression, so an added client field cannot silently outrun the strict server request type.
- **Per-round holds, not hold reuse:** the ACT protocol consumes a credential per request, so each round re-estimates over the grown messages array, re-checks `budget`, and acquires its own hold under `spend_gate` (`Change::Wallet` fires per round; `ChatResult::credits_charged` is the sum). `TurnPrep.tool_schemas` is serialized once at preparation so every round's estimate and wire request read one array.
- **Persistence:** a round writes a `tool_call` action (`tool_use` blocks with `tool_name` + `tool_call_id` + raw argument string, plus any `thinking`/`text` produced alongside, and the round's tokens/credits) and a `tool_result` action (`tool_result` blocks keyed by call id; no model, no credits; status `error` if any tool failed). Both chain off **the post the turn answers**, never the inference (a cap/budget exit ends the turn without an inference; hanging the trace there would leave it parentless) — and because `get_space_tree` keeps only post-bearing types, the chain collapses out of the render while staying resolvable in the Record. `db::last_action_in_space` is the last **post** for the same reason.
- **Model mistakes are results, not failures:** an unknown tool name, unparseable `arguments`, or a tool's own error become the tool *result* text the model reads next round. Only structurally unusable values fail the turn (raw exchange recorded, no action attached): a call with no id / no function name, or a `tool_calls` that is present and non-null but **not an array** (blocking or SSE alike — reading that as "no tools" would persist an often-empty completion as a successful answer). An absent or explicitly `null` `tool_calls` *is* "no tools" and stays an ordinary completion.
- Streaming: tool rounds are **invisible pauses** in v1 — no new `ChatStreamEvent` variants; content deltas are forwarded verbatim in every round, so pre-tool narration streams and then persists on the round's `tool_call` action (where the render collapses it).

**Completion classification is the transport's, and it is honest about the ceiling.** Both transports read the terminal `finish_reason` off the first choice (blocking: the completion body; streaming: every chunk, before the delta gate, last one named wins — providers put it on a trailing chunk with an empty delta) and apply one shared rule after tool calls are assembled:

- **`finish_reason: "length"` with no readable content and no tool calls** is `AppError::ResponseTruncated { output_tokens }` and **writes no generation**. This is the reasoning model's failure mode — it can spend the whole completion budget thinking and never start the answer — and every other signal reads like success: 200, parseable, honest usage, a real `thinking` block to persist. An `inference` written there would be a current generation with nothing readable in it: a reply could attach beneath it, and a `Revise` would have replaced a real answer with an empty one. The raw exchange still lands in the Record attached to no action (the shape a structurally unusable `tool_calls` takes), and the credential settles exactly as it does for a turn that produced text — the tokens went.
- **The ceiling with partial text** is an ordinary turn: the answer is real and is kept, and `ChatResult::truncated` says it is not finished, so no surface has to infer it from a token count. Nothing durable records *why* an answer stops — the marker is the caller's to show while it is watching.
- Raising the fixed `max_completion_tokens` is **not** the fix and never was: a larger ceiling raises every hold and admits the same failure. Honest classification is required either way.

**Reasoning ("thinking") is durable.** Both transports recover the model's reasoning from the same provider extensions (streaming `delta.reasoning_content` / `delta.reasoning`; blocking `message.reasoning_content` / `.reasoning`) and `persist_turn` writes it as a `thinking` content block at ordinal 0, ahead of the answer's `text` block (no schema change). It is **never replayed upstream and never part of the readable transcript**: both context queries join content blocks `ON cb.block_type = 'text'`, so a persisted thinking block is render-side disclosure only — what makes the GUI's "Thinking…" disclosure survive a reload.

### First-person traces (task 33)

A turn's tool rounds are replayed to the **responding participant** on later turns and to nobody else. `render_messages` renders only `user_input`/`inference` as posts; `prepare_turn` splices each spine inference's own rounds in *before* it, in the wire shape the model produced them (built by the same `assistant_tool_call_message`/`tool_result_message` helpers the live loop uses, so live and replayed bytes cannot drift).

**Attribution is the context assembly, not the reply DAG:** a trace chain hangs off the *post* the turn answered, so nothing structural links it to the answer — but the writing turn recorded exactly its own rounds as fed context (`db::assembly_trace_blocks`), making the rule *you see the traces of the turns whose posts you can see* — branch-correct and regeneration-correct by construction. A turn also records the traces it **replayed** in its own assembly; the reader dedupes first-on-spine-wins, so each trace renders once, at its producing turn. **The assembly is the ordered composition of the prompt:** `prepare_turn` builds `TurnPrep.context_action_ids` in the same loop that builds `messages`, so a replayed trace occupies its wire position. **No sliding-window elision:** traces stay inline until an explicit future consolidation event, so a participant's trunk is append-only — every request's `messages` is a literal prefix of every later one's. One fidelity limit: only `(id, name, arguments)` are persisted, so a replayed call is reconstructed canonically and provider extension fields on a call don't outlive their turn. Trace bytes ride the messages array, so `prompt_charge` covers them on both sides.

### Thread map + navigation tools (task 21)

`get_upstream_context` scopes a turn to its branch, so without help a model can't know sibling branches exist. `prepare_turn` builds a per-turn `ThreadSnapshot` — from exactly the GUI's materials (`db::get_space_tree_data` → `build_post_tree`), one path for threading and rendering — and appends a trailing `<thread-map>` block naming every fork point on the turn's spine and the branches off it, anchored to handles (`at #h12`), each entry `#handle · author · posts · last activity — opening line` (opening via `derive_space_title`; relative times are coarse buckets so bytes don't churn), plus a `· you participated, N posts` segment for branches the responding participant posted in (per-participant is free because the map is the volatile tail). **No silent stripping:** every branch gets a line.

- **Placement is pinned after the post being answered**, in a trailing message that closes with an explicit `Respond to #h.` pointer — keeping exactly one message volatile so a re-request of the same turn reuses the whole prefix including the post it answers. The pointer belongs to the *message*, not to the map (task 64's roster shares that message); see Identity, roster, and post timestamps.
- **Cache doctrine holds structurally:** branch metadata is never interleaved inline, and the map's data never enters the system prompt — the only system-message change is the static `TRAILING_BLOCK_NOTE` + `THREAD_MAP_NOTE` (+ `THREAD_MAP_TOOLS_NOTE` when tools attach), each of which flips once — the first when the space grows a trailing message at all, the other two at first branch — and is byte-stable after. Task 21 additionally held that a **linear space is byte-identical to pre-task-21** — no map, no note, no `tools` field. **That is the record of a past decision, not a standing invariant** (Mike, 2026-08-11): it was chosen under task 21's own constraints and does not bind new work, and task 64 deliberately broke it (an identity line in every space, a roster beside the map). **The surviving rule is stable-but-larger is fine; per-turn-varying is costly** — a feature may add bytes to a space that does not use it, provided it flips once and is byte-stable after. A *churning* prefix invalidates the upstream cache on every turn rather than once, and that is the cost worth vetoing. "It would add bytes" is a thing to weigh, never a reason on its own to refuse a feature.
- A `Revise` turn's map excludes the generation being replaced *and its subtree*, mirroring what `get_upstream_context` withholds.
- The map rides `messages`, so `prompt_charge` covers it and the hold grows with it — the accepted cost of no-stripping.
- Key regressions in `tests/chat_path.rs`: `a_linear_space_sends_no_thread_map_and_no_tools`, `a_branched_space_appends_a_thread_map_as_the_last_message`, `sibling_branch_turns_send_identical_trunk_bytes` (the cache invariant as explicit byte equality), `navigation_tools_round_trip_through_the_turn_loop`. Pure `ThreadSnapshot` behavior is unit-tested in `lib.rs`.

### Quoted references — the ordinal seam

The schema's `action_antecedent` `relation='reference'` rows (ordinal-keyed PK, `content_block_id` + byte `range_start/range_end` + `annotation`) are written and read end-to-end, designed as one seam with the `gpui-markdown-editor` embed-block plugin (see that crate's AGENTS.md). **The ordinal is the shared key:** `action_antecedent.ordinal` ↔ the body's `{{ embed N }}` marker ↔ the editor's embed-map key ↔ the footnote index. Ordinal 0 is reserved for the structural `reply` edge; reference edges take `1..=N` in supplied order, stable across generations (gaps after removal are fine).

- **Write:** `post_with_references(prompt, space_id, reply_to, Vec<ReferenceSpec>)` — a spec names the **concrete generation** quoted (references never remap to tips) plus `content_block_id` and a byte range. Every spec is validated **before any write** (antecedent exists — any space; block belongs to it; range maps honestly per the shared `quote_snippet` gate), so a bad reference leaves zero trace. Reference writes ride post's existing emissions.
- **Edit interplay:** `edit_post` replicates the tip's references onto the new generation at their original ordinals; `edit_post_with_removals(action_id, new_prompt, remove_ordinals)` drops named reference ordinals from the new generation only. Naming ordinal 0 or a non-reference ordinal is a typed error before any write — the reply edge is not removable through this surface.
- **Read:** `PostNode.references` (each with `content_block_id` + resolved `snippet` — `None` when the stored range no longer maps, never truncated/remapped), `PostNode::embed_map()` (ordinal → snippet, fed to `MarkdownEditorState::set_embeds`), `PostBlock.id`, and `references_to(action_id)` — the reverse index (every current-generation post referencing that concrete generation, with ranges).
- **Upstream — one rendering, every path a model reads (task 63):** a post says the same thing about its references whether a model reads it in the turn's own context, through `read_thread`, through `read_post`, or through `read_post(quote: N)` after following one (`tools::render_followed_post` — a followed post quotes things too, and handing the model a literal marker there would reintroduce the whole defect one call past the fix). `render_post_for_model` is that rendering and `ReferenceEntry` its unit: `[N] #<handle> · <author> — <annotation>` over the passage as a blockquote, splicing in at the marker and listing what the body never embedded under `Passages this post quotes:`. **Marker-less references reach the model** — the state is reachable by two designed routes (a draft whose marker was deleted; `edit_post` replicating an edge onto a body that no longer embeds it) and the human's footnote rail has always shown them, so `prepare_turn` reads the edges of *every* context post, not only marker-bearing ones (one indexed query per hop, beside the two `get_upstream_context` already walks). **The quote is attributed** because a bare blockquote inside another participant's post reads as that participant's own prose; `[N]` doubles as the `read_post(quote: N)` argument, so the inline passage is addressable for the first time. **A cross-space passage is attributed by its source space** — the label join in `db::reference_antecedents` is on `ant.space_id`, since a per-space override is that space's name for the participant and the reading space's override would misattribute. **A handle is offered only where it resolves to the passage being read**, and exactly one thing answers that: `ThreadSnapshot::node_for_action` — the turn's own snapshot, which *is* what `read_post` answers from, so the byline and the tool cannot disagree. **Every name comes from the snapshot when the snapshot has one**: a resolved node is a post of the turn's own space, so its handle *and* its label are read together and are already that space's effective ones; and an unaddressable target — which the snapshot cannot name directly — is named from the **referencing** post's own captured copy of the edge (`PostReference::antecedent_author_label`), which is what `read_thread` and `read_post` render from, so the context and the tools cannot attribute one passage two ways. The edge row's label answers only when even that is missing. A post's reference edges are written once with the post, so the captured copy and a fresh read describe the same edges and can differ in nothing but the label each joined. The edges themselves stay a database read deliberately — they are what *that generation* quotes, and taking them from the snapshot would drop a post's passages entirely when an edit lands between the two reads, instead of degrading only their naming. The edge row deliberately carries nothing that could answer it a second way: a row-derived predicate is a **separate read at a separate moment** (`get_space_tree_data` builds the snapshot, `reference_antecedents` reads the edges, nothing makes them atomic, and two windows share one `AppCore`), so an edit landing between them printed a handle whose `read_post` returned the edited text under the old excerpt. The snapshot is therefore read **before** the references are rendered and passed down. Being in it is the whole test, and it covers every case the row predicate used to enumerate: another space, a superseded generation, a trace/memory/decision action, a failed or in-flight generation — none of them is in the tree. Everything else is *named* — `<author> (a post outside this space, or an earlier version)` — and the addressable space is always the *turn's* space, including when the post being rendered was followed into another one. **The author survives that naming on every path**, which is why `PostReference` carries `antecedent_author_label` (the source space's effective label, joined on `ant.space_id` in `get_space_tree_data` as well as `reference_antecedents`): a **sibling branch is absent from the turn's context**, so `read_thread`/`read_post` is a model's *only* view of a post there, and a cross-space passage cannot be attributed from anything the reading space knows. **And it carries the author's `kind` beside it** (`antecedent_author_kind`, the same join, `get_space_tree_data` only — the model-facing renderings here want the source space's *words*, not a reader's): a label alone is not renderable, because "override to empty" is a real state and what to say instead — the one human is "You", an unnamed agent is "Eidola" — depends entirely on the kind. Reading only the label, the GUI's footnote rail had no second source for a blank one and fell back to "another space", so a cross-space quote of an unnamed author *still* changed attribution the moment it persisted (Codex review, PR #292; regression `a_cross_space_quote_carries_its_authors_kind_beside_its_label` in `tests/cross_space_references.rs`, which also pins that the join follows the **antecedent's** participant rather than the referencing post's). **A preview is neither rendering.** The thread map's opening line and `list_branches` summarize a post as chrome, so they elide the recognized markers and show the branch author's own prose (`strip_embed_markers`): expanding there would lead the teaser with a byline instead of the subject, and quoting the bare passage would attribute another participant's words to the branch author on a line that has just named them. It is the rule the GUI already applies to its own previews (`space_view::references::strip_embed_blocks`), with the same degradation — an unmapped or fence-defused marker stays literal on both surfaces — and a post with no resolvable reference is byte-identical. A label overridden to empty (the schema's non-NULL "override to empty", which `set_space_participant_override` deliberately allows) degrades on **both** arms: no author beside the parenthetical, and a bare `#handle` where a byline would otherwise trail the header separator into nothing. `message_header` itself keeps emitting the separator for a blank label — `is_header_line` keys on it, so a post header that dropped it would stop being stripped on receipt. **An entry carries state, not prose:** `ReferenceTarget` (addressable / elsewhere) × `ReferenceBody` (passage / unresolved range / backlink) decided at construction, rendered once in `ReferenceEntry::render`, so a new case is a compiler error at every construction site rather than a fourth site to get wrong. The three bodies are exactly the footnote rail's three rows — a **range-less edge is a backlink**, a pointer to a post rather than a quote of one (`ReferenceSpec`'s ranges are "both present or both absent"), and describing one as a quote whose range broke would be a plain untruth about an ordinary edge. All of it lands **before** the charge estimate, so the hold covers the bytes.
- **The chore prompts read it too (task 67):** the may-decline router and the branch summarizer are not turns, but they are model-facing, and both used to copy raw text — literal `{{ embed N }}` markers, un-embedded references dropped. Both now read `ThreadSnapshot::post_body`, so a quoted passage reaches them exactly as it reaches `read_thread`. **Expansion, not the preview elision**, on both, and for the same reason: a preview places a post's bytes on a line that has just named its author, while these two *read* the branch — eliding would take the noise and the meaning together, and a post whose point is what it quotes would route to nobody and summarize to nothing. Attribution is what makes expanding safe. The summarizer was free (`branch_slice` already sits on the snapshot); the **router** buys it with one whole-space read per triggering post, taken only for a space with a router model and never on the writer's path (the post is committed and emitted before refinement starts) — deliberately *one* read rather than the turn path's per-hop edge query, because the router needs the rendering, not this-exact-generation fidelity: a generation the snapshot no longer has falls back to the raw body, which is what that path sent before. Folding an action's blocks into one line also made `THREAD_SLICE_POSTS` count what it says. Prompt cost is unchanged in shape — both slices were already byte-clipped per post, so expansion changes *which* bytes the model sees, not how many it may. It does change **which end they come from**, and that is the one budgeting rule both chores now share (`utility::clip_middle`, replacing head-first `clip` at both call sites): a passage is a range its author chose and *nothing bounds its length*, so a marker standing before the post's own words (`{{ embed 1 }}\n\nHave the legal reviewer assess this`) expands into a quotation that can fill the whole per-post budget by itself — the router would then pick a participant without ever seeing the ask, and the summarizer would describe the source passage while dropping the branch author's disagreement with it, in a summary that stays cached and displayed until the branch changes. **Eliding the middle** is the cure because it needs no arithmetic about how a rendering will lay out: the expansion sits *between* the author's words in every shape that matters, so both ends are paid for before the quotation gets the remainder. It is also the rule the summarizer already applied one level up, where an over-cap branch is sliced head + tail. Prose sandwiched between two long quotations is the case it cannot save, and it loses its middle like any other over-budget text. Tests: `the_router_reads_a_quoted_passage_not_its_marker` (`tests/participants_orchestration.rs`), `the_summarizer_reads_quoted_passages_not_their_markers` (`tests/branch_summaries.rs`), plus `a_long_quote_does_not_evict_*` beside each prompt builder and `clip_middle`'s own unit tests in `utility.rs`.
- **One byline per post:** every author-label read returns the effective label (`COALESCE(space_participant.override_label, participant.label)`), `db::get_space_tree_data` included — it was the one read that did not, so a renamed participant answered to their base name in `read_thread`/`read_post`/the thread map (and in the GUI's post bylines) while the transcript used the override. The join stays plain, with no liveness filter: who wrote a post goes on being named after retirement.
- **Marker recognition** is `eidola_common::embed::embed_marker_spans` — the shared structural contract with the editor plugin: only a marker standing as its own blank-line-delimited top-level paragraph, outside fenced-code/block-math regions, expands — exactly the set the editor renders as embed blocks, so the UI and the wire never disagree. A marker whose passage did not resolve stays literal (the editor's degradation) and is footnoted instead. The editor keeps its own parser-driven recognition (it can't depend on eidola-common); lockstep is held by the corpus test `crates/eidola-gui/tests/embed_lockstep.rs` plus identical lexical cases in all three crates.
- **GUI wave 2** (surfaces + doctrine in `crates/eidola-gui/AGENTS.md`): Quote / Quote in Reply, the footnote rail, source highlights. Backing reads: `submit_with_references` and `action_location` (a persisted action's `(item_id, space_id)` — the item id is load-bearing: a quoted generation later edited/regenerated is absent from the current-tip tree, and the item lets the GUI select the superseding tip rather than opening a duplicate window). Draft ordinals may gap; the gap reconciles exactly once, at post time (specs compacted + markers rewritten together; the editor's `insert_embed_marker`/`remove_embed_marker` are the marker-byte owners).
- Tests: `tests/bus.rs` (rows, snippets, emissions, zero-trace failures, replication/removal), `tests/chat_path.rs` (`upstream_context_expands_embed_markers_into_quotes` — attributed expansion, a footnoted un-embedded ordinal, fence-defused markers going upstream literal; `a_reference_whose_marker_an_edit_removed_still_reaches_the_model`; `navigation_tools_round_trip_through_the_turn_loop` for `read_thread` parity), `a_per_space_rename_reaches_the_tools_as_well_as_the_transcript`; `a_quote_of_a_since_edited_post_is_not_offered_its_handle`; `a_reference_that_names_no_range_reads_as_a_backlink_not_a_broken_quote`; `a_quote_whose_author_has_no_name_here_keeps_a_clean_handle`), `tests/cross_space_references.rs` (`a_cross_space_passage_is_attributed_by_the_space_it_was_written_in`, `a_followed_post_renders_its_own_quotes_like_every_other_post`, `an_unvalidated_reference_to_a_non_post_is_withheld_by_every_read` — the edge is named, never addressed; `a_sibling_branchs_cross_space_quote_keeps_its_author_through_read_thread`, which pins the absent-sibling premise alongside the byline), plus the pure rendering in `lib.rs`/`tools.rs` and the addressability predicate in `db.rs`.

### Cross-space references — the permission model (task 37)

One sentence governs it: *you may quote what you can read; quoting **copies** the excerpt to the new audience; the link itself is not a capability.* **Membership is the ACL** (`db::is_space_member`: owned row ∪ live reference row, deliberately not filtered on `archived_at`) — and **membership means *live* membership: a live row and a live participant**. Retirement soft-removes the participant and leaves its `space_participant` rows standing on purpose (the trail records where the agent worked), so a question asked only of the row went on answering "member" for an agent just taken out of service — and since a turn binds its tools to the responding participant at the start, a retirement landing between two rounds left a live `read_post` still opening those conversations, and `list_my_spaces` still listing them (Codex review, PR #279). The rule is enforced **where membership is asked** (`is_space_member`, `participant_spaces`) rather than by sweeping `left_at` onto every row at retirement: one rule at the boundary that covers any future availability-ending state, that leaves the historical record undisturbed, and that no racing grant can slip past (`add_global_participant` already refuses a retired participant, and a row created anyway still would not answer). `space_participants` — the roster, and so planning and model→participant resolution — already read membership this way; the two ACL predicates had drifted from the definition their own docs claimed. **Author-label rendering paths keep their plain `space_participant` joins**: "who wrote this post" must go on naming retired authors — which is exactly why the *write* side has to be guarded too, and is (see the config-write contract above): a stale save that renamed a retired participant would have rewritten those bylines. Tests: `a_retirement_mid_turn_closes_the_passage_it_had_opened` (`cross_space_references.rs`), `a_retired_agent_discovers_no_spaces_mid_turn` (`global_agents.rs`) — both drive the real turn loop with a tool that retires the responder mid-turn.

- **Create:** `validate_reference_spec` refuses a spec whose antecedent lives in a space the authoring participant **cannot read** (`db::may_read_space`) — the rule's own sentence, *you may quote what you can read*, rather than bare membership, which is what it had drifted into. The human read bypass changed what a reader can read, and this had not followed: a reader who opened a room their agents opened between themselves could read a finding and not quote it, refused only after composing the draft — on exactly the flow the bypass exists for. Widening grants nothing, because quoting **copies** the excerpt and the premise is that the author can already read the passage; the link is not a capability. It is also **author-kind-aware by construction** — `may_read_space` widens for a human viewer and nobody else, so an agent that is not a member still fails it, and a future non-human caller inherits the membership rule rather than the bypass. Today that is theoretical: the one caller is `post`, which hard-codes the shared human as author. A **notebook** stays refused by that function's own carve-out, which is the privacy this gate was built for. The check runs inside the same pre-write loop (zero trace, no emission). The author today is always the shared human, referenced into every space by the default template, so the single-user case is untouched. `edit_post`'s replication is deliberately not gated (quoting copies; the passage is already public here). Branch summaries and `remember` provenance write `db::insert_reference_antecedent` directly — the gate lives at the *post-authoring* seam.
- **What a reference may name** (PR #261 review — a real leak, closed): membership answers *whose* material; this answers *what kind*. `validate_reference_spec` refuses a non-post antecedent and any block that isn't `text` (`db::POST_ACTION_TYPES` / `QUOTABLE_BLOCK_TYPE`) — otherwise a quote could name another participant's `tool_call`, a `decision`, a `memory` block, or any post's `thinking` block, and the upstream embed expansion would have expanded it into the next responder's context. **All three read paths re-apply the rule** for edges written below that seam: the expansion skips it (marker stays literal), `build_post_tree` resolves its `snippet` to `None` (edge renders — existence is public — passage withheld), and `db::referenced_post` reads post types only. The filters live in the *readers*, never in `db::reference_antecedents` (edit replication must not silently drop edges — that would rewrite history). The `#[doc(hidden)]` `test_insert_unvalidated_reference` seam exists only for the regression test.
- **Follow:** `read_post` gained an optional `quote: N` argument (`tools.rs`) that reads the post a quoted passage came from, membership-checked **per call** against the responding participant — so blocked → grant → retry needs no machinery, just the grant below. **Cross-space addressing goes through the reference edge, never a handle** (handles are global but a snapshot knows only this space's): the model can name only this post's quote number, so the reachable set is exactly "what someone here already quoted" — guessing is unrepresentable.
- **Denial leaks nothing** (`AppError::NotAParticipant`, `tools::FOLLOW_DENIED`): may confirm existence (public within the referencing space); carries no space id, title, participant, or content — it renders both into a model-read tool result and into UI a non-member sees.
- **The human arm of rule 4 is the same rule, asked at the same place** (wave 2): `action_location(viewer, action)` — the read the GUI resolves a quoted post's home with before navigating — takes the viewer as a **required** argument and refuses a non-member with `NotAParticipant`. A second, ungated entry point was considered and rejected: it would have opened an agent's notebook window to a reader who is not in it, which is the one space the shared human genuinely is not a member of. An unknown action still answers `Ok(None)` — conflating "no such action" with "not yours" would make the read a membership oracle.
- **Grant:** membership, and for a space-owned agent the promotion that must precede it, travel as **one transaction**: `promote_participant(id, persona, grant)` takes an optional `SpaceGrant { space_id, role }` written inside `promote_participant_tx` (`db::MembershipGrant`), and `add_global_participant` takes an optional `MembershipRole` for the already-shared case (`Observer` is what a read-only grant is *called* — roles are descriptive; membership itself is the ACL). **And *which* of those two a grant needs is itself decided at the write** — `AppCore::grant_space_membership(space, participant, role)` → `db::grant_space_membership_tx`, the door the invite form uses: it reads the scope under its own `BEGIN` and either promotes-with-grant, joins (insert-or-revive), or reports `AlreadyAMember`. A caller branching on the *picker's* snapshot asked for a promotion of a row another window had already shared — refused, for a membership that would have been added without complaint, and (when the competing promotion granted this very space) reporting failure about a state that already held (Codex review, PR #280). It is the decide-at-the-write family applied to the **choice of verb** rather than to a write's arguments (PR #279's persona). It is deliberately **not** `promote_participant` learning to tolerate an already-global row: that refusal is the *Share* affordance's, and its copy ("promotion is one-way and there is no demotion") is what a reader who pressed Share needs; a grant is a different request and only it may be satisfied by a row that is already shared. Each branch still carries its own premise into its own statement, and the typed refusals (unknown space, retired, non-agent, the human, Eidola) stay in front of the transaction where a message belongs rather than a rollback. **And deciding at the write means reserving the writer**: every transaction here opens through `db::begin_write` (`BEGIN IMMEDIATE`), because a deferred `BEGIN` reserves nothing and these transactions all read before they write. Measured on turso at our pin with two live connections on one `Database` — `db_conn` mints a fresh connection per call, so this is an in-process race, not merely a cross-process one — a deferred `BEGIN` lets both sides read the old state and answers the second write `BusySnapshot("database snapshot is stale, rollback and retry the transaction")`, which `busy_timeout` cannot rescue (a stale snapshot is not something you can wait out); `BEGIN IMMEDIATE` makes the loser **wait** for the winner's commit and then read *its* state, which is how the grant takes the join branch instead of failing (Codex review, PR #280). **And the result reflects the commit point**: the membership a grant answers with is read *inside* its transaction and handed back (`db::GrantOutcome`), never re-read after it — between the commit and a second read another window can end that membership or retire the agent, and the call would then report failure for work that committed, including the irreversible promotion. That is the failure-message-beside-a-committed-write state the transaction exists to prevent, reintroduced one line past it. `add_global_participant` had the same window (its join and the roster read that described it shared no transaction) and now goes through `db::join_space_participant_tx`. The rest of the family is clean by construction and was re-checked: `promote_participant` assembles `PromotionOutcome` from its *inputs* (the argument, the row read before the transaction, the uuid it minted, the grant it was handed); `retire_participant` answers `()`; `remove_space_participant`'s `bool` comes from the transaction's own `SpaceRemoval`, and its one post-transaction read is on the refusal branch, where nothing committed and the label already degrades honestly. Regressions: `db::tests::tx_contention` (in `src/db.rs`, beside the writers — those transactions are crate-private, and an integration test under `tests/` is an external consumer like any dependent). Test: `a_grant_decides_from_the_row_it_finds_not_from_the_pickers_snapshot`; the canonical blocked → grant → retry loop now goes through this door. Two calls were the wrong shape for the same reason the persona was (Codex review, PR #279), only sharper: **promotion is one-way**, so a grant refused after the promotion committed leaves an irreversible change nobody asked for standing beside a failure message. A grant naming the promotion's own home space is *satisfied* (the promotion joins it) rather than refused; an unknown space is refused before the transaction opens. `list_grantable_agents(space, viewer)` is the picker's read — live agents not already members, viewer-scoped so a space-owned agent is listed only where the viewer takes part in the space that owns it (a listing is a read, and obeys the same ACL its rows are about). **"Not already a member" means not *live*ly one, so an agent that left is offered again — and the write has to honour what the picker offers**: leaving is soft (`left_at`), the row stays on the space's primary key, and the insert-only join struck nothing, so the roster read that followed found no member and told the reader the *live* agent "has been retired and cannot rejoin a space" — the wrong sentence, and permanent, since every retry took the same path (Codex review, PR #280). `db::ensure_space_participant` is therefore **insert-or-revive**: one guarded statement whose `ON CONFLICT … DO UPDATE` clears `left_at` and applies the role being asked for, under `WHERE left_at IS NOT NULL` so a **live** membership is never rewritten (which is what the template instantiation's copied human reference — inserted moments earlier with the template's own role and overrides — depends on). The `WHERE EXISTS` liveness premise guards both paths for free: a `SELECT` that yields no row conflicts with nothing, so a retirement that wins the race revives nothing either. It answers whether the membership *changed*, which is what `add_global_participant` emits on: a fresh join or a revive emits `Change::Participants`; a re-add of a live member writes nothing and says nothing. Promotion's own grant (`db::insert_space_participant`, inside `promote_participant_tx`) needs none of this and deliberately keeps its plain insert: its candidate is space-**owned**, so it has no membership row anywhere but its home space, and a collision there is a bug the whole transaction should fail on. Tests: `an_agent_that_left_can_be_invited_back` (`cross_space_references.rs`), `a_membership_that_left_is_revived_and_a_live_one_is_left_alone` (`db.rs`).
- **Inbound:** `references_to_visible_to(action_id, viewer)` filters the reverse index to referrers in spaces the viewer takes part in ("can see" = "can open"); the unfiltered `references_to` remains available, but **the GUI reads the filtered one** (wave 2 — the recorded lean, implemented: the app never paints a backlink whose click it would refuse). Same-space backlinks are unaffected wherever the viewer is a member of the space being read; the one place they are not is a **notebook** opened from Settings ▸ Agents, where the human can read the conversation but is not a member — so its own highlights are withheld. Inbound references are deliberately not added to upstream turn context in this wave. **An incoming reference carries its referrer's author identity** — `IncomingReference.author_label` + `author_kind`, joined on the **referring** post's own space (`COALESCE(space_participant.override_label, participant.label)`, `participant.kind`) — the mirror of the pair a *quoting* edge carries about its antecedent, and for the mirror reason: a backlink listing is exactly the surface that meets a referrer from a conversation the reader's window never loaded, and nothing that window knows can name one. It is a **pair**, never a bare label: a per-space override of `''` is a real state, so the label can name nobody and only the kind is left to render from — which is why the presentation layer reads both through one byline rule rather than printing the label. **And the referrer's *identity across generations* travels with it** — `IncomingReference.item_id`, the referring post's item. The index reports *current* generations, and editing a referring post without touching its quote replicates the edge onto a fresh action: the backlink is the same backlink under an `action_id` no consumer had seen, so anything holding a selection of these rows across a reload keyed on the action alone loses a row to an edit that changed nothing about it (Codex review, PR #327). Regression: `an_edited_referrer_keeps_its_backlink_under_a_new_generation` (`tests/cross_space_references.rs`). **And the referrer's *place* travels with it** — `IncomingReference.space_title`, joined on the same referring space (`None` for a conversation never named; `space.title` carries no uniqueness constraint, so a presentation layer telling rows apart needs a tiebreak of its own and the GUI's picker numbers collisions). An author does not identify a post: one participant can quote a passage from two conversations, and a backlink listing that names only the author offers two rows that read alike and lead to different windows. It is the place rather than the referring post's content on purpose — a title says where a click goes, while lifting prose out of a space the reader may not be in would make this read a disclosure channel; the surface that renders it takes the filtered door, which reports only spaces the viewer may read. Both reads answer all three (the filtered twin is the same read with a membership gate in front). Pure reads still; no emissions. Regression: `an_incoming_reference_carries_its_referrers_author_identity` (`tests/cross_space_references.rs`), whose agent-quoted-by-a-human shape is what pins both joins to the referrer rather than the antecedent, and whose one-author-two-conversations arm is what pins the title as the discriminator.

## Agent-spawned sub-spaces (`subspaces.rs`)

An agent that needs work done elsewhere spawns a **sub-space**: a new space with **no human participant**, holding the spawning (owning) agent and the sub-agents it delegates to, opened by a *brief* the owner writes. Nothing is copied — the room starts fresh, and the parent hears back through an ordinary cross-space reference rather than a merged transcript.

**Ownership needs no column.** It is `space.parent_space_id` (documented navigational since the schema was written, NULL until this door) plus the owner's `role = 'owner'` membership row. That is the notebook lesson in reverse: a notebook needed `notebook_participant_id` because its consumers ask *whose* it is **without** membership, while a sub-space's owner is definitionally a member, so the membership row can carry it. `db::SUBSPACE_OWNER_SQL` is the one fragment every read resolving an owner shares, so "who owns this" cannot be answered two ways.

**Two rules about the owner's membership, and they are one design.** An owner cannot leave the *room* it owns — that membership is the whole record of who is answerable for the delegation, and nothing can grant it back, so the leave is refused in its own `WHERE` (`SpaceRemoval::RefusedSubspaceOwner`). An owner leaving the *parent* is an ordinary departure and is allowed — and it closes the delegations it was running **for that conversation** (`db::close_delegations_run_for`, scoped by `parent_space_id` so its rooms under other conversations are untouched), inside the departure's own transaction, with the same fixpoint descent and the same announcement per closed room that archival and retirement use. Left live, such a room could only fail: every report it wrote would act as a participant that is no longer in the parent and be refused for it, forever, against a meter nobody reads and a live-room slot nobody gets back — and it would be deaf to the only signal that changed, since no delegated room listens for `Change::Participants`. The first rule stops a room losing its owner; the second stops a room outliving the reason it existed. Both branches of the departure take it (a soft-remove and a leave alike), and the refusals take nothing. Tests: `an_owner_leaving_a_conversation_closes_the_delegations_it_ran_for_it` (`tests/subspaces.rs`), `an_owners_departure_from_the_parent_leaves_no_room_retrying` (`tests/subspace_driver.rs`).

**Which makes that membership structural, and it is held so at every write that could move it — three of them, and the set is the point.** One row records who is answerable for a delegation, whose live-room quota it counts against, and who its report will go to, so ordinary roster work must not be able to end it, add a second one, or leave it pointing at somebody who is gone: **the leave is refused, a second owner is refused, and retirement archives.** The third is not a fourth guard of the same kind — retirement writes neither of those rows (it soft-removes the participant and leaves its memberships standing, after which every membership *question* answers "no"), so nothing the first two do can reach it, and no door could repair what it leaves: a replacement owner is exactly what the second guard refuses, correctly, because ownership is not transferable. `db::retire_participant_tx` therefore archives every live sub-space the agent owns in the same transaction as the soft-remove, **owner-scoped rather than by descent** — so it reaches that agent's rooms at every depth and nobody else's. Archiving rather than refusing the retirement: one stuck delegation must not make a shared agent unretirable, and the notebook arm standing beside it in that same function already made the choice. The room stops being live, so it holds no quota, stops being a Library row promising work that cannot happen, and — because archival is what stops new turns anywhere (see Archival stops new work) — schedules nothing and refuses any turn already planned in it; the transcript survives whole, because archival is a visibility choice and neither membership nor the human read bypass filters on it. **And what those rooms had delegated onward goes with them**, at every depth and whoever owns it — the same rule `archive_space` applies (see Archiving a conversation closes its delegations). A nested room's owner is not being retired, but its *purpose* is: it exists to serve the conversation above it, and that conversation is closed, so its report is a turn the archived parent refuses and the delegation would stay outstanding forever. `db::archive_rooms_under_a_closed_one` is the shared descent, stated as the invariant it restores — *no live delegation under a closed room* — rather than as a walk, which is why one statement serves a door that names one space and a door that names an agent's whole set. Emissions: `Change::Participants` always, and `SpaceIndex` exactly when the transaction archived a space the Library **lists** (a sub-space is one; a notebook has never been), counted inside the write and returned as `db::Retirement`. Beside that, every space it closed is closed the way all three archival doors close one — announced and released (see Archiving a conversation closes its delegations) — the notebook included, because a room can be opened from a notebook and so a wait can be registered against one. `db::Retirement` therefore carries the ids as well as the count: the count decides the listing announcement, and only a list can say which rooms to close out. **And the guards are complete because the raw writes are not exported.** `db` is a public module, so rules that live in a transaction protect nothing if the statement it wraps is `pub` — a dependent could simply call the statement. Two kinds of guard are bypassed that way and both are load-bearing: the ones decided against **live state** inside a transaction (the refusals above; `retire_participant_tx`'s archival arm), and the ones decided against the **caller's own values** in front of it, where a message belongs rather than a rollback (`Inner::spawn_subspace` refusing a blank brief — a value cannot be raced, so that check is correctly *not* in the transaction, and that split is only sound while the transaction is unreachable). So every raw write this feature touches is crate-private: the membership primitives `insert_space_participant`, `ensure_space_participant`, `insert_participant_ref`, `soft_remove_participant`, plus `spawn_subspace_tx` with its `SubspacePlan` argument (an argument type reachable from outside is the write reachable from outside) and the `test_insert_space_capability` seam. The guarded doors are then the only way in, and the invalid state is unrepresentable at the API boundary rather than re-checked at each entrance — duplicating the checks inside the primitives would put one rule in two places to drift apart. Every caller was already inside app-core, and no downstream crate reaches `db::` for any of them, so nothing outside lost anything. `leave_space_participant` goes further and is **`#[cfg(test)]`**: it is the leave *without* the two structural refusals, it never had a production caller, and the compiler now holds it there — the same rule `the_raw_space_insert_has_no_production_caller` states about `insert_space`, one enforcement stronger. `the_raw_db_writers_are_not_exported` (`tests/subspaces.rs`) pins the class so a future `pub` is a failing test rather than a quiet hole; **pure reads stay `pub`** — they answer questions, they do not perform acts. **And the rule is the shape, not the vintage**: the whole `_tx` family has it, so `remove_space_participant_tx`, `join_space_participant_tx`, `grant_space_membership_tx`, `retire_participant_tx`, `promote_participant_tx`, `archive_space_tx` and `update_template_tx` are crate-private too, along with `discard_space_if_pristine` (the disposal that decides *inside* the delete whether anything here was worth keeping) and `instantiate_template` (the only path that mints a space with participants from birth) — each a transaction whose refusals or side effects are the reason its door exists, and none of them duplicated into its primitive, which would put one rule in two places to drift apart. The last two are the clearest case of each category: `Inner::archive_space` is what **releases** every room the transaction closed from any wait registered against it (an archived room is never armed, so nothing on the bus can deliver that later, and there is no un-archive door), and `Inner::update_template` refuses a blank title, a `cascade_limit` below 1, an unvalidated participant tuple and an already-removed template **in front of** the transaction. **And the pin closes the class rather than listing it**: alongside the enumeration (which pins existence and naming), `the_raw_db_writers_are_not_exported` sweeps `db.rs` for any `pub async fn …_tx(` — a `_tx` name says "transaction", and every transaction here has a door in front of it, so a writer added tomorrow is caught without anybody remembering to list it. No downstream crate ever reached `db::` for any of them (the GUI and CLI name exactly one `db::` symbol between them, `default_agent_label`, and only in prose), so nothing outside lost anything. The consequence for tests: a **transaction-level** regression belongs beside the writer, in `db.rs`'s own test module, because an integration test under `tests/` links the crate as an external consumer and an exported transaction for its benefit is the hole this rule closes. In detail: `remove_space_participant` refuses the owner **in the leave's own `WHERE`** (`SpaceRemoval::RefusedSubspaceOwner` — the notebook owner's rule applied to the other structural membership, and guarded in the statement for the same reason: a spawn mints the room and the membership in one transaction, so a removal that read the space a moment earlier saw an ordinary conversation), and both granting doors ask `db::subspace_owner_of` **inside their own transaction** before writing a `role='owner'` membership (`db::refuse_second_subspace_owner`, reached by `grant_space_membership` and by `add_global_participant`, which takes a role too — and defaults it to the agent's own, which can be `owner`). An ordinary space is untouched: `role` stays descriptive there. With both guards in place a departed or duplicated owner is unrepresentable, so `SUBSPACE_OWNER_SQL`'s `left_at IS NULL` filter and its total ordering are belt to that brace — if one ever appeared the read answers "no owner" (a sub-space that stops being one, which every consumer already handles) rather than resurrecting an ended membership, and answers the *older* of two rather than whichever the planner reached first.

**The door is `db::spawn_subspace_tx`, one `BEGIN IMMEDIATE` transaction that decides every guard at the write.** Each guard reads state a concurrent window can change (a membership, a retirement, another spawn, an archival), so asking before the writer is reserved would let two spawns pass a limit only one may. In order: the parent exists **and is not archived** — one read, like every other "may work happen here" gate, and reachable rather than theoretical, since a turn already past `prepare_turn` when an archival landed runs to completion by design, so the owning agent's spawn call is still to come while nothing about archival makes the parent row or the owner's membership stop looking live; there is somewhere for the report to land — an anchor is itself such a post, so this only bites a caller with no turn behind it opening a delegation from a conversation where nothing has been said, and it is refused *there* because the asymmetry is total (a refused spawn costs nothing; a room that runs its turns and then finds no post to reply to has spent real money on work nobody will ever be told about); the spawner is a **live global agent** and a live member of the parent (global because a space-owned participant cannot be referenced into another space at all — the rule that lets an agent own a room elsewhere is the same rule that lets it join one, which is what will make a `scope=='global'` gate on the tool that exposes this door structural rather than a second opinion); depth ≤ `MAX_SPAWN_DEPTH`; live sub-spaces owned < `MAX_LIVE_SUBSPACES_PER_OWNER`; requested capabilities ⊆ the parent's; every requested sub-agent is a live global agent (the `add_global_participant` rule, asked here so the refusal is the spawn's). Then, in one commit: the space row (parent link, **the anchor** — `parent_action_id`, the post in the parent this delegation is being opened from, refused unless it is a post the parent **currently shows**: current generation, terminal status, post type, the transcript's own predicate, so a superseded wording or a failed regeneration's hidden `error` tip cannot be the thing the report later replies to; see the driver's report seam for why it is captured here — the parent's `cascade_limit` and `router_model`, **born stamped**), the owner's `owner` membership, each sub-agent as a `member` with `override_notify_policy='all'`, the brief, and the capability rows. **No human membership row** — this is a new creation path, not `instantiate_template` (which joins the shared human unconditionally and whose template agents have nothing to do with a delegation). Refusals are `AppError::SpawnRefused` carrying a typed `SpawnRefusal` whose `Display` is model-facing prose, so the tool that exposes the door renders a refusal as a correctable tool result rather than failing a turn.

**`override_notify_policy='all'` on the sub-agents is what makes a human-less room live**: the seeded policies fire only on human-authored posts, and there will never be one here. The override is per-membership, so the agents' global rows are untouched (pinned in `subspaces.rs`'s roster test, which also asserts the parent membership is unchanged). **The owner's policy is written too, as `'human'`** — every membership a spawn writes states its policy rather than inheriting one. Leaving it NULL made the room adopt whatever that agent's global row said, and a shared agent configured `all` is ordinary: the first helper's answer would schedule the owner, whose answer would wake every notify-all helper again, so one spawn's work grew with the square of the roster until the cascade guard stopped it. `'human'` rather than `'explicit'` — both are silent among agents, and the difference shows only once somebody joins: `'human'` means the agent answerable for the delegation answers the human who came to look at it, which is what that agent is for, while `'explicit'` would leave it deaf to them. It is also the seeded default, so the owner behaves like an ordinary agent toward people and stays quiet among its helpers. Neither choice decides how the owner's *own* turns get driven — the orchestration layer plans those through its own channel — so this settles one thing: who a post in this room wakes. **And it stays settled**: `db::update_space_participant_override` refuses, in the statement's own `WHERE`, to set a live sub-space owner's policy to `all` **or to clear it**. Refusing `all` alone would not close it — an inherited (NULL) override resolves to the agent's *global* row, which the config door can flip to `all` afterwards, reopening the hazard through a write that never mentioned this space. Keeping the override always present and never `all` makes the global policy irrelevant here by construction (`COALESCE` takes the override every time), so no second guard is needed on the config door or on promotion's persona. What a reader keeps is the choice that matters — `human` or `explicit`; what they lose is "inherit", which is exactly the state that was unsafe. A zero-strike is *named* afterwards, never decided there. Tests: `a_notify_all_owner_is_quiet_among_its_helpers_and_answers_a_human`, `a_sub_space_owners_policy_cannot_be_edited_back_into_the_cascade` (which also flips the global to `all` and proves the room does not move).

**Guards are constants, not schema** — `MAX_SUBAGENTS_PER_SPAWN = 8` (every seat is written with notify-all, so each sub-agent answers every post *and* each answer notifies all the others: one spawn's scheduled work grows with the square of the roster, and the cascade guard is the only thing that ever stops it — a panel is the point, but a panel is small), `MAX_SPAWN_DEPTH = 3` (a space nobody spawned is depth 0, so great-grandchildren are admitted and their children refused; `db::space_depth` walks the chain and is cycle-guarded, because the column is a self-referencing FK with no cycle constraint and this is the one place a cycle becomes a hang) and `MAX_LIVE_SUBSPACES_PER_OWNER = 8` (archiving one frees a slot, which is also the stated remedy for a delegation someone regrets). `cascade_limit` inherits the *parent's* value — attenuation-flavored: a delegation never gets a looser runaway guard than the room it came from.

**Capability attenuation is a snapshot, and a grant is copied rather than composed.** `space_capability(space_id, name, config)` is written inside the spawning transaction and immutable afterwards; **absence of a row is absence of the capability**, so "a sub-space holding a grant its spawner lacked" is an invalid state checked once, at mint, against data. The only source a spawn may draw from is **its own parent's snapshot**, which is why a chain attenuates without anyone walking it: what B may give C is what B was given, and a capability B's *grandparent* holds is simply not there (`attenuation_holds_down_a_chain_a_grandparent_cannot_reach_through`). A spawn also refuses to seat a participant — the owner included — with **no model in its own row**, because a sub-space sees each participant's *base* configuration (nothing but the notify policy is overridden into one, so a model supplied by an override in the parent does not travel) and a model-less agent is skipped by every planner: seating one would report a room that scheduled nothing. A request names capabilities by name only — the `config` is copied from the parent's row byte for byte, so nothing can be widened on the way down; narrowing a config is a future refinement, not a v1 hole. The table is **empty in practice today** (tool availability is fully derived: registry + `has_map` + backend probe + `scope=='global'`); the shape is the point, so VM sandboxes and web search arrive as rows flowing through this gate rather than as new security surfaces. Because nothing in production grants a capability, the gate could otherwise only be tested on its refusals — hence the `test_grant_space_capability` seam, which seeds the root of a chain. **That seam is compiled out of release builds** (`#[cfg(any(test, feature = "test-support"))]` on the db half as well as the `AppCore` one), unlike the read seams beside it which carry `#[doc(hidden)]` alone: a read cannot forge state, while this one mints the very thing the model exists to make unmintable, and `#[doc(hidden)]` gates documentation and nothing else. `only_a_spawn_can_mint_a_capability` pins both that cfg and the fact that no other function in `db.rs` writes the table.

**The brief is a `brief` action — a fourth post type.** An agent-authored post outside a turn is neither `user_input` (which every display path maps to the human's role) nor `inference` (which claims a model call and a spend that never happened), so the vocabulary gained one entry rather than one of the two gaining a lie. The cost measured before choosing: the schema CHECK, `db::POST_ACTION_TYPES{,_SQL}`, `mechanical_plan`'s post gate and `render_messages`'s two matches — all additive, and the last three now read `db::is_post_action_type` / `db::is_agent_post_action_type` instead of inline literals, so a fifth type is one constant away. The upstream role split was already participant-derived and needed nothing. The GUI's `SpaceView::from_post` falls through to `assistant`, which is the truthful render. Reusing `user_input` would have cost nothing to write and would have attributed an agent's post to the human on every surface that maps by type, including `first_user_text`, whose "the first `user_input` item" contract the sub-space's brief would have quietly become.

**Billing is unchanged, and confirmed rather than assumed**: the pricing contract inspects only message/tool JSON shape, and holds are minted from the process's single configured account — nothing assumes a human at the root of a thread. A sub-space turn spends like any turn; the human authorized it by authorizing the owning agent's turn.

**Reads for a driver:** `post_author_label(action)` (how a post's author is named — the same `POST_AUTHOR_LABEL_SQL` / `POST_AUTHOR_JOIN_SQL` fragment `reference_antecedents` joins, so a passage cannot be attributed one way in a prompt and another in the record: that post's *own* space's effective label, and **no liveness filter**, so an author retired between writing a finding and its being reported is still named), `last_reply_by_participant(space, participant, antecedent)` (the owner's own answer to the post a delegation was opened from — where its report attaches; **the item's original author**, not the tip's, the same origin join settlement uses), `last_post_by_participant` (the anchorless fallback, same authorship), `visible_tip_of_action(action)` (the post that action's item currently shows, or `None` — what the walk asks of every frontier id before planning it), `subspaces_of(parent)` (every sub-space of a parent, archived included — a parent's history of delegations does not shorten), `live_subspaces_owned_by(owner)` (the rooms an agent is answerable for; also what the per-owner guard counts), `subspace(id)` (parent + owner from a sub-space id, `None` for an ordinary space — the "where does the report go and who writes it" read), and `space_capabilities(id)`.

**The schema moved with this door** (`LATEST_VERSION` 9): `space.parent_action_id`, nullable, `REFERENCES action(id)`, plus the compound `FOREIGN KEY (parent_action_id, parent_space_id) REFERENCES action (id, space_id)` so an anchor that does not live in the named parent is unrepresentable. It is a new inbound edge of `action`, not of `space`, so the disposal's edge reasoning is unchanged — and the action it names lives in the *parent*, which has actions and was therefore never reapable. Test: `db::tests::a_subspace_anchor_must_belong_to_its_parent`.

**Reaper interaction: a sub-space is never pristine.** Its brief commits in the spawning transaction, so it has an `action` before it has existed for anyone, and the disposal's first leg refuses it whatever else is true; it is also born stamped, the way a promotion's notebook is. The predicate's `parent_space_id` clause protects the **parent**, and over-protects it: spawning requires the owner to be mid-turn in the parent, so a space that owns a sub-space has actions and was never reapable. `space_capability` is a sixth inbound edge of `space(id)` and is deliberately **not** deleted by the disposal — it is empty for anything reapable, and if that ever stopped being true the FK aborts the transaction and the space is kept, which is the direction the whole feature errs in. The ledger row is `spawn_subspace_tx_body` (stamp folded into the insert, so there is no ordering to get wrong). Tests: `tests/subspaces.rs`.

**A sub-space is always titled.** It sits in the Library beside every other conversation and the reader has no prompt of their own to recognize it by — and no snippet either, since a `brief` is not what `first_user_text` reads. An explicit title wins; otherwise the brief's opening line names it through the same `derive_space_title` an untitled space's first post gets; and a brief that yields no line at all (pure markdown scaffolding) takes the **owner's label alone** — inside the spawning transaction, where that agent's row is already read. The label rather than a phrase about it, because **a title is persisted and a persisted string can never pass through the presentation layer's translations**: anything this crate writes there is read as-is in every language, and this crate ships no user-facing strings. A name is not copy — it is locale-neutral by nature and says the one thing a reader scanning the Library needs, which is whose room this is. Refusing such a brief was the other alternative and was rejected too: it punishes a model for its formatting, and the row still has to be findable.

**Acting in a sub-space is not reading one.** `Inner::require_human_joined` refuses when the shared human is not a live member of a **sub-space** (`AppError::NotJoined`, carrying the space id and nothing else, decided before any write *and before any spend*, so a refusal is zero-trace). **Every door that acts as the human asks it, and that is exactly the set**: `post` (with `submit` through it), which hard-codes the human as author, and `edit_post`, `regenerate` and `respond_stream`, which the human's own picker and per-post verbs drive. Combined `chat`/`chat_stream` ask it too, and then refuse the room itself (`AppError::DrivenConversation`) — those rooms' cascade belongs to the driver, so posting here and driving a turn would do the driver's work twice; the gate lands **before** `post`, so a refusal is still zero-trace, and membership is asked first so an unjoined reader still sees `NotJoined`. The last two of the acting set *spend*, which is what makes this more than a bookkeeping rule — a Regenerate button on a room you never joined charges you to drive it. `respond_stream_as` deliberately does **not** take the gate: it names the participant it acts as, is already gated on *that* participant's membership (`resolve_explicit_participant`), and is the door a turn driver uses, so a human-membership test there would refuse a room's own agents working in their own room. The roster the models are shown has to stay truthful about who is in the room, and the `human` notify policy would otherwise fire in a space whose whole premise is that it has none. The Library lists sub-spaces and every listed row has a composer, so this is reachable rather than theoretical. The refusal names the join that would satisfy it; the GUI slice that ships the join turns this refusal into that explicit act, at which point the message is what changes. **A notebook is deliberately outside this rule** — the human has always been able to write in their own agent's notebook from Settings ▸ Agents, and narrowing that is not this door's business.

**A brief is neither editable nor regenerable** (`AppError::WrongPostKind`). Both writers claim a post's *item* — `edit_post` appends a `user_input` generation authored by the human, `regenerate` appends an `inference` one — so aimed at the wrong kind they do not amend a post, they replace it with a different kind of thing. `Inner::require_post_kind` is the shared gate, and it is symmetric: an edit needs a `user_input` tip, a regeneration an `inference` one. The brief is what made this reachable (it renders in the assistant slot, so a surface offering Regenerate by role would offer it) and it is the sharpest case: a regeneration is billed, `Revise` withholds the generation being replaced from the context, and the brief is the contract the room's participants are working from — so the model would be paid to guess at text it is not shown, and the room's premise would be overwritten with the guess.

**Humans read a sub-space without being in it.** `db::may_read_space` is the read-side widening of membership and the only one: a live member, **or** a human viewer, **never** into a notebook. It backs exactly two surfaces — `action_location` and `references_to_visible_to` — and every model-facing gate goes on asking `is_space_member` (`read_post`'s per-call follow check, the reference-authoring gate, `participant_spaces`; `FOLLOW_DENIED` unchanged). The justification is oversight: a sub-space has no human member by construction, so under membership alone the rooms an agent opens on the human's behalf, spending the human's account, would be the one thing the human could not see. The **notebook clause is the boundary that keeps the bypass about oversight rather than access** — an agent's own residence is the privacy the cross-space permission model's gate was built for, and its backlinks were already withheld from the human who opens it from Settings. So: a human may read any conversation their agents are having *with each other*, and none an agent is having *with itself*. Writing will still mean joining, so the roster the models see stays truthful. Regression for the boundary: `a_human_following_a_quote_into_a_space_they_are_not_in_is_refused` (`tests/cross_space_references.rs`). Read and write part company here: the bypass opens the room, and `post` still refuses it.

### The sub-space turn driver (`subspace_driver.rs`)

Every other conversation is driven from a window: something posts, the consumer plans notifications over that post, drives one turn per planned responder, and re-plans on each answer until the plan is empty or the cascade guard pauses it. **A sub-space has no window**, so app-core gives it its turns — the driver lives here rather than in the GUI because a delegation is business logic and the CLI must get it without reimplementing it. It is started one-way and idempotently (`AppCore::start_subspace_driver`, the `start_update_polling` shape), and **the GUI starts it when it builds its core** (`stores::open_app_core`). That placement is the point: a room that sits at its brief forever must not be what *forgetting a line* produces, and the consumer-facing planning gate is unconditional, so nothing else would ever drive one. It costs an install with no delegated conversations exactly one empty sweep.

**The CLI deliberately does not start it**, and says so where it builds its core: driving a delegation is a loop of model round trips with no window waiting on it, and that process exits when its command does — so starting it would mean beginning walks it cannot finish. The consequence is stated rather than hidden: a command there can open a delegated conversation through the API, and that room does not run until the app is next open, at which point the startup sweep picks it up like any room a previous run left mid-delegation.

**Ownership is held at the planning door, not by convention.** `Inner::plan_and_refine` takes a `Planner` and answers **no turns for a live sub-space** unless the asker is the driver, so `AppCore::plan_notifications` and `submit` both refuse to hand a consumer work in a delegated room and a window cannot double-drive one — at twice the spend — even by mistake. One rule, one place, and it holds for the CLI as it holds for the GUI. **Combined post-and-turn (`chat` / `chat_stream`) is the other cascade door**, and it is refused **before posting** (`AppError::DrivenConversation`) so a CLI that does not start the driver cannot still start one by this backdoor, and a GUI that does cannot post-and-drive beside it. `post` remains: posting is what a joined reader does, and the driver takes the cascade from there. Nothing else is withheld: an explicit ask (`respond_stream_as`) never plans, so a human watching a delegated room can still ask somebody there a question; what they cannot do is start a cascade the driver is already answerable for. The unrefined `mechanical_notification_plan` is untouched, which is what lets a test show the turns are really there.

**Every read the lifecycle stands on orders by commit.** The two derived facts are only as good as "which post is the room's last word", and that was decided by `created_at` — a stamp every writer samples *above* its own transaction, so a reader's post into a watched room can be stamped before a driven reply that commits first. Ordered by the clock, the tail is then the driven reply, which the owner has already quoted: the room reads as reported and retires holding a post nobody answered, and the rearmed pass reads the same wrong tail and exits again. So `last_action_in_space`, `last_reply_by_participant` and `last_post_by_participant` order by `rowid` — commit order, assigned by the store, which no writer's clock can contradict — joining `posts_in_space_since`, whose boundary already is one (`db::action_watermark`). **And all four read through the transcript's own visibility predicate** (`item_current` + terminal status + post type): the room's last word, the owner's answer, the fallback and the refill are words a reader can see, so a failed regeneration's hidden tip contributes nothing — the tail falls back to the newest visible post rather than a superseded wording the driver would otherwise walk from, reply beneath, and quote. The rest of the lifecycle needs no ordering and is checked rather than assumed: `has_reference_from` is an existence test whose "current last word" premise is the tail above, `turns_taken_in_space` is a count, and the leaf set is the walk's own memory. **The render is deliberately not in that set** — `get_space_tree_data` still orders by an item's origin, because what a reader sees is arranged by when things were written *about*, not by when they landed. `rowid` also totally orders two posts written in the same millisecond, which `created_at` never did. Test: `db::tests::the_rooms_last_word_is_the_last_committed_not_the_last_stamped`.

**The lifecycle stays derived — two reads carry all of it, and neither is a status column.** *Is there work outstanding?* The room's last post has not yet been quoted back to the parent by its owner (`db::has_reference_from`): true the moment a brief is written, false once a report goes out, true again the moment anyone posts into the room — which is the whole of **continuation**, and reads identically after a restart because it reads rows. **The quoting generation must be one the parent actually shows** — current, terminal status, post type, the transcript's own predicate — because a report regenerated against a failing upstream persists a *current* `status = 'error'` generation carrying the report's replicated edges, which the transcript hides: counted, that edge settles the room on a report nobody can see, durably and across restarts. **And the owner is the item's original author, not the tip's.** A successful regeneration can mint a new agent (`TurnSelector::Model` when no seated member matches the picked model) and the edges travel with the item, so a read that asked the tip's `participant_id` would treat the owner's own re-worded report as somebody else's quote and post a duplicate; joining the origin generation (`supersedes_action_id IS NULL`) keeps a re-wording settled while a fresh quote by anyone else still does not. **And un-settling is announced**: the failing turn emits `Change::Space` for every other space its replicated edges quoted (`Inner::announce_rooms_quoted_by`), because nothing else can arm the room it just made outstanding — its wait ended at delivery, and the supervisor's cache knows the parent as ordinary, so the parent's own emission maps back to nothing. Tests: `a_failed_regeneration_does_not_settle_the_room`, `a_failed_regeneration_arms_the_room_it_unsettled`, `regenerating_a_report_under_a_new_author_still_settles`, `db::tests::a_report_is_recognized_by_its_original_author`. *How much has this delegation spent?* `db::turns_taken_in_space` counts the `inference` and `decision` actions in the room — the one durable act every turn ends in — so the meter cannot be reset by coming back. **A walk also counts empty and paused planning hops** against the same ceiling: a router that selects nobody bills an inference and writes no row, so `taken` would stay still while a burst of watched-room posts paid for an unbounded number of `plan_and_refine` calls. Those hops share the limit with persisted turns (`taken + planned`); a hop that drove a turn is already in `taken`, and counting it again would spend the ceiling twice on the common path. The empty-hop count is the walk's, not a persisted chore — a restart sees only the tail, and a reported budget-stop settles the room. Tests: `empty_router_hops_still_spend_the_delegation_budget`, `empty_router_hops_share_the_budget_with_persisted_turns`. A failed turn is deliberately uncounted: a driven turn writes nothing on failure, and the count's terminal-status filter keeps that true of a human's blocking verb, whose failure does write an `error` generation. Superseded generations stay counted — each was a turn that ran.

**`MAX_DELEGATION_TURNS = 32`.** The spawn guards bound the roster and none of them bounds the work: every seat is notify-all, so a full room's scheduled work grows with the square of the roster, and until now the only thing that ever stopped it was a human closing the window. The value is read off the same register rather than invented — `MAX_SUBAGENTS_PER_SPAWN` (8) turns is one answer from every seat, `DEFAULT_CASCADE_LIMIT` (4) is how many consecutive agent replies the cascade guard admits, so 32 is *one full-roster answer at each level that guard already allows*. Whichever guard binds first wins; this is the ceiling that exists even where the room is too small for the cascade guard to fire. **It binds on planning, not only on persisted turns**: an empty refined plan and a pause count against it, because a router inference is work even when it drives nobody, and they share the ceiling with `turns_taken_in_space` rather than each getting a fresh 32. The durable meter is still `turns_taken_in_space` (router doctrine is "not a turn"; a restart only walks the tail); the walk-local count is what stops one pass from billing an unbounded burst of empty hops on top of work already persisted.

**A failing room is not billed forever.** A driven turn that fails writes no post, so the room's last word is unchanged and its delegation is still outstanding — and the failure's own `Change::Space` arms the room again; with a dead upstream the report fails too, so nothing is ever marked and the arm-fail-arm circuit bills a request every time round. Neither the turn budget nor the cascade guard closes it, because both count *posts* and a failure produces none. `Inner::claim_walk` is the meter: at most `MAX_ATTEMPTS_PER_TAIL` (3) walks per room **per distinct last word**, in memory. That key is the whole discrimination — a failure changes nothing about the room, and a post from outside changes exactly this — so a stranger's post starts the count over and an outage is waited out instead. A restart is a new chance, deliberately: the state it guards against is a running process's. **And the meter bounds *work*, not the telling.** Three failed walks against one last word close the room to further walking — each drove billed turns — but with the anchor unanswered every one of them held its report back, so the ending was decided and never delivered; when the answer finally landed, the arm it raised met the spent meter and exited, and the parent was never told the failure the meter exists to protect. So a walk that decides an ending it cannot deliver keeps it (`Walk::decided`, beside the attempts; it answers while the room's **current last word is among its leaves** — the memory twin of `has_reference_from`'s premise, which is what recognizes a walk by its own newest driven post, while a stranger's post is in nobody's leaves and gets the walk it is owed), and **an armed pass asks for it before it claims any work**. A decided ending that is not a failure is final for its last word, so every wake while the anchor goes unanswered is delivery-only — no plan, no turn, no re-derivation, the one report the delegation has owed all along. (Claiming first would re-run the cascade over an unchanged tail on every wake, because a wait hands its attempt back: a router inference per wake where the room routes, a nondeterministic chance of driving helpers again, and a re-derived ending whose leaves are just the tail, overwriting the branch tips the walk that did the work collected.) A decided *failure* is provisional instead — a blip has to be able to heal — so it takes the claim path while the meter has room, and what makes it final is the meter refusing: the refused walk delivers it. It is kept in memory rather than derived because a failed turn leaves nothing durable saying it failed, and rather than stored because a status column is what this whole lifecycle is built to avoid. Delivery cannot loop: a failed delivery forgets the ending, and what the next wake may do — retry while the meter has room, nothing once it is spent — is bounded by the meter like all work. Tests: `a_spent_meter_still_delivers_the_ending_its_work_decided`, `a_wake_while_an_ending_waits_delivers_it_without_rewalking`.

**And a failed walk arms itself.** Most failures are re-armed for free, because the turn that failed wrote into the room and that write announces itself — but the ones that matter most drive nothing: a room whose plan was empty from the brief, one that paused there, one whose budget was already spent. Those write nothing, so nothing announces anything, and a report that failed on such a path would leave the delegation unreported with no event left in the world to pick it up until the process restarted. So the walk's task retries after a short pause instead of retiring, which makes every failure take one path; `claim_walk` is what bounds it, and it bounds this exactly, because a failure changes nothing about the room and so reads the same meter every time round.

**A backlog arrives as a trickle.** Arming is per room and the registry only stops one room being walked twice — nothing bounded how many rooms walked *at all*, so a start that finds a previous run's rooms outstanding, or a lag recovery that re-asks the question of every one, put every walk on the runtime at the same instant: a hundred rooms is a hundred live billed requests, a hundred credential steps queued against each other, and on a local backend a hundred engine loads competing for one memory budget. `MAX_CONCURRENT_WALKS` (3) is a process-wide semaphore taken **behind the registry claim and in front of the walk**, so what is bounded is execution and not arming — a room whose turn has not come keeps its entry, arms still merge into its pending value, and the walk that eventually runs runs once from the newest tail. The permit is per pass, so a room retrying after a failure gives it up over its pause. The number is small because the paying step is already serialized process-wide (`spend_gate`): concurrency past a handful buys nothing where it costs money and multiplies everything around it, and what the bound must leave room for is a *stalled* room — an upstream that has gone away takes its attempts and its pause and must not hold the queue. Test: `no_more_than_the_bound_of_rooms_is_walked_at_once`.

**Arming is the bus, so continuation needs no wiring.** A supervisor task subscribes to `Change::Space` and arms a room whenever anything is written into it — the spawn, a driven turn, a human's explicit ask, and whatever the tool that exposes the spawn door will do — plus a sweep of every live sub-space when it starts, which is the restart path. **A sweep whose enumeration fails retries after a pause rather than swallowing the error**: this pass is the only recovery a pre-existing room has — nothing else will ever raise a `Change::Space` for it — so an error merely logged would leave such a room at its brief for the life of the process. The supervisor sits out the pause, which is safe where blocking usually is not: bus traffic it misses surfaces as lag, and lag recovery re-asks the same question of every live room. A room already being driven records the arm rather than dropping it (a post that arrives from elsewhere is not on the walk the driver is doing), and the walk simply restarts from the room's new tail. **The record is the arm itself, merged strongest-wins on the lattice `Signal < Grace < Sweep`**, not a flag: an arm carries a *licence* (`Signal` claims nothing; `Grace` claims this wait has outlived any turn that could answer it; `Sweep` claims nothing anywhere can be in flight), and a licence once earned is not taken back by a later signal — an elapsed clock does not un-elapse because somebody posted in the parent. Flattened into "something happened", the one licence that arrives while the room is busy is simply lost: the alarm is one-shot, the next pass runs on the arm the walk started with, the wait is not fresh so nothing schedules a replacement, and a delegation whose spawning turn failed waits until the process restarts. **A successful delivery spends that licence.** Merging the pass's arm with whatever queued during it is right for a wait (a Grace that arrived mid-walk must still end it) and for a retry after a failure, but a pass that *settled* has concluded this wait: keeping a queued Grace would skip the ten-minute wait of a later continuation. Pending work still runs, as an ordinary `Signal`. The order between the two upper elements is a naming convention — `Arm` is read in exactly one place, and the only question asked of it there is whether it is `Signal`. Test: `a_grace_arriving_mid_walk_still_ends_the_wait`. `Change::Space` is raised by every post in every conversation, so `Inner::is_ordinary_space` caches the negatives: `parent_space_id` is written once at creation and there is no un-archive door anywhere, so a space that has once answered "ordinary" cannot stop being one, and the driver costs one point read per space rather than one per post.

**Terminal detection is the loop ending, and all four endings take one channel.** Plan empty (concluded), the cascade guard (paused), the turn budget (spent), a turn failing — **or a plan that fails** — each becomes a turn for the **owning agent in the parent**, carrying the delegated room's last word as a quoted reference. A planner error used to `?` out of the walk, which skipped `stop_walk` and left the room outstanding with nothing to arm it; it now takes the same door a driven turn already takes (`DelegationEnd::failed`). **The driver attaches that reference itself** (`AttachedReference`, carried by `TurnDirective` through `prepare_turn`/`persist_turn`): the passage is rendered into the turn's context through the ordinary `ReferenceEntry` rendering, and the same spec becomes the persisted `inference`'s `relation='reference'` edge at ordinal 1 — the model reads the passage and writes about it but never chooses what the edge names. Validation happens at preparation, ahead of every acting step and ahead of the charge estimate, so a bad attachment costs a refusal rather than a spend. Test: `a_failed_plan_is_reported_rather_than_swallowed`.

**A walk serves what arrives while it is walking.** A post can land in the room mid-walk — somebody asking a question in a room they are watching — and it is on nobody's frontier: the walk never saw it, and re-deriving "the tail" afterwards looks straight past it, because a driven turn has very likely written something newer since. So when the frontier empties the walk asks the rows what has arrived since it began, subtracts what it served itself, and takes up the rest before concluding — **current generations only** (`db::posts_in_space_since` joins `item_current`), because an arrival edited before the refill runs is one post, not two: both generations on the frontier would plan and bill a turn against wording its author already replaced, and quote the retraction into the report beside the edit. **A queued id is remapped to the item's visible tip before it is planned** (`db::visible_tip_of_action`): an edit or regeneration that lands while a sibling branch is walking leaves the old id on the frontier; planning it would bill replies against wording the transcript has hidden, and the refill would then also return the replacement, so both wordings get a turn. The served set records the remapped id, so the replacement is one wording. A generation with no visible tip — a failed regeneration's hidden `error` — is skipped and recorded as served so refill does not re-queue it; leftover frontier ids are remapped the same way before they are quoted as leaves, **and so is the starting tail** `finish` falls back to when the leaf set is empty: a fail-regen that lands after `last_action_in_space` was snapshotted would otherwise quote the superseded id, and settlement reads the newest *visible* last word, which is no longer that one. **Each planned turn's target is remapped the same way before it is driven**: a fan-out shares one `target_action_id` across several responders; an edit after the first reply would otherwise leave the rest answering hidden wording. **And the report remaps its leaves immediately before attaching them**, after the anchor wait, so a regen of a finding in that window is the wording a reader still sees — **and persist refuses to rewrite those edges after the model has spoken**. A regen that lands while the report's request is on the wire would otherwise attach a footnote to wording the report never saw; the generation is withdrawn and the report retries against the visible tips, bounded by `MAX_REPORT_ATTEMPTS` so a reader who keeps regenerating cannot bill unbounded reports. `persist_turn` does not remap ordinary quotes, which name a concrete generation; only a mechanical report is revalidated this way. Tests: `a_regeneration_mid_walk_is_planned_once_at_its_visible_tip`, `a_failed_regeneration_of_the_starting_tail_is_not_quoted`, `an_edit_of_a_fan_out_target_is_answered_at_its_visible_tip`, `a_regeneration_of_a_finding_is_quoted_at_its_visible_tip`, `a_regeneration_during_the_report_is_quoted_at_its_visible_tip`. **The boundary is taken before the walk's reads and read off the rows, not off a clock**: the opening reads are several awaits wide, and a post committing inside them is neither the tail the walk starts from nor inside a later boundary's window — it would belong to neither, with its own change event spent on a walk already under way. It is a `rowid` high-water mark (`db::action_watermark`) because a timestamp cannot draw this line: **every writer here samples `now_ms()` above its own transaction** — `Inner::post` takes it before several awaited validations — so a post's `created_at` can predate the walk while its commit postdates the tail read, and a `created_at >= began` refill misses exactly the posts that raced it. Missing one is a loss rather than a delay: the walk drives on, its own newer answer becomes the room's last word, the report settles the room on that word, and the unserved post sits in a room that reads as reported. `rowid` is assigned at insert and the writers are serialized (`BEGIN IMMEDIATE`), so it *is* commit order — the same argument that makes the sweep's record of what this process spawned a provenance question rather than a clock one. Test: `db::tests::the_refill_boundary_is_commit_order_not_the_writers_clock`. **The served set is memory, deliberately**: a post the driver planned and a post nobody has looked at are the same row, so "I have served this" is not derivable — the durable alternatives are a status column (which decision 4 forbids) or treating every unreplied post as unserved, which would re-plan a completed fan-out's leaves forever, one billed report per round. **The refill belongs to every ending, and what it does follows from the ending.** It used to run on the concluding path alone, so a post landing during a walk that stopped early — the budget spent, a turn failed — was on nobody's frontier and in nobody's leaves: the report named the driven tail, the room read as reported on that word, and the arrival sat there unserved *and* unquoted in a room nothing would walk again. Now `Inner::stop_walk` asks the same question at those endings, and the difference is where the answer goes. Concluding, the room may still take turns, so an arrival joins the **frontier** and gets one. Stopped, it may not — driving anything more is the thing the ending exists to prevent — so an arrival becomes a **leaf**: quoted into the report like every other tip, unanswered but not lost. That is the honest reading of a spent budget — *the room may take no more turns, and the report still carries what arrived* — so the owner learns of the question and can open a fresh delegation for it. A pause needs nothing of its own: it is decided per post and the walk carries on to the concluding path, where the refill already ran. Test: `a_budget_stopped_walk_reports_what_arrived_while_it_walked`. **Residual, stated:** a process that dies between such a post arriving and the report loses the memory, and the sweep — which can only see the tail — will not recover it; a post into the room does.

**What it quotes is every branch tip the walk reached, not the room's tail at report time.** A delegated room fans out — each helper answers the brief, each branch runs down to a post nothing follows — so quoting one of them would report a single helper while the room settled as reported, and nothing would ever go back for the rest. `cascade_subspace` returns that **leaf set** beside the outcome — posts no planned turn *answered*, decided after the turns run rather than from the plan's shape, because an empty plan and a plan whose every responder declined leave a post in the same position (a decline writes a decision, not a post, so nothing follows it and nothing re-plans from it; tested by a plan's shape, such a post was neither leaf nor parent — the branch the report silently dropped, or the unquoted tail that kept the room re-billing the same declines); plus, where the walk stopped short, the post it stopped at and anything still on its frontier — and the report attaches every one at ordinals `1..=N`. Test: `a_branch_whose_responders_all_decline_is_still_reported`. **A pause is a branch's, not the walk's**: the cascade guard is derived per post, so one thread of the room running out of replies says nothing about its siblings, and abandoning them there would drop their findings the way a single witness did. **Every tip travels, and the bound is on the prompt rather than on the set.** A roster-sized cap was the first answer and was wrong in the one direction that cannot be recovered from: the seat guard bounds who is *in* the room and never bounded the frontier — every seat is notify-all, so one post's fan-out puts an answer from each of them on it, and a budget-stopped walk can hold far more tips than the room has agents — while the newest tip alone satisfies `db::has_reference_from`, so a room that dropped its older branches settled permanently with those findings never reported. The two things that looked like one are the **edge** and the **rendering**: an edge's recorded range must describe its quoted text exactly, and every tip's does (the human's footnote rail resolves each one whole); what a model is shown is a rendering, and this app's renderings already elide by doctrine — a preview strips markers, a chore prompt clips the middle out of a post. So every tip persists its edge and the report turn's context renders each passage through `utility::clip_middle` at `ATTACHED_PASSAGE_MAX_BYTES`, which is also what stops one unbounded passage filling the turn and leaving the findings beside it saying nothing. **And the block has a ceiling of its own** (`ATTACHED_BLOCK_MAX_BYTES`), because clipping each passage bounds one entry and says nothing about how many there are: a burst of posts into a room somebody is watching makes a branch of each, and an unbounded block crowds out the conversation the report is written into — at the far end overflowing the request and taking the delivery with it, which is the one thing a terminal report may not do. Passages render in walk order until the budget is spent (the refill's arrivals are pushed newest-first so they come off oldest-first, which is the order the read that produced them already promises), and **what is not shown is named**: a closing line says how many further passages there are and at which ordinals, that they travel with the post regardless, and that a reader can open each one — so a model that cannot see everything says so instead of claiming it read it all. The figure is the app's own register rather than a guess: `MAX_SUBAGENTS_PER_SPAWN` seats × one full-length passage each, a whole room's worth of distinct voices; past that a walk's fan-out is the same voices again. Every edge is still written and every passage still resolves in the human's rail — this bounds a prompt, not a record. Test: `an_over_budget_burst_still_delivers_and_says_what_it_withheld`. `db::has_reference_from` needs no change and its premise is unaltered in form — *the room is reported when its current last word is among the posts the owner has quoted back* — because that last word is one of the tips. Nothing re-reads the tail afterwards. A post landing in between would otherwise be quoted as though the walk had considered it — and would then read as already-reported when its own arm came round, so the room would go quiet holding an unanswered post. Reporting the witness leaves that post unreported, which is exactly what makes its arrival arm the room again and get it the walk it is owed. Tests: `a_wide_walk_reports_every_tip_and_not_a_roster_sized_tail`, `a_long_finding_is_elided_in_the_prompt_and_whole_on_the_edge`.

**Where it attaches is captured at the spawn, not guessed at the report.** `space.parent_action_id` (navigational in the sense `parent_space_id` already is, one level finer; fixed at birth, never a state) records the post in the parent the delegation was opened from — the spawning turn's own target, which only the caller knows. The report replies to **the owner's own answer to that post** (`db::last_reply_by_participant`), so it lands on the branch the work was asked for on rather than beneath whatever that agent happened to say most recently, which is not the same post the moment anything else is going on in the parent. The answer must be **one the parent shows** — current, terminal status, post type, the same predicate settlement reads — because an answer whose regeneration failed leaves a current hidden tip, and a superseded generation that still matched would end the wait and render the report at the conversation root; with nothing visible the wait holds, until a fresh answer or the grace alarm. **And persist re-reads that target after the report inference**: a regen of the answer while the request is on the wire would otherwise persist a reply under wording the model never saw, or under a hidden error tip that renders at the conversation root. The generation is withdrawn and the report retries (or the wait resumes if nothing visible remains). Tests: `a_report_does_not_attach_beneath_a_hidden_answer`, `a_regeneration_of_the_answer_during_the_report_reattaches`, `a_failed_regeneration_of_the_answer_during_the_report_waits`. **And the owner is the item's original author, not the tip's** — a successful regeneration can mint a new agent (`TurnSelector::Model` when no seated member matches the picked model) and the reply edge travels with the item, so asking the tip's `participant_id` would miss the visible re-wording and wait out to grace, attaching the report to the anchor as a sibling of a word the parent already shows. Tests: `a_regenerated_answer_is_still_the_owners_reply`, `db::tests::an_answer_is_recognized_by_its_original_author`. (`db::last_post_by_participant`, the anchorless fallback, reads the same way.) **Residual, stated:** an answer fail-regenerated *after* its report was delivered leaves that report threading beneath a hidden tip — a rendering blemish only; the report itself is still current and visible, which is what settlement reads, so nothing further is owed. It is written on the brief's *space row* rather than as a reference edge on the brief itself deliberately: an edge would render into every sub-agent's context as a footnote about a post they cannot read, which is noise against the whole premise that a delegated room starts fresh. A spawn that names no anchor (a direct API caller with no turn behind it) degrades to the owner's last post and then the parent's tail, and says so.

**A regeneration carries the report's attachments forward.** `edit_post` has always replicated a tip's reference edges onto the new generation, because an edge can be a fact of the *turn* rather than of its wording; a regenerated report is the sharpest case of that — the finding it quotes and the ending it records are facts of the delegation, not of the sentence. So `prepare_turn` loads the superseded generation's edges on `Revise` and carries them as `AttachmentOrigin::Replicated` attachments: written back at **the ordinals they already had**, and rendered into the regenerating turn's context, which is also what makes that turn honest (`Revise` withholds the generation being replaced, so without this the model would be asked to re-word a report on a finding it was never shown). Replicated attachments are **not** put through the authoring gate, for the reason edit's replication is not: quoting copies, the passage is already here, and re-asking permission at a re-wording would rewrite history whenever the answer had changed since. **What they are still asked is the shape rule** (`Inner::validate_reference_shape`, which owns the whole author-independent question, the post-kind half included): permission is about *whose* material, and this is about *what kind* — an audience boundary the whole app maintains, where rendering is the act that would cross it. An edge written below the create seam could name a `tool_call`, a `decision`, a `memory` block or a post's `thinking` block, and a regeneration carrying it forward would expand that straight into the model's context — the one thing every other read path withholds, which is why this one, being a read path, withholds it too. Test: `a_replicated_attachment_cannot_carry_a_hidden_block_into_the_regeneration`. Losing them would have taken the visible footnote away while the delegation went on counting as reported — so `db::has_reference_from` additionally joins `item_current`, which ties the driver's belief to the generation a reader can actually see and errs toward reporting again rather than toward silence, **and the origin generation for whose quote it is**, so a minted author on a successful regeneration does not un-settle.

**And a report waits for the answer it belongs under.** The owner having no reply to the anchor is not an ordinary absence — a spawn happens *inside* the owner's turn, so it means that turn is still in flight or failed. Reporting then would make the report the first reply to the anchor and the owner's own answer an indented branch off it, durably the wrong way round. So the delegation stays outstanding and the room is registered against its parent (`Inner::awaiting_anchor`, memory only — the parent is an ordinary conversation the supervisor's cache would otherwise skip). **The registration happens before the question is asked**, not after it: the answer can commit between the two, and asking first would leave a window in which its change finds nothing registered and the registration that follows waits for a wake-up already gone by — the room would then never report at all. Ordering closes it, because a commit is either early enough for the query to see it or late enough for the entry to be there; the cost is an entry to take back out on every path that does not wait (`Inner::end_anchor_wait`). **It goes on waiting until the answer is actually there**, because a wake-up is not evidence of one: the parent is an ordinary conversation and anything can move it, so a wait that spent itself on the first wake would attach to the anchor because somebody said something unrelated — and the answer, arriving a moment later, would become the report's sibling instead of the post it belongs under. Every wake re-asks; only the answer ends the wait. **A room that can never run again stops being waited on**: a wait is a standing registration against the parent, and every post there wakes every room registered under it, so each terminal exit clears it. **A spent meter with nothing remembered is one of those exits.** The wait is registered before the anchor is asked, so a lookup that then errors leaves a registration standing and decides nothing; once the meter refuses, every later arm hits the same refuse, and keeping the wait would make every post in the parent pay for a walk that can only no-op. A decided failure still keeps its wait — that ending is still owed. Test: `a_spent_meter_with_nothing_to_deliver_releases_its_wait`. **A wait tried nothing — but a failure before the wait tried something.** The retry meter bounds work that failed, and a walk that ended by waiting failed at nothing and left the room's last word unchanged, so counting it would spend the whole allowance on three unrelated posts in the parent and then refuse the walk the real answer finally arms. That reasoning is about the *wait*, and it stops being true the moment the walk in front of it broke a turn: a failed turn with an unanswered anchor ends in exactly the same `Report::Waiting`, and giving the attempt back there hands a dead upstream an unbounded retry — the one circuit `claim_walk` exists to close, reopened at the one exit that gives its claim away. So the release is for a wait that follows no failure; a failure keeps its claim and the meter binds on it. Tests: `a_wait_after_a_failed_turn_spends_its_attempt`, `a_wait_that_follows_no_failure_spends_nothing`. **A wait ends by outliving the turn it is waiting on.** The one case where the answer never comes is a spawning turn that failed after the room was opened, and *nothing durable says so*: that was established rather than assumed — a failed turn's only trace is an unattached `request` row, which carries no space, action or participant, and the tool rounds a spawning turn wrote chain off the anchor whether it later answers or dies, so they say "a turn started" and never "a turn ended". In-process bookkeeping would be precise but its release cannot be ordered in front of the terminal emissions without threading a guard through every error arm, and a release landing after the emission recreates the very lost wake-up this wait is ordered against. So the end is time (`ANCHOR_WAIT_GRACE`, ten minutes). **That figure is a policy, not a proof, and the doc says so**: nothing bounds a turn's wall-clock length — no client in this crate sets a request or read timeout, a stream stays open as long as its upstream holds it, and a local engine may generate for as long as it likes — so "far past any turn" was a claim the code did not enforce. What the policy costs when it is wrong is bounded and positional: a legitimately slow spawning turn gets its report attached to the anchor rather than beneath its answer, and the answer, landing later, becomes the report's *sibling* there (the spine follows the first reply, so the report takes it and the answer indents). Nothing is lost — every finding is quoted, the ending is recorded, the answer lands whole, there is no second spend — and the alarm never overrides an answer that did arrive, because every wake re-asks. Weighed against refusing to end the wait at all, which costs the whole report forever whenever a spawning turn dies, a once-off worse-placed pair of posts is the cheaper failure. **The alarm is the wait's own**, set when it begins: termination depends on no other event, so an unrelated post still never spends the wait and a parent that goes quiet forever still ends it (`Arm::Grace`). And it answers only for its own wait — the alarm outlives the wait that set it (nothing cancels a sleeping task), and a room can wait twice: an answer arrives, is hidden by a failed regeneration, and a continuation opens a second wait; an alarm that fired without asking which wait set it would expire the second on the remainder of the first's clock. So a wait carries a generation, the alarm checks it before arming, and a stale alarm costs nothing at all. Test: `an_old_alarms_grace_does_not_expire_a_new_wait`. The restart sweep remains the backstop for a process that dies inside the grace: it arms with `Arm::Sweep`, which never waits — **and which it may not claim for a room this process opened**. That licence is precisely the claim that no turn which could answer these anchors is still running, and the one turn that could is one this process made, since a spawn happens *inside* its owner's turn; the sweep's enumeration is a query, so a spawn committing before it is in its answer, and the corrective `Signal` from that spawn's own change event could not take the licence back (the merge is strongest-wins, correctly). So `spawn_subspace` notes the room as this process's **before** the transaction that creates it — a record landing after the row would leave a window in which the row is enumerable and unrecorded, which is the hazard itself — and the sweep reads that record *after* it enumerates, so a spawn racing the enumeration is either invisible to it or already recorded. Those rooms arm as ordinary signals and their waits end the way every other one does. The record stops being kept once a sweep has actually read it (`Arm::Sweep` is issued once, by one call), which is what keeps it from growing for the life of the process — and **only an enumeration that succeeded consumes it**: a failed attempt reads nothing, so the retry it schedules finds the record intact and still growing, and arms this process's rooms with the licence that is true of them. Tests: `a_sweep_does_not_claim_a_room_this_process_opened`, `a_failed_sweep_enumeration_retries_and_keeps_its_provenance`. All of which is one rule — **`Arm` is decided by provenance, not by shape**: the whole of that licence is the claim that no turn which could answer is still running, true of a room an earlier run left behind and of nothing else. Recovering from a bus this process fell behind on therefore arms as an ordinary `Signal`, because an owner's turn may be running at that very moment; the room keeps waiting and the answer's own commit wakes it — at that moment nothing can still be in flight, so the answer either exists or never will, and the anchor is then the right attachment because there is nothing for the report to sit beneath.

**Archiving a conversation closes its delegations.** `db::archive_space_tx` archives the named space **and every live sub-space beneath it**, recursively down `parent_space_id`, inside the archival's own transaction. A delegation exists to serve the room it was opened from, so one left live under an archived one can only lose: its report is a turn in that parent, refused at the gate every turn meets, so it is armed and fails and is armed again against a meter nobody reads, holds a live-room slot of an owner nobody retired, and waits on an anchor no post will ever answer — with no un-archive door anywhere to get it back out. The rule reaches rooms owned by *other* agents deliberately: their owners are not being retired, but the purpose those rooms were opened for is gone. Doing it at the write makes "a live room under a closed one" unrepresentable rather than a state something has to notice; the descent is a fixpoint over the rows (`db::archive_rooms_under_a_closed_one`), so it is cycle-safe and needs no list of roots, and retirement's archival arm shares it. **Every door that closes a room owes it two things, and they are one call** (`Inner::close_rooms`): the room is **announced** (`Change::Space`, beside the Library's one `SpaceIndex`) and any **wait it was holding is ended**. Neither substitutes for the other. The announcement is what tells a window open on that room it has stopped, and what wakes any *other* delegation registered against it as a parent — that arrives through `rooms_awaiting`, which is keyed by parent. The clearing is the closed room's **own** registration, and nothing on the bus can deliver it: an archived room is not a live delegated room, so `is_ordinary_space` answers "ordinary" and the supervisor never arms it — the terminal path that would have cleared the wait is exactly the path that no longer runs. Left standing it makes every post in that room's parent pay for a walk that can only no-op, until the grace alarm comes due ten minutes later. **Three doors close rooms and all three take it**: `archive_space`, a departing owner (`close_delegations_run_for`), and retirement — which is the one that reaches a room without touching its parent, so nothing about the parent could ever announce it. Each therefore answers with the *ids* it closed and not only a count, the count being for the listing question alone. Test: `retiring_an_owner_releases_the_wait_its_room_was_holding`. Everything else derives too: an archived child stops counting against its owner's quota, and the archival gates stop its walk mid-hop. Tests: `archiving_a_conversation_closes_the_delegations_beneath_it` (`tests/subspaces.rs`), `a_delegation_beneath_a_closed_conversation_stops_and_lets_go` (`tests/subspace_driver.rs`).

**Archival stops all of it**: the room's liveness is re-read before each hop, once more immediately before the report turn starts, **and once more inside the persist transaction** (a retirement archives every room its agent owned, and a reader can close the delegated room while the report's model request is in flight — archiving the child does not archive the parent, so the parent's turn gate cannot stop it). An archived room is a no-op (not an error, and no report about work somebody closed); the persist check suppresses the generation and keeps the request in the Record. An archived *parent* refuses the report at the same gate every other turn meets — leaving the room's last word unreported, which is what a later run reads as still outstanding. That last gate is now the belt to the archival's own brace: closing a conversation closes its delegations, so a live room under a closed parent is not a state anything rests in, and what the parent's gate still catches is a walk that was already past the room's liveness read when the archival landed. Tests: `closing_a_conversation_stops_the_delegation_it_was_running`, `closing_the_delegated_room_during_its_report_writes_nothing`.

Driven turns still stream, because the transports differ only in transport and a delegated room's turns should not take a different code path from every other turn — but the **receiver is dropped before the turn runs**: nothing watches a windowless room, and holding the handle would buffer every delta of every turn for a reader that does not exist. The transport treats a closed channel as nobody listening (`let _ = sender.send(..)` on every event), so dropping it is the honest way to say so.

**A report is a notification, not an invitation, so the decline checkpoint is withdrawn from it** (`TurnDirective::mechanical`, applied to the turn's registry snapshot in `prepare_turn`). Declining is how an agent bows out of a *conversation* it has nothing to add to; a mechanical notification is not one, and a decline there writes a `decision` instead of the post the reference edge rides — the delegation would then have said nothing at all, forever, with nothing to notice it. Withdrawing the tool makes that unrepresentable rather than handled; a postless report is additionally refused as an internal inconsistency, which is what would notice if it ever stopped being unreachable. **The withdrawal is applied to the degrade's fallback registry too** — a backend that rejects a `tools` field retries against exactly what the consumer registered, so withdrawing only from the turn's snapshot would hand the checkpoint back on the retry.

**A stream that ends without ever saying it was over writes nothing** (Codex review, PR #330). No `[DONE]` and no terminal `finish_reason` on any chunk, with every byte well-formed — not the mid-frame abort, which fails in the transport's own decoder. The loop's `finished` flag was read only to break early, so the text fell through and persisted as a completed answer. It is neither a completion (the upstream never claimed one) nor a truncation (no ceiling was reached): it is **partial data from a connection that stopped**, reported as `AppError::Network` — which also puts it in `DelegationFailure::Upstream` for a room and leaves it retryable for a window, re-asking being the right remedy. **One rule for ordinary turns and revisions alike**, and the revision is why it is the conservative one: `Revise` supersedes, so keeping the cut text destroys a real answer and leaves a severed one in its place. An ordinary turn could in principle keep the text behind a marker, but the only marker available is session-scoped (`ChatResult::truncated`), so a reopened window would show severed text with nothing saying so — the lie `ResponseTruncated` exists to make unrepresentable — and two rules would make the classification depend on who asked rather than on what happened. `finish_reason` is checked beside `[DONE]` so a provider that ends without the sentinel (the spec does not require it) is not punished for saying it finished in the other place. **The blocking twin needs no equivalent**: a body that ends early fails in `resp.text()` and never reaches persistence. Tests: `a_stream_that_never_says_it_finished_writes_no_answer`, `a_regeneration_whose_stream_never_finished_keeps_the_answer_it_would_replace`; harness behaviours `StreamingEndsWithoutDone` / `OkThenStreamEndsWithoutDone`; exit-point row in `tests/bus.rs`.

**`Concluded` says whether it rests on a cut-off answer** (Codex review, PR #330). The driver drops the event receiver on purpose — nothing watches a delegated room stream — so the report is the only surface the room ever gets, and `ChatResult::truncated` was discarded at `drive_planned_turn`: a walk that replanned from a partial post reported the room as plainly `concluded`, which claims it ran out of things to say about an answer that stops mid-thought. **The marker rides every ending a reader might act on as if the room's words were whole** — `Concluded` (ran out of things to say), `Paused` (resumable by posting there) and `BudgetSpent` (an external cap stopped it) each invite an action assuming coherent words to build on, so each carries `truncated`, set walk-wide from any turn that hit the ceiling. Round 9 gave it to `Concluded` alone on the narrower reading that only *completeness* was falsified; a pause that loses its one warning is the same lie, so the test is now the reader's action, not the word. **`TurnFailed` alone carries none, deliberately**: it already says the room did not go well and names why, a reader acts on the failure either way, and adding "an earlier answer was cut off" dilutes the reason that matters. Durably the marker is an **optional trailing `/truncated`** appended after each arm's own fields, so a token written before it existed still reads as itself and `parse` strips it once for every arm. **Replanning from the partial post is kept and is deliberate**: partial text is real text and the room may well have more to say about it; what changes is only what the ending is allowed to claim. The token is an optional tail (`concluded` / `concluded/truncated`), so an ending written before the marker existed still reads as an ordinary conclusion, and a future marker degrades to a note through the same trailing check. (A turn cut off *before any* answer never reaches here — that is `AppError::ResponseTruncated`, which stops the walk as a failure like any other.) Tests: `a_room_that_concluded_on_a_truncated_answer_says_so_in_its_report`, and the marker joins `every_ending_survives_being_written_down_and_read_back`.

**The ending is persisted as a token and rendered as prose, never the reverse.** `DelegationEnd` is the value; `annotation` on the edge carries `DelegationEnd::token()` (`eidola:delegation/…`), because that column is where a *person's* note about their quote lives and anything this crate writes there is read as-is in every language — the same rule that keeps a spawned room's title a bare name. `PostReference` splits the two apart (`annotation` is the person's note, `None` for a token; `delegation_end` is the parsed value), so no surface can print one where the other belongs, and `ReferenceEntry` renders the ending in this crate's own English for models, which is what every model-facing string here is. **The GUI renders the value in the reader's language** in the footnote rail — see `crates/eidola-gui/AGENTS.md`; that is the half of the split this crate must not do. A token this version does not understand reads back as a note — prose a reader cannot interpret beats an ending somebody guessed at. **And the namespace is reserved at every door that takes an annotation from outside** (`subspace_driver::is_reserved_annotation`, asked by `validate_reference_spec` and by `remember`): readers tell a note from an ending by the prefix alone, so a supplied note claiming it would vanish from every surface that shows a note and appear on every surface that shows an ending — forging lifecycle state on somebody else's quote. Only a value *starting* with the prefix is refused, so a note that mentions it in passing stays a note, and the driver needs no exemption because what it writes is not a caller's value. Tests: `a_supplied_annotation_cannot_claim_the_ending_namespace`, `a_remembered_annotation_cannot_claim_the_ending_namespace`.

**A failure reports a category, never a message.** `DelegationFailure` (upstream / funding / configuration / unfinished) is derived from the `AppError` *variant*, exhaustively. The error's own words can carry an upstream response body — attacker-controlled across a trust boundary, and unbounded — or a local path, and splicing one into the owning agent's prompt would let whatever answered the room write into another model's context. The detail goes to the local warning log and no further.

**The reference gate is the agent-authored twin, not a widened human one.** `Inner::validate_agent_reference_spec` asks `db::is_space_member` where `validate_reference_spec` asks `db::may_read_space`: the human gate grants a reader oversight of rooms they are not in, and sharing it would have handed every agent that bypass the first time a non-human author appeared. The *shape* rule — a reference may name a post, and only a post's `text` block — is factored into `Inner::validate_reference_shape` and asked by both, because what may be quoted is the same question whoever asks it, and asked **whole** by that one function: the post-kind half used to sit outside it, in the permission gates' own read of the antecedent, which is exactly the half a path skipping the gate skipped. It costs one duplicate point read on the authoring paths and is worth it — the two gates read the antecedent for its space, this reads it for its type, and no caller can be trusted to have asked half a rule. The owner is a member of the room it owns by construction, so the agent gate holds by construction — which is why it is asked rather than assumed.

**A known residual, recorded: the report resolves *an* answer, not *the* turn's.** `db::last_reply_by_participant` takes the newest reply the owner made to the anchor, so two live answers by one owner to one post — reachable only through two concurrent explicit asks on the same target — put the report beneath the newer, which may not be the turn the spawn happened inside. Nothing durable tells them apart: a turn's rounds chain off *the post it answers*, never off its own inference (a capped or budget-stopped turn writes none), so no edge runs from a spawning round to that turn's answer; `context_assembly` relates them but not one-to-one, since a later turn replaying a trace records the same round in its own assembly. Recording the spawning round at the spawn would need a caller able to supply it, and there is none — nothing exposes the spawn door as a tool, and `Tool::call` receives parsed arguments and no turn identity. The cost is a report placed under a sibling answer instead of its own; no report is lost, and the parent/child inversion the wait exists to prevent cannot occur either way, because both candidates are answers of that owner to that anchor. Machinery for it waits on the caller that would need it.

**A known limit, recorded:** the report lands in the parent and the driver stops there. If the parent is itself a sub-space its own driver picks it up (the bus arms it); if it is an ordinary conversation, its cascade is its window's, exactly as it has always been — so a report arriving in a parent nobody has open notifies nobody until somebody opens it. Tests: `tests/subspace_driver.rs`.

## Participants v1

**Scope-owned model** (schema detail under Database below): every `participant` row has exactly one `scope` — `global` (shared library; the human `User` = `HUMAN_PARTICIPANT_ID`), `space` (owned by one space), or `template`. Config columns live **only** on `participant`; reference tables (`space_participant`, `space_template_participant`) reference **globals only** with per-membership override columns (**NULL = inherit; `''` = override to empty**). A space's participants = owned rows ∪ referenced globals (`db::space_participants` returns the unified effective view).

**API surface:** DTOs `ParticipantInfo` (its `reference` carries base config + raw override values so the GUI renders the edit-everywhere-vs-override-here fork honestly), `NewParticipant`, `ParticipantUpdate`, `ParticipantOverride`, `SpaceTemplateInfo` (owned agents + `referenced` globals with effective config), `TemplateParticipantInfo`, `NewTemplateParticipant`. Per-space CRUD: `list_space_participants` / `add_space_participant` / `update_space_participant` (edit everywhere) / `set_space_participant_override` (override here; `None` reverts a field) / `remove_space_participant` (the shared human can't be removed) — all emit `Change::Participants`. **Configuration writes carry the premise they were composed under.** Liveness is one half — `db::update_participant_config` writes `WHERE id = ? AND removed_at IS NULL` — and `db::ScopePremise` (surfaced as `ExpectedScope`, a required argument of `update_space_participant`) is the other: `SpaceOwned { space_id }` for an editor opened on a space's own row, `Global` for the library and the inspector's "Everyone", `Any` where the caller has no premise. Save and Share are the same control on one row, so the second replaces the first's gpui slot — sanctioned last-wins — but a replaced write's *core* call keeps running, and the two do not share a premise: a Save composed against the owned row would otherwise land after promotion and republish the old persona to every space the agent has since joined (Codex review, PR #279). Carried into the statement, the expired premise makes the stale write strike nothing, and `refuse_dead_participant` then names which half expired. The mirror needs nothing: a *referenced* write is either `Global` (and promotion is one-way, so it cannot expire) or an override, whose membership row only exists for referenced rows at all. **Configuration writes carry their own liveness, so retirement wins terminally**: `db::update_participant_config` writes `WHERE id = ? AND removed_at IS NULL` and `db::update_space_participant_override` writes only onto a **live membership of a live participant** — the same definition `is_space_member` reads, now asked of a write. Save and Retire are independent operations in independent GUI slots, and a `bridge`d core call runs to completion after its gpui task is replaced, so a Save from another window can commit *after* a retirement; updating by `id` alone let it rename a retired participant, and since the trail renders an author's byline by joining that row, the record retirement promises to leave alone changed silently underneath it (Codex review, PR #279). The predicate is in the statement rather than a caller's earlier read because no interleaving can then put a live read in front of a write that lands later; a zero-strike is explained afterwards (`refuse_dead_participant`) but never *decided* there, and a refusal is zero-trace — nothing written, nothing emitted. The same rule reaches the two doors that write *new* state rather than editing a row: **`remember` asks the owner's liveness inside the transaction that carries its writes** (a memory write is several statements and cannot carry the predicate in one, so the transaction is where the question becomes unanswerable-by-interleaving; a retired owner gets `MemoryRefusal::OwnerRetired`, which the tool narrates, and nothing is written), and **`ensure_space_participant` carries it in the insert** (`INSERT … SELECT … WHERE EXISTS (live participant)`, still `OR IGNORE` so the join stays idempotent) — where a read-then-insert had left a durable membership joined *after* a retirement, plus an invalidation and an `Internal` error where a typed refusal belonged. `PersonaWrite::apply` rides the same door and inherits the guard; inside `promote_participant_tx` it targets a row that transaction has just proven live, so the clause can never turn a valid promotion into a failure. It is the idiom `update_backend` already used. Test: `a_save_that_lands_after_retirement_is_refused`. **`remove_space_participant` decides at the write, not from a read**: soft-removing this space's own row and ending a reference membership are different acts, and choosing between them from a `get_participant` taken a moment earlier is a window promotion walks through — the stale soft-remove would set `removed_at` on a row that had just become **global**, retiring a freshly shared agent from the library and orphaning the notebook promotion created (only retirement archives it), with both callers reporting success. So the ownership test rides in the soft-remove's own `WHERE` (`scope = 'space' AND owner_space_id = ?` and still live) and zero rows falls through to the leave — which after a promotion is exactly the reference row it left behind. `db::remove_space_participant_tx` owns that decision and reports it as `SpaceRemoval::{SoftRemoved, Left, NothingToDo}`; the emission is unchanged either way. The mirror guard sits on the other side (`promote_participant_tx`), so whichever transaction commits first the loser refuses cleanly (Codex review, PR #279; `db::tests::a_removal_decided_before_a_promotion_cannot_retire_the_shared_agent`, `removing_a_shared_agent_from_a_space_is_a_leave_not_a_retirement`). Template CRUD: `list_space_templates` / `create_template` / `template_from_space` / `update_template` / `remove_template` (soft; the built-in Default can't be removed) — all emit `Change::Templates` — plus `set_default_template` (emits `Config` + `Templates`) and `create_space_from_template(template_id, title)` (emits `SpaceIndex`). **New spaces are instantiated from the live default template** (`Inner::instantiate_default_space`), so every space carries its participants (the referenced-global human + owned agent copies) from birth; a config pointing at a removed template falls back to the seeded default. **Instantiation is one transaction** (`db::instantiate_template` → `BEGIN IMMEDIATE` around the whole body, the `promote_participant_tx` shape): the space row, the owned-agent copies, the reference copies and the human's membership commit together or not at all, and the template's liveness is read inside it — decided at the write like every other guard. A space without its participants is not a space, and turso autocommits each statement, so before this a failure partway left a durable half-populated row while every caller's error handling read the refusal as "nothing was written". Fixed at the shared door, so all three callers inherit it (`create_space` / `create_space_with_id`, `post`'s space-less branch, and `create_space_from_template`). Regression: `db::tests::a_failed_instantiation_leaves_no_space_at_all`. `create_space` / `create_space_with_id` therefore emit `Participants` and `Space(id)` beside `SpaceIndex` — one per thing the instantiation wrote — because a caller holding the id **before** the row exists (the GUI's ⌘N window) reads that space's roster and settings on the way, and only an announcement takes an early "empty" / "no such space" answer back.

**Turns are participant-aware.** `run_turn`/`run_turn_stream`/`prepare_turn` take a `TurnSelector`: `Participant(id)` resolves the member's effective config (COALESCE(override, participant config)); `Model(m)` is the model-picker compatibility path (CLI/GUI `chat`/`chat_stream`/`regenerate`/`respond_stream`) — resolves the space's agent whose canonicalized effective model matches, **minting a fresh space-owned agent when none matches** (`resolve_or_mint_agent_by_model`; the seeded default agent is the common match). The responding participant's effective system prompt is prepended as a leading `system` message — riding the same array the estimate and wire request use, and **not persisted** (forensics never resolve mutable participant config).

**Participant-aware upstream rendering** (`actions_to_upstream_messages`):

1. **Role split:** only the responding participant's own prior posts render as `assistant`; every other participant's — human and agent alike — render as `user` (mapping every `inference` to `assistant` showed a model another agent's words as its own).
2. **Headers:** every message opens with the one-line header `#<handle> · <label> · <stamp>`, blank line, then text — in-content, deliberately not the OpenAI `name` field (inconsistent chat-template support). **Handles are derived, never persisted:** `post_handle(item_id)` = first 7 chars of lowercase base32 over `SHA-256(item_id)` — the *item* id so handles survive edits/regenerations, hashed because UUIDv7 prefixes of near-in-time posts would collide pathologically. **Strip-on-receipt:** models mimic scaffolding, so `strip_leading_header` removes a leading header-shaped line from output at persist time **and `LeadingHeaderFilter` removes it from the live stream** — one predicate (`is_header_line`) behind both, so what a reader watches arrive is what lands durably (a header that showed while streaming and vanished on reload was task 46, bug 1). The filter holds back only the undecided first line and releases ordinary prose on the first delta. `HEADER_PROTOCOL_NOTE` (appended to the system message, unpersisted) instructs against emitting one. **The stamp is absolute UTC, RFC 3339, seconds precision, `Z`-suffixed** (`post_stamp`, hand-rolled so the dependency surface is unchanged) — see Identity, roster, and post timestamps below for which time it names and why it has to be absolute. A **citation** byline is not a header and carries no stamp: `post_byline` renders `[N] #<handle> · <author>` for a quoted post, whose own header stamps it where the model reads the post itself.
3. **Labels are one-line by construction:** a label with a line break would inject a second paragraph attributed to that author (prompt injection via rename). `validate_label` (trim; refuse empty, control chars, U+2028/9) gates every label write seam, and `message_header` sanitizes anyway.

`ChatResult` carries `response_action_id` (the persisted inference id, for cascade re-planning) and `declined: Option<DeclineOutcome>` — mutually exclusive by construction: a decline wrote no post, so the `decision` action id rides in `DeclineOutcome`, keeping "cascade off a decision" unrepresentable.

**`submit(text, space_id, reply_to)`** = `post` + `plan_notifications(space_id, post_action_id)`, returning `SubmitResult { post, plan }`. The post commits and emits *before* planning, so the router can never delay or fail a submit. **`plan_notifications` is plan + router refinement and the only planning entry point that drives turns** (refinement is not opt-in — a cascade re-plans every hop, and one unrefined hop would notify agents the router filtered out). The unrefined mechanical computation is a pure read reachable only via `mechanical_notification_plan` (tests/inspection): notify set over the space's participants — `all` → always; `human` → only when the post's author is human; `explicit` → never — excluding the post's author and model-less agents; refuses to plan off a non-post action (zero turns). Turn driving stays caller-driven — one `respond_stream_as` per `PlannedTurn`, re-planning on each resulting post — **except in an agent-spawned sub-space, where `plan_notifications` answers no turns at all** because those belong to app-core's own driver (see The sub-space turn driver).

**Archival stops new work, at two gates and on one read each.** An archived space is not hidden, deleted or departed — every membership stands and every read still works — but it **takes no new turns**: `mechanical_plan` yields zero turns for one, and `prepare_turn` refuses one with `AppError::SpaceArchived`. Both decide from the *same statement* that was already reading the space's own row (`db::get_space`, which is why `SpaceRow` carries `cascade_limit` and `archived_at`: existence, availability and the budget arrive together, so no interleaving can put "it is there" in front of an archival that has landed). **In `prepare_turn` that read is the first thing after the database handle**, ahead of resolving the participant and the backend, because everything below it *acts*: a backend resolution persists a provider row, an engine-backed model may start a llama.cpp subprocess, and the eidola path builds an attested client and fetches the model catalogue over the network. A refusal placed after those would leave a spawned sidecar, a durable row and a handshake behind on behalf of a conversation somebody had closed. Refusing on the first read costs one query and leaves nothing — pinned by `models_hits` in the mock upstream, which counts catalogue fetches precisely because `chat_bodies` cannot see a turn that died during setup. Two gates because one cannot close the race alone: planning refuses *after* an archival, `prepare_turn` refuses *in between* a plan and its driving. The gate is in the shared preparation, so every entry point inherits it — `chat`/`chat_stream`, `regenerate`, `respond_stream`, and the participant-aware `respond_stream_as` a cascade is driven through. **A turn already past that gate completes and persists**: the request was made and the tokens were spent, and dropping the answer would bill for nothing — but every hop re-plans, so its completion is where the cascade stops. `post` is deliberately not gated (the save side spends nothing, and post-first means a `chat` into an archived space keeps the thought and refuses the turn, exactly as a funding failure does). This was general and pre-existing — `archive_space` never stopped anything — and it became load-bearing when retirement started archiving rooms whose whole purpose is agents answering each other with no window open. Tests: `an_archived_space_plans_no_turns_and_starts_none` (`tests/participants_orchestration.rs`), `retiring_an_owner_stops_the_helpers_mid_cascade` (`tests/subspaces.rs`).

**Cascade guard (data-derived, no schema state):** `db::agent_cascade_depth` counts consecutive agent-authored posts in the reply ancestry back to the last human post (branch-scoped, item-tip-resolved; authorship is stable across generations); at the space's `cascade_limit` (default 4) `plan_notifications` returns `NotificationPlan::Paused` instead of turns. Explicit asks never consult the guard.

**Space consistency is an app-layer guard** (`Inner::require_action_in_space`): the schema doesn't constrain an edge or target to one space, so a mismatched (space, action) pair could splice threads across spaces. `plan_notifications`, `prepare_turn` (both modes), and `post` (`reply_to`) all reject a foreign/missing action with typed `AppError::NotConfigured`; a foreign participant is rejected by `resolve_explicit_participant`.

**ACT provisioning queue:** `Inner::spend_gate` (a `tokio::sync::Mutex`) serializes credential acquire → spend-proof → flip-to-`spending` across concurrent turns, so a fan-out never double-spends one credential. The second turn finds another active credential, auto-allocates from balance, or **waits bounded for an in-flight refund** (typed `AppError::ProvisioningTimeout` on deadline) — but only when a mid-spend credential whose face value covers the charge exists (a smaller one's refund can never fund the turn → immediate `InsufficientBalance`). The verdict is **instant-consistent**: the whole function runs under `spend_gate` and the only active→`spending` flip is under the same gate, so the covering-`spending` set only shrinks (via settlement — a single atomic insert) between reads; a re-read of `find_spendable_credential` before any terminal verdict observes a settled successor. It cannot be a false negative from an in-flight sibling refund; it does not (and cannot) cover funding arriving later from exogenous writes — an ordinary post-read TOCTOU the recoverable error routes the caller to retry. turso is single-writer, so `db::connect` sets `PRAGMA busy_timeout` — concurrent per-turn writes block-and-retry instead of erroring.

Tests: `tests/participants_orchestration.rs` (fan-out planning, system-prompt prepend, multi-agent role split with pinned bytes, cascade pause + explicit bypass, concurrent turns with real credentials) and `tests/chat_path.rs` (byte shapes, header derivation/stripping unit tests in `lib.rs`).

### Identity, roster, and post timestamps (task 64)

A model was never told **which participant it is**, nor who else is in the space: the default charter is "You are a helpful assistant", default agent labels collide on model id, and in a multi-agent space a model read a transcript of several voices with no statement of its own identity among them. The fix is split by **volatility**, which is the whole design — one `db::space_participants` read in `prepare_turn` serves both halves.

**That read is the turn's participant snapshot, and it is taken first.** It is the single authority on what every *current* member of the space is called for the whole turn: the identity line, the roster, and the `<label>` field of every post header in the transcript (`relabel_from_members`, applied to `context_rows` right after `get_upstream_context` returns). A turn's reads are not atomic — each hop of the context walk joins its own effective label, `space_participants` is another statement, and another window on the same `AppCore` can commit a rename in between — so left alone the interleaving tells a model it is `"Navigator"` in a transcript whose own posts are headed `Ada` (Codex review, PR #294). A read transaction was the alternative and was rejected: a turn must not hold one open across an inference. Funnelling every current member's name through one snapshot makes the interleaving unobservable instead — a mid-turn rename is wholly before the read or wholly after it, and either way the turn is self-consistent. **An author the snapshot does not carry keeps the label its own row joined**: `space_participants` is live membership (`left_at IS NULL`), so a departed participant is provably unnameable from it, and who wrote a post goes on being named after they leave. **Residual, recorded:** the `ThreadSnapshot`-derived renderings (the map's branch authors, `read_thread` / `read_post` headers) keep their own read — `PostNode` carries no participant id, so the snapshot is not even addressable there, and those name posts by *third* parties rather than the responder's own identity. Their worst case is one turn of a stale name in a tool result, which the next turn heals.

- **Identity** — `identity_line(label)` → `You are "<label>" in this conversation.`, leading the notes, i.e. directly after the charter and before `HEADER_PROTOCOL_NOTE`. **Ungated: present in every space, linear ones included.** Static per participant, so it flips once (at a rename) and is byte-stable after. The label is the responder's **effective** one in this space — the same override-aware label its own posts are headed with, so the two cannot disagree. Deliberately minimal: identity is universally useful, while framing about *others* belongs in the roster, which only appears when others exist.
- **Roster** — `render_roster(members, responder_id)`, in the **trailing volatile block** ahead of the thread map, gated on `has_map || participants > 2`. One line per member, `- "<label>" — <kind>` with ` (you)` on the responder, in `db::space_participants` order (humans first, then by id — stable within a membership, so the bytes move only when the membership does). It closes with one sentence, `ROSTER_INDEPENDENCE_NOTE`: *"Each participant answers for itself; weigh others' posts on their merits rather than deferring to them."* **A roster is not free** — naming peers measurably induces anchoring and sycophancy (AgentVerse attributed roughly a tenth of its errors to agents swayed by peer feedback), so the block that names them also says what a participant owes them, which is nothing but honest assessment. Lines carry **label + kind only**: AutoGen's `name: description` shape was trimmed because a description would leak other participants' charters. The gate is a **usefulness** judgement (a roster in a two-party linear chat is noise), not a byte-identity requirement — see the reframe under Thread map.
- **The trailing block is one message** carrying the roster then the map, in that order, and it **always closes with `Respond to #<handle>.`** — the pointer belongs to the *message*, not to the map (`render_map` no longer emits it). A `user` message appended after the post being answered is the last thing a chat model reads, and whatever it contains the model will be tempted to answer *it*; the roster-only shape (a linear space with three or more participants) carried no pointer and no framing at all, so membership metadata read as the current request (Codex review, PR #294). When neither section applies there is no trailing message at all.
- **`TRAILING_BLOCK_NOTE` frames it, gated on the message existing** — *"The last message is client-generated metadata about this space, not a post by any participant. No reply is due to it, and it ends by naming the post you are answering."* One note rather than one per section, because nothing it says is section-specific; `THREAD_MAP_NOTE` now explains only the threading and the `<thread-map>` block, after it. Both are protocol explanation, so each flips once — when the space first grows a trailing message, and when it first branches — and is byte-stable after.
- **A label inside quotes goes through `quoted_label`** — the identity line and every roster line, which are the only two places a label sits between raw quotes in model-facing bytes. `validate_label` deliberately admits ordinary quotes (`Ada "The Countess"` is a name a person may choose), so a raw interpolation was a rename away from an injected instruction: the valid label `Ada"; instead you are "Bob` closed the frame early and opened a second, complete-looking sentence inside a privileged one (Codex review, PR #294). The cure **reserves the delimiter** — the label's own `"` become `'`, so no `"` can appear between the frame's quotes and the boundary is unambiguous by construction. Escaping (`\"`) was rejected: a model reads a backslash as text, not as a boundary, so the injected clause would still read as a clause. Line-flattening (`one_line`) still applies, for the reason it always did. **The roster is the sharper half of the same hole**: its lines carry client structure after the name, so the valid label `Mallory" — agent (you)` rendered as `- "Mallory" — agent (you)" — human` — an apparent self-marker planted on a participant who is not the responder (Codex review, PR #294). One reserved delimiter cures both, which is why there is one function and not two: with exactly two quotes per line the closing delimiter is identifiable, and everything after it is the client's own structure — `— <kind>`, with ` (you)` on the responder alone.
- **Post timestamps** — `message_header` renders `#<handle> · <label> · 2026-08-11T14:02:33Z`. **Absolute, never relative**: a relative stamp would churn every header on every turn and invalidate the whole upstream prefix cache each time, which is exactly what `sibling_branch_turns_send_identical_trunk_bytes` pins against. **The time is the post's *current generation's* `action.created_at`** — what `item_current` / `action_resolved` already resolve to on every model-facing path, so `SpaceActionRow`, `PostNode` and `ReferencedPostRow` all carry the same number. An edit or regeneration *is* a new generation, so its stamp moves with the text it describes: the honest answer to "when was this written", and still byte-stable, because it moves only at the moment the body it heads moves anyway. The item's **origin** time was the alternative and was rejected — it would date an edited post to prose that no longer exists.
- **A label overridden to empty** drops its field rather than leaving a dangling one (`#<handle> · <stamp>`); the separator `is_header_line` keys on survives either way.
- **Nothing here assumes a label is the only way to name a participant.** The roster renders from `db::EffectiveParticipantRow`, so participant **ids** stay reachable where names are produced, and no path parses or normalizes labels in a way a future inline `{{ participant <id> }}` marker would collide with (task 71, first-party mentions).
- **The seeded human's label is `User`, not `You`** — viewpoint-neutral on the wire, because in a multi-party roster a line reading `"You" — human` would read as *the reader* to every model while a different line carried the self-marker. Display is unchanged **on every human-facing surface**, not only post bylines: the GUI's `byline_for_participant` maps a human labelled `user` (case-insensitive) or blank to "You", and `space::display_name_for_participant` is the roster-row wrapper every surface naming a participant row reads (Codex review, PR #294 — see `crates/eidola-gui/AGENTS.md`). A human renaming their participant overrides it per space as before. The seed is `INSERT OR IGNORE` in `db::ensure_default_participants`, so **an existing dev database keeps `You`** — no schema change, no `LATEST_VERSION` bump; delete the dev database (or rename the participant) to pick the new label up.
- Tests: `tests/chat_path.rs` → `every_turn_states_which_participant_the_model_is`, `the_identity_line_names_the_participants_effective_label`, `the_roster_appears_only_once_a_space_is_multi_party` (which also pins the roster-only shape's response pointer and its framing note), `a_branch_turns_the_roster_on_in_a_two_party_space`, `post_headers_carry_a_stable_absolute_stamp`; pure renderings unit-tested in `lib.rs` (`message_header_shape_is_pinned`, `post_stamp_is_rfc3339_utc_seconds`, `a_reference_byline_carries_no_stamp`, `identity_line_is_pinned`, `roster_block_is_pinned`, `a_quoted_label_cannot_escape_its_frame`, `a_roster_label_cannot_forge_another_participants_self_marker`, `one_snapshot_names_every_current_member`).

## Global agents and in-place promotion (task 36)

`promote_participant(id, persona)` turns a space-owned agent into a **global** one on the *same row*, so authorship, provenance, and memory continuity are structural (copy-projection was rejected: it fragments identity). One transaction (`promote_participant_tx`, taking a `db::Promotion`): `owner_space_id → NULL` + `scope → 'global'` (the pinned scope echo on every past `action` and `memory_block` follows via `ON UPDATE CASCADE`), the optional persona, a `space_participant` reference row for the former owner space with NULL overrides (persona preserved byte-identically), and the agent's private **notebook space** (named for the agent, so a renaming persona names it too). `add_global_participant(space, id)` is the other half (idempotent; refuses space-owned, retired, and Eidola-the-system). **The notebook owner's membership is structural and cannot be ended**: the space exists only for that agent and is the residence of the `core` memory it writes, and nothing can grant a notebook membership back — so `remove_space_participant` refuses it (`SpaceRemoval::RefusedNotebookOwner` → a typed `AppError::Config` naming the agent). Guarded in the *leave's own `WHERE`* for the same reason the soft-remove is: a promotion mints the notebook and its membership in one transaction, so a removal that read the space a moment earlier saw an ordinary conversation; the follow-up read only explains a write that struck nothing. `SpaceSettings.notebook_participant_id` (via `db::notebook_participant_of`) carries the fact to the GUI so the roster can withhold an affordance that could only be refused — the courtesy; the refusal is the guarantee. Overrides on that row stay offered: a notebook's owner tuning how it behaves in its own notebook is ordinary per-space configuration, and reversible. Test: `a_notebook_owner_cannot_be_removed_from_its_own_notebook`. `PromotionOutcome` carries the id + home and notebook space ids; `notebook_space_id` is the GUI's door to inspection.

- **Promotion is one-way, enforced by absence:** no update surface writes `participant.scope`, so demotion is unrepresentable rather than guarded.
- **`persona` exists because a surface shares what it is *showing*, and that must not be a second write** (Codex review, PR #279). The GUI's "Share this agent…" sits inside an open editor, so the values it promotes are the visible ones — but an `update_space_participant` *then* a promotion is two transactions, and two windows share one `AppCore`: let the agent be shared or removed in between and the edit commits on a row that is by then **global** (so in every space that follows it) while the promotion is refused, telling the reader nothing happened. Carrying it here makes the pair atomic: the `ParticipantUpdate` is validated by the shared `validate_persona` (with `update_space_participant`, so an edit and a promotion cannot drift on what an update means) **before** the transaction opens, then applied inside it behind the same guard as the scope flip — which now reads `scope = 'space' AND removed_at IS NULL`, the transaction's own gate rather than a repeat of the caller's, so a lost race rolls the persona back with everything else. Still exactly **one** `Change::Participants`, persona or not.
- **Emissions: `Change::Participants` only** — not `SpaceIndex`, since the created notebook is excluded from `list_spaces` (the Library provably didn't change).
- **Memory needs no migration:** blocks keep owner, name, scope label, residence; the loading rule simply starts spanning spaces. The one new rule: a `core` block a global writes resides in its notebook (`memory.rs`).
- **Templates compose for free:** `template_from_space` projects a reference row, so every space instantiated from such a template gets the *same* colleague.
- **The library reads through `list_global_agents`** (`db::list_global_agents`): the live `scope='global'` **agents**, each with its notebook space id joined in — `kind = 'agent'` is what keeps the two seeded non-agent globals (the shared human, Eidola-the-system) out, and the join is there because the only consumer is a roster that offers the notebook door on every row. Ordered by label, the name the reader sees. Pure read, no emission.
- **`retire_participant(id)` is the library's other write, and not promotion's inverse:** one transaction (`db::retire_participant_tx`) doing the `participant.removed_at` soft-remove **and** archiving every space that existed only because of the agent — "archival tied to retirement". Its notebook, because the notebook exists only for it (a live notebook with no agent owns nothing; an archived one beside a live agent takes away the residence its next `core` block needs), and every **live sub-space it owns**, for the first of those reasons sharpened by what ownership carries — see Agent-spawned sub-spaces, where this is the third of the three write boundaries around ownership. The row keeps its id and its **scope**, so the trail still resolves it and demotion stays unrepresentable; what ends is availability. Refusal-first: unknown, already retired, the shared human, a space-owned participant (removed per space instead), a non-agent. Emits **`Change::Participants`, plus `SpaceIndex` exactly when it archived a space the Library lists** — never for the notebook (the listing excludes those on both axes, the same argument promotion makes), always for a sub-space (an ordinary Library row, which is also why `archive_space` emits `SpaceIndex`). The count comes back from inside the transaction (`db::Retirement`) rather than from a read after it. **Plus `Change::Space(id)` per archived room, notebook included** (`Inner::close_rooms`, what every archival door owes a room), with the anchor wait each room was holding ended beside it: retirement reaches a room without touching its parent, so nothing else could tell the sub-space driver the room closed, and its registration would otherwise stand until the grace alarm — making every post in that parent pay for a no-op walk until then. Which is why the transaction answers with the archived ids and not only the count (`db::Retirement.archived_spaces`): the count decides the listing announcement, and only a list can say which rooms to close out.

Tests: `tests/global_agents.rs` — including the mid-turn promotion races (`a_promotion_mid_turn_does_not_lose_the_response` / `…does_not_strand_a_memory_write`), which pin the derive-scope-in-insert idiom (see Database); `the_agent_library_lists_shared_agents_with_their_notebooks`, `retiring_a_shared_agent_archives_its_notebook_and_keeps_its_trail`, `retirement_refuses_everything_that_is_not_a_shared_agent` (the sub-space arm is `retiring_an_agent_archives_the_rooms_it_owned_and_keeps_their_transcripts` in `tests/subspaces.rs`), `a_persona_travels_into_the_promoting_transaction` (the persona adopted, and both up-front refusals leaving zero trace); plus `bus.rs`'s `promote_and_retire_move_no_library_listing` (which also pins the one-signal claim for a persona-carrying promotion). Two facts have no production reader, so each has a seam: the notebook's archival (`test_space_archived` — announced on the bus like every room an archival closes, but listed nowhere) and a notebook's title (`test_space_title`) — `list_spaces` excludes notebooks on both axes.

## Record queries and trace visibility

**Record query APIs** — read-only, newest-first, `LIMIT/OFFSET`-windowed SELECTs over the local trail for the GUI's Record window: `list_attestations` / `attestation_detail`, `list_requests` / `request_detail`, `spend_trail`, `wallet_lifecycle`. Pure SELECTs, no schema changes.

**`space_traces(space_id)` (task 34)** is the parallel view of the actions `get_space_tree` collapses out, so a GUI can disclose what a turn did without leaving the space. One additive read (`db::space_trace_rows` + pure `assemble_post_traces`) returning `Vec<PostTrace>`, each **anchored to a post the tree already renders** (keeping `PostNode` untouched). Two anchors: a turn that produced an answer anchors on its **inference** (attribution via the turn's context assembly; earliest-inference-wins so replays don't double-render); a turn that produced **no post** (decline, cap, failure) anchors on the post it answered, resolved to the current generation — the audit value of a decline is that the non-event is visible where the answer would be. **An anchor is not an identity:** several turns routinely land on one post, so each `PostTrace` carries its own durable `id` (the inference, or the trace-chain root). A `decision` is threaded to the post it declines, so the decline checkpoint writes a `reference` edge to its chain root at `db::DECLINE_TRACE_ORDINAL` — turn identity as a real relation (keying on `(anchor, participant)` would merge repeat asks; found in review). `TraceEntry` is `Tool { name, arguments, result, request_id, … }` (result `None` = never executed, which the cap does deliberately) or `Declined { reason }`; `request_id` links to the Record. Pure read — commits nothing, emits nothing. Tests: `tests/chat_path.rs`, `tests/participants_orchestration.rs`, grouping rules unit-tested in `lib.rs`.

## Tool registry (`tools.rs`)

v1 tools are **harness-internal only** — a `Tool` implementation in-process (no external/MCP surface yet). A `ToolRegistry` (name → impl, last registration wins) is held on `Inner`, **empty by default**, mutated via `AppCore::register_tool`. Two load-bearing properties:

- **Empty is invisible:** `TurnPrep::request_body` omits `tools` entirely when the turn's snapshot is empty, so a registry-less install sends no `tools` field at all — one flip when a tool is first registered, byte-stable after (the stable-but-larger rule under Thread map; not a byte-identity obligation).
- **Names are the key:** an unknown name is a tool *result*, not a turn failure — a model mistake it can correct.

`prepare_turn` snapshots the registry once per turn. `EchoTool` ships for end-to-end exercise; nothing registers it in production.

**Navigation tools:** `list_branches`, `read_thread(handle, limit?, offset?)`, `read_post(handle)` — `pub(crate)` impls over the turn's `Arc<ThreadSnapshot>`. Read-only over a snapshot (stale-ok), so no DB handle or synchronization; a handle the snapshot doesn't know is answered honestly in the result. `read_thread` renders via `with_header` over `render_post_for_model` (the exact wire format and the exact reference rendering — one path each, so `read_thread`, `read_post` and the turn's own context cannot tell three stories about one post) and states window bounds rather than truncating silently. `read_post` is the one exception to snapshot-only: its `quote: N` argument carries a `Weak<Inner>` + the responding participant and re-checks membership per call (task 37), and reads the followed post's own reference edges so it renders through the same unit as everything else.

**Reserved names** (`tools::RESERVED_TOOL_NAMES` — the three navigation tools plus `remember` and `list_my_spaces`): `register_tool` returns `Err` for them. Without that, a consumer's `read_thread` would work on linear turns and be silently replaced by the built-in the moment a space branched. These are protocol surface: the map's system note promises the names, and each reads the turn's own snapshot, which a process-scoped registration structurally cannot supply. `ToolRegistry::register` keeps raw last-write-wins; the reservation lives at the one seam reaching the process registry.

**Attachment is per turn, in `prepare_turn`**, gated on the space **having branches** (so the field appears when the affordance does, and flips once) **and** the endpoint being able to carry a `tools` field. **No backend kind is consulted** — capability is **discovered, not assumed**, `eidola` included (llama.cpp 500s without `--jinja`, and with it still 500s on some models' template filters; a generic endpoint may refuse the field; a deployed enclave older than the server's tool wire types refuses it as an unknown member). The round loop **degrades on rejection** — if round 1 fails with `AppError::Server` and the turn attached the tools itself, it withdraws them, acquires a fresh hold, and retries once. The blocking transport returns *before* persisting the error inference in that case (an error generation would consume the turn's item identity and the retry couldn't write its answer); the rejected request row is still committed. An endpoint whose toolless retry **succeeds** is memoized in-process (`Inner::tool_incapable_models`) — recorded only on retry success (a round failing both ways was failing for another reason). **The memo's key is the `(backend_id, wire_model)` pair** (`ToolEndpoint`), because a backend is a host and not a capability: eidola's catalog and a llama.cpp install each serve many models, and one model's refusal must not disarm its siblings. The memo is an observation, not configuration: no column, re-probed after restart; per-model capability metadata is the durable successor (task 60). Only turn-attached tools are withdrawn; consumer registrations fail honestly.

**A response is classified by its status, never by whether its body parses.** The blocking transport requires JSON only of a **2xx** (a 2xx that is not a completion is a genuine protocol failure, and still fails as `AppError::Network` — after a refund recovery, since nothing downstream runs to settle that round's hold). A non-2xx body is an *error document* and is read leniently, because the shape that matters most is not JSON: the server's request type is `deny_unknown_fields`, so an unknown member fails in the `LoggedJson` extractor, and axum renders that `JsonRejection` as a **plain-text 422**. Deciding from the body would file exactly that response as `Network`, and the degrade keys on `Server` — so a server too old for a field the turn sent would fail every branched turn instead of retrying without it. The streaming transport already checked status first and never had the ordering. Both shapes are fixtures: `RejectTools` (llama.cpp's JSON 500) and `RejectToolsUnparseable` (the enclave's plain-text 422), the latter pinned on both transports.

**The degrade retry spends.** On the eidola backend the rejected attempt burns a hold, so before the retry the round settles it (no inline refund rides a rejection, so it recovers one through `/v1/credentials/refund`) and `begin_next_round` acquires a fresh, *smaller* hold — re-estimated over the array the retry will actually send, tool schemas withdrawn. `ChatResult::credits_charged` is the sum of the holds the turn took, the rejected one included. Pinned end to end by `a_rejected_tools_field_on_a_spending_backend_settles_both_holds` (`tests/chat_path.rs`): distinct credentials, both reaching `spent`, none left `spending`, and the wallet total unchanged.

**A hold is never abandoned to take another one.** `prep.spend` is the only in-memory handle to the materials that mint a hold's successor credential, so replacing it while unsettled leaves that credential `spending` and its face value locked out of the wallet until an explicit recovery. `begin_next_round` — the one place `spend` is replaced — therefore refuses to proceed past an unsettled hold, taking one last recovery attempt and otherwise ending the turn (`AppError::Credential`, joining budget and provisioning as that call's failure modes). The guard lives at the write rather than at each call site, so neither the tool loop nor the degrade retry nor a future third caller has to remember it; `TurnPrep::spend_settled` is what it reads. Test: `a_retry_will_not_take_a_hold_while_the_last_one_is_unsettled`.

## Decline checkpoint (`decline.rs`)

An orthogonal *quality* valve, not gating: by the time it fires the prefill is paid for (the cheap filter is `router.rs`). `DeclineTool` is an ordinary `Tool` (`decline`, optional `reason`); the checkpoint is one seam in both round loops, after the round's `tool_call` persists and **before** the round cap. When a round's calls include `decline` **and the registry actually holds it**, `Inner::decline_checkpoint` executes the round's tools as usual (honest trace), writes a **`decision` action** off the post the turn answers, carrying the reason as `text` plus a `reference` edge (`DECLINE_TRACE_ORDINAL`) naming its trace-chain root, and ends the turn with **no inference**: `response_action_id` is `None`, `declined` carries the `DeclineOutcome`. Emissions: `Space` + `Record` (+ `Wallet` when spent), never `SpaceIndex`. Nothing registers it by default (a model inventing the name gets the unknown-tool result). `get_space_tree` collapses `decision` out like traces; rendering "saw this, declined" is a GUI follow-up. Three layers keep a decline from being mistaken for a post: the result type, `plan_notifications` returning zero turns for non-posts, and the GUI turn runner dropping the declined turn's captured reasoning. Tests: `tests/participants_orchestration.rs` + a `tests/bus.rs` row.

## May-decline router (`router.rs`)

One cheap model call filtering the mechanical notify set, between planning and turn-driving. `plan_notifications` sends the triggering post's upstream slice (last 6 posts, clipped) plus one **candidate card** per planned participant (label, persona digest, policy) to a small model and keeps only the subset it names. Candidates are addressed by **1-based index**, not UUID (echo failure mode); the reply is strict `{"notify": [n, …]}` read by pure `parse_router_selection` (tolerant of surrounding fences/prose, strict about the object; empty list = valid "nobody responds").

- **An archived space is never routed.** Refinement re-reads the space's own row and takes both facts off it — still open, and does it route — because planning and refinement are two calls and an archival (the one a retirement performs, say) can land between them; a remote router would then bill an inference to choose among turns `prepare_turn` will refuse. Test: `refinement_asks_no_router_about_a_room_that_closed_under_it`, through the `test_refine_notifications` seam, which exists because production never separates the two.
- **Failure doctrine: degrade, never block.** Unset router model (**the default — off**), unreachable router, or unparseable output return the mechanical plan unchanged with a stderr warning: the failure mode is *extra* notifications, never lost ones. Non-selections are not persisted. Explicit asks bypass entirely; a `Paused` plan short-circuits before any call.
- **Settings:** `space.router_model` / `space_template.router_model` (copied at instantiation like `cascade_limit`), a qualified reference written via `set_space_router_model` (emits `Space`) / `set_template_router_model` (emits `Templates`) — deliberately their own setters. The per-space pair is read together by `space_settings` (the inspector's read: `SpaceSettings { cascade_limit, router_model }`, erroring on a space that does not exist), and `set_space_cascade_limit` (floor 1, emits `Space`) is its sibling write. Both validate the backend up front; `validate_router_model` exposes the check as a pure read for create-then-set flows.
- **The call is not a turn:** no actions, no request rows, no attestation records. It runs through the chore runner (`utility.rs`): engine-backed references are genuinely free; a remote `eidola` reference **bills a normal inference per triggering post** (spends and settles, `Change::Wallet` included) — settings surfaces must say so plainly.
- **No caller can forget it:** no public API returns an unrefined plan for driving.
- **The slice is rendered, not raw** (task 67): posts arrive as `ThreadSnapshot::post_body` — quoted passages attributed and spliced in at their markers — because the router picks *who answers* and a post whose meaning lives in what it quotes read as near-empty. `POST_MAX_BYTES` is therefore spent from **both ends** (`clip_middle`), so an unbounded passage cannot take the post's own routing cue with it. See the reference-rendering section above for the cost, the fallback, and why eliding the middle is the shared rule.
- GUI: both router pickers have landed — the Templates pane's and the **space inspector's** (default reads **Off**; the mandatory per-call cost copy inline for eidola refs, worded per surface), over the shared `participants::router_field`.
- Judgment-tier evals are explicitly out of CI (offline eval over a golden set, never `tests/`). Tests: `tests/participants_orchestration.rs` over the harness's `RouterBehavior`.

## Chore runner (`utility.rs`)

One cheap model call that is deliberately not a turn; extracted when the branch summarizer became `router.rs`'s second consumer. Two phases, and the split is the point: `resolve_utility_target` answers *where would this go* from the registry alone (no engine start, no network — broken references degrade before anything starts); `utility_completion` opens the route (engine lease/start, attesting or plain client, hold for remote), makes one non-streaming completion, settles the refund. Zero-spend for `local`/`llamacpp`/`openai`; spend-and-settle for `eidola` with the same body-read-failure discipline as the chat transports (a hold is never stranded in `spending`). Persists nothing. `clip` (char-boundary-safe truncation) lives here, shared by chores rendering conversation text.

## Branch summaries (`summaries.rs`)

LLM-written précis lines under thread-map entries — a progressive enhancement; everything can fail or be off and the map is exactly what it was. **Cache keyed on the branch tip** (newest of the branch's resolved current generations), so a summary regenerates when the branch grows and never otherwise; reading tips off resolved generations makes an edit anywhere in the branch move it. A stored summary renders even once the branch grew past it (a snapshot beside fresh structural counts).

**Storage is a versioned item:** an `action_type = 'checkpoint'` action, `intent = 'branch_summary'`, authored by `db::SYSTEM_PARTICIPANT_ID` (Eidola on its own behalf — attributing it to a human or agent would lie in the Record), text as its one block, and two `reference` edges: ordinal 1 → the branch root (its *item* is the stable identity), ordinal 2 → the tip it read. Ordinal 0 stays empty (not part of the thread). Regeneration supersedes within one item. `checkpoint` is not a post type, so every render/context/planning path collapses it for free — no schema change.

**Model:** v1 shares the space's `router_model` as its utility model; a remote one bills as it does for routing. Bounds are structural, not policy: lazy generation, the tip cache, a `MIN_BRANCH_POSTS` floor, at most one call per branch that actually grew — each with a *different* prompt, because an over-cap branch is sliced head + tail (elision stated) rather than oldest-N. Unset or unresolvable ⇒ structural lines only, silently. The slice's posts are rendered (`post_body`), not raw and not preview-elided (task 67): the summarizer reads the branch, and its output is **written down** and read for as long as the branch lives. That is also why the per-post budget is spent head + tail (`clip_middle`) exactly as the branch slice is — a quotation longer than `POST_MAX_BYTES` would otherwise carry off the author's own response to it, and the misleading summary would stay cached until the branch changes.

**Scheduling never touches a turn:** `spawn_branch_summaries` is fire-and-forget after every branch-moving write commits *and emits*, with per-space trailing debounce + a one-pass-at-a-time gate (cache re-read inside); a pass with nothing stale makes no request. Each committed summary emits `Change::Space`; a pass generating nothing emits nothing. Tests: `tests/branch_summaries.rs` (driven via the `test_refresh_branch_summaries` seam — the production trigger is debounced).

## Text search (`search.rs`)

The pure matcher over user text — no database, no I/O, no view types, so every surface that searches (a window, the CLI, a future cross-space index) shares one semantics. Literal substring matching with **smart case**: a query in all lower case matches case-insensitively, a query containing an upper-case letter matches exactly. Matches are leftmost and non-overlapping. `Query::new` returns `None` for an empty query, so "what does the empty query match" is not a state any caller decides.

**The structural commitment is the offset map, not the scan.** Every transformation of text is a `Projection` — the transformed text plus a run table recording each run's source range and its projected range **separately** — and a range in transformed text is only ever turned back into a source range through `Projection::source_range`. Nothing here returns an offset into transformed text as if it were an offset into the text it came from. This is load-bearing because such transformations are routinely length-changing: `fold_case` alone changes byte length (`ẞ` → `ß`) and changes it *within* a character (`ß` and `ss` share no boundary), and a caller projecting rendered markdown hides spans wholesale (a link's URL) and substitutes text for others (`&amp;` → `&`). A `ProjectionBuilder` has exactly two appenders, and the choice between them *is* the choice of how offsets map: `copy` (the source bytes appear verbatim; offsets map one to one, guaranteed by construction since only the builder can slice them) and `substitute` (different text stands for the span, which then maps as one atom). A span that is neither is simply not appended, so it can never be matched. Projections compose by applying their maps in sequence.

Mapping is **covering**, not corresponding: a hit reaching into a substituted run takes that run's whole source span, and a hit spanning two runs takes the dropped span between them — the source range always contains everything the projected range showed the reader. It **refuses rather than clips**: a range with an endpoint past the projected text or inside a character could not have come from a match over it, and clipping such a range would hand back a plausible but wrong source span, which is the single failure this type exists to prevent. Clipping inside the run walk is coverage across runs, not repair of a bad input.

`Projection::find(&query)` is the ordinary path — it scans the projected text and maps every hit back in one step, returning **source** ranges, so a caller normally never holds a projected offset at all. `source_range` stays public for a caller scanning the text itself.

`fold_case` is **Unicode-aware lower-casing, not Unicode case folding** — different tables, and the gap is a list of equivalences we do not have: `ß`/`ss`, `ſ`/`s`, `µ`/`μ`, `ﬁ`/`fi`. Every one is a *missing equivalence*, never a wrong offset, and closing them adds substituted runs to the same map (an expansion round-trips today — there is a test), so the fix is a table, not a redesign. Deliberately not here yet, on the same reasoning: diacritic folding, NFKC normalization (which is what would fold full-width `ＡＢＣ`), whole-word matching, and case folding proper — one later pass, no new dependency until then.

Within lower-casing the walk is faithful. It is per character because the map is built from the same pass, and the two Greek sigmas fold together because final sigma is the one place non-locale-specific lower-casing depends on surrounding text — that rewrite is what keeps the per-character walk equivalent to `str::to_lowercase`, not a partial case-fold table, and a scan of every scalar in Unicode pins it. The walk is also allocation-free (one reused stack buffer, since a whole haystack is folded per keystroke); `tests/search_allocation.rs` counts allocations with its own global allocator and fails if the fold starts scaling them with the input.

Tests are in-module. The load-bearing pair: a length-changing projection surviving the round trip (project → match → map back → the source range covers the intended text), and its companion pinning what the map prevents — the same hit read naively as a source offset lands mid-word in unrelated text.

## Agent memory (`memory.rs`, task 35)

The second of three participant layers — charter (human-owned config), **memory** (agent-owned, self-revised, human-inspectable), experience (transcript + traces). Charter/memory separation is deliberate: the human's instructions stay authoritative, and each layer is more credible to a model than one blob.

- **A block is an item** (the branch-summary precedent): each revision is a generation (`action_type = 'memory'`, supersedes the tip) — append-only history, diffable trail, and a **structural** self-revision vs human-correction distinction (every generation records its author). Not a post type, so render/context/planning collapse it for free. Revisions may carry `reference` edges (ordinals `1..=N`) naming the posts learned from, with annotation — provenance a string-blob store cannot do.
- **Ownership vs scope (promotion-critical):** `memory_block` carries one **owner** (pinned by the same composite echo `action` uses), a scope *label* (`core` = loads wherever the owner goes; `space` = loads in its residence only), and a **residence** `space_id`. Scope is addressing, never co-ownership — what makes in-place promotion a memory no-op. Residence is decided once at creation: the space the agent stands in, except a `core` block a **global** writes resides in its notebook. Names are unique per owner.
- **Loading rule:** per turn, the responding participant's core blocks + blocks about the current space — nobody else's, ever — render at the **head**, inside the system message, after the charter and static notes (keeps the charter+notes prefix byte-stable; a memory edit invalidating that participant's cache is correct — CLAUDE.md semantics). Slow memory at the head, volatile thread map at the tail; all bytes ride `messages`, so `chargeable_prompt_tokens` covers them.
- **The tool seam is turn-scoped** (the navigation-tool precedent): `remember(block, text, scope?, sources?, annotation?)` binds to *this* turn's responding participant, residence space, and `ThreadSnapshot` — none of which the process registry's `Tool` trait can carry. Name reserved; constructed in `prepare_turn`.
- **Off by default:** the whole feature (loading read *and* tool) gates on `AppCore::set_memory_enabled` (process-scoped consumer opt-in, like `register_tool`) — an install that never enables it never reads, so it costs no query and no bytes. The opt-in is a consumer decision about the *feature*, not a byte-identity obligation (see Thread map). Past that opt-in `remember` attaches wherever the navigation tools do, on the same learned per-`(backend, wire_model)` capability (see Tool registry) — **no backend kind is excluded.** An endpoint that turns out to refuse a `tools` field has `remember` withdrawn with the rest by the degrade retry and keeps `MEMORY_NOTE`: such a turn still *reads* its memory and cannot revise it, which is a property of that endpoint, learned, and re-probed next restart — not of any backend.
- **Hygiene** is revision-shaped, plus guard rails — `MAX_MEMORY_BLOCKS` (8) per owner, `MAX_MEMORY_BLOCK_BYTES` (2000) per block — refused as *tool results* (correctable model mistakes), honest about the limit, decided before any write (zero trace). A committed block emits `Change::Space(residence)` — safe mid-loop because `memory` is not a post type.
- Inspection: `memory_blocks(participant_id)` (pure read; full revision trail with contents, author, provenance).
- Tests: `tests/agent_memory.rs`; the loading rule's SQL in `db.rs` (`participant_memory_loads_core_everywhere_and_space_blocks_only_at_home`). Memory *quality* is offline-eval material, never CI.

## Cross-space discovery (`discovery.rs`, task 36)

`list_my_spaces` — the space-level analog of `list_branches`. A turn's context is branch-scoped, so a promoted agent can't otherwise know its other conversations exist. **Bounded by membership:** reads `db::participant_spaces` and nothing else, takes no arguments (no id or filter could reach a non-member space; removal takes effect the moment the human removes it — the boundary is the query, not a check a caller could forget). Reports *what and where*, never contents, and says so in the result. Turn-scoped and reserved like `remember`. **Its gate is structural, deliberately not the memory opt-in:** attaches only when the responding participant is a `global` agent — which exists only because a human promoted one — so the tool and its note appear exactly when the capability does, flipping once at promotion. (Riding the memory opt-in was rejected both ways: it would blind a promoted agent until memory was enabled, and switch on unasked-for cross-space visibility when it was.) `GLOBAL_AGENT_NOTE` joins the system message on the same terms: flips once at promotion, byte-stable after. Renderer unit-tested in-module; round trip in `tests/global_agents.rs`.

## Config (`config.rs`)

`Config` struct (TOML serde) with `*_override` fields and resolver methods falling back to compiled-in defaults — the domain separator, update feed, and `default_template` (the UUID new spaces instantiate from; resolves to the seeded `DEFAULT_TEMPLATE_ID` when unset; persisted via `set_default_template`).

- **The `default_model` config key is gone (Participants v1)** — the model lives on the default template's agent. The transitional resolved default is the **async `AppCore::default_model()`** (the default template's first agent's `model_ref`, else `DEFAULT_MODEL`), **not** a `ConfigState` field: `config_state()` is pure-config and DB-free so it's safe inside the core runtime (the CLI calls it there), whereas resolving the model reads the DB — a nested `block_on` panicked. There is no `set_default_model`.
- The eidola connection + trust bundle is **no longer here** — it moved to the `eidola` backend row (see Backends), so `Config` resolves without the database. The parse helpers (`parse_trust_measurement`, `parse_cert_config`) stay here for the row-based setters.
- GUI circadian theme settings: `AppearanceSetting` (`appearance`: `system` default / `day` / `night` / `auto`), `TimeOfDayTint` (`time_of_day_tint`: `on` default / `off`), `LightCharacter` (`light_character`: `cool` / `neutral` default / `warm`, serde aliases for pre-rename `bluish`/`orange`) — persisted via `set_appearance` / `set_time_of_day_tint` / `set_light_character` (all emit `Change::Config`).
- Base type-scale factor: `font_scale` (`f32`, default 1.0), clamped into `[FONT_SCALE_MIN, FONT_SCALE_MAX]` (0.8–2.0); the discrete ladder `FONT_SCALE_STEPS` + `font_scale_step_up`/`_down` back the GUI's zoom; `set_font_scale` clamps + emits `Change::Config`.
- Display language: `language` (`Option<String>`, unset = follow the system), persisted via `set_language` (emits `Change::Config`). **Stored verbatim and never parsed here** — this crate ships no user-facing strings, so it has no opinion on which languages exist, what a tag maps to, or what an unrecognized one falls back to; all of that is the presentation layer's (`crates/eidola-gui/src/i18n.rs`). Blank normalizes to unset on read and on write. Keeping the key opaque is what lets app-core stay locale-free while the preference still lives beside `appearance` and `font_scale`, where the client's persisted preferences belong. Test: `language_preference_round_trips_and_stays_opaque`.

## Install (`updater/install/`)

What happens after a release verifies. `stage()` downloads the unsigned payload container, hashes it against the value the **CI-signed manifest** records, unpacks it into a private staging tree, downloads the detached Apple material, hashes it against the value the **human attestation** records, runs `eidola_apple::apply` to compose them, and then reads the result back with `eidola_apple::inspect` and requires the Team ID, bundle identifier and hardened-runtime flag to be the ones the attestation named. Each expected value comes from the document that can be trusted for it, and never from the document that supplied the bytes: `release.json` is unsigned, so its schema-2 artifact index says only *where* bytes live.

**The updater is this mechanism's primary consumer by design.** An external auditor composes a payload with detached signatures rarely; the updater does it on every update, so a break in Apple's format surfaces on the next update rather than the next time a stranger checks us.

**Nothing is installed.** `stage()` produces a `StagedInstall` inside a staging root it owns, and every failure removes that root — the reconstruction crate is explicitly not atomic once it starts writing, which is exactly why it runs against a private copy. Promotion (replacing the running app, relaunching) is deliberately absent: it is a restart-UX decision, and `promotion_readiness()` is a read-only probe reporting whether this process could do it without privileges it must not acquire on its own. The probe asks the question the swap asks — a rename aside and a rename into place are operations on entries in the *parent* directory, needing write and search there and nothing inside the old bundle, so a read-only `.app` in a writable directory is promotable. The local database lives in the data directory, not inside the bundle, so a swap never touches the single-writer `flock` — but a relaunch that overlapped the old process would, which is why the swap belongs at quit.

The failure taxonomy is the contract: `Download` is the one variant worth retrying; every other variant means a document and the bytes it describes disagree. `PlanIncomplete` refuses a plan that would apply signature material without checking what it claims, so "forgot to compare the identity" is unrepresentable rather than merely discouraged. Containers are unpacked by rules matching what reconstruction already demands of a tree (no symlinks, no traversal, no duplicate members), and member names are refused rather than normalized — `a/./b` and `a//b` are names our packer cannot produce. `unpack_zip` and `MAX_CONTAINER_BYTES` are **public** for one reason: `release-tool` proves the same reconstruction on the signing side, and two extractors or two ceilings would be two rule sets — what the release officer checks must be unpacked, and bounded, exactly as a user's client will. A container above that ceiling would otherwise verify tool-side and be refused by every client on the wire, which is the same "publishable in a shape clients reject" failure the attestant-key pre-flight exists to prevent.

The values the plan needs about the signature come from `VerifiedAttestation::apple` (`AppleSignatureAttestation`: shipped-container hash, detached-material hash, Team ID, signing identifier), which the verifier populates exactly when the attestation's schema records them. `team_id` is `Option` all the way through: an ad-hoc-signed artifact names no team, and that is a fact the plan compares against rather than a gap it fills in. `ExpectedSignature.hardened_runtime` is deliberately **not** an attested field — the hardened runtime is a property of the signing recipe, fixed for every release, so a plan asserts it rather than reading it from a document a coerced signer writes.

`tests/updater_fixtures.rs` drives the whole path on **every platform** against the committed synthetic universal fixture: reconstruction is pure Rust, so Linux CI proves what a Mac does. The positive test asserts the staged bundle is byte-identical to the fixture's signed app, and leans on the fixture's own asymmetry — its unsigned input carries no hardened-runtime flag and its signed output does — so a test that finds the flag set has watched the composition happen rather than a payload pass through.

## Updates (`updates.rs`) and trust root (`trust_root.rs`)

Verified update-notification flow ("a newer release exists; here's the door"). Polls the GitHub release marked `latest` (the human-attested marker — `tinfoil-build.yml` deliberately doesn't set it), verifies the release's `artifact-manifest.json` + Sigstore bundle against the **embedded** trust root (full Fulcio chain + pinned CI identity + Rekor via `updater::ci_sigstore`, plus an `@refs/tags/<tag>` identity↔tag binding check that blocks replaying an authentic old manifest under a newer tag), then structurally compares attested claims against expected claims (types/structure, never values — concrete set in the module docs; schema 2 requires **both** `narHash` and a well-formed `archiveSha256` on Nix rows — `archiveSha256` is the only artifact hash checkable without Nix, so a schema-2 manifest that drops it has removed the user's independent check and must read as `ClaimsChanged`; schema-1 rows predate the field and legitimately have none, which is why the requirement is keyed to the declared schema rather than applied unconditionally). **Schema rotations are two-sided and land in two releases** (`releases/README.md`), and `release.json` rotates the same way: `supported_release_schema_versions` accepts schema 2 — the artifact index the installer downloads from — while `release-tool` keeps emitting schema 1, and `updater::check_schema_shape` holds a release to the shape it declares in both directions, refusing a schema-1 document that carries the index as loudly as a schema-2 one that omits it. `attestation.json` rotates identically: `supported_attestation_schema_versions` accepts schema 2 — the macOS signing block (`apple_shipped_artifact_sha256`, `apple_signature_bundle_sha256`, `apple_team_id`, `apple_signing_identifier`), the key-dependent values the manifest may never hold — while `release-tool` keeps emitting schema 1, and `human_attestation::check_apple_field_shape` applies the same two-sided rule, over the raw JSON rather than the parsed struct because `serde` cannot tell an absent key from an explicit `null` and `apple_team_id` is legitimately null for a signature naming no team. The schema gate takes its supported set as a parameter so the refusal a client pinned to `[1]` must perform is testable rather than merely asserted (`schema_two_attestation_is_refused_by_a_client_pinned_to_schema_one`). The emit side is welded to the templates — the `apple_signature_reconstructs` claim substitutes those fields, and the templates that bind are the previous release's — so both flips land in the same later release; `releases/README.md` carries the sequencing. For the manifest: `SUPPORTED_MANIFEST_SCHEMA_VERSIONS` accepts the new version one release before `scripts/artifact-manifest.sh` emits it, so between those releases this module must read the old *and* the new shape as authentic. Rows a newer schema introduces live in `EXPECTED_ARTIFACTS_SINCE_SCHEMA_N`, and rows it *retires* live in the mirrored `EXPECTED_ARTIFACTS_THROUGH_SCHEMA_M` — a rename is one of each, so each spelling is expected exactly under the schemas that record it. Both render with an `" or absent"` alternative while a schema on the other side of the boundary is still accepted, and both verdicts key to the schema the manifest itself declares: a declared schema that records the row reports `missing (…)` when it is absent, and a declared schema that does not reports `present, but …` when it is carried. Retiring rows are additionally bounded below by the oldest schema this build accepts — a row also *started* somewhere, and the artifact set of a shape this module never understood gets no verdict. Both lists self-tighten off `SUPPORTED_MANIFEST_SCHEMA_VERSIONS` alone: when the old version leaves it, arriving rows become unconditional and retiring rows leave expectations, with no further edit. Emission without the version bump is as loud as the bump without emission. Artifact rows are also exact key sets per type (`describe_artifact`), the same rule `scripts/check-manifest-determinism.sh` applies to the committed manifest — an extra per-row field is how an unreviewed claim would otherwise arrive. Today: schema 3 adds `eidola-gui-macos-universal-zip` (`type: "file"`, the macOS unsigned shipping zip's `sha256`), the Debian packages (`eidola-gui-linux-deb-{amd64,arm64}`, `type: "file"` — the `.deb` is the byte stream its hash covers), and the Linux Nix installable under its narrowed name (`eidola-gui-linux-nix-amd64`), retiring the schema-2 spelling `eidola-gui-linux-amd64`; all accepted but not yet emitted, and the emission flip refuses to compose a manifest whose artifact set is not exactly what its declared schema requires (`scripts/artifact-manifest.sh check-complete`). Typed `UpdateCheckResult`: `UpToDate` / `UpdateAvailable` (verified; one action — open the release page) / `Unverifiable` (hard visible security state; never silent, never links the artifact; survives later `CheckFailed`s) / `ClaimsChanged` (authentic but the threat model changed — side-by-side diff, default NOT trusted; explicit `accept_changed_claims` records the choice per exact version+manifest-hash) / `CheckFailed` (network blip; quiet). State persists in `<data_dir>/update-state.json`; `start_update_polling` runs at launch + ~6h. `Config.update_feed` points dev/test at a fixture feed — `tests/updates_check.rs` exercises the matrix against the real captured `v0.0.8` signed release (schema 1; the fixture expected-claims set pins that era).

`trust_root.rs` re-exports the build-time-generated `trust_root.gen.rs` constants (server URL, enclave measurement, attestant fingerprints, CI identity, schema versions, embedded JSON). Sources live under `releases/`; see `docs/trust-root.md` and `releases/README.md`.

## Local models (`local_models.rs`)

On-device inference via llama.cpp in server mode: a managed `llama-server` subprocess per loaded model, bound to `127.0.0.1` on an ephemeral port, speaking the same OpenAI-compatible HTTP — so the chat path treats a loaded local model as just another upstream.

**Routing is by backend kind, not model-id prefix:** `prepare_turn` resolves via `parse_model_ref`; engine-backed kinds (`local`, `llamacpp`) swap the attested client + credential spend for a plain loopback client with `TurnPrep.spend = None` — no charge, no ACT header, no refund machinery, no `Wallet` emissions, `credits_consumed = NULL`, provider `(<backend-id>, "inference")` — so local inference needs zero onboarding. `openai`-kind turns take the same no-spend path over HTTPS with the backend's key as `Bearer` (`TurnPrep` carries `backend_id`, recorded on request rows, and a `wire_model` distinct from the canonical qualified id, which actions record and `ChatResult` reports). Everything downstream (SSE parsing, context assembly, `persist_turn`, emission placement) is shared.

**Storage is the filesystem:** the managed `local` singleton owns `<data_dir>/models/` (one `.gguf` per model + optional `.meta.json` sidecar; downloads stream to `.part` and rename; a manually dropped `.gguf` is picked up on scan); each `llamacpp` backend scans its user-owned `models_dir` (load/unload only — download/delete refused). **Runtime state** (in-flight downloads, engine supervisors) lives in `LocalRuntime` on `Inner`, engines keyed by `(backend_id, slug)`; every transition emits `Change::LocalModels` (progress throttled ~2.5 Hz); consumers re-snapshot via `local_models_state()` (carries `external: Vec<ExternalEngineBackend>`). **Not every row in that snapshot is a file**: the managed store *synthesizes* a `LocalModelInfo` for an in-flight download (streaming to `.part`, so no `.gguf` exists yet) and for a standing failure that left nothing on disk, both only when the scan found no file for the slug. `LocalModelInfo::on_disk` is the discriminator — true exactly for the rows `scan_engine_dir` produced (so external backends' rows always are) — and status is *not* a substitute: a failure row is `Available`, the same status a scanned idle file carries. Any consumer reasoning about **file presence** rather than about what to show must read `on_disk`. **Selectable and installed are not visible** — the *listing* keeps both kinds of row, which is where the progress and the error are read; every surface that instead asserts a file joins on `on_disk`, and three review rounds swept the class to these four (each was wrong in the same way, and each has a regression):

1. **`backend_models`, the selectable surface** — filters on `on_disk` alone, because a picker offers files: a failed-download row read as `Available` was offered as a model and could only fail at load time (`a_failed_download_is_listed_but_never_selectable`, `tests/local_models.rs`). The GUI's `LocalModelsStore::selectable_models` / `external_selectable_models` take the identical test.
2. **The CLI's orphaned-engine flag** — a re-download of a deleted-out-of-band slug otherwise erased `— backing file missing` while a running engine still served the vanished file (`crates/eidola-cli/AGENTS.md` → `model`).
3. **The macOS status menu's `(file missing)` marker** — the same erasure in the menu bar; there the *naming* join stays permissive and only presence tightens (`crates/eidola-gui/AGENTS.md` → App lifecycle).
4. **The catalog's installed marker**, joined on `file_name` rather than id — CLI `catalog_installed` and Settings → Backends → Local, where "Installed" *replaces* the Download verb, so a failed download hid its own retry.

**A standing failure is a report, and it carries what a way out needs.** The `failures` map holds an `EngineFailure` — the message plus the `source_url` a *download* failure was fetching from — because the synthesized row is the only thing that remembers where it came from: with no file and no URL, a surface showing it has nothing to offer but the error text. `source_url` is `None` for a load failure, whose `.gguf` is on disk and whose retry is an ordinary Load. **`dismiss_local_model_failure` is the acknowledgement**, idempotent, touching no file, engine or row, and emitting `Change::LocalModels` only when something was actually forgotten. It exists as its own verb because `delete_local_model` merely *happens* to clear a failure on its way past: that is a file operation, and asking a reader to press Delete to dismiss an error asks them to believe something is being deleted. Regression: `a_failed_download_remembers_its_url_and_can_be_dismissed`; the GUI's half is `crates/eidola-gui/AGENTS.md` → Settings ▸ Backends ▸ Local.

The remaining `state.models` joins are safe by construction and were checked: display-name lookups (`SpaceView::model_display`, `participants_view`) make no claim about a file, and joins keyed on `Loaded`/`Loading` status can only match rows the scan produced.

**Engines load on demand, managed as a memory pool.** A request triggers the load: `prepare_turn`'s engine arm leases a ready engine (`lease_engine` — LRU bump + in-flight counter; the `EngineLease` on `TurnPrep` releases on drop) or calls `load_local_model`, with one gate: a `llamacpp` backend with `auto_start = 0` refuses request-triggered loads before any spawn (typed `NotConfigured`); the managed `local` backend always auto-starts; explicit `load_local_model` ignores `auto_start`. `load_local_model` is idempotent — ready → return, warming → join that load, absent → load. Before spawning, the pure eviction planner (`plan_evictions`) makes room inside the **memory budget** (4/5 physical RAM; test-overridable) using estimated footprints (file size + 1 GiB overhead heuristic — estimates only decide evictions; a genuinely-too-big load fails at the engine honestly): LRU engines that are neither pinned, serving an in-flight turn, nor warming are unloaded until the model fits; if that can't free enough, the load is refused *without unloading anything*, naming what holds the memory. Planning + inserting the warming entry happen in **one critical section** (`reserve_engine`) so concurrent loads can't double-book; a `ReservationGuard` rolls back on error. **Pinning** (`set_local_model_pinned`) is runtime state — protection from automatic unloading only.

Engine lifecycle: spawn `llama-server -m <gguf> --port <free> --alias <selection-id> -c 8192 --jinja --no-webui -ngl 999` (alias = selectable id so chat bodies match verbatim), poll `/health` until ready (5-min budget, stderr tail captured into failures); a supervisor task owns the child — unload signals it, unexpected exit records + emits, `kill_on_drop` reaps on process death. **The readiness budget bounds each probe, not only the gaps between them**: the deadline is an arm of the same `select!` as the shutdown signal, because an endpoint that accepts the request and never answers is exactly what a warming engine looks like, and it would otherwise suspend the budget entirely while every joining caller waited (`test_set_engine_ready_timeout` shortens it for tests; regression `a_hanging_health_probe_still_hits_the_readiness_deadline`). **An entry's identity is its `EngineInstance`, not its key.** `(backend_id, slug)` names a *load*, so unload-then-reload puts a second engine under one key while the first supervisor is still alive — and `select!` is free to take the health or exit arm rather than the shutdown one it raced. Every effect a supervisor or a `ReservationGuard` has on shared state therefore goes through **one gate**, `LocalRuntime::if_still_registered`, which runs the effect only while that instance still holds the key and hands it nothing but its own entry (an `OccupiedEntry`), so an arm that skips the gate has nothing to act on. The complete list of what passes through it — **add to this list, never to the pattern**: the spawn licence (`spawn_if_still_registered`), promotion to ready (`mark_engine_ready`), retirement (`retire_instance`), and failure reporting (`fail_instance`, which retires *and* files inside the gate). Two things deliberately stay outside: bus emissions, which are idempotent invalidations and cost only a redraw (silenced during a quit, for the reason above), and the user-driven verbs (`unload_local_model`, the quit drain), which act by key because "whatever is loaded under this id" is exactly what they mean. Asking in one place is what turns the rule into an invariant: while each arm asked separately, one forgot — the failure-filing arm treated an *absent* key as licence to record, so a deliberate unload could leave "exited unexpectedly" on a row that is merely available, and the next occupant of the key inherited it. Silence there swallows nothing: the waiting caller is told over its own channel and a joining one reads "the engine load was cancelled", which is what happened. Without it a stale supervisor marks a still-warming replacement ready (routing turns at a port nothing serves yet) or deletes it while reporting its own child's death, orphaning a subprocess nothing can ever unload. Regression `a_stale_supervisor_cannot_touch_the_engine_that_replaced_it`. **And an engine may not outlive what its backend row meant**: removing, disabling, or repointing a backend's `models_dir` / `engine_path` retires every engine registered under that id (`Inner::retire_backend_engines`), and a **disabled backend starts nothing** — `load_local_model` requires the row for every engine backend, the `local` singleton included, so the explicit verb (`eidola model load`, the Load button) cannot start an engine the chat path would refuse to use. Managing *files* stays open: download and delete are not processes. **The sweep alone would guarantee nothing**, because a load reads its backend's configuration and then awaits — file lookup, engine resolution, port pick, `fs::metadata` — before it registers anything, so a retirement in that window sweeps a map the load has not written to yet. A load therefore carries the `BackendEpoch` it read its configuration under and `reserve_engine` refuses a stale one, inside the same critical section the sweep takes (the shutdown latch's shape, one level up: [`EngineInstance`] gives an *entry* an unforgeable identity, this gives one to a load that has no entry yet). The bump happens *after* the row is written, which is the fail-safe order — the worst case is refusing a load that had already read the new configuration, and its message says to try again. **And a registration is the licence to run a subprocess**: the reservation and the spawn are separated by a `tokio::spawn` and an unbounded scheduling delay, so the one place this crate starts a process (`spawn_if_still_registered`, in `supervise_engine`) re-reads the registry under that same lock and starts nothing unless *this* instance still holds its key. That one question answers the quit drain, an unload, an eviction and a retired backend at once — each of them removes the entry under this lock — and answers whichever path is added next without anyone remembering to add a check; it is why the latch needs no separate look here. Killing a child a moment after starting it is not the same as never starting it: a model is mmapped and gigabytes are touched on the way up, and a repointed backend's binary may be one the user has just replaced. The residual is inherent — a process already started can only be killed, on the very next poll of the supervisor's `select!`. So the two write points are `reserve_engine` (may this load create a registration?) and the spawn (does this registration still exist?). Regressions `a_retired_backend_never_starts_a_process`, `only_a_live_registration_may_start_a_process`. **Retirement also forgets what those engines had to say** — a standing engine failure describes a directory and a binary the backend no longer has, and a removed row is only *soft*-removed, so re-adding the id would revive the row and the stale error with it. A **download** report is not an engine's: it belongs to the file and carries the URL a retry needs, so it survives. **A configuration write and its cleanup are one operation**, held together by a per-backend gate (`Inner::lock_backend_config`, taken by all four of add / enable / update / remove). Each of them commits and *then* acts on in-memory state, so without it an older operation's cleanup outlives a newer write: disable commits, enable commits over it, a load registers the engine the final configuration authorises, and the disable's cleanup stops it — a load that reported success, an enabled backend, and no engine. An in-memory generation cannot stand in: the cleanup that should run is the one belonging to the write the *database* kept, and a counter bumped either side of the commit orders itself rather than the commits (persisting it in the transaction would order it, but that is a schema change). Holding a lock across a *load* was refused for good reason — a load walks the filesystem, picks a port and spawns a child — and the reasoning does not carry to one short statement plus a synchronous sweep of two maps, per backend. Loads never take this gate. **Either effect invalidates**: `retire_engines_for` emits `Change::LocalModels` when an engine was stopped *or* a report forgotten — a backend whose engine had already failed has no engine to stop and a report to forget, and a summary counting only engines could not see it — while a retirement that finds neither stays silent, since an invalidation nobody needs redraws every subscriber on every disable. Regressions `a_load_in_flight_when_its_backend_is_retired_registers_nothing`, `a_retirement_invalidates_a_reservation_made_under_the_old_configuration`, `a_disabled_backend_starts_no_engine_even_when_asked_explicitly`, `a_re_added_backend_does_not_inherit_its_predecessors_error`, `a_retired_instance_files_no_failure`, `retiring_a_backend_forgets_its_engine_reports_but_not_its_downloads`, `retiring_a_backend_that_only_has_a_failure_still_invalidates`, `retiring_a_backend_with_nothing_to_retire_emits_nothing`, `an_older_disables_cleanup_cannot_retire_an_enabled_backends_engine`.

**Three races, one principle, three guards — and they are not interchangeable.** The principle every one of them applies is *the authority for an effect is read at that effect's write point, under the same lock that changes it, never captured earlier*. What differs is the authority, which is why a fourth window should be classified before it is cured:

1. **A load versus a retirement** — may this load *create* an engine? Authority: the `BackendEpoch` it read its configuration under, validated in `reserve_engine`. Closes the window between reading a backend row and registering an engine from it.
2. **An instance versus the registry** — may this supervisor *act*? Authority: its `EngineInstance` still holding its key, asked in `if_still_registered` (spawn, ready, retire, fail). Nothing to do with configuration: unload, eviction and the quit drain are not configuration changes.
3. **A configuration write versus its own cleanup** — whose cleanup is this? Authority: the write order itself, established by holding `lock_backend_config` across commit *and* cleanup, because nothing readable after the fact says which write the database kept.

No single statement covers all three ("an engine exists only while the configuration that authorised it is current" is exactly axis 1, is silent about axis 2, and does not tell axis 3 which cleanup to run), and collapsing them would hide that each guards a different question. Removal is a *soft* remove and re-adding the same id revives the row, so an engine left behind is inherited by the revival — the next load of `<slug>@<id>` joins it and every turn runs against the old directory's file while Settings describes the new one. Regressions in `tests/backends.rs` (`removing_a_backend_retires_its_engines_so_a_revival_cannot_inherit_them`, `repointing_or_disabling_a_backend_retires_its_engines`).

**`shutdown_engines` is the quit-path teardown** (the GUI's `on_app_quit` hook): synchronous, infallible, reading the **engine registry** — drains the map and signals every supervisor, touching no filesystem or database. It exists separately from looping `local_models_state` because that snapshot is reconstructed by *scanning* the model directories, so an engine whose backing file was renamed/deleted mid-session is invisible to it while its subprocess is alive — and on macOS `[NSApp terminate:]` ends in `exit()` (no `kill_on_drop`), which would orphan it to launchd. **`running_engines` is its read-only sibling** and exists for the same reason from the other direction: any surface that *reports* what is running must take **membership** from the registry, in both directions — the scan-based snapshot loses an engine the moment its backing file does (or its backend row is removed, or its directory goes unreadable) while the subprocess keeps its memory, and it equally *keeps* a stopped engine's row alive whenever a rescan fails and the previous snapshot is preserved. It is synchronous, infallible, ordered by the `<slug>@<backend>` id, and carries only what the registry itself knows — **no display name**, since that lives in the `.meta.json` sidecar beside the file that may be gone; a caller joins `LocalModelsState` on `RunningEngine::id` for a pretty name and falls back to the slug. (First consumer: the GUI status menu's engine readout, which had exactly this defect — see `crates/eidola-gui/AGENTS.md` → App lifecycle.) The drain also sets a one-way **shutdown latch**, inside the same `engines` lock the reservation takes and checked there (`reserve_engine`), so no load can create a registration after the registry has been walked — the authority read at the write point, never captured. It needs no second check before `command.spawn()`, because **a live registration is the licence to run a subprocess** (`spawn_if_still_registered`, below). A quit is also the one time nothing on this path emits: the GUI's bus bridge would panic ("Can't spawn on main thread after on_app_quit"), so **every** supervisor emission goes through one gate silent while the latch is set (gated on the latch, not the shutdown arm — an ordinary unload still emits). The latch also fixed a second swallow: the warming loop's `/health` probe was awaited outside its `select!`, so the shutdown oneshot wasn't polled for the probe's duration — and warming is exactly when `/health` hangs (socket accepted while a multi-GB model loads, no request timeout); the probe now races the signal. Regressions in `tests/local_models.rs` (`shutdown_reaches_an_engine_the_model_scan_cannot_see` and its read-only twin `running_engines_reports_an_engine_the_model_scan_cannot_see`) + in-module.

The curated catalog (`LOCAL_MODEL_CATALOG`) lists Google's five official Gemma 4 QAT Q4_0 GGUFs; `normalize_model_url` also accepts any direct `.gguf` URL or HF file page (`/blob/` → `/resolve/`). **The query is stripped for inspection, never from the request**: the file name, the `.gguf` check and the transfer's identity are decided on the path alone — so equivalent spellings still collapse onto one slug — while `ModelDownloadTarget::url`, the URL actually fetched, keeps it, because a signed S3/CDN link carries its authorization there and a request without it 403s. `canonical_url` is the query-free form, and it is what the `.meta.json` sidecar records: provenance, not a short-lived credential left on disk (a failed download's retry URL keeps the query, in memory only, and is an argument to Retry — no surface renders it). **The other half of that trade is the error text**: `reqwest` attaches the request URL to every request-phase error and prints it in `Display`, and `Response::bytes`/`text`/`json` do the same, so formatting one with `{e}` copies a live token into a standing failure that surfaces render and the CLI prints. `error::request_error_text` strips the URL and is the one path a `reqwest::Error` becomes text through in this crate — including `AppError::from_request`, so no call site has to remember. (Established by running the failures, not by reading docs: the URL is in the top-level `Display` only, never repeated by a source, and `bytes_stream` chunk errors carry none.) Regressions `a_signed_urls_authorization_survives_to_the_fetch`, `a_signed_download_url_is_fetched_with_its_authorization`, `a_failed_signed_download_keeps_its_token_out_of_the_error`. **A download's identity is its slug, and `resolve_model_download` is the one derivation of it** — `download_local_model` keys its in-flight map (`downloads`, the source of the "already downloading" refusal) on exactly what that function returns, so equivalent spellings of one model collapse onto one transfer. It is `pub` because a caller outside this crate that keys work on "this download" **must** key it the same way or it will ask for a transfer already under way and be refused: the GUI store's pending slot is that caller (`crates/eidola-gui/AGENTS.md` → Backends ▸ Local). Regression `equivalent_spellings_resolve_to_one_slug`. **Cancellation is a wakeable signal, not a polled flag**: `DownloadEntry::cancel` is a watch channel raced against every network wait, each of which also races `DOWNLOAD_STALL_TIMEOUT` (120 s of silence). A flag read between chunks cannot reach a transfer blocked on a server that stopped talking — which is precisely when Cancel gets pressed — so the partial file and the map entry stayed and every retry was refused as already downloading. The bound lives in `run_download`, not on the shared client, which also carries loopback engine traffic where a long silence is normal. Regression `cancelling_a_stalled_download_interrupts_the_blocked_read`. **Engine resolution is split by kind** (both halves pure, unit-tested): the `local` engine is the **bundled sidecar** — `resolve_local_engine` tries the `llama_server_path` config override, then `EIDOLA_LLAMA_SERVER` (set by the Linux GUI wrapper to the *copied* `$out/bin/llama-server`, which is also the sibling the exe-relative rule would find), then **one exe-relative rule on every platform: a `llama-server` sibling of the running executable** (CLI/Nix/dev builds, the Linux Nix GUI, and the macOS `.app`, whose sidecar ships at `Contents/MacOS/llama-server` next to the main binary — so app-core knows nothing about `.app` internals; the layout is owned by `flake.nix` + `scripts/package-gui-app.sh`) — **no `$PATH` scan**, so a missing engine surfaces the honest "this build doesn't include the bundled engine" state; `llamacpp` backends use `resolve_external_engine` (explicit `engine_path`, else `$PATH` then Homebrew/system dirs). On macOS both resolvers reject a binary with no executable Mach-O slice (`usable_engine_binary` — the universal `.app` ships the arm64-only sidecar to Intel Macs, where mere existence must not advertise an engine that can only exec-fail). Engines are per-process; every on-disk model is selectable — the request loads the engine. Tests: `tests/local_models.rs` (wiremock downloads, credential-free chat rows, pin round-trip, eviction wiring against `/usr/bin/false`) plus in-module resolver tests — including `the_bundled_engine_rule_is_a_sibling_and_nothing_else`, which asserts the *absence* of any `Contents/Resources/bin` candidate so the retired bundle layout cannot quietly come back; the real subprocess lifecycle is exercised manually.

## Database (`db.rs`) and migrations

Embedded [Turso](https://crates.io/crates/turso) (pure-Rust libSQL) database at `~/Library/Application Support/eidola/eidola.db`. Three-layer schema (wallet, transport, semantic) in `schema/schema.sql`.

**One writer, loudly (`db::DbLock`):** turso is single-writer, and two processes on one file (open GUI + a CLI invocation) used to contend silently. `AppCore::build` takes an exclusive advisory lock (`flock` via `fs4`) on `<data_dir>/eidola.db.lock` **before** building anything; `Inner` holds it for the process lifetime; a second opener gets `AppError::DatabaseInUse` naming the holder's pid. **Keep it `flock`, not a pidfile-existence check:** the lock lives on the open file description, so the kernel releases it however the process exits — a crash cannot wedge it; a leftover lockfile means nothing (regression-tested). The file contents are just the holder's pid (unreadable stamp still refuses, `pid: None`). Keyed on the **data** dir, so disjoint dirs never contend (what keeps tempdir tests parallel-safe). Two `AppCore`s in one process are refused like two processes; restart-modeling tests drop the first core first. The CLI parses argv before building the core; the GUI opens the core **before** its app context exists and renders this variant as a native alert (`crates/eidola-gui/AGENTS.md` → Startup failures — inside `Application::run` the same refusal was an un-unwindable panic and a macOS crash report). **`AppCore::open_database` is the companion for that surface**: the lock is taken in `build`, but the database itself lives behind a `OnceCell` filled on the first `db_conn()`, so the two session-ending failures were found at different times — this variant at construction, a refused schema only once something read. It forces the open (and with it the startup sweep, whose premises only strengthen when nothing has been spawned yet), is idempotent, and is what lets a client learn everything fatal in one moment. Tests: `tests/db_lock.rs`.

**Schema management — fresh-start, no migrations:** `schema.sql` is the whole baseline (pre-release history collapsed; no real users). Fresh installs (`user_version == 0`) apply it via `execute_batch` and set `LATEST_VERSION`; a database already at `LATEST_VERSION` just re-runs idempotent seeds; **any other version is refused** with an honest "delete your dev database" error. Changing the schema: (1) edit `schema.sql` to the new desired state — this IS the change; (2) bump `LATEST_VERSION` in `db.rs`; (3) `cargo test -p eidola-app-core` (`migrations_match_schema` stays trivially green). **`LATEST_VERSION` is 9.** Limitation: no `ALTER TABLE ALTER COLUMN`; a `NOT NULL` column still needs a `DEFAULT`.

**FK enforcement is real:** turso defaults `foreign_keys` **OFF** (every FK is unenforced documentation until enabled, per connection), so `db::connect()` sets `PRAGMA foreign_keys = ON` on every connection (`Inner::db_conn` and `open()` route through it), plus `PRAGMA busy_timeout` (concurrent per-turn writes block-and-retry instead of erroring). `turso_enforcement_smoke` pins the observed behavior: single-column FKs, composite FKs, MATCH-SIMPLE NULL-skip, CHECKs, and **`ON UPDATE CASCADE` on a composite FK** (task 36's in-place promotion rests on it — proven before anything was built on it). When adding tables, respect insertion/seed order.

**The `space` row carries `touched_at`** — the nullable pristineness stamp (see Disposing of untouched spaces). NULL means nothing has ever changed this space's configuration footprint since it was instantiated; actions deliberately do not write it.

**Scope-owned participant schema:** config columns (`kind`/`label`/`model_ref`/`system_prompt`/`notify_policy`, `role`, `removed_at`) live ONLY on `participant` — drift is impossible rather than managed. Reference tables carry a pinned `participant_scope = 'global'` CHECK echo + composite FK `(participant_id, participant_scope) → participant(id, scope)`, making "may only reference a global" declarative. `action` carries the same pinned echo (`IN ('global','space')`), so template-owned authorship is unrepresentable. `space` has `cascade_limit` (default 4), `router_model` (NULL = router off), and nullable `notebook_participant_id` (partial-unique — one notebook per agent; chosen over a `kind` column because consumers need *whose*: `list_spaces` excludes notebooks unconditionally, `notebook_space_for` opens one). `SpaceRow` carries `cascade_limit`, `archived_at` and `router_model` beside the identity columns so that every gate deciding "may work happen here" — `prepare_turn`, `mechanical_plan`, and the router refinement — takes its whole verdict off one statement rather than two that an archival can land between. `space_capability` (`(space_id, name)` PK + JSON `config`) is the sub-space attenuation snapshot — written only by the spawn door, immutable after, empty in practice today. `space_template` is a soft-remove registry. Schema integrity: an item's tip is provably unique (`idx_one_successor_per_action` + `idx_one_root_per_item`).

**The scope echo is never carried by a caller.** A turn spans HTTP round trips, so a scope captured at `prepare_turn` time can go stale — a promotion landing mid-flight made the next `insert_action` fail the composite FK, losing the response (found in review, reproduced, fixed). `insert_action` and `insert_memory_block` **derive the echo inside their own single statement** (`(SELECT scope FROM participant WHERE id = ?)`), and `ActionEntry` / `NewMemoryBlock` have no scope field at all: turso is single-writer, so nothing can interleave within the statement, and with nothing captured there is no read-then-write window. The column is `NOT NULL`, so an unknown participant fails loudly rather than writing a NULL echo MATCH SIMPLE would skip. Pinned by `a_scope_echo_can_be_derived_inside_the_insert`. Apply this idiom (derive authority at the write point) to any future echo column.

**Seeds:** idempotent at every open — the singleton backends, the **global** human `User` (`HUMAN_PARTICIPANT_ID`), `SYSTEM_PARTICIPANT_ID` ("Eidola", `kind='system'`, never referenced into any space, member nowhere), and the "Default" template (`config::DEFAULT_TEMPLATE_ID`) owning one template-scoped agent. **A seed makes a fresh database usable and never re-asserts state over a user's later edits**: `INSERT OR IGNORE` on a well-known id only distinguishes "never existed" from "user removed it" for rows nothing can hard-delete — false for the Default template's owned agent, which `update_template_tx` replaces wholesale with fresh ids. The seeded agent is therefore written **only in the same call that creates the template row** (the `INSERT OR IGNORE` rows-changed count is the creation signal): after first open, no seed path can touch a template's participants — re-injection is unrepresentable rather than guarded. **The template + agent pair is one transaction** (`ensure_default_template_tx`): `conn.execute` autocommits, so a process exit between the writes would commit the template row alone and consume the creation signal, permanently skipping the agent — and the post-crash state is indistinguishable from a deliberately emptied template, so rollback makes it unrepresentable instead of detected. Nothing ever backfills an existing database. Regressions in-module + `tests/template_seed.rs`.

**Projections** are row copies switching owner columns: `instantiate_template` (template-owned → fresh space-owned rows; references → space references with overrides; ensures the human) and `template_from_space` (the reverse). Replacing a template's owned agents runs in one transaction (`update_template_tx` — `BEGIN … COMMIT`, `ROLLBACK` on error) so concurrent instantiation never observes a partial set.

**Doctrine:** forensic Record queries never resolve mutable participant config (they read model/credits from `action`/`request` rows); "don't add a removed global to a space" is an app-layer typed error. Notable reads referenced elsewhere: `agent_cascade_depth`, `action_author`, `participant_spaces`, `is_space_member`, `action_space_and_type`, `referenced_post` (post types + `text` blocks only), `current_branch_summaries`, `participant_memory`, `memory_blocks_owned`, `memory_revisions`, `assembly_trace_blocks`, `post_authors`, `space_trace_rows`, `raw_space_actions` (the unfiltered test read). `ReferenceEdgeRow`/`AntecedentEdgeRow` carry the antecedent's action type + block type so *readers* apply the quotable rule without queries dropping rows.

## Errors (`error.rs`)

`AppError` enum; request error classification (attestation vs network vs server); typed variants UIs route on (never strings):

- `NoAccount`, `InsufficientBalance { available, required }`, `ProvisioningTimeout { message }` — onboarding/funding.
- `ToolLoop { message }` — the bounded tool loop couldn't finish honestly (round cap with the model still asking, or structurally unusable `tool_calls`); everything that happened is committed first.
- `ResponseTruncated { output_tokens }` — the model reached its completion ceiling without writing any answer. **No generation was written**, so the answer a regeneration would have replaced is intact; the raw exchange is in the Record and the credential settled. Data, not prose: the presentation layer says it in the reader's locale.
- `RegenerationInFlight { item_id }` — a second regeneration of one post while the first is still running in this process. Refused before the credential, so nothing was spent and nothing written.
- `DatabaseInUse { pid, message }` — another process holds the DB lock (`pid` best-effort).
- `NotAParticipant { participant_id, action_id }` — the cross-space ACL; non-leaking by construction (names only what the caller supplied).
- `SpaceArchived { space_id }` — a turn was asked for in an archived space. Archival closes a conversation, so it takes no new turns; it does not abort one already streaming, and it hides, deletes and forbids nothing else.
- `NotJoined { space_id, message }` — the human wrote into an agent-spawned sub-space they have not joined. Reading one is unconditional and writing into one is membership; this is where the two part. Carries the space id the caller already named, so the surface can offer the join that would satisfy it.
- `DrivenConversation { space_id }` — combined `chat`/`chat_stream` was asked in a live sub-space. Those rooms take their turns from the driver; this door would post and then start a second cascade alongside it. Asked after the membership gate, so an unjoined reader still sees `NotJoined`. `post`/`submit`/`respond_stream_as` remain.
- `WrongPostKind { message }` — an edit aimed at something that is not the human's own input, or a regeneration aimed at something that is not an agent's inferred answer. Typed so a surface can withhold the affordance rather than discover it by writing.
- `SpawnRefused { refusal }` — a sub-space spawn turned down by a guard, the attenuation gate, or an ineligible participant. The payload is a typed `SpawnRefusal` whose `Display` is the model-facing sentence, so the tool exposing the door renders a correctable result instead of failing a turn. Nothing was written.

Chat errors are returned **as themselves**: a turn's failures are the typed variants above, unwrapped, so every consumer routes on the variant it sees. The `ChatFailed { space_id }` wrapper that used to carry a persisted space id back to the caller is gone with the client state that read it — the GUI creates a space when its window opens, so it never has to learn an id from a failure (see `crates/eidola-gui/AGENTS.md`). A caller that lets `post`/`chat` create the space for it (the CLI's one-shot `chat`) and needs the id after a failure reads `list_spaces`.

## Account reads (`lib.rs`)

`account_show` / `account_prices` / `account_balances` / `account_checkout` / `account_subscription` are thin authenticated reads over the server's linked surface. **They persist nothing and emit no `Change`**: there is no durable commit to announce, and what they carry is the payment processor's state rather than ours — so nothing on the bus can invalidate them, and the consequence lands on the consumer: a surface showing one asks for it when the reader arrives, and offers a way to ask again (the GUI's Account pane does both — see `crates/eidola-gui/AGENTS.md`).

`account_subscription` answers a three-value `SubscriptionState` — `NoCustomer` (never transacted), `Inactive` (a payment relationship, nothing in force), `Active` — because those are three different surfaces, not two. "In force" is the *server's* definition (Stripe `active` / `trialing` / `past_due`), and it is the same predicate checkout refuses to double-subscribe over, so the app can never be told "no subscription" by one call and "already subscribed" by the next. A state string this version does not recognize is refused rather than guessed at: both guesses are harmful, and client and server ship together. It carries no portal link: minting one is `account_portal()` over its own endpoint, called at the moment the reader opens it, because the session is short-lived and minting it is a write the standing read has no reason to pay for.

## Terms acceptance (`lib.rs`)

**Two acts, kept apart on purpose: what is *submitted*, and what is *reported*.** `Inner::submit_terms` is the only path that records anything and `Inner::terms_standing` is the only path that reads the server back. `accept_terms(presented)` is submit-then-report; `account_create(accepted_terms)` is the same pair with the report attached to its result.

**Submission takes the snapshot the caller displayed, and nothing is re-read on the way to it.** `current_terms()` fetches the required `(document, version, url, sha256)` set; the UI presents it; that *same* value is the argument to `accept_terms` / `account_create`. Re-fetching inside acceptance was the defect this shape removes — a version advancing between the presentation and the acceptance would have recorded agreement to text the user never saw. With the snapshot passed through, the server (which records a pair only while it is still required) answers a stale one with a conflict, and the 428 gate re-prompts with the new text. An empty snapshot puts nothing on the wire.

**The report is read back, because success at recording is not the same claim as completeness.** Acceptance is recorded one document at a time and each submission is judged alone, so "everything I submitted was accepted" is silent about a document that became *required* after the snapshot was taken — and vacuously true when the snapshot was empty because the gate had not been switched on yet. Both leave an account the purchase gate refuses with no warning having been given. So `terms_standing` re-reads `GET /v1/terms` and compares it with what is known to have been recorded (`documents_not_covered`, a version comparison mirroring the server's own gate), answering `TermsAcceptance`:

- `Complete` — nothing required is uncovered (also the answer when nothing is required; for a caller those are one standing).
- `Outstanding { documents }` — named, and the caller must say so. Reached both by a document appearing after the snapshot and by a failed submission, where nothing is known to have been recorded and everything currently required is listed. It may over-list in that second case, which is the safe direction: re-accepting is a no-op, silence is a purchase that fails later.
- `Unknown { error }` — the server could not be read back. Not a claim of completeness.

**This is not the removed re-read returning.** That read *decided what was submitted*; this one only reports, and it is structurally unable to become the other thing: `documents_not_covered` answers with document **names**, and `submit_terms` takes `TermsDocument`s, which carry the hash. A name has no hash to submit. **Widening that return type to documents is what would re-open the hole** — don't.

`account_create` still treats acceptance as **best-effort** (the account exists whether or not it lands, and failing the call would strand it), which is why the outcome is reported rather than swallowed: `AccountCreateResult::terms`. Regressions: `tests/terms_acceptance.rs`, plus `documents_not_covered`'s unit tests in `lib.rs`.

## Automatic credential provisioning

Turns resolve their spend credential via `Inner::ensure_spendable_credential`, called under `spend_gate`: an active credential covering the estimated charge is used directly; otherwise app-core auto-allocates `min(available, max(DEFAULT_ALLOCATION_CREDITS, charge))` from the account balance transparently. `DEFAULT_ALLOCATION_CREDITS = 1_000_000` (credits are micro-USD; ≈ $1.00 ≈ 30 worst-case per-turn holds; sizing rationale in the doc comment). As a bounded retry loop under the gate, a concurrent turn finding balance committed waits for an in-flight refund rather than double-booking (see the ACT provisioning queue above for the exact wait conditions). Failures are typed: `NoAccount` / `InsufficientBalance` / `ProvisioningTimeout`. The explicit `account_allocate` path is unchanged; GUI and CLI get silent provisioning for free.

## Chat-path test harness (`tests/chat_harness/`)

The full `chat`/`chat_stream` HTTP paths are exercised by `tests/chat_path.rs` on an in-process mock upstream. The harness injects a plain-HTTP `reqwest::Client` via the `#[doc(hidden)]` seam `AppCore::with_test_http_client` (bypassing per-handshake attestation) and serves a raw tokio HTTP/1.1 upstream that mints *cryptographically real* anonymous credentials using the same `anonymous-credit-tokens` primitives as the server — issued credentials actually decode and spend.

Every test seam — `with_test_http_client`, the `Inner::http_override` field and each branch reading it, and the `test_*` methods below — is compiled only under the non-default `test-support` cargo feature, enabled for this crate's own test builds via the `[dev-dependencies]` self-reference in `Cargo.toml`. Release builds of downstream crates (cli, GUI) therefore contain no attestation-bypass path at all; the feature must never appear in a `[dependencies]` entry. A downstream crate's *tests* may enable it via its own `[dev-dependencies]` on `eidola-app-core` — never its `[dependencies]`.

- Per-test `ChatBehavior` selects blocking / streaming / mimicked-header (whole, and split across deltas) / non-2xx / mid-SSE-abort / connection-drop, plus tool arms: `ToolRoundsBlocking(n)` / `ToolRoundsStreaming(n)` (the SSE arm splits one call across four deltas so the per-index accumulator is genuinely exercised) / `ToolRoundsStreamingWithExtras` / `ToolCallMalformed` / `ToolCallBadArguments` / `ToolCallsNotAnArray(+Streaming)` / `ToolCallsNull` / `ToolScript` (interior-mutable — navigation-tool arguments are handles that only exist once the fixture space is built) / `RejectTools` (500s any request carrying `tools` with llama.cpp's verified error shape) / `DeclineBlocking` / `DeclineStreaming`.
- `blocking_and_streaming_dispatch_use_the_shared_request_body` compares ordinary and tool-follow-up bodies from both real transports with `eidola_common::chat_completion_request_body`, asserts their independently expected stream modes, then invokes the server's feature-gated test-only deserialization bridge on the same bodies. This catches both post-builder outer fields and nested message drift while the server's `types.rs` regression separately covers the shared-builder matrix.
- `RouterBehavior` scripts the may-decline router independently (answers only requests whose wire model is the registered router model, so one mock serves router + turns); `SummaryBehavior` does the same for the branch summarizer (recognized by system prompt, dispatched first). `RefundMode` selects refund-recovery success vs failure.
- The harness records request bodies (`chat_bodies()`) — the byte-pinning mechanism behind the cache-invariant and context-shape tests. Expected bytes are written long-hand by helpers, never reimplemented: `system_message{,_with}` (charter + identity line + notes), `roster`, `trailing` (roster then map, the whole trailing volatile message), `thread_map` / `map_entry`, `memory_section`, and `headed` for a post's `#<handle> · <label> · <stamp>` rendering. **A header stamp is a real wall-clock value**, so `Stamps::of(core, space)` captures a space's post times from `get_space_tree` and `Stamps::headed` pins against them — and because it reads each item's *current generation*, a test asserting pre-edit bytes must hold the snapshot it took before the edit (that is the semantics, not an accident).
- Reused by `tests/global_agents.rs`, `tests/cross_space_references.rs`, `tests/participants_orchestration.rs`, `tests/local_models.rs`, `tests/agent_memory.rs`, `tests/branch_summaries.rs`.
- `ChatBehavior::OkEitherTransport` answers a plain success in whichever transport asked, for the one test that must drive both twins against one upstream (`OkBlocking` answers a streamed ask with a body its parser reads as no content at all).
- The completion-ceiling arms answer in whichever transport asked, for the same reason — the classification is a property of the turn, not of how the bytes arrived: `ReasoningOnlyLength` (reasoning to the ceiling, no content, `finish_reason: "length"`), `PartialAnswerLength` (content *then* the ceiling), and `OkThenReasoningOnlyLength` (an ordinary first answer, then the ceiling — how a test gets a readable generation and a regeneration that fails to replace it).
- `MockConfig::chat_delay_ms` holds each chat answer before writing it. The mock is otherwise instantaneous, which makes an in-flight turn unobservable; a test about *concurrency* (two regenerations of one post) needs a window it can act inside.
- `chat_harness::reopen_core(dir, base_url)` builds a second `AppCore` over a profile the first one used — the **restart** seam, for guards that must survive one (the previous core has to be dropped first; a mock started on *its* runtime dies with it, so a restart test starts one on a runtime of its own).
- Notable `#[doc(hidden)]` test seams on `AppCore`: `test_chat_with_budget`, `test_space_actions`, `test_refresh_branch_summaries`, `test_drive_subspace` / `test_drive_subspace_armed` (one delegated room driven to a stop and reported, awaited; the second chooses whether the walk is the kind a change signal arms or the kind the startup sweep arms), `test_open_anchor_window` / `test_open_cascade_window` / `test_open_report_persist_window` (stop a walk between registering against its parent and asking whether that parent has answered; once inside a walk after its first driven turn; and immediately before a mechanical report's generation is committed — the only way an ordering, a post arriving mid-walk, or a regen of a finding or attach target / archival during the report HTTP is observable from outside), `test_open_regeneration_claim_window` (the same shape, immediately before a regeneration claims its item: what the claim is worth depends on what is read on each side of it, which nothing outside can otherwise stage), `test_insert_unvalidated_reference`, `test_space_archived` (a notebook's archival has no production reader), `test_fail_next_subspace_enumerations` (the transient store error the sweep's retry recovers from), `test_fail_next_anchor_lookups` (the transient store error after a wait is registered, which leaves a spent meter with nothing to deliver), `test_fail_next_plans` (the transient planner error that becomes a reported ending rather than a walk that dies outstanding), `test_register_loaded_local_model` / `test_register_engine` / `test_set_memory_budget`. Add seams sparingly, always `#[doc(hidden)]` **and** `#[cfg(feature = "test-support")]`.

Each test asserts both the typed/wrapped error and the bus emissions, executing the exit-point rows documented in `tests/bus.rs`.
