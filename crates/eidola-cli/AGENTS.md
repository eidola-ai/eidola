# eidola-cli — Agent Development Guide

Depends on `eidola-app-core` as a regular Rust crate. It either constructs `AppCore::new(config_dir, data_dir)` and invokes methods directly (see `crates/eidola-app-core/AGENTS.md`) or asks a running Eidola to do it over the control socket — see Client mode below.

## Structure and error surface

`main` parses argv **first** — so `--help` / `--version` / argument errors work even when another Eidola process holds the local database's exclusive lock — then builds the core, routing a construction failure through the same `report(&err)` renderer as a command failure. That renderer prints actionable hints for the typed errors: `NoAccount` → `eidola account create`; `InsufficientBalance` → `eidola account prices` / `checkout`; `DatabaseInUse` → quit the other Eidola.

## Client mode (`client.rs`, `session.rs`)

The local database has one writer, so with the app running this process cannot open the profile at all. It asks the app instead, over the control socket in the data directory (the wire contract is `eidola_app_core::ipc`; the listener is the GUI's).

**The selection rule** (`Session::open`) — dial first, then decide:

- **The socket answers, for this profile** ⇒ client mode. The app does the work; this process renders it. **A profile is both roots**, and the socket is found through the data one alone — the two are resolved from independent environment variables (`dirs::config_dir()` / `dirs::data_dir()`, i.e. `XDG_CONFIG_HOME` and `XDG_DATA_HOME` on Linux), so a shared data root is not a shared profile. The greeting states the config root the answering app composes its profile from (`HelloResult::config_dir`), and one that is not ours is refused *in the handshake*, before a verb is dispatched: adopting it would have run the command against another account's credentials, another default template and another update feed under this one's name. Compared after `canonicalize` where the path resolves, so a symlinked home or a trailing slash is not a refusal; an app that states *no* root is one older than the field, which is a check this build cannot make rather than a mismatch it may invent, so it is let through. Refusal is `Startup::OtherProfile`, naming both roots and the remedy.
- **Nothing is listening** — no socket file, or one nobody answers on (`ENOENT` / `ECONNREFUSED`, and *only* those, via the pure `client::no_listener`) ⇒ embedded mode, exactly as before the socket existed. Any other dial failure is a condition of its own and is reported as one: reading a permission failure as "the app must not be running" would send this process off to take a lock it may not be entitled to and then report the wrong problem.
- **The profile is held and nothing answered for it** ⇒ say so, never a silent wait. It arrives two ways and both render the same actionable sentence: no socket plus `DatabaseInUse` (the pure `session::unanswered`, which is the *only* place that error changes meaning — reached this way it says the holder is not serving the socket that exists to make this command work), and a socket that accepted a connection and never greeted it (the handshake's `HANDSHAKE_TIMEOUT`; `hello` states two constants, so a connection ungreeted after it is not busy, it is not being served).
- `--embedded` (global) forces embedded mode for debugging. It forces the *mode*, not the lock, so it still fails while another Eidola holds the profile.

**One surface, written once.** `Session` exposes each verb with the same signature and the same `Failure` in both modes, so the commands render one answer and earn one hint regardless of who ran the work — that is what the typed `AppError` on the wire buys. `Failure` is `App` (identical in both modes), `Protocol`, `Unrecognized` (a newer app's variant, its own message intact, its variant *named* in the hint) and `Transport`, plus `EmbeddedOnly` for a command that needs the profile here and `AccountReplaced` for a result that came back for an account this machine no longer speaks for — its own variant because nothing failed, the work succeeded for somebody else, and the only correct thing to do with it is not use it. `UnknownVerb` earns the "the running Eidola is older than this `eidola`" hint; `UnsupportedProtocol` names both versions.

**What client mode will not do**, and why it is one line rather than a list of exceptions: the socket carries the profile's *contents*, never its *identity*. `configure` and the bare invocation that reads the trust bundle back, the account's own identity and consent (`account create`, `accept-terms`, `reset`, `configure`, `allocate`), and the backend registry's membership (`backend add`, `backend remove`) each need the profile in this process, because each decides what this installation *is* or where its prompts may go — exactly what a per-client consent layer would gate, and that layer does not exist yet. Each is refused **by name** with the remedy (`Session::local` takes the phrase it prints), never half-done. `service` is unaffected: it is handled before any session exists.

**One authoritative read of the profile's own account.** `Session::account_identity` reads `account_id` out of `config.toml` on every call, in both modes. It needs no lock — it is the same file `AppCore` itself re-reads per call — and in client mode it is authoritative *because* the handshake already refused an app composed from another config root, so the file this process reads is the file the answering app writes. That pairing is what lets a client-mode command ask "is the account still the one this was minted for?" without a verb for the profile's identity, which the socket deliberately does not have.

**Where the two modes genuinely differ, they say so:**

- **`model load`** — the engine belongs to whichever process loaded it. Embedded, that is this one, so it serves until Ctrl-C and unloads on the way out. In client mode it is the app's, held for the app's lifetime, so the command returns and points at `eidola model unload`; unloading on exit would take away exactly what was just asked for.
- **The default model is resolved by whoever takes the turn.** Embedded, that is this process — it owns the profile for the whole command, so resolving before the turn *is* resolving at turn start, and the resolved name is what lets the run narrate a possibly-long engine load. In client mode the app owns it, and the default template (or that template's agent model) can change between any lookup here and the turn; on the wire a resolved default is indistinguishable from a model the reader named, so sending one would leave the app unable to apply its own current answer. So a turn that named no model travels with **no model**, and the cost is stated rather than papered over: nothing can narrate an engine load ahead of a turn whose model this process does not know, and the closing report names the model that answered. An explicitly named model always travels. Regressions: `a_turn_that_names_no_model_leaves_the_default_to_the_app` (which fails if the run takes a `chat.default_model` lookup at all) and `a_turn_that_names_a_model_sends_it`.
- **`model download`** — the transfer belongs to the answering process. In client mode the progress loop is *watching*, not driving, and says so: the download continues if you stop watching.
- **`model list`'s registry** is `running_engines` from whichever process owns the engines — in client mode the app's, which is the only way a process without the profile can learn what is loaded. The reconciliation below is unchanged; it is the pairing that matters, and `Session::models` reads scan and registry in one round trip so an engine cannot start or die between the halves.
- **A streamed event this build cannot read** (only possible against a newer app) is counted, never dropped in silence: the turn still completes and a `warning:` line names the count and both versions, because those events were part of the answer.
- **Ctrl-C during a turn** — and this one is billing-relevant, so state it forwards. In **client mode** interrupting costs the *delivery*, not the turn: the app runs it on its own runtime, so losing the connection detaches the turn rather than cancelling it, and the answer is written, the credential settles, and the post is in the space when you come back (`crates/eidola-app-core/src/ipc/serve.rs` → What a lost caller costs; the only racy edge is a caller that vanishes before the turn reaches the runtime, where nothing runs and nothing is spent). **Embedded**, the turn runs on *this* process's runtime, so Ctrl-C takes the process and the turn with it — after the tokens may already have been spent upstream. The CLI installs no handler on the chat path in either mode, which is deliberate: there is nothing honest to promise at that moment, and a line claiming a cancellation would be false in client mode and unprovable in embedded.
- **Sub-space rooms** — embedded mode does not start the turn driver (see `Session::from_core` for why), so a delegated room a command opens waits for the app. In client mode the answering process *is* running the driver, so it is driven immediately.

Regressions: `client.rs` drives a scripted stand-in for the app over a real socket (the handshake naming the app, a verb answering, an absent socket and a stale one both reading as no-listener, a socket that never greets timing out under a paused clock, both directions of protocol skew naming both versions, an unknown verb costing one command with the connection surviving, a typed `AppError` arriving typed, and a turn whose chunks stream — including a frame for another id that must be skipped an event shape this build has no variant for, and a response line larger than the *request* ceiling arriving intact — answers are read under `MAX_RESPONSE_BYTES` via `FrameReader::for_responses`, because a result grows with the profile while a request does not, and reading answers under the request bound would refuse a legitimate listing as though the app had malfunctioned). `session.rs` covers the pure decisions and the rule end to end: a socket that answers takes the command, `--embedded` skips it even when it answers, a profile held with no socket beside it is the honest refusal rather than a hang, an app greeting from another config root is refused with only `hello` on its record (so the refusal is provably ahead of dispatch), and the account identity is proved to come off disk on every read rather than from anything captured at open. The commands themselves are driven through `run` against a scripted app in `main.rs`, which is where a client-mode command's *wire* behaviour is assertable: what it sent, in what order, and what it refused to print.

## Commands

- `eidola chat` without `--model` leaves the default template's agent model to whichever process takes the turn (see Client mode above); `--model` accepts qualified `<model>@<backend>` references. The model-picker chat path uses `TurnSelector::Model`, so a plain pick reuses the space's matching agent. **Stdout is the answer and nothing else** — reasoning, the engine-loading narration and the closing report all go to stderr, so a piped stdout captures only the text. `chat_summary` is that closing report: the usage footer, and ahead of it a `warning:` line when `ChatResult::truncated` says the answer stopped at the model's length allowance rather than because the model was done (Codex review, PR #330). Without it a mid-sentence answer arrived under an ordinary footer and an exit code of 0 — every other signal reads like success, and `truncated` is the only one that does not. It is pure so what a finished turn says is assertable without taking one, and it leads because it is about the text just printed rather than about the run; the exit code stays 0, because a partial answer is a successful turn with real text in it. Ahead of both, a `note:` line when `ChatResult::declined` says the agent saw the context and bowed out: that turn writes no post at all, so stdout is empty under a full, ordinary footer — precisely what a model that emitted nothing looks like, and `declined` is the only signal separating them. It is a `note:` rather than a `warning:` because nothing is degraded — the decline is the turn working as intended, and the defect was only that no surface said so. `DeclineOutcome::reason` is commentary the agent may omit, so an empty one is reported as an absence ("it gave no reason") rather than left to read as a missing sentence; `action_id` stays out of the line, since a `decision` is not a post and the CLI has nothing to navigate to. Regressions: `an_answer_cut_off_at_the_length_limit_says_so`, `a_declined_turn_says_so`, `a_declined_turn_with_no_reason_still_says_so`, `an_ordinary_answer_says_nothing_extra` (the footer must stay byte-identical for the common case). **`Command::Chat` is the CLI's only `ChatResult` consumer** — there is no regenerate command and no sub-space path here — so the class is one site.
- `eidola backend {list,add openai,add llamacpp,enable,disable,remove,models}` manages the backend registry (`disable eidola` = no-account on-device mode). `add llamacpp` takes `--engine-path` and `--no-auto-start`; `list` shows engine + auto-start state for llamacpp rows.
- `eidola wallet credentials list` prints its two sections — in-flight and active — out of **one** lifecycle read (`wallet_listing` → `wallet_sections`), and that is a correctness property rather than an economy. Settlement removes a `spending` credential and creates its `active` successor atomically, so sampling the two states separately can print a credential still in flight beside the successor it already became: a pair that never coexisted, and the more likely the busier the app is. All three wallet reads hit the same `credential_lifecycle` SQL view, so filtering one snapshot by `state` reproduces both sections exactly; ordering is restored to oldest-first (the snapshot arrives newest-first) with `nonce` breaking ties, so the display order is stable rather than merely sorted. **Embedded mode had the same two-read shape** and was coherent only because nothing else holds the profile to write during a one-shot command — a fact about deployment, not a property of the code — so both modes now read the one snapshot. `spend_amount` is optional on a lifecycle row where the per-state query typed it as always present; the absent case is unreachable through a healthy profile and is therefore *said* (`charge not recorded`) rather than rendered as `0 charged`, a number that would read as a fact. `recover` still uses the per-state read, which is coherent on its own. Regressions: `the_two_sections_are_one_snapshot_split_in_two`, `an_in_flight_line_never_invents_a_charge`, and `the_wallet_listing_reads_one_snapshot` — which drives a scripted app that settled *between* the moments a two-read listing would have sampled, and fails if the listing takes a second read at all.
- `eidola model {list,download,delete,load,unload,pin,unpin}` manages local llama.cpp models. A chat against any engine-served model loads the engine on demand inside the request path (the CLI narrates the wait); `eidola model load` serves until Ctrl-C. **`list`'s table is a directory *scan*, so it cannot be the running-engine answer** (`crates/eidola-app-core/AGENTS.md` → Local models): an engine whose backing `.gguf` was deleted or renamed under it holds its port and its memory while no row carries it. **The reconciliation runs in both directions, because one payload must tell one story.** `reconciled_status` is the other half, and the fix a second Codex review earned: a row's `Loaded`/`Loading` comes from *the very same engine map* the registry reports — the scan takes that lock once per directory entry it walks, and the registry is read after the whole walk — so where they disagree the registry is simply the later read of one map. A row claiming an engine the registry no longer carries is describing a subprocess that has since exited or been unloaded, and it is rendered `available`; before this, `model list` printed a stopped engine as running while holding the authoritative answer in the same response. A row the registry *does* carry takes its port and pin from that later read too. Only a claim of *running* is reconciled: a `Downloading` row is left alone even when an engine for its id exists, because that pair is real (re-downloading a slug whose engine is still up) and promoting it would hide the transfer the row exists to report — that engine earns its own line below instead. `unaccounted_engines` is that other direction: it reconciles the scan against `AppCore::running_engines` — the in-process registry — and prints a `running engines not listed above:` section for every engine no `Loaded`/`Loading` row already spoke for, flagged `— backing file missing` only when **no row the scan actually found** carries the id (external `llamacpp` backends included, whose models this table never prints — those are listed, not flagged). **Row existence is not that evidence**, which is the fix a Codex review earned: the managed store *synthesizes* rows for an in-flight download (streaming to `<file>.part`) and for a standing failure that left nothing on disk, so re-downloading the very slug whose `.gguf` was deleted under a running engine would otherwise talk the flag away at exactly the moment it became true. The evidence is `LocalModelInfo::on_disk` — app-core's own record of which rows came from the directory scan — read on both sides of the reconciliation. The same bar governs the listing's **catalog markers** (`catalog_installed`, joined on `file_name` instead of id): a failed or in-flight download of a catalog entry leaves a row named exactly like it, and calling that `[installed]` would talk the reader out of the retry the row's own error line is asking for. Full class inventory: `crates/eidola-app-core/AGENTS.md` → Local models. No such engine ⇒ no section, so the normal listing is byte-identical. Unit-tested in `main.rs`. Note the registry belongs to whichever process owns the engines: in embedded mode they are children of the CLI process that loaded them, so a one-shot `model list` sees an empty registry and this section is reachable only from a process that loaded an engine itself (in client mode it is the app's registry, and the section is reachable from any invocation) — the reconciliation is what keeps the two sources from ever disagreeing silently, and it is what any longer-lived CLI (a REPL, a service-attached listing) needs from day one.
- `eidola configure` writes the eidola connection + trust bundle as per-column overrides on the `eidola` backend row; each member has a clear-to-pin flag, `--clear-trusted-measurements` included (see `crates/eidola-app-core/AGENTS.md` → Backend registry for why reverting by key isn't enough). **Every input is resolved and validated before the first write** — PEM files read + parsed (`config::validate_cert_pem`), measurement specs parsed — because the bundle is written a column at a time, so a late parse failure used to leave the client half-redirected (base URL committed, measurement rejected, exit 1). Input-shaped failure is now all-or-nothing; a *write* failing mid-sequence (local DB error) is not covered and would still split the bundle. **Blank input is not a clear on a file path:** `parse_cert_config` maps blank to "no value" (right for the config surface, where the setter then clears the column), so an empty `--hardware-*-ca` file used to pass validation and silently revert the chain to the pinned AMD roots *while `--base-url` aimed the client at the mock shim* — `configure` exiting 0 having built a client that fails every handshake. `read_ca_pem` rejects blank contents and points at `--clear-hardware-*-ca`. `just client-local` / `just client-reset` drive it for local-stack dev.
- `eidola update check` runs the update-notification check and prints the same five states the GUI's Updates window renders (exit code 2 = unverifiable security state, 3 = claims-changed); the previous full-pipeline command moved to `eidola update verify`. **The verdict is about the build that ran it**, which in client mode is the app's: the comparison uses the running build's version *and* the claim expectations compiled into it, and the persisted state it folds into is the profile's. So "up to date" names the build that was compared rather than this binary's version, and `update_check_attribution` prints a `note:` naming both builds when they differ — the same command reporting a different availability or security state merely because the app is running is a fact to disclose, not to hide. Same release ⇒ no note: the version names the release and the expectations come from that release's trust root, so the app reached the answer this binary would have. Pure, so it is assertable without a check: `an_update_verdict_from_another_build_says_whose_it_is`.
- `eidola account checkout` **binds the link to the account it was minted for.** The URL is minted against the credentials held when the request goes out, and that round trip is long enough for the account to be reset or reconfigured under it — in client mode by the app, which owns the profile. Printing or opening it then would offer to fund an account whose secret this machine no longer holds, under the current account's name. So the identity is captured before the mint and re-checked after (`Session::account_identity`), and a mismatch is `Failure::AccountReplaced` — nothing printed, nothing opened, with a hint pointing at `eidola account show`. This is the same guard the GUI keeps in its own view (`eidola-gui/src/account.rs` → `mint_is_current`); embedded mode cannot reach the race, since this process holds the profile's only writer lock for the whole command, but the check is one path for both modes rather than a mode-specific exception. Regressions: `a_checkout_link_minted_for_a_replaced_account_is_refused`, `a_checkout_link_for_the_account_still_configured_is_offered`.
- `eidola account create --accept-terms` records terms acceptance; `eidola account accept-terms` handles re-acceptance after a 428. Both **print a snapshot and then submit that same snapshot** — the documents are fetched once and passed into `account_create` / `accept_terms`, so a version published while the prompt was open is refused by the server rather than agreed to unseen. **Neither flag suppresses the display**: `--accept-terms` and `--yes` decide whether a second invocation or a prompt is needed, never whether the documents are shown, because a claim of agreement cannot be made about text the run never printed. `CreateConsent` in `main.rs` is that rule as a decision rather than a condition chain, and `account_create_never_submits_documents_it_did_not_print` sweeps every input for it. **Both then report the account's standing** through `report_terms_standing` (`TermsAcceptance`, read back from the server): silence only for `Complete`, a named warning for `Outstanding`, and a distinct one for `Unknown`, because a reader told nothing concludes there is nothing to do. Accepting every printed document is not the same as having nothing left to accept — a document that became required while the prompt was open was in no snapshot and refused by no submission — and the CLI is currently the **only** surface that tells the user at all, so this wording is the whole remedy.
- `eidola service {install,start,stop}` — see below.

## `service.rs` — the Linux systemd user service

`install` writes `$XDG_CONFIG_HOME/systemd/user/eidola.service` — a `const` template with the resolved `eidola-gui` path substituted, launching it `--windowless` — then `systemctl --user daemon-reload` + `enable`; `start`/`stop` are the matching calls. **These three verbs are handled in `main` before the core is built**, because the running service holds the database lock and `service stop` must work exactly then.

The doctrine below was verified empirically against systemd 257 (`systemd-path`, `systemd-analyze --user unit-paths`, `systemd-analyze verify`); don't relax it without re-verifying:

- **A relative `XDG_CONFIG_HOME` is ignored, not honored** (`resolve_config_home`): the XDG spec calls a relative value invalid, and systemd obeys — with `XDG_CONFIG_HOME=rel/cfg`, systemd still resolves `$HOME/.config` and searches `$HOME/.config/systemd/user`. Honoring it would file the unit where the manager never looks and report success for a service that doesn't exist. Whoever resolves this path must agree with **systemd**, not the spec's letter alone. Empty and unset fall through the same way, and **the `HOME` fallback obeys the same rule** (systemd ignores a relative or empty `HOME`, answering from the passwd database). Where we diverge: systemd has a third source we don't read, so rather than guess we refuse — honest and actionable, unlike resolving against the CWD.
- The resolved exec path is made **absolute, existing, and executable *by the installing user*** (`absolute_existing_exec`): lexical `std::path::absolute`, deliberately *not* `canonicalize` — the two things a `--exec` most often names are symlinks on purpose (a Nix profile entry, `target/release/eidola-gui`), and pinning to today's link target would silently keep launching an old binary after rebuilds. Executability is `faccessat(…, X_OK, AT_EACCESS)` via `rustix`, not a mode-bit mask — a root-owned mode-`010` binary has an execute bit this user still can't use; only the kernel's effective-uid check (supplementary groups included) answers the question, and systemd rejects such a file too.
- **A control character in the path is refused outright**: systemd cannot express one in a command name — raw (even quoted) *splits the directive*, and the C-escaped form is decoded then rejected as `Executable path contains special characters`. There is no third encoding, so the refusal joins the missing/non-executable cases at the before-any-write seam; the message escapes the path rather than echoing the offending byte. A **space** is unaffected: quoting covers it.
- **PATH discovery shares the exact usability predicate** (`is_usable_exec`) and walks *past* an unusable candidate to a later good one (`which`'s first-runnable-match semantics) — a stale `chmod`-less copy earlier on `PATH` can't mask a working install, and discovery can never hand `resolve_exec` a path its own gate refuses.
- **Quoting** (`systemd_quote_exec`): `"…"` with `\`-escaped `"`/`\`, and `%` → `%%`. `ExecStart=` splits on whitespace, so unquoted spaces would truncate the program word. **`%` is escaped but `$` deliberately is not**: a specifier expands everywhere (quotes included), while environment expansion does *not* apply to the program word — escaping `$` to `$$` would be corrupting (systemd takes the doubled form literally). The function is named `_exec` because the rule flips for a later *argument*; the unit's only other word is the fixed literal `--windowless`.
- **The install preflight probes `systemctl --user daemon-reload`, not `--version`**: the version query is answered by the binary and succeeds where no per-user manager runs (containers, WSL), which previously produced half-installs. `daemon-reload` is the cheapest call that must reach the user manager, is idempotent, and is needed anyway — so refusal happens before any write (the zero-trace pattern).
- The unit is a Rust `const` rather than a `data/` asset on purpose: the Nix build's crane source filter keeps Rust plus a short extension allowlist (`.sql`, `.ttf`), so a `.service` file would silently vanish from the packaged source.

Unit-tested against a temp XDG dir in `service.rs` (rendering, quoting, `$`/`%` handling, resolution, refusal cases, discovery walk-past, idempotent rewrite, relative-XDG ignore).
