# eidola-server-engine

The process on each inference node: it serves **exactly one model**, of any architecture the engine implements (MiMo-V2.6-Flash; DeepSeek-V4.1-Flash text only, *DeepSeek-V4.1-Flash* below; Qwen3.8-27B text only, *Qwen3.8-27B* below; Qwen3.5-2B and -0.8B text only, on the CPU executor, *Qwen3.5* below), through Eidola's own engine crates (`eidola-engine`, `-chat`, `-model`, `-cpu`, and `-cuda` in a `cuda` build), in process, behind a narrow HTTP API that only Eidola's gateway calls. Requests flow client → gateway → node; TLS and attestation are the enclave shim's job, so the node speaks plain HTTP behind it. AGPL-3.0-only. Workspace conventions live in the root `AGENTS.md`; the engine's own doctrine in `crates/eidola-engine/AGENTS.md` and its siblings.

| Module | Contents |
|---|---|
| `config.rs` | The environment, read once at boot. Every variable is required; nothing is defaulted. Each executor's own settings are required with it and refused with the other. |
| `auth.rs` | The gateway token: its shape checked at boot, compared in constant time per request. |
| `model.rs` | The weights hash (definition below), checked before any weight is loaded; the architecture from `config.json`; `LoadedModel` and what it serves (`Served`). |
| `api.rs` | The strict request subset and its validation. |
| `error.rs` | `ApiError`: full detail to the caller, category-only `Display` for logs. |
| `pipeline.rs` | Prompt (the model's format) → tokens → engine request; tokens → detokenizer → stop sequences → reasoning / tool calls. |
| `worker.rs` | The engine's step loop on its own thread; the channel bridge, admission bound, cancellation; the step watchdog. |
| `http.rs` | Routes and response shapes; the framed stream and the padding of every other response. |
| `telemetry.rs` | The node's metrics and logs over OTLP: the coarsened counts and levels, the observable instruments, the pipeline, the process's `instance_id`. |
| `cuda.rs` | (`cuda` feature) The CUDA executors' host-side refusals, their KV block counts derived from the device budgets and their host-tier counts from the host budget, the GPU confidential-computing check, opening the devices, and building the executor: `prepare` for MiMo-V2.6-Flash on one GPU, `prepare_deepseek` for DeepSeek-V4.1 on two (*DeepSeek-V4.1-Flash*), `prepare_qwen` for Qwen3.8 on one (*Qwen3.8-27B*). |
| `gpu_cc.rs` | The GPU confidential-computing check: the decision (a pure function over NVML's reported values, tested everywhere) and, with the `cuda` feature, the NVML query. |
| `swap.rs` | The boot refusal of a guest with active swap (`/proc/swaps`). |
| `lib.rs` | `boot` (verify, load, start) and `start` (over an already verified model). |

The modules are shared by the architectures: where they differ, each module holds one function or match arm per architecture (`prepare`, `prepare_deepseek` and `prepare_qwen` in `cuda.rs`, `render_mimo`, `render_deepseek` and `render_qwen` in `pipeline.rs`), and the per-architecture code they call lives in each engine crate's `mimo`, `deepseek` and `qwen` modules. DeepSeek-V4.1's, Qwen3.8's and Qwen3.5's examples and tests carry their names (`examples/deepseek_generate/`, `tests/deepseek*.rs`, `tests/qwen.rs`, `tests/qwen35.rs`); the other tests are of the shared node (most over the MiMo-V2.6 dev model; `tests/cuda.rs` boots all three).

## What the node trusts, and what it refuses

The node trusts its measured configuration (the environment; see below) and the bytes of its weights directory **only after** they hash to the configured weights hash. It trusts nothing in a request beyond what the strict subset names.

**At boot** it refuses to start (non-zero exit, a content-free message naming the variable or file) on:

- any configuration variable missing, empty or malformed;
- on Linux, for a `verified-readonly` node or one with a host tier, any active swap area (`swap.rs`, first of all; see *The host tier*);
- a gateway token of any shape but the gateway's (`is_gateway_token`);
- `WEIGHTS_STORAGE=verified-readonly` with any weights file (the directory, shards, semantic and chat files) not on read-only storage (`storage.rs`; checked before any weights file is opened, mapped or parsed), or any of those files not a regular file (a symlink, say);
- a file in the weights directory whose name is not UTF-8 (the manifest is keyed by exact names; checked from the listing, before hashing);
- a weights directory whose weights hash differs from `WEIGHTS_SHA256` (checked before dequantising anything);
- a file the architecture reads missing (`weights_manifest::required_files`), an unpinned tokenizer or chat template (the chat crate's pins), a tokenizer larger than the model's head, or an unusable `generation_config.json`;
- sizing the model or the engine core cannot honour: `MAX_MODEL_LEN` above `max_position_embeddings`, more draft tokens than MTP layers, or a scheduler configuration `Engine::new` refuses (for example a step budget below one speculative decode row);
- `cuda` as the executor in a build without the `cuda` feature (it does not parse); with it, everything in *The CUDA executor* below (for DeepSeek-V4.1, *DeepSeek-V4.1-Flash* → Executors) that the executor or the node refuses. A refused CUDA executor ends the boot: the node never falls back to the CPU executor.

**Per chat request**, in this order, each before anything is admitted:

| Check | Status | `error.type` |
|---|---|---|
| `Authorization: Bearer <gateway token>` | 401 | `authentication_error` |
| `X-Eidola-Weights-Sha256` present | 428 | `weights_hash_required` |
| … and equal to this node's weights hash (hex, any case); **checked before the body is read** | 412 | `weights_hash_mismatch` |
| a read slot is free (the read bound, below); **checked before the body is read** | 503 | `overloaded` |
| body ≤ 32 MiB | 413 | `request_too_large` |
| strict subset (`deny_unknown_fields` at every level, every content-part variant included) | 400 | `invalid_request_error` |
| `model` is the configured model id | 404 | `model_not_found` |
| `stream: true` with `stream_options.include_usage: true`; text-only content, `tool_choice` `auto`/`none`, ≤ 4 non-empty stops of ≤ 256 bytes each, `max_completion_tokens` ≥ 1, valid `cache_key`; `cached_prefix` in its one shape, with a `cache_key` and at least one cached token (`check_cached_prefix`) | 400 | `invalid_request_error` |
| an admission slot is free | 503 | `overloaded` |
| template accepts the messages; sampling parameters valid (`SamplingParams::new`) | 400 | `invalid_request_error` |
| prompt + 1 fits `MAX_MODEL_LEN` and the KV pools | 400 | `context_length_exceeded` |
| with `cached_prefix`: the tokenized prompt has at most `cached_tokens + new_tokens` tokens | 409 | `prompt_budget_exceeded` |
| with `cached_prefix`, at the engine's first admission: its prefix cache holds at least `cached_tokens` of the prompt's leading tokens under the key (a `cached_tokens` reaching the final prompt token never can) | 409 | `cached_prefix_missing` |

Every `error.type` is an `eidola_common::engine_protocol::error_type` constant. A gateway sends a refused request to another node only when `engine_protocol::refused_before_admission` holds for its status and type: the first three rows, `model_not_found`, and `overloaded` (raised only when a read or admission slot is not free). `error::tests::only_pre_admission_refusals_say_so` holds every `ApiError` to that list, so a refusal raised after admission (`engine_unavailable`, once the engine has a request) must never reuse one of those types. The two declared-prefix refusals are not on it (the cache a declaration names is on the node its key routes to, so another node would refuse it too): a gateway returns them to its client by `engine_protocol::declared_prefix_refusal`, which `error::tests::declared_prefix_refusals_say_so_and_nothing_else_does` holds to exactly those two `ApiError`s.

The authentication check is about money, not privacy: it keeps anyone but the gateway (which bills) from spending the node's compute. No privacy property depends on who can call the node. Authentication precedes the weights check, so an unauthenticated caller learns nothing about the weights.

The weights-hash check is redundant with the node's measurement (which covers the weights) but early, cheap and independent: a gateway sends the hash from its own compiled-in pin (`releases/trust/engine-enclaves.json`, via the gateway's `engine_trust::protocol`), never from placement data, so a misregistered node refuses traffic rather than serving the wrong weights. The header's name is `eidola_common::engine_protocol::WEIGHTS_HEADER`, which both sides read. `GET /v1/engine/info` reports the verified hash so a misregistration is visible before any traffic.

## The weights hash

The node's weights hash identifies every covered file the weights directory holds, and so every file it reads from it:

- every `*.safetensors` file in the directory;
- `config.json`, and `model.safetensors.index.json` when present (the model crate's `SEMANTIC_FILES`);
- `tokenizer.json`, `chat_template.jinja` and `generation_config.json` when present (the chat artifacts). The tokenizer and template are also pinned by the chat crate; `generation_config.json` is not, and it decides MiMo's EOS ids and default sampling, so it must be covered here.

The covered names are the same for every architecture; which must be present is the architecture's (`eidola_common::weights_manifest::required_files`), checked after the hash: MiMo-V2.6 and Qwen3.8 need all four of `config.json`, the tokenizer, the template and `generation_config.json`; DeepSeek-V4.1 needs `config.json` and the tokenizer, and reads `generation_config.json` only when there is one. A covered file the node does not read (DeepSeek's `chat_template.jinja`, its vision shard) is hashed all the same.

The **manifest** is one line per file, `<sha256, lowercase hex>␠␠<file name>\n` (exactly `sha256sum`'s output), sorted by file name in byte order. The weights hash is the SHA-256 of the manifest's bytes, lowercase hex. The spelling and the file set are shared with the gateway's model catalog (`eidola_common::weights_manifest`: `canonical_manifest` and `is_safe_name` here delegate to it, and `the_hashed_files_are_the_catalogs` holds this node's file lists to its `COVERED_FILES`), whose build checks each catalog row's published per-file manifest aggregates to the row's hash (`canonical_manifest_for` the row's architecture). It is the model's identity everywhere (`docs/model-identity.md` specifies it for reimplementation, with `scripts/weights-hash.py` to recompute it). It pins the weights, not exact behaviour: the engine build and its numerics are pinned by the deployment's measurement, not by this hash. Every manifest name is a **safe name**, `[A-Za-z0-9_][A-Za-z0-9._-]*` (`model-00001-of-00002.safetensors`): a shard named otherwise is refused from the listing, before anything is hashed, and `canonical_manifest` refuses one too. That is what makes the offline procedure below reproduce the manifest byte for byte: `sha256sum` escapes a name holding a backslash or newline (prefixing its line with `\`), `xargs` splits on whitespace and quotes, a leading `-` reads as an option, and the shell's `*` skips a leading `.`. Any name in the directory that is not UTF-8 is refused too (the model crate's `WeightSet` also refuses a non-UTF-8 shard name rather than converting it lossily, so distinct names can never share a manifest entry). Offline, inside the directory:

```sh
LC_ALL=C ls *.safetensors config.json model.safetensors.index.json \
    tokenizer.json chat_template.jinja generation_config.json 2>/dev/null \
  | LC_ALL=C sort | xargs sha256sum | sha256sum      # macOS: shasum -a 256
```

Every byte used is a byte hashed: shards are memory-mapped once and both hashed and loaded from that mapping; the other files are read once and parsed from the hashed bytes. `LoadedModel` can only be built by `LoadedModel::load`, which checks the hash first, and `start` re-checks a loaded model's hash and storage mode against the configuration.

**What binds the bytes after boot is the storage, not this process.** The hash is checked once; the shards stay memory-mapped (shared, file-backed), and routed experts are dequantised from them on later forwards, so a file modified in place after the check would change the model while `/v1/engine/info` still reports the verified hash. Copying hundreds of gigabytes into private memory is not an option, so the binding is the deployment's: in production the weights directory is a dm-verity volume, mounted read-only, whose every read the kernel checks against the root hash in the measured configuration, so no read can return bytes other than those the hash covered. The process does not assume that: `WEIGHTS_STORAGE` is part of the measured configuration, and `verified-readonly` refuses deployments that clearly are not immutable, **before any weights file is opened, mapped or parsed** (the directory, then each file named in its listing; only metadata is read):

- every platform: each path's mount is read-only (`statvfs` `ST_RDONLY`). That flag is per mount: a read-only bind mount can sit over a filesystem still writable through another mount of the same superblock, so on its own it is dev-grade, and macOS (development only) stops here;
- **the directory is resolved once.** `model.rs::PinnedDir` resolves the configured path before anything else, and every check, listing and open after it goes through that resolution, never the configured path again, so a symlink on the configured path (or a directory above it) changed after the check cannot redirect what is hashed and mapped. On Linux it is `/proc/self/fd/<n>` of an `O_PATH` descriptor on the directory (no read access; the kernel resolves the magic link to the directory the descriptor holds); elsewhere (development only) the canonical path at that moment. Under `verified-readonly` every file the node reads must also be a regular file (`lstat`, not followed): a symlink's target is resolved again at every open, through paths the directory's read-only mount does not cover, while a regular file in a directory on a read-only superblock cannot be replaced. `dev-writable` follows symlinks (a Hugging Face cache snapshot is one);
- Linux: each path also resolves through `/proc/self/mountinfo` (its device id, and the longest mount point containing its canonical path, the last such mount winning) to a mount whose mount options **and superblock options** both contain `ro`. A filesystem on a dm-verity device always has a read-only superblock, so production passes; a read-only bind over a writable filesystem is refused. Mountinfo is read and parsed as bytes (mount points are byte strings), so an unrelated mount with a non-UTF-8 path cannot block the check.

Verified in containers: a superblock-read-only tmpfs is accepted, while a read-only bind mount of a writable filesystem and Docker's `--tmpfs …:ro` (a read-only mount over a writable tmpfs superblock) are refused; on macOS a read-only disk image is accepted and an ordinary directory refused. What this does not establish: that the bytes are the right ones (the weights hash does that, once), or that a privileged process in the VM will not remount the superblock read-write later; dm-verity is what binds every read. In turn `dev-writable` boots anywhere but says so in `/v1/engine/info` (`weights_storage`) and in `/healthz`'s body. A gateway pins the production configuration, so it never routes to a `dev-writable` node: its build refuses a pinned deployment whose config sets anything but `verified-readonly`.

## Wire contract

`POST /v1/chat/completions` accepts the gateway's strict request subset (`eidola-server-gateway/src/types.rs`: `model`, `messages`, `max_completion_tokens`, `temperature`, `top_p`, `stream`, `stream_options.include_usage`, `stop`, `tools`, `tool_choice`, `add_generation_prompt`, `continue_final_message`, an assistant message's `reasoning_content`, `cached_prefix`, with the same nullability and nested strictness) plus `cache_key`. Keep the two in step: a field the gateway starts forwarding must be added here, or every such request is refused. The gateway refuses what this node would refuse before routing it (`engine_router::subset`): the rules over a parsed request (`tool_choice`, the stop list, a zero completion limit, empty `messages`, image parts) are `eidola_common::engine_protocol`'s `check_*` functions and `SubsetError`, which `api::parse_request` calls too, so a change to one changes both; the content-part strictness and the sampling ranges (`SamplingParams::new`) are mirrored there, so changing either here means changing the gateway's mirror. Before either parse, `eidola_common::engine_protocol::check_request_json` scans the body without allocating and refuses (400) more than `MAX_REQUEST_JSON_VALUES` (2^18) JSON values, object keys counted, or nesting deeper than `MAX_REQUEST_JSON_DEPTH` (64): the parse trees cost memory per value, so the value count is what bounds a read slot. The gateway refuses the same bodies first.

- **Content parts** are stricter than the gateway's: every variant denies unknown fields. The template renders parts from the raw body and treats an `image_url`, `image`, `audio` or `video` key on any part as multimodal content, so a key the strict type does not name must never reach it. `image_url` parts are refused outright (text-only model).
- **`tool_choice`**: absent or `auto` offers the tools and parses calls; `none` renders the prompt **without** the tool definitions (the model is never offered a tool it may not call) and parses nothing, so it changes the prompt, and with it the reusable cache prefix, relative to the same request under `auto`; `required` and named functions are refused (no constrained decoding). App-core's chat path never sets `tool_choice`, but its local inference proxy relays whatever a local caller sends, so `none` is reachable and is supported exactly rather than refused.
- **`cached_prefix`** (`eidola_common::engine_protocol::CachedPrefix`, `{"cached_tokens": <u32>, "new_tokens": <u32>}` and nothing else; `null` is no declaration): the client's statement that the first `cached_tokens` tokens of the prompt as this node tokenizes it are in the prefix cache under the request's `cache_key`, and that the prompt has at most `new_tokens` more. The request is priced by those two numbers upstream, so the node runs it only if both hold and refuses it `409` otherwise, before anything of it is computed: the budget after tokenizing (`pipeline::prepare`, before submission, and **after the window**: a client budgets what a request adds at no more than the window leaves, so a prompt past the window is past that budget too, and it is refused for its length, since a client told its budget was exceeded sends the request again undeclared and would be refused and charged a second time; `a_declared_prompt_past_the_window_is_refused_for_its_length`), the cached part by the engine at first admission (`Request::required_cached_tokens`; `crates/eidola-engine/AGENTS.md` → A required prefix). **Its response opens only once the engine has admitted it** (`worker::Output::Admitted`, sent before the request's first tokens), so `cached_prefix_missing` is a plain HTTP error for a streamed request too, however long it waited for a seat; a request without a declaration opens its response as soon as the engine accepts the submission, as before. The usage reported is unchanged: `prompt_tokens_details.cached_tokens` is the hit the engine found, at least the declared number on a served request, and never an input to a price. **What a client can declare and have served** is `declared_prompt`'s rule on a resumed count the cache really holds as tokens: for a new turn, a tool round or a regeneration, the previous request's `prompt_tokens` (its prompt ends at the generation prompt, and the next one continues after an added token, so it is a token prefix: `a_new_turn_declaring_the_last_ones_prompt_is_served`, `a_regeneration_declaring_its_prompt_is_served`). For a continuation, prompt plus completion holds only where the continued prompt re-encodes to the earlier prompt followed by the generated tokens through the declared boundary; a `continuable` cut promises the text, not that the model sampled the canonical encoding of it, and where it did not (the dev model often does not, `.Large`+`roken` re-encoding as `.L`+`arger`+`oken`) the cache serves only up to the earlier prompt's regeneration point and the declaration is refused. The earlier prompt alone, with the completion counted as added bytes (`declared_prompt(prompt_tokens, completion_bytes, 0, window)`), is served in every case tested (`a_continuation_declaring_prompt_and_completion_needs_canonical_tokens`).
- **`cache_key`**: 32 bytes, base64url without padding — the shape `eidola_common::engine_protocol` states, which the gateway checks before a request is paid for (`api::tests::the_decoder_agrees_with_the_shared_shape_rule` holds this decoder to it). Decoded at parse time, the text scrubbed, and turned into the request's lineage under the core's per-boot key (`SaltDeriver::lineage`): the engine salt `HMAC-SHA256(boot_key, "eidola/kv/v1" ‖ key)` that names its cache entries and the key `HMAC-SHA256(boot_key, "eidola/kv-enc/v1" ‖ key)` its idle KV is encrypted under; the decoded key is dropped (zeroed) before the request reaches the engine. No key ⇒ `CacheScope::Private`: a fresh random salt and key, nothing reusable by any other request.
- **Messages and tools render from the body as sent.** The strict serde types only validate; the prompt is rendered from the same bytes parsed by the chat crate's order-preserving JSON parser, because `serde_json::Value` would sort keys and round big integers that the template prints.
- **Request data is never a control token.** The prompt is encoded with the chat crate's `encode_prompt` over `render_prompt`'s data spans: an added token (`<|im_end|>`, `<|im_start|>`, `<think>`, `<tool_call>`, …) spelled by a message, a tool result, a role, a tool-call name or argument, or a tool definition is encoded as ordinary text, and only the template's own text makes one (`crates/eidola-engine-chat/AGENTS.md` → Request data is never a control token; `tests/control_tokens.rs`). Nothing is refused or rewritten: the text reaches the model as text.
- **Sampling**: `temperature` and `top_p` from the request, else `generation_config.json`'s (as vLLM applies a model's generation config), else 1.0; `top_k` from the generation config; a fresh random seed per request.
- **A `length` ending says whether it can be continued exactly**: the finishing choice carries `continuable`, the chat layer's `resumes_exactly_as_tokens` over the engine's own output, the decoder's lossy final flush included (`a_length_ending_says_whether_it_can_be_continued_exactly`). The verdict holds in tokens: the decoder tells the chat layer where the model sampled added tokens, and an ending is continuable only when those are the tags the template writes back, since everything else a client returns is encoded as text (`tests/control_tokens.rs`). It is also false where a continuation could not run or would not be exact for the node's own reasons: when the ending is the **context window** rather than the request's `max_completion_tokens` (`Prepared::window_bound`: no limit, or one at or past the room, leaves a continuation prompt of the whole window, refused `context_length_exceeded`; `a_length_ending_at_the_context_window_is_not_continuable`), when the engine ended it for lack of KV memory (`FinishReason::KvExhausted`, which reads `length` on the wire: a continuation's prompt is the same tokens and needs at least the memory this one ran out of, so it would be refused or end the same way; reachable only with pools smaller than one `MAX_MODEL_LEN` sequence, which the CUDA executor's derivation refuses; `a_length_ending_out_of_kv_memory_is_not_continuable`), when the stop matcher was holding a possible partial stop sequence at the cut, and when the model sampled a special token, which the text given out does not show. A client continues only where it is `true`.
- **Continuation** (`continue_final_message`, `add_generation_prompt: false`): accepted under `check_continuation`, the prompt rendered ending inside the final message at the field continued (`crates/eidola-engine-chat/AGENTS.md` → Continuation) and the output parsed from there. Under the request's cache key the engine's continuation hit point (`crates/eidola-engine/AGENTS.md`) is where the previous request's sealed prompt-plus-output ends, so a continuation is served from cache up to the first token its re-encoding diverges at, and at least through the previous prompt's last whole block.
- **`max_completion_tokens`**: clamped to the room left in `MAX_MODEL_LEN`; absent means that room.
- **Stop sequences** are matched here on the decoded text (special tokens skipped), before reasoning/tool parsing, by one KMP automaton per sequence (at most 4 sequences of at most 256 bytes, `api::MAX_STOP_BYTES`: stops are delimiters, Eidola's chat path sends none and its local proxy relays only a local caller's, and the cap bounds the matcher's tables and held-back text to a few kilobytes per request, which an uncapped 32 MiB body would amplify to hundreds of MiB): only the longest suffix that is a prefix of some sequence is held back, so text that cannot begin one is released at once, and the work is linear in the text however long a sequence is. The first occurrence to complete wins; on a match the text before it is released, the sequence and everything after it dropped, `finish_reason` is `stop` (or `tool_calls` if calls were emitted), and the engine request is cancelled. `completion_tokens` counts through the token that completed the match.
- **Every answer is a stream.** A request must ask for one, `stream: true` with `stream_options.include_usage: true`, and is refused (400) otherwise: the running count below is what the gateway bills a request it ends early by, and the frames are what let it tell a slow engine from a stopped one, so the gateway asks for a stream whatever its own client asked for and assembles a client's blocking answer itself (`crates/eidola-server-gateway/AGENTS.md` → Routing to engines). The stream is OpenAI's chunk shape: a role chunk at once, one chunk per non-empty delta (`reasoning_content`, `content`, `tool_calls` with `index`, each call whole), a finish chunk with an empty delta (and `continuable` on a `length` ending), a usage chunk with `choices: []`, then `[DONE]`. A mid-stream failure ends the stream with an `event: error` event. Every stream is written in frames, and every other response padded (Response shape, below).
- **Usage** includes `prompt_tokens_details.cached_tokens`, the prompt positions served from the prefix cache. It is for the client's information only: nothing here prices, and the gateway's charge never depends on it.
- **The running count.** The role chunk and every delta chunk also carry the running `usage`: the prompt, and the completion tokens decoded so far, text the stop matcher holds back included. A step that moved the count and gave out no delta (a tool call still being read, which the parser gives out whole at its end; a held stop prefix or partial tag; a skipped special token) sends a chunk with an empty delta (`"delta": {}`, `finish_reason: null`) carrying the count alone, which the gateway keeps and does not forward. The gateway keeps the last count it received and charges a stream it cuts short (its client left, its deadline, an engine failure) for exactly that, so this count is what a cut request is billed by; it forwards only the final usage chunk to its client. The gateway cuts a stream by dropping its connection, which the guard turns into a `Cancel` (below). Tests: `streaming_shapes_text_and_usage` (present on every delta chunk, starting at zero, never decreasing, never past the final count; a request without a stream or without `include_usage` refused), `held_back_steps_report_the_running_count` (steps held back by the stop matcher report the count alone).

`GET /v1/engine/info` (gateway token, no weights header) returns `model`, `weights_sha256`, `weights_storage`, `executor` (`cpu` / `cuda`), `device` (`null` for the CPU executor; for CUDA the driver's device `name`, `compute_capability` `"major.minor"`, the kernel `image` it runs, `sm_count` and `memory_bytes`: hardware facts, nothing about any request), `build` (`crate`, `version`, and `git_sha`: the `EIDOLA_GIT_SHA` value the build was given at compile time, `null` otherwise; nothing is read from the build environment implicitly), and `instance_id`, the process's random id, which its telemetry carries as `service.instance.id` (Telemetry, below). `GET /healthz` is unauthenticated and content-free: `200 ok` while the engine thread runs (`ok; weights-storage=dev-writable` on a development node), `503` after it stopped or once the step watchdog has found it wedged (Concurrency, below). The gateway's router probes both before a node takes traffic and periodically after: `/healthz` must be exactly `ok` and `/v1/engine/info` must report the pinned model, weights hash and `verified-readonly`, so changing either response's shape changes what the gateway accepts (`crates/eidola-server-gateway/AGENTS.md` → Routing to engines).

## Response shape

The host of this VM and the network between it and the gateway see each write's size and time, so neither follows the answer (`docs/privacy-guarantees.md` §3.8; the reasoning, the published attacks and what the client hop does: `crates/eidola-server-gateway/AGENTS.md` → Client-facing traffic shape).

- **A stream is frames of one size on a fixed tick** (`http::Shaped`): `eidola_common::engine_protocol::STREAM_CADENCE`, one 4 KiB frame every 20 ms, from the moment the response opens (the role chunk is in the first) until the frame that carries `[DONE]` or the `event: error`. Each tick takes what the engine has produced since the last off the request's event channel (`try_recv`, up to `STREAM_BACKLOG_BYTES` waiting) and writes one frame: whatever event bytes are waiting, up to its size, and padding the reader ignores for the rest. The events are cut by `eidola_common::stream_shape::Framer`, the gateway's own framer for its client, and the gateway reads them back with that module's `StreamReader`, so the two sides of the hop share one format; the tick is this node's own (`tokio::time::Interval`, a late tick moving the schedule rather than doubling up). `Cache-Control: no-cache, no-transform`, and nothing here compresses.
- **The rate, against the fastest stream.** A chunk is one engine step, not one token (a step's accepted tokens, up to `1 + DRAFT_TOKENS`, are one delta), and with the running usage and the model's 64-digit id it is about 400 bytes on the wire. 200 KiB/s is about 500 chunks a second, a step every 2 ms, and 2,000 tokens a second at four tokens a step; the fastest single-request decode step measured for the served model on its GPU is 7.3 ms, in another serving engine, and this one's is slower (`crates/eidola-engine-cuda/AGENTS.md`), so the cap does not bind. The engine's aggregate rate across requests does not enter: each stream has its own frames. Faster output waits in the stream's backlog and is delivered at the cap; past `STREAM_BACKLOG_BYTES` (1 MiB, five seconds of frames) the stream stops taking output, its event buffer fills, and the engine cuts it off as it cuts off a reader that stopped (Concurrency, below). **Cost**: up to 20 ms between a step and its frame, and 200 KiB/s on the connection for as long as a response runs, mostly padding.
- **Every other response is padded** (`http::shape_response`, a layer around every route and the fallback): the body with trailing spaces to `stream_shape::body_bucket` (the next power of two, at least 4 KiB) and a matching `Content-Length`: every `ApiError` refusal (the authentication refusal included, which no handler sees), `/v1/engine/info`, `/healthz`, a 404 or 405. JSON is unchanged by trailing whitespace; the gateway's probe compares `/healthz` with its padding set aside (`stream_shape::unpadded`).
- **What it does not hide**: when a response opened (after admission, before prefill; for a request declaring a cached prefix, after the engine's first admission of it, so its time waiting for a seat too) and how long it ran; a padded body's bucket; the request, which is not padded; and this VM's own activity (its scheduling, and the GPU's work and transfers), which the host observes directly.
- Tests: `a_streamed_answer_is_frames_of_one_size_on_a_tick` (over a raw socket: every HTTP chunk is the frame size, the writes are at least a tick apart, and the frames read back as the events), `every_other_response_is_padded_to_a_bucket`; the framer and reader's own tests in `eidola-common` (`stream_shape`). `TestNode::chat_stream` reads every streamed test through the shared reader and checks the body is whole frames.

## Concurrency

The executor seam is synchronous, so one dedicated thread owns the `Engine` and runs its step loop. HTTP tasks reach it over channels: commands (`Submit`, `Cancel`) in, one bounded event channel per request out (`worker::EVENT_BUFFER` = 256 events, each one step's few tokens; the engine thread never blocks on a reader). A reader that has gone away, or has stopped reading long enough to fill its buffer, is cut off at the next send: the request is cancelled in the engine (no more compute) and its channel closed, so the reader gets an error after draining. A streamed response drains its channel once a tick (Response shape), and its byte-bounded backlog and the kernel socket buffers behind it absorb far more than 256 events, so only a reader that has truly stopped is cut off. Between steps the thread drains every pending command. When the last request in the engine ends (finished, or cancelled while running), the thread runs the maintenance it left at once (`Engine::flush`: the blocks it left cached encrypted, the ones it freed zeroed, the keys those operations carried dropped) before publishing its counters, rather than leaving it to the next sweep; with requests still running, the next step runs it anyway. When idle it sleeps until a command arrives or the one-second sweep is due, and sweeps the prefix cache so expired KV is zeroed without traffic. The idle sweep keeps an absolute deadline (each wait is for the time left until it), so commands that leave the engine idle (refused submissions, cancels of finished requests), however frequent, cannot postpone it; while busy, each engine step sweeps on the core's own schedule.

- **Admission** is bounded by `MAX_REQUESTS` (rendering, tokenizing, running or queued). A permit is taken before rendering or tokenizing and is **owned by the work it bounds** for that work's whole life: it moves into the blocking preparation task (which runs to completion even when a disconnect drops the handler), comes back with the prepared request, travels with the submission, and is then shared between the engine's record of the request and the response's guard, which lives exactly as long as the request's receiver: the slot is released only when the request has left the engine **and** its buffered output has been drained or dropped. Buffered output is therefore bounded by `MAX_REQUESTS × EVENT_BUFFER` events. With none free the request is refused at once (`overloaded`); nothing queues unboundedly in front of the engine. Rendering and tokenization run on the blocking pool.
- **Reading is bounded too.** The body (up to 32 MiB) and its two parses (the strict serde types and the order-preserving JSON) exist before admission, so a second bound with as many slots as admission (`AppState::reading`) covers them: a slot is taken after the weights-hash check and before the first body byte is read, and released once the request holds its admission permit or is refused. With none free the request is refused at once (`overloaded`), its body unread. Request memory in front of the engine is therefore at most `MAX_REQUESTS` bodies of ≤ 32 MiB with their parses (being read or parsed) plus `MAX_REQUESTS` parsed requests (admitted, being rendered or tokenized), whatever the traffic. The gateway is the only authenticated caller, so a slow upload holding a read slot is the gateway's own doing.
- **Cancellation**: each request holds a guard that sends `Cancel` when dropped, so a client disconnect (the SSE stream or the handler future dropped) releases the sequence before the engine's next step, including a request still waiting for a seat. Independently, the engine thread cancels a request whose reader has gone away the next time it has output for it.
- **Failure**: an `ExecutorError` is fatal (the host cannot know which writes landed). **Any** exit of the engine thread (that, a panic, every handle dropped) is fatal, structurally: the thread owns an `ExitSignal` whose drop (on return or unwind alike) turns health `503` and resolves `Node::engine_stopped`; `serve` treats that receiver resolving in any way, signal or dropped sender, as fatal and returns an error at once, without draining (graceful draining is only for SIGINT/SIGTERM); `run` then tears the runtime down within `TEARDOWN_LIMIT`, so open connections (even one stalled mid-upload) cannot keep the process alive, and `main` exits non-zero. In-flight requests see their channel close and get an error.
- **A step that never returns is fatal too** (`worker::Watchdog`). The executor seam is synchronous, so a step stuck inside the executor (a driver call that never returns) would otherwise go unnoticed: health would stay `200 ok`, so the gateway's probe would keep passing and its breaker stay closed; new requests would queue behind the stuck step until admission filled and then be refused `overloaded`, which the gateway counts as load, not ill health; and every open stream would go on carrying padding frames on its tick, so its request would be held to the gateway's 30-minute deadline. So the engine thread records when each call that reaches the executor starts (`Engine::step`, the idle `Engine::sweep`, the last request's `Engine::flush`) and clears it when the call returns, and a watchdog on its own OS thread checks it a few times per limit; it shares only atomics with the engine thread and the map of in-flight requests' channels, which the engine thread never holds locked across an executor call. Its own thread, not a task, because it must run when the runtime's workers are busy or the runtime is gone, and must take nothing the stuck thread or the runtime might hold: the map is taken with `try_lock`, bounded, and the exit follows whether or not it was. Nor does the exit wait on output: the log line saying why is written by a thread of its own, because the log's writer blocks while standard output is full or locked (`a_wedged_engine_ends_the_process_though_its_log_cannot_be_written`). A call running past `worker::STEP_STALL_LIMIT` (120 s; its doc comment gives the reasoning: the longest legitimate step, a full step budget of prefill at the end of a 2^20-position context, estimates to about 14 s on the B300) trips it, once: health turns `503`, `submit` refuses (`engine_unavailable`) rather than queueing behind the stuck step, every in-flight request gets `Output::Failed` (its channel closes after it), so each stream's next frame carries an `event: error` and the gateway settles it on what was generated and counts the failure toward its breaker; it logs one content-free line, waits `STALL_EXIT_GRACE` (1 s, fifty ticks) for the frames, and ends the process with `libc::_exit(STALL_EXIT_STATUS)` (70), which runs no `atexit` handler or library destructor (the GPU driver's among them) that could wait on what the stuck thread holds, so the platform restarts the node. The stuck thread is never joined. Only if the step returns during the grace does the engine thread stop by itself first (`stopped`, then `main`'s ordinary non-zero exit). Not watched: the executor's construction at boot (weights load, graph capture; the node does not listen until it is done) and its drop at the end of a graceful shutdown, which `ENGINE_SETTLE_LIMIT` bounds.
- **What a wedged node's exit does not scrub.** The stuck thread owns the executor and the engine, and nothing else may touch them, so the forced exit runs none of what an engine stop does: no last `flush` (freed blocks still holding KV not zeroed, blocks left idle not encrypted), no executor drop (the CUDA executor's zeroing of its whole device memory and step scratch, `crates/eidola-engine-cuda/AGENTS.md` → Idle scrub). Device memory at that moment, the plaintext KV and scratch of the requests in flight included, is left to the driver as the process ends; the node does not scrub it and does not rely on the driver to. Host memory (the CPU executor's pools, the host tier, whose blocks are ciphertext anyway, the process's own buffers) goes back to the guest kernel, inside the confidential VM, which zeroes a page before it maps it into another process as anonymous memory. Idle cache entries stay ciphertext under keys held only in the dying process's memory. The engine's privacy invariants 4 and 6 (zero on free, bounded retention) describe a running engine and are not covered across this exit.
- **Graceful shutdown is bounded.** On SIGINT/SIGTERM `serve` stops accepting and lets open requests finish for at most `DRAIN_LIMIT` (5 s); `run` then tears the runtime down (`TEARDOWN_LIMIT`), which drops every request still open, so each guard cancels its request in the engine by the ordinary path. `main` keeps no engine handle, so with the router gone the engine thread runs the maintenance those requests left (freed KV zeroed, idle KV left encrypted, keys dropped) and stops, and `run` waits for that for at most `ENGINE_SETTLE_LIMIT` (2 s) before the process exits `0`. A long generation or a stalled reader therefore cannot hold the node until it is killed (`tests/engine_exit.rs`).

## Content-free by construction

Prompts, outputs, cache keys and salts are content; so is anything derived from one request (its token counts, its error details). None of it is logged:

- `ApiError`'s `Display` (the only rendering that reaches logs) is the error category alone; the detail goes only into the caller's response body (`error.rs`, tested).
- Configuration and boot errors name variables, files and limits, never values; the gateway token is held only as its SHA-256 and prints as a redaction marker.
- The engine core's secret types (`CacheKey`, `EngineSalt`, `KvKey`, `Lineage`) print redacted and are zeroed on drop. The cache key is decoded into a fixed stack buffer handed to `CacheKey::from_buffer`, which copies it into the zeroizing allocation and scrubs the buffer; the key's JSON text is scrubbed too: serde deserializes it straight into `api::CacheKeyText`, which zeroes it on drop, so it is scrubbed even when a later field fails to parse and serde drops the partly built request; the order-preserving parse's copy is zeroed explicitly. Not reachable from here: the body's bytes in the HTTP stack's shared read buffers, and serde_json's scratch buffer when the key's JSON string uses escapes. The gateway token is scrubbed after boot verification, but stays in the process environment (removing a variable is `unsafe` in this edition).
- `ValidRequest` prints a marker, not its fields.
- **Freed heap memory is zero.** The binary's global allocator (`zeroing::ZeroOnFree` over the system allocator, installed in `main.rs`) zeroes every heap block before freeing it, and grows or shrinks a block by allocating, copying and freeing the old one zeroed, never by the system allocator's own `realloc`, which would free the old block with its contents. So what the node handles per request (bodies, parse trees, rendered prompts, token ids, output text) and what the CPU executor computes per step (`eidola-engine/AGENTS.md` → Privacy invariants, Step scratch) is gone from host memory once freed. Allocation is the system allocator's, untouched, so no executor computes a different number under it. The zeroing stores are kept by an empty `asm!` block that takes the block's address. It does not reach the stack, memory a C library or the kernel holds, or heap memory still live (a dependency's cache: the tokenizer's BPE word cache keeps words of past prompts until it evicts them). Cost on the CPU executor over the dev model (`ZEROING_BENCH=1 cargo test --release -p eidola-server-engine --test zeroing`): about 480 MB freed, and zeroed, per 24-token request, and 20 requests in 5.5 to 5.6 s under it against 4.8 to 5.7 s without it on a shared Mac, within the run-to-run spread; the CUDA executor's host heap traffic is a small fraction of that. Tests: `zeroing::tests` (a freed block reaches the system allocator zero; `realloc` keeps the bytes, never calls the inner `realloc`, and frees the old block zero), and `tests/zeroing.rs` (the node over the CPU executor under it, answering the same tokens every time).
- Nothing is logged per request: a line per request is a timestamped record of it, kept wherever the node's logs go (its stdout, and the telemetry vendor's log store). Refusals are answered and not logged; failures are counted (`engine.node.requests{outcome=failed}` for a request the engine could not take, `outcome=stream_failed` for a stream that ended with an error event; `watchdog.rs` checks both). The node logs only its own lifecycle: its configuration and boot, a fatal stop (an executor failure, a wedged step), and its shutdown.

**Counters**: `worker::Stats` keeps content-free counters, zero until the engine has had a request (submitted, finished, cancelled, rejected, refused at admission for a declared prefix the cache does not hold, in the engine, waiting and running, idle-KV keys held, steps, the core's and the prefix cache's own counts). The tests read them, and the node's metrics are made from them (Telemetry, below).

## Telemetry

The node exports its own metrics and logs over OTLP (`telemetry.rs`), through the pipeline the gateway and billing share (`eidola-telemetry`), when its `OTEL_EXPORTER_OTLP_ENDPOINT` (under its prefix) is set and not empty. The endpoint and `OTEL_EXPORTER_OTLP_HEADERS` are deployment secrets (`engine_deployment::SECRETS`), not measured, so a measured config names no telemetry vendor and anyone running these configs points them at their own. The exporters verify with the bundled Mozilla roots over the pure-Rust provider, as the gateway's do. No traces are exported.

**Logs** are the node's lifecycle (configuration and boot, a fatal stop, shutdown), to stdout and, when enabled, through the OTLP log bridge, at the fixed filter `main.rs` explains (the pipeline's own crates at `warn`, so the exporter's events do not feed its bridge). The pipeline starts before the weights are verified, so a refused boot reaches the log store too, flushed when the process exits. The step watchdog's exit (`worker::exit_stalled`, `_exit`) waits on nothing, the log flush included, so its line reaches stdout but may not reach the store; the gateway's probe says it from outside (a failed probe, then a new instance).

**Metrics: what they carry.** Counters, each a count since the process started: requests accepted, finished, cancelled, cut off, rejected, refused for a declared prefix, refused `overloaded` (the node's own count, at either bound), failed before a stream opened and failed after (`engine.node.requests{outcome}`); steps that ran a sequence, their wall time (the step call as the engine thread sees it, `worker::Worker::run`), and the sequences they ran summed over them (the mean batch); prompt positions computed (a row that is not decoding, a preempted sequence's recomputation included) and tokens generated; drafts proposed and accepted; preemptions; first admissions, each one prefix-cache lookup, and the prompt tokens they found cached and did not; cache entries dropped under device pressure (`KvManager::evictions`, or `TierStats::device_drops` with a host tier) and from the host tier, and blocks demoted and promoted. Gauges, levels as the engine thread last published them (every step, and every idle sweep): sequences waiting and running; and per pool (the KV groups in the architecture's order, then the recurrent-state pool) the blocks a sequence maps, the blocks the cache holds idle and the free ones, and its host tier's use (`KvManager::pool_usage`). The pool count walks every block, so it is recounted at most once a second (`worker::POOL_RECOUNT_INTERVAL`), not every step. `telemetry::Counts` lists the counters and `the_counts_coarsened_are_exactly_these` how each is observed; the instruments are `engine.node.*` (`telemetry::COUNTER_INSTRUMENTS`, `GAUGE_INSTRUMENTS`).

**What it leaves out, and why.**

- **Anything per request.** No request id, cache key, lineage, salt, timestamp of an event, token, or size of any one request: every value is a sum over all the engine's work, or a level over all it holds.
- **Anything per key.** The prefix cache's hits and misses are summed across all traffic; nothing says which lineage hit, how many lineages there are, or how many entries a key holds. The entry count is left out too: one entry per cached block, so it is the retained conversations' lengths, which the coarsened idle blocks say less precisely.
- **Device memory in use.** The pools and the executor's scratch are allocated at boot, so it does not move; the info answer's `device.memory_bytes` is the size, and the pools' occupancy is what changes.
- **A step-time histogram.** The sum and count give the mean; fixed buckets would add a series per bucket for little sizing value. The idle-KV key count is a check on an invariant (`Engine::flush`), not a measure of load.

**Time resolution, and what is left.** Every instrument is observable: the SDK reads the engine's counts and levels when it exports, once per `eidola_telemetry::METRIC_EXPORT_INTERVAL` (60 s) on its own timer from when the process started, and at no other time (`the_instruments_export_what_the_node_observes`). Nothing is recorded per request, and nothing outside the process can ask for a reading, so the resolution is the export interval's at times no reader chooses. Within one interval in which a single request fell, an aggregate describes that request (`docs/privacy-guarantees.md` §3.3): steps, rows, step time, prompt positions and generated tokens then are that request's work, on the node that did it. Read against what the gateway exports for the same interval, its exact token totals by model (`chat.completion.tokens`), exact work counts would say how much of that request's prompt the prefix cache held, which nothing the gateway exports says. So every counter that could say it is observed floored to its quantum (`telemetry::Counts::coarsened`; cumulative, so an observed count never goes backward):

- **Prompt positions**, those computed and those the prefix cache found and did not, floored to 1,024 (`PROMPT_TOKEN_QUANTUM`). With the exact prompt total, any one of them exact is the cached part. An interval with one request shows that only to within 1,024, and a short prompt's not at all. The gateway never reads one request's reported cached tokens (its charge never depends on them); summed across traffic and floored, the hit rate is an operational number and not one request's history.
- **Steps and their rows**, floored to 64 (`STEP_QUANTUM`). A prompt takes a step per prefill chunk (256 positions on the Qwen deployment), and the decode steps follow from the exact generated and draft counts, so exact steps would give the uncached part to within a chunk.
- **Step time**, floored to a second (`STEP_MICROS_QUANTUM`), many prefill chunks' work on a production GPU. Over a busy interval the mean step time moves by a few percent at most.
- **Cache evictions and tier transfers**, floored to 64 blocks (`BLOCK_QUANTUM`, 1,024 positions at the deployments' 16-position block). One entry is one block, so a promoted hit's blocks are its cached length, and an evicted or demoted entry's a retained conversation's.

The rest are exact: requests by outcome, preemptions and lookups count events, not lengths, and generated tokens and drafts say no more than the gateway's completion totals. The pools are coarsened too, as levels:

- **The pools' occupancy** is rounded to 1/256 of each pool (`quantize_occupancy`). It is a level at an instant: with one request running, a pool's blocks in use would be its length in blocks so far, and the idle blocks the lengths of the conversations the cache retains. At a production pool's size a step is hundreds of blocks; a small pool (the dev model's) is reported exactly.

What coarsening does not hide: a request long enough moves the coarsened counts by about its size; the counts converge over many intervals, as any sum does; and the sequence counts are exact (how many requests the engine held at the export, nothing about any one). This is the residual §3.3 states.

**The export on the wire.** The host and network between the node and the vendor see one metrics request per interval, on the node's timer, and a logs request after a lifecycle line. Every series is observed at every export, zeros included, and which series exist depends on the node's shape (its pools, whether it has a host tier), never its activity (`the_series_observed_do_not_follow_activity`); OTLP's protobuf carries each value at a fixed width and the exporter does not compress, so a metrics export's size does not follow the values either.

**Labels and identity.** Every series carries `model`, the weights hash, plus fixed values (an outcome, a type, a pool by its index from a fixed list of eight). The resource carries `service.instance.id`, the node's `instance_id`: random per process, lowercase hex (`telemetry::instance_id`), and in its `/v1/engine/info` answer too. The gateway's probe reads it there and puts it on its lifecycle lines about the upstream, beside the pinned deployment and an opaque id derived from the upstream's URL (`crates/eidola-server-gateway/AGENTS.md` → Observability), so the operator goes from a placement row to the series that node exports; a new instance there is said once, as a restart. The node itself knows neither its deployment's name nor its URL, and exports neither.

Why per node, and what it costs:

- **The operator needs it.** A model's nodes have to be told apart to run them: one node's KV cache full while another idles, one sick node among healthy ones. A sum over a model's nodes hides exactly those. The standard is that an operator held to these rules is not severely disadvantaged against one who is not.
- **Each series is still an aggregate.** It sums the node's work over the export interval, with nothing per request, and the coarsening above applies to each node's values.
- **The network already shows which node is busy.** The platform hosting the nodes sees each node's connection to the gateway and how long it carries a stream, and so would an operator able to watch the provider's network. Per-node series tell the operator, through its telemetry, what that layer already shows the platform.
- **What the telemetry vendor gains, and the residual.** The vendor learns per-node load per interval, which the model's sum would not give it. With cache-key affinity a conversation's turns land on its home node, so in a quiet period, when few conversations are active, the vendor can follow one conversation's turns as activity on one node: when each turn ran, and roughly how much work it was, to within the coarsened values. It still has no content, no lengths beyond those coarsened values, no account and no key, and nothing that ties a node's activity to a person.

## The executor seam

`EXECUTOR` selects the executor and the served architecture selects which one of it; `lib.rs::start` builds it on the engine thread and the rest of the node is executor-agnostic (`worker::spawn` is generic over `Executor`). For DeepSeek-V4.1 and Qwen3.8, their sections below. `cpu` is `eidola-engine-cpu`'s f32 reference executor with one step shape (`MAX_SEQS` × `MAX_BATCHED_TOKENS`, unpadded) and MTP drafting over `DRAFT_TOKENS` depths; `LoadedModel` dequantises the f32 reference model for it. A gateway may pin a `cpu` deployment (on the platform release's CPU image, with no GPU: `crates/eidola-server-gateway/AGENTS.md` → Eidola-hosted engines), whose host memory the zeroing allocator scrubs as it frees it (Content-free by construction). `cuda` (the `cuda` feature) is `eidola-engine-cuda`'s executor, below. The node only constructs executors: it changes no number either computes.

## The CUDA executor

This section is MiMo-V2.6-Flash's executor; DeepSeek-V4.1's, on two GPUs, is under *DeepSeek-V4.1-Flash* → Executors, and Qwen3.8's under *Qwen3.8-27B* → Executors. `eidola-engine-cuda` runs exactly MiMo-V2.6-Flash's configuration on one Blackwell GPU, and the node neither widens nor narrows that: it hands the executor its configuration and returns the executor's own refusal (`cuda: unsupported model: <field> is …`). It has one step shape (`MAX_SEQS` × `MAX_BATCHED_TOKENS`, as on the CPU executor), replays captured graphs for pure-decode steps when `CUDA_GRAPHS` is `on` (captured at boot, one per rung of its decode ladder; prefill stays eager; doctrine and the pending GPU validation in `crates/eidola-engine-cuda/AGENTS.md` → Decode graphs) and runs every step eagerly when it is `off`, drafts `DRAFT_TOKENS` tokens a step with the checkpoint's MTP layers when that is not 0 (up to Flash's three; doctrine and its GPU validation in `crates/eidola-engine-cuda/AGENTS.md` → Drafting). Pinned deployments draft `k = 3`: attention is batch-invariant, so the verify pass computes each position's logits bit for bit as a decode step does and acceptance takes the target's argmax, which makes greedy output byte-identical at every width; the width is purely a speed setting, and uses device 0 (`cuda::DEVICE_ORDINAL`; which physical GPU that is is the deployment's choice, `CUDA_VISIBLE_DEVICES` or the one GPU a confidential VM is given). For it `LoadedModel` builds no reference model: the executor copies the checkpoint to the device as stored, from the same verified mapping the hash was computed over.

**Boot order** (`boot` → `LoadedModel::load` → `start` → `cuda::prepare` → the engine thread), each step refusing before the next begins:

1. the weights storage (`verified-readonly`), then the weights hash, then `config.json` and the chat files;
2. `MAX_MODEL_LEN` against `max_position_embeddings` (a `DRAFT_TOKENS` past Flash's three MTP layers never gets here: the grammar refuses it);
3. the executor's `CudaExecutor::preflight`: the model is Flash's, field for field, the sampleable vocabulary, the context, the step shape and the KV geometry, all from `config.json` alone, with no device;
4. the KV block counts derived from `KV_DEVICE_BYTES` (below), refused if they cannot hold one `MAX_MODEL_LEN` sequence, then the executor's preflight again over the derived geometry;
5. with `GPU_CC=required`, the GPUs' confidential-computing state (below); with `not-required`, a warning that it is unchecked;
6. the device opens (`no CUDA driver or device` on a machine without one), and `KV_DEVICE_BYTES` must be less than its memory;
7. on the engine thread, `CudaExecutor::new`: the device requirements (`check_device`: compute capability 10.x, opt-in shared memory, 148 SMs, cluster launch), every kernel image against the compiled-in manifest (a missing or altered image is refused), then the weights, then every pool. Running out of device memory is a driver error here, and refuses the boot like any other;
8. `Engine::new` over it, and only then does the node listen.

**GPU confidential computing** (`gpu_cc.rs`). On the platform, the GPU image's measured boot already opens the GPUs to CUDA work only after their device IDs check out and NVIDIA's local verifier has passed for exactly `gpus` of them (it sets NVML's CC ready state last). The node makes that claim its own, and adds what NVIDIA's default appraisal policy does not test: with `GPU_CC=required`, before any device is opened, it loads the driver's NVML (`libnvidia-ml.so.1`, by `libloading`, which the executor's driver loader already brings into the graph; nothing linked at build time) and requires `nvmlSystemGetConfComputeState` to report `ccFeature` enabled (1), `devToolsMode` off (0) and `environment` production (2), and `nvmlSystemGetConfComputeGpusReadyState` accepting work (1); any other value, an unknown one included, a missing library or a failing call refuses the boot. Names, values and struct layout are `nvml.h` from driver 595.71.05 (CUDA 13.2.2's `cuda_nvml_dev` 13.2.86), the driver the platform's GPU image ships; both queries are system-wide. The decision is `gpu_cc::check`, a pure function over those four values, so it is tested on any machine; only the query needs a driver. `not-required` skips the check (with a warning) for development on a GPU without CC, such as a rented B300 with CC off: the setting is measured like every other, so it cannot change without changing the configuration hash, and the gateway's build refuses to pin a deployment that sets anything but `required` (`check_deployment`), so a gateway never routes to a node that skipped it. It is `cuda`-only (refused with `cpu`, like the executor's other settings). What validates it where: the refusal path (`required` on a machine without NVML or without a CC-mode GPU, in process and as the binary) and the `not-required` boot run anywhere, the Mac and a non-CC GPU host included; the accepting path needs a GPU in CC mode with the ready state set, which only the platform's GPU image (or an equivalent CC host) provides.

**KV sizing.** `KV_DEVICE_BYTES` is the device memory for the KV pools; `cuda::derive_kv_blocks` turns it into per-group block counts from measured values alone (never from what the device reports), so one configuration derives the same pools on every node. With `B` the block size and, for the sliding group's window `W`, `R = ceil((W - 1) / B) + 1` (the core's bound on one window's blocks), the sliding group gets `1 + MAX_SEQS × ((1 + P) × R + 1) + ceil(MAX_BATCHED_TOKENS / B)` blocks (the null block; per seated sequence its live window, the partly filled block after it and `P` retained windows, `P` = 3 with the prefix cache and 0 without; and the positions one step adds), so sliding blocks never run out while the global pool has room. With drafting the drafter group (the MTP depths' KV, a sliding window too) gets the same count by the same rule. The global group gets the rest, `floor((KV_DEVICE_BYTES − sliding bytes) / global block bytes) − 1`, capped at the tables' `i32` range, sliding bytes counting the drafter pool. Every pool also holds one pad block past its count (where a decode graph's padding rows write; no table ever maps it), and the budget is charged for it: sliding bytes are each sliding pool's count plus one, and the `− 1` is the global pool's. Block bytes are the executor's own (`GroupGeometry::block_bytes`: BF16 K and V of every layer of the group, and for a drafter block its boundary tap, an f32 row of the hidden size per depth). Weights, scratch and the sampler's buffers come on top of the budget: leave them room.

**The host tier.** `KV_HOST_BYTES` is the confidential VM's memory the prefix cache keeps idle entries in when the KV pools run short (demoted as the ciphertext they already are, promoted back for a hit: `eidola-engine/AGENTS.md` → Host tier); 0 is none. For `cuda`, `cuda::derive_host_blocks` scales the device pools' mix to it: each group gets `floor(n_g × H / Σ n_h b_h)` host blocks (`n` the derived device counts, `b` the block bytes, the null block among them), so the tier never exceeds the budget, and a budget under two blocks in a group is refused before the device (the least accepted budget is `engine_deployment::cuda_kv_host_min_bytes`, which the gateway's build holds a pinned deployment's non-zero tier to; `cuda::tests::the_shared_host_minimum_is_the_derivations` holds the two equal); the executor pins it (`cuMemHostAlloc`). For `cpu`, `lib.rs::cpu_host_blocks` gives every group `H / CpuExecutor::kv_block_bytes` blocks, `mlock`ed. The gateway charges the whole budget to the VM's `memory` (`engine_deployment::check_resources`). **The node never runs where memory reaches durable media**: `swap::check_guest` refuses a guest with any active swap area (`/proc/swaps`, header then one line per area; a swap file, a partition or zram alike; a kernel without swap support has no list, and passes) before anything else at boot, on Linux, for every `verified-readonly` node and every node with a host tier. Hibernation is not something the guest supports: it writes its image to a swap area, and there is none. A `dev-writable` node without a tier (the dev model, the in-process tests, CI runners that have swap) is not checked, and on other systems (macOS, development only) the check is compiled out rather than switchable at run time. The pinned allocations make the tier unswappable on their own; refusing swap covers the rest of the process (prompts, outputs, keys in flight).

**Zero-on-free on the device.** The core queues `Maintenance::Zero` for every block whose refcount reaches zero (`eidola-engine`'s privacy invariants); the CUDA executor applies it as one `cuMemsetD8Async` over the block's whole byte range (every layer's K and V of that group), on the step's stream ahead of the forward, and its pools start zeroed (`alloc_zeros`). `ResetSlot` scrubs per-slot state the same way. `Encrypt` and `Decrypt` run the AOT cipher kernel over the same byte ranges (`crates/eidola-engine-cuda/AGENTS.md` → The executor → Idle encryption), so a cached block nobody uses is ciphertext on the device. The per-boot salt and key derivation and the TTL sweep are the core's and the worker's, executor-independent. Its `tests/engine.rs` checks "every free block is zero on the device or has a zero queued" after every step on a real checkpoint.

## The image

`oci/eidola-server-engine/Containerfile` builds the node's release image, `ghcr.io/eidola-ai/eidola-server-engine` (the prefix `engine_deployment::deployment::ENGINE_IMAGE_PREFIX` holds every pinned deployment to, by full digest): bake targets `server-engine` / `ci-server-engine`, CI's `oci-engine` job, `just engine-image` locally (prints the digest). It is compiled by StageX like the gateway's, from the same pinned release (`sx2026.09.0`), but it cannot be the gateway's static musl binary, and the reason is linkage:

- **The node is a dynamic glibc binary.** The executor reaches the driver through `cudarc`'s dynamic loading and the CC check reaches NVML through `libloading`: both `dlopen` (`libcuda.so.1`, `libnvidia-ml.so.1`) at run time, and nothing of CUDA is linked at build time, so the build needs no toolkit. A static musl binary cannot `dlopen`, and NVIDIA's libraries are built against glibc, so a musl process cannot host them.
- **It is cross-compiled for `x86_64-unknown-linux-gnu` by StageX's own toolchain.** StageX's rustc is musl-hosted and ships a standard library only for its musl target, so the Containerfile's `std` stage builds the standard library for the glibc target from the `rust-src` that same rustc ships (`-Zbuild-std`, the one step that uses unstable cargo, in its own stage) and installs it into rustc's sysroot; the node then builds on stable with a plain `--target`. The linker is StageX's `x86_64-linux-gnu` cross GCC (`core-cross-x86_64-gnu-gcc`), pointed with `--sysroot` at StageX's glibc (`user-glibc`, from StageX's user tier), which is also the glibc the image ships. The cross GCC carries a glibc of its own, configured under its `/opt/cross` prefix; nothing links against it. That rustc is the one `rust-toolchain.toml` names (root `AGENTS.md` → One Rust version everywhere), and the `toolchain` stage checks `oci/pallet-rust`'s record of it against `rustc --version`.
- **The unwinder is LLVM's libunwind, linked statically; no `libgcc_s` ships.** The cross GCC's `libgcc` was built without libc (GCC's `inhibit_libc`: it was configured with no target headers where it looks for them), so its unwinder can neither find a running program's frames (it imports no `dl_iterate_phdr` or `_dl_find_object`) nor call `abort`: a Rust panic or a C++ exception traps instead of unwinding. The `std` stage therefore compiles libunwind from `rust-src` (as Rust's own bootstrap does) and builds std with its `llvm-libunwind` feature, so the unwinder is inside the binary, which names only `libc` and `libm`. No driver library the node loads needs `libgcc_s` (on driver 595.71.05 only `libcudadebugger` names it).
- **The image carries the C runtime, never the driver.** `/lib64` holds the loader (`ld-linux-x86-64.so.2`, the binary's interpreter at the path the x86-64 ABI gives it) and exactly the glibc the binary was linked against (`libc`, `libm`, `libdl`, `libpthread`, `librt`, stripped of StageX's debug information), and OpenSSL 3's `libcrypto.so.3`. **OpenSSL is there only as a file for NVIDIA's library**: in confidential-computing mode `libcuda` loads `libnvidia-pkcs11-openssl3.so.<driver>`, which needs `libcrypto.so.3`, and the container must supply it; the node itself never links or loads it. It is StageX's OpenSSL release (same version, source hash and configuration as `core-openssl`) rebuilt with the gnu cross compiler, since StageX's own is musl-linked. Every other library the driver loads (checked on driver 595.71.05's `libcuda`, NVML, `libnvidia-gpucomp`, `-nvvm`, `-tileiras`, `-ptxjitcompiler`, `-sandboxutils`) needs only glibc. The Containerfile's `assemble` stage refuses to build if the binary's interpreter is not `/lib64/ld-linux-x86-64.so.2`, if any shipped ELF carries an RPATH or RUNPATH, or if any shipped ELF names a library the image does not ship.
- **The driver comes from the platform, and the loader's own search path finds it.** On the platform the GPU image's measured root holds the driver's user space (595.71.05) under `/usr/lib/x86_64-linux-gnu`; the NVIDIA container runtime (CDI mode, `runtime: nvidia`) bind-mounts those files and the device nodes into the container at the same paths, and its hooks add the soname links. StageX's glibc is configured under `/usr` with its libraries in `/usr/lib/x86_64-linux-gnu`, so its loader searches `/etc/ld.so.cache`, then `/lib64`, then `/usr/lib/x86_64-linux-gnu`: the image's own libraries and the mounted driver are both on the default path, for the node and for every library the driver loads, and no binary carries a search path. The driver's libraries must match the guest's kernel module; the R580 (CUDA 13.0) driver API is the oldest the executor targets.
- **The kernel images come in as an image pinned by digest.** They are compiled by NVIDIA's CUDA toolkit, which StageX does not carry, so `oci/eidola-engine-kernels/Containerfile` builds them with the kernel crate's own Nix expression (the build `just engine-kernels` runs) inside a pinned `nixos/nix` container, fails unless the build's `manifest.json` equals `kernels.manifest.json` byte for byte, and ships `cubin/`, `fatbin/` and that `manifest.json` in a `FROM scratch` image (`ghcr.io/eidola-ai/eidola-engine-kernels`; bake `engine-kernels` / `ci-engine-kernels`). The node's Containerfile names that image by digest on its `AS kernels` line, the one place the digest is written. The bake targets supply the same input as the `engine-kernels` target built from the tree, and `scripts/artifact-manifest.sh` fails the build unless that build's digest is the pinned one, so a new pin is published by the first run that builds it and `just engine-image` works before anything is published; `just engine-kernels-image` prints the digest to pin. Trust stays with the manifest: the `assemble` stage requires the image's `manifest.json` to be the committed one and every listed cubin and fatbin to have its recorded size and SHA-256, and copies exactly those files to `/opt/eidola/kernels` (`cubin/`, `fatbin/`), which a deployment's `KERNELS_DIR` names. The node checks each against the compiled-in manifest again before loading it.
- **Nothing else.** No shell, no `/etc`, no environment (every setting is the deployment's measured env), `USER 65534:65534`, `ENTRYPOINT ["/eidola-server-engine"]`. The weights are never in the image: a deployment mounts its model pack read-only at `/tinfoil/models/<name>`.

The image's digest is a function of source: StageX's pinned images, the OpenSSL source hash, `Cargo.lock` and the standard library's own lockfile, the kernel image's digest (itself a function of the kernel crate: toolkit and upstream sources by hash), and the Containerfile, with BuildKit's `rewrite-timestamp` output like every other image. Two builds of `server-engine` through `scripts/artifact-manifest.sh` with every stage of both Containerfiles rebuilt (pinned base images only from cache) produced the same digest on an Apple-silicon host under linux/amd64 emulation; the first native amd64 build is CI's. Cargo runs at most four compiler processes, and the kernel build Nix on at most four cores (one `nvcc` per core, and a CUTLASS translation unit takes gigabytes: sixteen ran a 16 GiB builder out of memory); parallelism reaches neither output. The one closed component is NVIDIA's CUDA toolkit, used at build time to compile the kernels (`crates/eidola-engine-kernels/AGENTS.md` → The closed-tool boundary); its output is pinned by the committed manifest, not trusted. The driver is NVIDIA's closed user space, supplied and measured by the platform's GPU image, outside this image's digest. The digest is recorded in `artifact-manifest.json` from manifest schema 4 (accepted by clients, not yet emitted: `releases/README.md`). **Checked without a GPU** (a linux/amd64 container, driver 595.71.05's `libnvidia-ml` and `libcuda` from NVIDIA's Ubuntu package bind-mounted at `/usr/lib/x86_64-linux-gnu/<soname>`, a Flash-shaped weights directory): the node boots through its host-side checks to the CC check, loads NVML and `libcuda` from `/usr/lib/x86_64-linux-gnu` and NVML's `libpthread`/`libdl`/`librt` from `/lib64` over the loader's system search path (`LD_DEBUG=libs`), and refuses with NVML's own `Driver Not Loaded`; with `not-required` it reaches the device and refuses `no CUDA driver or device`; and `libnvidia-pkcs11-openssl3` loads with its `libcrypto.so.3` resolved to `/lib64`. On the synthetic dev model with the CPU executor it answers token for token as a node built by the repository's own Rust toolchain does. **Not yet validated on the platform:** a run against a real GPU in confidential-computing mode; that the runtime's CDI hooks succeed on a `FROM scratch` image with no `/etc` (the update-ldcache hook writes `/etc/ld.so.conf` and needs a writable root); and that the unprivileged user can read the mounted model pack and open the device nodes; all need the platform's GPU image.

## Configuration

**Every variable below is read under a prefix** (`eidola_common::env`, shared with the gateway and the billing binary). `EIDOLA_ENV_PREFIX`, read bare and first, names it; set, it must match `^[A-Z][A-Z0-9_]*_$` or boot is refused, and each variable is read as `{prefix}{NAME}` with no fallback to the bare name, the secret token included. Unset or empty, names are read as written, which is how development, the tests and the session scripts run (`just run engine-server`). The prefix exists because the platform's secrets are organisation-scoped and reach a container by their own names; the committed deployments set `ENGINE_` (`ENGINE_MODEL_ID`, …, and the secret `ENGINE_GATEWAY_TOKEN`), and the deployment grammar requires a config to declare one (`engine_deployment::deployment_env`) and reads its names under it. The prefix in use is logged at startup.

All required (the `cpu`- and `cuda`-only ones with their executor, and refused with the other); an empty value counts as missing. Everything but the secret token is parsed by `eidola_common::engine_deployment::parse_measured` (the variable names live there too, bare, re-exported as `config::env`, with `Sizing`, `CacheConfig` and `WeightsStorage`); `Config::from_lookup` reads the prefix, calls it under that prefix, reads the token beside it, and maps the parsed `ExecutorSettings` onto `ExecutorConfig`. Its errors name the variable as read (`ENGINE_MAX_SEQS must be a positive integer`); the later boot checks against the weights and the devices name the setting. A build without the `cuda` feature refuses `EXECUTOR=cuda` with that reason before the grammar runs. The gateway's build runs every pinned deployment's whole env through the same function, so a pin can only name a configuration this node boots with.

| Variable | Meaning |
|---|---|
| `MODEL_ID` | The one model id served. In a pinned deployment it is the weights hash itself (the gateway's build refuses any other value): a model is identified by its weights, and the gateway sends every request under the hash its client's reference resolved to. |
| `WEIGHTS_DIR` | Weights and chat artifacts. |
| `WEIGHTS_SHA256` | The expected weights hash (64 hex digits). |
| `WEIGHTS_STORAGE` | `verified-readonly` (production: read-only, kernel-verified mount; checked) or `dev-writable` (reported in info and health). |
| `GATEWAY_TOKEN` | The gateway's bearer: a secret, never in the measured env, and not bound to the measurement (`auth.rs`: it protects the operator's GPUs, not a client's privacy, so a binding would hold the operator to nothing and make a rotation a new engine identity). |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS` | Where the node's telemetry goes, and the headers that authenticate it (Telemetry, above): secrets, read by `telemetry::init`, not by `Config`; unset or empty, nothing is exported. |
| `EXECUTOR` | `cpu` (or `cuda` in a `cuda` build). |
| `BIND_ADDR` | `host:port`. |
| `KV_BLOCK_SIZE` | Positions per KV block, every group. With the prefix cache on it must divide the declared-prefix quantum (`engine_protocol::CACHED_PREFIX_QUANTUM`, 256; `quantum_covers_block_size`), so every count a client declares is a block boundary the cache can resume at; refused by the grammar, so a pin never names one the node refuses. |
| `KV_BLOCKS` | `cpu` only: blocks per group, including the null block. |
| `KV_DEVICE_BYTES` | `cuda` only: device memory for the KV pools, in bytes, one value per device the architecture runs on, comma-separated in device order (MiMo one, DeepSeek-V4.1 two; `engine_deployment::parse_kv_device_bytes`, and `check_device_budgets` holds the count to the weights at boot); per-group block counts are derived from it (*The CUDA executor*). Each less than the device's memory. |
| `KERNELS_DIR` | `cuda` only: the kernel build output; every image is checked against the compiled-in manifest. In the release image, `/opt/eidola/kernels` (*The image*). |
| `KV_HOST_BYTES` | Host memory for the prefix cache's host tier, in bytes (page-locked; *The host tier*); 0 for none, and must be 0 when `PREFIX_CACHE` is `false`; at most 2 TiB (the largest VM). Both executors. |
| `CUDA_GRAPHS` | `cuda` only: `on` (pure-decode steps replay graphs captured at boot) or `off` (every step eager); nothing else parses. Keep `off` until the decode graphs' GPU validation has passed. DeepSeek-V4.1's executor captures no graphs: it boots only with `off`. Qwen3.8's captures one per rung of its decode ladders (*Qwen3.8-27B* → Executors). |
| `GPU_CC` | `cuda` only: `required` (the GPUs must be in production confidential-computing mode and accepting work before a device opens; every pinned deployment) or `not-required` (unchecked, with a warning; development only, never pinned); nothing else parses. |
| `MAX_MODEL_LEN` | Longest sequence; ≤ `max_position_embeddings`. |
| `MAX_SEQS`, `MAX_BATCHED_TOKENS`, `MAX_PREFILL_CHUNK` | Scheduler step limits; `MAX_BATCHED_TOKENS` ≥ `MAX_SEQS × (1 + DRAFT_TOKENS)`. |
| `DRAFT_TOKENS` | Speculative width `k` (0 disables); ≤ the model's MTP layers; ≤ 3 with `cuda` (the most any implemented architecture ships, MiMo-V2.6-Flash's three; the executor's preflight also refuses a checkpoint declaring fewer, so a wider draft is the node's to refuse, not the pin's). Pinned deployments set 3. |
| `MAX_REQUESTS` | Admission bound (each slot may hold a request body of up to `eidola_common::engine_protocol::MAX_REQUEST_BODY_BYTES`; the host memory a value commits the node to, read and admission pools together, is `eidola_common::engine_deployment::host_memory_bytes`, about 616 MiB a slot, which the sizing aid `check_resources` counts against a VM's memory; no pin check does, since the platform does not attest the VM's memory). |
| `PREFIX_CACHE` | `true` / `false`. |
| `CACHE_IDLE_TTL_SECS`, `CACHE_MAX_AGE_SECS` | Prefix-cache retention bounds (idle ≤ max age). With `PREFIX_CACHE`, the one source of the retention a gateway publishes for the model: its pin records the deployment config's values and its build holds them equal. |

**The node's environment is exactly the measured allow-list** (`eidola_common::engine_deployment::env::MEASURED`, the names `parse_measured` reads, under the config's prefix, and `EIDOLA_ENV_PREFIX` itself) plus the secrets `GATEWAY_TOKEN`, `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS` under the prefix: the gateway's build refuses a pinned deployment whose env sets anything else, a bare name included, so no variable a dependency happens to read (`TOKIO_WORKER_THREADS`, `RUST_MIN_STACK`, `MALLOC_*`, `LD_*`, the CUDA driver's `CUDA_*`) reaches a production node through its measured config. The node also reads none itself: the HTTP runtime's worker count is set explicitly (one per available vCPU), so tokio never consults `TOKIO_WORKER_THREADS`, and no engine crate reads an environment variable outside its tests. Every allocation-driving size is capped by the grammar (`engine_deployment::caps`: `MAX_MODEL_LEN` ≤ 2^20, `KV_BLOCK_SIZE` ≤ 1,024, `KV_BLOCKS` ≤ `i32::MAX`, `KV_DEVICE_BYTES` < the supported GPU's 287,428,640,768 bytes, `MAX_SEQS` ≤ 1,024, `MAX_BATCHED_TOKENS` and `MAX_PREFILL_CHUNK` ≤ 65,536, `DRAFT_TOKENS` ≤ 8, and ≤ 3 with `cuda`, `MAX_REQUESTS` ≤ 4,096), refused before loading. `KERNELS_DIR` must be absolute and clean (no empty, `.` or `..` component, not `/`), and `CUDA_GRAPHS` exactly `on` or `off`. A pinned deployment must run `cuda`; `cpu` is the reference and development executor. Its `KERNELS_DIR` must lie outside `/tinfoil` (the kernels ship in the measured image, never in an attached mount), and its `KV_DEVICE_BYTES` must hold at least `engine_deployment::cuda_kv_min_bytes`: the minimum `cuda::derive_kv_blocks` accepts (one `MAX_MODEL_LEN` sequence in the global pool, every seat's sliding windows, a step's positions, with drafting the drafter pool of the same block count, its blocks' boundary taps included, and each pool's pad block), mirrored from the same formula, so a pin never names a budget the node refuses at boot. Changing the derivation means changing both. It must also leave room on the one GPU: the device fit: `KV_DEVICE_BYTES` + the weights + `engine_deployment::cuda_device_reserve_bytes` must fit the memory of the deployment's GPU (`deployment.json`'s `gpu`, an `engine_deployment::SupportedGpu`): the 287,428,640,768 bytes the driver reports for the NVIDIA B300 SXM6 AC, as `/v1/engine/info` showed on it, or the 192,265,846,784 (183,359 MiB) it reports for the NVIDIA B200 on a node. The weights are bounded from above by the pack's data size (`artifact_data_bytes`: the modelwrap reference's `hashOffset`, the byte length of the uncompressed EROFS image that holds every file of the pack, per modelwrap's `SPEC.md`), since the executor copies tensors as stored and only re-lays out scale grids and widens small vectors. The reserve bounds the executor's own allocations from above: 4 GiB fixed (CUDA context, kernel modules, decode-graph captures, the weights' layout slack), 1.25 MiB per `MAX_BATCHED_TOKENS` (the step's scratch, an f32 logits row per token among it: about 1.03 MB at Flash's shapes), a 1.5 GiB expert-row floor, per `MAX_SEQS` 1.25 MiB for each of the sampler's distribution rows (an f64 over the vocabulary: one without drafting, `2k + 2` with `k` drafts), the device block tables (a third group's with drafting, as in the host mirror `host_memory_bytes` counts: both take the count from `engine_deployment::kv_groups`, and `cuda::derive_kv_blocks` refuses to boot an executor reporting another), the RoPE tables, and split attention's partial rows (`engine_deployment::split_partial_rows`: `min(MAX_SEQS × (1 + k), MAX_BATCHED_TOKENS) × ⌈MAX_MODEL_LEN / 1,024⌉` rows of 16,640 bytes, the executor's own count, which `cuda::tests` holds equal); with drafting also per `MAX_SEQS` the drafter's slot state and the step's level rows (`engine_deployment::drafter_seat_rows`, 16 KiB each), 32 KiB of step tables, four global page lists and the global work items of every 1,024 positions (`cuda_device_reserve_bytes`' docs give the derivation from the executor's allocations). Because the reserve is never zero, the rule is stricter than the node's own boot refusal of a budget not less than its device's memory. Changing the executor's allocations means revisiting that reserve. `MAX_BATCHED_TOKENS` must be at least `MAX_SEQS × (1 + DRAFT_TOKENS)` (`engine_deployment::decode_step_tokens`: a decode row costs `1 + k` query slots, and the scheduler leaves a row a step cannot afford out of that step, so a smaller step would stall the newest seated sequences while older ones decode), refused by the grammar before any weight is loaded. Logging is fixed at `info` in the binary (`main.rs`; the telemetry pipeline's own crates at `warn`), colour follows whether stdout is a terminal (so the logger reads no `NO_COLOR`), and `RUST_LOG` is not read, bare or prefixed: everything that changes the node's behaviour must be measured, and a filter delivered any other way (a secret, say) could turn on a dependency's debug logging, which the content-free discipline below does not cover. `GATEWAY_TOKEN` must have the shape the gateway holds its own token to (`eidola_common::engine_deployment::is_gateway_token`: 16 to 1024 visible ASCII characters); boot refuses any other token, and the gateway's build refuses any secret besides these three (`engine_deployment::SECRETS`). **The model-shape numbers in these bounds are the architecture's** (`eidola_common::architecture::Shape`, one per device, read through `Architecture::devices`; `deployment.json` names the architecture): `cuda_kv_min_bytes`, `cuda_device_reserve_bytes`, `check_resources` and, for a model split across devices, `check_device_resources` take the shape, so MiMo-V2.6-Flash's KV bytes per position, sliding window, drafter bytes and executor scratch live behind `Architecture::MimoV26Flash` and nowhere else (`cuda::tests::the_shared_minimum_is_the_derivations` holds the derivation to Flash's shape). `MimoV26Pro` is a stub: its shape is `unimplemented!`, and nothing may deploy it.

## DeepSeek-V4.1-Flash

`config.json`'s `model_type` `deepseek_v41` selects it (read after the hash; anything else goes through MiMo's configuration parser, which refuses what it is not). Text only; doctrine for its format in `crates/eidola-engine-chat/AGENTS.md` → DeepSeek-V4.1, for its executor in `crates/eidola-engine-cpu/AGENTS.md` → DeepSeek-V4.1.

- **Prompt**: `deepseek::encode` (compiled in; no template file is read), then `encode_prompt`, so request data spells no added token. The BOS is the prompt's own text. The request's `tools` go on the system message the format reads them from; `tool_choice: none` encodes without them, as for MiMo. History tool-call arguments go to the encoder as sent (`normalize_tool_call_arguments` is MiMo's).
- **Thinking and effort**: the node's subset carries neither a thinking switch nor a `reasoning_effort` (the gateway forwards neither), so every prompt is `EncodeOptions::from_request(None, None)` (`pipeline::deepseek_options`): thinking on, effort `high`. A request naming either field is refused by the strict subset.
- **Output**: `OutputConfig::deepseek_v4_1(thinking, tool_schemas)`; DSML calls of declared tools come out as `tool_calls`.
- **Refused** (400, at preparation): a continuation (`continue_final_message`; the format has none, and none of its answers is `continuable`, so a conforming client never sends one), a request whose last message is the assistant's (the format writes a generation header only after a user, tool or system message), an image part (the subset) or text spelling the image placeholder (the encoder). `developer` is not a role of the subset.
- **Vocabulary**: `sampleable_vocab_size` is the tokenizer's ids below the image token (129,264 of the released 129,280): the text model cannot embed it, and every id after it is the vision tower's, so none is ever sampled (`LoadedModel::sampleable_vocab_size`).
- **Sampling defaults**: `generation_config.json`'s when present, else 1.0 / 1.0 / no `top_k` (the released checkpoint has none).
- **Engram map**: the executor needs the compressed-vocabulary map the reference derives from the tokenizer, and the node derives it the same way, from the verified tokenizer (`eidola_engine_chat::deepseek::compressed_vocab`; the model crate then checks its class count against `engram_compressed_vocab_size`). The released checkpoint carries no map. Shards that do carry one as `engram.token_map` (`model::ENGRAM_TOKEN_MAP_TENSOR`) must carry exactly the derived map or the model is refused, so the map is one function of the measured files wherever it could be read from, and a checkpoint trained against another map is never served with this one.
- **Executors**: `cpu` is `DsCpuExecutor` (two logical devices, one captured shape, every group `KV_BLOCKS` blocks); the node refuses at boot what it would panic on (a block size the pooling ratio does not divide, more drafts than the drafter's slots) and a host tier, which it does not offer. `cuda` is `eidola-engine-cuda`'s `DsCudaExecutor` on two GPUs, device `d` (encoder 0, decoder 1) on GPU `d` (`cuda::DEEPSEEK_DEVICES`), built by `cuda::prepare_deepseek` in this order, each step refusing before the next:
  1. `KV_DEVICE_BYTES` names two budgets (`check_device_budgets`);
  2. `CUDA_GRAPHS` is `off`: the executor runs every step eagerly and captures no decode graphs, so `on` is refused (`cuda::deepseek_config`);
  3. the executor's own `preflight` over the node's sizing (one step shape, `MAX_SEQS` × `MAX_BATCHED_TOKENS`; `DRAFT_TOKENS` against the drafter's slots; the block size against the pooling ratio; `MAX_MODEL_LEN`; the sampleable vocabulary below the image token), with no device;
  4. the block counts from the two budgets (`cuda::derive_deepseek_kv_blocks`), one for the window groups (the encoder's, the decoder's and the drafter's windows) and one for the banks, each the null block among them. With `B` the block size, `W` the model's window (128: the most positions before a row's own a window group holds for it, the drafter's context), `R = ceil(W / B) + 1` and `P` = 3 retention points with the prefix cache (else 0), every window group gets `1 + MAX_SEQS × ((1 + P) × R + 1) + ceil(MAX_BATCHED_TOKENS / B)`, as MiMo's sliding pools do: per seat its live window, the block after it and `P` retained windows, and a step's new blocks. The serving core takes idle windows back from entries running chains keep before a window allocation fails, so the blocks a window group cannot give back are the running sequences' live windows and a step's new blocks, within that count: a window allocation never fails, and the banks alone bound concurrency and context (`eidola-engine/AGENTS.md` → Window pools). The banks get what the tighter device leaves beside its windows, `min_d floor((budget_d − window × V_d) / K_d)`, `V_d` and `K_d` the bytes of one block of every window group and every bank group on device `d` (the executor's own `deepseek::executor::geometry`; the drafter's group is on device 1), refused when either device cannot hold its windows and, beside them, one `MAX_MODEL_LEN` sequence of banks and the null block, capped at `i32::MAX`; no pool holds a pad block (no graphs). The host tier's count (`cuda::derive_deepseek_host_blocks`) is `floor(KV_HOST_BYTES / (S_0 + S_1))`, `S_d` the bytes of one block of every group on device `d`, one count for every group of both devices, 0 for none and refused under two; then the preflight again over the derived counts;
  5. with `GPU_CC=required`, `gpu_cc::check_devices` over NVML's state and device count (`gpu_cc::query_devices`, `nvmlDeviceGetCount_v2`): the production CC state and at least two GPUs reported; with `not-required`, a warning;
  6. GPUs 0 and 1 open, each budget less than its GPU's memory; `/v1/engine/info` reports device 0's GPU;
  7. on the engine thread, `DsCudaExecutor::new`: each device's kernel images against the compiled-in manifest, then the weights from the verified mapping and the Engram map (`Served::DeepSeek::token_map`, derived at load for either executor as above), then every pool.

  The shared sizing aid (`engine_deployment::check_device_resources`, which no pin check runs) follows the same rule: `engine_deployment::cuda_kv_min_bytes` over a `Shape` with `uniform_kv_groups` (`eidola_common::architecture::DEEPSEEK_V41_FLASH`, each device's groups as the executor lays them out, each marked bank or window) is ⌈`MAX_MODEL_LEN` / `B`⌉ + 1 blocks of `uniform_kv_bank_block_bytes` beside `uniform_kv_window_blocks` blocks of `uniform_kv_window_block_bytes` (each group's block padded to 16 bytes, the drafter's only when drafting), and `cuda_kv_host_min_bytes` two blocks of every group per device; `cuda::tests::the_shared_deepseek_minimums_are_the_derivations` holds both to this derivation, exactly and one byte below on either device, over the released configuration and the dev model's across block sizes, context lengths, seats, step sizes, the cache switch and draft widths 0 to 3. At the released sizing (`B` = 256, 64 seats, 8,192-token steps, the cache on) a bank block is 136,704 bytes on device 0 and 91,136 on device 1, a window block 2,703,360 (3,108,864 on device 1 with the drafter's), and a window group holds 609 blocks: a 2^20-position context needs 2.21 GB on device 0 and 2.27 GB on device 1 (2.02 GB without drafts), 2^17 positions 1.72 GB and 1.94 GB, and the KV is no longer what limits the context: the step's scratch is. The device fit charges each device `engine_deployment::device_weights_bytes` (the drafter's 9.26 GB on device 1 only when drafting) and `cuda_device_reserve_bytes`, which for this shape counts the executor's step scratch by its own allocations (`architecture::StepScratch`, `engine_deployment::step_scratch_bytes`: per step row the row's buffers and the indexer's scores and candidate mask over every visible entry, `2 × (MAX_MODEL_LEN / ratio + 1)` bytes and a word per 32 candidate blocks, which is what grows with step tokens times the context; per seat the sampling rows, the open entries and, drafting, the draft pass; 40 KiB of fixed slack), beside the fixed 4 GiB, the block tables and the RoPE tables. `cuda::tests::the_shared_step_scratch_is_the_executors` holds that count to the executor's own layout across contexts, step sizes, seats and draft widths (the index scratch exactly, the whole within its fixed slack, the tables and loaded weights within their terms). At 2^20 positions the sizing aid admits undrafted 8,192-token steps (device 1's KV room 10,233,054,144 bytes) and three drafts at 4,096-token steps (10,713,172,224), each about 21 whole sequences of banks, and refuses three drafts at 8,192-token steps at any budget (device 1's weights and reserve alone pass its memory by 384,161,536 bytes; `deepseek_fits_two_b300s_at_its_whole_window_by_its_step`); `cuda::tests::the_released_model_lays_out_wherever_the_shared_check_admits_it` lays the released model out at exactly the budgets it admits within a B300 less the fixed 4 GiB, and shows the refused one does not lay out even with the least KV. Validated without a GPU (`tests/cuda.rs`): every refusal above, and the node's derived configuration over host devices (`deepseek::host::HostDevice`) generating the CPU executor's greedy tokens; on two GPUs only by the ignored test in *Tests*.
- **Deployment**: two B300s, one KV budget each (`engine_deployment::check_device_resources`: each device's least KV (above; a block size the pooling ratio does not divide is refused), its weights bound from `Architecture::devices` and the executor's reserve within the GPU's memory; the pack at most both devices' weights). ## Qwen3.8-27B

`config.json`'s `model_type` `qwen3_5` with FP8 weights selects it, read after the hash by `model::qwen_architecture`, exactly: only when every dimension equals `QWEN38_DIMS`. Another FP8 shape is refused, except a synthetic dev model by the rule *Qwen3.5* states (a `dev-writable` node and a hidden size below 1,024), which is how the Qwen3.8 dev model and fixtures boot. An architecture names a shape and the weights hash names the model, so an FP8 checkpoint of another release with exactly these dimensions (Qwen3.5-27B's or Qwen3.6-27B's) is read as this architecture; which model a node serves is its weights hash. Text only; doctrine for its format in `crates/eidola-engine-chat/AGENTS.md` → Qwen3.8, for its executors in `crates/eidola-engine-cpu/AGENTS.md` → Qwen3.8 and `crates/eidola-engine-cuda/AGENTS.md` → Qwen3.8, and its state and outstanding work in `crates/eidola-engine/architectures/qwen3.8-27b.md`.

- **Loaded model**: the model crate's `QwenModel` over the verified mapping (`Served::Qwen`), for either executor: its large weights stay in the mapping (both executors read them from there), and only the norms, the DeltaNet's small projections and the block scales are decoded at load. The model's own `chat_template.jinja` (pinned by the chat crate), the pinned tokenizer, and `generation_config.json` (its two end-of-sequence ids, `<|im_end|>` and `<|endoftext|>`, and the sampling defaults: temperature 1.0, `top_p` 0.95, `top_k` 20) are all required.
- **Prompt**: `qwen::ChatTemplate::render_prompt`, then `encode_prompt`, so request data spells no added token. String tool-call arguments in the history are decoded by the template's own rule. `tool_choice: none` renders without the tools, as for MiMo.
- **Template options** (`pipeline::qwen_options`): the subset carries no thinking switch, `reasoning_effort` or `preserve_thinking`, so each is left undefined, as MiMo's are, and the template's defaults hold: thinking on (the generation prompt opens `<think>\n`), at the template's default effort (`xhigh`, whose instructions it writes into a system turn), and **every past turn's reasoning kept**. Keeping it is a decision, not only a default: it is what makes a new turn's prompt the last turn's prompt followed by more, the token prefix a client declares cached (`declared_prompt`; `a_new_turns_prompt_begins_with_the_last_ones`, `a_new_turn_declaring_the_last_ones_prompt_is_served`). `preserve_thinking: false` drops the reasoning before the last user message, so no later turn would extend an earlier one and every new turn would be priced and computed without its history cached; it also costs the model its own earlier reasoning. A request naming any of the three is refused by the strict subset.
- **Output**: `OutputConfig::qwen3_8(None, tools)`; the `<think>` splitter (the output starts in the reasoning) and `<tool_call>` markup of declared tools come out as `reasoning_content` and `tool_calls`.
- **Refused** (400, at preparation): a continuation (`continue_final_message`): the template trims the field it would continue, so none of its answers is `continuable` and a conforming client never sends one. Image parts (the subset) and whatever the template itself raises on (a system message after the first, no user query).
- **Vocabulary**: every tokenizer id (248,077 of the head's 248,320) is sampleable. The vision placeholders are among the added tokens, so they cannot be cut off as DeepSeek-V4.1's are; a sampled placeholder is embedded from its row by the CUDA executor, while the CPU reference executor refuses it (vision is not served), which ends its engine. The dev model's head gives those rows zeros so they never rank.
- **Executors**: `cpu` is `QwenCpuExecutor` (one captured shape; both KV groups `KV_BLOCKS` blocks; the state pool below; `lib.rs::qwen_cpu_config`): the node refuses at boot what it would panic on (drafting without the model's MTP layer) and a host tier, which it does not offer. `cuda` is `eidola-engine-cuda`'s `QwenCudaExecutor` on one GPU (`cuda::DEVICE_ORDINAL`), built by `cuda::prepare_qwen` in this order, each step refusing before the next:
  1. `KV_DEVICE_BYTES` names one budget (`check_device_budgets`);
  2. a draft width needs the model's MTP layer (`cuda::qwen_config`);
  3. the pools from the budget (`cuda::derive_qwen_pools`): a **state pool** of `1 + S × (2 + P)` buffers (`S` = `MAX_SEQS`, `P` = 3 retention points with the prefix cache, else 0; `engine_deployment::recurrent_state_buffers`): the zero state, and per seat its base and the one fresh buffer a step may store for it (the serving core's minimum progress, `1 + 2S`) and its retention points' snapshots, as MiMo's sliding pools hold `P` retained windows a seat; snapshots of finished turns are cache in the same pool, reclaimed least recently used first (`eidola-engine/AGENTS.md` → State pool). Every **KV group** (the target's 16 attention layers and, drafting, the drafter's layer with its boundary tap) gets one count of blocks, what the budget leaves beside the state pool, at least one `MAX_MODEL_LEN` sequence and the null block, capped at `i32::MAX`, and each pool holds one pad block more (where a decode rung's padding rows write), which the budget is charged for. The host tier (`cuda::derive_qwen_host_pools`) scales the device mix to `KV_HOST_BYTES`, KV blocks and state buffers alike, each refused under two;
  4. with `GPU_CC=required`, the CC state (`gpu_cc::check`); with `not-required`, a warning;
  5. GPU 0 opens, the budget less than its memory;
  6. on the engine thread, `qwen::cuda::CudaDevice::open` in the **fast** profile (`cuda::QWEN_PROFILE`: the FP8 and large BF16 linears on CUTLASS, attention by FA2 at head dimension 256; its contract is reproducibility whatever shares the batch, the chunking or the cache, and the exact profile, equal to the CPU executor bit for bit, is the verification mode; `eidola-engine-cuda/AGENTS.md` → Qwen3.8), its kernel images checked against the compiled-in manifest; then `QwenCudaExecutor::new` with the live state strategy and `CUDA_GRAPHS` as configured: the weights from the verified mapping, every pool and its fixed step scratch, and with `on` a graph captured for every rung of the decode ladders (draft width 0, and `DRAFT_TOKENS` when drafting, of the node's one step shape: powers of two up to `MAX_SEQS` rows, at most `MAX_BATCHED_TOKENS / (1 + k)`), which uniform decode steps replay; a capture that fails refuses the boot. Other steps run eagerly. It drafts `DRAFT_TOKENS` tokens a step from the one MTP layer run again on its own output, so any width up to the grammar's cuda cap of 3.

  The shared sizing aid follows the same rules through `Shape::recurrent` (`eidola_common::architecture::QWEN38_DENSE_27B`, its `HybridDims`): `cuda_kv_min_bytes` is ⌈`MAX_MODEL_LEN` / `B`⌉ + 1 blocks of `recurrent_kv_block_bytes` beside the state pool's images (`HybridDims::state_image_bytes`, 156,917,760 bytes at the released shape: every DeltaNet layer's convolution history and state matrix in f32 and a tag, padded to whole convolution rows as the executor strides them) and each pool's pad block, and `cuda_kv_host_min_bytes` two of each on the host; `cuda::tests::the_shared_qwen_minimums_are_the_derivations` holds both exactly, and one byte below refused, over the released configuration and the fixture's across block sizes, lengths, seats, steps, the cache switch and draft widths. The reserve (`cuda_device_reserve_bytes`) counts, beside the fixed 4 GiB, each seat's live image, tail of `B − 1 + k` positions and kept states (`recurrent_seat_bytes`, about 193 MB a seat at `B` = 16 and `k` = 3), one more for the padding rows' seat, the RoPE tables, and the fast profile's step scratch, which the executor sizes once at construction (`recurrent_step_scratch_bytes`, after its `capacities` and `program::alloc_scratch`): about 404 KB per row of its widest forward (max(`MAX_BATCHED_TOKENS`, `S × k`)), the DeltaNet's staging, FA2's partial rows (a row per 1,024 positions of the context for every forward row, 12,384 bytes each: about 12 bytes per row and position), the head's and the sampler's rows over the vocabulary, and the step tables, the rungs' fixed one and the eager one, bounded by `recurrent_table_words` (a word a block of the context per target row and a word a position per drafter row, the drafter's pages being positions). The exact attention's scores, 96 bytes per row, layer and position, are the exact profile's alone, which the node does not run. `the_nodes_qwen_configuration_computes_what_the_cpu_executor_does` (`tests/cuda.rs`) runs the node's configuration over the kernels' bodies compiled for the host in the exact profile: the greedy tokens are the CPU executor's at draft widths 0 and 2, eagerly and on the padded rung path, and with graphs on the host device's refusal to capture refuses the construction. `the_nodes_qwen_pools_and_scratch_are_the_shared_counts` plans the fast profile on the host (FA2 checked, not computed; on the model crate's 256-wide fixture, since FA2 is compiled for heads of 256) in a counting device: every pool, pad blocks and the padding seat included, is the size the shared rules count, and everything else allocated, at construction and as the eager table grows over a prompt filling the window and its decode, stays within `recurrent_step_scratch_bytes`.
- **Deployment**: one GPU, one KV budget (sized by `check_resources` over the shape above). `MAX_PREFILL_CHUNK` is 256 (`eidola_engine_cuda::qwen::SERVING_PREFILL_CHUNK`): the DeltaNet's token recurrence is serial within a run, one position after another, so a step's prefill cost follows its longest run, and a smaller chunk spreads a long prompt over more steps while several sequences prefill side by side. A row's bits do not depend on the chunking (the executor's invariance across chunking is asserted), so this is a choice of speed alone (`eidola-engine-cuda/AGENTS.md` → Qwen3.8). `deploy/engine/qwen3.8-27b/b200x1/` is one NVIDIA B200 at the whole 262,144-position context: 64 seats, steps of 2,048 tokens of prefill chunks of 256, three drafts, decode graphs on, a 115 GiB KV budget (the state pool's 321 buffers, 50.4 GB, and about 1,040,000 positions of KV) and a 64 GiB host tier. The reserve beside it is about 34.8 GB, 17.9 GB of it the step's scratch (`eidola-common`'s `qwen_fits_one_b200_at_its_whole_context`): the state pool, which grows with the seats, is what limits them, and 128 seats would leave the KV about 150,000 positions. It is pinned on TDX, its machines the platform endorsements' `tdx-b200-1-5-20-prod`, and its weights pack is the modelwrap schema 1 pack of the row's repository, whose data size (30,890,057,728 bytes) bounds the weights in that sizing. The dev model's heads are 128 wide, so a `cuda` node on it is refused by the executor's fast profile at construction; the dev model is the CPU executor's.

## Running it locally

`just run engine-server` builds the synthetic dev model into `target/engine-dev-model` (`examples/dev_model.rs`), prints its weights hash, and serves it on `127.0.0.1:8090` with gateway token `dev-gateway-token`:

```sh
W=$(curl -s -H 'Authorization: Bearer dev-gateway-token' 127.0.0.1:8090/v1/engine/info | jq -r .weights_sha256)
curl -N 127.0.0.1:8090/v1/chat/completions -H 'Authorization: Bearer dev-gateway-token' \
  -H "X-Eidola-Weights-Sha256: $W" -H 'content-type: application/json' \
  -d '{"model":"mimo-dev","messages":[{"role":"user","content":"hi"}],"max_completion_tokens":16,"stream":true,"stream_options":{"include_usage":true}}'
```

**A batch client** (`examples/chat_batch.rs`, development only; nothing in it is part of the node or its image) sends the chat requests of a JSONL file to a running node as the gateway does, at a given concurrency: the bearer token from `GATEWAY_TOKEN`, the weights header (the hash given, which must be the one `/v1/engine/info` reports), and the stream with usage. Each line is a request body in the subset without `model`, `stream` and `stream_options`, which the client sets, plus an optional `id`; it is sent with its members in the file's order and spelling (the chat crate's order-preserving JSON), after `api::parse_request` has accepted it, so a line the node would refuse is reported unsent. Each stream is read back with `stream_shape::StreamReader` and written as one line, the deltas joined into one `chat.completion` (or the error body), as requests finish; a rerun onto the same output skips the ids it already answered (after completing a last line an interruption left without its newline, or cutting it off if it is not whole JSON), and a request refused `overloaded` is sent again after a pause. Over the dev model above: `GATEWAY_TOKEN=dev-gateway-token cargo run -p eidola-server-engine --example chat_batch -- http://127.0.0.1:8090 "$W" requests.jsonl out.jsonl --concurrency 4`.

**The Qwen3.8 dev model** (`just run engine-server qwen`, or `cargo run -p eidola-server-engine --example dev_model -- --qwen <dir>`; model id `qwen-dev`) is the model crate's `qwen_tiny` fixture (one attention and three DeltaNet layers, one MTP layer, 4,096 positions) with its embedding and head widened from 512 rows to the released 248,320, `config.json` with that vocabulary and the released special and vision token ids, the head's vision-placeholder rows zero (*Qwen3.8-27B* → Vocabulary), and the chat crate's pinned Qwen3.8 tokenizer, template and generation config. **The Qwen3.5 dev model** (`just run engine-server qwen35`, or `--qwen35 <dir>`; model id `qwen35-dev`) is *Qwen3.5* → The dev model.

**The DeepSeek-V4.1 dev model** (`tests/common/fixture.rs`, `cargo run -p eidola-server-engine --example dev_model -- --deepseek <dir>`; serve it with the environment above, `WEIGHTS_DIR` and `_SHA256` its own, `MAX_MODEL_LEN` at most 1,024 and `DRAFT_TOKENS` at most 4) is the model crate's `deepseek_tiny` fixture with its four vocabulary-shaped tensors widened from 96 rows to 129,280, `config.json` with that vocabulary, the released image token id and the derived Engram vocabulary's 99,092 classes, and the chat crate's pinned DeepSeek tokenizer; like the released checkpoint it carries no Engram map, and no template or generation config.

**The dev model** is the model crate's committed synthetic fixture with `embed_tokens` and `lm_head` widened from 256 rows to MiMo's padded 152,576 (the fixture's rows first, then deterministic random rows at the same scale), so the real pinned tokenizer and template can drive it; every other tensor is the fixture's. Its weights are random: the output is gibberish, and nothing about it is a quality signal. A built directory records a fingerprint of its inputs (`.fixture-fingerprint`: SHA-256 over a generator version, the generator's own source, and every input file); a directory whose fingerprint does not match is rebuilt beside it and swapped in by rename, so neither the tests nor `just run engine-server` can use a stale model. Rebuilds hold an exclusive lock on a sibling `.lock` file and recheck the fingerprint under it, so concurrent test binaries never move aside a model another has just published.

## Generating from the released checkpoint on the CPU

`examples/deepseek_generate/` (development only; nothing in it is part of the node or its image) runs greedy chat requests through DeepSeek-V4.1 on the CPU reference executor, along the node's own path without its HTTP side: `LoadedModel::load` (storage `dev-writable`, the weights hash checked, the reference model and the Engram map built as at boot), `api::parse_request` and `pipeline::prepare` (the format's encoder and tokenizer), `deepseek_cpu_config` and `scheduler_config` (the node's own executor and scheduler configuration, which `start` uses too) over `DsCpuExecutor` and the engine core, and `pipeline::Decoder` (detokenizer, reasoning and tool-call parsers). `runner.rs` is the logic, `main.rs` its environment (documented there), `prompts.json` the requests (a plain question, a short reasoning task, a code request, a tool-call request with one tool; read with the chat crate's order-preserving JSON and sent as that text, every key where the file has it, since the format renders a tool's schema as the JSON a client sent and a `serde_json::Value`, whose maps sort their keys, would make another prompt of the same length), `session.sh` the one command for a Linux machine holding the checkpoint:

```sh
CHECKPOINT=<checkpoint dir> OUT=<results> crates/eidola-server-engine/examples/deepseek_generate/session.sh
```

- **The runs.** Every prompt at the drafter's width (5 for the released checkpoint), then the ones marked `check_width0` again at width 0. Greedy output is the same at every width (`crates/eidola-engine/AGENTS.md` → Determinism contract), so their tokens must be identical; a difference exits 2. One request at a time, each up to `EIDOLA_DSGEN_MAX_NEW_TOKENS` (96) new tokens. With thinking on (the node's default), 96 tokens is mostly reasoning: content and tool calls appear only if the reasoning ends sooner.
- **The weights hash is checked on every run**, by the node's loader; there is no switch that skips it. `session.sh hash` computes it once with the offline procedure (*The weights hash*, files hashed in parallel) and caches it in `$OUT/weights.sha256`, so the first run reads the checkpoint twice and every later run once. A skip switch would save that read (minutes on local NVMe, against hours of generation) at the price of transcripts from unverified bytes and a hash-skipping path in this crate. A checkpoint fetched without the vision shard (`model-00001-of-00048`) loads and runs the same, but its hash is not the published model's: the hash covers the shards present.
- **What it records**, per request and per width in total (`$OUT/run/requests/<name>.w<width>.json`, `summary.json`, `transcripts/`, and `transcripts.txt`, the transcripts of exactly the requests the summary lists, which `session.sh summary` prints: `transcripts/` can also hold files of requests an earlier run of the directory had): tokens generated, steps, tokens per decode step, wall time per step (`step_log`), prefill steps, positions and seconds, peak resident memory (and on Linux the resident set split into anonymous and file-backed), the reasoning, content and tool calls as the node parses them, and draft acceptance **per slot**, read from the executor's row records (`DsCpuExecutorConfig::record`: the one setting that differs from a node's, and it changes no computed value). Slot `i` is *reached* when every slot before it in its row was accepted; its conditional acceptance is accepted over reached, its unconditional acceptance accepted over proposed. The smoke test holds the per-slot totals to the engine's own `Stats::drafted`. Each request's file also holds the prompt's token ids (`prompt_token_ids`) and every generated token with its own bytes (`generated_pieces`: the text when they are UTF-8 alone, else hex), so a request can be driven again teacher-forced without encoding anything.
- **Sizing comes from the prompts**, never from the model's 2^20 positions: one sequence, a context of the longest prompt plus the new tokens, the draft width and a block, every group `2 × ceil(context / 16) + 32` blocks (about 33 MB of pools for the committed prompts at the released cell sizes), and a prefill of up to `EIDOLA_DSGEN_PREFILL_CHUNK` (512) positions a step, so each committed prompt prefills in one step.
- **A saved result is reused only for the inputs that made it.** Each request's file carries a fingerprint: the SHA-256 of the weights hash (which the loader verifies before anything is generated), the running executable's own SHA-256 (so any rebuild, a numerics fix among them, runs everything again), the request body (messages, tools, token limit, greedy sampling), the draft width, the block size and the prefill chunk. A file with another fingerprint is run again and overwritten, and the summary reads only files with this run's, so a reused output directory never labels old tokens with a new checkpoint's hash or compares tokens from different checkpoints.
- **Time is estimated and bounded.** Before any work it logs a prior (the model crate's measured 1.3 s per position, prefill only); the first request's prefill, as soon as its output arrives, and then its first decode step calibrate (`calibration.json`, kept across runs). A run is refused, exit 3, as soon as a bound on it exceeds `EIDOLA_DSGEN_TIME_LIMIT_HOURS` (12): with a decode step measured (or none needed: at one new token the prefill gives it), the worst case, every prompt position at the measured prefill rate and every new token after the first its own decode step; with only the prefill measured, the prefill alone, a lower bound, which refuses too. `run.json` keeps what the estimate needs from the load (the drafter's slot count and each request's prompt length, by fingerprint, for one weights hash and build), so a later run of the same inputs with a calibration on file is refused before the checkpoint is read; a run whose requests changed is estimated after the load, when their lengths are known. The estimate is redone after every request. Every finished request is checkpointed (written by rename), so a rerun skips it; the calibrating request of a refused run is not kept.
- **Memory.** On Linux it refuses to load with less than `EIDOLA_DSGEN_MIN_AVAILABLE_GB` (64) available. Estimated for the released checkpoint, not yet measured: the dense tensors the loader decodes to f32 take about 36 GB (about 165 M parameters a layer over 40 layers, the embedding and head 1.3 B, the Engram projections 0.3 B, the drafter 0.6 B); routed experts (about 270 GB of FP4) and the two Engram tables (about 98 GB each) stay mapped and are read per step; each expert a step routes to is decoded for that step (about 35 MB), in parallel across experts (`eidola-engine-model/AGENTS.md` → DeepSeek-V4.1). With the pools, the step's activations and the records, that is about 40 to 50 GB anonymous; the rest of a 340 GB machine is page cache over the mapped checkpoint, which holds nearly every expert once they have been read.
- **Measured on the released checkpoint** (every shard matching its upstream hash, weights hash `dc8555f4…d4d5` by the loader; 24 CPUs): short prompts get correct, concise answers (a capital, an elapsed-time sum, a Rust function) and a call to the declared tool, and the two prompts run at both widths give the same tokens. At width 5 the drafter's first to fifth slots are accepted 56, 44, 34, 30 and 27 times in 62 steps: 3.08 drafts and 4.03 tokens a step. About 0.9 s per prefill position, 4.3 s per decode step at width 0 and 9.4 s at width 5; peak resident 361 GB, of which about 37 GB anonymous and the rest the mapped checkpoint.
- **What it does not show.** Speed: the CPU executor is the numerics reference, not a serving backend. Agreement with the reference implementation: nothing here compares with another model's output; the transcripts are the first text of the whole model through this engine, to be read.
