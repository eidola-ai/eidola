# eidola-server-engine

The process on each inference node: it serves **exactly one model** through Eidola's own engine crates (`eidola-engine`, `-chat`, `-model`, `-cpu`, and `-cuda` in a `cuda` build), in process, behind a narrow HTTP API that only Eidola's gateway calls. Requests flow client → gateway → node; TLS and attestation are the enclave shim's job, so the node speaks plain HTTP behind it. AGPL-3.0-only. Workspace conventions live in the root `AGENTS.md`; the engine's own doctrine in `crates/eidola-engine/AGENTS.md` and its siblings.

| Module | Contents |
|---|---|
| `config.rs` | The environment, read once at boot. Every variable is required; nothing is defaulted. Each executor's own settings are required with it and refused with the other. |
| `auth.rs` | The gateway token: Argon2id-verified at boot, constant-time per request. |
| `model.rs` | The weights hash (definition below), checked before any weight is loaded; `LoadedModel`. |
| `api.rs` | The strict request subset and its validation. |
| `error.rs` | `ApiError`: full detail to the caller, category-only `Display` for logs. |
| `pipeline.rs` | Template → tokens → engine request; tokens → detokenizer → stop sequences → reasoning / tool calls. |
| `worker.rs` | The engine's step loop on its own thread; the channel bridge, admission bound, cancellation; the step watchdog. |
| `http.rs` | Routes and response shapes; the framed stream and the padding of every other response. |
| `cuda.rs` | (`cuda` feature) The CUDA executor's host-side refusals, its KV block counts derived from the device budget and its host-tier counts from the host budget, the GPU confidential-computing check, opening the device, and building the executor. |
| `gpu_cc.rs` | The GPU confidential-computing check: the decision (a pure function over NVML's reported values, tested everywhere) and, with the `cuda` feature, the NVML query. |
| `swap.rs` | The boot refusal of a guest with active swap (`/proc/swaps`). |
| `lib.rs` | `boot` (verify, load, start) and `start` (over an already verified model). |

## What the node trusts, and what it refuses

The node trusts its measured configuration (the environment; see below) and the bytes of its weights directory **only after** they hash to the configured weights hash. It trusts nothing in a request beyond what the strict subset names.

**At boot** it refuses to start (non-zero exit, a content-free message naming the variable or file) on:

- any configuration variable missing, empty or malformed;
- on Linux, for a `verified-readonly` node or one with a host tier, any active swap area (`swap.rs`, first of all; see *The host tier*);
- a gateway token that does not verify against `GATEWAY_TOKEN_HASH`, or a hash that is not Argon2id;
- `EIDOLA_ENGINE_WEIGHTS_STORAGE=verified-readonly` with any weights file (the directory, shards, semantic and chat files) not on read-only storage (`storage.rs`; checked before any weights file is opened, mapped or parsed), or any of those files not a regular file (a symlink, say);
- a file in the weights directory whose name is not UTF-8 (the manifest is keyed by exact names; checked from the listing, before hashing);
- a weights directory whose weights hash differs from `EIDOLA_ENGINE_WEIGHTS_SHA256` (checked before dequantising anything);
- an unpinned tokenizer or chat template (the chat crate's pins), a tokenizer larger than the model's head, or an unusable `generation_config.json`;
- sizing the model or the engine core cannot honour: `MAX_MODEL_LEN` above `max_position_embeddings`, more draft tokens than MTP layers, or a scheduler configuration `Engine::new` refuses (for example a step budget below one speculative decode row);
- `cuda` as the executor in a build without the `cuda` feature (it does not parse); with it, everything in *The CUDA executor* below that the executor or the node refuses. A refused CUDA executor ends the boot: the node never falls back to the CPU executor.

**Per chat request**, in this order, each before anything is admitted:

| Check | Status | `error.type` |
|---|---|---|
| `Authorization: Bearer <gateway token>` | 401 | `authentication_error` |
| `X-Eidola-Weights-Sha256` present | 428 | `weights_hash_required` |
| … and equal to this node's weights hash (hex, any case); **checked before the body is read** | 412 | `weights_hash_mismatch` |
| a read slot is free (the read bound, below); **checked before the body is read** | 503 | `overloaded` |
| body ≤ 32 MiB | 413 | `request_too_large` |
| strict subset (`deny_unknown_fields` at every level, every content-part variant included) | 400 | `invalid_request_error` |
| `model` is the configured model id | 404 | `model_not_found` |
| `stream: true` with `stream_options.include_usage: true`; text-only content, `tool_choice` `auto`/`none`, ≤ 4 non-empty stops of ≤ 256 bytes each, `max_completion_tokens` ≥ 1, valid `cache_key`; `cached_prefix` in its one shape, with a `cache_key` and at least one cached token (`check_cached_prefix`) | 400 | `invalid_request_error` |
| an admission slot is free | 503 | `overloaded` |
| template accepts the messages; sampling parameters valid (`SamplingParams::new`) | 400 | `invalid_request_error` |
| prompt + 1 fits `MAX_MODEL_LEN` and the KV pools | 400 | `context_length_exceeded` |
| with `cached_prefix`: the tokenized prompt has at most `cached_tokens + new_tokens` tokens | 409 | `prompt_budget_exceeded` |
| with `cached_prefix`, at the engine's first admission: its prefix cache holds at least `cached_tokens` of the prompt's leading tokens under the key (a `cached_tokens` reaching the final prompt token never can) | 409 | `cached_prefix_missing` |

Every `error.type` is an `eidola_common::engine_protocol::error_type` constant. A gateway sends a refused request to another node only when `engine_protocol::refused_before_admission` holds for its status and type: the first three rows, `model_not_found`, and `overloaded` (raised only when a read or admission slot is not free). `error::tests::only_pre_admission_refusals_say_so` holds every `ApiError` to that list, so a refusal raised after admission (`engine_unavailable`, once the engine has a request) must never reuse one of those types. The two declared-prefix refusals are not on it (the cache a declaration names is on the node its key routes to, so another node would refuse it too): a gateway returns them to its client by `engine_protocol::declared_prefix_refusal`, which `error::tests::declared_prefix_refusals_say_so_and_nothing_else_does` holds to exactly those two `ApiError`s.

The authentication check is about money, not privacy: it keeps anyone but the gateway (which bills) from spending the node's compute. No privacy property depends on who can call the node. Authentication precedes the weights check, so an unauthenticated caller learns nothing about the weights.

The weights-hash check is redundant with the node's measurement (which covers the weights) but early, cheap and independent: a gateway sends the hash from its own compiled-in pin (`releases/trust/engine-enclaves.json`, via the gateway's `engine_trust::protocol`), never from placement data, so a misregistered node refuses traffic rather than serving the wrong weights. The header's name is `eidola_common::engine_protocol::WEIGHTS_HEADER`, which both sides read. `GET /v1/engine/info` reports the verified hash so a misregistration is visible before any traffic.

## The weights hash

The node's weights hash identifies every file it reads from the weights directory:

- every `*.safetensors` file in the directory;
- `config.json`, and `model.safetensors.index.json` when present (the model crate's `SEMANTIC_FILES`);
- `tokenizer.json`, `chat_template.jinja` and `generation_config.json` (the chat artifacts). The tokenizer and template are also pinned by the chat crate; `generation_config.json` is not, and it decides the EOS ids and default sampling, so it must be covered here.

The **manifest** is one line per file, `<sha256, lowercase hex>␠␠<file name>\n` (exactly `sha256sum`'s output), sorted by file name in byte order. The weights hash is the SHA-256 of the manifest's bytes, lowercase hex. The spelling and the file set are shared with the gateway's model catalog (`eidola_common::weights_manifest`: `canonical_manifest` and `is_safe_name` here delegate to it, and `the_hashed_files_are_the_catalogs` holds this node's file lists to its `REQUIRED_FILES` / `OPTIONAL_FILES`), whose build checks each catalog row's published per-file manifest aggregates to the row's hash. It is the model's identity everywhere (`docs/model-identity.md` specifies it for reimplementation, with `scripts/weights-hash.py` to recompute it). It pins the weights, not exact behaviour: the engine build and its numerics are pinned by the deployment's measurement, not by this hash. Every manifest name is a **safe name**, `[A-Za-z0-9_][A-Za-z0-9._-]*` (`model-00001-of-00002.safetensors`): a shard named otherwise is refused from the listing, before anything is hashed, and `canonical_manifest` refuses one too. That is what makes the offline procedure below reproduce the manifest byte for byte: `sha256sum` escapes a name holding a backslash or newline (prefixing its line with `\`), `xargs` splits on whitespace and quotes, a leading `-` reads as an option, and the shell's `*` skips a leading `.`. Any name in the directory that is not UTF-8 is refused too (the model crate's `WeightSet` also refuses a non-UTF-8 shard name rather than converting it lossily, so distinct names can never share a manifest entry). Offline, inside the directory:

```sh
LC_ALL=C ls *.safetensors config.json model.safetensors.index.json \
    tokenizer.json chat_template.jinja generation_config.json 2>/dev/null \
  | LC_ALL=C sort | xargs sha256sum | sha256sum      # macOS: shasum -a 256
```

Every byte used is a byte hashed: shards are memory-mapped once and both hashed and loaded from that mapping; the other files are read once and parsed from the hashed bytes. `LoadedModel` can only be built by `LoadedModel::load`, which checks the hash first, and `start` re-checks a loaded model's hash and storage mode against the configuration.

**What binds the bytes after boot is the storage, not this process.** The hash is checked once; the shards stay memory-mapped (shared, file-backed), and routed experts are dequantised from them on later forwards, so a file modified in place after the check would change the model while `/v1/engine/info` still reports the verified hash. Copying hundreds of gigabytes into private memory is not an option, so the binding is the deployment's: in production the weights directory is a dm-verity volume, mounted read-only, whose every read the kernel checks against the root hash in the measured configuration, so no read can return bytes other than those the hash covered. The process does not assume that: `EIDOLA_ENGINE_WEIGHTS_STORAGE` is part of the measured configuration, and `verified-readonly` refuses deployments that clearly are not immutable, **before any weights file is opened, mapped or parsed** (the directory, then each file named in its listing; only metadata is read):

- every platform: each path's mount is read-only (`statvfs` `ST_RDONLY`). That flag is per mount: a read-only bind mount can sit over a filesystem still writable through another mount of the same superblock, so on its own it is dev-grade, and macOS (development only) stops here;
- **the directory is resolved once.** `model.rs::PinnedDir` resolves the configured path before anything else, and every check, listing and open after it goes through that resolution, never the configured path again, so a symlink on the configured path (or a directory above it) changed after the check cannot redirect what is hashed and mapped. On Linux it is `/proc/self/fd/<n>` of an `O_PATH` descriptor on the directory (no read access; the kernel resolves the magic link to the directory the descriptor holds); elsewhere (development only) the canonical path at that moment. Under `verified-readonly` every file the node reads must also be a regular file (`lstat`, not followed): a symlink's target is resolved again at every open, through paths the directory's read-only mount does not cover, while a regular file in a directory on a read-only superblock cannot be replaced. `dev-writable` follows symlinks (a Hugging Face cache snapshot is one);
- Linux: each path also resolves through `/proc/self/mountinfo` (its device id, and the longest mount point containing its canonical path, the last such mount winning) to a mount whose mount options **and superblock options** both contain `ro`. A filesystem on a dm-verity device always has a read-only superblock, so production passes; a read-only bind over a writable filesystem is refused. Mountinfo is read and parsed as bytes (mount points are byte strings), so an unrelated mount with a non-UTF-8 path cannot block the check.

Verified in containers: a superblock-read-only tmpfs is accepted, while a read-only bind mount of a writable filesystem and Docker's `--tmpfs …:ro` (a read-only mount over a writable tmpfs superblock) are refused; on macOS a read-only disk image is accepted and an ordinary directory refused. What this does not establish: that the bytes are the right ones (the weights hash does that, once), or that a privileged process in the VM will not remount the superblock read-write later; dm-verity is what binds every read. In turn `dev-writable` boots anywhere but says so in `/v1/engine/info` (`weights_storage`) and in `/healthz`'s body. A gateway pins the production configuration, so it never routes to a `dev-writable` node: its build refuses a pinned deployment whose config sets anything but `verified-readonly`.

## Wire contract

`POST /v1/chat/completions` accepts the gateway's strict request subset (`eidola-server-gateway/src/types.rs`: `model`, `messages`, `max_completion_tokens`, `temperature`, `top_p`, `stream`, `stream_options.include_usage`, `stop`, `tools`, `tool_choice`, `add_generation_prompt`, `continue_final_message`, an assistant message's `reasoning_content`, `cached_prefix`, with the same nullability and nested strictness) plus `cache_key`. Keep the two in step: a field the gateway starts forwarding must be added here, or every such request is refused. The gateway refuses what this node would refuse before routing it (`engine_router::subset`): the rules over a parsed request (`tool_choice`, the stop list, a zero completion limit, empty `messages`, image parts) are `eidola_common::engine_protocol`'s `check_*` functions and `SubsetError`, which `api::parse_request` calls too, so a change to one changes both; the content-part strictness and the sampling ranges (`SamplingParams::new`) are mirrored there, so changing either here means changing the gateway's mirror. Before either parse, `eidola_common::engine_protocol::check_request_json` scans the body without allocating and refuses (400) more than `MAX_REQUEST_JSON_VALUES` (2^18) JSON values, object keys counted, or nesting deeper than `MAX_REQUEST_JSON_DEPTH` (64): the parse trees cost memory per value, so the value count is what bounds a read slot. The gateway refuses the same bodies first.

- **Content parts** are stricter than the gateway's: every variant denies unknown fields. The template renders parts from the raw body and treats an `image_url`, `image`, `audio` or `video` key on any part as multimodal content, so a key the strict type does not name must never reach it. `image_url` parts are refused outright (text-only model).
- **`tool_choice`**: absent or `auto` offers the tools and parses calls; `none` renders the prompt **without** the tool definitions (the model is never offered a tool it may not call) and parses nothing, so it changes the prompt, and with it the reusable cache prefix, relative to the same request under `auto`; `required` and named functions are refused (no constrained decoding). App-core's chat path never sets `tool_choice`, but its local inference proxy relays whatever a local caller sends, so `none` is reachable and is supported exactly rather than refused.
- **`cached_prefix`** (`eidola_common::engine_protocol::CachedPrefix`, `{"cached_tokens": <u32>, "new_tokens": <u32>}` and nothing else; `null` is no declaration): the client's statement that the first `cached_tokens` tokens of the prompt as this node tokenizes it are in the prefix cache under the request's `cache_key`, and that the prompt has at most `new_tokens` more. The request is priced by those two numbers upstream, so the node runs it only if both hold and refuses it `409` otherwise, before anything of it is computed: the budget after tokenizing (`pipeline::prepare`, before submission, and **after the window**: a client budgets what a request adds at no more than the window leaves, so a prompt past the window is past that budget too, and it is refused for its length, since a client told its budget was exceeded sends the request again undeclared and would be refused and charged a second time; `a_declared_prompt_past_the_window_is_refused_for_its_length`), the cached part by the engine at first admission (`Request::required_cached_tokens`; `crates/eidola-engine/AGENTS.md` → A required prefix). **Its response opens only once the engine has admitted it** (`worker::Output::Admitted`, sent before the request's first tokens), so `cached_prefix_missing` is a plain HTTP error for a streamed request too, however long it waited for a seat; a request without a declaration opens its response as soon as the engine accepts the submission, as before. The usage reported is unchanged: `prompt_tokens_details.cached_tokens` is the hit the engine found, at least the declared number on a served request, and never an input to a price. **What a client can declare and have served** is `declared_prompt`'s rule on a resumed count the cache really holds as tokens: for a new turn, a tool round or a regeneration, the previous request's `prompt_tokens` (its prompt ends at the generation prompt, and the next one continues after an added token, so it is a token prefix: `a_new_turn_declaring_the_last_ones_prompt_is_served`, `a_regeneration_declaring_its_prompt_is_served`). For a continuation, prompt plus completion holds only where the continued prompt re-encodes to the earlier prompt followed by the generated tokens through the declared boundary; a `continuable` cut promises the text, not that the model sampled the canonical encoding of it, and where it did not (the dev model often does not, `.Large`+`roken` re-encoding as `.L`+`arger`+`oken`) the cache serves only up to the earlier prompt's regeneration point and the declaration is refused. The earlier prompt alone, with the completion counted as added bytes (`declared_prompt(prompt_tokens, completion_bytes, 0, window)`), is served in every case tested (`a_continuation_declaring_prompt_and_completion_needs_canonical_tokens`).
- **`cache_key`**: 32 bytes, base64url without padding — the shape `eidola_common::engine_protocol` states, which the gateway checks before a request is paid for (`api::tests::the_decoder_agrees_with_the_shared_shape_rule` holds this decoder to it). Decoded at parse time, the text scrubbed, and turned into the request's lineage under the core's per-boot key (`SaltDeriver::lineage`): the engine salt `HMAC-SHA256(boot_key, "eidola/kv/v1" ‖ key)` that names its cache entries and the key `HMAC-SHA256(boot_key, "eidola/kv-enc/v1" ‖ key)` its idle KV is encrypted under; the decoded key is dropped (zeroed) before the request reaches the engine. No key ⇒ `CacheScope::Private`: a fresh random salt and key, nothing reusable by any other request.
- **Messages and tools render from the body as sent.** The strict serde types only validate; the prompt is rendered from the same bytes parsed by the chat crate's order-preserving JSON parser, because `serde_json::Value` would sort keys and round big integers that the template prints.
- **Request data is never a control token.** The prompt is encoded with the chat crate's `encode_prompt` over `render_prompt`'s data spans: an added token (`<|im_end|>`, `<|im_start|>`, `<think>`, `<tool_call>`, …) spelled by a message, a tool result, a role, a tool-call name or argument, or a tool definition is encoded as ordinary text, and only the template's own text makes one (`crates/eidola-engine-chat/AGENTS.md` → Request data is never a control token; `tests/control_tokens.rs`). Nothing is refused or rewritten: the text reaches the model as text.
- **Sampling**: `temperature` and `top_p` from the request, else `generation_config.json`'s (as vLLM applies a model's generation config), else 1.0; `top_k` from the generation config; a fresh random seed per request.
- **A `length` ending says whether it can be continued exactly**: the finishing choice carries `continuable`, the chat layer's `resumes_exactly_as_tokens` over the engine's own output, the decoder's lossy final flush included (`a_length_ending_says_whether_it_can_be_continued_exactly`). The verdict holds in tokens: the decoder tells the chat layer where the model sampled added tokens, and an ending is continuable only when those are the tags the template writes back, since everything else a client returns is encoded as text (`tests/control_tokens.rs`). It is also false where a continuation could not run or would not be exact for the node's own reasons: when the ending is the **context window** rather than the request's `max_completion_tokens` (`Prepared::window_bound`: no limit, or one at or past the room, leaves a continuation prompt of the whole window, refused `context_length_exceeded`; `a_length_ending_at_the_context_window_is_not_continuable`), when the engine ended it for lack of KV memory (`FinishReason::KvExhausted`, which reads `length` on the wire: a continuation's prompt is the same tokens and needs at least the memory this one ran out of, so it would be refused or end the same way; reachable only with pools smaller than one `MAX_MODEL_LEN` sequence, which the CUDA executor's derivation refuses; `a_length_ending_out_of_kv_memory_is_not_continuable`), when the stop matcher was holding a possible partial stop sequence at the cut, and when the model sampled a special token, which the text given out does not show. A client continues only where it is `true`.
- **Continuation** (`continue_final_message`, `add_generation_prompt: false`): accepted under `check_continuation`, the prompt rendered ending inside the final message at the field continued (`crates/eidola-engine-chat/AGENTS.md` → Continuation) and the output parsed from there. Under the request's cache key the engine's continuation hit point (`crates/eidola-engine/AGENTS.md`) is where the previous request's sealed prompt-plus-output ends, so a continuation is served from cache up to the first token its re-encoding diverges at, and at least through the previous prompt's last whole block.
- **`max_completion_tokens`**: clamped to the room left in `MAX_MODEL_LEN`; absent means that room.
- **Stop sequences** are matched here on the decoded text (special tokens skipped), before reasoning/tool parsing, by one KMP automaton per sequence (at most 4 sequences of at most 256 bytes, `api::MAX_STOP_BYTES`: stops are delimiters, Eidola's chat path sends none and its local proxy relays only a local caller's, and the cap bounds the matcher's tables and held-back text to a few kilobytes per request, which an uncapped 32 MiB body would amplify to hundreds of MiB): only the longest suffix that is a prefix of some sequence is held back, so text that cannot begin one is released at once, and the work is linear in the text however long a sequence is. The first occurrence to complete wins; on a match the text before it is released, the sequence and everything after it dropped, `finish_reason` is `stop` (or `tool_calls` if calls were emitted), and the engine request is cancelled. `completion_tokens` counts through the token that completed the match.
- **Every answer is a stream.** A request must ask for one, `stream: true` with `stream_options.include_usage: true`, and is refused (400) otherwise: the running count below is what the gateway bills a request it ends early by, and the frames are what let it tell a slow engine from a stopped one, so the gateway asks for a stream whatever its own client asked for and assembles a client's blocking answer itself (`crates/eidola-server-gateway/AGENTS.md` → Routing to engines). The stream is OpenAI's chunk shape: a role chunk at once, one chunk per non-empty delta (`reasoning_content`, `content`, `tool_calls` with `index`, each call whole), a finish chunk with an empty delta (and `continuable` on a `length` ending), a usage chunk with `choices: []`, then `[DONE]`. A mid-stream failure ends the stream with an `event: error` event. Every stream is written in frames, and every other response padded (Response shape, below).
- **Usage** includes `prompt_tokens_details.cached_tokens`, the prompt positions served from the prefix cache. It is for the client's information only: nothing here prices, and the gateway's charge never depends on it.
- **The running count.** The role chunk and every delta chunk also carry the running `usage`: the prompt, and the completion tokens decoded so far, text the stop matcher holds back included. A step that moved the count and gave out no delta (a tool call still being read, which the parser gives out whole at its end; a held stop prefix or partial tag; a skipped special token) sends a chunk with an empty delta (`"delta": {}`, `finish_reason: null`) carrying the count alone, which the gateway keeps and does not forward. The gateway keeps the last count it received and charges a stream it cuts short (its client left, its deadline, an engine failure) for exactly that, so this count is what a cut request is billed by; it forwards only the final usage chunk to its client. The gateway cuts a stream by dropping its connection, which the guard turns into a `Cancel` (below). Tests: `streaming_shapes_text_and_usage` (present on every delta chunk, starting at zero, never decreasing, never past the final count; a request without a stream or without `include_usage` refused), `held_back_steps_report_the_running_count` (steps held back by the stop matcher report the count alone).

`GET /v1/engine/info` (gateway token, no weights header) returns `model`, `weights_sha256`, `weights_storage`, `executor` (`cpu` / `cuda`), `device` (`null` for the CPU executor; for CUDA the driver's device `name`, `compute_capability` `"major.minor"`, the kernel `image` it runs, `sm_count` and `memory_bytes`: hardware facts, nothing about any request), and `build` (`crate`, `version`, and `git_sha`: the `EIDOLA_GIT_SHA` value the build was given at compile time, `null` otherwise; nothing is read from the build environment implicitly). `GET /healthz` is unauthenticated and content-free: `200 ok` while the engine thread runs (`ok; weights-storage=dev-writable` on a development node), `503` after it stopped or once the step watchdog has found it wedged (Concurrency, below). The gateway's router probes both before a node takes traffic and periodically after: `/healthz` must be exactly `ok` and `/v1/engine/info` must report the pinned model, weights hash and `verified-readonly`, so changing either response's shape changes what the gateway accepts (`crates/eidola-server-gateway/AGENTS.md` → Routing to engines).

## Response shape

The host of this VM and the network between it and the gateway see each write's size and time, so neither follows the answer (`docs/privacy-guarantees.md` §3.8; the reasoning, the published attacks and what the client hop does: `crates/eidola-server-gateway/AGENTS.md` → Client-facing traffic shape).

- **A stream is frames of one size on a fixed tick** (`http::Shaped`): `eidola_common::engine_protocol::STREAM_CADENCE`, one 4 KiB frame every 20 ms, from the moment the response opens (the role chunk is in the first) until the frame that carries `[DONE]` or the `event: error`. Each tick takes what the engine has produced since the last off the request's event channel (`try_recv`, up to `STREAM_BACKLOG_BYTES` waiting) and writes one frame: whatever event bytes are waiting, up to its size, and padding the reader ignores for the rest. The events are cut by `eidola_common::stream_shape::Framer`, the gateway's own framer for its client, and the gateway reads them back with that module's `StreamReader`, so the two sides of the hop share one format; the tick is this node's own (`tokio::time::Interval`, a late tick moving the schedule rather than doubling up). `Cache-Control: no-cache, no-transform`, and nothing here compresses.
- **The rate, against the fastest stream.** A chunk is one engine step, not one token (a step's accepted tokens, up to `1 + EIDOLA_ENGINE_DRAFT_TOKENS`, are one delta), and with the running usage and the model's 64-digit id it is about 400 bytes on the wire. 200 KiB/s is about 500 chunks a second, a step every 2 ms, and 2,000 tokens a second at four tokens a step; the fastest single-request decode step measured for the served model on its GPU is 7.3 ms, in another serving engine, and this one's is slower (`crates/eidola-engine-cuda/AGENTS.md`), so the cap does not bind. The engine's aggregate rate across requests does not enter: each stream has its own frames. Faster output waits in the stream's backlog and is delivered at the cap; past `STREAM_BACKLOG_BYTES` (1 MiB, five seconds of frames) the stream stops taking output, its event buffer fills, and the engine cuts it off as it cuts off a reader that stopped (Concurrency, below). **Cost**: up to 20 ms between a step and its frame, and 200 KiB/s on the connection for as long as a response runs, mostly padding.
- **Every other response is padded** (`http::shape_response`, a layer around every route and the fallback): the body with trailing spaces to `stream_shape::body_bucket` (the next power of two, at least 4 KiB) and a matching `Content-Length`: every `ApiError` refusal (the authentication refusal included, which no handler sees), `/v1/engine/info`, `/healthz`, a 404 or 405. JSON is unchanged by trailing whitespace; the gateway's probe compares `/healthz` with its padding set aside (`stream_shape::unpadded`).
- **What it does not hide**: when a response opened (after admission, before prefill; for a request declaring a cached prefix, after the engine's first admission of it, so its time waiting for a seat too) and how long it ran; a padded body's bucket; the request, which is not padded; and this VM's own activity (its scheduling, and the GPU's work and transfers), which the host observes directly.
- Tests: `a_streamed_answer_is_frames_of_one_size_on_a_tick` (over a raw socket: every HTTP chunk is the frame size, the writes are at least a tick apart, and the frames read back as the events), `every_other_response_is_padded_to_a_bucket`; the framer and reader's own tests in `eidola-common` (`stream_shape`). `TestNode::chat_stream` reads every streamed test through the shared reader and checks the body is whole frames.

## Concurrency

The executor seam is synchronous, so one dedicated thread owns the `Engine` and runs its step loop. HTTP tasks reach it over channels: commands (`Submit`, `Cancel`) in, one bounded event channel per request out (`worker::EVENT_BUFFER` = 256 events, each one step's few tokens; the engine thread never blocks on a reader). A reader that has gone away, or has stopped reading long enough to fill its buffer, is cut off at the next send: the request is cancelled in the engine (no more compute) and its channel closed, so the reader gets an error after draining. A streamed response drains its channel once a tick (Response shape), and its byte-bounded backlog and the kernel socket buffers behind it absorb far more than 256 events, so only a reader that has truly stopped is cut off. Between steps the thread drains every pending command. When the last request in the engine ends (finished, or cancelled while running), the thread runs the maintenance it left at once (`Engine::flush`: the blocks it left cached encrypted, the ones it freed zeroed, the keys those operations carried dropped) before publishing its counters, rather than leaving it to the next sweep; with requests still running, the next step runs it anyway. When idle it sleeps until a command arrives or the one-second sweep is due, and sweeps the prefix cache so expired KV is zeroed without traffic. The idle sweep keeps an absolute deadline (each wait is for the time left until it), so commands that leave the engine idle (refused submissions, cancels of finished requests), however frequent, cannot postpone it; while busy, each engine step sweeps on the core's own schedule.

- **Admission** is bounded by `EIDOLA_ENGINE_MAX_REQUESTS` (rendering, tokenizing, running or queued). A permit is taken before rendering or tokenizing and is **owned by the work it bounds** for that work's whole life: it moves into the blocking preparation task (which runs to completion even when a disconnect drops the handler), comes back with the prepared request, travels with the submission, and is then shared between the engine's record of the request and the response's guard, which lives exactly as long as the request's receiver: the slot is released only when the request has left the engine **and** its buffered output has been drained or dropped. Buffered output is therefore bounded by `EIDOLA_ENGINE_MAX_REQUESTS × EVENT_BUFFER` events. With none free the request is refused at once (`overloaded`); nothing queues unboundedly in front of the engine. Rendering and tokenization run on the blocking pool.
- **Reading is bounded too.** The body (up to 32 MiB) and its two parses (the strict serde types and the order-preserving JSON) exist before admission, so a second bound with as many slots as admission (`AppState::reading`) covers them: a slot is taken after the weights-hash check and before the first body byte is read, and released once the request holds its admission permit or is refused. With none free the request is refused at once (`overloaded`), its body unread. Request memory in front of the engine is therefore at most `EIDOLA_ENGINE_MAX_REQUESTS` bodies of ≤ 32 MiB with their parses (being read or parsed) plus `EIDOLA_ENGINE_MAX_REQUESTS` parsed requests (admitted, being rendered or tokenized), whatever the traffic. The gateway is the only authenticated caller, so a slow upload holding a read slot is the gateway's own doing.
- **Cancellation**: each request holds a guard that sends `Cancel` when dropped, so a client disconnect (the SSE stream or the handler future dropped) releases the sequence before the engine's next step, including a request still waiting for a seat. Independently, the engine thread cancels a request whose reader has gone away the next time it has output for it.
- **Failure**: an `ExecutorError` is fatal (the host cannot know which writes landed). **Any** exit of the engine thread (that, a panic, every handle dropped) is fatal, structurally: the thread owns an `ExitSignal` whose drop (on return or unwind alike) turns health `503` and resolves `Node::engine_stopped`; `serve` treats that receiver resolving in any way, signal or dropped sender, as fatal and returns an error at once, without draining (graceful draining is only for SIGINT/SIGTERM); `run` then tears the runtime down within `TEARDOWN_LIMIT`, so open connections (even one stalled mid-upload) cannot keep the process alive, and `main` exits non-zero. In-flight requests see their channel close and get an error.
- **A step that never returns is fatal too** (`worker::Watchdog`). The executor seam is synchronous, so a step stuck inside the executor (a driver call that never returns) would otherwise go unnoticed: health would stay `200 ok`, so the gateway's probe would keep passing and its breaker stay closed; new requests would queue behind the stuck step until admission filled and then be refused `overloaded`, which the gateway counts as load, not ill health; and every open stream would go on carrying padding frames on its tick, so its request would be held to the gateway's 30-minute deadline. So the engine thread records when each call that reaches the executor starts (`Engine::step`, the idle `Engine::sweep`, the last request's `Engine::flush`) and clears it when the call returns, and a watchdog on its own OS thread checks it a few times per limit; it shares only atomics with the engine thread and the map of in-flight requests' channels, which the engine thread never holds locked across an executor call. Its own thread, not a task, because it must run when the runtime's workers are busy or the runtime is gone, and must take nothing the stuck thread or the runtime might hold: the map is taken with `try_lock`, bounded, and the exit follows whether or not it was. Nor does the exit wait on output: the log line saying why is written by a thread of its own, because the log's writer blocks while standard output is full or locked (`a_wedged_engine_ends_the_process_though_its_log_cannot_be_written`). A call running past `worker::STEP_STALL_LIMIT` (120 s; its doc comment gives the reasoning: the longest legitimate step, a full step budget of prefill at the end of a 2^20-position context, estimates to about 14 s on the B300) trips it, once: health turns `503`, `submit` refuses (`engine_unavailable`) rather than queueing behind the stuck step, every in-flight request gets `Output::Failed` (its channel closes after it), so each stream's next frame carries an `event: error` and the gateway settles it on what was generated and counts the failure toward its breaker; it logs one content-free line, waits `STALL_EXIT_GRACE` (1 s, fifty ticks) for the frames, and ends the process with `libc::_exit(STALL_EXIT_STATUS)` (70), which runs no `atexit` handler or library destructor (the GPU driver's among them) that could wait on what the stuck thread holds, so the platform restarts the node. The stuck thread is never joined. Only if the step returns during the grace does the engine thread stop by itself first (`stopped`, then `main`'s ordinary non-zero exit). Not watched: the executor's construction at boot (weights load, graph capture; the node does not listen until it is done) and its drop at the end of a graceful shutdown, which `ENGINE_SETTLE_LIMIT` bounds.
- **What a wedged node's exit does not scrub.** The stuck thread owns the executor and the engine, and nothing else may touch them, so the forced exit runs none of what an engine stop does: no last `flush` (freed blocks still holding KV not zeroed, blocks left idle not encrypted), no executor drop (the CUDA executor's zeroing of its whole device memory and step scratch, `crates/eidola-engine-cuda/AGENTS.md` → Idle scrub). Device memory at that moment, the plaintext KV and scratch of the requests in flight included, is left to the driver as the process ends; the node does not scrub it and does not rely on the driver to. Host memory (the CPU executor's pools, the host tier, whose blocks are ciphertext anyway, the process's own buffers) goes back to the guest kernel, inside the confidential VM, which zeroes a page before it maps it into another process as anonymous memory. Idle cache entries stay ciphertext under keys held only in the dying process's memory. The engine's privacy invariants 4 and 6 (zero on free, bounded retention) describe a running engine and are not covered across this exit.
- **Graceful shutdown is bounded.** On SIGINT/SIGTERM `serve` stops accepting and lets open requests finish for at most `DRAIN_LIMIT` (5 s); `run` then tears the runtime down (`TEARDOWN_LIMIT`), which drops every request still open, so each guard cancels its request in the engine by the ordinary path. `main` keeps no engine handle, so with the router gone the engine thread runs the maintenance those requests left (freed KV zeroed, idle KV left encrypted, keys dropped) and stops, and `run` waits for that for at most `ENGINE_SETTLE_LIMIT` (2 s) before the process exits `0`. A long generation or a stalled reader therefore cannot hold the node until it is killed (`tests/engine_exit.rs`).

## Content-free by construction

Prompts, outputs, cache keys and salts are content; so is anything derived from one request (its token counts, its error details). None of it is logged:

- `ApiError`'s `Display` (the only rendering that reaches logs) is the error category alone; the detail goes only into the caller's response body (`error.rs`, tested).
- Configuration and boot errors name variables, files and limits, never values; the gateway token is held only as its SHA-256 and prints as a redaction marker.
- The engine core's secret types (`CacheKey`, `EngineSalt`, `KvKey`, `Lineage`) print redacted and are zeroed on drop. The cache key is decoded into a fixed stack buffer handed to `CacheKey::from_buffer`, which copies it into the zeroizing allocation and scrubs the buffer; the key's JSON text is scrubbed too: serde deserializes it straight into `api::CacheKeyText`, which zeroes it on drop, so it is scrubbed even when a later field fails to parse and serde drops the partly built request; the order-preserving parse's copy is zeroed explicitly. Not reachable from here: the body's bytes in the HTTP stack's shared read buffers, and serde_json's scratch buffer when the key's JSON string uses escapes. The gateway token is scrubbed after boot verification, but stays in the process environment (removing a variable is `unsafe` in this edition).
- `ValidRequest` prints a marker, not its fields.
- Per-request logging is limited to refusal categories at `debug` and failures at `warn`, with no sizes.

**Metrics**: `worker::Stats` keeps content-free counters (submitted, finished, cancelled, rejected, refused at admission for a declared prefix the cache does not hold, in-engine, idle-KV keys held, engine steps, preemptions, drafts proposed and accepted). They are in-process only today (the tests read them); exporting them over OTLP like the gateway's telemetry is not wired yet. Aggregate token totals are deliberately not counted: at low traffic a short window's total is one request's size.

## The executor seam

`EIDOLA_ENGINE_EXECUTOR` selects the executor; `lib.rs::start` builds it on the engine thread and the rest of the node is executor-agnostic (`worker::spawn` is generic over `Executor`). `cpu` is `eidola-engine-cpu`'s f32 reference executor with one step shape (`MAX_SEQS` × `MAX_BATCHED_TOKENS`, unpadded) and MTP drafting over `DRAFT_TOKENS` depths; `LoadedModel` dequantises the f32 reference model for it. `cuda` (the `cuda` feature) is `eidola-engine-cuda`'s executor, below. The node only constructs executors: it changes no number either computes.

## The CUDA executor

`eidola-engine-cuda` runs exactly MiMo-V2.6-Flash's configuration on one Blackwell GPU, and the node neither widens nor narrows that: it hands the executor its configuration and returns the executor's own refusal (`cuda: unsupported model: <field> is …`). It has one step shape (`MAX_SEQS` × `MAX_BATCHED_TOKENS`, as on the CPU executor), replays captured graphs for pure-decode steps when `EIDOLA_ENGINE_CUDA_GRAPHS` is `on` (captured at boot, one per rung of its decode ladder; prefill stays eager; doctrine and the pending GPU validation in `crates/eidola-engine-cuda/AGENTS.md` → Decode graphs) and runs every step eagerly when it is `off`, drafts `DRAFT_TOKENS` tokens a step with the checkpoint's MTP layers when that is not 0 (up to Flash's three; doctrine and its GPU validation in `crates/eidola-engine-cuda/AGENTS.md` → Drafting). Pinned deployments draft `k = 3`: attention is batch-invariant, so the verify pass computes each position's logits bit for bit as a decode step does and acceptance takes the target's argmax, which makes greedy output byte-identical at every width; the width is purely a speed setting, and uses device 0 (`cuda::DEVICE_ORDINAL`; which physical GPU that is is the deployment's choice, `CUDA_VISIBLE_DEVICES` or the one GPU a confidential VM is given). For it `LoadedModel` builds no reference model: the executor copies the checkpoint to the device as stored, from the same verified mapping the hash was computed over.

**Boot order** (`boot` → `LoadedModel::load` → `start` → `cuda::prepare` → the engine thread), each step refusing before the next begins:

1. the weights storage (`verified-readonly`), then the weights hash, then `config.json` and the chat files;
2. `MAX_MODEL_LEN` against `max_position_embeddings` (a `DRAFT_TOKENS` past Flash's three MTP layers never gets here: the grammar refuses it);
3. the executor's `CudaExecutor::preflight`: the model is Flash's, field for field, the sampleable vocabulary, the context, the step shape and the KV geometry, all from `config.json` alone, with no device;
4. the KV block counts derived from `KV_DEVICE_BYTES` (below), refused if they cannot hold one `MAX_MODEL_LEN` sequence, then the executor's preflight again over the derived geometry;
5. with `EIDOLA_ENGINE_GPU_CC=required`, the GPUs' confidential-computing state (below); with `not-required`, a warning that it is unchecked;
6. the device opens (`no CUDA driver or device` on a machine without one), and `KV_DEVICE_BYTES` must be less than its memory;
7. on the engine thread, `CudaExecutor::new`: the device requirements (`check_device`: compute capability 10.x, opt-in shared memory, 148 SMs, cluster launch), every kernel image against the compiled-in manifest (a missing or altered image is refused), then the weights, then every pool. Running out of device memory is a driver error here, and refuses the boot like any other;
8. `Engine::new` over it, and only then does the node listen.

**GPU confidential computing** (`gpu_cc.rs`). On the platform, the GPU image's measured boot already opens the GPUs to CUDA work only after their device IDs check out and NVIDIA's local verifier has passed for exactly `gpus` of them (it sets NVML's CC ready state last). The node makes that claim its own, and adds what NVIDIA's default appraisal policy does not test: with `EIDOLA_ENGINE_GPU_CC=required`, before any device is opened, it loads the driver's NVML (`libnvidia-ml.so.1`, by `libloading`, which the executor's driver loader already brings into the graph; nothing linked at build time) and requires `nvmlSystemGetConfComputeState` to report `ccFeature` enabled (1), `devToolsMode` off (0) and `environment` production (2), and `nvmlSystemGetConfComputeGpusReadyState` accepting work (1); any other value, an unknown one included, a missing library or a failing call refuses the boot. Names, values and struct layout are `nvml.h` from driver 595.71.05 (CUDA 13.2.2's `cuda_nvml_dev` 13.2.86), the driver the platform's GPU image ships; both queries are system-wide. The decision is `gpu_cc::check`, a pure function over those four values, so it is tested on any machine; only the query needs a driver. `not-required` skips the check (with a warning) for development on a GPU without CC, such as a rented B300 with CC off: the setting is measured like every other, so it cannot change without changing the configuration hash, and the gateway's build refuses to pin a deployment that sets anything but `required` (`check_deployment`), so a gateway never routes to a node that skipped it. It is `cuda`-only (refused with `cpu`, like the executor's other settings). What validates it where: the refusal path (`required` on a machine without NVML or without a CC-mode GPU, in process and as the binary) and the `not-required` boot run anywhere, the Mac and a non-CC GPU host included; the accepting path needs a GPU in CC mode with the ready state set, which only the platform's GPU image (or an equivalent CC host) provides.

**KV sizing.** `EIDOLA_ENGINE_KV_DEVICE_BYTES` is the device memory for the KV pools; `cuda::derive_kv_blocks` turns it into per-group block counts from measured values alone (never from what the device reports), so one configuration derives the same pools on every node. With `B` the block size and, for the sliding group's window `W`, `R = ceil((W - 1) / B) + 1` (the core's bound on one window's blocks), the sliding group gets `1 + MAX_SEQS × ((1 + P) × R + 1) + ceil(MAX_BATCHED_TOKENS / B)` blocks (the null block; per seated sequence its live window, the partly filled block after it and `P` retained windows, `P` = 3 with the prefix cache and 0 without; and the positions one step adds), so sliding blocks never run out while the global pool has room. With drafting the drafter group (the MTP depths' KV, a sliding window too) gets the same count by the same rule. The global group gets the rest, `floor((KV_DEVICE_BYTES − sliding bytes) / global block bytes) − 1`, capped at the tables' `i32` range, sliding bytes counting the drafter pool. Every pool also holds one pad block past its count (where a decode graph's padding rows write; no table ever maps it), and the budget is charged for it: sliding bytes are each sliding pool's count plus one, and the `− 1` is the global pool's. Block bytes are the executor's own (`GroupGeometry::block_bytes`: BF16 K and V of every layer of the group, and for a drafter block its boundary tap, an f32 row of the hidden size per depth). Weights, scratch and the sampler's buffers come on top of the budget: leave them room.

**The host tier.** `EIDOLA_ENGINE_KV_HOST_BYTES` is the confidential VM's memory the prefix cache keeps idle entries in when the KV pools run short (demoted as the ciphertext they already are, promoted back for a hit: `eidola-engine/AGENTS.md` → Host tier); 0 is none. For `cuda`, `cuda::derive_host_blocks` scales the device pools' mix to it: each group gets `floor(n_g × H / Σ n_h b_h)` host blocks (`n` the derived device counts, `b` the block bytes, the null block among them), so the tier never exceeds the budget, and a budget under two blocks in a group is refused before the device (the least accepted budget is `engine_deployment::cuda_kv_host_min_bytes`, which the gateway's build holds a pinned deployment's non-zero tier to; `cuda::tests::the_shared_host_minimum_is_the_derivations` holds the two equal); the executor pins it (`cuMemHostAlloc`). For `cpu`, `lib.rs::cpu_host_blocks` gives every group `H / CpuExecutor::kv_block_bytes` blocks, `mlock`ed. The gateway charges the whole budget to the VM's `memory` (`engine_deployment::check_resources`). **The node never runs where memory reaches durable media**: `swap::check_guest` refuses a guest with any active swap area (`/proc/swaps`, header then one line per area; a swap file, a partition or zram alike; a kernel without swap support has no list, and passes) before anything else at boot, on Linux, for every `verified-readonly` node and every node with a host tier. Hibernation is not something the guest supports: it writes its image to a swap area, and there is none. A `dev-writable` node without a tier (the dev model, the in-process tests, CI runners that have swap) is not checked, and on other systems (macOS, development only) the check is compiled out rather than switchable at run time. The pinned allocations make the tier unswappable on their own; refusing swap covers the rest of the process (prompts, outputs, keys in flight).

**Zero-on-free on the device.** The core queues `Maintenance::Zero` for every block whose refcount reaches zero (`eidola-engine`'s privacy invariants); the CUDA executor applies it as one `cuMemsetD8Async` over the block's whole byte range (every layer's K and V of that group), on the step's stream ahead of the forward, and its pools start zeroed (`alloc_zeros`). `ResetSlot` scrubs per-slot state the same way. `Encrypt` and `Decrypt` run the AOT cipher kernel over the same byte ranges (`crates/eidola-engine-cuda/AGENTS.md` → The executor → Idle encryption), so a cached block nobody uses is ciphertext on the device. The per-boot salt and key derivation and the TTL sweep are the core's and the worker's, executor-independent. Its `tests/engine.rs` checks "every free block is zero on the device or has a zero queued" after every step on a real checkpoint.

## The image

`oci/eidola-server-engine/Containerfile` builds the node's release image, `ghcr.io/eidola-ai/eidola-server-engine` (the prefix `engine_deployment::deployment::ENGINE_IMAGE_PREFIX` holds every pinned deployment to, by full digest): bake targets `server-engine` / `ci-server-engine`, CI's `oci-engine` job, `just engine-image` locally (prints the digest). It is compiled by StageX like the gateway's, from the same pinned release (`sx2026.09.0`), but it cannot be the gateway's static musl binary, and the reason is linkage:

- **The node is a dynamic glibc binary.** The executor reaches the driver through `cudarc`'s dynamic loading and the CC check reaches NVML through `libloading`: both `dlopen` (`libcuda.so.1`, `libnvidia-ml.so.1`) at run time, and nothing of CUDA is linked at build time, so the build needs no toolkit. A static musl binary cannot `dlopen`, and NVIDIA's libraries are built against glibc, so a musl process cannot host them.
- **It is cross-compiled for `x86_64-unknown-linux-gnu` by StageX's own toolchain.** StageX's rustc is musl-hosted and ships a standard library only for its musl target, so the Containerfile's `std` stage builds the standard library for the glibc target from the `rust-src` that same rustc ships (`-Zbuild-std`, the one step that uses unstable cargo, in its own stage) and installs it into rustc's sysroot; the node then builds on stable with a plain `--target`. The linker is StageX's `x86_64-linux-gnu` cross GCC (`core-cross-x86_64-gnu-gcc`), pointed with `--sysroot` at StageX's glibc (`user-glibc`, from StageX's user tier), which is also the glibc the image ships. The cross GCC carries a glibc of its own, configured under its `/opt/cross` prefix; nothing links against it. That rustc is the one `rust-toolchain.toml` names (root `AGENTS.md` → One Rust version everywhere), and the `toolchain` stage checks `oci/pallet-rust`'s record of it against `rustc --version`.
- **The unwinder is LLVM's libunwind, linked statically; no `libgcc_s` ships.** The cross GCC's `libgcc` was built without libc (GCC's `inhibit_libc`: it was configured with no target headers where it looks for them), so its unwinder can neither find a running program's frames (it imports no `dl_iterate_phdr` or `_dl_find_object`) nor call `abort`: a Rust panic or a C++ exception traps instead of unwinding. The `std` stage therefore compiles libunwind from `rust-src` (as Rust's own bootstrap does) and builds std with its `llvm-libunwind` feature, so the unwinder is inside the binary, which names only `libc` and `libm`. No driver library the node loads needs `libgcc_s` (on driver 595.71.05 only `libcudadebugger` names it).
- **The image carries the C runtime, never the driver.** `/lib64` holds the loader (`ld-linux-x86-64.so.2`, the binary's interpreter at the path the x86-64 ABI gives it) and exactly the glibc the binary was linked against (`libc`, `libm`, `libdl`, `libpthread`, `librt`, stripped of StageX's debug information), and OpenSSL 3's `libcrypto.so.3`. **OpenSSL is there only as a file for NVIDIA's library**: in confidential-computing mode `libcuda` loads `libnvidia-pkcs11-openssl3.so.<driver>`, which needs `libcrypto.so.3`, and the container must supply it; the node itself never links or loads it. It is StageX's OpenSSL release (same version, source hash and configuration as `core-openssl`) rebuilt with the gnu cross compiler, since StageX's own is musl-linked. Every other library the driver loads (checked on driver 595.71.05's `libcuda`, NVML, `libnvidia-gpucomp`, `-nvvm`, `-tileiras`, `-ptxjitcompiler`, `-sandboxutils`) needs only glibc. The Containerfile's `assemble` stage refuses to build if the binary's interpreter is not `/lib64/ld-linux-x86-64.so.2`, if any shipped ELF carries an RPATH or RUNPATH, or if any shipped ELF names a library the image does not ship.
- **The driver comes from the platform, and the loader's own search path finds it.** On the platform the GPU image's measured root holds the driver's user space (595.71.05) under `/usr/lib/x86_64-linux-gnu`; the NVIDIA container runtime (CDI mode, `runtime: nvidia`) bind-mounts those files and the device nodes into the container at the same paths, and its hooks add the soname links. StageX's glibc is configured under `/usr` with its libraries in `/usr/lib/x86_64-linux-gnu`, so its loader searches `/etc/ld.so.cache`, then `/lib64`, then `/usr/lib/x86_64-linux-gnu`: the image's own libraries and the mounted driver are both on the default path, for the node and for every library the driver loads, and no binary carries a search path. The driver's libraries must match the guest's kernel module; the R580 (CUDA 13.0) driver API is the oldest the executor targets.
- **The kernel images come in as an image pinned by digest.** They are compiled by NVIDIA's CUDA toolkit, which StageX does not carry, so `oci/eidola-engine-kernels/Containerfile` builds them with the kernel crate's own Nix expression (the build `just engine-kernels` runs) inside a pinned `nixos/nix` container, fails unless the build's `manifest.json` equals `kernels.manifest.json` byte for byte, and ships `cubin/`, `fatbin/` and that `manifest.json` in a `FROM scratch` image (`ghcr.io/eidola-ai/eidola-engine-kernels`; bake `engine-kernels` / `ci-engine-kernels`). The node's Containerfile names that image by digest on its `AS kernels` line, the one place the digest is written. The bake targets supply the same input as the `engine-kernels` target built from the tree, and `scripts/artifact-manifest.sh` fails the build unless that build's digest is the pinned one, so a new pin is published by the first run that builds it and `just engine-image` works before anything is published; `just engine-kernels-image` prints the digest to pin. Trust stays with the manifest: the `assemble` stage requires the image's `manifest.json` to be the committed one and every listed cubin and fatbin to have its recorded size and SHA-256, and copies exactly those files to `/opt/eidola/kernels` (`cubin/`, `fatbin/`), which a deployment's `EIDOLA_ENGINE_KERNELS_DIR` names. The node checks each against the compiled-in manifest again before loading it.
- **Nothing else.** No shell, no `/etc`, no environment (every setting is the deployment's measured env), `USER 65534:65534`, `ENTRYPOINT ["/eidola-server-engine"]`. The weights are never in the image: a deployment mounts its model pack read-only at `/tinfoil/models/<name>`.

The image's digest is a function of source: StageX's pinned images, the OpenSSL source hash, `Cargo.lock` and the standard library's own lockfile, the kernel image's digest (itself a function of the kernel crate: toolkit and upstream sources by hash), and the Containerfile, with BuildKit's `rewrite-timestamp` output like every other image. Two builds of `server-engine` through `scripts/artifact-manifest.sh` with every stage of both Containerfiles rebuilt (pinned base images only from cache) produced the same digest on an Apple-silicon host under linux/amd64 emulation; the first native amd64 build is CI's. Cargo runs at most four compiler processes, and the kernel build Nix on at most four cores (one `nvcc` per core, and a CUTLASS translation unit takes gigabytes: sixteen ran a 16 GiB builder out of memory); parallelism reaches neither output. The one closed component is NVIDIA's CUDA toolkit, used at build time to compile the kernels (`crates/eidola-engine-kernels/AGENTS.md` → The closed-tool boundary); its output is pinned by the committed manifest, not trusted. The driver is NVIDIA's closed user space, supplied and measured by the platform's GPU image, outside this image's digest. The digest is recorded in `artifact-manifest.json` from manifest schema 4 (accepted by clients, not yet emitted: `releases/README.md`). **Checked without a GPU** (a linux/amd64 container, driver 595.71.05's `libnvidia-ml` and `libcuda` from NVIDIA's Ubuntu package bind-mounted at `/usr/lib/x86_64-linux-gnu/<soname>`, a Flash-shaped weights directory): the node boots through its host-side checks to the CC check, loads NVML and `libcuda` from `/usr/lib/x86_64-linux-gnu` and NVML's `libpthread`/`libdl`/`librt` from `/lib64` over the loader's system search path (`LD_DEBUG=libs`), and refuses with NVML's own `Driver Not Loaded`; with `not-required` it reaches the device and refuses `no CUDA driver or device`; and `libnvidia-pkcs11-openssl3` loads with its `libcrypto.so.3` resolved to `/lib64`. On the synthetic dev model with the CPU executor it answers token for token as a node built by the repository's own Rust toolchain does. **Not yet validated on the platform:** a run against a real GPU in confidential-computing mode; that the runtime's CDI hooks succeed on a `FROM scratch` image with no `/etc` (the update-ldcache hook writes `/etc/ld.so.conf` and needs a writable root); and that the unprivileged user can read the mounted model pack and open the device nodes; all need the platform's GPU image.

## Configuration

All required (the `cpu`- and `cuda`-only ones with their executor, and refused with the other); an empty value counts as missing. Everything but the secret token is parsed by `eidola_common::engine_deployment::parse_measured` (the variable names live there too, re-exported as `config::env`, with `Sizing`, `CacheConfig` and `WeightsStorage`); `Config::from_lookup` calls it, verifies the token against the parsed hash, and maps the parsed `ExecutorSettings` onto `ExecutorConfig`. A build without the `cuda` feature refuses `EIDOLA_ENGINE_EXECUTOR=cuda` with that reason before the grammar runs. The gateway's build runs every pinned deployment's whole env through the same function, so a pin can only name a configuration this node boots with.

| Variable | Meaning |
|---|---|
| `EIDOLA_ENGINE_MODEL_ID` | The one model id served. In a pinned deployment it is the weights hash itself (the gateway's build refuses any other value): a model is identified by its weights, and the gateway sends every request under the hash its client's reference resolved to. |
| `EIDOLA_ENGINE_WEIGHTS_DIR` | Weights and chat artifacts. |
| `EIDOLA_ENGINE_WEIGHTS_SHA256` | The expected weights hash (64 hex digits). |
| `EIDOLA_ENGINE_WEIGHTS_STORAGE` | `verified-readonly` (production: read-only, kernel-verified mount; checked) or `dev-writable` (reported in info and health). |
| `GATEWAY_TOKEN` / `GATEWAY_TOKEN_HASH` | The gateway's bearer (secret) and its Argon2id hash (measured; make one with `cargo run -p hash-secret`; parameters outside that tool's profile are refused before anything is hashed). |
| `EIDOLA_ENGINE_EXECUTOR` | `cpu` (or `cuda` in a `cuda` build). |
| `EIDOLA_ENGINE_BIND_ADDR` | `host:port`. |
| `EIDOLA_ENGINE_KV_BLOCK_SIZE` | Positions per KV block, every group. With the prefix cache on it must divide the declared-prefix quantum (`engine_protocol::CACHED_PREFIX_QUANTUM`, 256; `quantum_covers_block_size`), so every count a client declares is a block boundary the cache can resume at; refused by the grammar, so a pin never names one the node refuses. |
| `EIDOLA_ENGINE_KV_BLOCKS` | `cpu` only: blocks per group, including the null block. |
| `EIDOLA_ENGINE_KV_DEVICE_BYTES` | `cuda` only: device memory for the KV pools, in bytes; per-group block counts are derived from it (*The CUDA executor*). Less than the device's memory. |
| `EIDOLA_ENGINE_KERNELS_DIR` | `cuda` only: the kernel build output; every image is checked against the compiled-in manifest. In the release image, `/opt/eidola/kernels` (*The image*). |
| `EIDOLA_ENGINE_KV_HOST_BYTES` | Host memory for the prefix cache's host tier, in bytes (page-locked; *The host tier*); 0 for none, and must be 0 when `EIDOLA_ENGINE_PREFIX_CACHE` is `false`; at most 2 TiB (the largest VM). Both executors. |
| `EIDOLA_ENGINE_CUDA_GRAPHS` | `cuda` only: `on` (pure-decode steps replay graphs captured at boot) or `off` (every step eager); nothing else parses. Keep `off` until the decode graphs' GPU validation has passed. |
| `EIDOLA_ENGINE_GPU_CC` | `cuda` only: `required` (the GPUs must be in production confidential-computing mode and accepting work before a device opens; every pinned deployment) or `not-required` (unchecked, with a warning; development only, never pinned); nothing else parses. |
| `EIDOLA_ENGINE_MAX_MODEL_LEN` | Longest sequence; ≤ `max_position_embeddings`. |
| `EIDOLA_ENGINE_MAX_SEQS`, `EIDOLA_ENGINE_MAX_BATCHED_TOKENS`, `EIDOLA_ENGINE_MAX_PREFILL_CHUNK` | Scheduler step limits; `MAX_BATCHED_TOKENS` ≥ `MAX_SEQS × (1 + DRAFT_TOKENS)`. |
| `EIDOLA_ENGINE_DRAFT_TOKENS` | Speculative width `k` (0 disables); ≤ the model's MTP layers; ≤ 3 with `cuda` (the most any implemented architecture ships, MiMo-V2.6-Flash's three; the gateway's build holds a pinned deployment to its own architecture's `Shape::mtp_layers`, and the executor's preflight also refuses a checkpoint declaring fewer). Pinned deployments set 3. |
| `EIDOLA_ENGINE_MAX_REQUESTS` | Admission bound (each slot may hold a request body of up to `eidola_common::engine_protocol::MAX_REQUEST_BODY_BYTES`; the host memory a value commits the node to, read and admission pools together, is `eidola_common::engine_deployment::host_memory_bytes`, about 616 MiB a slot, which a pinned deployment's VM must hold). |
| `EIDOLA_ENGINE_PREFIX_CACHE` | `true` / `false`. |
| `EIDOLA_ENGINE_CACHE_IDLE_TTL_SECS`, `EIDOLA_ENGINE_CACHE_MAX_AGE_SECS` | Prefix-cache retention bounds (idle ≤ max age). With `EIDOLA_ENGINE_PREFIX_CACHE`, the one source of the retention a gateway publishes for the model: its pin records the deployment config's values and its build holds them equal. |

**The node's environment is exactly the measured allow-list** (`eidola_common::engine_deployment::env::MEASURED`, the names `parse_measured` reads) plus the secret `GATEWAY_TOKEN`: the gateway's build refuses a pinned deployment whose env sets anything else, so no variable a dependency happens to read (`TOKIO_WORKER_THREADS`, `RUST_MIN_STACK`, `MALLOC_*`, `LD_*`, the CUDA driver's `CUDA_*`) reaches a production node through its measured config. The node also reads none itself: the HTTP runtime's worker count is set explicitly (one per available vCPU), so tokio never consults `TOKIO_WORKER_THREADS`, and no engine crate reads an environment variable outside its tests. Every allocation-driving size is capped by the grammar (`engine_deployment::caps`: `MAX_MODEL_LEN` ≤ 2^20, `KV_BLOCK_SIZE` ≤ 1,024, `KV_BLOCKS` ≤ `i32::MAX`, `KV_DEVICE_BYTES` < the supported GPU's 287,428,640,768 bytes, `MAX_SEQS` ≤ 1,024, `MAX_BATCHED_TOKENS` and `MAX_PREFILL_CHUNK` ≤ 65,536, `DRAFT_TOKENS` ≤ 8, and ≤ 3 with `cuda`, `MAX_REQUESTS` ≤ 4,096), refused before loading. `KERNELS_DIR` must be absolute and clean (no empty, `.` or `..` component, not `/`), and `CUDA_GRAPHS` exactly `on` or `off`. A pinned deployment must run `cuda`; `cpu` is the reference and development executor. Its `KERNELS_DIR` must lie outside `/tinfoil` (the kernels ship in the measured image, never in an attached mount), and its `KV_DEVICE_BYTES` must hold at least `engine_deployment::cuda_kv_min_bytes`: the minimum `cuda::derive_kv_blocks` accepts (one `MAX_MODEL_LEN` sequence in the global pool, every seat's sliding windows, a step's positions, with drafting the drafter pool of the same block count, its blocks' boundary taps included, and each pool's pad block), mirrored from the same formula, so a pin never names a budget the node refuses at boot. Changing the derivation means changing both. It must also leave room on the one GPU: the device fit: `KV_DEVICE_BYTES` + the weights + `engine_deployment::cuda_device_reserve_bytes` must fit `SUPPORTED_GPU_MEMORY_BYTES`, the 287,428,640,768 bytes the driver reports for the one supported GPU (`SUPPORTED_GPU`, the NVIDIA B300 SXM6 AC), as `/v1/engine/info` showed on it. The weights are bounded from above by the pack's data size (`artifact_data_bytes`: the modelwrap reference's `hashOffset`, the byte length of the uncompressed EROFS image that holds every file of the pack, per modelwrap's `SPEC.md`), since the executor copies tensors as stored and only re-lays out scale grids and widens small vectors. The reserve bounds the executor's own allocations from above: 4 GiB fixed (CUDA context, kernel modules, decode-graph captures, the weights' layout slack), 1.25 MiB per `MAX_BATCHED_TOKENS` (the step's scratch, an f32 logits row per token among it: about 1.03 MB at Flash's shapes), a 1.5 GiB expert-row floor, per `MAX_SEQS` 1.25 MiB for each of the sampler's distribution rows (an f64 over the vocabulary: one without drafting, `2k + 2` with `k` drafts), the device block tables (a third group's with drafting, as in the host mirror `host_memory_bytes` counts: both take the count from `engine_deployment::kv_groups`, and `cuda::derive_kv_blocks` refuses to boot an executor reporting another), the RoPE tables, and split attention's partial rows (`engine_deployment::split_partial_rows`: `min(MAX_SEQS × (1 + k), MAX_BATCHED_TOKENS) × ⌈MAX_MODEL_LEN / 1,024⌉` rows of 16,640 bytes, the executor's own count, which `cuda::tests` holds equal); with drafting also per `MAX_SEQS` the drafter's slot state and the step's level rows (`engine_deployment::drafter_seat_rows`, 16 KiB each), 32 KiB of step tables, four global page lists and the global work items of every 1,024 positions (`cuda_device_reserve_bytes`' docs give the derivation from the executor's allocations). Because the reserve is never zero, the rule is stricter than the node's own boot refusal of a budget not less than its device's memory. Changing the executor's allocations means revisiting that reserve. `EIDOLA_ENGINE_MAX_BATCHED_TOKENS` must be at least `EIDOLA_ENGINE_MAX_SEQS × (1 + EIDOLA_ENGINE_DRAFT_TOKENS)` (`engine_deployment::decode_step_tokens`: a decode row costs `1 + k` query slots, and the scheduler leaves a row a step cannot afford out of that step, so a smaller step would stall the newest seated sequences while older ones decode), refused by the grammar before any weight is loaded. Logging is fixed at `info` in the binary (`main.rs`), and `RUST_LOG` is not read: everything that changes the node's behaviour must be measured, and a filter delivered any other way (a secret, say) could turn on a dependency's debug logging, which the content-free discipline below does not cover. `GATEWAY_TOKEN` must have the shape the gateway holds its own token to (`eidola_common::engine_deployment::is_gateway_token`: 16 to 1024 visible ASCII characters); boot refuses any other token before verifying it, and the gateway's build refuses any secret besides it. **The model-shape numbers in these bounds are the architecture's** (`eidola_common::architecture::Shape`, read through `Architecture::shape`; `deployment.json` names the architecture): `cuda_kv_min_bytes`, `cuda_device_reserve_bytes` and `check_resources` take the shape, so MiMo-V2.6-Flash's KV bytes per position, sliding window, drafter bytes and executor scratch live behind `Architecture::MimoV26Flash` and nowhere else (`cuda::tests::the_shared_minimum_is_the_derivations` holds the derivation to Flash's shape). `MimoV26Pro` is a stub: its shape is `unimplemented!`, and nothing may deploy it.

## Running it locally

`just run engine-server` builds the synthetic dev model into `target/engine-dev-model` (`examples/dev_model.rs`), prints its weights hash, and serves it on `127.0.0.1:8090` with gateway token `dev-gateway-token`:

```sh
W=$(curl -s -H 'Authorization: Bearer dev-gateway-token' 127.0.0.1:8090/v1/engine/info | jq -r .weights_sha256)
curl -N 127.0.0.1:8090/v1/chat/completions -H 'Authorization: Bearer dev-gateway-token' \
  -H "X-Eidola-Weights-Sha256: $W" -H 'content-type: application/json' \
  -d '{"model":"mimo-dev","messages":[{"role":"user","content":"hi"}],"max_completion_tokens":16,"stream":true,"stream_options":{"include_usage":true}}'
```

**The dev model** is the model crate's committed synthetic fixture with `embed_tokens` and `lm_head` widened from 256 rows to MiMo's padded 152,576 (the fixture's rows first, then deterministic random rows at the same scale), so the real pinned tokenizer and template can drive it; every other tensor is the fixture's. Its weights are random: the output is gibberish, and nothing about it is a quality signal. A built directory records a fingerprint of its inputs (`.fixture-fingerprint`: SHA-256 over a generator version, the generator's own source, and every input file); a directory whose fingerprint does not match is rebuilt beside it and swapped in by rename, so neither the tests nor `just run engine-server` can use a stale model. Rebuilds hold an exclusive lock on a sibling `.lock` file and recheck the fingerprint under it, so concurrent test binaries never move aside a model another has just published.
