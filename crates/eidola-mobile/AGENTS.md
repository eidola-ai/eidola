# eidola-mobile — Agent Development Guide

The mobile app: `eidola-app-core` compiled to `wasm32-unknown-unknown` (without `desktop`), hosted by the native shells under `mobile/` and reaching everything outside the webview through the shell contract (`mobile/shell-contract.md`), with a phone interface on gpui (`src/ui/`). GPL-3.0-only, like the GUI.

| Module | What |
|---|---|
| `protocol` | The contract's wire format: request texts, reply parsing, base64 (`B64Ref` writes straight into the request text, `B64` decodes as the reply is parsed), the `Hello` check, and `ShellError` — every way a call can fail, typed. |
| `client` | `ShellClient<T: Transport>`: one typed call per contract method. A `Transport` moves texts; `call` posts the request before it returns, so dropping the future never withdraws it. An optional trace records every request and reply in order (the self-test's barrier check). |
| `socket` | `ShellDialer`: app-core's `Dialer` over `tcp.*`; `ShellSocket` is the `AsyncRead`/`AsyncWrite`. |
| `files` | `ShellFiles`: app-core's `HostStorage` over `files.*`. |
| `boot` | Hello, the profile, the core (`prepare`), and `bundle.confirm` (`confirm`). |
| `update` | `ShellBundles`: app-core's `BundleStore` over `bundle.*` (writes split at the request bound); `check`, `install`, `report`, `revert` — the self-update on the shell (below). |
| `ui` | The phone interface on gpui (below). Target-independent; natively it compiles and its unit tests run. |
| `dev` (feature `dev`) | A development bundle's seeding: the default agent on a local OpenAI-compatible server, the local dev stack's gateway trusted in place of the pins, and an update check that reads a fixture release. |
| `fixture` (features `dev`, `self-test`) | A release index and manifest taken as verified (`StagedRelease`), for the self-test and development bundles: no manifest recording a bundle can be CI-signed outside a release. |
| `web` (wasm32) | The webview's transport over `js/bridge.js`, and the bundle's entry points (`start`; `startDev` with `dev`; `selfTest` with `self-test`). |
| `selftest` (feature `self-test`) | The headless self-test (below). |

Everything but `web` is target-independent: `tests/bridge.rs` runs it natively against `tests/fake_shell/`, a shell written in Rust that speaks the contract's JSON (files in memory, the pipe over real sockets) and logs every request's arrival and reply.

## The bridge

- **The JS side moves texts and nothing else** (`js/bridge.js`, imported by wasm-bindgen as a snippet file, so the bundle has no inline script): `platform()`, `postIos(text)` (the promise of the reply text), `openAndroid(onReply)` and `postAndroid(text)` (held until the port arrives). Ids, JSON, base64 and every error are Rust's.
- **Replies are matched by id in Rust on Android** (one port carries every reply); iOS answers each message itself. `protocol::reply_id` reads a reply that opens with `{"id":N` (Android's always does) without scanning the rest; anything else is parsed in full.
- **Copies per byte received**: the shell's base64 text becomes a Rust `String` (wasm-bindgen's one `encodeInto`), serde unescapes it only if the shell escaped `/` (both do), base64 decodes into the reply's buffer, and the reader copies out of that. Sending: the bytes are base64-written into the request text, which wasm-bindgen hands to JS once. Measured natively (release, `protocol::tests::measure_the_bridge_codec`, ignored by default), routing and decoding a 1 MiB receive reply takes about 0.5 ms and encoding a 1 MiB send about 0.7 ms; the self-test measures the whole path on each platform, where the shell and the webview's message passing dominate.
- **Nothing panics on shell input.** A reply that is not JSON, has no result, carries bytes that are not base64 or numbers out of range is `ShellError::Malformed`; a code this app does not know is `Code::Other`. `From<ShellError> for io::Error` maps codes to kinds (`connect_failed` is `ConnectionRefused`, `not_found` is `NotFound`, `closed` is `ConnectionAborted`).
- **The contract check** (`Hello::check`): a shell is accepted at contract version 2 or later that lists every method the app calls (`protocol::REQUIRED_METHODS`). Versions only add, so a later shell keeps everything; an older one, or one whose method list falls short of its version, is refused with `ShellError::Contract` before anything else is asked of it.

## The pipe (`socket`)

- **Receiving is pulled**: a `tcp.receive` is in flight only while a reader waits on an empty buffer, and at most one per socket (the contract's rule). The shell reads from the network only while a receive is pending, so a reader that stops stops the network, with at most one receive's bytes (`RECEIVE_MAX`, 256 KiB by default; the self-test compares 64 KiB to 1 MiB) waiting in the socket.
- **Sending is buffered** like a kernel send buffer: writes are accepted into at most `SEND_BUFFER` (256 KiB) and go out one `tcp.send` at a time, so a TLS stream's small records coalesce while a send is in flight; a full buffer makes the writer wait. A failed send fails the next write or flush. `poll_flush` returns once the shell has handed everything to its OS; `poll_shutdown` flushes and sends `tcp.shutdown`; dropping posts `tcp.close`, as does abandoning a connect midway (`CloseOnDrop`).
- IPv6 literals arrive bracketed from URLs; the brackets are stripped (the contract takes none).

## Boot (`boot`) and boot health

`boot::prepare` runs `shell.hello` and its check, `HostProfile::load` over `ShellFiles`, `AppCore::on_host` with the shell's dialer, `AppCore::open_database` (the database opens and its schema is one this build accepts; a first launch creates it) and `AppCore::flush_storage` (what that wrote is synced on the shell); `boot::confirm` is `bundle.confirm`. `boot::boot` is the two in a row, for hosts with nothing to draw (the self-test, the native tests).

**Boot health is judged at the first frame**: a bundle is healthy once it runs, speaks to its shell, has the profile open and durable, **and has drawn**. The interface opens its window at once ("Opening…"), prepares behind it, shows its first screen (the Library, or the first run), and in the frame after the one that drew it confirms (`ui::app` → `AppView`, `window.on_next_frame`). The network is no part of it, so a bundle booted offline still confirms; a bundle that cannot open the profile, or boots but cannot draw, never confirms, and the shell falls back at the next launch (`shell-contract.md` → Provisional activation). A failed prepare is shown (the error's own text under a localized line) and never confirmed.

The profile's name (`boot::PROFILE`) keys app-core's single-writer lock, which on wasm32 is held in process; natively it is a real file lock, so native tests pass `BootOptions::profile` a directory of their own.

## The self-update (`update`)

app-core's updater (`eidola_app_core::updater::mobile`, its AGENTS.md → Mobile self-update) decides everything; this crate carries its store calls to the shell. `check` (`AppCore::prepare_bundle_update`) finds the next release and verifies it as the desktop does, and stages nothing; its error keeps a release that failed a check (`ReleaseCheckError::Rejected`) apart from a feed it could not reach (`Unreachable`). The Updates screen (below) shows the release, its attestations, any claims change and the digest the shell's sheet will show, and only the user's approval calls `install` (`AppCore::install_bundle_update` over `ShellBundles`): the container is downloaded over the shell's pipe, its hash and every file checked against the manifest, and only then `bundle.begin`, `bundle.write` per file, `bundle.seal` (its digest, file count and length must be the manifest's) and `bundle.activate`. The app then reloads, and the new bundle confirms itself (after its first frame, in the interface; `boot::boot` in the self-test); one that never confirms is reverted by the shell at the next launch. `report` reads that state for the interface, `revert` activates the embedded bundle. The contract's result types are app-core's (`protocol` re-exports them), so a reply is read once into the type the updater uses.

## The interface (`src/ui/`)

One window filling the webview and a **stack of screens** over the **Library** (`library.rs`: the conversations as a table of contents — the title in the prose face, when last active, the first words beneath; the pen starts a new one, the gear opens Settings): a **conversation** (`conversation_view.rs` + `composer.rs`), the **first run** (`onboarding.rs`), and **Settings** with its screens (`settings.rs`, `account_view.rs`, `purchase.rs`, `appearance.rs`, `updates_view.rs`, `about.rs`), built from shared pieces (`widgets.rs`: the header and its back chevron, rows, pill buttons, notes, copy rows, a one-line text field on the markdown editor, a read-only prose block). The desktop app's look and voice adapted to a phone, not its windows shrunk.

- **Navigation** (`app.rs`, `nav.rs`): a screen emits `NavEvent::{Back, To(Dest), Home}` and the root view carries it out at its next render (where there is a window to build the next screen's editors in). The first screen waits for the account store's registry read: the **first run** when there is no account and the Eidola backend is still enabled (going on without an account turns it off), else the Library; nothing flashes in between. **Android's back gesture** pops a screen: each pushed screen pushes one session-history entry (`js/nav.js`), the shell turns the gesture into a history step while there is one (`mobile/shell-contract.md` → Screen and keyboard), and its `popstate` reaches the root view through `nav::system_back`; a back the app takes itself pops its entry quietly; after a reload the history is stepped back to the root. iOS has no system back gesture in a webview; the chevron is the way back there.
- **State** (`crates/eidola-gui/STATE.md`, kept lean): `stores::SpacesStore` holds the Library index (`Loadable`, a supersede slot) and the registry of live conversations (one `Conversation` entity per space, shared by every view of it); `conversation::Conversation` is the desktop's `Space` cut to what a phone needs. Tasks are fields: the save in `post_runner` (one at a time), each streaming turn in its own keyed slot, the read in `load_task`, each cascade re-plan keyed by turn. `account_store::AccountStore` holds the configured account (a config snapshot), the balance, prices, subscription and terms (each a `Loadable` with its own supersede slot, read on every visit to a screen that shows it: nothing on the bus invalidates a server read) and whether the Eidola backend is enabled; `account_store::WalletStore` the wallet's lifecycle; `update_store::UpdateStore` the update check and the shell's bundle state. The **bus bridge** (`stores::install_bus_bridge`, the one detached task) dispatches app-core's change bus: `SpaceIndex` re-reads the Library, `Space(id)` re-reads that conversation (and the Library), `Participants` and a lagged bus re-read every live one, `Config` re-applies the theme and locale and re-reads the account's snapshot, `Backends` the registry, `Wallet`/`Account` the wallet. Views call stores; nothing calls `AppCore` from a view. The interface's host (`host.rs`: `Host`, implemented by `ShellHost` over the shell client plus the page's reload and own-origin reads) is how a store reaches the shell: `shell.openExternal`, `bundle.state`, the install and the revert.
- **Overlays, not optimism**: the transcript is the database's (`get_space_tree`); the reader's posts while they save and until a read shows them (`Pending`, every one of them, in order) and each answer while it streams (`Turn`) are drawn over it and leave only when a read containing what they stood for lands (`branch::retain_unread`; a failed read keeps them), so nothing blinks between a commit and the read showing it. Unread posts are nodes of the tree the branch is walked through (`branch::visible`), each under the post it replies to, so a chain of them written faster than the reads stays on the branch, and **the branch's tip is the last of them** (`branch::tip`): the next message replies to the reader's latest post even before any read has shown it. A read that began before the one on screen (`AppCore::change_seq`, sampled before the read) is not applied.
- **Honest states**: a refused save gives the words back to the composer (`ConversationEvent::SubmitFailed`) with the reason in the recovery notice; a failed turn keeps Retry (re-asks that participant) until retried or dismissed, unless nothing could lift it (`errors::is_retryable`: an archived space); a failed first read is a panel with Retry, a failed refresh keeps the posts with a "Couldn't refresh — retry" strip; a refused creation says so and offers no composer (`RowState::Gone`). Saves and reads of a space whose creation is in flight wait for it (`RowState::Deciding`, a `watch` channel).
- **Navigation never cancels domain work** (the desktop's rule: domain entities outlive their views). The registry's references are weak, so a conversation the reader leaves while it is saving, streaming or planning the replies to an answer is held by `SpacesStore::left` until that work settles (`Conversation::is_busy`, observed); the save's plan is followed and the answer lands with its recovery state, and a reader who comes back joins the same entity and its running stream (`SpacesStore::open`).
- **A new conversation is created when it opens** (`SpacesStore::create`: the id minted here, the entity registered at once, the row committed behind it from the default template), and **one left untouched goes with its screen** (`SpacesStore::left` → `AppCore::discard_if_pristine`, which decides inside the delete; a conversation still saving or answering is left alone; one left before its creation landed is disposed of when it does; a reopen during a disposal waits for its verdict, and reads the transcript the moment the disposal keeps the space: an entity's `Origin` says whether it was just created — answered-and-empty, nothing to read — or listed, whose read waits on a deciding row).
- **One branch at a time**: the path from the first post to the newest answer; where a post has several replies, the one shown carries "‹ 1 of 2 ›". Writing continues the branch on screen (`reply_to` = its last post); **Reply** under any post starts a branch from it, and the view follows the branch written into. An unparented row continues from the row before it (app-core's linear tail), as on desktop.
- **Posts render as on desktop**: each body a read-only `MarkdownEditor` in the shared prose style; a streaming answer is the same editor growing, with its reasoning behind a disclosure ("Thinking…" live, "Show/Hide thinking" after; an open disclosure stays open as the turn lands, `ConversationEvent::Landed`). The transcript is a gpui `list` (momentum scrolling on the web backend) in `FollowMode::Tail`: it follows a growing answer for a reader parked at the end and leaves one who scrolled away. A tap on the transcript puts the keyboard away; its controls keep it (`keep_keyboard`).
- **The composer** is the enabled editor in the prose style, a placeholder over it while empty, a 44 pt send button. On a phone the touch that lands in the field asks for the keyboard (`Window::request_virtual_keyboard`, captured before the editor takes the press: focus alone does not summon it); IME needs nothing here (the web backend mirrors the editor's input handler into a hidden text area the system keyboard and its composition type into); sending ends an open composition first. The send button and every control take no focus (`prevent_default`), so the keyboard stays up between messages.
- **The frame** (`app.rs`): the paper fills the viewport; the screens are laid out inside `Window::fully_visible_bounds()` — the safe areas (`env(safe-area-inset-*)`, read by the web backend) intersected with the visual viewport (the keyboard: `insets().ime` stays zero on the web). On Android the shell already pads by the system bars and the keyboard. The viewport reads 0×0 on the first frame, so that frame draws only the paper and asks for another.
- **Theme** (`theme.rs`): the desktop's Circadian palettes and prose (`eidola-theme`), resolved from the profile's config (default `auto`, with the time-of-day tint) against the webview's appearance (`prefers-color-scheme`, live) on the **fixed clock** (`DayPhases::Clock`: a webview cannot read tzdb coordinates). **The faces are the bundle's own**: gpui's web text system shapes only loaded fonts, and naming one that does not resolve panics, so the chrome is Newsreader (`UI_FAMILY`) and code is KaTeX Typewriter (`MONO_FAMILY`, embedded with the editor's math fonts). The browser's fonts are a fallback for emoji **and CJK** (`CanvasFontFallback::EmojiAndCjk`, `web.rs`), so Chinese renders in the system's face. Inline code is KaTeX Typewriter too, which has one weight; gpui shapes a line at one size, so inline code cannot be set lighter or smaller than the words around it without another embedded face. **The heading ramp is gentler than the desktop's** (h1 1.5×, h2 1.3×, h3 1.15×, h4–h6 1.05× the body, at the desktop's uniform Medium weight; `theme::prose_style`), so a heading does not take a phone's screen from the words beneath it; the composer shares it, so a post still reads as what was typed.
- **Localization** (`i18n.rs`, `locales/`, `build.rs`): the desktop's pipeline — `eidola-i18n`'s codegen at build time, typed accessors (`msg::…`), every translation embedded, nothing read at runtime; its runtime rules (the merged-bundle fallback, Chinese by script) are shared too. en is the source; es, fr, zh-Hans, zh-Hant are shipped. The locale is the stored `language` preference, else the webview's `navigator.languages` (iOS reports the device's only for languages the app declares: the shell's `CFBundleLocalizations`). The error copy reuses the desktop's sentences for the same typed errors. **State holds the value, render chooses the words** (`errors::error_copy` at render).
- **Accessibility**: every control carries a probe (`probe.rs`: role + localized label, stable slash-scoped name that never localizes) and is at least 44 pt (`TOUCH`). **gpui's web backend builds no accessibility tree yet**, so these reach no screen reader today — a known upstream gap.
- **Icons** are embedded (`ui::Icons`, `gpui_kit_assets::icon_assets!`): the icon crate's web build would fetch from a CDN, which the shell refuses.

### The first run (`onboarding.rs`)

The desktop's onboarding (`crates/eidola-gui/AGENTS.md` → Onboarding window) as a few pages, one at a time, in the desktop's own words (its FTL messages, copied per locale): what Eidola is ("Pause here" and "Your control"), "Your responsibility", then the choice — a new account, an existing one, or going on without one. The narrative pages and the choice keep their verbs at the foot of the screen. Opened at launch (above), and from Settings ▸ Account with no account (at the choice; it then returns there). The desktop's rules hold, rule for rule:

- **Consent is bound to the documents rendered**: the consent page shows `AccountStore::terms` (fetched when the page opens, one link per document with its version, each opened in the system browser), the agreement records the `(document, sha256)` pairs on screen when the box was ticked (`consent_fingerprint`), and `consented_terms` — the only way to the value creation submits, read by the Create button and by the creation — answers only while it matches the snapshot in hand. The box is inert until documents are on screen.
- **An account created but not saved** (`AppError::AccountNotSaved`) shows its credential as copy rows and the file it was also written to; Create stays off while they are on screen.
- **Linking** sets the credentials and reads the balance, rolling the credentials back on a refusal; "no such account" and "wrong secret" are one answer (`AppError::Server { status: 401 | 403 }`).
- **Going on without an account** turns the Eidola backend off (the first run then stays closed); creating or linking an account turns it back on — a phone has no on-device models, so that is the backend an account is for. (The desktop leaves the backend as it is on creation; its Settings show the switch.)
- The desktop's get-started sentence carries its unlinkability link inline; here the link is a row of its own (a link inside the prose editor would open nothing: the shell refuses other origins), and the page's words are the desktop's with the link's text kept.

### Account, wallet and adding credit (`account_view.rs`, `purchase.rs`)

Checked against `docs/anonymous-credits.md`; the behaviour is the desktop's Settings ▸ Account and Wallet:

- **No account: the screen offers the first run's account steps, never a creation of its own** (creation records terms acceptance, which may only be submitted for documents the reader was shown).
- The credentials as copy rows, the secret masked until revealed; the balance and its pools (each with its expiry, the desktop's buckets), read on every visit; the subscription's standing with its billing door (a portal session minted at the tap); **reset is two steps** (an armed warning, then "Reset account" or "Keep account"), and forgets the credentials only — the wallet's credentials stay. The reveal, the armed reset and a billing door in flight are dropped when the credentials on display change, from wherever.
- **The wallet is read-only**: every credential and where it stands (active, in flight, spent, expired). The desktop's "Recover in-flight" is not offered here; the provisioner and the turn's own recovery are app-core's.
- **Adding credit**: the plans in the desktop's words (`plans.ftl`, copied), narrowed to one-time top-ups only on an answered, affirmative subscription read. A tap mints a checkout link (the row says "Opening checkout…" until it lands) and hands it to `shell.openExternal`: **the system browser, never the app; no in-app payment, no store purchase**. A link is opened only for the account it was minted for (`CheckoutMint::minted_for` against `AppCore::account_fingerprint`, read past the store's snapshot); a mismatch is said, not opened. The first time the app comes back to the foreground after a link went out (the page's `visibilitychange`, `js/page.js` → `nav::came_to_foreground`), the balance and the subscription are read again.

### Appearance (`appearance.rs`)

The desktop's General appearance axes that apply on a phone — day and night (System, Auto, Day, Night), the time-of-day light, a fixed light (shown while the time-of-day light is off), the text size (the desktop's ladder) — each a config write that applies live through the bus. The notes say what differs: Auto and the time-of-day light follow the fixed clock (day 06:00–18:00), because a webview cannot read where the sun is. **The language follows the device**: the desktop has no language picker either.

### Updates (`updates_view.rs`, `update_store.rs`)

The desktop's verified update flow (`UpdatesDisplay`), with the phone's own last step. Opening the screen is the check. Honest states: "Checking…" only while a check runs; up to date (with the latest version); a release that records no phone bundle; a release that failed a check is a **security warning**, never offered; one that could not be fetched is quiet; **a release whose claims changed shows the side-by-side and is offered only after "Treat as update"**. An offered release shows its version, who attested it (and their Rekor entries), when it was released and the digest the shell's sheet will show once it runs. **Nothing is downloaded or staged until "Install update"**: the check holds the `PendingBundleUpdate` in the store, `UpdateStore::approve` is the only thing that takes it and only that button calls it. Approved, it is downloaded, checked, staged and activated, and the app reloads into it; the new bundle confirms itself after its first frame. Below the check, what the shell reports: the running bundle (embedded, or the update and whether it is confirmed or on trial; probes `updates/serving/{embedded,update-confirmed,update-on-trial}`), its digest, an update waiting for the next launch, **the last update that failed its trial** ("Your last update (…) didn't start; you're back on version …", also on the Settings row), and the way back to the bundle built into the app (`revert`, then a reload).

### About and the licences (`about.rs`)

About says what is running in the words of whoever knows it: the app's version (compiled in), and the shell's account of itself (platform, version, contract) and of the bundle it served (version, digest, standing) — **stated as what the shell reports** — with a pointer to the shell's own digest sheet, which is the check. **The licences screen** reads the bundle's own `licences.json` from the document's origin (served by the shell from the bundle; `js/page.js`), generated when the bundle is built (`crates/mobile-licences`, below); each component (name, version, its declared licence, what it is) opens its licence texts.

### Development bundles (feature `dev`)

`mobile/build-bundle.sh --dev-backend URL` builds the app with feature `dev` and its own page (`web/dev/boot.js`, reading `dev-backend.json`): at boot `dev::seed` registers the OpenAI-compatible server at URL as backend `dev` and seats the default template's agent on its model, and stores `appearance = system`, `tint = off` (so the device's light/dark switch shows each palette whatever the hour). `mobile/tools/openai_stub.py` is such a server: it streams fixed reasoning, then a markdown answer (a heading, a list, code, a table) about the last thing the reader wrote — so a whole conversation runs through the real pipe, turn and stream with no account and no engine. Two more options serve the UI tests: `--dev-eidola FILE` trusts the local dev stack's gateway behind its attesting shim mock (`mobile/tools/account_stack.sh`; base URL, hardware CAs, measurement, and the shim's TLS root passed as a boot option) in place of the built-in pins, so the first run's account steps run against a real gateway with the same per-handshake attestation; `--dev-update URL` makes the update check read a fixture release there (`mobile/tools/update_fixtures.py`: a `StagedRelease` taken as verified), after which the real bundle reader, approval, download, byte checks and staging run. The dev bundle also **mirrors every probe into the page** (`probe::mirror` → `js/probes.js`: invisible, labelled, touch-transparent elements named by probe), which is how the UI tests find what they tap. A release bundle carries none of this.

## The bundle build (`mobile/build-bundle.sh`)

- The toolchain is `rust-toolchain.toml`'s (the wasm target is added on demand: the Nix toolchain hashes that file); the wasm-bindgen CLI is exactly the lockfile's `wasm-bindgen` version, installed by `cargo install --locked` into `mobile/.tools/` (git-ignored).
- `--profile mobile` (root `Cargo.toml`): the release profile's determinism (fat LTO, one codegen unit, no incremental state) without `strip`, which would drop the `target_features` section wasm-bindgen reads; wasm-bindgen removes the name and producers sections instead.
- **turso needs an 8 MiB stack** (`-zstack-size`; the default 1 MiB overflows on the first insert as `memory access out of bounds`).
- Paths are remapped (the checkout, `CARGO_HOME`, the standard library's sources to `/rustc/<commit>`, and the target directory, last so it wins inside the checkout: code a build script generates into `OUT_DIR` carries that path into panic locations — html5ever's, through gpui-component) so no machine path reaches the wasm. These flags go through `--config` and are joined to `.cargo/config.toml`'s `getrandom_backend` cfg; a `RUSTFLAGS` variable would replace them all, so the script refuses to run with one set.
- The output is `index.html`, `app.css`, `boot.js`, wasm-bindgen's `eidola_mobile.js`, `eidola_mobile_bg.wasm`, the snippets under `snippets/eidola-mobile-<hash>/js/` (the hash is of the package name and version, not a path), and `licences.json` (not in the self-test bundle). The script prints the sizes and the bundle digest.
- **`licences.json`** is written by `crates/mobile-licences` (a binary with one dependency, which the release image's build runs too: `oci/eidola-mobile-bundle/Containerfile`) from the lockfile, offline: every crate `cargo tree` lists for `eidola-mobile` on wasm32 with the bundle's features (normal edges, procedural macros left out), each with its declared licence and the licence files its package ships (or, shipping none, the SPDX texts of what it declares, from `LICENSES/`; this repository's own crates take theirs from there), then the embedded assets — the Newsreader faces (OFL-1.1), the Lucide icons (ISC) — and the Kotlin standard library the Android shell carries (Apache-2.0). Sorted, every distinct text once, no paths: a function of the lockfile and the sources it names, so two clean builds give the same bytes.
- `mobile/bundle-repro.sh` builds twice in fresh target directories and requires identical files.
- `wasm-bindgen`'s `JsValue::from(u64)` is a BigInt, which `JSON.stringify` refuses: nothing crosses as a `u64` (the bridge passes texts).

## The release bundle (`mobile/build-bundle-release.sh`)

The bundle a release records (`eidola-mobile-bundle`, manifest schema 6), publishes and embeds in the release APK is built in the pinned StageX toolchain, like every other release artifact Rust builds: `oci/eidola-mobile-bundle/Containerfile`, the bake target `mobile-bundle`, every build stage on linux/amd64, exported as the bundle's files.

- StageX's Rust ships a standard library for `x86_64-unknown-linux-musl` alone, but its LLVM targets WebAssembly and its lld includes `wasm-ld`. The image builds the wasm32 standard library from the `rust-src` StageX ships (`-Zbuild-std`, the one unstable step, as in the arm64 CLI's image; rlibs carry bitcode so the fat LTO reaches into std) into the sysroot, then builds the app on stable with the same `mobile` profile, stack size and `.cargo/config.toml` cfg as `build-bundle.sh`. Paths are remapped to the same names (`/eidola`, `/cargo`, `/rustc/<commit>`).
- Its `licences.json` is written by the same generator as the development build's (`cargo run --frozen -p mobile-licences`, offline, reading `LICENSES/` and `mobile/android/tools.sh`, which the image copies in), so the file is the same in both.
- The wasm-bindgen CLI is built from its published crate, pinned by SHA-256 (the index's checksum), with the lockfile it carries, without default features (they add TLS to the test runner's downloads), and refused unless its version is the lockfile's `wasm-bindgen`.
- **It is not the bundle `build-bundle.sh` makes, and cannot be.** Measured: the same tree gives different code. rustup's 1.97.1 is built against Rust's LLVM fork at 22.1.6, StageX's against LLVM 22.1.8; the dist standard library for wasm32 is built by Rust's bootstrap, the release one by cargo from `rust-src`; and cargo folds the compiler's version string into every crate's hash (`rustc 1.97.1 (8bab26f4f 2026-07-14)` against StageX's bare `1.97.1`), which reaches the wasm through the symbol names wasm-bindgen exports, so even `eidola_mobile.js` differs. The function count differs too (about 0.6% fewer in the release build). Matching them would mean building the development bundle in the container, which is what `build-bundle-release.sh` is; the host build stays the fast loop (about three minutes cold on an Apple-silicon Mac, against six to nine for the container's stages emulated there).
- **How far its host independence is checked.** On every change, `.github/workflows/mobile-bundle-release.yml` builds it from scratch in two different x86-64 environments (Ubuntu 24.04 with the pinned BuildKit, Ubuntu 22.04 with the Docker engine's) and requires identical files: same architecture, different kernel, engine, runtime, filesystem and BuildKit. Weekly, `.github/workflows/mobile-bundle-cross-arch.yml` compares a native x86-64 build with one emulated on arm64 (about two and a half hours under QEMU), which is the check a dependence on the host's CPU would fail. Measured by hand: an arm64 Mac running the stages under Rosetta gave the same bytes as a native x86-64 runner for one merge commit (`ddf7b546…` on both), and two builds on one Mac (the second with `--no-cache`, a third on four CPUs) gave the same files. No digest is committed: the release manifest records it. Code the release bundle does not reach is dropped by LTO and moves nothing.
- `scripts/artifact-manifest.sh build-mobile` runs it in CI's artifact chain against the stamped trust root, then builds the APK over it; `record-mobile` composes the row from the files (`mobile/tools/bundle_container.py`) and checks its digest against the one the shells show (`mobile/tools/bundle_digest.py`).

## The self-test (`selftest`, `mobile/self-test.sh ios|android`)

Built only into the self-test bundle (`build-bundle.sh --self-test`, its own page `web/self-test/`), never into a release bundle. The harness runs two `tinfoil-shim-mock`s on this machine (one attesting the measurement the app is told to trust, one another; the emulator reaches them at `10.0.2.2`, in their certificates through `EXTRA_TLS_NAMES`) in front of a static upstream serving `GET /v1/terms`, plus `mobile/tools/echo_server.py`, writes `selftest.json` into the bundle, embeds it in a debug shell, launches it, kills it and launches it again. It uses its own simulator and AVD, both named `eidola-bridge`.

- **First launch**: boot and confirm; set the profile's trust (base URL, ARK, ASK, measurement); under the client's trace, commit a space and at once send a request — the barrier held if every file call posted before the request's `tcp.connect` was answered first, a sync of the write-ahead log among them (the debug shell's `debug.syncLog` confirms the flush); that request is attested over the pipe, and the same request to the other shim is refused as an untrusted measurement; the bundle store (stage, seal, compare the shell's digest with the contract's definition, remove); the bridge's round trip, the pipe's echo throughput at three receive sizes, the file API's.
- **Second launch**: the space is there, and the trust settings with it (the request is attested again with nothing configured); the webview's own storage is empty.
- **The self-update**, across those launches and two more. The harness serves, through the trusted shim, the captured v0.0.8 release (genuinely signed) and two bundle containers written by `mobile/tools/bundle_container.py`: the self-test bundle plus a marker file, and a page with no app. The bundle fetches its fixtures (`update_url`) at run time, because the releases contain it. Phase 1 verifies v0.0.8 with `updater::mobile::prepare` over the shell's pipe (the desktop's verification, for real, against the throwaway attestant pin; its manifest's schema 1 is then refused by the accepted-schema allow-list, which only the bundle reader after verification applies), then approves the update, taken as verified evidence (no manifest recording a bundle can be CI-signed outside a release): downloaded, checked, staged, sealed, activated. Phase 2 (the relaunch) boots the update on trial and confirms it, its digest the release's, and approves the broken bundle; the harness opens the shell's native sheet (Android: the launcher shortcut's intent) and finds the update's digest in it. The next launch is the broken bundle's trial, which never confirms; at the one after, phase 3 finds the shell fell back to the confirmed update with the failure recorded, and reverts to the embedded bundle.

**The verdict follows the measurements**: a report's checks and measurements go in only through `selftest::verdict::Report`, where a measurement always brings the check of whether what it measured was correct (an echo that timed out, failed to connect or came back with a wrong byte; a file that read back wrong), so a failed transfer fails the self-test whatever its numbers; the numbers themselves are informational. Each launch writes `selftest-<n>.json` (synced) to the file directory, which the harness reads from outside the app, and logs to the console. Reports, the console, the shims' logs and screenshots land in `mobile/build/self-test/<platform>/`.

## Tests

**The UI tests** (local gates, like the shells' own; they need docker, for the database): `just mobile-ios-ui-test` (`mobile/ios/test-ui.sh`, XCUITest in its own simulators `eidola-phone` and `eidola-phone-zh`) and `just mobile-android-ui-test` (`mobile/android/test-ui.sh` + `ui_test.py`, `adb shell input` and `uiautomator dump` on the AVD `eidola-shell`). Each brings up the account side of the dev stack (`mobile/tools/account_stack.sh`: the real gateway over the compose stack's PostgreSQL, behind a shim mock, with `billing_edge_stub.py` at its edge standing in for the payment processor — the gateway has no Stripe key — so prices, checkout links and the subscription are the stub's, and a balance read after a stub "purchase" carries it as a pool), serves a fixture update (`update_fixtures.py`: a bundle that confirms, then one that never does), builds a development bundle with all three, and drives with real taps and typing: **the first run on a fresh install** (the introduction, the consent page with the gateway's documents, Create refused until agreed, the new account's credentials, the plans, a checkout handed to the system browser and the balance read again on coming back, the account with its pool, the two-step reset armed and kept); **a whole conversation** (a new conversation with the keyboard up, a streamed answer with its reasoning open, the markdown answer, a reply branch and its switch, leaving mid-answer and coming back to it still streaming, a long conversation scrolled, the Library, an untouched conversation not kept, a cold relaunch, the night palette); **settings applied live** (the night palette from Appearance, checked by the screen's luminance, the text size; the wallet, About, the licences); **the update** (offered, claims accepted, nothing staged before the approval, approved, restarted into and confirmed; a broken one approved, killed on its trial and fallen back from, with the message; the revert to the embedded bundle); Android also uses the system back gesture between screens; iOS also composes Chinese on the Pinyin keyboard and walks the first run and the settings screens in zh-Hans. Screenshots and screen recordings land in `build/ui/` (gitignored).

`tests/ui_lifecycle.rs` drives the interface's stores and entities under gpui's test app over a real core answering from a mock model: leaving while a post saves still gets it answered, coming back mid-answer joins the same entity and its running turn, and a conversation reopened while its disposal is deciding is read once the disposal keeps it. `tests/ui_update.rs` drives the Updates screen's store over a host that counts what reaches the shell: nothing is installed by a check, a release whose claims changed is not installed until the reader accepts the change, an approval installs once and restarts the app, and a release that failed a check (or a feed that could not be reached) offers nothing.

`cargo test -p eidola-mobile` (build it with `-p eidola-gui` on macOS, as for the editor: that crate turns on gpui's runtime shaders): the wire format's unit tests (every malformed reply typed; escaped slashes; the contract check), and `tests/bridge.rs` — bytes intact both ways through many receives, one receive in flight; a reader that stops reading stops the pipe; close on drop and a typed refused connect; files round trip and an over-large write split; a shell answering nonsense fails typed; boot confirms only after the database's log is synced, an older shell is refused after `shell.hello` alone, a corrupt profile never confirms; a commit survives a relaunch; a request reaches the shell only after the commit before it is synced (file replies slowed to 500 ms); attestation over the pipe against an in-process shim, and refusal of another measurement. `tests/update.rs`: an approved update staged through `ShellBundles` in call order (a wasm over the request bound split in two writes), nothing asked of the shell before approval, the relaunch serving it on trial with the shell's digest the release's, and its boot confirming it; a bundle that never confirms reported on trial and reverted at the next launch; the user's revert; a tampered file never reaching the shell. `fake_shell` keeps the contract's bundle store: staging, sealing with the digest of the bytes stored, provisional activation, and a document load on every relaunch. `tests/selftest.rs` (the crate's self-reference turns `self-test` on for its tests) runs the self-test's transfers (`selftest::transfers`) against the fake shell: correct ones pass, and a corrupted echo, a failed connect or a file that reads back wrong each fail the verdict. Native tests must not drop a core inside a tokio context (its runtime would be dropped inside another), hence `park_on` for boots.
