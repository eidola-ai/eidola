# eidola-mobile — Agent Development Guide

The mobile app: `eidola-app-core` compiled to `wasm32-unknown-unknown` (without `desktop`), hosted by the native shells under `mobile/` and reaching everything outside the webview through the shell contract (`mobile/shell-contract.md`), with a phone interface on gpui (`src/ui/`). GPL-3.0-only, like the GUI.

| Module | What |
|---|---|
| `protocol` | The contract's wire format: request texts, reply parsing, base64 (`B64Ref` writes straight into the request text, `B64` decodes as the reply is parsed), the `Hello` check, and `ShellError` — every way a call can fail, typed. |
| `client` | `ShellClient<T: Transport>`: one typed call per contract method. A `Transport` moves texts; `call` posts the request before it returns, so dropping the future never withdraws it. An optional trace records every request and reply in order (the self-test's barrier check). |
| `socket` | `ShellDialer`: app-core's `Dialer` over `tcp.*`; `ShellSocket` is the `AsyncRead`/`AsyncWrite`. |
| `files` | `ShellFiles`: app-core's `HostStorage` over `files.*`. |
| `boot` | Hello, the profile, the core (`prepare`), and `bundle.confirm` (`confirm`). |
| `update` | `ShellBundles`: app-core's `BundleStore` over `bundle.*` (writes split at the request bound); `check`, `install`, `report`, `revert` — the self-update on the shell (below). |
| `ui` | The phone interface on gpui (below). Target-independent; natively it compiles and its unit tests run. |
| `dev` (feature `dev`) | A development bundle's seeding: the default agent on a local OpenAI-compatible server. |
| `web` (wasm32) | The webview's transport over `js/bridge.js`, and the bundle's entry points (`start`; `startDev` with `dev`; `selfTest` with `self-test`). |
| `selftest` (feature `self-test`) | The headless self-test (below). |

Everything but `web` is target-independent: `tests/bridge.rs` runs it natively against `tests/fake_shell/`, a shell written in Rust that speaks the contract's JSON (files in memory, the pipe over real sockets) and logs every request's arrival and reply.

## The bridge

- **The JS side moves texts and nothing else** (`js/bridge.js`, imported by wasm-bindgen as a snippet file, so the bundle has no inline script): `platform()`, `postIos(text)` (the promise of the reply text), `openAndroid(onReply)` and `postAndroid(text)` (held until the port arrives). Ids, JSON, base64 and every error are Rust's.
- **Replies are matched by id in Rust on Android** (one port carries every reply); iOS answers each message itself. `protocol::reply_id` reads a reply that opens with `{"id":N` (Android's always does) without scanning the rest; anything else is parsed in full.
- **Copies per byte received**: the shell's base64 text becomes a Rust `String` (wasm-bindgen's one `encodeInto`), serde unescapes it only if the shell escaped `/` (both do), base64 decodes into the reply's buffer, and the reader copies out of that. Sending: the bytes are base64-written into the request text, which wasm-bindgen hands to JS once. Measured natively (release, `protocol::tests::measure_the_bridge_codec`, ignored by default), routing and decoding a 1 MiB receive reply takes about 0.5 ms and encoding a 1 MiB send about 0.7 ms; the self-test measures the whole path on each platform, where the shell and the webview's message passing dominate.
- **Nothing panics on shell input.** A reply that is not JSON, has no result, carries bytes that are not base64 or numbers out of range is `ShellError::Malformed`; a code this app does not know is `Code::Other`. `From<ShellError> for io::Error` maps codes to kinds (`connect_failed` is `ConnectionRefused`, `not_found` is `NotFound`, `closed` is `ConnectionAborted`).
- **The contract check** (`Hello::check`): a shell is accepted at contract version 2 or later that lists every method the app calls (`protocol::REQUIRED_METHODS`). Versions only add, so a later shell keeps everything; an older one, or one whose method list falls short of its version, is refused with `ShellError::Contract` before anything else is asked of it.

## The pipe (`socket`)

- **Receiving is pulled**: a `tcp.receive` is in flight only while a reader waits on an empty buffer, and at most one per socket (the contract's rule). The shell reads from the network only while a receive is pending, so a reader that stops stops the network, with at most one receive's bytes (`RECEIVE_MAX`, 256 KiB by default; the self-test compares 64 KiB to 1 MiB) waiting in the socket.
- **Sending is buffered** like a kernel send buffer: writes are accepted into at most `SEND_BUFFER` (256 KiB) and go out one `tcp.send` at a time, so a TLS stream's small records coalesce while a send is in flight; a full buffer makes the writer wait. A failed send fails the next write or flush. `poll_flush` returns once the shell has handed everything to its OS; `poll_shutdown` flushes and sends `tcp.shutdown`; dropping posts `tcp.close`, as does abandoning a connect midway (`CloseOnDrop`).
- IPv6 literals arrive bracketed from URLs; the brackets are stripped (the contract takes none).

## Boot (`boot`) and boot health

`boot::prepare` runs `shell.hello` and its check, `HostProfile::load` over `ShellFiles`, `AppCore::on_host` with the shell's dialer, `AppCore::open_database` (the database opens and its schema is one this build accepts; a first launch creates it) and `AppCore::flush_storage` (what that wrote is synced on the shell); `boot::confirm` is `bundle.confirm`. `boot::boot` is the two in a row, for hosts with nothing to draw (the self-test, the native tests).

**Boot health is judged at the first frame**: a bundle is healthy once it runs, speaks to its shell, has the profile open and durable, **and has drawn**. The interface opens its window at once ("Opening…"), prepares behind it, shows the Library, and in the frame after the one that drew the Library confirms (`ui::app` → `AppView`, `window.on_next_frame`). The network is no part of it, so a bundle booted offline still confirms; a bundle that cannot open the profile, or boots but cannot draw, never confirms, and the shell falls back at the next launch (`shell-contract.md` → Provisional activation). A failed prepare is shown (the error's own text under a localized line) and never confirmed.

The profile's name (`boot::PROFILE`) keys app-core's single-writer lock, which on wasm32 is held in process; natively it is a real file lock, so native tests pass `BootOptions::profile` a directory of their own.

## The self-update (`update`)

app-core's updater (`eidola_app_core::updater::mobile`, its AGENTS.md → Mobile self-update) decides everything; this crate carries its store calls to the shell. `check` (`AppCore::prepare_bundle_update`) finds the next release and verifies it as the desktop does, and stages nothing. No screen offers an update yet; the one that does shows the release, its attestations, any claims change and the digest the shell's sheet will show, and only the user's approval calls `install` (`AppCore::install_bundle_update` over `ShellBundles`): the container is downloaded over the shell's pipe, its hash and every file checked against the manifest, and only then `bundle.begin`, `bundle.write` per file, `bundle.seal` (its digest, file count and length must be the manifest's) and `bundle.activate`. The app then reloads, and the new bundle confirms itself (after its first frame, in the interface; `boot::boot` in the self-test); one that never confirms is reverted by the shell at the next launch. `report` reads that state for the interface, `revert` activates the embedded bundle. The contract's result types are app-core's (`protocol` re-exports them), so a reply is read once into the type the updater uses.

## The interface (`src/ui/`)

One window filling the webview, two screens: the **Library** (`library.rs`: the conversations as a table of contents — the title in the prose face, when last active, the first words beneath; the pen starts a new one) and a **conversation** (`conversation_view.rs` + `composer.rs`). The desktop app's look and voice adapted to a phone, not its windows shrunk.

- **State** (`crates/eidola-gui/STATE.md`, kept lean): `stores::SpacesStore` holds the Library index (`Loadable`, a supersede slot) and the registry of live conversations (one `Conversation` entity per space, shared by every view of it); `conversation::Conversation` is the desktop's `Space` cut to what a phone needs. Tasks are fields: the save in `post_runner` (one at a time), each streaming turn in its own keyed slot, the read in `load_task`, each cascade re-plan keyed by turn. The **bus bridge** (`stores::install_bus_bridge`, the one detached task) dispatches app-core's change bus: `SpaceIndex` re-reads the Library, `Space(id)` re-reads that conversation (and the Library), `Participants` and a lagged bus re-read every live one, `Config` re-applies the theme and locale. Views call stores; nothing calls `AppCore` from a view.
- **Overlays, not optimism**: the transcript is the database's (`get_space_tree`); the reader's post while it saves (`Pending`) and each answer while it streams (`Turn`) are drawn over it and leave only when a read containing what they stood for lands, so nothing blinks between a commit and the read showing it. A read that began before the one on screen (`AppCore::change_seq`, sampled before the read) is not applied.
- **Honest states**: a refused save gives the words back to the composer (`ConversationEvent::SubmitFailed`) with the reason in the recovery notice; a failed turn keeps Retry (re-asks that participant) until retried or dismissed, unless nothing could lift it (`errors::is_retryable`: an archived space); a failed first read is a panel with Retry, a failed refresh keeps the posts with a "Couldn't refresh — retry" strip; a refused creation says so and offers no composer (`RowState::Gone`). Saves and reads of a space whose creation is in flight wait for it (`RowState::Deciding`, a `watch` channel).
- **A new conversation is created when it opens** (`SpacesStore::create`: the id minted here, the entity registered at once, the row committed behind it from the default template), and **one left untouched goes with its screen** (`SpacesStore::left` → `AppCore::discard_if_pristine`, which decides inside the delete; a conversation still saving or answering is left alone; one left before its creation landed is disposed of when it does; a reopen during a disposal waits for its verdict).
- **One branch at a time**: the path from the first post to the newest answer; where a post has several replies, the one shown carries "‹ 1 of 2 ›". Writing continues the branch on screen (`reply_to` = its last post); **Reply** under any post starts a branch from it, and the view follows the branch written into. An unparented row continues from the row before it (app-core's linear tail), as on desktop.
- **Posts render as on desktop**: each body a read-only `MarkdownEditor` in the shared prose style; a streaming answer is the same editor growing, with its reasoning behind a disclosure ("Thinking…" live, "Show/Hide thinking" after; an open disclosure stays open as the turn lands, `ConversationEvent::Landed`). The transcript is a gpui `list` (momentum scrolling on the web backend) in `FollowMode::Tail`: it follows a growing answer for a reader parked at the end and leaves one who scrolled away. A tap on the transcript puts the keyboard away; its controls keep it (`keep_keyboard`).
- **The composer** is the enabled editor in the prose style, a placeholder over it while empty, a 44 pt send button. On a phone the touch that lands in the field asks for the keyboard (`Window::request_virtual_keyboard`, captured before the editor takes the press: focus alone does not summon it); IME needs nothing here (the web backend mirrors the editor's input handler into a hidden text area the system keyboard and its composition type into); sending ends an open composition first. The send button and every control take no focus (`prevent_default`), so the keyboard stays up between messages.
- **The frame** (`app.rs`): the paper fills the viewport; the screens are laid out inside `Window::fully_visible_bounds()` — the safe areas (`env(safe-area-inset-*)`, read by the web backend) intersected with the visual viewport (the keyboard: `insets().ime` stays zero on the web). On Android the shell already pads by the system bars and the keyboard. The viewport reads 0×0 on the first frame, so that frame draws only the paper and asks for another.
- **Theme** (`theme.rs`): the desktop's Circadian palettes and prose (`eidola-theme`), resolved from the profile's config (default `auto`, with the time-of-day tint) against the webview's appearance (`prefers-color-scheme`, live) on the **fixed clock** (`DayPhases::Clock`: a webview cannot read tzdb coordinates). **The faces are the bundle's own**: gpui's web text system shapes only loaded fonts, and naming one that does not resolve panics, so the chrome is Newsreader (`UI_FAMILY`) and code is KaTeX Typewriter (`MONO_FAMILY`, embedded with the editor's math fonts). The browser's fonts are a fallback for emoji **and CJK** (`CanvasFontFallback::EmojiAndCjk`, `web.rs`), so Chinese renders in the system's face. Inline code is KaTeX Typewriter too, which has one weight; gpui shapes a line at one size, so inline code cannot be set lighter or smaller than the words around it without another embedded face. **The heading ramp is gentler than the desktop's** (h1 1.5×, h2 1.3×, h3 1.15×, h4–h6 1.05× the body, at the desktop's uniform Medium weight; `theme::prose_style`), so a heading does not take a phone's screen from the words beneath it; the composer shares it, so a post still reads as what was typed.
- **Localization** (`i18n.rs`, `locales/`, `build.rs`): the desktop's pipeline — `eidola-i18n`'s codegen at build time, typed accessors (`msg::…`), every translation embedded, nothing read at runtime; its runtime rules (the merged-bundle fallback, Chinese by script) are shared too. en is the source; es, fr, zh-Hans, zh-Hant are shipped. The locale is the stored `language` preference, else the webview's `navigator.languages` (iOS reports the device's only for languages the app declares: the shell's `CFBundleLocalizations`). The error copy reuses the desktop's sentences for the same typed errors. **State holds the value, render chooses the words** (`errors::error_copy` at render).
- **Accessibility**: every control carries a probe (`probe.rs`: role + localized label, stable slash-scoped name that never localizes) and is at least 44 pt (`TOUCH`). **gpui's web backend builds no accessibility tree yet**, so these reach no screen reader today — a known upstream gap.
- **Icons** are embedded (`ui::Icons`, `gpui_kit_assets::icon_assets!`): the icon crate's web build would fetch from a CDN, which the shell refuses.

### Development bundles (feature `dev`)

`mobile/build-bundle.sh --dev-backend URL` builds the app with feature `dev` and its own page (`web/dev/boot.js`, reading `dev-backend.json`): at boot `dev::seed` registers the OpenAI-compatible server at URL as backend `dev` and seats the default template's agent on its model, and stores `appearance = system`, `tint = off` (so the device's light/dark switch shows each palette whatever the hour). `mobile/tools/openai_stub.py` is such a server: it streams fixed reasoning, then a markdown answer (a heading, a list, code, a table) about the last thing the reader wrote — so a whole conversation runs through the real pipe, turn and stream with no account and no engine. The dev bundle also **mirrors every probe into the page** (`probe::mirror` → `js/probes.js`: invisible, labelled, touch-transparent elements named by probe), which is how the UI tests find what they tap. A release bundle carries none of this.

## The bundle build (`mobile/build-bundle.sh`)

- The toolchain is `rust-toolchain.toml`'s (the wasm target is added on demand: the Nix toolchain hashes that file); the wasm-bindgen CLI is exactly the lockfile's `wasm-bindgen` version, installed by `cargo install --locked` into `mobile/.tools/` (git-ignored).
- `--profile mobile` (root `Cargo.toml`): the release profile's determinism (fat LTO, one codegen unit, no incremental state) without `strip`, which would drop the `target_features` section wasm-bindgen reads; wasm-bindgen removes the name and producers sections instead.
- **turso needs an 8 MiB stack** (`-zstack-size`; the default 1 MiB overflows on the first insert as `memory access out of bounds`).
- Paths are remapped (the checkout, `CARGO_HOME`, the standard library's sources to `/rustc/<commit>`, and the target directory, last so it wins inside the checkout: code a build script generates into `OUT_DIR` carries that path into panic locations — html5ever's, through gpui-component) so no machine path reaches the wasm. These flags go through `--config` and are joined to `.cargo/config.toml`'s `getrandom_backend` cfg; a `RUSTFLAGS` variable would replace them all, so the script refuses to run with one set.
- The output is `index.html`, `app.css`, `boot.js`, wasm-bindgen's `eidola_mobile.js`, `eidola_mobile_bg.wasm` and the snippet `snippets/eidola-mobile-<hash>/js/bridge.js` (the hash is of the package name and version, not a path). The script prints the sizes and the bundle digest.
- `mobile/bundle-repro.sh` builds twice in fresh target directories and requires identical files.
- `wasm-bindgen`'s `JsValue::from(u64)` is a BigInt, which `JSON.stringify` refuses: nothing crosses as a `u64` (the bridge passes texts).

## The self-test (`selftest`, `mobile/self-test.sh ios|android`)

Built only into the self-test bundle (`build-bundle.sh --self-test`, its own page `web/self-test/`), never into a release bundle. The harness runs two `tinfoil-shim-mock`s on this machine (one attesting the measurement the app is told to trust, one another; the emulator reaches them at `10.0.2.2`, in their certificates through `EXTRA_TLS_NAMES`) in front of a static upstream serving `GET /v1/terms`, plus `mobile/tools/echo_server.py`, writes `selftest.json` into the bundle, embeds it in a debug shell, launches it, kills it and launches it again. It uses its own simulator and AVD, both named `eidola-bridge`.

- **First launch**: boot and confirm; set the profile's trust (base URL, ARK, ASK, measurement); under the client's trace, commit a space and at once send a request — the barrier held if every file call posted before the request's `tcp.connect` was answered first, a sync of the write-ahead log among them (the debug shell's `debug.syncLog` confirms the flush); that request is attested over the pipe, and the same request to the other shim is refused as an untrusted measurement; the bundle store (stage, seal, compare the shell's digest with the contract's definition, remove); the bridge's round trip, the pipe's echo throughput at three receive sizes, the file API's.
- **Second launch**: the space is there, and the trust settings with it (the request is attested again with nothing configured); the webview's own storage is empty.
- **The self-update**, across those launches and two more. The harness serves, through the trusted shim, the captured v0.0.8 release (genuinely signed) and two bundle containers written by `mobile/tools/bundle_container.py`: the self-test bundle plus a marker file, and a page with no app. The bundle fetches its fixtures (`update_url`) at run time, because the releases contain it. Phase 1 verifies v0.0.8 with `updater::mobile::prepare` over the shell's pipe (the desktop's verification, for real, against the throwaway attestant pin; its manifest's schema 1 is then refused by the accepted-schema allow-list, which only the bundle reader after verification applies), then approves the update, taken as verified evidence (no manifest recording a bundle can be CI-signed outside a release): downloaded, checked, staged, sealed, activated. Phase 2 (the relaunch) boots the update on trial and confirms it, its digest the release's, and approves the broken bundle; the harness opens the shell's native sheet (Android: the launcher shortcut's intent) and finds the update's digest in it. The next launch is the broken bundle's trial, which never confirms; at the one after, phase 3 finds the shell fell back to the confirmed update with the failure recorded, and reverts to the embedded bundle.

**The verdict follows the measurements**: a report's checks and measurements go in only through `selftest::verdict::Report`, where a measurement always brings the check of whether what it measured was correct (an echo that timed out, failed to connect or came back with a wrong byte; a file that read back wrong), so a failed transfer fails the self-test whatever its numbers; the numbers themselves are informational. Each launch writes `selftest-<n>.json` (synced) to the file directory, which the harness reads from outside the app, and logs to the console. Reports, the console, the shims' logs and screenshots land in `mobile/build/self-test/<platform>/`.

## Tests

**The UI tests** (local gates, like the shells' own): `just mobile-ios-ui-test` (`mobile/ios/test-ui.sh`, XCUITest in its own simulator `eidola-phone`) and `just mobile-android-ui-test` (`mobile/android/test-ui.sh` + `ui_test.py`, `adb shell input` and `uiautomator dump` on the AVD `eidola-shell`). Each builds a development bundle against `openai_stub.py` on this machine and drives a whole conversation with real taps and typing: a new conversation with the keyboard up, a streamed answer with its reasoning open, the markdown answer, a reply branch and its switch, a long conversation scrolled, the Library, an untouched conversation not kept, a cold relaunch, the night palette; iOS also composes Chinese on the Pinyin keyboard. Screenshots and a screen recording land in `build/ui/` (gitignored).

`cargo test -p eidola-mobile` (build it with `-p eidola-gui` on macOS, as for the editor: that crate turns on gpui's runtime shaders): the wire format's unit tests (every malformed reply typed; escaped slashes; the contract check), and `tests/bridge.rs` — bytes intact both ways through many receives, one receive in flight; a reader that stops reading stops the pipe; close on drop and a typed refused connect; files round trip and an over-large write split; a shell answering nonsense fails typed; boot confirms only after the database's log is synced, an older shell is refused after `shell.hello` alone, a corrupt profile never confirms; a commit survives a relaunch; a request reaches the shell only after the commit before it is synced (file replies slowed to 500 ms); attestation over the pipe against an in-process shim, and refusal of another measurement. `tests/update.rs`: an approved update staged through `ShellBundles` in call order (a wasm over the request bound split in two writes), nothing asked of the shell before approval, the relaunch serving it on trial with the shell's digest the release's, and its boot confirming it; a bundle that never confirms reported on trial and reverted at the next launch; the user's revert; a tampered file never reaching the shell. `fake_shell` keeps the contract's bundle store: staging, sealing with the digest of the bytes stored, provisional activation, and a document load on every relaunch. `tests/selftest.rs` (the crate's self-reference turns `self-test` on for its tests) runs the self-test's transfers (`selftest::transfers`) against the fake shell: correct ones pass, and a corrupted echo, a failed connect or a file that reads back wrong each fail the verdict. Native tests must not drop a core inside a tokio context (its runtime would be dropped inside another), hence `park_on` for boots.
