# eidola-server-gateway — Agent Development Guide

An OpenAI-compatible proxy that translates requests to upstream AI providers, with a billing system using anonymous credentials for privacy-preserving usage tracking.

- **Upstreams:** Tinfoil (inference.tinfoil.sh) — OpenAI-compatible; all models run in confidential enclaves (AMD SEV-SNP / Intel TDX / NVIDIA CC) — and, for a model the catalog lists as Eidola-hosted, Eidola's own inference nodes (`src/engine_router`, see Eidola-hosted engines). No shipped row is Eidola-hosted yet.
- **Database:** PostgreSQL 17+ (`schema/schema.sql`).
- **Deployment:** Tinfoil Containers — all services run inside confidential enclaves. The Tinfoil shim terminates TLS and serves self-contained v3 attestation; the server runs plain HTTP behind it.
- **API endpoints:** defined in `openapi.json`, generated from utoipa annotations — see Conventions in the top-level AGENTS.md (`just update-openapi`).
- **Role:** the gateway — accounts, billing, anonymous credentials, routing. Inference itself is an upstream's job (today Tinfoil's; later Eidola's own engine nodes).
- **Names that did not follow the crate:** the image is `ghcr.io/eidola-ai/eidola-server-gateway`, but its bake targets are still `server` / `ci-server` and its `artifact-manifest.json` key is still `eidola-server`. The key is what installed clients compare (`EXPECTED_ARTIFACTS` in `eidola-app-core/src/updates.rs`), and `scripts/artifact-manifest.sh` derives it from the bake target name, so changing either is a manifest artifact-set rotation — accept side one release, emit side the next (`releases/README.md`) — never a rename in place. An OCI digest does not depend on the repository name, so the row checks the same image whichever name it was pushed under; images of releases cut before the rename live at `ghcr.io/eidola-ai/eidola-server` and must stay there.

## Key design decisions

- Axum HTTP server with typed routing, extractors, and `utoipa-axum` OpenAPI integration.
- Plain HTTP internally; TLS terminated by the Tinfoil shim. Its self-contained v3 envelope endorses the TLS SPKI and HPKE key and carries a fresh hardware report plus vendor collateral.
- Tinfoil attestation verified per-connection via the `tinfoil-verifier` crate (see that crate's AGENTS.md).
- Deterministic enclave measurement via `measure-enclave` (see that crate's AGENTS.md) → `releases/trust/server-enclave.json` (the cli build input) + `artifact-manifest.json` (the signed deployment record). One level further down, the gateway is itself a pinning client: `releases/trust/engine-enclaves.json` is its build input naming the Eidola-hosted engine deployments it accepts (see Eidola-hosted engines below).
- Statically linked musl binaries; StageX-based OCI images (reproducible, `FROM scratch`, non-root).
- Request-based — no sessions/caching in the proxy layer.
- Account auth (Basic + Argon2id) via `BasicAuth` extractor; chat completions auth via `TokenAuth`.
- **Tool calling is wire-level pass-through** (`types.rs`): the request accepts `tools` / `tool_choice`, an assistant `tool_calls` with nullable `content`, and `role: "tool"` + `tool_call_id`; the response and SSE chunk relay `message.tool_calls` / `delta.tool_calls` and `finish_reason: "tool_calls"`. The server **never executes a tool** — the loop lives in app-core. Each new field is a raw `serde_json::Value`, deliberately: the proxy re-serializes everything it parses, so a narrower struct would silently drop provider extension fields and the streaming-only `index` framing key the client's accumulator needs (the same defect the `reasoning_content` / `reasoning` fields were added to fix). `content` is `Option` with **no** `skip_serializing_if`, so a deliberate `"content": null` survives to the upstream chat template. The strict `deny_unknown_fields` on the request stays: the server remains the authority on what it accepts; opacity is scoped to the *inside* of tool payloads. `types.rs` composes this strict deserialization with `eidola_common::chat_completion_request_body`, and its `test-support` bridge lets app-core's harness deserialize real captures through the same strict type without creating a production dependency. The model list **does** declare tool calling per model (see Model catalog below), which is what lets a client withhold the field instead of discovering its absence by paying for a round; the strict request type is unchanged by that, so an upstream 4xx pass-through remains the honest error when a request is malformed or a declaration turns out to be wrong.
- Stripe integration via a thin `reqwest` wrapper (no `async-stripe`).
- **One definition of "subscribed."** `stripe::IN_FORCE_SUBSCRIPTION_STATUSES` (`active`, `trialing`, `past_due`) is the whole rule, resolved through `Subscription::is_in_force` by both `GET /v1/account/subscription` and the checkout guard — so a client shown "no subscription" can never be refused for already having one. `incomplete` and everything past it are deliberately out: a first payment that never succeeded entitles nothing. Stripe's list endpoint takes at most one `status`, so the filter lives here rather than in the query.
- **And therefore the list is walked, not sampled.** With the filter client-side, one page is an answer only when it is the whole list — so `StripeClient::in_force_subscription` pages with `starting_after` until Stripe says `has_more: false`, and it is the **only** subscription read the client exposes (`list_subscriptions` is gone; the page fetch is private). A customer with a page of newer `incomplete` checkout attempts ahead of one older `active` subscription otherwise reads as unsubscribed — and since the checkout guard asks this same question, they could then buy a second paid subscription over a live one. Pagination rather than one call per entitling status: it costs **one** round trip for any real customer (page size 100, early exit on the first in-force hit) where the status route costs three every time, including for the customer with no subscriptions at all, and it keeps the in-force rule in one place instead of re-encoding it in query construction. **No inbound field whose absence would be a guess is optional**: `ListResponse.has_more` is required, exactly like `SubscriptionItem.current_period_end` and for the same reason — defaulted to `false`, a response that omits it reads as "the whole list has been seen", so a shape change or a malformed intermediary turns an incomplete walk into a confident "no subscription" and the checkout guard sells a second subscription over a live one. Absence fails the parse instead (`a_page_that_omits_has_more_refuses_rather_than_assuming_the_end`). **Every way the walk can end without seeing the whole list refuses (503) rather than answering** — `MAX_SUBSCRIPTION_PAGES` binding (a thousand non-canceled subscriptions), and a page that reports `has_more` while carrying no rows to page from. Both are *incomplete* walks, not ended ones, and "no subscription" said about an incomplete walk is exactly the claim the walk exists to stop making: checkout declines to sell what it cannot rule out, and the client shows "couldn't check". Terminating the loop is not on its own a licence to guess. Tests: `an_in_force_subscription_behind_a_full_page_is_still_found`, `the_walk_stops_at_the_first_page_that_answers`, `a_walk_that_runs_out_of_pages_refuses_rather_than_saying_no`, `a_page_promising_more_but_carrying_none_refuses_too` (`stripe.rs`, against a local stand-in for Stripe's list endpoint — the pagination protocol is only observable over a real request).
- **The Stripe API version is pinned** (`stripe::STRIPE_API_VERSION` = `2025-03-31.basil`, sent as `Stripe-Version` as a *client default header*, so a request added later cannot forget it). Unpinned, a request is served at the **account's default version** — a dashboard setting, changeable by a human who is not looking at this repository, that silently rewrites what a sealed, attested binary does; everything else about this server's behavior is a function of its measured source. It had already cost us: Basil moved the billing period from the subscription onto its **items**, the response went on deserializing because our field was `Option`, and the app's "current billing period ends …" line quietly never rendered again. So `Subscription` now reads `items.data[].current_period_end` — **required** at the item level, precisely so the next such move is a loud parse failure rather than a silent `None` — and reports the **soonest** boundary (items can bill on mixed intervals; for our single-price subscriptions it is simply that item's period). **Bumping the pin is a review task**: re-read the intervening changelogs against every shape `stripe.rs` parses. Two things the header does *not* cover — webhook payloads are versioned per endpoint in Stripe's dashboard (so `webhook.rs`'s `serde_json::Value` lookups carry the same latent risk, untouched here), and a bump must be applied to the webhook endpoint separately.
- **Subscription state is not stored.** No column, no webhook denormalization: Stripe is the source of truth and is read on demand. `GET /v1/account/subscription` therefore always answers 200 with a three-value `state` — `none`, `inactive`, `active` — because "never transacted" and "lapsed" are different situations for a client, and a 404 conflated them.
- **`none` means "has never transacted", and is decided on money, not on a customer row.** `create_checkout` persists the Stripe customer **before** it validates the price or the reader finishes paying, so a rejected request or an abandoned first checkout leaves a `stripe_customer_id` with nothing under it. Reading that as `inactive` sent the reader to a billing portal holding no card, no invoice and no receipt — the app's "payment methods, invoices and past receipts" copy claiming a history that did not exist. So the `inactive` branch also asks `db::has_stripe_ledger_history`: a `credit_ledger` row with a `stripe_event_id` is exactly "Stripe told us money moved for this account" (internal rows like credential issuance carry none and correctly do not count). Not a fourth state — the third one finally means what it always documented.
- **Minting a billing-portal session is its own endpoint** (`POST /v1/account/portal`), not a field on the subscription standing. It came back three times as one seam: coupling the two Stripe calls with `try_join!` let a failed mint destroy the answer; `join!` fixed the error path and left the **latency**, since both futures are still awaited — so a slow (not failing) mint held the standing, and for that whole time the Account pane read "unknown" and offered recurring plans to a live subscriber whose checkout the guard would refuse. Only removing the call decouples them. Splitting also deletes two lesser wrongs: minting is a Stripe **write**, so every status read was creating a portal session and throwing it away, and the session expires quickly, so the link could never responsibly be held — our own client already discarded it and asked again at the click. The standing read is now one Stripe call (the walk) plus at most one ledger query. `SubscriptionResponse.management_url` is **gone**; clients read `state` for the standing and `POST /v1/account/portal` when the reader is about to open it. That endpoint refuses (404) for an account with no payment relationship, on the same predicate `none` uses, so the app is never offered a door the server then declines — asked **local-first**: `||` short-circuits, so the ledger is consulted before the subscription walk, and Stripe is reached only for the customer the ledger cannot vouch for (an unbilled trial). Ordered the other way, every returning customer paid for a remote round trip that could not change the outcome, and a slow or failing `/subscriptions` withheld their billing portal while the portal itself was healthy (`the_portal_asks_the_ledger_before_it_asks_stripe`). Regression: `the_subscription_read_mints_no_portal_session` — a source scan, because the handler needs a database and what is asserted is the *absence* of a call.
- **Stripe's redirect targets are real site routes**, held as constants in `account.rs` (`PAYMENT_COMPLETE_URL` / `PAYMENT_CANCELED_URL` / `BILLING_PORTAL_RETURN_URL` → `www.eidola.ai/payment-complete/`, `/payment-canceled/`, `/billing/`). The site generator emits **flat routes only**, so a nested path like `/payment/success` is unproducible; renaming a page in `www/pages/` breaks a live redirect and must move with these constants. Checkout's success/cancel URLs are overridable per request but the client never sends them, so the defaults are what ship.
- **Model catalog — what a model *is* versus what we *sell*.** `backend.rs`'s `MODEL_CATALOG` is a hardcoded build input, bound to the image and therefore to the enclave measurement. Each row carries what upstream publishes per model (`context_length`, and a `ModelCapabilities` of `tool_calling` / `reasoning` / input+output `Modality` lists) plus two figures nobody publishes and we declare ourselves: `max_output_tokens`, the largest completion we are prepared to ask for, and `output_budget_class`, naming which public ladder the model draws from. Every capability leaf on the wire is an **object with a `supported` boolean**, never a bare boolean, so a leaf can grow a sibling key — an effort ladder, a per-model weights measurement — without a type change breaking a deployed client. Each row also declares its `hosting` (`tinfoil` or `eidola`), and two leaves exist for what an Eidola-hosted row differs on: `prompt_cache` (`{supported, idle_ttl_secs, max_age_secs}`) and `pinned_weights` (`{supported, sha256, repo, revision}`). A Tinfoil-hosted row publishes both as `{supported: false}` with no siblings; an Eidola-hosted row's values come from its compiled-in engine pin, never from the row itself (see Eidola-hosted engines). **It must not become a boot-time mirror of the upstream list**: clients shape requests from what this enclave publishes (whether an agent is offered tools, most of all), so mirroring at boot would make that an unmeasured input and a changed upstream could silently alter it. Same argument the GUI makes about translations being build inputs. **A capability flag is an input to an offer or to request shaping, never to a verification decision** — that is also why `is_moderated`-style trust claims are refused: trust in this product belongs to the attestation chain, not to a field that says "trust me".
- **The catalog is deliberately smaller than the upstream list, and the gap is written down.** This server registers exactly one inference route, so a model served only by `/v1/embeddings`, `/v1/audio/*`, `/v1/convert/file` or `/v1/realtime` is not something a conversation can be routed to — and the strongest form of "never offer a choice we know to be impossible" is not to list it, so no downstream picker filter is needed. `NOT_SOLD_UPSTREAM_MODELS` records every such id with the upstream route the omission is *about* and the reason. That record is what distinguishes "deliberately not sold" from "we missed it": a scheduled check against the live list can only stay loud if the known differences are declared, and `the_omission_record_is_disjoint_from_the_catalog` / `every_catalog_row_is_a_chat_model` keep both halves honest. **The route is carried as a field rather than only in the prose so it can be checked**: the drift job holds a route-bound omission to it, and upstream moving that model onto the chat route makes the record wrong rather than silent. `upstream_route: None` is the omission that is not about routing at all and must stay rare — `websearch` is published *on* the chat route today and is still a tool rather than a model, so a rule keyed on that endpoint alone would report it daily until someone muted the check. The per-request pricing shape (`ModelPricing::per_request`, `PricingOverride.request`) stays even though no shipped row wears it now — it is contract, tested against a synthetic fixture rather than against whichever model happened to need it.
- **The catalog pinning test derives from the catalog.** `the_catalog_reaches_the_wire_whole` walks `MODEL_CATALOG` itself rather than a second hand-written copy of the same numbers beside it. Two static copies in one file agree by construction and can only catch a stray edit; they cannot catch upstream moving a value out from under a row that was right when transcribed, because both copies are equally stale. What is left here is what a unit test can prove: every declared field reaches the wire unchanged and prices arrive multiplied by the markup and nothing else.
- **The live second copy is a scheduled diff, not a gate.** `backend::catalog_drift` fetches `GET https://inference.tinfoil.sh/v1/models` and diffs every pinned row on every axis the catalog transcribes — id presence, `context_window`, all three prices, `tool_calling`, `reasoning`, and `multimodal` against whether the row offers image input — plus the task surface, which is read from `endpoints` rather than `type` because upstream calls `gpt-oss-safeguard-120b` a `safety` model and `voxtral-small-24b` an `audio` one and both serve `/v1/chat/completions` and are deliberately sold. Three things are loud, and `NOT_SOLD_UPSTREAM_MODELS` is what leaves only three: a sold row whose upstream value moved; a published model nothing accounts for ("we missed it" — an id in neither list, **or** one whose route-bound omission record has stopped describing it, which is the same situation for a reader and takes the same two cures, sell it or write down why not); and a sold id or an omission record upstream no longer publishes (a stale row, or a stale omission). Cached-input price is unread (there is no contract field to disagree with), as are names, descriptions and output modalities (upstream publishes no output-modality list). Every compared field is **required** on the wire type: a capability that stopped being published is a shape change, and one that quietly defaulted to `false` would invent drift nobody caused. **The comparison is offline and unit-tested in the PR gate** against synthetic lists built from `MODEL_CATALOG` itself, one fixture per loud class; only the fetch is `#[ignore]`d, and `.github/workflows/catalog-drift.yml` runs that daily — never in a gate, because upstream moving a value is not something a pull request introduced.
- **Pricing contract:** the server recomputes `eidola-common::prompt_charge` — the identical function of the identical `messages`/`tools` arrays the client computes — as its pre-flight minimum, and clamps charged prompt tokens to it, so the client's hold covers the charge by construction. Tool bytes count (every `tool_calls` entry's and tool schema's compact JSON serialization) at the same safe cost factor.

## Environment variables

- `TINFOIL_API_KEY` (required) — Tinfoil inference API key.
- `DATABASE_URL` (required) — PostgreSQL connection string.
- `DATABASE_PASSWORD` (optional) — in production with an external database, inject as a Tinfoil secret instead of embedding in `DATABASE_URL`.
- `DATABASE_SSL_CERT` (optional) — PEM root CA for PostgreSQL TLS verification; public material, normal env var.
- `CREDENTIAL_MASTER_KEY` (required) — hex-encoded 32-byte AES-256 key encrypting issuer private keys at rest in Postgres. Production: a Tinfoil secret; local dev: the all-zeros key from `.env.example`. Must remain stable across upgrades so encrypted issuer keys stay accessible.
- `BIND_ADDR` (default `127.0.0.1:8443`) — HTTP bind address; Containerfile overrides to `0.0.0.0:8080`.
- `STRIPE_API_KEY` / `STRIPE_WEBHOOK_SECRET` (optional) — billing endpoints / webhook return 503 without them.
- `TINFOIL_BASE_URL` (optional) — override the default `https://inference.tinfoil.sh/v1`.
- `TINFOIL_REPO` (optional) — repo whose latest signed release the runtime measurement resolver (`src/upstream_trust`) verifies (default `tinfoilsh/confidential-model-router`).
- `TINFOIL_MEASUREMENT_REFRESH_SECS` (optional, default `600`) — how often `src/upstream_trust` re-checks Tinfoil's latest release. Bounds the release→deploy race window; 10m stays well within GitHub's unauthenticated rate limit. Parsed at startup by `helpers::refresh_secs_from_env` and handed to `spawn_refresh` — the task no longer reads the environment itself, so a bad value refuses the boot rather than panicking a detached ticker.
- `TINFOIL_PRICING_OVERRIDES` (optional) — JSON per-model pricing overrides, e.g. `{"kimi-k3":{"input":2.0,"output":6.0}}`. Token-based models take `input`/`output` ($/M tokens); per-request models take `request`. Defaults in `backend.rs` `MODEL_CATALOG`, whose ids, prices, and context lengths track Tinfoil's published list (`GET https://inference.tinfoil.sh/v1/models`) and reach the wire whole per `the_catalog_reaches_the_wire_whole`. Context lengths mirror the live API's exact `context_window` (1,048,576; 262,144; 131,072; …), never the documentation's roundings. **Cached-input prices are deliberately not modeled** — `ModelPricing` has one prompt-token rate, so a cached turn is charged at the full input price, which over-covers rather than under-covers; wiring the discount in would change the wire contract on both sides.
- `PRICING_MARKUP` (optional, default `1.5`) — markup factor on all model prices. The server refuses to start below 1.5 — the pricing contract's safe cost factor (`eidola-common`'s `SAFE_COST_FACTOR_NUM/DEN = 3/2`): the contract charges prompt bytes at 1/1.5 of worst-case token count, so a lower markup would sell tokens below cost (`validate_pricing_markup` in `backend.rs`).
- `TERMS_FEED_BASE_URL` (optional) — base URL of the published website (production `https://www.eidola.ai`) the terms-feed poller (`src/terms_feed.rs`) polls for current legal-document versions. See Terms gate below.
- `TERMS_REFRESH_SECS` (optional, default `600`) — terms-feed poll interval.
- `TERMS_OF_SERVICE_SHA256` / `PRIVACY_POLICY_SHA256` (+ optional `_VERSION`, default 1, and `_URL`) — static dev/test pins seeded once at startup through the same monotonic upsert. Neither feed nor pins set = gate disabled.
- `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_HEADERS` / `OTEL_SERVICE_NAME` (optional) — OpenTelemetry export (see Observability).
- `ENGINE_TOKEN` (required when the build pins an engine deployment, ignored otherwise) — the bearer token Eidola's inference nodes verify (their `GATEWAY_TOKEN`); a Tinfoil secret, held in a scrubbed `EngineToken`, never logged. `ENGINE_TOKEN_HASH` measures it like the other `_HASH` secrets (`verify_measured_secrets`). The boot refuses to start without it when `PINNED_MODELS` is non-empty. It stays in the process environment after boot (removing a variable is `unsafe` in this edition), as the node's token does.
- `ENGINE_PLACEMENT_REFRESH_SECS` (optional, default `30`) — how often the `engine_placement` table is re-read; through `helpers::refresh_secs_from_env`, so zero is refused.

**Refresh periods are validated at configuration time.** `TINFOIL_MEASUREMENT_REFRESH_SECS` and `TERMS_REFRESH_SECS` both go through `helpers::parse_refresh_secs`, which **refuses zero** along with anything unparseable. Zero is the case worth naming: it parses as an integer, so a hand-rolled `parse::<u64>()` accepts it, and the damage only appears once the task it configures starts — `tokio::time::interval` panics on a zero period (killing the detached upstream-measurement refresh, leaving the server on its bootstrap allowlist while every attestation fails from the next router deploy), and the terms poller's `sleep` returns immediately, turning the loop into an unbounded refetch-and-write storm. Both leave the process up and apparently healthy, so a new periodic task reads its period through the same helper rather than parsing its own.

## Client-facing traffic shape (`src/padding.rs`)

A network observer between a client and this server sees ciphertext, and ciphertext has a size and an arrival time. Relayed chunk by chunk, a streamed completion put one TLS record per upstream chunk on the wire, so record sizes traced each token's length and their spacing traced the model's cadence. Published attacks recover topics and text from exactly that: token lengths from record sizes (Weiss et al., USENIX Security 2024), topic classes from sizes and inter-arrival times across dozens of models (Whisper Leak, arXiv 2511.03675), and query fingerprints from how many tokens each speculative-decoding step accepted (arXiv 2411.01076). Both hosting paths had it, since both are relayed by the same handler. So the response is re-framed before it leaves; this section is the reasoning.

- **Streaming: fixed-size frames on a fixed tick.** `handle_streaming_request` sends `padding::StreamEvent`s (each chunk's JSON, the metadata event, `[DONE]`) through `padding::channel`'s `EventSender`, and the body is its `PaddedStream`: every `TICK` (50 ms) it writes exactly one frame of `FRAME_BYTES` (2048), from the moment the response opens until the frame that carries `[DONE]`. A frame is whatever event bytes are waiting, up to its size, and padding for the rest; an event larger than a frame (the metadata event usually is) continues in the next one. Nothing else reaches the body: no axum `Sse`, no keep-alive (the ticks keep the connection alive), and `the_chat_handler_answers_only_through_the_padding` holds the handler to that. Every write is the same size and the writes run on a clock, whether a tick saw one token, a burst of speculated ones, or none.
- **Why a tick and not token batches.** A frame released whenever N tokens (or N bytes) had accumulated would be one size, but its timing would trace the generation rate, which is the cadence the attacks read. A fixed tick hides per-token timing completely; what it leaks is when the stream ends. Also rejected: writing only on ticks that carry data (the on/off pattern shows pauses, prefill, tool-call boundaries); a small set of frame sizes chosen per tick (a rate class per tick, a coarser version of the same trace); rounding the stream's end up to a duration bucket, because the client stops reading at `[DONE]` and must either wait out the padding (latency on every turn) or close early (which shows the real end).
- **Why 2048 bytes every 50 ms.** A relayed one-token chunk is about 210 bytes on the wire (`id`, `object`, `created`, `model` and the choice envelope around a few bytes of text), so the frame rate, 40 KiB/s, carries about 190 tokens a second: above what the models sold here stream to one request, so the cap rarely binds. When it does, output queues and is delivered at the cap. **The queue is bounded in bytes** (`MAX_BACKLOG_BYTES`, 1 MiB per stream): `EventSender::send` admits an event only when the bytes already waiting plus its own fit, or, for one event larger than the bound on its own, when nothing else is waiting; otherwise it waits, and the upstream read behind it waits too. So the stream never holds more than the bound, except one oversized event alone (moved from the producer, which already held it, and cut across frames). A bound counted in messages would not do: one large delta, or a channel's worth of them, passes any byte figure (`the_backlog_is_bounded_in_bytes_even_for_a_large_event`, with a stalled writer). The costs, stated: up to 50 ms added before a token reaches the client (the wait for its frame), 20 updates a second (reads as continuous text), and 40 KiB/s for as long as the response runs, about 2.4 MB a minute, mostly padding. The client counts that padding toward neither its read ceiling nor its Record (`crates/eidola-app-core/AGENTS.md` → Reading from a peer).
- **When the clock starts, and what that does to time-to-first-token.** The ticks start when the response opens, which is when the upstream accepted the stream (`dispatch_stream` returns on the upstream's response headers). The node sends them before prefill (its axum `Sse` answers before the first event), and an OpenAI-compatible streaming server such as vLLM does the same; Tinfoil's servers are their code, not ours, so for that path this is expected rather than pinned. So the first token, and with it whether a prompt prefix was served from the engine's cache, falls inside the padded stream, where no frame differs from another. It is visible only as part of the total duration. Not masked: the time to the response headers (connection, a new connection's attestation handshake, upstream admission), which says nothing about content; and a cache hit's shorter prefill shortens the total duration. A time-to-first-token floor was considered and not adopted: it gives up the latency a cache hit buys, and the host still sees the engine's GPU and DMA timing directly.
- **Padding is event-stream syntax every client already ignores.** When the waiting bytes end before the frame does, the rest is a comment event (`:` + spaces + blank line), which the format defines as dispatching nothing and which axum's keep-alive has always sent on this route. A remainder of one or two bytes is too short for a comment and goes inside the last JSON event as whitespace after the value (`data: {…}  `), which JSON permits and every JSON parser accepts; after `[DONE]`, it is blank lines. **Nothing is added inside a JSON value**: a padding member in the chunk (OpenAI's `obfuscation` field is one) would reach a client's typed parse of the chunk, where a strict one refuses an unknown member. Tested both ways: a spec-compliant event-stream parser and a naive one (split on blank lines, keep `data: ` blocks, stop at `[DONE]`) each read exactly the original events, in order, with nothing extra (`a_client_reads_exactly_the_original_events`, `a_one_or_two_byte_remainder_is_still_padding_every_client_ignores`).
- **Every frame is the same, so the end and the error paths are too.** Usage, the finish chunk, the metadata event with its refund, an upstream error's metadata event and `[DONE]` are all events in the one byte stream, cut into the same frames. The only shapes left: a stream that fails to open is a JSON error response rather than a stream (padded like every other response, below), which shows that it failed and nothing about the content; and a client that disconnects drops the body, whose receiver drops, so the producer's next send fails and settles as before.
- **One write per tick, and what happens below it.** Each tick yields one `Bytes`, which hyper writes as one HTTP/1.1 chunk (a constant `800\r\n` header) and flushes, since the body has nothing more until the next tick (`each_tick_is_one_http_chunk_of_the_frame_size`, over a real connection, reads padding frames before the producer has sent anything). A late tick moves the schedule rather than writing two frames back to back (`MissedTickBehavior::Delay`; `a_late_reader_never_gets_frames_back_to_back`). Below this process, the attestation shim (outside the measured gateway image) proxies the stream and terminates TLS, and it may re-chunk, coalesce or split writes, cut TLS records, or speak HTTP/2 to the client. None of that can bring back a content-dependent shape: every write it receives is the same size, on a schedule set by the clock, so whatever it does is a function of those. That is also why TLS record padding and HTTP/2 `PADDING` are not used: the TLS is the shim's, and with every write one size there is nothing left for them to hide. `Cache-Control: no-cache, no-transform` asks intermediaries not to compress, since compression would shrink the padding to nothing. **Nothing in this server compresses**: there is no compression layer (`the_chat_handler_answers_only_through_the_padding` holds the manifest to having no compression crate), and `pad_body` refuses a content-encoded body with a padded 500 rather than send it. The shim is outside this repository; it is a reverse proxy that forwards the server's bytes, and `no-transform` is what this server can say to it and to anything after it.
- **Every other response: a size bucket, from a layer around every route.** `padding::shape`, applied in `main.rs` around the whole router (every route, `/openapi.json` and the fallback), runs `shape_response` on every response: a handler that panics is answered with a fixed 500 rather than a dropped connection, and then `pad_body` pads the body with trailing spaces to the next power of two, at least `MIN_BODY_BUCKET` (4 KiB), sets a matching `Content-Length`, and adds `no-transform` to `Cache-Control`. That covers what the handler never sees, because axum runs the extractors first: `TokenAuth`'s refusal, `ChatRequest`'s and `LoggedJson`'s refusals of a malformed, mistyped or oversized body, a 404, a 405. JSON, `text/*` and untyped bodies are padded (trailing whitespace leaves JSON unchanged); an event stream passes through as it comes (its frames shape it, and the layer must not buffer it); a status with no body (1xx, 204, 304) is left alone; any other type would be corrupted by trailing bytes and passes unpadded, and no route serves one. **Every route, not only chat completions**: one rule leaves nothing to classify and so nothing to misclassify (the reasoning the telemetry sampler follows); content reaches only the chat route, but any response whose length depends on what the client sent is the same leak, and 4 KiB for a small account answer costs nothing that matters. **Refusals quote nothing from the request**: axum's JSON rejections echo the offending field name or scalar, which a padded body would still carry in its length bucket, so `LoggedJson` and `ChatRequest` answer each rejection class with a fixed message and the rejection's own status (`handlers::refusal`). A blocking answer's time still tracks its length (it is generation time), so the stream is the shape this protects best, and it is what the client uses for turns. Test: `every_refusal_on_the_router_is_padded_and_echoes_nothing` drives a missing credential, an unknown field and a mistyped value quoting a 9,000-byte scalar, malformed JSON, an oversized body, a wrong method, an unknown path and a panicking handler through `shape` and the real extractors (`TokenAuth` extracts under any state, since it reads none).
- **The gateway-to-engine hop is not padded.** The host observes that connection directly, and it also sees the engine's GPU and DMA timing (in confidential-computing mode, every bounce-buffer transfer's size and time), which traces per-step output cadence however the bytes on the wire are framed. Padding the hop would cost the node's own stream work and buy little against the one observer who can see it. The client-facing stream is where the padding counts: there the observer is anyone on the network path.
- **Billing is unchanged.** The settle path reads usage from the upstream's chunks before anything is framed, and padding never enters a chunk; a client reads back the same usage, so the charge is the same either way (`billing_is_identical_with_and_without_padding`). The stream-timing instruments still stamp chunks at the upstream socket.
- **What an observer still learns:** when a response opened (and so how long the upstream took to accept it); its total duration at tick resolution, which includes time-to-first-token and generation time and so tracks the answer's length; for a model faster than the frame rate, a lower bound on its bytes (frames × 2048); a blocking answer's size bucket and duration; whether a stream failed to open; and everything about the request, which is not padded (the prompt's size travels as it is).
- **Tests** (`src/padding/tests.rs`): every frame is the frame size and the frame count is a function of the total encoded length alone, over generated delta sequences of any text (`frame_sizes_do_not_depend_on_token_lengths`); both parsers read exactly the events; billing; frames on ticks rather than arrival, on a paused clock (`frames_go_out_on_ticks_not_on_arrival`); the byte-bounded backlog with a large event and a stalled writer; a dropped stream failing the producer's send, a waiting one included; one chunk per tick over a real connection; a late reader; blocking buckets, `no-transform` and the refused content encoding; every refusal on the shaped router; and the source scan (handler, `main.rs`, manifest). Each was checked to fail with its protection removed.

## Terms gate (`src/terms_feed.rs`)

Each legal document's exact source bytes are published by the site builder at `/terms/source.md` and `/privacy/source.md` (rendered pages carry `eidola:version` / `eidola:source-sha256` meta tags and a visible version line). The server computes the SHA-256 itself, parses the front-matter `version`, and records observed versions in the shared `required_document` table — **append-only**, one row per (document, version) with `first_required_at`. The gate enforces the highest recorded version per document, so monotonicity is structural (a stale CDN edge or outage can only pause advancement, never regress it) and the table is a permanent audit trail. A same-version observation with different bytes is a versioning-contract violation and refused (warn from the poller; fatal for an explicit env seed). The table is shared, so one instance observing a new version converges every instance immediately. This decouples terms updates from the measured, per-release-immutable server config — legal documents outlive any release.

**Gate semantics:** checkout and credential issuance require the account's max accepted version per document ≥ the required version (HTTP 428 `terms_acceptance_required`; clients fetch `GET /v1/terms`, record acceptance via `POST /v1/account/terms`, stored append-only in `account_acceptance` with the version stamped). **The client submits the pair it displayed, never a fresh read.** `POST /v1/account/terms` records a `(document, sha256)` pair only while it is still in the required set and answers a stale one with 409 Conflict, which is what makes the rule enforceable: `AppCore::current_terms` returns a snapshot, the UI shows it, and that same snapshot is the argument to `AppCore::accept_terms` / `AppCore::account_create` (GUI onboarding consent slide; CLI `account create --accept-terms`). A version advancing mid-flow therefore produces the conflict instead of a silent acceptance of text nobody read, and `AppError::TermsAcceptanceRequired` routes the re-prompt with the new text. **Acceptance is per document and the gate is per account**, so a client cannot infer the second from the first: `POST /v1/account/terms` says nothing about a document that became required after the client's snapshot, which is why app-core re-reads `GET /v1/terms` afterwards to report the standing (`TermsAcceptance`; see `crates/eidola-app-core/AGENTS.md`). Nothing on the wire changed for that — the read-back is an ordinary public fetch.

CI enforces the ordering contract: any PR changing a legal document's bytes must increment its front-matter version by exactly 1 (`scripts/check-legal-doc-versions.sh`, wired into `rust-checks.yml`).

## Observability

OpenTelemetry ships metrics and logs directly to Grafana Cloud (or any OTLP endpoint) via HTTP/protobuf, enabled when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; otherwise stdout logging only. It ships **no traces**. Instruments and the trace pipeline live in `telemetry.rs`; `middleware.rs` opens the root request span. Full reasoning in [docs/server.md](../../docs/server.md#telemetry-scope-and-boundary), enforcing `privacy-guarantees.md` §3.2–3.3:

- **Spans are recorded everywhere and exported only when a request asks to be traced.** `AggregatingSpanProcessor` sees every span and turns it into a histogram observation; a batch exporter is also registered but drops unsampled spans, and `ClientDirectedSampler` returns `RecordOnly` unless middleware installed a sampled parent. Never switch the sampler to `AlwaysOn` (everything exports) or `AlwaysOff` (yields `Drop`, which is non-recording — `on_end` stops firing and every aggregate silently reads zero). There is deliberately no route classifier: the rule is uniform so nothing can be misclassified, which is how `/v1/credentials/refund` was silently traced under the old prefix rule.
- **Client-directed tracing lives in one place**, `requested_trace_parent` in `middleware.rs`: a hand-parsed `traceparent` whose sampled flag is honored, and nothing else. **Do not install a `TextMapPropagator`** — a global one also injects trace context into the server's outbound calls, putting the trace id on requests to Tinfoil, Stripe, and GitHub. Today no outbound request carries trace context. The sampler must stay unable to promote a trace on its own; it only propagates middleware's decision to child spans. **And keep the trace layer's context activation off** (`otel_trace_layer` in `telemetry.rs`): the `tracing-opentelemetry` default attaches each entered span's OTel context to the ambient task-local, and the SDK logger stamps that context's trace id onto every exported log record, sampled or not — regrouping a request's log lines under one id. `exported_logs_carry_no_trace_context` pins this.
- **The OTLP exporters send through our client, never their default** (`otlp_http_client` in `telemetry.rs`, shared by the trace, metric and log exporters). The exporter's default is a `reqwest` 0.13 client, which verifies against the platform trust store — and the image is `FROM scratch` with none, so that client cannot be built and the server panics in `telemetry::init()` whenever an endpoint is set (production sets one). `tests/otlp_startup.rs` runs the binary against an empty trust store to pin this. Ours carries the bundled Mozilla roots (`tls_config()`), as every other outbound client here does (`tls_backend_preconfigured(tls_config())`), one client per signal, each carrying the timeout the exporter would have resolved (`otlp_timeout` mirrors its private resolver: `OTEL_EXPORTER_OTLP_<SIGNAL>_TIMEOUT`, then `OTEL_EXPORTER_OTLP_TIMEOUT`, then 10 s), because a supplied client does not inherit the exporter's. A new outbound `reqwest` client follows the same rule.
- **`#[instrument(skip_all)]`, always.** The attribute captures every argument as a span field by default — nullifiers, spend proofs, account ids. Add fields explicitly or not at all.
- **Metrics carry the whole observability load**, so they are dense: per-operation duration from spans, TTFT, stream duration, inter-chunk gap, output rate, stream outcome, webhook outcome, token totals. Three rules when adding one — never use a caller- or upstream-derived label value (`lookup_model`, `TRACKED_SPANS`, `HANDLED_EVENT_TYPES` each resolve against a fixed list, with an `other` fallback; that is what bounds cardinality), prefer a ratio to a duration since dividing out the token count cancels the response-length term, and always set explicit boundaries on a histogram — the SDK default ladder is millisecond-scaled while every duration instrument here records seconds, so the defaults put all traffic in the first bucket.
- **`Display` on `ServerError` is the log-safe rendering, not the full one** — `to_error_response` is the full detail and goes only to the client. `PaymentRequired` and `Backend` deliberately omit their `message` because those carry, respectively, a function of the prompt's chargeable bytes and an upstream-authored string. Unit tests in `error.rs` pin this. A new error message that interpolates anything request-derived must join the redacted set.
- Log call sites take `{e}` on a `ServerError` freely — the redaction lives in the type, not in the call site. Do not hand-format an error's fields into a log instead. Raw library errors follow the same discipline before they become a `ServerError` message: `db.rs` formats `tokio_postgres` errors via `db_error_summary` (kind + SQLSTATE only — `Debug` would print Postgres DETAIL, which quotes row values), `stripe.rs` strips reqwest's URL suffix (`without_url()` — Stripe URLs carry object ids) and routes serde failures through `parse_error_summary`, and client-blob decode errors (base64/CBOR/hex) are discarded rather than interpolated.

## Tinfoil Containers / TEE integration

The server runs plain HTTP inside a Tinfoil Container; the shim terminates WebPKI TLS and serves `/.well-known/tinfoil-attestation` with a self-contained v3 envelope for client-side verification.

- `CREDENTIAL_MASTER_KEY` is injected as a Tinfoil secret (encrypted, enclave-only) in production.
- With an external PostgreSQL (until Tinfoil supports persistent disks): connection metadata in `DATABASE_URL`, `DATABASE_PASSWORD` as a Tinfoil secret, `DATABASE_SSL_CERT` if the server cert doesn't chain to a WebPKI root.
- **The container gets no attestation device and no attestation socket.** The shim is a CVM-level service outside every workload container and obtains each v3 challenge's SEV-SNP report itself; nothing in this crate requests a report. Mapping `/dev/sev-guest` into the container (the old `devices` field, which the strict config validator for `cvm-version` ≥ 0.11 rejects) would only have let a compromised gateway process mint reports over data of its choosing. The supported in-container route (`attestation: true` plus `/tinfoil/attestation.sock`) is likewise for workloads that attest themselves, which this one does not — add it only alongside code that uses it.

`tinfoil-config.yml` (workspace root) is the Tinfoil Container configuration: image digests from `artifact-manifest.json`, `_HASH` env vars for measured secrets (Argon2id hashes via `cargo run -p hash-secret`), CVM resources. Its SHA-256 is embedded in the kernel command line and bound into the enclave measurement — any change produces a different measurement. `memory` must be one of the sizes Tinfoil's validator accepts (8192, 16384, 32768, …); `scripts/artifact-manifest.sh stamp-config` refuses a config with no `ghcr.io/eidola-ai/eidola-server-gateway@sha256:` image line to stamp, so a renamed image cannot silently ship a stale digest.

### Release checklist: bringing `tinfoil-config.yml` onto the current platform

Each item moves the enclave measurement, so it lands with a release's manifest regeneration (`just update-manifest`, or the `artifact-manifest` job's suggested files), never in a feature change.

1. **Reconcile the OVMF pin — this blocks the next tagged release as things stand.** `tinfoil-build.yml` pins `tinfoilsh/measure-image-action` v0.13.1, which measures SEV-SNP with EDK2 OVMF `v0.0.4` (`78c89017…`), while `OVMF_VERSION` / `OVMF_SHA256` in `scripts/artifact-manifest.sh` still pin `v0.0.3` (`3a38d062…`). The two measurers therefore disagree on the SNP launch digest and the tag workflow's "measurements match" cross-check will fail. Move the script pin to the firmware the pinned action uses (verify the asset with `gh attestation verify … -R tinfoilsh/edk2`), confirm with Tinfoil which firmware their hosts launch for the chosen `cvm-version`, and regenerate. Any future bump of the action pin (Dependabot proposes them) must be checked for the same drift.
2. **Bump `cvm-version` from `0.7.3`.** Pick a current release line (≥ 0.11 brings the strict workload validator; ≥ 0.14.10 attested keys) and update `CVM_MANIFEST_VERSION` / `CVM_MANIFEST_SHA256` in the same change, verifying the manifest's Sigstore provenance. The strict validator then applies to this file at measurement time (the action runs `tinfoil-config` validation for ≥ 0.11): re-validate the whole file against it rather than assuming the current fields survive — `devices` is already gone, `memory: 8192` is a valid size, and every other key must be checked against the validator of the chosen version.
3. **Publish the renamed image before tagging.** The first push of `ghcr.io/eidola-ai/eidola-server-gateway` creates a new GHCR package; make it public (Tinfoil pulls it by digest at deploy) and give the repository's Actions write access before the tag run needs it. Keep `ghcr.io/eidola-ai/eidola-server` — released configs reference it.
4. **Observability.** The default `OTEL_SERVICE_NAME`, tracer, and meter name are now `eidola-server-gateway`; update dashboards and alerts keyed on `eidola-server` (or set `OTEL_SERVICE_NAME` to keep the old series continuous).

## Upstream measurement resolution (`src/upstream_trust/`)

`inference.tinfoil.sh` is a *router* enclave reverse-proxying to per-model GPU enclaves; the router trusts those downstream enclaves via "latest Sigstore-signed release of the repo". Statically pinning the router measurement bought little rigor over Tinfoil's own model while causing a fail-closed outage on every Tinfoil router release (their sign→deploy lag is ~zero; ours was hours). So the server resolves the allowed router measurement **at runtime** to match Tinfoil's actual trust level, while still running our superior per-handshake, nonce-fresh attestation on every request. **This subsystem is temporary — deleted when we self-host inference**, at which point `main.rs` hands `attesting_client` a statically pinned measurement set.

- The attesting client **follows no redirect** (`crates/tinfoil-verifier/AGENTS.md` → Redirects): a prompt goes to the configured upstream origin or nowhere, and a `3xx` reaches the backend code as the upstream's own status rather than being chased to another attested host.
- It never touches `tinfoil-verifier` (whose connector bakes the allowed set at construction): to change the set we rebuild the `reqwest::Client` and hot-swap via `arc_swap::ArcSwap` (backend reads lock-free per request; `main.rs` supplies an `AttestingClientFactory` closure so this module stays telemetry-free).
- `sigstore.rs` verifies the GitHub artifact attestation (a Sigstore **`dsse`/in-toto** bundle — distinct from the `hashedrekord` blob bundle app-core's `ci_sigstore` verifies) end-to-end: Fulcio chain + identity (GitHub Actions OIDC issuer + repo **and exact tag** — tighter than Tinfoil's own clients), DSSE PAE signature, Rekor SET + RFC 6962 inclusion proof, `sha256(tinfoil-deployment.json) == subject digest`; the measurement is read from the signed `snp-tdx-multiplatform/v1` predicate. Crypto primitives ported from app-core's `ci_sigstore` (same pinned `releases/trust/sigstore-trusted-root.json`, the sole `releases/` input the server `build.rs` embeds); the SCT + Rekor-checkpoint gaps in `docs/gaps.md` apply identically.
- **No static fallback:** bootstrap resolves + verifies the latest release synchronously as the readiness gate; failure means the server refuses to start. Bootstrap's initial allowed set is a rolling window of 2 — latest plus the previous **published** release — so a cold start mid rolling-deploy still attests the draining previous router (the previous entry is best-effort; a missing/unverifiable one warns and boots latest-only).
- The periodic refresh keeps a rolling window of the last two measurements and never clears or widens trust on error: a new measurement is adopted only after its replacement client builds successfully; a failure keeps the current client (requests fail closed until the next successful tick).
- End-to-end regression: `tests/upstream_trust_verify.rs` verifies a real captured `v0.0.115` release bundle and asserts the tag/repo/digest/tamper rejections.

## Eidola-hosted engines (`src/engine_trust/`)

The gateway pins Eidola's own inference nodes (`eidola-server-engine`, see `crates/eidola-server-engine/AGENTS.md`) the way clients pin the gateway: the trust chain gains one level, built with the same mechanism. Engine source → engine image digest → `deploy/engine/<model-id>/<variant>/tinfoil-config.yml` → TDX launch identity (`measure-enclave`'s `measure-engine-enclaves`) → `releases/trust/engine-enclaves.json` → embedded in the gateway build. Layout, sidecar and measurement: `crates/measure-enclave/AGENTS.md` → Engine deployments. Requests for an Eidola-hosted model are routed to those deployments by `src/engine_router` (see Routing to engines below); today no deployment is pinned and no catalog row is Eidola-hosted, so the router is built only when a build pins one, and is exercised by its tests.

- **The engine config is parsed into a typed, deny-unknown-fields mirror of Tinfoil's schema and validated with a port of its validator; widening the allow-list means adding the typed field and its validation together.** The mirror (`engine_deployment::deployment`) follows `tinfoil-config/types.go` field for field over the allowed subset (an `int` there is an integer here; env values must be quoted strings, not scalars a plain `String` would coerce), and the ported rules cite their source: `decode.go`'s 1 MiB `MaxConfigBytes` (on the raw bytes, before parsing) and single document, `validation.go`'s `gpus` 0 to 8, environment-name grammar for env and secrets, grants listed once, `runtime` empty or `nvidia`, a non-negative pack `schema`, `shim.go`'s non-zero `upstream-port`. **YAML constructs where `yaml.v3` and libyaml can disagree are refused from a real parser's event stream** (`engine_deployment::yaml_events`, over `unsafe-libyaml`, the parser `serde_yaml` is built on): anchors and aliases anywhere (shim.go refuses aliases; an explicit `? &a key` included), explicit tags, `%YAML`/`%TAG` directives, merge keys (`<<`), and any mapping key that is not a plain scalar (quoted, or a complex `?`/flow key). The one container must be named `eidola-server-engine` (`the_config_holds_to_tinfoils_decoder_and_validator` feeds each ported rule a violating value). Deployment path components share one grammar, `engine_deployment::is_safe_component`, used here and by the measurer's directory walk (`a_deployment_path_uses_safe_components`).
- **Pinned deployments run the CUDA executor, with every allocation bounded.** The CPU executor is the numerics reference and the development path, so the shared check refuses `EIDOLA_ENGINE_EXECUTOR=cpu` in a pinned deployment (the node itself still boots it for `just run engine-server` and tests). Every allocation-driving size is capped in the node's own grammar (`engine_deployment::caps`, each with its reason: the model's 2^20-position window, the sampler scratch per sequence, the activation scratch per step token, `i32` block tables, admission slots), so the node refuses an oversized value before loading weights; and `check_resources` holds what configuration alone fixes to the deployment: `engine_deployment::host_memory_bytes` (the node's read pool — each slot a 32 MiB body live with its strict and order-preserving parses — and its admission pool — each slot's tree, rendered prompt and tokens — plus block tables and 4 GiB of process headroom: 645,922,816 bytes, about 616 MiB, per request slot) to the VM's `memory`. The parse trees cost memory per JSON value, not per byte (a 7-byte `{"":0}` is a whole map), so the request's value count is capped at the source: `engine_protocol::check_request_json` refuses a body of more than `MAX_REQUEST_JSON_VALUES` (2^18) values or nesting deeper than `MAX_REQUEST_JSON_DEPTH` (64) before anything is parsed, in the node's `parse_request` and in this gateway's `LoggedJson` extractor alike (a 400). The per-value and per-byte costs (`PARSE_PER_VALUE_BYTES`, `ORDERED_PER_VALUE_BYTES`, …) are measured, not estimated: the node's `tests/parse_memory.rs` runs the densest shapes at the cap through `parse_request` under a counting allocator and holds the peak to `read_slot_bytes` and what the admitted request keeps to `ordered_tree_bytes`; and `KV_DEVICE_BYTES` to the least the node's `cuda::derive_kv_blocks` accepts (`engine_deployment::cuda_kv_min_bytes`: one `MAX_MODEL_LEN` sequence in the global pool, every seat's sliding windows and a step's positions in the sliding pool, with drafting a drafter pool of the sliding pool's blocks and their boundary taps, each pool's pad block, at MiMo's per-position bytes; a node test holds the two equal) and, since a node runs on one device, the device fit: `KV_DEVICE_BYTES` + the weights + `engine_deployment::cuda_device_reserve_bytes` must fit `SUPPORTED_GPU_MEMORY_BYTES`, the 287,428,640,768 bytes the driver reports for the one supported GPU (`SUPPORTED_GPU`, the NVIDIA B300 SXM6 AC), as `/v1/engine/info` showed on it. The weights are bounded from above by the pack's data size (`artifact_data_bytes`: the modelwrap reference's `hashOffset`, the byte length of the uncompressed EROFS image that holds every file of the pack, per modelwrap's `SPEC.md`), since the executor copies tensors as stored and only re-lays out scale grids and widens small vectors. The reserve bounds the executor's own allocations from above: 4 GiB fixed (CUDA context, kernel modules, decode-graph captures, the weights' layout slack), 1.25 MiB per `MAX_BATCHED_TOKENS` (the step's scratch, an f32 logits row per token among it: about 1.03 MB at Flash's shapes), a 1.5 GiB expert-row floor, per `MAX_SEQS` 1.25 MiB for each of the sampler's distribution rows (an f64 over the vocabulary; `2k + 2` rows with `k` drafts), the device block tables, the RoPE tables and split attention's partial rows (`split_partial_rows`), and with drafting the drafter's slot state, the step's level rows and step tables per `MAX_SEQS` (`cuda_device_reserve_bytes`' docs derive each term from the executor's allocations). Because the reserve is never zero, the rule is stricter than the node's own boot refusal of a budget not less than its device's memory (`allocations_are_capped_and_fit_the_deployment`, and `eidola-common`'s `the_device_holds_kv_weights_and_the_executors_reserve`). The CUDA executor's own settings are measured like the rest: `KV_DEVICE_BYTES`, `KERNELS_DIR` (absolute and clean, and outside `/tinfoil`, so the kernels come from the pinned image and never from an attached mount: `check_kernels_dir`) and `CUDA_GRAPHS` (`on` or `off`) are required, `KV_BLOCKS` (the `cpu` executor's) is refused, and `DRAFT_TOKENS` is at most 3 (MiMo-V2.6-Flash's MTP layers), as the node's grammar holds them; a drafting deployment fits by the same rules (`allocations_are_capped_and_fit_the_deployment`).
- **One check per deployment, shared with the measurer.** Every rule about what a deployment's config and sidecar may say lives in `eidola_common::engine_deployment::deployment::check_deployment`, which both the build check below and `measure-enclave`'s generator call, so the generator can only emit a pin the build accepts. A weights pack must state its layout, `schema` 1 or 2 (Tinfoil's `ModelSpec.Schema`; the pack's root hash depends on the layout it was built with, so it is required rather than defaulted). The build check adds what only it can: the pin file's shape, the config's path and hash, and the pin's agreement with the checked deployment. The attesting client's pin compiler (`tinfoil_verifier::validate_pins`) runs on both sides: the generator builds each pin as the typed `AllowedMeasurement` and compiles it before rendering, and the build compiles every pin it reads, so no rule is one-sided.
- **The file is checked on every gateway build, and is a function of the tree in both directions.** `build.rs` runs `engine_trust/manifest.rs::check` (the same file compiled into the crate's tests via `#[path]`, so fixtures exercise the code that gates the build) and panics on any disagreement: strict shape (unknown, missing or mistyped members refused at every level; lowercase fixed-width hex); each deployment's `config` is `deploy/engine/<its model>/<variant>/tinfoil-config.yml`, exists, and hashes to `config_sha256`; the config pins its release manifest inline (`cvm-version: X@sha256:<hex>`) and that string is `cvm_version`; it runs exactly one `ghcr.io/eidola-ai/eidola-server-engine@sha256:<digest>` container whose quoted env serves this model id and these weights from `verified-readonly` storage with the recorded prompt-cache policy, takes `GATEWAY_TOKEN` as a secret and measures only its Argon2id hash. **The whole measured env is read by the node's own boot grammar, not a mirror of it**: `eidola_common::engine_deployment::parse_measured` is what the node's `Config::from_lookup` calls before verifying its secret token, and the check runs every pinned deployment's env through it, so every variable the node requires, missing or malformed, fails the build (`every_variable_the_node_requires_is_checked`); what it cannot see is what needs the weights (model length, MTP depth) or the node build (a `cuda` executor). `cvm-version` is read by `parse_cvm_version`, the grammar `measure-enclave` measures with. **The pin is compiled by the attesting client's own pin compiler**: it is deserialized as `tinfoil_verifier::AllowedMeasurement` and passed to `tinfoil_verifier::validate_pins` (what `attesting_client` runs), so a TDX policy the client would refuse — `{}`, a wrong width, an empty MR_SEAM list, DEBUG attributes — fails the build with the client's reason (`a_tdx_policy_the_attesting_client_refuses_is_refused`). The file itself is first read with **the runtime's typed parse** (`engine_trust/file.rs`, compiled into `build.rs` by `#[path]` and used by `allowed_measurements`): unknown and repeated members are refused at every level, a repeated model id included, so a file the build accepts is one the running gateway can read (`a_repeated_member_anywhere_is_refused`). The config is held to **an allow-list of keys** (the typed mirror's fields, from Tinfoil's schema in `tinfoil-config/types.go`, which the measurer parses with too): at the top level `cvm-version`, `cpus`, `memory`, `gpus`, `models` (the read-only model packs that carry the weights), `containers` and `shim`; in the shim `upstream-port` and `paths`; in the container `name`, `image`, `env`, `secrets`, `models` (the pack grant), `runtime` and `gpus`; in a model pack `name`, `repo`, `mpk` and `schema` (required, 1 or 2). Everything else fails the typed parse — `entrypoint`/`command` would run another executable from the pinned image, `volumes`/`devices`/`cap_add`/`privileged` widen what it touches, `networks`/`cvm-network` open egress or inbound ports, the shim's `dummy-attestation` replaces the hardware evidence, a pack's `exec` makes weights executable — and a key is added only with the reason it is needed (`the_config_uses_only_the_keys_an_engine_needs`). The `cuda` executor's container must have `runtime: nvidia` and `gpus: all` (every attested GPU), the `cpu` executor's neither (`the_engine_container_has_the_gpu_access_its_executor_needs`). **The env is exactly the node's measured variables** (`check_env_names` over `env::MEASURED`): any other name, one a dependency reads included, is refused (`the_env_is_exactly_the_measured_variables`). **The VM is a launchable shape** (`check_vm_resources`): `cpus` from 1 to 256 and `memory` a power of two from 8 GiB to 2 TiB (MiB); Tinfoil's published checks require only positive values, so these bounds are ours, held for every accepted `cvm-version` (`the_vm_is_a_launchable_shape`). The grammar also carries the scheduler's own boot refusal, `MAX_BATCHED_TOKENS > DRAFT_TOKENS` (`eidola-common`'s `a_step_holds_a_decode_row`), and the `cuda` executor's draft width, at most MiMo-V2.6-Flash's three MTP layers. Three more come from what the node reads. **The gateway token is the only secret** (`check_secrets`): a secret reaches the node outside the measurement, so any other (`RUST_LOG`, say) could change its behaviour unmeasured (`the_gateway_token_is_the_only_secret`); the node itself reads no other environment variable, its log level being fixed in the binary. **The shim exposes exactly the node's routes** (`check_shim_paths`, over `NODE_ROUTES`: `/v1/chat/completions`, `/v1/engine/info`, `/healthz`), matched as the shim matches (cvmimage `tinfoil/cmd/shim/api.go`, `pathMatchesPattern`: an exact path, or a trailing `*` on a segment boundary). Every route must be matched and every pattern must match one; an empty or absent list is refused, since the shim reads it as "forward every path" (`the_shim_exposes_exactly_the_nodes_routes`). **The weights are the one pinned pack** (`check_weights_pack`): exactly one model pack, its `repo` equal to the pin's `<repo>@<revision>` and its `mpk` naming a root hash, granted to the engine container alone, with `EIDOLA_ENGINE_WEIGHTS_DIR` inside its mount — Tinfoil binds a granted pack read-only at `/tinfoil/models/<name>` in the granted container only (cvmimage `docs/runtime-policy.md`) — so the directory the node verifies and serves is the verified pack (`the_weights_dir_is_the_granted_pinned_pack`). The bearer token's shape is shared too (`is_gateway_token`): the gateway's `EngineToken` and the node's boot refuse the same tokens. Three rules join them, each about what the measurement would otherwise fail to cover. **The engine is the only container, pinned by full digest** (`ghcr.io/eidola-ai/eidola-server-engine@sha256:<64 hex>`): MRCONFIGID binds the config's bytes, not what a tag resolves to, so a companion container or a tag would run unmeasured code (`every_image_is_the_digest_pinned_engine`). **A deployment's GPUs are attested exactly** (`eidola_common::engine_deployment::check_gpu_attestation`, which the measurer applies too): the attestation shim collects exactly the config's top-level `gpus` worth of GPU evidence items (Tinfoil's `tinfoil-config/decode.go` sets `shimConfig.ExpectedGPUs = config.GPUs`), so `EIDOLA_ENGINE_EXECUTOR=cuda` requires `gpus` in Tinfoil's NVIDIA-CC shapes (1 or 8, per its docs and `tinfoil-config/validation.go`) and `expected_gpus` equal to it — fewer would leave accelerators unattested, and a CUDA config without `gpus` gets no GPUs while its pin fails every handshake — and `cpu` requires both absent or 0 (`a_cuda_deployment_attests_its_gpus`). `tinfoil-verifier` does not refuse `expected_gpus: 0` itself, because for a CPU-only pin "no GPU evidence" is a legitimate requirement. **The shim reaches the node**: `shim.upstream-port` equals the port of the measured `EIDOLA_ENGINE_BIND_ADDR`, which listens on every interface as the gateway's own deployment does, since the shim runs outside the workload container (`the_shim_reaches_the_node`). And `GATEWAY_TOKEN_HASH` is one a token can verify against, in `hash-secret`'s profile: `parse_gateway_token_hash` first holds the parameters to Argon2id v=19, m 19,456–65,536 KiB, t 2–4, p 1–4 and a 32-byte output (refused before anything is hashed, so an extreme hash cannot make the check or the node's boot allocate at will), then runs `verify_password`'s own hashing step over an empty candidate. A weights pack's `mpk` must be a whole modelwrap artifact reference (`rootHash_hashOffset_uuid`, modelwrap `ParseRef`: 64-hex root, decimal `u64` offset, lowercase UUID). That makes `tinfoil-verifier` a build-dependency of the gateway: a host build of its dependency tree (about 100 crates) for the build script, accepted so that the check and the client cannot disagree; a TDX pin's MRCONFIGID is the config's hash; the sidecar `deployment.json` states the same weights provenance, GPU count and TDX machine policy, and is read with a typed parse that refuses unknown and repeated members at every level (the TDX policy is mirrored member for member from `tinfoil_verifier::TdxPolicy`) and `null` for an optional member (`the_sidecar_is_read_strictly_at_every_level`); every deployment of one model agrees on weights and prompt-cache policy (`eidola_common::engine_deployment::deployment::check_model_agreement`, which `measure-enclave` runs before rendering the file too); no config is pinned twice. And the reverse: every `deploy/engine/<model>/<variant>/` directory must be pinned (`require_every_deployment_pinned`). What it cannot re-derive is MRTD (and a SEV-SNP digest), which need the platform's release images — release-time work, like the server enclave. An empty `models` object is a valid file and is what is committed while no engine is deployed. `deploy/engine/` is kept in the tree (by its README) so `cargo:rerun-if-changed` watches a directory that exists; a missing path would make the build script rerun on every build.
- **The catalog is bound to the pins at compile time.** `backend.rs` evaluates `catalog_binding_problem(MODEL_CATALOG, engine_trust::PINNED_MODELS)` in a `const` item, so an Eidola-hosted row without a pin, a pin without a row, or a Tinfoil-hosted row sharing a pinned id is a compile error naming the rule — the strongest form available, since the catalog is Rust source and the pins are generated Rust constants; a `build.rs` check could not see the catalog without parsing Rust. The same `const fn` is called on fixtures by `the_catalog_and_the_engine_pins_bind_both_ways`, because today the production pair is trivially bound (no Eidola-hosted rows, no pins).
- **Same-sha pinning.** A gateway build accepts exactly the engine deployments committed in its own tree: no list of previous measurements, no transition pins, nothing that widens the set at runtime. Rollout is therefore ordered — **new engines → new gateways → client → shift → retire**: deploy the new engine deployments beside the old ones (their configs and pins committed, so a gateway built from that tree accepts both); ship that gateway; ship the client pinning that gateway; shift traffic; then remove the old deployments' directories and pins, and the next gateway build no longer accepts them. An in-place config change (a new engine image digest, say) moves its pin with it, so the engine must be deployed before a gateway carrying the new pin ships.
- **Weights stay compiled in.** The weights hash the gateway sends a node (`X-Eidola-Weights-Sha256`) and the one it publishes (`pinned_weights.sha256`) come from `PinnedModel`, which only the generated list can construct (private fields; tests use a `cfg(test)` fixture constructor). `protocol::engine_request_headers` takes a `&PinnedModel`, so placement data can choose a node but never what that node must be serving.
- **Prompt-cache retention has one source of truth: the deployment's measured config.** The node takes `EIDOLA_ENGINE_PREFIX_CACHE` / `EIDOLA_ENGINE_CACHE_IDLE_TTL_SECS` / `EIDOLA_ENGINE_CACHE_MAX_AGE_SECS` from its config with no default; the pin records the same three values and the build check holds them equal; the catalog's `prompt_cache` leaf is derived from the pin. The engine core's library defaults (15 min idle, 2 h max age) reach a deployment only by being written into its config, as `just run engine-server` does.
- **`cache_key` (`types::CacheKey`).** The strict request type accepts an optional `cache_key` in the shared shape (`eidola_common::engine_protocol::is_cache_key_text`: 32 bytes, base64url, unpadded, canonical), refusing anything else at deserialization with a message that never quotes the value. It is secret material: decoded into a boxed scrubbed-on-drop buffer, the text scrubbed, `Debug` redacted. **It is never serialized** — the field's `skip_serializing_if` predicate always skips (spelled that way rather than `skip_serializing` so the OpenAPI schema still documents it), and `CacheKey`'s own `Serialize` refuses — so the Tinfoil path, which forwards `.json(request)`, cannot carry it (`the_tinfoil_upstream_never_receives_the_cache_key`, against a local stand-in, both transports). The only writer is `protocol::engine_request_body`, which writes it back for a node and scrubs its copies. Out of reach: the body bytes in the HTTP stack's buffers and serde_json's scratch buffer for an escaped string, as on the node. Pricing is unaffected — `prompt_charge` reads only `messages` and `tools`. The client sends one only for a row whose `prompt_cache` leaf declares support and both bounds, scoped to one conversation lineage and rotated within those bounds (`crates/eidola-app-core/AGENTS.md` → Prefix-cache keys); it mints keys with `eidola_common::engine_protocol::encode_cache_key`, which `the_shared_encoder_round_trips_through_the_decoder` holds to this decoder.
- **The Tinfoil backend refuses an Eidola-hosted model** (`ensure_served_here`, 503, before any byte is sent), so a catalog row that names a self-hosted model can never fall through to Tinfoil, whatever calls the backend: `handlers::dispatch` sends such a request to the engine router.
- **Wire contract with the node** (`protocol.rs`): `Authorization: Bearer <EngineToken>` (scrubbed buffer, redacted `Debug`, the header value marked sensitive), the weights header (`eidola_common::engine_protocol::WEIGHTS_HEADER`, the constant the node itself reads), and the body. **The body keeps the client's key order and the contract's scalars.** The node renders the prompt from the body as sent through an order-preserving parser, so a tool schema's property order reaches the chat template, and the gateway's parse (`serde_json`'s sorted maps) loses it; so a request bound for a node is a `protocol::ValidatedRequest` (the strict parse plus the exact bytes, built only by parsing those bytes), and `engine_request_body` re-emits those bytes compactly with every object's members in document order. **Every scalar, though, is re-spelled exactly as `serde_json` writes the parsed value**, because that text is what the pricing contract measured (`prompt_charge` over the parsed request, computed identically by the client): forwarding a raw `1.0000000000000000000001` or an escaped string would send the node more bytes than were priced. A key repeated in an object keeps its first position and its last value (`serde_json`'s reading), found through a per-object key index, so canonicalizing an opaque object of any size is linear (`indexed_member_merging_matches_the_scanning_rule`, `a_large_object_canonicalizes_in_linear_time`). The three members the gateway decides are written last: `stream`/`stream_options` (forced to `include_usage: true` for a stream, as on the Tinfoil path) and `cache_key` (re-encoded from the validated key; the client's copy parsed out is scrubbed). The fields the strict type narrows (`temperature` and `top_p`, `f32`) are written from the typed request, as `.json(request)` writes them on the Tinfoil path, so `0.123456789` reaches either upstream as the same `f32` (`both_hosting_paths_receive_the_same_sampling_values`). Both upstreams therefore receive the same scalars and the same per-entry measures from one pricing input; only key order differs (sorted to Tinfoil). Tests: `the_body_keeps_key_order_and_canonical_scalars`, `the_engine_receives_exactly_what_was_priced` (the forwarded body prices to the charged tokens, and each forwarded tool and tool call is exactly as long as its measure). The chat handler's extractor (`handlers::ChatRequest`) builds one for every request: `LoggedJson`'s shape limits and refusals, unchanged (axum's own extractor decides content type and syntax, and a refused body gets exactly the refusal it got before: `the_chat_extractor_keeps_the_bytes_and_refuses_as_before`), and then `ValidatedRequest::from_bytes` over the same bytes. The node's strict subset is the gateway's request plus `cache_key`; keep the two in step (`crates/eidola-server-engine/AGENTS.md` → Wire contract).
- **The engine router's inputs**: `engine_trust::accepted_deployments(model_id)` returns each accepted deployment's `config_sha256` (what placement names a deployment by; on TDX its MRCONFIGID) with its pin in `tinfoil-verifier`'s `AllowedMeasurement` shape (`allowed_measurements` is the pins alone); `pinned_model(id)`, `engine_request_headers`, `engine_request_body`; and `ModelHosting` on every catalog row, which `handlers::dispatch` routes by.
- **Image build.** The gateway Containerfile copies `releases/trust/engine-enclaves.json` and `deploy/engine*` into the build stage (neither depends on the gateway's own digest, so no cycle), and the flake's filtered source includes `deploy/engine/` for the gateway.
- **Open item for the maintainer: can Tinfoil deploy a config from a path other than the repository root?** Today the gateway's `tinfoil-config.yml` sits at the root, where Tinfoil's deployment system reads it. Engine configs live at `deploy/engine/<model>/<variant>/tinfoil-config.yml`. If Tinfoil can deploy from such a path, nothing more is needed. If it cannot, each engine deployment needs a repository of its own carrying that config at its root, which conflicts with the single-repository guarantee (`docs/privacy-guarantees.md` §7.1). The design works either way: the committed config here stays canonical and is what the pin hashes, so a sibling repository could only ever carry a byte-identical copy (its hash is the pin's `config_sha256`, and on TDX the guest refuses to boot under any other config, because MRCONFIGID is that hash), but the guarantee's wording would need an amendment first.

### Routing to engines (`src/engine_router/`)

A request for a model whose catalog row is `hosting: eidola` goes through `EngineRouter::send` / `send_stream` instead of the Tinfoil backend (`handlers::dispatch`), and comes back in the Tinfoil backend's shapes (`BackendResponse`, `BackendStreamEvent`), so billing settles it through the same `handlers::settled_cost` (usage → charge, clamped to the contract; no usage → the whole charge) and the forwarded bytes are the priced bytes (`engine_request_body`, above). A gateway whose build pins no deployment has no router (`AppState::engines` is `None`).

- **Placement is availability, never trust** (`placement.rs`, table `engine_placement` in `schema/schema.sql`: `model_id`, `deployment` = the config hash, `base_url`, `enabled`). Postgres is outside the enclave, so a row only makes an upstream a candidate: it is used only if it is enabled, names a pinned model and one of the deployments **this build** pins for it (same-sha pinning: a row for a deployment another gateway build pins is ignored here), and has a plain `https` base URL (no credentials, query or fragment). `admissible` is that filter, pure and unit-tested; `PostgresPlacement` reads the named columns only, so the table can grow additively under every gateway version sharing it. Re-read every `ENGINE_PLACEMENT_REFRESH_SECS`; a failed read keeps the current placement. An upstream already known (same model, URL and deployment) keeps its client, pooled connections and health across refreshes; anything else is new. **Applying the table**: the gateway has no migration runner (`schema.sql` is applied once to a fresh database), so the section is self-contained and idempotent (`IF NOT EXISTS`, re-runnable comments) and an operator applies it to an existing database by hand; `placement_reads_the_schemas_table` (`#[ignore]`, `DATABASE_URL`) reads it back through the production source. Nothing about health is written to the table: breaker state is each gateway's own.
- **Every upstream has its own attesting client, built over its model's pins** (`attesting_client_factory`: `tinfoil_verifier::attesting_client` with the model's compiled-in `AllowedMeasurement`s, the bundled WebPKI roots for TLS, no SEV-SNP root override). The pins are the model's and never placement's: an engine that attests another model's measurement is refused at the handshake (`an_engine_is_attested_against_its_models_pins`). One client per upstream rather than per model because the verifier addresses its inline attestation request to the host of the base URL the client was built with. Device evidence is the verifier's own rule (`expected_gpus` on the pin: exactly that many `nvidia-gpu-evidence/v1` items bound to the handshake's nonce), passed through unchanged (`gpu_evidence_must_match_the_pin`). Keep-alive pooling is the client's default; a handshake on a GPU node triggers fresh SPDM reports, so requests ride an attested pooled connection (`pooled_connections_are_attested_once`: one attestation for a probe and five requests).
- **No traffic before a probe, and the probe checks the weights** (`probe`): `GET /healthz` must answer exactly `ok` (a development node's `ok; weights-storage=dev-writable` fails), and `GET /v1/engine/info` (with the gateway's token) must report the pinned model id, the pinned weights hash (case-insensitive) and `weights_storage: verified-readonly`. Both run over the upstream's attesting client. A new upstream is `Unverified` until a probe passes; healthy ones are re-probed every `probe_interval` (10 s); a misregistered engine never takes traffic (`a_misregistered_engine_never_takes_traffic`).
- **Circuit breaker** (`breaker.rs`, local to the process): a healthy upstream opens after `failure_threshold` (3) consecutive request failures, or at once on a failed probe or on a refusal that means it is misconfigured (the node's own 401 `authentication_error`, 404 `model_not_found`, 412 `weights_hash_mismatch` or 428 `weights_hash_required`); an open one is probed again after its backoff (5 s, doubling per failed probe up to 300 s) and closes on a passing probe. A served request resets the count; a passing periodic probe does not. Failures are: no response at all, a 5xx other than the node's `overloaded`, a broken or unparseable response, and every way a stream can go wrong. `overloaded` (503) is load, not ill health.
- **Choosing an engine** (`rendezvous.rs`): with a `cache_key`, highest-random-weight hashing over the model's routable upstreams — route key `SHA-256("eidola/route/v1" ‖ key)`, weight = first 8 bytes big-endian of `SHA-256(route_key ‖ len(base_url) as u64 BE ‖ base_url)` — so a conversation stays on the engine holding its prefix cache and only the keys an upstream wins move when it leaves (`a_conversation_stays_on_its_engine`, `removing_an_upstream_moves_only_its_keys`, `the_weight_is_the_documented_hash`). No secret: the key is 256 client-chosen random bits. The key never reaches logs, metrics or placement; the hashers (`sha2`'s `zeroize` feature), the route key and the weights are scrubbed. Without a key, the upstream with the fewest requests in flight (counted from dispatch until the response or stream is finished), ties rotated (`without_a_key_the_least_loaded_engine_is_chosen`).
- **Retries**: a request is tried on at most `request_attempts` (3) upstreams in rank order, moving on only when the engine gave no response (no attested connection, or a pooled connection that closed under it: only a response's usage settles a charge, so a repeat costs compute, never the client) or refused it **before admission**, read by the node's exact status and error type through `eidola_common::engine_protocol::refused_before_admission` (the misconfiguration refusals above, and 503 `overloaded`, which the node raises only when a read or admission slot is not free). The node's error types are `engine_protocol::error_type` constants its `ApiError` returns, and its `only_pre_admission_refusals_say_so` test holds every variant to that rule, so the two cannot drift; a wire field saying "retryable" would carry the same fact in a second place. Any other answer, an error included, may come after the engine ran the request (`engine_unavailable`, raised when the engine stops after submission, is one), and is returned, never retried elsewhere (`an_overloaded_or_vanished_engine_passes_the_request_on`, `an_answer_after_admission_is_returned_not_retried`). With no routable upstream: 503 `no engine is available for this model` (with the full refund, as any backend error).
- **The node's subset is enforced before routing** (`subset.rs`, called first in `plan`, so a request is refused with the node's reason even when no engine is available, and no engine ever sees it: `a_request_outside_the_node_subset_never_reaches_an_engine`). The rules over a parsed request are `eidola_common::engine_protocol`'s (`check_tool_choice`: absent, `auto` or `none`; `check_stop`: at most 4, non-empty, at most 256 bytes; `check_max_completion_tokens`: not 0; and non-empty `messages`), the same functions the node calls, so the two cannot drift. Two rules are mirrored, each with its source: content parts, which the node's type holds to exactly `{type, text}` (unknown keys denied on every variant; image parts refused) while the gateway's ignores extra keys, so they are re-read from the request's bytes; and the sampling ranges of `SamplingParams::new` (temperature finite and ≥ 0, `top_p` in (0, 1]; `eidola-common` is float-free). Every refusal is a fixed message (log-safe). Residual, by nature not checkable here: what needs the model's template or tokenizer (tool-call `arguments` that are not a JSON object, a prompt beyond the context length) is refused by the node (400) and passed back with the full refund.
- **The stream relay skips nothing.** Every way a stream can go wrong ends it with an error, counted against the upstream, and the handler settles it as a failed stream: the node's `event: error` frame (its own error), an end without `[DONE]` or a broken connection (a network error), a chunk that does not parse, a block that is not UTF-8 (refused, never lossily repaired), or an event type the node does not send. Data-less blocks (SSE comments) dispatch nothing, as the format defines. So a later `[DONE]` can never present skipped output as a complete, billed response (`an_unreadable_stream_event_ends_the_stream_as_an_error`, `the_stream_parser_reads_events_and_refuses_bad_bytes`).
- **What the router logs**: upstream base URLs, model ids, statuses and attestation or connection errors, all operator data. Never a body, a key, a token or a value derived from one.
- **Tests** (`engine_router/tests.rs`) run fake engines speaking the node's protocol, each behind an in-process `tinfoil-shim-mock` (now a library: `tinfoil_shim_mock::start`, with optional nonce-bound GPU evidence items) serving real attestation over a mock AMD root, reached through `attesting_client_factory` itself. Only the roots differ from production: TDX quotes verify to Intel's root, which no test can sign for, so the fixture models are pinned to the shims' SEV-SNP measurements. Each protection was checked to fail its test when removed: key affinity, load awareness, the deployment, enabled and https filters, per-model pins, `expected_gpus` passed through, each probe check (weights, model, storage, health body), probe-before-traffic, opening on failures, keeping a failed probe open, tripping on 412, passing on overload and on no response, not counting overload, returning (not retrying) any 503 but `overloaded`, `engine_unavailable` kept out of the pre-admission list (which fails the gateway, `eidola-common` and node tests), a malformed chunk, an unknown event type and a non-UTF-8 block each ending the stream, the subset check before routing, the content-part and sampling mirrors, forwarding `engine_request_body` rather than the raw bytes, a `[DONE]`-less stream and an error frame each being an error of its own kind, usage carried from the stream, known upstreams kept across refreshes, the pooled client, the extractor's content-type check, the documented weight, and each deployment's config hash.
- **Deploying the first pinned engine** needs the gateway's own `tinfoil-config.yml` to carry `ENGINE_TOKEN` as a secret and its Argon2id hash as `ENGINE_TOKEN_HASH` (`cargo run -p hash-secret`), the same token whose hash the engine deployments measure as `GATEWAY_TOKEN_HASH`. That moves the gateway's measurement, so it lands with that release's manifest regeneration, never in a feature change; and the placement section of `schema.sql` must be applied to the production database first.

## Compose files (local development)

`compose.yaml` — two supported workflows share one file:

- **Full container stack** (`just dev` → `scripts/dev.sh --container`): postgres + gateway + shim + stripe-cli in containers, detached. Gateway image rebuilt each invocation.
- **Host mode** (`just services` → `scripts/dev.sh --host`): postgres + shim + stripe-cli in containers, with `SHIM_UPSTREAM_URL=http://host.docker.internal:8080` so the shim forwards to a cargo-built server on the host. Writes `.env.local` (`STRIPE_WEBHOOK_SECRET` + `BIND_ADDR=0.0.0.0:8080`) for the host server to source.

The shim service forwards `DEV_MEASUREMENT` as a bare pass-through (`- DEV_MEASUREMENT`, no `=`), so it reaches the container only when set in the environment running compose or in `.env` (which compose reads from the project directory automatically) — an unset var leaves the shim on its all-zeros default rather than an empty measurement, which would panic it. `scripts/local-client.sh` resolves the same variable the same way, environment before `.env`, so one value governs both what the shim advertises and what the client trusts on every documented path. Its `.env` reader covers compose's grammar except `${VAR}` interpolation (reimplementing that is reimplementing compose): such a value warns and then fails the script's own shape check, pointing at exporting the variable instead. The script's other settings (`EIDOLA_DEV_CERT_DIR` / `EIDOLA_DEV_BASE_URL`) are client-side only by design — they say where a stack already is, and have no compose counterpart to follow.

Both build only the images they need, idempotently apply `schema.sql`, capture the Stripe webhook secret if `STRIPE_API_KEY` is set (else skip stripe-cli), and start detached. `just down` tears down both. Profiles: `gateway` gates the gateway container, `stripe` gates stripe-cli; postgres and shim have no profile. The shim has `extra_hosts: host.docker.internal:host-gateway` (Linux host-gateway) and intentionally no `depends_on: gateway` (host mode); `postgres`/`gateway`/`shim` declare `platform: linux/amd64` so compose doesn't warn on arm64 hosts.
