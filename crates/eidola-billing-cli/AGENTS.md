# Private billing tool

This binary links `eidola-billing`, connects directly to PostgreSQL and Stripe, and runs with the caller's credentials. It is never an administrative gateway endpoint. Keep the CLI a presentation layer over the shared billing service; do not add another balance mutation path here. The `serve-webhooks` and `work` commands are separately deployable roles in the same binary/image; neither starts the other. The image (`oci/eidola-billing/Containerfile`) is built and published by CI like the gateway's and recorded in `artifact-manifest.json` from schema 5 (`.github/AGENTS.md` → `oci-billing`); no deployment config for it lives in this repository.

- Keep database and Stripe credentials in the environment, never command-line arguments, persisted support records, or output. Read every variable through `eidola_common::env::Env`, under `EIDOLA_ENV_PREFIX` (deployments: `BILLING_RECEIVER_`, `BILLING_WORKER_`; support commands normally unprefixed); never call `std::env::var` directly.
- Refunds name an explicit durable operation UUID. Reusing it means retrying the same request, not authorizing a second refund. Keep normal refunds and cash-only goodwill refunds visibly distinct.
- A preview makes no mutations. Execution repeats validation under the shared locks. Output is JSON for both human operators and private automation.
- Reconciliation reads authoritative provider state and applies recorded intents; it never treats a refund observation as permission to cancel account credits.
- `README.md` is the operator playbook. Keep it aligned with the shared service's failure states, including uncertain outcomes and expired reservations.
- `runtime.rs` owns only HTTP ingress, process lifecycle and the database-work retry loop. Stripe raw-body verification and the minimal event parser live in `eidola-billing::webhook`; there is one signature implementation, including multi-`v1` secret rotation. The receiver requires database access and its signing secret, never a Stripe API key; workers require the provider key and open no listener. The receiver accepts only Stripe's thin event notifications, so no Stripe object's contents reach it; it refuses a snapshot event. Store only event identities, never webhook payloads.
- Receiver acknowledgment follows durable enqueue. The public `/healthz` checks database access and ingress compatibility, while worker execution checks the independent execution protocol. Do not infer financial completion from receiver health or successful delivery. Unknown job types/versions remain visible for review.
- Receiver authentication tolerates at most five minutes of clock skew in either direction. Unsupported thin event types are acknowledged even when they name no related object; supported billing events still require valid IDs. Deployment must synchronize clocks, monitor aging uncertain submissions before the safe retry deadline, and disable portal plan switching/prorations until those grant shapes are supported.
- SIGTERM/SIGINT interrupt initial protocol admission too, including a stalled database connection/query; poll shutdown while awaiting that check. After startup, stop new work and allow an active request/batch a bounded 30-second grace. Cancellation must drop database guards and leave pending work recoverable. The worker timer scans durable work only, never Stripe accounts. Logs contain fixed categories, not account/provider identifiers or response bodies.
- `telemetry.rs` starts logging and OpenTelemetry for the two roles only; a support command starts neither and exports nothing. With `OTEL_EXPORTER_OTLP_ENDPOINT` set and not empty (read under the prefix, like everything else), the role exports metrics and logs through `eidola-telemetry`'s pipeline — the gateway's: every OTLP setting read explicitly under the prefix, exporters sending through our own clients carrying the bundled roots, because the image is `FROM scratch` with no trust store (`tests/otlp_startup.rs` starts both roles against an empty one), and the same caveat that the exporter still merges the bare `OTEL_EXPORTER_OTLP_HEADERS` over ours. Default service names are `eidola-billing-receiver` and `eidola-billing-worker`; each process adds a random `service.instance.id` so replicas' cumulative series stay apart. No traces: nothing asks for one, and Stripe's dashboard holds the request log. The receiver's instruments are `billing.webhook.deliveries{event_type, outcome}` (`event_type` a supported type, `unsupported`, or `unknown` when refused before its type was read; `outcome` from `WEBHOOK_OUTCOMES`) and `http.server.request.duration{http.request.method, http.route, http.response.status_code}`; the worker's are in `eidola-billing` (`crates/eidola-billing/AGENTS.md` → Telemetry), plus the backlog gauges `runtime::report_backlog` reads every 30 s.
- Logs are operator signals, once per condition or change of state, never a line per delivery or batch: `DatabaseHealth` logs the database's calls starting to fail (naming the SQLSTATE or fixed description), its refusing this build's protocol (an empty `billing_protocol`, or another version) and answering again, for both roles; `FailingStreak` warns once when five signed deliveries in a row fail verification (a wrong `STRIPE_WEBHOOK_SECRET`) or arrive with stale timestamps (an unsynchronized clock), re-armed by a verified delivery; a role that stops on an error (a startup protocol refusal, missing configuration) logs why before flushing telemetry; Stripe's 401/403 and unsupported pending work are logged once in `eidola-billing`. The shutdown-grace warnings stay, as incidents.
- `tests/receiver.rs` exercises real HTTP delivery and PostgreSQL durability, duplicates/conflicts, write failures, malformed/oversized input, snapshot refusal, rotation, protocol refusal and shutdown during a blocked startup protocol read for both runtime roles. Use a disposable `BILLING_TEST_DATABASE_URL` for its ignored tests. `runtime::tests` checks batch shutdown behavior; shared billing tests own multi-worker and financial race coverage.

Check billing changes against [anonymous credits](../../docs/anonymous-credits.md).
