# eidola-engine-cuda

The CUDA executors of the engine, one module per architecture: `src/mimo/` (MiMo-V2.6, `CudaExecutor`), `src/deepseek/` (DeepSeek-V4.1, `DsCudaExecutor`, *DeepSeek-V4.1* below) and `src/qwen/` (Qwen3.8, `QwenCudaExecutor`, *Qwen3.8* below). The root modules are shared by both: `device.rs`, `module.rs`, `launch.rs`, `kv_cipher.rs`, `sampler.rs`, `bf16.rs`, `ops.rs` (the RMSNorm smoke kernel) and `lib.rs` (`CudaError`, `Unsupported`, `narrow`). Everything before *DeepSeek-V4.1* describes MiMo-V2.6's executor: the serving core's `Executor` on one Blackwell GPU, running the kernels `eidola-engine-kernels` builds ahead of time, through the CUDA driver API. It is held to the seam contract (`eidola-engine/src/executor.rs`, normative) and diffed against the CPU reference executor and the model crate's f32 reference forward. AGPL-3.0-only. Workspace conventions live in the root `AGENTS.md`.

## Host boundary

- **Driver API only.** `cudarc` with `driver` + `dynamic-loading`, bindings pinned to CUDA 13.0 (`cuda-13000`, the R580 driver's API). No CUDA runtime, no NVRTC, nothing linked at build time: the crate builds and its tests run on a machine without CUDA. Do not enable `cudarc`'s `nvrtc` feature; `module.rs` calls `cuModuleLoadData` directly.
- **No host C++.** Every upstream kernel's launch parameters are built in Rust:
  - **CUTLASS** (`gemm.rs`): the 2048-byte `GemmUniversal::Params` (problem shape, mainloop TMA descriptors and, for the blockwise kernel, scale-factor pointers and layouts, epilogue alpha and output descriptor, the cluster-launch-control scheduler's tile counts, divisors and raster order, hardware info), field by field. Descriptors are encoded by the driver and post-processed exactly as CuTe does (bit 21 of word 1 cleared unless the first 128 KiB are dense). Pinned by `tests/mimo_cutlass_params.rs` against CUTLASS's own host path: every byte CUTLASS defines must match.
  - **DeepGEMM** (`moe_gemm.rs`): the five 2-D descriptors its host code builds (L2 promotion 256 B, packed-FP4 B as `16U4_ALIGN16B`), the `Identity` epilogue arguments, grid = the instance's SM count.
  - **FlashInfer** (`attention.rs`): `PagedParams` as a `repr(C)` struct with compile-time size and offset checks against the generated C++ (296 bytes), inside the kernels' by-value `AttnParams` (304 bytes: it and the address of the work-item count), CCCL's `fast_mod_div` reproduced for `uint_fastdiv`, and FlashInfer's work lists (a work item per request × query tile × KV chunk, a CTA walking them per KV head; *Batch invariance*). The work lists are derived on the host (`HostPlan`) with checked arithmetic: each request's pages cover exactly its KV (`(pages - 1) * page_size < kv_len <= pages * page_size`) and start where its reduction anchors them (position 0 for a split, an anchor for a window), it has 1..=`kv_len` queries, every index fits the kernel's `i32` arrays, and a plan runs only on the page size, group size and kind of layer (split or anchored) it was made for, and a split only within the partial rows its scratch holds.
- **Images only through `KernelDir`**, size and SHA-256 checked against the compiled-in manifest. `KernelDir::new` takes only a directory: no other manifest can be supplied, so nothing but the compiled-in hashes can approve bytes.
- **No silent narrowing.** Every count, stride, grid dimension and offset reaches a kernel through `narrow` (`try_from`, refused before launch) or a conversion whose range is proven beside it; the crate denies `clippy::cast_possible_truncation`, `cast_possible_wrap` and `cast_sign_loss` in every target (library, tests, examples; `[lints]` in `Cargo.toml`), so a new `as u32` does not build. The few float narrowings (log-probabilities stored as f32, an f32's exponent) carry a local `expect` with the reason.
- **Safe launch wrappers own kernels bound by image and entry.** `RmsNorm`, `Gemm` and the module-taking wrappers (`EngineOps`, `MoeGemm`, `Attention`, `Sampler`) resolve their entries through `KernelModule::bound_kernel` / `expect_image`, which refuse another image or entry, so no safe call can hand one kernel another's argument layout. A bare `Kernel` launches only through `unsafe`.
- **A resolved `Kernel` shares ownership of its loaded image** with the `KernelModule` it came from; the image is unloaded when the last of them goes, so no function handle outlives it.
- **Every driver call binds the context first.** The current context is per thread and the executor may run on a thread other than the one that loaded it. `Kernel::launch` binds its module's context, and the paths that make raw driver calls bind before them: descriptor encoding in the GEMM launches and KV maintenance. A plain launch happened to work without a current context on R580, but descriptor encoding fails with `CUDA_ERROR_INVALID_CONTEXT` (`tests/smoke.rs` launches all three from a fresh thread).
- **Every launch wrapper checks its kernel's limits on the host** and returns an error instead of launching. The checks cover divisibility (128- and 512-wide quantization groups), the alignment of every operand a kernel reads or writes in vectors (the fused QKV's buffers, strides and offsets, the gather's, both SwiGLUs' and the f32-scale quantization's rows and codes, the combine's, the placement's scratch), row and stride coverage, at most 256 experts and 8 per token, a router row of at most 4096, an expert layout holding every routed pair, whole GQA groups, a vocabulary of at most 2^20 for both sampling and acceptance, and whole rows in every array (`tests/mimo_preconditions.rs`). Device-resident indices (block ids, logit rows) are the executor's to keep in range; it builds them from the host mirror. CC 10.0 runs `sm_100a`, 10.3 runs `sm_103a`, any other 10.x runs `sm_100f`; a foreign architecture's cubin is refused, never JIT-compiled. `CudaExecutorConfig::image` can force the family image.

## DeepSeek-V4.1

`src/deepseek/` is DeepSeek-V4.1's module tree, the sibling of `src/mimo/`; it shares only the root modules (`device.rs`, `module.rs`, `launch.rs`, `kv_cipher.rs`, `sampler.rs`, `bf16.rs`). It holds the kernel ABI, the launch wrappers of every kernel image of the forward, and `DsCudaExecutor`, which launches them. Without a GPU, the executor is held to the CPU reference executor over a host device, both with the reference numerics and with the kernels' own bodies compiled for the host behind the wrappers' checks and grids (*Verification*); `scripts/deepseek_gpu_session.sh` is the one device session that runs every device test of this section (*The device session*). **On a GPU** (one B300): the executor without drafts has run the tiny scenarios equal to the CPU reference executor, and the released checkpoint has run one half at a time equal to the model crate's forward bit for bit. Drafting, the host tier, the memory scenarios and the invariance pass have run on the host only.

`deepseek/abi.rs` mirrors `eidola-engine-kernels`' `csrc/ds_abi.cuh` (normative; that crate's `AGENTS.md` → *The ABI* lists the structs and the decisions they fix) as `repr(C)` structs with device addresses as `u64`, the header's names without their prefix. `layout!` asserts each mirror's size, 8-byte alignment and every field's offset at compile time against the numbers the header asserts, so `cargo check` fails on a mirror that drifts; a launch wrapper additionally checks its kernel's `params_bytes`, as MiMo's do. `ProbeParams` and the `PROBE_*` ops are the numerics probe's (`eidola_ds_probe`): a device test replays the host vectors of the numerics header through it.

**The scalar kernels' wrappers** (`deepseek/ops.rs`: `DsOps` over the `ds_ops` and `ds_ops_div` images; `deepseek/gemm_ref.rs`: `DsGemmRef` over `ds_reference`; `deepseek/head.rs`: `DsHead` over `ds_head`). Each method takes its kernel's parameter struct, launches nothing for no rows, and otherwise runs the kernel's `*_grid` function first: a pure function that refuses a null or misaligned required address, a width that is not whole 32-wide blocks, a stride shorter than its row, a count past a kernel's limit (8 residual copies, 6 for the mix; 1,024 experts, 16 active), an unknown format, rotation or element type, a pool plane whose entries pass its block or whose codes and scales overlap, a layout too small for the worst placement of its pairs (`layout_rows_bound`), a non-zero reserved field and a grid past the driver's limits, and returns the grid the kernel's body is written for (`eidola-engine-kernels/AGENTS.md` → *The scalar kernels* lists them). The grid functions are unit-tested without a device. A wrapper cannot see a buffer's length or what a device index array holds: those stay the caller's (`unsafe`), as the ABI header says for each struct. Loading binds every entry by image and symbol and requires its launch contract's parameter size and block shape. `rot_quant` picks the entry by format (the global KV's divides, so it is in the other image); `place` is two launches over a `[groups]` scratch, with `expert_layout` its host form.

**Their device tests** are `tests/deepseek_ops.rs` and `tests/deepseek_gemm_ref.rs`, over the seeded cases of `tests/deepseek_cases` (inputs from one generator, outputs from the model crate's functions; the same cases whose digests the kernels crate's host check reproduces from the kernels' bodies). Each file has one device test, `device_suite`, which runs every check to its end whatever the others did and writes a JSON summary (`ds_ops.json`, `ds_gemm_ref.json`: the device, each check with its outcome and seconds, and the timings) under `EIDOLA_DS_SUMMARY_DIR`, else the test target's temporary directory; it fails if any check did. On both images: every kernel's 512 small cases and 2 at the released widths, every output bit and every byte around it; outputs written over their inputs (`rms_norm`, `expand`, `engram_inject`); a row launched alone against the same row in its batch, the other rows' outputs untouched (the quantiser, RMS norm, the mix, collapse, expand, the plain product, the head, SwiGLU, `lin8`, the grouped projection); a launch over no rows writing nothing; the four quantiser formats over every finite BF16 value beside neighbours within a few binades, and over blocks of zeros of both signs, the smallest values, both sides of each scale floor, exact scale boundaries and ties; the Engram path as a layer runs it (gather, quantiser from stored rows, `lin8`, injection in place) against `engram::inject`. On the device's own image only: each kernel at the released model's largest shapes over 64 rows (the whole vocabulary for the head over 9 rows and for the Markov head; 8,192 rows for the placement), checked and then timed (`us_per_launch`, `us_per_row`: launches enqueued back to back, wall time to the stream's end), and `bf16_round` and both casts over every f32 through the numerics probe against the committed digests. Without a device the same files hold the vector files current, build what the device suite builds for itself, and hold the injection's composed reference to `engram::inject`; `released_cases_are_built` (ignored: run with `--release`) builds every largest-shape case with its reference.

```sh
# One B300, a kernel build output (scripts/build-in-docker.sh, or the kernel image's files):
EIDOLA_ENGINE_KERNELS_DIR=<build output> EIDOLA_DS_SUMMARY_DIR=<dir> \
  cargo test --release -p eidola-engine-cuda --test deepseek_ops --test deepseek_gemm_ref -- --nocapture --test-threads 1
```

It prints one line per check (`ok` or `FAILED` with the first differing element), one JSON line per timing, and each summary's path.

**Attention, index scores and selection** (`deepseek/attention.rs`, `deepseek/index.rs`; the kernels and why each is batch-invariant: `eidola-engine-kernels/AGENTS.md` → *DeepSeek-V4.1 attention, index and selection*). Each is bit-identical to the model crate's function, so a wrapper has no tolerance and no host plan: it checks its parameter struct (`check_attn`, `check_window_slots`, `check_score`, `check_select`: shapes within the kernel's shared memory, slots and strides covering each other, mask words covering the score rows, alignment, null arrays) and launches over a grid that is a function of the row count and the configuration alone.

- `DsAttention::attend`: grid `(ceil(heads / g), rows)`. `heads_per_block` picks `g`: 1 while every block of the launch is resident at once (a decode row's 64 heads on 64 blocks), then 2, 4, 8, so a block's entries are dequantised once for several heads. No bit depends on `g` (`attend_grouped` takes it, for the tests and the bench).
- `DsAttention::window_slots`: the window part of the lists, in position or ring order.
- `DsIndex::score`: grid `(x, rows)` from the score rows' capacity and the row count (`score_grid`); how many entries a row sees is device data its blocks walk.
- `DsIndex::select`: one block per row.
- Host forms, for an executor's host mirror and the tests: `window_positions` / `window_slots`, `candidate_blocks`, `global_slots`, each the model crate's function (`ring_order`, `candidate_mask`, `top_k`) through a block table.

**GPU validation of the DeepSeek attention, index and selection kernels** (with the kernel build of the committed manifest). One command, unattended, a few minutes; it prints one line per image and test, the bench table (`timings_on_the_device`, which runs after the correctness test so a fault in it cannot take the device from that test), and the paths of `ds_attention_bench.json` and `ds_index_bench.json` (in `EIDOLA_DS_BENCH_DIR`). With `EIDOLA_DS_DIAG=1` a job that differs prints every differing output (how many bytes, where, the first of them) and the run goes on through the other jobs before it fails, which is what locates a device-only fault:

```sh
EIDOLA_ENGINE_KERNELS_DIR=<build output> EIDOLA_DS_BENCH_DIR=<dir> \
  cargo test --release -p eidola-engine-cuda --test deepseek_attention --test deepseek_index -- --nocapture --test-threads 1
```

**The quantised GEMMs on tensor cores** (`deepseek/gemm.rs`: `DsGemmTc` over the `ds_gemm_tc` image; the kernels and their exactness and batch-invariance arguments: `eidola-engine-kernels/AGENTS.md` → *DeepSeek-V4.1 tensor-core GEMMs*). `GemmForm` names the three forms of `lin8` and `lin4`: `Exact` (the scalar reference, `DsGemmRef`), `Banded` (tensor cores, exact block products: the reference's bits) and `Tolerance` (tensor cores, the hardware's block products). All three take the reference's parameter structs and layouts (weights as stored, the expert layout at any `row_align`), so a caller switches form without building anything else. `DsGemmSet` holds a half's reference and tensor-core images and runs `lin8` and `lin4` in its form. A tensor-core launch picks its block shape (`TokenTile`: the split block `S8`, 8 rows by 16 outputs, 256 threads, K shared out among its warps and the blocks' contributions added in order; tiles `T8` and `T32`, 128 threads) from the row count alone, and for `lin4` the group count: `TokenTile::for_lin8` and `for_lin4`, from the measurements below (`SPLIT_MAX_ROWS`, `SPLIT_MAX_ROWS_PER_GROUP`, `TOLERANCE_T8_MAX_ROWS`, `BANDED_T8_MAX_ROWS_PER_GROUP`). `lin8_tc_grid` / `lin4_tc_grid` refuse first what the kernels cannot take (operand arrays not 16-byte aligned, inputs not whole 32-wide blocks, a zero alignment, a non-zero reserved field, a grid past the driver's limits; unit-tested). **The executor's form** is `DsCudaExecutorConfig::gemm` (default `Exact`): building the executor hands it to both halves' devices (`Device::select_gemm`). `CudaDevice` takes every form; `HostDevice` and the tests' compiled bodies take `Exact` and `Banded` (the same bits) and refuse `Tolerance`; `DryDevice` takes every form and checks each launch against the reference's grid and both tensor-core forms'. The node keeps `Exact`. The GPU tests and the dev examples read the form from `EIDOLA_DS_GEMM_FORM` (`GemmForm::from_env`), and the session script's `ds_tiny_banded` and `halves_banded` steps run the executor with `Banded` against the CPU reference executor and against the exact run's recordings.

`tests/deepseek_gemm.rs` (`device_suite`, both images) runs the probe over every band pair of the banded form in four families of operands, then each product against the reference: the banded form byte for byte in every block shape, the tolerance form within its bound and the same bits in every shape, and a row alone against the same row in a batch, an expert's rows in a layout of only them against the full layout, in both forms. Cases are small random shapes (every grid remainder, layouts with empty groups at alignments 1, 3, 8 and 16) and the released dense and expert shapes from 1 row up (dense to 2,048 rows, experts to 2,048 tokens over all 384 experts), on model-like and on arbitrary codes. It fails if a banded pair's sum comes back inexact, if any element's bits move with its place in an MMA, if a banded output differs from the reference, or if a tolerance output is out of the bound; the unbanded probe counts are recorded, not required. `ds_gemm.json` holds every check, the probe's counts and first differing elements, and the tolerance form's histogram. `examples/deepseek_gemm_bench.rs` times every form per row count (1 to 8,192) at a dense shape (`wo_b`, 5120 × 8192) and the experts' gate and up (4608 × 5120, 384 experts, 6 a token, runs aligned to 8 rows), with TFLOP/s and the weight bytes read per second; `--all-tiles` times every block shape. The session script's `ds_gemm` and `deepseek_gemm_bench` steps run both (*The device session*).

**On a B300**: the suite passed on both images, 96 checks. The probe found every banded sum exact (8.59 billion dot products a case) and no element moved: the banded form is the reference's bits, and it equalled the reference at every shape. Whole blocks are not correctly rounded (the kernels crate's section gives the counts), so the tolerance form differs: over 21,284,807 `lin8` outputs 286 differed from the reference (266 by one BF16 unit in the last place, 9 by two, 5 by 3 to 4, 4 by 5 to 8, 2 by 9 to 16, none by more; largest relative error 0.071, largest error 0.0188 of its row's root mean square), and over 161,582,766 `lin4` outputs none. **The tolerance bound** is therefore 2 BF16 units in the last place, or 2^-10 of the row's root mean square for an output near zero after cancellation (every measured output was within it). **What limits them** (Nsight Compute, `ds_gemm_profile`; its clocks are lower, so ratios). Every decode kernel is latency-bound, neither memory nor compute. The earlier builds had 1 to 2 resident warps a scheduler (the split block's staging held it to two blocks an SM; the 8-row tile's 80 blocks for `wo_b` leave most SMs empty, 6 % achieved occupancy of 62.5 %), about 130 instructions a warp for every 512 bytes of weights (indexing, staging and per-element scale decoding; the MMAs were 2 %), and the banded form's conversions to 64-bit integers ran on the FP64 pipe, narrow on these parts. With the split block reading its operands from global memory the tolerance form's `wo_b` at 1 row executed 9.0 million instructions at 4.3 resident warps a scheduler, but stalled on long scoreboards (49 % of samples), at the instructions that combined loaded values (the scale bytes packed into one word, the FP4 halves into another) right where they were loaded: the next chunk's loads, issued early, were waited for at once. DRAM throughput was 11.6 %. The banded form's split block executed 31.9 million instructions (about 390 a warp for each 512 bytes: the band arithmetic of all eight columns of an MMA, of which one row is used at 1 row) and was issue- and dependency-bound (ALU 35 %, issue slots 39 %). For the experts at 1 token the split block (1,728 blocks over FP4 blocks of 256 bytes) executed 37 million instructions against the 8-row tile's 26 million, with the same load-combining stalls, and lost to it. The split block now keeps every loaded value in its own register until it is used, takes 2 blocks a warp per chunk in the banded form (4 in the tolerance form), and is held to three blocks an SM; that build has not run on a device. `ds_gemm_profile` in the session script profiles the GEMMs with Nsight Compute.

### The executor

`DsCudaExecutor` implements the seam for the window-chain model as the CPU reference executor does (`eidola-engine-cpu/AGENTS.md` → DeepSeek-V4.1: the same groups, ratios, devices and coverage, the chain, the token history, the drafter's group and draft width, the host tier, and the two pool sizes: `num_blocks` for the banks, `window_blocks` for the window groups), eagerly: every step is launched afresh and no graph is captured. `preflight` is the configuration checks alone (shape, spec, block layouts), with no device; `layout` is the whole executor with no checkpoint, for `DryDevice`.

| Module | Contents |
|---|---|
| `support.rs` | `check_supported`: the shape the executor splits a model by (`DsShape`), or the field that rules it out. The split and groups are the reference executor's; the rest is what the ABI fixes (widths in whole 32-blocks, ratio-2 pooling, 32-bit Engram rows, a selection or candidate pool published earlier on the same half). |
| `kernels.rs` | `DsKernels`: one method per kernel family the executor launches (24), taking its ABI struct. `CudaDevice` implements it by calling each family's wrapper, which checks the struct and picks the grid; `HostDevice` by the model crate's functions. |
| `half.rs` | `Device` (the quantised GEMMs' form, allocation, zero, upload, download, copy, the idle cipher, the sampler and chain acceptance, host-tier memory and its copies, the kernels) and `CudaDevice`: one stream of an opened device with the sampler and cipher images and the kernel images' wrappers (`DsOps`, `DsGemmSet` over the reference and tensor-core GEMMs, `DsHead`, `DsAttention`, `DsIndex`), each loaded and verified per half. |
| `plan.rs` | The step planner, pure: row order, per-layer row counts, the pooling pairs, window slot lists, the draft pass's rows and lists (`DraftPlan`), the expert layout's bound and placement. |
| `kv.rs` | Block layouts (`GroupGeometry`), pools, device block tables with a host mirror, `Zero` / `Copy` / `Encrypt` / `Decrypt`, the host tier (`Demote` / `Promote` / `ZeroHost`), position tags. |
| `weights.rs` | A half's weights in kernel layouts, and `weight_bytes`: the same sums as arithmetic over the configuration. |
| `model.rs` | A half (`HalfNet`): scratch, per-slot state, one model layer as launches, and the drafter (the pass, a slot's logits, the context KV). A feed-forward's routed part runs over a `Routing` (groups, group table, placement scratch, expert-major weights): the layer's own experts, or a staged half's cache. |
| `boundary.rs` | `ToEncoder`, `ToDecoder` and its check, `StepTransfer`. |
| `executor.rs` | The seam: maintenance, the step's order, drafting, sampling and acceptance, timings. |
| `host.rs` | `HostDevice`: host memory and every family computed with the model crate's functions. Tests only. |
| `staged.rs` | Dev-only (*The whole model on one GPU*): `ExpertIndex`, `plan_rounds`, `HostExperts`, `ExpertCache`, `DevOnly`, and the staged constructors. |
| `dry.rs` | `DryDevice`: no memory at all. Allocations are addresses, read-backs zeros, and a launch runs its wrapper's checks and grid only. With a half laid out without its checkpoint (`HalfWeights::load` with no store) it gives a configuration's device bytes by kind and whether every launch of a step is accepted, at any scale. |

**Two logical devices.** An `Encoder` half and a `Decoder` half each own a `Device`, their weights, pools, tables, scratch and state as separate allocations, and hand kernels only their own addresses. `DsCudaExecutorConfig::devices` names each half's ordinal: the same one twice is two streams of one GPU; two ordinals is two GPUs, with no other change (exercised by the two-GPU session, *The released model on two GPUs*, which has not yet run on a device).

**The boundary** is host values, staged through host memory both ways. Decoder → encoder: the Engram rows gathered from the tables the decoder's device holds, as stored. Encoder → decoder: the split layer's bank entry for every position (its stored bytes), and the residual copies with the collapse weights for exactly the rows the chain's bottom layer computes. `ToDecoder::check` refuses anything else before the decoder runs, and the tests hold each step's set equal to the reference executor's.

**Row order** (`plan.rs`). Kernels compute rows `0 .. rows`, so every launch group must be a prefix. A step's positions are ordered head rows first, then by the number of chain layers that compute them, descending, then in the reference executor's order. The head's rows, each chain layer's rows, the boundary rows and all positions are then prefixes, on both halves alike. A chain layer writes its window KV over the rows it computes and runs from its queries on over the rows the next layer computes.

**A step.** Maintenance and table updates (a host block outside the tier refused first); the draft pass of the rows that draft (*Drafting*); the decoder's device gathers its Engram rows; the encoder embeds, runs each layer before the split over every position (Engram injection, the attention input, the window KV write, a pooled source's entries, then queries, the selection where the layer runs its indexer, attention, the output projection, the routed and shared experts), then the split layer's bank stub; the crossing; the decoder stores the bank entries, runs the chain, writes the drafter's context KV, runs the head over the sampling rows and the drafted positions, and the sampler (`eidola_sample` over `sampleable_vocab_size`) or, for a drafting row, chain acceptance. Window slot lists are built on the host from the table mirror; the selection's part is written on the device.

**Drafting** is the seam's block-drafter contract as the reference executor implements it, on the decoder's device, before the forward. A row asking for `k` drafts at position `p` (never position 0, and only with its chain's top layer starting at its context) runs the draft blocks over the drafter's slots: slot `i` stands at `p + i`, slot 0 embeds the row's last token and the others the noise token, and each block's attention lists the block's context KV of the `window` positions before `p` in ring order and then the pass's own slots (`ATTN_PACKED`: the slots follow the last listed context entry). A pass's rows are slot-major with the widest rows first, so the rows drafting slot `i` are a prefix (`DraftPlan`). Slots are then sampled left to right **on the device**: slot `i`'s logits are the pass's base logits plus the Markov head over the Markov embedding of the token before it (the previous slot's tokens are read where the sampler left them, through `LinearParams::x_rows`), drawn by `eidola_sample` on the draft stream at position `p + 1 + i`, its distribution kept. The drafted ids are read back once: the encoder's device and the host's Engram hash need them, and that is the only host step of the chain (a few hundred bytes; a device Engram hash would remove it). The forward then computes `p ..= p + k` as ordinary positions, the head reads all of them, `eidola_sample` leaves the target's distributions there without drawing, and `eidola_chain_accept` accepts over them and the kept conditionals. The drafter's context KV is written for every position the chain's top layer computes: the means of the residual copies entering the drafter's target layers (those before the split cross the boundary as taps beside the rows the top layer computes) through `main_proj`, its norm and each block's window projection, rotated at the position. The spec reports the drafter's group and `max_draft_tokens` as the reference executor does; `draft_width: 0` is the model without its drafter.

**The host tier** (`host_blocks`) is one host allocation per group of whole block images, page-locked on a CUDA device (`cuMemHostAlloc`). `Demote` and `Promote` are one copy each, queued in maintenance order; a demoted block must be held encrypted (a plaintext one panics, as on the reference executor), so the host holds ciphertext and zeros only. `ZeroHost` is applied by the host once the device's queue has drained, before the step returns or before a later copy of the same step touches that block.

**Position tags** (`position_tags`) are a host record, per entry of every layer of every block, of the position whose KV it holds. They follow the bytes through `Zero`, `Copy`, `Demote` and `Promote`; every write sets one and every read checks it (a layer's window, every visible entry of the bank it reads, the drafter's context), so a step that reads KV no step computed fails with the group, layer and position: a chain layer's window before the layer's start, or a block mapped and never written. Four bytes of host memory per entry and layer; the tests run with them, and without them such a read is not detected (the mapping checks remain: an unmapped or encrypted block, a write to a shared block).

**Memory.** A block's image is the ABI's: per layer, planes of packed entries back to back, padded to 16 bytes; `Zero`, `Copy` and the cipher cover it as one range. The reference executor stores the same bytes entry by entry, and `GroupGeometry::cells` is that permutation, so plaintext blocks are compared byte for byte; ciphertext is not comparable (the two images order the keystream differently). Weights are copied as stored (FP8 codes with tile scales, `wo_a` included; BF16; f32; Engram tables as codes and scales), with three changes of shape: routed experts are laid out expert-major (each expert's gate rows then up rows in one array, down rows in another), norm weights are widened to f32, and an Engram module's two gate weights are kept as their product. An FP8 weight holding a NaN code is refused. Per-slot state is the pooled sources' open entries (the f32 projections of each slot's last `ratio + 1` positions), kept behind the step's rows of the projection scratch so a pair may name either; `ResetSlot` scrubs it. `DsCudaExecutor::memory` reports each half's bytes by kind.

`weights::tests` holds `weight_bytes` to these (the checkpoint's tensor headers) and to what the loader uploads for the fixture. On the device a half adds its RoPE tables and widened norms, the encoder the split layer's stub, and neither reads the image router bias. A drafting decoder holds the drafter without its confidence head (nothing reads it) and with its own copy of the embedding, 259,786,856,376 bytes of weights in all for sequences of 4,096 positions; without drafts the drafter is not loaded. A draft pass computes every slot whatever number of drafts its row asked for, so near the length limit its last slots stand past the last position a sequence holds: a drafting decoder's RoPE tables hold `slots - 1` positions more than `max_model_len` (`DsShape::rope_positions`), and a pass past them is refused. Nothing else of a pass is indexed by a slot's position: its own KV is scratch by pass row, its context is read at positions before the row's, and no pool entry, block table or tag is written for a slot.

**Scrubs.** The first rowless step after one with rows zeroes every scratch buffer in place, the drafter's among them (the per-slot state behind the projection scratch stays: `ResetSlot` scrubs a slot's). Dropping the executor zeroes pools, tables, state, scratch and the host tier first (best effort). The crossing's values are host memory for one step and are zeroed when dropped.

**Batch invariance.** A request's logits are the same bits alone or beside others: in any slot, in any blocks, in any bucket, in any row of the step, with its prompt cut into any chunks. Every kernel computes a row from that row's inputs alone on a grid that is a function of the row count and the configuration (`eidola-engine-kernels/AGENTS.md`), and the planner's row order changes which row a position is, never what it reads. The tests hold it through the engine on the tiny models (target rows and, with drafts, every draft slot's logits), and at the released scale in the halves example's invariance pass.

**Not supported.** Graphs. Batching: each encryption or decryption is its own launch, and each demotion or promotion its own copy. The drafter's confidence head.

### Verification

```sh
cargo test -p eidola-engine-cuda --lib deepseek::        # planner, layouts, arithmetic, refusals
cargo test -p eidola-engine-cuda --test deepseek_host    # the executor on the host device, about five minutes
```

`tests/deepseek_common` drives the real `Engine` over a pair: the executor under test and `DsCpuExecutor`, given the same steps, every step asking for logits. Each step must agree in tokens and their counts, in logits bit for bit at every sampling row and drafted position, in every draft slot's logits bit for bit, in the bytes of every plaintext block of every group (the drafter's included), in which blocks are encrypted, in the set that crossed (drafted ids and drafter taps included) and in the chain's work; the harness adds the engine's invariants, zero-on-free on the device's bytes, scrubbed state for free slots, idle blocks encrypted and mapped ones plaintext, free host blocks zero and held ones ciphertext. Every pair runs with position tags. Scenarios, on the committed fixture and on its window-of-80 configuration (a query's list spanning two 64-slot blocks): batched single requests, chunked against unchunked prefill around the chain's reach, one triangle for a long prompt, hits at regeneration, continuation and branch points with a required prefix admitted and refused, a sequence cancelled mid-triangle, preemption and resume, window pools far below the banks (a 700-position conversation through 38 window blocks with its continuation and regeneration hits, and concurrent sequences whose windows do not fit 17 at once, preempting), shedding to `KvExhausted`, a request alone and beside others (in another slot, larger buckets, other chunks, other rows around it), and randomized interleavings (on odd seeds over a host tier) drained to all-zero pools. With drafts: greedy speculation at every width `0 ..= slots` equal to plain decoding across acceptance patterns from every draft rejected to every draft accepted (the sampleable vocabulary narrowed to 3, 2 and 1 ids, the Markov term removed), seeded sampled speculation, sequences run to a length limit of 64 (passes whose slots stand past it), and every scenario above again with every slot drafted (the wide configuration with five slots, so the drafter's list spans two blocks). Memory, with drafts: idle KV of every group is ciphertext and a hit decrypts it bit-exact; a recomputed block of an `All`-coverage group reseals to the same bytes, beside another sequence and in other chunks; device pressure demotes every group's blocks to the host tier as the ciphertext they are, byte for byte, and the hit that promotes them is the reference executor's. Ciphertext is compared on the executor under test with itself, since the two block images order the keystream differently.

`tests/deepseek_host.rs` runs them on `HostDevice`. That checks everything of the executor but the kernels and the driver calls: the planner, layouts and images, weights, the step's order, the boundary, maintenance, state. What only a device shows: the entry points' placement of threads (warp shuffles, shared memory, `__syncthreads`), what the compiler emits, the driver calls, the two sampler kernels under the draft chain's row layout, and page-locked host memory.

### The released model, one half at a time

`examples/deepseek_halves.rs` (dev-only) runs the released checkpoint on the exact executor on one GPU, which holds one half and not both. Through the executor's own step path (`DsCudaExecutor::encode_half`, `decode_half`): the encoder half over real text in chunks, every position in the chain, recording the split layer's bank entry and the boundary row of every position and each layer's residual copies; then, the encoder freed, the decoder half teacher-forced from that recording, with logits at every position. The Engram table the decoder's device would hold stays off it: its rows are gathered on the host from the mapped checkpoint, as the boundary carries them. The reference is the model crate's `DsModel` on the CPU over the same tokens (the encoder layers and the bank stub, then the decoder from the recorded boundary); every layer's streams, the boundary, the bank and the logits are compared bit for bit, the first difference named by array, position and element, with top-1 and KL beside. `ds_halves.json` holds each half's memory by kind, load time, per-step times (the host gather, the layers' compute, and the read-backs, told apart by draining the device's queue before each read) and positions per second, and the comparison. Phases (`encoder`, `decoder`, `reference`) read what earlier ones left, so the CPU reference can run after the device is released.

**The invariance pass** ends each device phase: the text's first positions (`EIDOLA_DS_HALVES_INVARIANCE`, by default twice the chunk) run again in two other slots, in other blocks (one slot's in descending order), side by side in one step with the later slot's row first, one cut every third of a chunk and the other every two thirds. Every layer's streams, the boundary (or the logits) of both slots must equal the first run's bit for bit; the phase reports each array and the process fails on a difference.

**On a B300** the three phases ran over 555 tokens in steps of 96 with every one of the 45 compared arrays equal: both halves' layers, the boundary, the bank and the logits. The halves loaded in 148 s and 106 s, and a step of 96 positions computed in about 2 s on either half (about 21 ms a position a half on the exact kernels). The host gather of the Engram rows the decoder's device would hold reads the cold mapped checkpoint on 32 threads; on one thread it cost 4 to 15 s a step there, more than the encoder's compute. The invariance pass has not run on a device. What holds on the host: the whole flow on the fixture over `HostDevice`, equal to the reference, both invariance passes equal, a flipped recorded bit named exactly; and the released configuration laid out with no checkpoint on a `DryDevice` of one B300's memory, both halves over 555 tokens in steps of 96 and the invariance pass, every launch accepted by its wrapper (`cargo test -p eidola-engine-cuda --example deepseek_halves`). The example repeats that dry run before it loads a half. `deepseek::executor`'s `the_released_model_drafts_within_one_device_a_half` does the same for the whole executor with five drafts and a host tier.

### The whole model on one GPU (dev-only)

The released model (about 510 GB) does not fit one B300 (about 288 GB); production runs it on two. For development on one device, `deepseek/staged.rs` (only with the crate's `dev-staged-experts` feature) loads every half's weights except the backbone's routed experts (`HalfWeights` with `routed: false`: the arrays are not allocated and the layer's expert addresses are 0, so an unstaged launch over them is refused) and gives each half an `ExpertCache`: four device arrays of `capacity` experts in the expert-major layout, a host `ExpertIndex` of which (layer, expert) each slot holds, and its own group table and placement scratch (`capacity` words each, scrubbed with the half's scratch). The drafter's experts stay resident.

A staged feed-forward (`HalfNet::moe` with a backbone layer and a cache) runs the router, reads the selected ids back, and splits the rows into rounds of consecutive rows whose distinct experts fit the cache (`plan_rounds`; a row's own experts must fit, so `capacity >= active`). It runs the shared expert first; then per round the index admits the round's experts (a missing one takes the least recently used slot this admission does not use, a never-used one first), the misses are copied from host memory into their slots on the half's stream, the round's ids are rewritten to slot numbers, and the placement, both grouped products, the SwiGLU between them and the combine run over rows `first .. first + count` with `capacity` groups. The kernels are the production ones and every one computes a pair or a row from its own inputs, so the logits are the unstaged executor's bit for bit: only the weights' addresses, the layout's row order and the launches' row counts differ, all of which batch invariance already covers. An unstaged feed-forward runs `routed`, `shared_expert` and `combine` over all its rows, in that order. Each layer costs a read-back (a synchronisation) and the copies of its misses.

`HostExperts` holds the experts for the copies: read once into host memory in the device's order (`HostMode::Read`, on several threads each taking a contiguous run of experts, its rate recorded), or read from the mapped checkpoint on every miss (`HostMode::Mapped`). Plain, not page-locked, memory: a copy from it is staged by the driver.

## Qwen3.8

`src/qwen/` is Qwen3.8-27B's module tree, a sibling of `src/mimo/` and `src/deepseek/`; it shares the root modules, and in the fast profile MiMo's CUTLASS GEMM wrapper (`mimo::gemm::Gemm`), whose kernels it runs as they are. `QwenCudaExecutor<D: QwenDevice>` implements the seam for the hybrid model as the CPU reference executor does (`eidola-engine-cpu/AGENTS.md` → Qwen3.8): the same groups, state pool, tails, drafter rows, draft chain, canonical rewrite, taps and kept normed states, the same maintenance (`SaveState` included), and **state images byte for byte the reference executor's** (per DeltaNet layer its conv history then `S`, f32, then the tag; plaintext and ciphertext alike, since the cipher pieces are the same).

**Two profiles** (`QwenProfile`, fixed when the device is opened; one deployment runs one profile for every step, whatever the batch):

- **Exact** (the verification mode): every kernel equal to the model crate bit for bit, so the executor equals the CPU reference executor bit for bit through the scheduler, eagerly and replaying graphs.
- **Fast** (the serving mode): the FP8 linears on CUTLASS's blockwise tcgen05 GEMM (the checkpoint's BF16 block scales widened to f32 at load, exactly; the kernels' activation and weight layouts are its SFA and SFB), with its operands swapped up to 64 rows (below); the BF16 linears on CUTLASS's BF16 GEMM into an f32 scratch, rounded to BF16 by `eidola_qwen_round` (the head, the drafter's input projection), and the DeltaNet's `a` and `b` projections as one small-N GEMM of our own over their stacked weight (`eidola_qwen_fast_gemm_bf16`, below), its rows rounded straight into the recurrence's f32 `ab` rows; the gates in f32 (`eidola_qwen_fast_gate`: the hardware exponential where the exact gates take `det_exp` and an f64 division; within two BF16 units of them, asserted); attention by FlashInfer FA2 at head dimension 256 (`qwen/attention.rs`, below); and **the Gated DeltaNet in blocks** (below): its definition there is the chunked form of the recurrence over blocks at absolute positions, not the token recurrence. Everything else is the exact kernels. Its contract is reproducibility between calls: tokens and every logit's bits the same whatever shares the batch, however the prompt is chunked, decoded or prefilled, from a cache hit or fresh, eagerly or replaying a graph, at every draft width (greedy). That holds because every launch computes a row from its own inputs with a geometry that depends on the rows only through their count, CUTLASS's per-element arithmetic does not depend on M or on which of its FP8 instances a row lands in (asserted on the device, below), attention keeps MiMo's batch-invariant structure, and a DeltaNet position's output and every stored state are functions of the token prefix (below). Its distance from the exact profile is measured, not asserted: per GEMM (units in the last place) and per model (top-1, KL). The FA2 instances are compiled for 256-wide heads: the fast profile refuses a model with other heads.

**The DeltaNet in blocks** (fast profile; `QwenDevice::block_deltanet`, `dn_chunk`, `eidola-engine-kernels/AGENTS.md` → Qwen3.8 for the kernels and the definition). Blocks are `chunk` positions at absolute positions, `chunk` the block size's largest power-of-two divisor and at most 16 (`block_chunk`: 16 at the serving block size of 16), so every boundary the serving core stores a state at is a block's. A block's output rows are its chunked form from the state at its start, its tile always 16 rows with the positions after the block's present ones zero in every operand; a row reads only rows at or before it, so its bits are the same whether it is prefilled with the rest of its block, decoded with only the positions before it, or folded; the state is written only after whole blocks. So a position's output and every stored state are functions of the token prefix, whatever the chunking, the batch, a cache hit, decode or prefill, and the draft width, and the serving core's contract (a base at a boundary, the tail after it, snapshots at boundaries only, drafts never stored) holds as it is: every row starts from its base and recomputes its block's earlier positions from the tail, which is the lagging strategy (below), forced in blocks; a draft is a position after the host tokens, computed and never stored, and a block that drafts complete is updated in the kernel for the drafts after it and stored only when host tokens reach its end; `SaveState` is a fold of whole blocks. A decode row therefore reads its base and writes nothing until its block completes. Per DeltaNet layer: the preparation with `log_decay` (the per-position log decay where the token recurrence takes `α`), then `eidola_qwen_fast_dn_intra` and `eidola_qwen_fast_dn_state` over the pass's runs, each run's blocks numbered among the launch's (`DnSeq::tile`) in a scratch of `chunk_tiles(staged, runs)` blocks (`W`, `U`, `P` and factors per block and value head, the queries and keys rounded to TF32 per block and key head; the idle scrub zeroes it with the rest). The intra kernel's loops stop at a block's present positions, and the state kernel computes a row's output only where the row produces one, so a decode row's cost is its block's few positions and one read of its base. A run may store its live image only at a block boundary (`dense_logits` cuts its pieces at whole blocks). Its distance from the exact profile is measured: on the host, through `dense_logits` on the fixture (`blocked_deltanet_stays_near_the_reference_forward`), and per kernel against the token recurrence (in BF16 units from the exact kernel's outputs, and from f64).

**FA2 at head dimension 256** (`qwen/attention.rs`, `QwenAttention` over `flashinfer_fa2_sink_paged_d256`): MiMo's plan (`mimo::attention`'s `HostPlan`, `PassCaps`, `PaddedPass`, `PlanView`) at a largest query tile of 64 (the image has tiles 16 and 64), every layer a split at absolute multiples of 1,024 keys merged in chunk order, requests cut at multiples of 64 query positions, work lists walked by fixed grids, a sink of `-inf` per head. The target's pages are its blocks from position 0. The drafter's layer holds no KV at position 0 and attends from position 1, so its requests count keys from there: relative key `j` is position `j + 1`, a page is one position (page size 1: position row `o` of block `b` is page `b · 2 · block_size + o` of both planes, `drafter_page`), and the chunk boundaries and the 64-key cut fall at `1 + 64·m`, still a fixed function of the position. Every request's partial rows fit one pass (`plan::partial_rows`: the largest attention's rows times the chunks of `max_model_len + K + 1` positions).

**A step is one launch sequence over fixed scratch** (`program.rs`), reading every per-step value from one table of 32-bit words (`plan.rs`) filled by one host-to-device copy; nothing in it allocates, copies from the host, reads back or synchronises. The executor checks the rows and describes the step as a `StepPlan`: the drafter's passes, the one target forward (its rows, the DeltaNet sequences, the row copies (`eidola_qwen_copy_rows`, every index bounded by the kernel) that stage and keep the recurrence's inputs, the attention rows and FA2 requests), the head's rows, the sample rows and acceptance, and the copies that keep the drafter's states. **The target runs once a step**, over every row's host tokens followed by its drafts, so a drafting step reads the target's weights once, as an undrafted one does. That is possible because the serving core gives drafts only to a row of one host token `p`, and everything the drafts are a function of is known before the step: the token at `p`, the target's normed state at `p - 1` (kept by the slot's last row, or, after a resume, the tap of the block ending there), and the drafter's KV at positions up to `p - 1`. Its order: the status word cleared; **the lead drafter** (the drafter's row at each drafting row's `p`, then each chain depth over the previous depth's normed rows, each depth's drafts drawn on the device, Qwen's sampler on the draft stream, into draft lanes the next depth embeds); **the target** over `[t_c .. t_p, d_1 .. d_k]` a row (a DeltaNet layer's recurrence starts each row from its source, the slot's live image or its base buffer, folds the kept positions between the source and `context_len` from the tail, runs the host tokens, stores every named state write and the state after the host tokens into the slot's live image, as the kernel's `live_after` allows mid-run, and runs on through the drafts storing no state; every new position's inputs join the tail, and the drafts' KV goes into their reserved positions; the drafts reach the token array by one-word copies from their lanes over placeholders the table holds), and one head launch over every sampled row's last host row and every draft's row; **the trailing drafter**, the drafter's KV alone over the host positions of rows that do not draft (prefill rows read the target's normed rows of this very step, so they come after it; nothing reads their attention or MLP); plain rows drawn and drafting rows' target distributions and chain acceptance (Qwen's, below), into the read-back; the drafter's canonical KV at **every** draft's position (KV only: the projections, norm, RoPE and write); the normed rows into the boundary taps of every block ending in `c ..= p + k` and the slot's kept states. A rejected draft's drafter KV and tap are rewritten when that position is computed again, before anything reads them: the drafter reads keys at or before its own position, and a block is sealed only once its positions are committed. The drafts are the reference executor's to the bit: the same inputs (`eidola-engine-cpu`'s two target passes compute the same rows as this one, by row independence), the same draft stream at the drafted position, so nothing about the step's order enters them, and a row resuming from a snapshot, after a preemption or on its first decode step needs nothing carried between steps but the kept states and taps it already had. The step's one read-back is the status word and the tokens (and, for `return_logits`, the produced tokens' logit rows). `tests/qwen_host.rs` (`a_drafting_step_runs_the_target_once`) counts the FP8 linear launches of every drafting decode step on both paths: one target forward's, plus the drafter's.

**The DeltaNet's `a` and `b` projections** (`[v_heads, hidden]` BF16 each, 48 × 5,120 on the released model) are one weight on the device: `a`'s rows, `b`'s, then zero rows to a multiple of 8 (`weights::ab_rows`: 96 rows on the released model, so no padding; 16 for the fixture's 6 value heads). The exact profile reads it as the two matrices it holds, through the exact linear into BF16 rows that two widenings stage; the fast profile multiplies the whole stack at once (`QwenKernels::gemm_bf16`, into the head's f32 scratch, which `head_tmp` sizes for a forward's rows of it too) and one `eidola_qwen_round` writes its first `2 · v_heads` columns as BF16 values into `ab_new`, the layout the widenings write. The multiply is `eidola_qwen_fast_gemm_bf16` (`qwen_fast.cu`), not CUTLASS: CUTLASS's 128-wide output tile put the 96-row weight on one CTA (18 µs a launch at one row on a B200, 48 launches a step). It runs a warp per output and CTAs of four outputs by four rows (`small_gemm_grid`: 24 CTAs at one row, 384 at 64), lane `l` summing its 8-element chunks `l, l + 32, …` of K by fused multiply-adds from +0 and the lanes combined by an xor butterfly: one order for every output, which no row count, neighbour or position in a CTA enters. That form reads the weight once per four rows and each row once per output, which at a prefill's 2,048 rows cost 198 µs a launch on a B200; from `SMALL_TILED_ROWS` (128) rows the kernel's tiled form runs instead (`eidola_qwen_fast_gemm_bf16_tiled`, `small_gemm_tiled_grid`: a warp eight rows by four outputs, a CTA's four warps sharing their rows, so a lane loads each of its rows and weight rows once a chunk for 32 sums, two rows' sums a paired fused multiply-add, `fma.rn.f32x2`). Every (row, output) is summed in the same order and combined by the same butterfly, so the choice by row count leaves a row's bits its own (`small_gemm_forms`, on the host bodies and on the device). `CudaDevice::gemm_bf16_form` runs either form at any row count (the tests, the bench); `CudaDevice::gemm_bf16_cutlass` keeps the CUTLASS form for the bench.

**The FP8 GEMMs by row count** (`cuda::fp8_kind`, over the `m_pad` rows the scales are laid out for): up to 16 rows CUTLASS's blockwise kernel swapped at an activation tile of 16 (`GemmKind::Fp8Swap(SwapTile::T16)`), up to 32 at 32, up to 64 at 64, above that the unswapped kernel (`Fp8Blockwise`, prefill's 2.2 PFLOP/s). The swapped instances (`cutlass_fp8_blockwise_swap`, `eidola-engine-kernels/AGENTS.md` → Qwen3.8) put the weight's rows on the MMA's 128-row side and the activation rows on its narrow one, so a decode-size step neither promotes a 128 × 128 accumulator per K block for one real row nor spends half of each pipeline stage on activation rows that are not there. They read the same arrays as the unswapped kernel; their Params are built by `mimo::gemm` like the others' (CUTLASS's problem `(N, M, K)`, its SFA the weight's scales with the layout `((128, N/128), (128, K/128))`, its SFB the activations' with `((1, M), (128, K/128))`, D's descriptor over `[N, M]`), pinned against CUTLASS's own host path by `tests/mimo_cutlass_params.rs`. Choosing by row count is admissible only because a row's bits are the same in every instance it can land in: `tests/qwen_ops.rs`'s `fast_fp8_configs_agree` runs each of the four over 300 rows and over rows alone and in batches at several offsets, and the dispatch either side of each boundary, against the unswapped kernel's batch, bit for bit. If a GPU ever shows them differing, the fix is one instance for all row counts, not a narrower test. `CudaDevice::lin8_on` runs any of them by name (the tests, the bench).

**The quantiser and the norms** run in both profiles and are exact. The quantiser is a warp per 128-wide block (`eidola_qwen_quant`: four elements a lane, the lanes' amaxes combined by a butterfly of shuffles, then each lane's codes) and one row a CTA at decode sizes, or four rows a CTA, every row's load issued before any row's arithmetic, once that still leaves 1,024 CTAs (`quant_grid`: grid `(⌈K/512⌉, rows)` or `(⌈K/512⌉, ⌈rows/4⌉)`, the kernel reading its rows a CTA as `⌈rows / y⌉`; four rows a CTA at every size had cost a decode launch 6 to 8 µs on a B200 against 2.2 at one), bit for bit its reference form `quant_thread` (one thread per block). Its arithmetic is the reference's without branches (the reference's own branches and per-element division cost 40 µs a launch at 2,048 × 5,120 on a B200, about ten times its memory time): the amax on the BF16 magnitudes' bits as integers, a NaN's as 0 (for magnitudes the bits order as the values, so this is `max32`'s fold from +0 in any order); each code `e4m3_code` (`ds::e4m3_encode` without a branch, equal to it over every f32); and each quotient a product with the scale's reciprocal (rounded once) wherever that gives the reference's code, which is everywhere but within 8 units in the last place of an E4M3 midpoint, between 2^-11 and 2^-6, or under a scale that is not a normal number, where a lane divides as the reference does (the bound is in `qwen_ops.cuh`). The norm (`eidola_qwen_norm`) stages a unit's inputs (after the residual add) in shared memory before its 16 serial sums, which then read them at shared-memory latency in the reference's order; a unit wider than 1,024 (the hidden norms) takes a CTA, narrower units (the query and key heads, with RoPE) a warp each, eight a CTA (`norm_grid`: `(units, rows)` or `(⌈units · rows / 8⌉, 1)`); each thread moves 16-byte vectors where the unit's strides and arrays allow, issuing a batch of three vectors' loads (a 5,120-wide unit's whole share, one round trip a phase at decode sizes; or eight elements') before any store, in 48 registers, so five CTAs fit an SM (holding a thread's 32 elements at once takes 122 registers, two CTAs an SM, and measured 77 to 87 µs a launch at 2,048 rows on a B200); a unit is at most `NORM_MAX` (8,192) wide. The DeltaNet's gated norm (`eidola_qwen_dn_norm`) is a warp a (row, head), four a CTA (`dn_norm_grid`: `(⌈heads · rows / 4⌉, 1)`), a head staged in shared memory four values a lane, so a head is at most 128 wide (`dn_norm_grid` refuses more, as `dn_rec_grid` does); its cost at prefill sizes is its f64 SiLU. The widening (`eidola_qwen_widen`) takes eight elements a thread, a 16-byte load and two 16-byte stores where the rows allow. Each of these has a plain form beside it in `qwen_ops.cuh`, its reference form (a thread or a CTA a unit), which the host check and the device test hold it to bit for bit (`norm_forms`, `dn_norm_forms`, `widen_forms`, `quant_sweep`).

**Staging the recurrence as data.** Each run's staged positions (its folds, then its new positions) and conv rows (three history rows, the folds, the new rows) are compact and consecutive; the kernels read them through the sequences' `first`/`count`, the `window` array and the copies' items. Images are laid out a whole number of conv rows apart (`image_stride` a multiple of `lcm(256, 4 · conv_dim)`), so any image's conv history is rows of one buffer per layer; the tail is per DeltaNet layer `[slot][capacity]` rows (`tails_conv`, `tails_ab`), so a copy's rows do not depend on the layer either. The recurrence's outputs of the new positions are gathered to token rows for the gated norm. A layer costs three widenings in the exact profile (the conv inputs, `a` and `b`) and one in the fast profile (the conv inputs), and two row-copy launches besides the kernels: the staging of conv and `a`/`b` rows before the recurrence, and their keeping and the outputs' gathering after it.

**The grouped row copy** (`eidola_qwen_copy_rows` in `qwen_ops`, `CopyParams`): up to three groups in one launch, each MiMo's row-copy arguments (eight buffers of rows of its width, and the items' source and destination buffer and row as table words), a block an item of the groups in order, sixteen bytes a thread when both rows are aligned to them and word by word otherwise. Every buffer and row index is bounded (an item out of range copies nothing and raises `STATUS_BAD_INDEX`, bit 4), and an item copying a row onto itself copies nothing: the inert self-copies that pad a rung's lists cost a launch nothing but their blocks' first loads. The host device copies the same items in order.

**The recurrence's two forms** (`qwen_deltanet`): the general form (`eidola_qwen_dn_rec`) stages each chunk of 8 positions while the block runs the last one and keeps a thread's share of the chunk in registers, 135 registers and three blocks an SM; the short form (`eidola_qwen_dn_rec_short`) runs the same steps on the same grid, staging each chunk before it runs and reading the sequence record where it is used, bounded to 80 registers and six blocks an SM, so twice the state is in flight. At a decode step the recurrence is the state's traffic (at 64 rows of the released model, 201 MB a layer read and written), which three blocks an SM left at about half the bandwidth. Both compute every value with the same functions in the same order; `program.rs` takes the short form when the launch's runs average at most 8 positions (`DN_SHORT_RUN`: a decode step's, a draft check's), a choice of the launch's shape alone. `tests/qwen_kernels_host.rs` and `tests/qwen_ops.rs` (`dn recurrence`) hold both forms to the model crate.

**Sampling** (`qwen/sampler.rs`, `qwen_sampling` in both profiles): the serving core's `sampling` bit for bit, as the shared sampler is (`eidola-engine-kernels/AGENTS.md` → Qwen3.8), in four launches a sample over a work area of `SAMPLE_WORK_ROW` bytes a row (the program's `sample_work`): the argmax, the exponentials by chunk blocks and each chunk's pinned sum, the division by the chunk sums added in order and a histogram of p's top bits, then per row the selection: top-k, top-p and min-p keep a prefix of the order (p descending, id ascending), gathered as the keys at or above a threshold the histograms find (at most 2,048 candidates) and run through the reference's own steps over them, the masses of rank prefixes being their pinned sums in id order. The shared sampler's bitwise searches over the whole vocabulary (a pinned sum a step, its chunks summed one thread each) cost 14.5 ms a sampled row on a B200. Chain acceptance is three launches (the accept tests a thread a sequence; the pinned chunk sums of the one distribution each then draws from, a block a chunk; the draw, scanning one chunk) over `ACCEPT_WORK_ROW` bytes a sequence (the program's `accept_scratch`). The vocabulary is at most 262,144 ids (`sampler::MAX_VOCAB`; `sample_check`, `accept_check` refuse more, on both devices). A top-p row whose nucleus passes 2,048 ids, a top-k past 2,048 and a top-k at or past the vocabulary alone take the bitwise search, exact and slow.

**Decode graphs** (`QwenCudaExecutorConfig::graphs`, `CudaGraphs::On`/`Off`; `set_decode_path` chooses `Eager`, `Direct` or `Replay` for tests and measurement; `decode_stats` counts steps by path). The rungs are MiMo's `draft_ladder` at draft width 0 and, when drafting, at `K`. A rung's shape is an all-padding step's (`rung_shape`) with room for the variable lists of any step that fits it (folds up to `K` a row under the live strategy, `tail_capacity` under the lagging one; state writes; taps); a drafting rung's target forward is `1 + K` rows a sequence, one FA2 request each, and its lead drafter one row a sequence per depth. Its layout fixes every array's offset, and all rungs share one fixed table. A **uniform decode step** (every row one host token, sampled, the rung's draft width, and with drafting `c ≥ 1`) is planned with padding rows up to the rung and packed into its layout; one that does not fit (a fold past the rung's room) runs eagerly. A **padding row** is the padding slot (past every slot the seam names: its live image, tail and kept states) at position `K`, its KV written and read in each pool's pad block (past every block id), its recurrence from the zero state storing nothing the seam sees, its draws greedy over its pass's logit row 0, its tokens never returned, and it keeps no tap or state. With graphs on, construction captures every rung: the all-padding step packed, run directly (checking its status), captured, replayed once; a capture failure refuses the construction. Every rung's all-padding step is packed at construction on any device. Maintenance (`Zero`, `Copy`, the cipher, the host tier, `SaveState`, which runs the fold alone over its own table) stays eager before the table's upload. Replaying a capture computes what running its launches directly computes; against the eager path every real row computes the same bits (row-local launches, M-independent GEMMs, batch-invariant attention, padding confined to the pad block and slot), which the tests assert across paths.

**Scratch** is sized once (`capacities`): the largest bucket's tokens and rows, every slot's drafts, the rungs' padded lists, the exact attention's scores at a fixed stride of `max_model_len + K + 1` (exact profile only: a row's scores whatever its position, so a captured launch serves any context), FA2's partial rows (fast profile only). The eager path's table grows as a step needs; the rungs' is fixed. **The idle scrub**: the first rowless step after a step with rows zeroes every scratch buffer, both tables, each pool's pad block and the padding slot's state, in place (`idle_scrubs` counts them).

**State strategy** (`StateStrategy`): `Live` (the default) keeps a live image per slot at its last row's host-token end, so a row folds only the drafts accepted since; `Lagging` loads the base and folds the whole tail every row, as the reference executor does. Both store the same bytes; `Lagging` is for measurement (`EIDOLA_QWEN_STRATEGY` in the real-weights example). With the DeltaNet in blocks (the fast profile) every row is lagging whatever the configuration names, and no row stores a live image: a state exists at block boundaries only.

**Devices** (`QwenDevice`): `CudaDevice` (one GPU, the images verified against the manifest: Qwen's four (`qwen_ops`, `qwen_ops_div`, `qwen_deltanet`, `qwen_sampling`), the cipher, and in the fast profile the CUTLASS GEMMs, `qwen_fast`, FA2 and the blocked DeltaNet (`qwen_fast_deltanet`); graphs captured on its one stream) and `HostDevice` (host memory, each launch handed to a host function after its grid function: the tests give it the kernels' own bodies compiled for the host, `oracle/qwen_launch_host.cc`; the row copy, the sampler and chain acceptance are its reading of those kernels, `eidola_engine::sampling`; the recurrence's short form runs the general form's host body; it captures no graphs, so the rung path runs on it directly). `HostDevice::planning_fast` plans as the fast profile does and checks each FA2 launch without computing it; `HostDevice::block_deltanet` computes the exact profile but for the DeltaNet, which runs in blocks (the intra kernel's body, the state kernel's host form, whose tensor-core K-steps are its own reading), so the blocked form goes through the real scheduler without a GPU. Every family's `*_grid` function refuses what its kernel cannot take before anything launches.

**Not yet**: device-side page lists (the host derives each row's pages from its mirror and uploads them; the drafter's are a word a position, the target's a word a block), piecewise capture of prefill and mixed steps, a staging kernel fusing the row copies into the recurrence's own loads, FA2 decode with chunks shorter than 1,024 keys (the chunk is MiMo's plan's `SPLIT_KEYS`, and a shorter one multiplies the partial rows a prefill pass needs), a split-K form of the narrow FP8 GEMMs (N = 5,120: `o_proj`, `down_proj`, the DeltaNet's `out_proj`, 40 CTAs at decode sizes on the swapped kernel; a split fixed by (N, K) for every row count, the unswapped kernel's prefill included, so a row lands in one summation order whatever its batch). ## The dev-only oracle

`oracle/cutlass_params.cu` is a host program that `#include`s the kernels crate's three CUTLASS translation units, so its types are the AOT kernels' types, runs CUTLASS's `to_underlying_arguments` / `get_grid_shape` / `can_implement` for a list of shapes and fake addresses, logs every `cuTensorMapEncodeTiled` call, and prints the Params bytes with a mask of the bytes CUTLASS defines (padding is found by building the struct three times over different stack contents). Its output is `tests/data/cutlass_params.jsonl`. It is compiled with any CUDA 13 toolkit and the pinned CUTLASS tree on a GPU host (descriptor encoding needs a context); the command is in its header. Built with `-DEIDOLA_ORACLE_NO_DRIVER` it runs with no GPU and no driver, inside the kernel build's own toolchain (`nix-shell crates/eidola-engine-kernels/nix` in the pinned `nixos/nix` container on the kernels' store volume): every encode call is still logged, the descriptors it returns are zeros, and each record says `"driver":false`; outside the descriptors its bytes are a GPU host's (it reproduces every driver-encoded record that way). The swapped FP8 GEMM's records come from such a run. Never part of the engine. Regenerate it when the CUTLASS pin or a GEMM instantiation changes.

**Construction order is structural.** `CudaExecutor::new` checks, in order:

1. the configuration (and the MTP layers for the draft width), the sampleable vocabulary and the context;
2. the KV geometry (`GroupGeometry::validate`: every product in checked `usize`, a block within the 32-bit page stride, block ids within the `i32` tables) and the resulting `ModelSpec`;
3. the device;
4. it loads and verifies every kernel image.

Steps 1 and 2 need no device: `CudaExecutor::preflight` runs exactly them (the same code `new` runs) from the checkpoint's `config.json` and returns the `ModelSpec`, so a host can refuse a configuration on a machine without a GPU and size its KV pools from the spec's groups (the inference node does both).

Only then does it move weights. The idle-KV cipher's image is loaded and verified with the others, before the weights and the KV pools. `ModelWeights::load` takes the loaded `Kernels`, so no weight can reach the device first, and a wrong device, image or kernel directory fails in about a second instead of after the checkpoint has filled the GPU (`tests/mimo_construction.rs`, whose preflight test runs without a device; it also refuses a kernel directory holding every image but the cipher's before any weight is read). Scratch sizes are computed with checked arithmetic, all of them before any allocation.

## The executor

- **Seam.** One step, validated whole before any of it takes effect: the maintenance and table updates are staged (`KvStore::stage`: checked, and the tables they lead to computed, with nothing applied), the rows are checked against those staged tables, and the forward's input against the model (`GpuModel::check_input`); only then is the staged work committed (`KvStore::commit`: memsets and device-to-device copies on the stream, dirty table rows uploaded), followed by the forward over every host token and sampling on the device over `sampleable_vocab_size`. A malformed step panics or errs with the device and the mirror as they were. Block tables live on the device and change only through the seam; the host mirror is what plans attention and checks the contract.
- **Safe entry points check their host indices.** `GpuModel::forward` runs `check_input` first: tokens inside the vocabulary, positions inside the RoPE tables, logit rows inside the step, KV targets inside their pools (never the null block), and each plan's page size, query rows and largest page against its group. `Sampler::sample` takes its rows on the host and bounds every logit row before uploading them; `chain_accept` does the same for its plan. Everything else that launches takes raw pointers and is `unsafe`. Types that carry launch indices are built only by their checking constructors: `HostPlan`'s fields are private and it carries the group and page size it was checked for (`HostPlan::new`, then `Attention::upload`, which takes nothing else), and `GpuModel` is built only by the executor, its weights and KV layout readable but not replaceable. A step's bucket must be one of the configured ladder's, exactly, or the step is refused before anything is staged.
- **Contract checks**, as in the CPU reference executor, before anything is launched: a write into a block mapped by more than one table entry, a read through an unmapped entry, positions disagreeing with `context_len`, drafts at position 0, more drafts than depths, drafts on a row that does not sample or has more than one host token (the serving core drafts only decode rows; see *Drafting*), and a drafter row with no state to continue from (neither the slot's own state at `c - 1` nor a block boundary's tap), panic.
- **Memory.** One pool per KV group, in the canonical order (global, then sliding, then the drafter's when drafting) whatever the layer selection. Each pool holds `num_blocks` blocks plus one **pad block** (`GroupGeometry::pad_block`, id `num_blocks`): outside every id the seam may name, so no table maps it and no maintenance reaches it; only padding rows of a decode graph write and read it (*Decode graphs*). Capacities are keyed by kind (`KvBlocks { global, sliding }`), never by position; a group no retained layer uses must be given no blocks. Scratch is sized from the retained layers: a dense-only selection allocates no expert buffers, an expert-only one no dense ones. Block `b` holds every layer's K `[block, kv heads, 192]` then V `[block, kv heads, 128]`, BF16, contiguous, so `Zero` and `Copy` are single ranges and paged attention addresses a layer with page stride = the whole block. Per-slot model state (`state_width`) is scrubbed by `ResetSlot`; it is empty without drafting (*Drafting*).
- **Idle encryption.** `Encrypt` and `Decrypt` (`eidola-engine`'s privacy invariants: idle KV is ciphertext) XOR exactly the bytes `Zero` clears with the block's ChaCha20 keystream: its pieces in `GroupGeometry::block_ranges` order (a target block's one range; a drafter block's rows in each layer's K and V planes, then its tap), each as little-endian words from a fresh keystream block, which is `eidola_engine::kv_cipher`'s image rule. `stage` refuses a block named by two of them in one step, a copy of a block one of them names, a zero (or a promote) listed after one of them, and a key index the step lacks; `commit` turns each run of consecutive ones into one `eidola_kv_chacha20` launch (`KvCipher::apply`, `unsafe` like every launcher taking raw device ranges: each range inside one live allocation until the launch completes, no two overlapping; `commit` meets that from the staged block ranges), queued in maintenance order on the step's stream, so every decryption completes before the forward reads. The keys reach the device only in that launch's item list: uploaded from a host list that is scrubbed once the copy returns (a pageable copy has left it by then), and zeroed on the stream right after the launch. That host list is a `CipherItems`, sized for the step's operations up front and scrubbing any allocation it grows out of, because a growing `Vec` frees its old buffer with the keys in it (`kv_cipher.rs` tests the growth path). Every other place a key lives in growable host storage holds `KvKey`s, whose bytes sit in their own zeroizing allocation, so a `Vec` of them moves only pointers. The executor keeps no key between steps. Not covered: the driver's staging of that upload (inside the encrypted VM under confidential computing), and keystream words in registers, which later kernels overwrite. The item list is the one device allocation that grows (to the largest step's item count, 64 bytes an item, a power of two), well inside `DEVICE_FIXED_RESERVE_BYTES`.
- **Idle scrub.** A step leaves its working data on the device: the model's scratch (token ids, positions, KV targets, the residual stream, QKV, attention outputs, routing, logits, split attention's partials), the sampler's (rows, f64 distributions, tokens, status), the drafting buffers (levels, the target's hidden states, distributions, read-back) and the eager drafted step's table, the decode and drafted graphs' step tables and read-back, and every pool's pad block (with drafting, padding rows write KV from drafts taken greedily from real row 0's logits). The first step with no rows after a step with rows (the maintenance-only step the node runs when the engine goes idle, `Engine::flush`) zeroes all of them in place once its maintenance has run, and waits for it (`CudaExecutor::residue_ranges`; `idle_scrubs` counts them); later rowless steps (sweeps while idle) do not repeat it, and steps with rows never run it. In place, because the graphs captured these addresses; nothing a real row computes reads their earlier contents, so the scrub changes no bit. Not listed, and why: the KV pools' other blocks, the taps and the per-slot state are the seam's (zeroed, encrypted and reset by maintenance); weights, RoPE tables and the MTP copy lists are constants; the cipher's item list is zeroed behind every launch; the eager path's attention work lists are allocated per step and freed (page ids and lengths, the information the persistent block tables also hold); the host tier holds only ciphertext; host-side copies (the step's inputs, read-backs) are the host's. **On drop** (`impl Drop`, also what `CudaExecutor::scrub_device` runs) the executor zeroes every one of those buffers and its whole KV store (pools with any live plaintext KV, taps, state, tables) before the memory is freed, which is when the node's worker drops an engine whose executor failed; best effort, since on a failed context the memsets fail too.
- **Host tier.** `CudaExecutorConfig::host_blocks` (`KvBlocks`, keyed by kind like the device pools; all zero, the default, for none) gives each group a pool of block images in page-locked host memory (`KvStore::set_host_tier`: one `cuMemHostAlloc` per group, so the kernel never pages it out and the copy engines can reach it; zeroed when allocated). A host block's image is the device block's `block_ranges` pieces back to back. `Demote` is one `cuMemcpyDtoHAsync` per piece and `Promote` one `cuMemcpyHtoDAsync` per piece, on the step's stream in maintenance order, so a demote reads its block before the zero queued after it and a promote lands after the zero before it and before the decryption that follows it; `stage` refuses a demote of a block an earlier operation of the step changed, a promote into a block after its encryption or decryption, and a host block outside the tier (or the null one). `ZeroHost` is applied by the CPU once the stream drains (`KvStore::finish_host`, which `execute` calls before returning), so it never races a copy still reading the block and a host block is zero before any later step can write it. That deferral equals maintenance order only while every host zero comes after each copy of its block, which the core's order gives (host zeros last); `stage` refuses a demote into or a promote from a host block listed after its zero. A step may otherwise name one host block several times (demoted into twice, demoted and then zeroed or promoted from): the core reuses a host block it frees mid-step, and those orders mean the same in stream order as sequentially. The core only ever moves ciphertext through these, and nothing else reads a host block (`read_host_block` is a test aid). Under confidential computing each copy goes through the driver's encrypted staging buffer, so the host sees its size and timing (about a block per piece, so about a prefix's length per hit), never its bytes. The copies are on the step's critical path when they happen (the core demotes under pressure, inside the step that needs the room); a demotion running ahead of pressure on a second stream is a possible follow-up once the bench shows what they cost.
- **Forward** (`model.rs`): f32 residual stream; per layer RMSNorm → FP8 (f32 per-128 scales) → fused-QKV FP8 GEMM (BF16) → RoPE (host-computed tables, bit-identical to the reference's) + KV write → FA2 attention → `o_proj` BF16 GEMM with the value scale as alpha (f32) → residual; RMSNorm → dense SwiGLU (FP8 GEMMs) or experts: router top-k in f32, in the form the step's token count picks (`executor_router`; `ROUTER_PER_TOKEN_MAX`'s comment records why): up to 15 tokens one cluster launch, an 8-block cluster per token; above that two launches (every (token, expert)'s score from blocks of 8 tokens × 16 experts into a scratch buffer, then one warp per token selecting), expert-major placement (DeepGEMM's psum layout, sized for the worst case so nothing is read back: *Expert layouts*), FP8 with power-of-two per-128 scales (DeepGEMM's recipe), two grouped GEMMs, weighted combine in ascending expert order → residual. The gather launches one block per token and 512-wide word (stored into the rows of the token's pairs) and the expert SwiGLU one block per routed (token, slot) pair and 1024 elements, addressing rows through `row_of`, so their cost follows the token count rather than the layout's row bound (every pair plus up to 127 padding rows per expert reached); they leave padding rows unwritten, which reaches only padding outputs (`eidola-engine-kernels/AGENTS.md`, *The decode path's small kernels*). The fused-QKV kernel and the combine run a thread per 8 elements of a token, so neither puts a token's whole row on one block. Head: final RMSNorm of the wanted rows → BF16 → `lm_head` BF16 GEMM, f32 logits.
- **Weights** (`weights.rs`): the checkpoint must hold exactly the tensors the loader reads for the retained layers and the draft depth (`expected_tensors`: sinks only on layers with sinks; MTP layers `0..k` with `k` drafts), besides the families it skips (`SKIPPED_PREFIXES`: `visual.`, `audio_encoder.`, `speech_embeddings.`; `MTP_PREFIX`, `model.mtp.`, without drafting, and MTP layers from `k` on with it) and the unselected layers; anything else, and anything missing, is a layout error before a tensor is read (`check_layout`; under a read MTP layer an unknown tensor is refused like any other), and the loader's own reads are checked against the same set. An MTP layer is loaded like a sliding target layer with a dense FFN, plus `enorm`, `hnorm`, `final_layernorm` (f32) and `eh_proj` (BF16, as stored). Copied as stored; only scale grids are re-laid-out. The fused QKV stays rank-major with each chunk padded to whole 128-row tiles, which turns the checkpoint's per-chunk scale tiling into an ordinary grid; dense gate/up are stacked; experts' gate/up rows are stacked per expert and their E8M0 scales packed into DeepGEMM's SFB words.
- **Chain acceptance: host plans and device drafts.** `Sampler::chain_accept` takes each row's drafts and distribution rows as host values (`AcceptRow`), bounds every index the kernel derives from them (k drafts plus the bonus token within the row's output, target and draft rows within the distributions and within `u32`, draft ids within the vocabulary; `AcceptPlan`, which needs no device), and refuses two rows naming different ids for one draft distribution row (the kernel reads a draft id at its distribution's index, so a draft is the token drawn from that row and rows may share one only with the same ids), and only then uploads them into `AcceptInputs`, which nothing else writes (the tests' path). A drafted step's drafts are made on the device and never reach the host, so their ids are bounded by the kernels instead: `eidola_sample` writes no id at or past the sampleable vocabulary (it cannot produce one: every argmax and draw is below it; it would write 0 and raise `STATUS_BAD_TOKEN`), and `eidola_chain_accept` checks every draft id before reading through it (`STATUS_BAD_TOKEN`, the row ending with no tokens); a step that raises the bit fails. The row and distribution indices of a drafted step are the planner's (`Sampler::launch_accept`, `draft_step` the drafted step's row count: one depth's drafts of every row together).
- **Two paths, one launch sequence.** `GpuModel::launch` is the forward's launches from the embedding to the head, reading every per-step value through device addresses (`Indirect`); the eager path (`GpuModel::forward`) uploads its inputs into scratch and calls it, and the decode graphs record it over their step table. Without drafting, prefill and mixed steps run eagerly and pure-decode steps replay a graph when graphs are on (*Decode graphs*); with drafting every step is a drafted step (*Drafting*), uniform drafted decode steps replaying a graph.

## Drafting

`CudaExecutorConfig::draft_tokens` (`k`, 0 to 3) drafts with MiMo-V2.6-Flash's MTP layers, depth `d` served by MTP layer `d`, exactly as the CPU reference executor does (`eidola-engine-cpu/AGENTS.md` → MTP row layout, which the seam makes normative): depth `d`'s row at `s` consumes the token at `s` and the **target's** hidden state at the anchor `s - 1 - d`, uses RoPE position `s - 1 - d`, writes its KV at `s`, and predicts `s + 1`; the draft for `p + 1 + i` is depth `i`'s prediction at `p + i`, every depth anchored at `p - 1`. No depth reads another depth's output: that is the vendor's serving convention (SGLang's multi-layer MTP worker, non-chained for MiMo; the CPU AGENTS cites it), and a DeepSeek-style chain was measured to make depths 2 and 3 nearly useless on Flash (*Numerics* → acceptance). `MtpHidden` (`Normed`, the default, as vLLM and SGLang feed; `PreNorm`, as llama.cpp) chooses which of the target's states that is; acceptance on the GPU against the vendor's serving stack is what settles it (`eidola-engine-model/AGENTS.md`).

**One step, no host round trip** (`draft.rs`'s module docs give the order): every row's levels at `c - 1` are loaded (level `l` at `x` is the target's state at `x - l`), from the slot's state or a block boundary's tap; for each drafting row the depths run at `p` and along the chain (`p + 1 ..= p + i` at depth `i`, every row anchored at or before `p - 1`, so on loaded levels), each depth's logits at `p + i` sampled on the device into draft `i + 1` (`Stream::Draft`, the argmax for greedy rows); the target runs **once** over every row's host tokens and drafts (a drafting row has one host token, so nothing its drafter needs comes from this step: this is the one-pass ordering the CPU executor's docs describe). One copy launch then keeps the target's states in a buffer of their own (`draft::buf::TARGET`, a row per step token: the MTP forwards reuse the forward scratch) and stores the levels into the slot's state for `p ..= p + k` and into the tap of every block whose last position the row covered (a level before position 0 as zeros, as the CPU executor's). Target distributions and chain acceptance follow, rows without drafts sampling plainly; then the drafter rows not yet computed run depth by depth (every host position of rows without drafts, and `p + 1 ..= p + k` of drafting rows less the chain's), anchored at the kept target states or at loaded levels, whatever acceptance decided: a row past the accepted drafts writes KV at a position the host reserved for drafts, which is rewritten when that position is computed again before its block can seal; a tap stored for a rejected draft's position likewise. MTP outputs feed only their logits and KV, so nothing of theirs is stored.

**Drafts stay on the device.** Every per-step value is data in one step table of 32-bit words (`draft::Layout`): token ids, positions, KV targets, the work lists, logit rows, sampler and acceptance rows, and the copy lists; the sampler writes each depth's drafts into the table's lanes, and a row copy puts them into the next forward's token array. The copies (gathering each MTP row's anchored target state into the MTP input, the target's states into the target buffer, the levels into the state and taps, the drafts into token arrays) are one kernel, `eidola_copy_rows`, over a fixed table of buffers (`draft::buf`), every buffer and row index bounded by the kernel against the buffer's rows (`STATUS_BAD_INDEX`); the planner never lets two items of one launch overlap. The table is uploaded once and the read-back (the status word, every drafting row's tokens and count, every plain row's token) is the step's one synchronization.

**The drafter group** (`KvLayout::Planar`): a sliding window of the MTP layers' KV, `KvRole::Drafter` in the spec, after the target groups. Each depth has a K plane and a V plane of position rows (row `b × B + o` is position `o` of block `b`), so its attention pages are single positions and a request lists exactly the positions a query sees: depth `d` has no KV below position `d + 1`, which a block's first page would otherwise expose to the softmax. The KV write goes straight to a plane row (`eidola_qkv_rope_kv` with block 0 and the row as the slot); attention reads with independent K and V page strides (`AttnLayer`). Every block also holds a **boundary tap**, `k` f32 rows of the hidden size (levels `0 .. k` at the block's last position: the target's states at its last `k` positions) in a buffer beside the planes; `Zero` and `Copy` of a drafter block cover its rows in every plane and its tap. Block bytes count the tap (`GroupGeometry::block_bytes`), so the node's KV budget pays for it.

**Per-slot state** holds every depth's level at each of the `k + 1` positions a step can leave the slot at (`p ..= p + k`); the executor records per slot which positions those are and where the sequence continues from (the read-back tells it), and the next step loads entry `c - 1 - p` when the slot continues from `c - 1`, else the tap of the block ending at `c - 1` (a fresh slot after a prefix hit or a resume: the host resumes only at block boundaries). `ResetSlot` scrubs the state and forgets the record.

**The MTP forward** (`GpuModel::launch_mtp`) reuses the target layer's launches (`layer`): `hnorm` of the gathered target states and `enorm` of the embeddings, each to BF16 rows, interleaved by one row copy into `[e ‖ h]` rows of `2 × hidden` in the FP8 activations' buffer, `eh_proj` (the BF16 GEMM of `o_proj`'s shape) into the residual stream, then the sliding attention block over this depth's planes, the dense SwiGLU, and the layer's own final norm over every row; logits through the shared head when a draft is taken. No kernel was added for it.

**What is not drafted.** A row with more than one host token never drafts (the serving core gives drafts only to decode rows; an executor asked otherwise panics). `record_all_logits` and `capture_layers` are not recorded while drafting. `record_drafts` keeps every drafted step's drafts per row (`take_drafts`, through `&self`), for the tests and the acceptance reports.

## Decode graphs

**Why.** Measured on a B300 against SGLang TP1 (same box, same token ids, the eager executor): a single-request decode step took 56.6 ms against SGLang's 7.3 ms, and throughput trailed 4–9× from concurrency 1 to 64. The eager step is dominated by host work: per step it allocates the attention work lists afresh (eight device buffers per group), makes about two dozen pageable host-to-device copies, encodes every GEMM's TMA descriptors through the driver (three per CUTLASS launch, five per DeepGEMM launch: on the order of a thousand `cuTensorMapEncodeTiled` calls over 48 layers), binds the context and builds parameters for every one of several hundred launches. Under confidential computing every host-to-device transfer is bounced through encrypted staging and launches cost more, so replay is the serving path there, not an optimization.

**The audit: what kept a decode step from being captured**, and where each item stands.

| Item (eager path) | Graph path |
|---|---|
| Attention work lists allocated per step (`Attention::upload`: eight freshly allocated arrays per group) | persistent: the step table |
| Inputs copied per array (tokens, positions, two KV-target arrays and seven work-list arrays per group, logit rows, sample rows) | one copy of a prefix of the step table |
| Launch counts from the step's token count (every row-wise kernel's grid and count, GEMM M, TMA descriptors encoded per launch) | the rung's row count, fixed at capture; descriptors encoded once, at capture |
| Attention launch shape from the plan (query tile from the longest packed query run, work items, requests) | a decode row's packed run is one row × the GQA group size (16 or 8), so the tile is always 16; requests and merged rows are the rung's rows, and the grid is fixed (`PassCaps`): a sliding layer's work items are the rows, a global layer's (one per row and 1,024-key chunk) are device data its CTAs walk, at most 148 a KV head |
| Expert layout (the psum layout's row bound from the token count) | a function of the rung; the routing is device data the grouped GEMMs' scheduler reads (*Expert layouts*) |
| `memset` of the whole `x`/`h` activations (`max_tokens` rows, 256 MB at 8,192 tokens) | only the rung's rows |
| Sampler rows uploaded inside `Sampler::sample` | in the step table; `Sampler::launch_sample` launches over device rows |
| Host reads mid-step | none on either path; the per-layer copies (`capture_layers`) and `record_all_logits` force the eager path |
| Maintenance (`Zero`, `Copy`, `ResetSlot`) and changed table rows | still eager, before the step table's upload, outside the graph (small, and only when the host changed something) |
| Page lists and KV targets derived on the host from the table mirror | still: uploaded as data in the step table (*Follow-ups*) |

Already capture-safe: one non-default stream; cudarc's event tracking off (an event recorded during capture would join the graph); every launch through `cuLaunchKernelEx` (DeepGEMM's cluster attribute included); kernel attributes set when a kernel is resolved, never per launch; MoE scratch sized for the worst case so nothing is read back.

**The capture contract.** A launch sequence is replayable only if, for the executor's whole life:

1. **Every address it takes is fixed**: weights, scratch, KV pools, RoPE tables, the step table, the read-back buffer, the sampler's distribution scratch. Nothing in the sequence allocates, frees, or reallocates.
2. **Every count and shape it takes is a function of the rung alone**: rows, rows padded to four, the router's form, the expert layout and its row count, the attention tile (16), each group's grid, request slots and merged rows (`PassCaps`), logit rows (rows), sample rows (rows).
3. **Every per-step value is device data read indirectly**, in the step table: token ids, positions, per group the KV targets (block and offset) and the work list (`q_indptr`, `indptr`, `last_page_len`, `o_indptr`, the merge's `indptr`, request / query-tile / KV-tile indices and their count, page indices), FlashInfer's KV chunk size, logit rows, and sample rows (parameters, position, logit row). One host-to-device copy fills it before the launch.
4. **Nothing inside copies from the host, reads back, or synchronizes.** The step's one read-back (the rung's tokens and the status word, one buffer) comes after the graph and is the step's only synchronization.
5. **Padding rows are inert**: they write and read only the pad block, every other launch is row-local, and their tokens are never returned.
6. **The step table is rewritten only after the previous step's read-back**, which is synchronous today; a pipelined executor needs two tables (*Seam*).

`GpuModel::launch`'s and `DecodeGraphs::program`'s safety contracts state the same, and `graph.rs`'s module doc gives the padding argument.

**Ladder.** The rungs are powers of two below the largest bucket's row capacity (`min(max_seqs, max_tokens)`: one host token per decode row), each configured bucket's row capacity, and that capacity itself (`decode_ladder`). A step of `n` rows takes the smallest rung `≥ n`, so padding is under half the rung. Padding is cheap where it is large: a small decode step is bound by reading weights, a GEMM's M tile is 128 rows, and the padding rows are identical, so together they route to at most `top_k` (8) extra experts. With the node's one bucket of 64 sequences the ladder is 1, 2, 4, 8, 16, 32, 64: seven graphs.

**Memory.** All rungs share one step table, sized for the largest rung, and one read-back buffer. The table is about `rows × (11 + 7 × groups)` words, three work-item words per row and chunk (a sliding group's row is one work item; a global group's one per 1,024 positions of `max_model_len`), and the page lists: per group `rows ×` its page bound (`max_decode_pages`: every block of `max_model_len` for global attention; for a window `W`, the pages from the row's anchor, `floor((W + S − 2) / B) + 1` with `S = lcm(64, B)`). For Flash at 64 rows and a 131,072-token `max_model_len` that is about 2.2 MB, nearly all the global page list (2 MB) and work items (98 KB). Each graph's own cost is the driver's executable graph (several hundred kernel nodes and their parameters, CUTLASS's 2 KB each); `DecodeGraphs::capture_bytes` records the driver's free memory before and after each capture, and `mimo_decode_bench` prints it. One pad block per group (3.2 MB sliding, 0.4 MB global on Flash at 16 positions) is the only other memory.

**Capture at boot, not lazily.** With graphs on, `CudaExecutor::new` captures every rung, in order, after the weights: each rung's launches run once directly over an all-padding step (which exercises every launch on this device), are captured (`CU_STREAM_CAPTURE_MODE_THREAD_LOCAL`), instantiated, uploaded, and replayed once over the same step. Reasons: a capture failure refuses the boot instead of degrading a live request; no request pays a capture's latency the first time a new size appears; the steady state makes no driver allocations at all, which is what confidential computing wants; and the cost is fixed and small (rungs × three forwards at boot).

**Upload.** Arrays sit in a fixed order: the fixed-size ones first (sample rows at an even word for their `u64` seeds; the work arrays at their reservation), then each group's page list, the smallest reservation first, so a step uploads one prefix of the table, through the last group's used pages (`DecodeLayout::upload_words`). On Flash that is everything up to the global page list's used part, the global work arrays' whole reservation included.

**Numerics.** The graph is a recording of the padded launch sequence, so replaying it is bit-identical to launching that sequence directly. Against the eager path each real row computes the same bits: attention is batch-invariant (*Batch invariance*), so the padding rows beside a real row change none of its bits, and every other launch computes a row independently of the row count (row-wise kernels, GEMM rows whose reduction order does not depend on M, the expert GEMMs per row wherever the padding rows move its expert's run, the combine per token). `tests/mimo_graphs.rs` checks tokens and logits bit for bit on all three paths.

**Kill switch.** `CudaExecutorConfig::graphs` (`CudaGraphs::On` / `Off`); on the inference node `EIDOLA_ENGINE_CUDA_GRAPHS`, exactly `on` or `off`, required with the CUDA executor (the node takes no defaults) and refused with the CPU one. Keep it `off` until the GPU validation below passes, then `on`. On one executor, `CudaExecutor::set_decode_path` chooses among `Eager`, `Direct` (the padded launches without their graph, which separates a padding effect from a capture effect) and `Replay` for tests and measurement; `decode_stats` counts steps by path. A capture-bearing executor holds graph handles, which are not `Send`: build it on the thread that runs it (the node does).

**Seam.** The executor seam needs no change for replay. Overlapping host scheduling of step `N + 1` with device step `N` would split `Executor::execute` into submit and collect. It is not implemented, because it is not small: step `N + 1`'s token ids are step `N`'s samples, so they would have to be fed on the device (the step table naming, per row, a read-back slot to take its token from), the step table would need double-buffering (contract item 6), and the engine would have to plan a step before it knows the previous one's tokens (for speculation, before it knows how many were accepted). The CPU executor is untouched.

**Follow-ups.**

- **Device-side page lists.** The forward does not read the device block tables: the host derives each row's page list and KV target from its mirror and uploads them, so the upload grows with context (`rows × context / B` words for the global group). A small kernel deriving the work list and KV targets from the persistent tables and each row's `context_len` would shrink the per-step upload to `O(rows)` words, which matters most under confidential computing. It is a kernel change (with the manifest rebuilt reproducibly); nothing here needs it to be correct.
- **Prefill.** Prefill and mixed steps stay eager. A piecewise plan: capture the launches between attention calls per token bucket (row-wise kernels, GEMMs and the expert path depend only on the token count), and launch attention eagerly between the pieces, since its work list's size depends on the query lengths.
- **Speculative decode** (done; `draft.rs`). With drafting, the decode graphs above are not captured: every step runs drafter rows. A **uniform drafted decode step** (every row one host token, sampled, one draft width `w` in `0 ..= k`, at position `k` or past it, so every depth has its rows) replays a graph per rung of width `w`'s `draft_ladder`: like the decode ladder over rows that each cost `1 + w` tokens (`min(max_seqs, max_tokens / (1 + w))` per bucket). Two widths are captured (`draft_ladders`): `k`, and 0, which a step that ran short of KV is given; the serving core gives no other uniform width except when every row is trimmed alike near the model length, which runs eagerly. The serving core no longer narrows a step's width to stay within 128 tokens (`eidola-engine/AGENTS.md` → Draft width): measured on the B300 (full checkpoint, context 1,024, replay), 64 rows took 30.5 ms a step at `k = 2` (192 tokens) against 30.6 ms for 42 rows (126 tokens), and 33.3 ms at `k = 3` (256 tokens) against 31.0 ms for 32 rows (128 tokens), so the full width yields the most tokens per second (*Expert layouts*); under the per-row contiguous layout that preceded the psum one, 64 rows at `k = 2` and 3 had taken 40.9 and 44.0 ms against 14.9 ms at `k = 1` (context 80), which is what the narrowing was for. Capture runs the planner over an all-padding step: a **padding row** is a drafting decode row at position `k` whose KV writes, attention reads and drafter rows all go to the pad blocks (and their planes' rows), whose stores go to write-only level rows, and whose samples are greedy over logits row 0. A graph step stores a tap (or a write-only row) at every position `p ..= p + k`, so its copy counts do not depend on block alignment. A real step's launch list (every count, tile, grid and table offset; `draft::Launch`) must equal its rung's capture's exactly, or the step is refused; page lists and the global work lists vary inside reservations the rung's table holds (`PassCaps`; every row's verify run cut in at most two pieces at a 64-key boundary; global: every block of `max_model_len` for each piece, and a work item per piece and chunk; sliding and drafter: from the window's anchor through the drafts, for each piece). The capture contract is unchanged: the table, the level buffer, the sampler scratch and the read-back have fixed addresses, the drafts are written into and read from the table inside the graph, and the status word is cleared inside it. Graphs on and off give the same tokens (`tests/mimo_drafting.rs`).

## Expert layouts

The routed experts' two grouped GEMMs (`moe_gemm.rs`) run DeepGEMM's psum layout (`MGroupedContiguousWithPsumLayout`, its `use_psum_layout`) at every token count: the experts' runs back to back in expert order, each starting at the previous run's end rounded up to 128 rows, and the grouped layout is each expert's end row (256 words). The buffers are sized for the worst case (`engine_ops::psum_rows`: every pair plus up to 127 padding rows per expert reached, 1,024 rows for one token), so nothing is read back; the scheduler walks the 256 ends, visits only each expert's own blocks, and narrows an expert's last block to its rows rounded up to 16 (the swap-AB MMA's N, `ensure_zero_padding = false`). Its work therefore follows the routed rows.

**Capture.** A launch's arguments are the layout's row bound (from the step's token count, so a rung's), the descriptors built from it, and DeepGEMM's fixed grid of 148 persistent blocks; the routing reaches the kernel only as device data (`grouped_layout`), which the persistent scheduler reads as it walks the experts. A captured launch therefore replays correctly for any routing of the rung's rows: the bound holds every placement of them (`psum_rows_hold_the_worst_placement`).

**What a step's experts cost.** Each expert a step reaches costs its 32 blocks of N (its whole weights streamed through the tensor cores) whatever its row count, so the GEMMs' time follows the number of experts reached, not the tokens. DeepGEMM's masked layout (`[256][M][K]`, a count per expert), which ran batches of at most 128 tokens until the psum layout took them too, visits exactly the same blocks for the same routing, but always 128 rows wide; on the B300 the psum layout's gate/up and down were 9-13 % faster per layer at 16 to 128 tokens (synthetic routing reaching about every expert: 260 against 297 µs at 16 tokens, 595 against 652 µs at 128). Neither layout has a per-step hint: the instances are built ahead of time with one tile configuration (DeepGEMM's own host heuristics also fix it for every M-grouped GEMM), M is the layout's bound, and the grid is fixed. So a single decode row added to an extend can only add the experts it reaches, at most `top_k` per layer: in a mixed step of one decode row beside a 16- or 64-token extend of fixed synthetic ids (`mixed_bench`), the masked GEMM's median launch went from 48.7 to 91.1 µs and from 62.3 to 145 µs, with the same 94 launches of the same grid and every other kernel within 0.04 ms a step. The extra time can only be extra blocks, which only experts the step newly reaches add (inferred: the per-expert counts were not read back, and at 64 tokens the growth is more than eight new experts per layer explains from the extend's own cost, so the extend's routing may itself move with its token ids, which shift by one beside the row). The psum layout runs the same blocks narrower, so it can only shrink that; with real traffic a step's rows already spread over most experts.

DeepGEMM's per-row contiguous layout (`grouped_layout[row]`, -1 for padding) is not used: on SM100 its scheduler computes every 128-row block of M, padding blocks included (against group 0's weights; the skip it has is SM90-only), so a step of 129 to 512 tokens ran 263 to 286 full blocks per GEMM whatever the routing. That was the step-time cliff past 128 tokens: on the B300 a 256-token extend took 44.3 ms against 19.1 ms for 128 tokens, and 64 decode rows drafting two tokens 41 ms against 15 ms drafting one, with the gate/up GEMM at 308-476 µs per layer even on all-padding steps that route to 8 experts.

`eidola_moe_permute` writes the layout: one block up to 5,120 pairs (640 tokens; `PERMUTE_ONE_BLOCK_PAIRS` records the measured crossover), else one block per 512 pairs (at most 128, `permute_grid`), each with per-warp shared-memory histograms of its contiguous run. Above one block, `eidola_moe_permute_count` (the same grid) first writes every block's per-expert counts to the model's `permute` scratch (`PERMUTE_SCRATCH_WORDS`), and the placement reads each expert's counts of every block (the expert's total, and its pairs in the blocks before); every block scans the runs into the same starts, and each warp places its eighth of its block's run in order, 32 at a time (`__match_any_sync` ranks), so pairs keep their order within an expert. No block waits for another: the counts cross blocks only at the boundary between the two launches, so nothing assumes the grid is resident at once, and since the count launch writes every word the placement reads, nothing carries from one step (or graph replay) to the next. Up to 5,120 pairs (every decode rung, and prefill chunks to 640 tokens) it is the one placement launch, reading no scratch. Its host form is `engine_ops::expert_placement`; the unit tests emulate DeepGEMM's psum scheduler over it (every routed row in exactly one computed block of its own expert, no block overlapping another or past the bound, exactly `ceil(count / 128)` blocks per expert), emulate the kernel's block and warp cuts and per-block prefix against it at every grid the host picks and at others leaving short and empty runs, and `tests/mimo_moe_ops.rs` compares the kernel with it word for word, from one block to the most and past it (32,768 tokens).

**Numerics.** Each real row is computed from the same A row, scales and weights in the same K order as under the masked layout (and, above 128 tokens, the per-row contiguous one); only which rows share a block, and the MMA's N on an expert's last block, differ. Every real row's output is expected to be bit-identical to theirs: when the psum layout replaced the contiguous one above 128 tokens, the logprobs of 38 eval prompts (14,702 positions) were byte-identical, and in `tests/mimo_moe_gemm.rs` the psum GEMM's worst relative errors equalled the masked GEMM's to every printed digit. The same argument makes a padded graph step bit-identical to its eager run, where the padding rows move an expert's run and widen its last block (`tests/mimo_graphs.rs` and `tests/mimo_drafting.rs` check it).

## Batch invariance

**The decision.** Attention is batch-invariant, unconditionally: it is the executor's only attention path, with no flag and no fallback. A request's output must not depend on the requests it shares a step with (isolation); determinism follows. Every other launch already computed a row from that row alone, in a fixed order (row-wise kernels, GEMM rows whose reduction does not depend on M, the expert GEMMs per row whatever the layout: *Expert layouts*, both router forms: `eidola-engine-kernels/AGENTS.md`); attention did not, in two ways. The query tile (16, 64 or 128 rows, chosen per step from the longest packed query run) also chose the KV shape: four KV warps over 128-key tiles at 16 rows, one warp over 128-key tiles at 64, one over 64-key tiles at 128, so a decode row beside a prefill or inside a verify run reduced its softmax in another order. And a sliding layer's tiles started at its query tile's first row's window, so a row's tile boundaries moved with the rows it shared a tile with. What the seam guarantees as a result, and what it does not, is the serving core's determinism contract (`eidola-engine/AGENTS.md`): bit for bit on one kernel build and one kind of device, whatever the batch, chunking, cache state or graph path; not timing, not seeded sampled rows across draft widths, not across builds, images or devices.

**The structure** (`attention.rs`, `eidola-engine-kernels/csrc/flashinfer_fa2_sink_paged.cu`):

- **One reduction shape.** Every instance reduces with one KV warp over 64-key tiles (`KV_TILE`). The query tile is kept for speed (16 rows for decode, 64 and 128 for longer runs, by the same rule as before): within one KV shape every query fragment runs the same code, so it does not change a row's arithmetic, given the next rule.
- **Query tiles inside one KV tile.** A CTA walks KV tiles up to the one its query tile's *last* row reaches, so a row whose tile mates reach further meets fully masked KV tiles past its own last one. That is not an exact no-op: after every KV tile FlashInfer rescales a row's state by `exp2(m_prev · s − m · s)`, which `-use_fast_math` contracts into a fused multiply-add, so an unchanged maximum rescales by `exp2` of the product's rounding error, which is not always 1. `HostPlan::new` therefore cuts every request at multiples of 64 of its query positions, counted from its first listed page (absolute for global layers, the anchor's phase for sliding ones): every query tile lies inside one KV tile, and every row's walk ends at its own last KV tile. Fully masked KV tiles *before* a row's first visible key are exact (its state is still empty and the rescale is `exp2(−∞) = 0`). On the B300 the first build without this cut changed every logit after a prefill chunk that started off a 16-key boundary (chunks of 300, 63 or 65, or a step budget shared with other requests), by at most 2.6e-2; chunks starting on one were exact, because 8- and 16-row query tiles from such a start never cross a 64-key boundary. A prefill chunk of `n` queries costs at most one more partial query tile per 64 keys.
- **Anchored sliding tiles** (`Reduction::Anchored`). A sliding request lists its pages from an anchor: the layer's first position with KV (0 for a target layer, `d + 1` for MTP depth `d`) plus a multiple of 64 positions (and of the page size: `lcm(64, B)`), the largest at or below its first query's first visible position (`Reduction::kv_start`). The kernel's `AnchoredSink` variant starts every query tile's keys at a multiple of 64 from there and masks each row's true window per key, so a row's tile boundaries are absolute. Pages wholly before the first query's window are listed as `MASKED_PAGE`, the null block, which nothing writes (it reads as zeros): every key there is masked, so its key never reaches a row, its probability is exactly 0 and a zero value adds exactly 0; and blocks the serving core has already released behind the window are never read. The drafter's planar pages are the null block's first row likewise.
- **A fixed split of global keys** (`Reduction::Split`). A global row's keys are split at absolute multiples of 1,024 positions (`SPLIT_KEYS`), each chunk a work item writing a partial state (a BF16 output and an f32 log-sum-exp per query head), and FlashInfer's `PersistentVariableLengthMergeStatesKernel` merges a row's partials in chunk order (its grouping of index sets depends only on their count, a function of the row's position). The cut at every 64 keys of query positions is a cut at every 1,024, so a row at `p` merges exactly chunks `0 ..= p / 1,024` and every row of a work item sees at least one key of its chunk (no partial is ever fully masked). The sink is added to chunk 0's state only (`kv_tile_idx == 0`), so the merge carries it into each row exactly once. Global layers' pages always start at position 0.
- **Work items walked by fixed grids.** Every instance walks its work list from its block index in steps of the grid up to a count it reads from device memory (`AttnParams::work_items`). An eager launch's grid is its work items; a captured one's is fixed by the rung (`PassCaps`): a sliding layer's work items are its rows, a global layer's (one per row and chunk, growing with the context) are device data walked by at most 148 CTAs a KV head (`PERSISTENT_CTAS`). A work item computes the same bits whichever CTA runs it.
- **Partial rows and passes.** Split attention's partial rows live in one scratch of `split_partial_rows` rows: the most tokens a captured step holds (`min(max_seqs × (1 + k), max_tokens)` of the last bucket) times the chunks of a `max_model_len` sequence, so a rung's global work list is always one pass. An eager step whose partial rows outgrow it (a long prefill chunk at a long context) runs in passes over contiguous runs of query rows, each an attention launch and a merge; how a step is cut into requests and passes changes no row's reduction. On Flash at 64 seats, `k = 3` and 131,072 positions the scratch is 32,768 rows of 16,640 bytes, 545 MB (`eidola_common::engine_deployment::split_partial_rows`, in the device reserve).
- **Graph reservations.** A rung reserves, per group, its request slots (a drafted row's verify run may be cut in two at a 64-key boundary, so two a row when a row has more than one query), work items, pages and partial rows (`PassCaps`); `HostPlan::padded` fits a step's plan into them, the request arrays padded with empty requests, and refuses one that does not fit. A sliding row's page bound grows by the anchor (`Reduction::max_pages`: 12 pages a decode row at a window of 128 and pages of 16, against 9), and every row with a second piece lists its pages twice.

**Price.** Measured on the B300 with a bench of these structures beside the previous ones (per-layer attention, scaled to Flash's 9 global and 39 sliding layers): attention went from 0.883 to 1.046 ms a decode step for one row at context 4,101, 1.490 to 1.784 ms for 64 rows, 5.70 to 6.71 ms for a mixed step of 64 decode rows and a 364-token prefill, and 13.85 to 16.78 ms for a 2,048-token prefill after 4,096 positions. Weighted by the share of decode and mixed steps in a tool-loop workload that is an expected throughput cost of about 2.6 % at concurrency 64, 2.5 % at 32 and 1.9 % at 1; real tool-loop mixed steps carry about 570 prefill tokens rather than 364, so 64 is probably nearer 3.2 %. Not in that bench: the persistent walk of a captured global launch (expected neutral: 592 CTAs fill the part as the old grids did) and passes (only when a step's partial rows outgrow the scratch). Measured end to end on the B300 (tool loop, against the previous engine, before the 64-key cut): without drafting 0.9 %, 3.0 % and 4.6 % at concurrency 1, 32 and 64 (mixed steps 54.75 against 52.02 ms at 64, decode steps 17.44 against 17.25), with three drafts 1.9 % and 3.6 % at 32 and 64. The cost is mostly in mixed steps, whose prefill rows at long contexts now pay the global split (partial rows written and merged, nine merge launches a step) where they had one 128-key-tile pass; re-measure after the cut, which adds at most one partial query tile per 64 keys. The alternatives measured with it: one KV warp without the split cost 11.8 % at one row (decode at long contexts loses its KV parallelism); four KV warps everywhere cost 6.5-7.6 % at 32-64 rows (prefill pays for the striping); a split at 512 keys cost 3.0 % at 64 rows, at 2,048 keys 5.3 % at one row.

## Numerics

Bit equality with the f32 reference is not a goal for the kernels; the GPU's divergence must be explained by its quantization recipe, and is measured, not assumed:

- **Sampler**: bit-identical to `eidola-engine::sampling` (probabilities and tokens, every filter, every stream, chain acceptance) given equal logits.
- **Kernels** (synthetic inputs vs host references over the same quantized operands): RMSNorm 1 BF16 ulp; FP8 GEMM BF16 output rounding (3.9e-3 relative); BF16 GEMM ≤ 5.6 f32 ulp of Σ|terms|; DeepGEMM 3.9e-3 relative (BF16 out); attention ≤ 2.7e-3 absolute on values in [-1, 1] (FA2 rounds probabilities to BF16).
- **Model** (truncated real checkpoint, layers 0/1/2/5, 256 real tokens): residual stream relative L2 2.5e-3 → 1.2e-2 across the four layers; logits top-1 96.9 %, KL mean 8.6e-4. The f32 reference with the executor's quantization points emulated (`tests/mimo_qref/`) diverges from the f32 reference by the same amount (top-1 96.9 %, KL 8.9e-4), and the GPU sits within KL 2.2e-4 of that emulation: the divergence is the activation-quantization recipe. Chunked and unchunked prefill agree to KL 2.6e-5; decode steps agree with the reference (8/8 top-1, KL 4e-4).
- **Full Flash** (all 48 layers, the same 256 tokens): logits top-1 99.6 %, KL mean 5.8e-3 against f32; the quantization emulation alone gives 99.2 % / 4.7e-3, and the GPU is within KL 1.1e-3 of it. Against the vendor serving path (SGLang TP1 with DeepGEMM MoE and FA4 attention, same box, same token ids) on the model's own continuations (1,094 positions), top-1 agreement is GPU vs f32 98.9 %, SGLang vs f32 99.2 %, GPU vs SGLang 98.8 %. Only top-20 log-probabilities were kept for these pairs, which bounds KL from below but does not give it, so no KL is stated for them. Quality is equal: GSM8K (first 200, no thinking, greedy) 193/200 for both, a 40-case tool-call suite 39/40 for both with the expected arguments checked as a subset, and 37/40 for both under exact argument matching (the same three searches fail for both: each adds a `max_results` nobody asked for).
- **Batch-invariant.** A row's logits are the same bits whatever else is in its step and however its sequence was chunked (*Batch invariance*): a decode row alone and beside a prefill, a prefix copied and recomputed, a prefill chunked and whole, a decode step and the prefill that held the position, all bit for bit (`tests/mimo_executor.rs`, `tests/mimo_real_flash.rs`, `tests/mimo_invariance.rs`).
- **Drafting.** The MTP layers run through the same kernels and quantization recipe as the target's (FP8 QKV and SwiGLU, BF16 `o_proj` and `eh_proj`, FA2 over one-position pages), so drafts carry the GPU's tolerance: a greedy draft may differ from the CPU executor's where the drafter's logits are within the measured margin. Greedy speculation never changes greedy output: acceptance takes the target's argmax, and the verify pass computes each position's logits bit for bit as a decode step does, so drafted and undrafted greedy runs are identical at every width (`tests/mimo_drafting.rs`). Before the attention was batch-invariant they were not: on the full checkpoint (240 eval prompts, 256 tokens, greedy) they differed in 145, 157 and 160 completions at `k` = 1, 2, 3, at near-ties of a median 0.15 logits. Seeded sampled rows are equal across runs at one draft width, not across widths (the acceptance and residual streams are not the sample stream). Acceptance itself (the sampler's draws, `chain_accept`, the residual) is bit-exact against `eidola-engine::sampling` given equal logits.
- **Acceptance** (full checkpoint, 240 prompts, under the earlier chained convention: depth `d` fed depth `d - 1`'s output at RoPE `s - 1`), per draft: `k = 1` accepted 0.936 of first drafts (1.94 tokens a step, 183 tokens/s for one row against 113 undrafted); `k = 2` 0.934 / 0.227; `k = 3` 0.934 / 0.227 / 0.003, and `MtpHidden::PreNorm` 0.940 / 0.169 / 0.005. The first draft (depth 0) is the same function under both conventions, so its rate stands; the second and third are to be re-measured under the anchored one (*GPU validation of drafting*).

## DeepGEMM SM count

DeepGEMM's persistent scheduler takes the SM count as a template argument and uses it as the grid stride, so an instance is correct only when launched with exactly that many blocks on a part with at least that many SMs. The built instances use 148, which equals the B300's count. `ops::deepgemm_grid` launches with the instance's count (`DEEPGEMM_INSTANCE_SMS`, checked against the template argument in every manifest symbol by a unit test) and refuses a device with fewer SMs; a part with more runs correctly on 148 of them. A part with a different count that needs every SM gets its own instance in the kernel build.
