# eidola-engine-cuda

The CUDA executor for the MiMo-V2.6 engine: the serving core's `Executor` on one Blackwell GPU, running the kernels `eidola-engine-kernels` builds ahead of time, through the CUDA driver API. It is held to the seam contract (`eidola-engine/src/executor.rs`, normative) and diffed against the CPU reference executor and the model crate's f32 reference forward. AGPL-3.0-only. Workspace conventions live in the root `AGENTS.md`.

| Module | Contents |
|---|---|
| `executor.rs` | `CudaExecutor`, `CudaExecutorConfig`: the seam (maintenance, tables, forward, sampling), contract checks. |
| `draft.rs` | Speculative decoding: the drafted step's planner, its step table's layout and packing, the launch list and its runtime, drafted-step graphs (`DraftGraphs`, `draft_ladder`), `MtpHidden`. |
| `graph.rs` | Decode-graph replay: the kill switch (`CudaGraphs`), the rung ladder, padding, the step table's layout and packing, capture and replay. |
| `model.rs` | `GpuModel` (the batched target forward and the MTP forward over the same per-layer launches), `Kernels` (every loaded kernel), KV grouping of layers, RoPE tables. |
| `weights.rs` | The checkpoint on the device in kernel layouts (no dequantization), MTP layers for the draft depth. |
| `kv.rs` | `KvStore`: KV pools per group (each with a pad block past the seam's ids; the drafter's laid out by layer, with boundary taps), device block tables with a host mirror, per-slot state, `Zero`/`Copy`/`ResetSlot`. |
| `gemm.rs` | CUTLASS FP8-blockwise and BF16 GEMMs: their `Params` built in Rust. |
| `moe_gemm.rs` | DeepGEMM FP8 × MXFP4 grouped GEMM (the psum layout): its TMA descriptors built in Rust. |
| `attention.rs` | FlashInfer FA2 sink attention: `PagedParams` mirror, the batch-invariant work lists (`Reduction`, `HostPlan`, `PassCaps`), the launch and the split's merge. |
| `sampler.rs` | The device sampler and chain acceptance (host-plan and device-side launches). |
| `engine_ops.rs` | Wrappers for our own kernels (`engine_ops.cu`), and the decode path's launch geometry (`RouterForm`, `executor_router` and its bound `ROUTER_PER_TOKEN_MAX`, the one-token form's `router_grid` and the split form's `router_scores_grid` and `router_select_grid`, `permute_grid`, `gather_grid`, `swiglu_grid` and the dense `swiglu_f32scale_grid`, `quant_grid`, `combine_grid`, `qkv_grid`, `copy_grid`). |
| `support.rs` | `check_supported` and `check_drafting`: the one model configuration the kernels can run; `Unsupported` names the field. |
| `tma.rs` | `cuTensorMapEncodeTiled` specs, CuTe's descriptor fix-up. |
| `device.rs`, `module.rs`, `launch.rs`, `ops.rs`, `bf16.rs` | Device, verified image loading and launch, argument lists, the RMSNorm smoke kernel and DeepGEMM's grid, BF16 bits. |

## Host boundary

- **Driver API only.** `cudarc` with `driver` + `dynamic-loading`, bindings pinned to CUDA 13.0 (`cuda-13000`, the R580 driver's API). No CUDA runtime, no NVRTC, nothing linked at build time: the crate builds and its tests run on a machine without CUDA. Do not enable `cudarc`'s `nvrtc` feature; `module.rs` calls `cuModuleLoadData` directly.
- **No host C++.** Every upstream kernel's launch parameters are built in Rust:
  - **CUTLASS** (`gemm.rs`): the 2048-byte `GemmUniversal::Params` (problem shape, mainloop TMA descriptors and, for the blockwise kernel, scale-factor pointers and layouts, epilogue alpha and output descriptor, the cluster-launch-control scheduler's tile counts, divisors and raster order, hardware info), field by field. Descriptors are encoded by the driver and post-processed exactly as CuTe does (bit 21 of word 1 cleared unless the first 128 KiB are dense). Pinned by `tests/cutlass_params.rs` against CUTLASS's own host path: every byte CUTLASS defines must match.
  - **DeepGEMM** (`moe_gemm.rs`): the five 2-D descriptors its host code builds (L2 promotion 256 B, packed-FP4 B as `16U4_ALIGN16B`), the `Identity` epilogue arguments, grid = the instance's SM count.
  - **FlashInfer** (`attention.rs`): `PagedParams` as a `repr(C)` struct with compile-time size and offset checks against the generated C++ (296 bytes), inside the kernels' by-value `AttnParams` (304 bytes: it and the address of the work-item count), CCCL's `fast_mod_div` reproduced for `uint_fastdiv`, and FlashInfer's work lists (a work item per request × query tile × KV chunk, a CTA walking them per KV head; *Batch invariance*). The work lists are derived on the host (`HostPlan`) with checked arithmetic: each request's pages cover exactly its KV (`(pages - 1) * page_size < kv_len <= pages * page_size`) and start where its reduction anchors them (position 0 for a split, an anchor for a window), it has 1..=`kv_len` queries, every index fits the kernel's `i32` arrays, and a plan runs only on the page size, group size and kind of layer (split or anchored) it was made for, and a split only within the partial rows its scratch holds.
- **Images only through `KernelDir`**, size and SHA-256 checked against the compiled-in manifest. `KernelDir::new` takes only a directory: no other manifest can be supplied, so nothing but the compiled-in hashes can approve bytes.
- **No silent narrowing.** Every count, stride, grid dimension and offset reaches a kernel through `narrow` (`try_from`, refused before launch) or a conversion whose range is proven beside it; the crate denies `clippy::cast_possible_truncation`, `cast_possible_wrap` and `cast_sign_loss` in every target (library, tests, examples; `[lints]` in `Cargo.toml`), so a new `as u32` does not build. The few float narrowings (log-probabilities stored as f32, an f32's exponent) carry a local `expect` with the reason.
- **Safe launch wrappers own kernels bound by image and entry.** `RmsNorm`, `Gemm` and the module-taking wrappers (`EngineOps`, `MoeGemm`, `Attention`, `Sampler`) resolve their entries through `KernelModule::bound_kernel` / `expect_image`, which refuse another image or entry, so no safe call can hand one kernel another's argument layout. A bare `Kernel` launches only through `unsafe`.
- **A resolved `Kernel` shares ownership of its loaded image** with the `KernelModule` it came from; the image is unloaded when the last of them goes, so no function handle outlives it.
- **Every driver call binds the context first.** The current context is per thread and the executor may run on a thread other than the one that loaded it. `Kernel::launch` binds its module's context, and the paths that make raw driver calls bind before them: descriptor encoding in the GEMM launches and KV maintenance. A plain launch happened to work without a current context on R580, but descriptor encoding fails with `CUDA_ERROR_INVALID_CONTEXT` (`tests/smoke.rs` launches all three from a fresh thread).
- **Every launch wrapper checks its kernel's limits on the host** and returns an error instead of launching. The checks cover divisibility (128- and 512-wide quantization groups), the alignment of every operand a kernel reads or writes in vectors (the fused QKV's buffers, strides and offsets, the gather's, both SwiGLUs' and the f32-scale quantization's rows and codes, the combine's, the placement's scratch), row and stride coverage, at most 256 experts and 8 per token, a router row of at most 4096, an expert layout holding every routed pair, whole GQA groups, a vocabulary of at most 2^20 for both sampling and acceptance, and whole rows in every array (`tests/preconditions.rs`). Device-resident indices (block ids, logit rows) are the executor's to keep in range; it builds them from the host mirror. CC 10.0 runs `sm_100a`, 10.3 runs `sm_103a`, any other 10.x runs `sm_100f`; a foreign architecture's cubin is refused, never JIT-compiled. `CudaExecutorConfig::image` can force the family image.

## The dev-only oracle

`oracle/cutlass_params.cu` is a host program that `#include`s the kernels crate's two CUTLASS translation units, so its types are the AOT kernels' types, runs CUTLASS's `to_underlying_arguments` / `get_grid_shape` / `can_implement` for a list of shapes and fake addresses, logs every `cuTensorMapEncodeTiled` call, and prints the Params bytes with a mask of the bytes CUTLASS defines (padding is found by building the struct three times over different stack contents). Its output is `tests/data/cutlass_params.jsonl`. It is compiled with any CUDA 13 toolkit and the pinned CUTLASS tree on a GPU host (descriptor encoding needs a context); the command is in its header. Never part of the engine. Regenerate it when the CUTLASS pin or either GEMM instantiation changes.

## Supported configuration

**The executor supports exactly the configuration space a real checkpoint exercises and the tests cover: no permitted-but-untested degrees of freedom.** That is MiMo-V2.6-Flash's configuration, field for field, for the whole model or any subset of its layers. `check_supported` runs before any device memory is touched and refuses everything else with `CudaError::Unsupported`, naming the field. Shapes are template arguments or compile-time constants in the kernels, so another shape would read or write out of bounds rather than fail. The scalars the kernels take at run time are held to the tested values too.

| Field | Required | Why |
|---|---|---|
| hidden size | 4096 | DeepGEMM instances, UE8M0 words, the router's staged row |
| vocabulary | 152,576 | the BF16 `lm_head` GEMM |
| dense intermediate | 16,384 | the FP8 GEMMs, f32-scale SwiGLU |
| every layer: QK / V head dims, rotated dims | 192 / 128 / 64 | FA2 instances, `eidola_qkv_rope_kv`, RoPE tables |
| every layer: query heads | 64 | one attention plan per KV group serves all its layers |
| global layers: KV heads, RoPE θ, sinks | 4, 1e7, none | as Flash |
| sliding layers: KV heads, window, RoPE θ, sinks | 8, 128, 1e4, present | as Flash |
| experts, expert intermediate | 256, 2048 | DeepGEMM's group count and instances; router and placement arrays |
| experts per token | exactly 8 | the router kernel always renormalizes, which the reference skips for one expert |
| `norm_topk_prob`, routing scale | true, 1.0 | the router kernel |
| router dtype (`moe_router_dtype`) | `bfloat16` | the loader reads the router weight as BF16, the kernel scores it in f32 |
| `attention_chunk_size` | 128 | read by no implementation; pinned so another declaration is refused, not ignored |
| epsilon, value scale | 1e-6, 0.707 | the tested values |
| per-layer attention and FFN kind (`hybrid_layer_pattern`, `moe_layer_freq`) | Flash's, by source layer: global at 0, 5, 11, 17, 23, 29, 35, 41, 47, sliding elsewhere; dense at 0, experts elsewhere | each retained layer is Flash's layer of that index |
| checkpoint layers, `keep_layers` | 48; a strictly ascending, non-empty subset | the retained model keeps the checkpoint's order, no layer twice |
| top-level KV heads, `tp_size` metadata | 4 | the fused QKV's rank-major chunk count; `num_key_value_heads` is read only as that count's fallback, so no per-layer check sees it |
| FP8 scale tiles, MXFP4 scale block | 128 × 128, 32 | the FP8 GEMMs' scale grids, DeepGEMM's SFB words |
| activation scheme | `dynamic` | activations are quantized per row at run time (`amax / 448`); a static scheme is another contract |
| BF16 modules (`ignored_layers`) | every `o_proj` (all 48 layers and the MTP decoder), nothing else | where the loader reads BF16 (`eh_proj` is stored BF16 outside the FP8 method and read as such) |
| context window (`max_position_embeddings`) | 1,048,576 | as Flash |
| `max_model_len` | at most the context window | positions past it are outside what the checkpoint declares |
| sampleable vocabulary | at most 2^20, and no more than the head | `sampling.cu`'s chunks |
| with drafting: MTP layers declared (`num_nextn_predict_layers`), draft width | 3; 1 to 3 | depth `d` is MTP layer `d` (`check_drafting`) |
| with drafting: each MTP layer | Flash's sliding geometry (8 KV heads, window 128, θ 1e4, sinks, 64 query heads, 192 / 128 / 64 dims), dense SwiGLU of 16,384, `eh_proj` BF16 `[4096, 8192]` | the drafter group, the FA2 instances, the FP8 GEMMs and the BF16 GEMM of `o_proj`'s shape |

Each field, changed alone, is refused (`support::tests`; the MTP fields only while drafting, since nothing of the MTP layers is read otherwise). Pro differs in its hidden size (6144), query heads (128), global KV heads (8), experts (384), value scale and epsilon; serving it is the multi-GPU executor's scope, not a widening of this one. Every f32 vector loaded (norms, sinks, router bias) must have exactly the model's width; the BF16 and FP8 tensors' shapes are checked likewise.

**The device is part of the configuration.** `check_device` holds every device-side requirement a retained kernel bakes in, and refuses the rest with `CudaError::Unsupported`, naming the field:

| Field | Required | Why |
|---|---|---|
| compute capability | 10.x, and a forced image this device runs (`sm_100f` on any 10.x; `sm_100a` / `sm_103a` only on their own) | the images are Blackwell datacenter code |
| opt-in shared memory per block | at least `REQUIRED_SMEM_PER_BLOCK` (231,424 bytes) | the largest launch: CUTLASS's BF16 GEMM (`o_proj`, `lm_head`), dynamic plus static |
| SM count (when any layer has experts) | at least 148 | DeepGEMM's persistent instances are compiled for 148 SMs |
| cluster launch (when any layer has experts) | supported | DeepGEMM launches 2-CTA clusters, and the router at up to 15 tokens an 8-block cluster per token |

A dense-only subset of layers needs neither of the last two. `support::tests` refuses a synthetic device missing each requirement alone; `tests/smoke.rs` reads every kernel's launch contract and static shared memory from the loaded images, and fails if the largest is not exactly `REQUIRED_SMEM_PER_BLOCK` or if anything but the expert path (DeepGEMM, the router) launches a cluster. The launch-time guards (`ops::deepgemm_grid`, the driver's own refusal) stay as defense in depth.

**Construction order is structural.** `CudaExecutor::new` checks, in order:

1. the configuration (and the MTP layers for the draft width), the sampleable vocabulary and the context;
2. the KV geometry (`GroupGeometry::validate`: every product in checked `usize`, a block within the 32-bit page stride, block ids within the `i32` tables) and the resulting `ModelSpec`;
3. the device;
4. it loads and verifies every kernel image.

Steps 1 and 2 need no device: `CudaExecutor::preflight` runs exactly them (the same code `new` runs) from the checkpoint's `config.json` and returns the `ModelSpec`, so a host can refuse a configuration on a machine without a GPU and size its KV pools from the spec's groups (the inference node does both).

Only then does it move weights. `ModelWeights::load` takes the loaded `Kernels`, so no weight can reach the device first, and a wrong device, image or kernel directory fails in about a second instead of after the checkpoint has filled the GPU (`tests/construction.rs`, whose preflight test runs without a device). Scratch sizes are computed with checked arithmetic, all of them before any allocation.

## The executor

- **Seam.** One step, validated whole before any of it takes effect: the maintenance and table updates are staged (`KvStore::stage`: checked, and the tables they lead to computed, with nothing applied), the rows are checked against those staged tables, and the forward's input against the model (`GpuModel::check_input`); only then is the staged work committed (`KvStore::commit`: memsets and device-to-device copies on the stream, dirty table rows uploaded), followed by the forward over every host token and sampling on the device over `sampleable_vocab_size`. A malformed step panics or errs with the device and the mirror as they were. Block tables live on the device and change only through the seam; the host mirror is what plans attention and checks the contract.
- **Safe entry points check their host indices.** `GpuModel::forward` runs `check_input` first: tokens inside the vocabulary, positions inside the RoPE tables, logit rows inside the step, KV targets inside their pools (never the null block), and each plan's page size, query rows and largest page against its group. `Sampler::sample` takes its rows on the host and bounds every logit row before uploading them; `chain_accept` does the same for its plan. Everything else that launches takes raw pointers and is `unsafe`. Types that carry launch indices are built only by their checking constructors: `HostPlan`'s fields are private and it carries the group and page size it was checked for (`HostPlan::new`, then `Attention::upload`, which takes nothing else), and `GpuModel` is built only by the executor, its weights and KV layout readable but not replaceable. A step's bucket must be one of the configured ladder's, exactly, or the step is refused before anything is staged.
- **Contract checks**, as in the CPU reference executor, before anything is launched: a write into a block mapped by more than one table entry, a read through an unmapped entry, positions disagreeing with `context_len`, drafts at position 0, more drafts than depths, drafts on a row that does not sample or has more than one host token (the serving core drafts only decode rows; see *Drafting*), and a drafter row with no state to continue from (neither the slot's own state at `c - 1` nor a block boundary's tap), panic.
- **Memory.** One pool per KV group, in the canonical order (global, then sliding, then the drafter's when drafting) whatever the layer selection. Each pool holds `num_blocks` blocks plus one **pad block** (`GroupGeometry::pad_block`, id `num_blocks`): outside every id the seam may name, so no table maps it and no maintenance reaches it; only padding rows of a decode graph write and read it (*Decode graphs*). Capacities are keyed by kind (`KvBlocks { global, sliding }`), never by position; a group no retained layer uses must be given no blocks. Scratch is sized from the retained layers: a dense-only selection allocates no expert buffers, an expert-only one no dense ones. Block `b` holds every layer's K `[block, kv heads, 192]` then V `[block, kv heads, 128]`, BF16, contiguous, so `Zero` and `Copy` are single ranges and paged attention addresses a layer with page stride = the whole block. Per-slot model state (`state_width`) is scrubbed by `ResetSlot`; it is empty without drafting (*Drafting*).
- **Forward** (`model.rs`): f32 residual stream; per layer RMSNorm → FP8 (f32 per-128 scales) → fused-QKV FP8 GEMM (BF16) → RoPE (host-computed tables, bit-identical to the reference's) + KV write → FA2 attention → `o_proj` BF16 GEMM with the value scale as alpha (f32) → residual; RMSNorm → dense SwiGLU (FP8 GEMMs) or experts: router top-k in f32, in the form the step's token count picks (`executor_router`; `ROUTER_PER_TOKEN_MAX`'s comment records why): up to 15 tokens one cluster launch, an 8-block cluster per token; above that two launches (every (token, expert)'s score from blocks of 8 tokens × 16 experts into a scratch buffer, then one warp per token selecting), expert-major placement (DeepGEMM's psum layout, sized for the worst case so nothing is read back: *Expert layouts*), FP8 with power-of-two per-128 scales (DeepGEMM's recipe), two grouped GEMMs, weighted combine in ascending expert order → residual. The gather launches one block per token and 512-wide word (stored into the rows of the token's pairs) and the expert SwiGLU one block per routed (token, slot) pair and 1024 elements, addressing rows through `row_of`, so their cost follows the token count rather than the layout's row bound (every pair plus up to 127 padding rows per expert reached); they leave padding rows unwritten, which reaches only padding outputs (`eidola-engine-kernels/AGENTS.md`, *The decode path's small kernels*). The fused-QKV kernel and the combine run a thread per 8 elements of a token, so neither puts a token's whole row on one block. Head: final RMSNorm of the wanted rows → BF16 → `lm_head` BF16 GEMM, f32 logits.
- **Weights** (`weights.rs`): the checkpoint must hold exactly the tensors the loader reads for the retained layers and the draft depth (`expected_tensors`: sinks only on layers with sinks; MTP layers `0..k` with `k` drafts), besides the families it skips (`SKIPPED_PREFIXES`: `visual.`, `audio_encoder.`, `speech_embeddings.`; `MTP_PREFIX`, `model.mtp.`, without drafting, and MTP layers from `k` on with it) and the unselected layers; anything else, and anything missing, is a layout error before a tensor is read (`check_layout`; under a read MTP layer an unknown tensor is refused like any other), and the loader's own reads are checked against the same set. An MTP layer is loaded like a sliding target layer with a dense FFN, plus `enorm`, `hnorm`, `final_layernorm` (f32) and `eh_proj` (BF16, as stored). Copied as stored; only scale grids are re-laid-out. The fused QKV stays rank-major with each chunk padded to whole 128-row tiles, which turns the checkpoint's per-chunk scale tiling into an ordinary grid; dense gate/up are stacked; experts' gate/up rows are stacked per expert and their E8M0 scales packed into DeepGEMM's SFB words.
- **Chain acceptance: host plans and device drafts.** `Sampler::chain_accept` takes each row's drafts and distribution rows as host values (`AcceptRow`), bounds every index the kernel derives from them (k drafts plus the bonus token within the row's output, target and draft rows within the distributions and within `u32`, draft ids within the vocabulary; `AcceptPlan`, which needs no device), and refuses two rows naming different ids for one draft distribution row (the kernel reads a draft id at its distribution's index, so a draft is the token drawn from that row and rows may share one only with the same ids), and only then uploads them into `AcceptInputs`, which nothing else writes (the tests' path). A drafted step's drafts are made on the device and never reach the host, so their ids are bounded by the kernels instead: `eidola_sample` writes no id at or past the sampleable vocabulary (it cannot produce one: every argmax and draw is below it; it would write 0 and raise `STATUS_BAD_TOKEN`), and `eidola_chain_accept` checks every draft id before reading through it (`STATUS_BAD_TOKEN`, the row ending with no tokens); a step that raises the bit fails. The row and distribution indices of a drafted step are the planner's (`Sampler::launch_accept`, `draft_step` the drafted step's row count: one depth's drafts of every row together).
- **Two paths, one launch sequence.** `GpuModel::launch` is the forward's launches from the embedding to the head, reading every per-step value through device addresses (`Indirect`); the eager path (`GpuModel::forward`) uploads its inputs into scratch and calls it, and the decode graphs record it over their step table. Without drafting, prefill and mixed steps run eagerly and pure-decode steps replay a graph when graphs are on (*Decode graphs*); with drafting every step is a drafted step (*Drafting*), uniform drafted decode steps replaying a graph.

## Drafting

`CudaExecutorConfig::draft_tokens` (`k`, 0 to 3) drafts with MiMo-V2.6-Flash's MTP layers, depth `d` served by MTP layer `d`, exactly as the CPU reference executor does (`eidola-engine-cpu/AGENTS.md` → MTP row layout, which the seam makes normative): depth `d`'s row at `s` consumes the token at `s` and the **target's** hidden state at the anchor `s - 1 - d`, uses RoPE position `s - 1 - d`, writes its KV at `s`, and predicts `s + 1`; the draft for `p + 1 + i` is depth `i`'s prediction at `p + i`, every depth anchored at `p - 1`. No depth reads another depth's output: that is the vendor's serving convention (SGLang's multi-layer MTP worker, non-chained for MiMo; the CPU AGENTS cites it), and a DeepSeek-style chain was measured to make depths 2 and 3 nearly useless on Flash (*Numerics* → acceptance). `MtpHidden` (`Normed`, the default, as vLLM and SGLang feed; `PreNorm`, as llama.cpp) chooses which of the target's states that is; acceptance on the GPU against the vendor's serving stack is what settles it (`eidola-engine-model/AGENTS.md`).

**One step, no host round trip** (`draft.rs`'s module docs give the order): every row's levels at `c - 1` are loaded (level `l` at `x` is the target's state at `x - l`), from the slot's state or a block boundary's tap; for each drafting row the depths run at `p` and along the chain (`p + 1 ..= p + i` at depth `i`, every row anchored at or before `p - 1`, so on loaded levels), each depth's logits at `p + i` sampled on the device into draft `i + 1` (`Stream::Draft`, the argmax for greedy rows); the target runs **once** over every row's host tokens and drafts (a drafting row has one host token, so nothing its drafter needs comes from this step: this is the one-pass ordering the CPU executor's docs describe). One copy launch then keeps the target's states in a buffer of their own (`draft::buf::TARGET`, a row per step token: the MTP forwards reuse the forward scratch) and stores the levels into the slot's state for `p ..= p + k` and into the tap of every block whose last position the row covered (a level before position 0 as zeros, as the CPU executor's). Target distributions and chain acceptance follow, rows without drafts sampling plainly; then the drafter rows not yet computed run depth by depth (every host position of rows without drafts, and `p + 1 ..= p + k` of drafting rows less the chain's), anchored at the kept target states or at loaded levels, whatever acceptance decided: a row past the accepted drafts writes KV at a position the host reserved for drafts, which is rewritten when that position is computed again before its block can seal; a tap stored for a rejected draft's position likewise. MTP outputs feed only their logits and KV, so nothing of theirs is stored.

**Drafts stay on the device.** Every per-step value is data in one step table of 32-bit words (`draft::Layout`): token ids, positions, KV targets, the work lists, logit rows, sampler and acceptance rows, and the copy lists; the sampler writes each depth's drafts into the table's lanes, and a row copy puts them into the next forward's token array. The copies (gathering each MTP row's anchored target state into the MTP input, the target's states into the target buffer, the levels into the state and taps, the drafts into token arrays) are one kernel, `eidola_copy_rows`, over a fixed table of buffers (`draft::buf`), every buffer and row index bounded by the kernel against the buffer's rows (`STATUS_BAD_INDEX`); the planner never lets two items of one launch overlap. The table is uploaded once and the read-back (the status word, every drafting row's tokens and count, every plain row's token) is the step's one synchronization.

**The drafter group** (`KvLayout::Planar`): a sliding window of the MTP layers' KV, `KvRole::Drafter` in the spec, after the target groups. Each depth has a K plane and a V plane of position rows (row `b × B + o` is position `o` of block `b`), so its attention pages are single positions and a request lists exactly the positions a query sees: depth `d` has no KV below position `d + 1`, which a block's first page would otherwise expose to the softmax. The KV write goes straight to a plane row (`eidola_qkv_rope_kv` with block 0 and the row as the slot); attention reads with independent K and V page strides (`AttnLayer`). Every block also holds a **boundary tap**, `k` f32 rows of the hidden size (levels `0 .. k` at the block's last position: the target's states at its last `k` positions) in a buffer beside the planes; `Zero` and `Copy` of a drafter block cover its rows in every plane and its tap. Block bytes count the tap (`GroupGeometry::block_bytes`), so the node's KV budget pays for it.

**Per-slot state** holds every depth's level at each of the `k + 1` positions a step can leave the slot at (`p ..= p + k`); the executor records per slot which positions those are and where the sequence continues from (the read-back tells it), and the next step loads entry `c - 1 - p` when the slot continues from `c - 1`, else the tap of the block ending at `c - 1` (a fresh slot after a prefix hit or a resume: the host resumes only at block boundaries). `ResetSlot` scrubs the state and forgets the record.

**The MTP forward** (`GpuModel::launch_mtp`) reuses the target layer's launches (`layer`): `hnorm` of the gathered target states and `enorm` of the embeddings, each to BF16 rows, interleaved by one row copy into `[e ‖ h]` rows of `2 × hidden` in the FP8 activations' buffer, `eh_proj` (the BF16 GEMM of `o_proj`'s shape) into the residual stream, then the sliding attention block over this depth's planes, the dense SwiGLU, and the layer's own final norm over every row; logits through the shared head when a draft is taken. No kernel was added for it.

**What is not drafted.** A row with more than one host token never drafts (the serving core gives drafts only to decode rows; an executor asked otherwise panics). `record_all_logits` and `capture_layers` are not recorded while drafting. `record_drafts` keeps every drafted step's drafts per row (`take_drafts`, through `&self`), for the tests and the acceptance reports.

## Decode graphs

**Why.** Measured on a B300 against SGLang TP1 (same box, same token ids, the eager executor): a single-request decode step took 56.6 ms against SGLang's 7.3 ms, and throughput trailed 4–9× from concurrency 1 to 64. The eager step is dominated by host work: per step it allocates the attention work lists afresh (eight device buffers per group), makes about two dozen pageable host-to-device copies, encodes every GEMM's TMA descriptors through the driver (three per CUTLASS launch, five per DeepGEMM launch: on the order of a thousand `cuTensorMapEncodeTiled` calls over 48 layers), binds the context and builds parameters for every one of several hundred launches. Under confidential computing every host-to-device transfer is bounced through encrypted staging and launches cost more, so replay is the serving path there, not an optimization.

**The audit: what kept a decode step from being captured**, and where each item stands.

| Item (eager path) | Graph path |
|---|---|
| Attention work lists allocated per step (`Attention::upload`: eight freshly allocated arrays per group) | persistent: the step table |
| Inputs copied per array (tokens, positions, two KV-target arrays and seven work-list arrays per group, logit rows, sample rows) | one copy of a prefix of the step table |
| Launch counts from the step's token count (every row-wise kernel's grid and count, GEMM M, TMA descriptors encoded per launch) | the rung's row count, fixed at capture; descriptors encoded once, at capture |
| Attention launch shape from the plan (query tile from the longest packed query run, work items, requests) | a decode row's packed run is one row × the GQA group size (16 or 8), so the tile is always 16; requests and merged rows are the rung's rows, and the grid is fixed (`PassCaps`): a sliding layer's work items are the rows, a global layer's (one per row and 1,024-key chunk) are device data its CTAs walk, at most 148 a KV head |
| Expert layout (the psum layout's row bound from the token count) | a function of the rung; the routing is device data the grouped GEMMs' scheduler reads (*Expert layouts*) |
| `memset` of the whole `x`/`h` activations (`max_tokens` rows, 256 MB at 8,192 tokens) | only the rung's rows |
| Sampler rows uploaded inside `Sampler::sample` | in the step table; `Sampler::launch_sample` launches over device rows |
| Host reads mid-step | none on either path; the per-layer copies (`capture_layers`) and `record_all_logits` force the eager path |
| Maintenance (`Zero`, `Copy`, `ResetSlot`) and changed table rows | still eager, before the step table's upload, outside the graph (small, and only when the host changed something) |
| Page lists and KV targets derived on the host from the table mirror | still: uploaded as data in the step table (*Follow-ups*) |

Already capture-safe: one non-default stream; cudarc's event tracking off (an event recorded during capture would join the graph); every launch through `cuLaunchKernelEx` (DeepGEMM's cluster attribute included); kernel attributes set when a kernel is resolved, never per launch; MoE scratch sized for the worst case so nothing is read back.

**The capture contract.** A launch sequence is replayable only if, for the executor's whole life:

1. **Every address it takes is fixed**: weights, scratch, KV pools, RoPE tables, the step table, the read-back buffer, the sampler's distribution scratch. Nothing in the sequence allocates, frees, or reallocates.
2. **Every count and shape it takes is a function of the rung alone**: rows, rows padded to four, the router's form, the expert layout and its row count, the attention tile (16), each group's grid, request slots and merged rows (`PassCaps`), logit rows (rows), sample rows (rows).
3. **Every per-step value is device data read indirectly**, in the step table: token ids, positions, per group the KV targets (block and offset) and the work list (`q_indptr`, `indptr`, `last_page_len`, `o_indptr`, the merge's `indptr`, request / query-tile / KV-tile indices and their count, page indices), FlashInfer's KV chunk size, logit rows, and sample rows (parameters, position, logit row). One host-to-device copy fills it before the launch.
4. **Nothing inside copies from the host, reads back, or synchronizes.** The step's one read-back (the rung's tokens and the status word, one buffer) comes after the graph and is the step's only synchronization.
5. **Padding rows are inert**: they write and read only the pad block, every other launch is row-local, and their tokens are never returned.
6. **The step table is rewritten only after the previous step's read-back**, which is synchronous today; a pipelined executor needs two tables (*Seam*).

`GpuModel::launch`'s and `DecodeGraphs::program`'s safety contracts state the same, and `graph.rs`'s module doc gives the padding argument.

**Ladder.** The rungs are powers of two below the largest bucket's row capacity (`min(max_seqs, max_tokens)`: one host token per decode row), each configured bucket's row capacity, and that capacity itself (`decode_ladder`). A step of `n` rows takes the smallest rung `≥ n`, so padding is under half the rung. Padding is cheap where it is large: a small decode step is bound by reading weights, a GEMM's M tile is 128 rows, and the padding rows are identical, so together they route to at most `top_k` (8) extra experts. With the node's one bucket of 64 sequences the ladder is 1, 2, 4, 8, 16, 32, 64: seven graphs.

**Memory.** All rungs share one step table, sized for the largest rung, and one read-back buffer. The table is about `rows × (11 + 7 × groups)` words, three work-item words per row and chunk (a sliding group's row is one work item; a global group's one per 1,024 positions of `max_model_len`), and the page lists: per group `rows ×` its page bound (`max_decode_pages`: every block of `max_model_len` for global attention; for a window `W`, the pages from the row's anchor, `floor((W + S − 2) / B) + 1` with `S = lcm(64, B)`). For Flash at 64 rows and a 131,072-token `max_model_len` that is about 2.2 MB, nearly all the global page list (2 MB) and work items (98 KB). Each graph's own cost is the driver's executable graph (several hundred kernel nodes and their parameters, CUTLASS's 2 KB each); `DecodeGraphs::capture_bytes` records the driver's free memory before and after each capture, and `decode_bench` prints it. One pad block per group (3.2 MB sliding, 0.4 MB global on Flash at 16 positions) is the only other memory.

**Capture at boot, not lazily.** With graphs on, `CudaExecutor::new` captures every rung, in order, after the weights: each rung's launches run once directly over an all-padding step (which exercises every launch on this device), are captured (`CU_STREAM_CAPTURE_MODE_THREAD_LOCAL`), instantiated, uploaded, and replayed once over the same step. Reasons: a capture failure refuses the boot instead of degrading a live request; no request pays a capture's latency the first time a new size appears; the steady state makes no driver allocations at all, which is what confidential computing wants; and the cost is fixed and small (rungs × three forwards at boot).

**Upload.** Arrays sit in a fixed order: the fixed-size ones first (sample rows at an even word for their `u64` seeds; the work arrays at their reservation), then each group's page list, the smallest reservation first, so a step uploads one prefix of the table, through the last group's used pages (`DecodeLayout::upload_words`). On Flash that is everything up to the global page list's used part, the global work arrays' whole reservation included.

**Numerics.** The graph is a recording of the padded launch sequence, so replaying it is bit-identical to launching that sequence directly. Against the eager path each real row computes the same bits: attention is batch-invariant (*Batch invariance*), so the padding rows beside a real row change none of its bits, and every other launch computes a row independently of the row count (row-wise kernels, GEMM rows whose reduction order does not depend on M, the expert GEMMs per row wherever the padding rows move its expert's run, the combine per token). `tests/graphs.rs` checks tokens and logits bit for bit on all three paths.

**Kill switch.** `CudaExecutorConfig::graphs` (`CudaGraphs::On` / `Off`); on the inference node `EIDOLA_ENGINE_CUDA_GRAPHS`, exactly `on` or `off`, required with the CUDA executor (the node takes no defaults) and refused with the CPU one. Keep it `off` until the GPU validation below passes, then `on`. On one executor, `CudaExecutor::set_decode_path` chooses among `Eager`, `Direct` (the padded launches without their graph, which separates a padding effect from a capture effect) and `Replay` for tests and measurement; `decode_stats` counts steps by path. A capture-bearing executor holds graph handles, which are not `Send`: build it on the thread that runs it (the node does).

**Seam.** The executor seam needs no change for replay. Overlapping host scheduling of step `N + 1` with device step `N` would split `Executor::execute` into submit and collect. It is not implemented, because it is not small: step `N + 1`'s token ids are step `N`'s samples, so they would have to be fed on the device (the step table naming, per row, a read-back slot to take its token from), the step table would need double-buffering (contract item 6), and the engine would have to plan a step before it knows the previous one's tokens (for speculation, before it knows how many were accepted). The CPU executor is untouched.

**Follow-ups.**

- **Device-side page lists.** The forward does not read the device block tables: the host derives each row's page list and KV target from its mirror and uploads them, so the upload grows with context (`rows × context / B` words for the global group). A small kernel deriving the work list and KV targets from the persistent tables and each row's `context_len` would shrink the per-step upload to `O(rows)` words, which matters most under confidential computing. It is a kernel change (with the manifest rebuilt reproducibly); nothing here needs it to be correct.
- **Prefill.** Prefill and mixed steps stay eager. A piecewise plan: capture the launches between attention calls per token bucket (row-wise kernels, GEMMs and the expert path depend only on the token count), and launch attention eagerly between the pieces, since its work list's size depends on the query lengths.
- **Speculative decode** (done; `draft.rs`). With drafting, the decode graphs above are not captured: every step runs drafter rows. A **uniform drafted decode step** (every row one host token, sampled, one draft width `w` in `0 ..= k`, at position `k` or past it, so every depth has its rows) replays a graph per rung of width `w`'s `draft_ladder`: like the decode ladder over rows that each cost `1 + w` tokens (`min(max_seqs, max_tokens / (1 + w))` per bucket). Two widths are captured (`draft_ladders`): `k`, and 0, which a step that ran short of KV is given; the serving core gives no other uniform width except when every row is trimmed alike near the model length, which runs eagerly. The serving core no longer narrows a step's width to stay within 128 tokens (`eidola-engine/AGENTS.md` → Draft width): measured on the B300 (full checkpoint, context 1,024, replay), 64 rows took 30.5 ms a step at `k = 2` (192 tokens) against 30.6 ms for 42 rows (126 tokens), and 33.3 ms at `k = 3` (256 tokens) against 31.0 ms for 32 rows (128 tokens), so the full width yields the most tokens per second (*Expert layouts*); under the per-row contiguous layout that preceded the psum one, 64 rows at `k = 2` and 3 had taken 40.9 and 44.0 ms against 14.9 ms at `k = 1` (context 80), which is what the narrowing was for. Capture runs the planner over an all-padding step: a **padding row** is a drafting decode row at position `k` whose KV writes, attention reads and drafter rows all go to the pad blocks (and their planes' rows), whose stores go to write-only level rows, and whose samples are greedy over logits row 0. A graph step stores a tap (or a write-only row) at every position `p ..= p + k`, so its copy counts do not depend on block alignment. A real step's launch list (every count, tile, grid and table offset; `draft::Launch`) must equal its rung's capture's exactly, or the step is refused; page lists and the global work lists vary inside reservations the rung's table holds (`PassCaps`; every row's verify run cut in at most two pieces at a 64-key boundary; global: every block of `max_model_len` for each piece, and a work item per piece and chunk; sliding and drafter: from the window's anchor through the drafts, for each piece). The capture contract is unchanged: the table, the level buffer, the sampler scratch and the read-back have fixed addresses, the drafts are written into and read from the table inside the graph, and the status word is cleared inside it. Graphs on and off give the same tokens (`tests/drafting.rs`).

## Expert layouts

The routed experts' two grouped GEMMs (`moe_gemm.rs`) run DeepGEMM's psum layout (`MGroupedContiguousWithPsumLayout`, its `use_psum_layout`) at every token count: the experts' runs back to back in expert order, each starting at the previous run's end rounded up to 128 rows, and the grouped layout is each expert's end row (256 words). The buffers are sized for the worst case (`engine_ops::psum_rows`: every pair plus up to 127 padding rows per expert reached, 1,024 rows for one token), so nothing is read back; the scheduler walks the 256 ends, visits only each expert's own blocks, and narrows an expert's last block to its rows rounded up to 16 (the swap-AB MMA's N, `ensure_zero_padding = false`). Its work therefore follows the routed rows.

**Capture.** A launch's arguments are the layout's row bound (from the step's token count, so a rung's), the descriptors built from it, and DeepGEMM's fixed grid of 148 persistent blocks; the routing reaches the kernel only as device data (`grouped_layout`), which the persistent scheduler reads as it walks the experts. A captured launch therefore replays correctly for any routing of the rung's rows: the bound holds every placement of them (`psum_rows_hold_the_worst_placement`).

**What a step's experts cost.** Each expert a step reaches costs its 32 blocks of N (its whole weights streamed through the tensor cores) whatever its row count, so the GEMMs' time follows the number of experts reached, not the tokens. DeepGEMM's masked layout (`[256][M][K]`, a count per expert), which ran batches of at most 128 tokens until the psum layout took them too, visits exactly the same blocks for the same routing, but always 128 rows wide; on the B300 the psum layout's gate/up and down were 9-13 % faster per layer at 16 to 128 tokens (synthetic routing reaching about every expert: 260 against 297 µs at 16 tokens, 595 against 652 µs at 128). Neither layout has a per-step hint: the instances are built ahead of time with one tile configuration (DeepGEMM's own host heuristics also fix it for every M-grouped GEMM), M is the layout's bound, and the grid is fixed. So a single decode row added to an extend can only add the experts it reaches, at most `top_k` per layer: in a mixed step of one decode row beside a 16- or 64-token extend of fixed synthetic ids (`mixed_bench`), the masked GEMM's median launch went from 48.7 to 91.1 µs and from 62.3 to 145 µs, with the same 94 launches of the same grid and every other kernel within 0.04 ms a step. The extra time can only be extra blocks, which only experts the step newly reaches add (inferred: the per-expert counts were not read back, and at 64 tokens the growth is more than eight new experts per layer explains from the extend's own cost, so the extend's routing may itself move with its token ids, which shift by one beside the row). The psum layout runs the same blocks narrower, so it can only shrink that; with real traffic a step's rows already spread over most experts.

DeepGEMM's per-row contiguous layout (`grouped_layout[row]`, -1 for padding) is not used: on SM100 its scheduler computes every 128-row block of M, padding blocks included (against group 0's weights; the skip it has is SM90-only), so a step of 129 to 512 tokens ran 263 to 286 full blocks per GEMM whatever the routing. That was the step-time cliff past 128 tokens: on the B300 a 256-token extend took 44.3 ms against 19.1 ms for 128 tokens, and 64 decode rows drafting two tokens 41 ms against 15 ms drafting one, with the gate/up GEMM at 308-476 µs per layer even on all-padding steps that route to 8 experts.

`eidola_moe_permute` writes the layout: one block up to 5,120 pairs (640 tokens; `PERMUTE_ONE_BLOCK_PAIRS` records the measured crossover), else one block per 512 pairs (at most 128, `permute_grid`), each with per-warp shared-memory histograms of its contiguous run. Above one block, `eidola_moe_permute_count` (the same grid) first writes every block's per-expert counts to the model's `permute` scratch (`PERMUTE_SCRATCH_WORDS`), and the placement reads each expert's counts of every block (the expert's total, and its pairs in the blocks before); every block scans the runs into the same starts, and each warp places its eighth of its block's run in order, 32 at a time (`__match_any_sync` ranks), so pairs keep their order within an expert. No block waits for another: the counts cross blocks only at the boundary between the two launches, so nothing assumes the grid is resident at once, and since the count launch writes every word the placement reads, nothing carries from one step (or graph replay) to the next. Up to 5,120 pairs (every decode rung, and prefill chunks to 640 tokens) it is the one placement launch, reading no scratch. Its host form is `engine_ops::expert_placement`; the unit tests emulate DeepGEMM's psum scheduler over it (every routed row in exactly one computed block of its own expert, no block overlapping another or past the bound, exactly `ceil(count / 128)` blocks per expert), emulate the kernel's block and warp cuts and per-block prefix against it at every grid the host picks and at others leaving short and empty runs, and `tests/moe_ops.rs` compares the kernel with it word for word, from one block to the most and past it (32,768 tokens).

**Numerics.** Each real row is computed from the same A row, scales and weights in the same K order as under the masked layout (and, above 128 tokens, the per-row contiguous one); only which rows share a block, and the MMA's N on an expert's last block, differ. Every real row's output is expected to be bit-identical to theirs: when the psum layout replaced the contiguous one above 128 tokens, the logprobs of 38 eval prompts (14,702 positions) were byte-identical, and in `tests/moe_gemm.rs` the psum GEMM's worst relative errors equalled the masked GEMM's to every printed digit. The same argument makes a padded graph step bit-identical to its eager run, where the padding rows move an expert's run and widen its last block (`tests/graphs.rs` and `tests/drafting.rs` check it).

## Batch invariance

**The decision.** Attention is batch-invariant, unconditionally: it is the executor's only attention path, with no flag and no fallback. A request's output must not depend on the requests it shares a step with (isolation); determinism follows. Every other launch already computed a row from that row alone, in a fixed order (row-wise kernels, GEMM rows whose reduction does not depend on M, the expert GEMMs per row whatever the layout: *Expert layouts*, both router forms: `eidola-engine-kernels/AGENTS.md`); attention did not, in two ways. The query tile (16, 64 or 128 rows, chosen per step from the longest packed query run) also chose the KV shape: four KV warps over 128-key tiles at 16 rows, one warp over 128-key tiles at 64, one over 64-key tiles at 128, so a decode row beside a prefill or inside a verify run reduced its softmax in another order. And a sliding layer's tiles started at its query tile's first row's window, so a row's tile boundaries moved with the rows it shared a tile with. What the seam guarantees as a result, and what it does not, is the serving core's determinism contract (`eidola-engine/AGENTS.md`): bit for bit on one kernel build and one kind of device, whatever the batch, chunking, cache state or graph path; not timing, not seeded sampled rows across draft widths, not across builds, images or devices.

**The structure** (`attention.rs`, `eidola-engine-kernels/csrc/flashinfer_fa2_sink_paged.cu`):

- **One reduction shape.** Every instance reduces with one KV warp over 64-key tiles (`KV_TILE`). The query tile is kept for speed (16 rows for decode, 64 and 128 for longer runs, by the same rule as before): within one KV shape every query fragment runs the same code, so it does not change a row's arithmetic, given the next rule.
- **Query tiles inside one KV tile.** A CTA walks KV tiles up to the one its query tile's *last* row reaches, so a row whose tile mates reach further meets fully masked KV tiles past its own last one. That is not an exact no-op: after every KV tile FlashInfer rescales a row's state by `exp2(m_prev · s − m · s)`, which `-use_fast_math` contracts into a fused multiply-add, so an unchanged maximum rescales by `exp2` of the product's rounding error, which is not always 1. `HostPlan::new` therefore cuts every request at multiples of 64 of its query positions, counted from its first listed page (absolute for global layers, the anchor's phase for sliding ones): every query tile lies inside one KV tile, and every row's walk ends at its own last KV tile. Fully masked KV tiles *before* a row's first visible key are exact (its state is still empty and the rescale is `exp2(−∞) = 0`). On the B300 the first build without this cut changed every logit after a prefill chunk that started off a 16-key boundary (chunks of 300, 63 or 65, or a step budget shared with other requests), by at most 2.6e-2; chunks starting on one were exact, because 8- and 16-row query tiles from such a start never cross a 64-key boundary. A prefill chunk of `n` queries costs at most one more partial query tile per 64 keys.
- **Anchored sliding tiles** (`Reduction::Anchored`). A sliding request lists its pages from an anchor: the layer's first position with KV (0 for a target layer, `d + 1` for MTP depth `d`) plus a multiple of 64 positions (and of the page size: `lcm(64, B)`), the largest at or below its first query's first visible position (`Reduction::kv_start`). The kernel's `AnchoredSink` variant starts every query tile's keys at a multiple of 64 from there and masks each row's true window per key, so a row's tile boundaries are absolute. Pages wholly before the first query's window are listed as `MASKED_PAGE`, the null block, which nothing writes (it reads as zeros): every key there is masked, so its key never reaches a row, its probability is exactly 0 and a zero value adds exactly 0; and blocks the serving core has already released behind the window are never read. The drafter's planar pages are the null block's first row likewise.
- **A fixed split of global keys** (`Reduction::Split`). A global row's keys are split at absolute multiples of 1,024 positions (`SPLIT_KEYS`), each chunk a work item writing a partial state (a BF16 output and an f32 log-sum-exp per query head), and FlashInfer's `PersistentVariableLengthMergeStatesKernel` merges a row's partials in chunk order (its grouping of index sets depends only on their count, a function of the row's position). The cut at every 64 keys of query positions is a cut at every 1,024, so a row at `p` merges exactly chunks `0 ..= p / 1,024` and every row of a work item sees at least one key of its chunk (no partial is ever fully masked). The sink is added to chunk 0's state only (`kv_tile_idx == 0`), so the merge carries it into each row exactly once. Global layers' pages always start at position 0.
- **Work items walked by fixed grids.** Every instance walks its work list from its block index in steps of the grid up to a count it reads from device memory (`AttnParams::work_items`). An eager launch's grid is its work items; a captured one's is fixed by the rung (`PassCaps`): a sliding layer's work items are its rows, a global layer's (one per row and chunk, growing with the context) are device data walked by at most 148 CTAs a KV head (`PERSISTENT_CTAS`). A work item computes the same bits whichever CTA runs it.
- **Partial rows and passes.** Split attention's partial rows live in one scratch of `split_partial_rows` rows: the most tokens a captured step holds (`min(max_seqs × (1 + k), max_tokens)` of the last bucket) times the chunks of a `max_model_len` sequence, so a rung's global work list is always one pass. An eager step whose partial rows outgrow it (a long prefill chunk at a long context) runs in passes over contiguous runs of query rows, each an attention launch and a merge; how a step is cut into requests and passes changes no row's reduction. On Flash at 64 seats, `k = 3` and 131,072 positions the scratch is 32,768 rows of 16,640 bytes, 545 MB (`eidola_common::engine_deployment::split_partial_rows`, in the device reserve).
- **Graph reservations.** A rung reserves, per group, its request slots (a drafted row's verify run may be cut in two at a 64-key boundary, so two a row when a row has more than one query), work items, pages and partial rows (`PassCaps`); `HostPlan::padded` fits a step's plan into them, the request arrays padded with empty requests, and refuses one that does not fit. A sliding row's page bound grows by the anchor (`Reduction::max_pages`: 12 pages a decode row at a window of 128 and pages of 16, against 9), and every row with a second piece lists its pages twice.

**Price.** Measured on the B300 with a bench of these structures beside the previous ones (per-layer attention, scaled to Flash's 9 global and 39 sliding layers): attention went from 0.883 to 1.046 ms a decode step for one row at context 4,101, 1.490 to 1.784 ms for 64 rows, 5.70 to 6.71 ms for a mixed step of 64 decode rows and a 364-token prefill, and 13.85 to 16.78 ms for a 2,048-token prefill after 4,096 positions. Weighted by the share of decode and mixed steps in a tool-loop workload that is an expected throughput cost of about 2.6 % at concurrency 64, 2.5 % at 32 and 1.9 % at 1; real tool-loop mixed steps carry about 570 prefill tokens rather than 364, so 64 is probably nearer 3.2 %. Not in that bench: the persistent walk of a captured global launch (expected neutral: 592 CTAs fill the part as the old grids did) and passes (only when a step's partial rows outgrow the scratch). Measured end to end on the B300 (tool loop, against the previous engine, before the 64-key cut): without drafting 0.9 %, 3.0 % and 4.6 % at concurrency 1, 32 and 64 (mixed steps 54.75 against 52.02 ms at 64, decode steps 17.44 against 17.25), with three drafts 1.9 % and 3.6 % at 32 and 64. The cost is mostly in mixed steps, whose prefill rows at long contexts now pay the global split (partial rows written and merged, nine merge launches a step) where they had one 128-key-tile pass; re-measure after the cut, which adds at most one partial query tile per 64 keys. The alternatives measured with it: one KV warp without the split cost 11.8 % at one row (decode at long contexts loses its KV parallelism); four KV warps everywhere cost 6.5-7.6 % at 32-64 rows (prefill pays for the striping); a split at 512 keys cost 3.0 % at 64 rows, at 2,048 keys 5.3 % at one row.

## Numerics

Bit equality with the f32 reference is not a goal for the kernels; the GPU's divergence must be explained by its quantization recipe, and is measured, not assumed:

- **Sampler**: bit-identical to `eidola-engine::sampling` (probabilities and tokens, every filter, every stream, chain acceptance) given equal logits.
- **Kernels** (synthetic inputs vs host references over the same quantized operands): RMSNorm 1 BF16 ulp; FP8 GEMM BF16 output rounding (3.9e-3 relative); BF16 GEMM ≤ 5.6 f32 ulp of Σ|terms|; DeepGEMM 3.9e-3 relative (BF16 out); attention ≤ 2.7e-3 absolute on values in [-1, 1] (FA2 rounds probabilities to BF16).
- **Model** (truncated real checkpoint, layers 0/1/2/5, 256 real tokens): residual stream relative L2 2.5e-3 → 1.2e-2 across the four layers; logits top-1 96.9 %, KL mean 8.6e-4. The f32 reference with the executor's quantization points emulated (`tests/common/qref.rs`) diverges from the f32 reference by the same amount (top-1 96.9 %, KL 8.9e-4), and the GPU sits within KL 2.2e-4 of that emulation: the divergence is the activation-quantization recipe. Chunked and unchunked prefill agree to KL 2.6e-5; decode steps agree with the reference (8/8 top-1, KL 4e-4).
- **Full Flash** (all 48 layers, the same 256 tokens): logits top-1 99.6 %, KL mean 5.8e-3 against f32; the quantization emulation alone gives 99.2 % / 4.7e-3, and the GPU is within KL 1.1e-3 of it. Against the vendor serving path (SGLang TP1 with DeepGEMM MoE and FA4 attention, same box, same token ids) on the model's own continuations (1,094 positions), top-1 agreement is GPU vs f32 98.9 %, SGLang vs f32 99.2 %, GPU vs SGLang 98.8 %. Only top-20 log-probabilities were kept for these pairs, which bounds KL from below but does not give it, so no KL is stated for them. Quality is equal: GSM8K (first 200, no thinking, greedy) 193/200 for both, a 40-case tool-call suite 39/40 for both with the expected arguments checked as a subset, and 37/40 for both under exact argument matching (the same three searches fail for both: each adds a `max_results` nobody asked for).
- **Batch-invariant.** A row's logits are the same bits whatever else is in its step and however its sequence was chunked (*Batch invariance*): a decode row alone and beside a prefill, a prefix copied and recomputed, a prefill chunked and whole, a decode step and the prefill that held the position, all bit for bit (`tests/executor.rs`, `tests/real_flash.rs`, `tests/invariance.rs`).
- **Drafting.** The MTP layers run through the same kernels and quantization recipe as the target's (FP8 QKV and SwiGLU, BF16 `o_proj` and `eh_proj`, FA2 over one-position pages), so drafts carry the GPU's tolerance: a greedy draft may differ from the CPU executor's where the drafter's logits are within the measured margin. Greedy speculation never changes greedy output: acceptance takes the target's argmax, and the verify pass computes each position's logits bit for bit as a decode step does, so drafted and undrafted greedy runs are identical at every width (`tests/drafting.rs`). Before the attention was batch-invariant they were not: on the full checkpoint (240 eval prompts, 256 tokens, greedy) they differed in 145, 157 and 160 completions at `k` = 1, 2, 3, at near-ties of a median 0.15 logits. Seeded sampled rows are equal across runs at one draft width, not across widths (the acceptance and residual streams are not the sample stream). Acceptance itself (the sampler's draws, `chain_accept`, the residual) is bit-exact against `eidola-engine::sampling` given equal logits.
- **Acceptance** (full checkpoint, 240 prompts, under the earlier chained convention: depth `d` fed depth `d - 1`'s output at RoPE `s - 1`), per draft: `k = 1` accepted 0.936 of first drafts (1.94 tokens a step, 183 tokens/s for one row against 113 undrafted); `k = 2` 0.934 / 0.227; `k = 3` 0.934 / 0.227 / 0.003, and `MtpHidden::PreNorm` 0.940 / 0.169 / 0.005. The first draft (depth 0) is the same function under both conventions, so its rate stands; the second and third are to be re-measured under the anchored one (*GPU validation of drafting*).

## DeepGEMM SM count

DeepGEMM's persistent scheduler takes the SM count as a template argument and uses it as the grid stride, so an instance is correct only when launched with exactly that many blocks on a part with at least that many SMs. The built instances use 148, which equals the B300's count. `ops::deepgemm_grid` launches with the instance's count (`DEEPGEMM_INSTANCE_SMS`, checked against the template argument in every manifest symbol by a unit test) and refuses a device with fewer SMs; a part with more runs correctly on 148 of them. A part with a different count that needs every SM gets its own instance in the kernel build.
